### R-281 | area: drive-routes | parallel-safe: yes | automatable: partly

**Summary:** The seven routes that make the Drive integration reachable for the first time — `connect`, `oauth2callback`, `status`, `disconnect`, `save`, `export`, `documents` — written by two agents over disjoint files, then one security review and two rounds of remediation. **Like R-279 and R-280 this wave is inert:** no component renders any of these routes yet, so nothing a user can reach changes on this push. So this entry is not about behaviour either. It is about five things the wave proved, in descending order of what it would cost to lose them: a data-loss defect living in the SAFE branch of a data-loss-prevention prompt, which survived two fixes that were each correct about the case they aimed at; a wire test that now asserts the uploaded BYTES and not merely their declared type; three guarantees that existed only on paper and were green anyway; a mutation harness that reported sixteen kills without ever running vitest once; and the OAuth residual this flow ships with on purpose.

**THE BLOCKER, AND THE FACT THAT IT TOOK THREE ROUNDS — read the sequence, not just the fix.** Each round was correct about the case it aimed at, and the defect survived in the adjacent one.

* **Round 1.** `onConflict: "new"` — the branch a user reaches by clicking *"Save as a new Doc"*, i.e. the SAFE half of the prompt that exists to prevent data loss — called `createDoc`, whose `files.list`-by-name duplicate check **adopted** the conflicted Doc and PATCHed it. Doc names are deterministic per posting and `updateDoc` deliberately never renames, so the lookup hit the preserved file every time. Proved at route level through the real client: `"patchedFileIds": ["CONFLICTED1"], "createIssued": false`, with the response still reporting `created: true` and `fileId: "CONFLICTED1"` — the client is told a new Doc exists while the old one was destroyed. The same root cause broke AC-E13's "never PATCH a non-Doc" branch, which is also `createDoc`.
* **Why every test missed it.** `save/route.test.js` mocks `@/lib/drive/driveClient` **wholesale**, so its test *"onConflict:'new' … creates a new Doc instead of touching the conflicted one"* asserted `updateDoc` was not called **on the mock**, while the real PATCH happened inside the mocked-away `createDoc`. **A test that mocks the module it is trying to constrain cannot see through it** — it can only restate the mock. This is the general form worth carrying: whenever an assertion is about what a dependency *does*, mocking that dependency makes the test vacuous by construction, and it will stay green against a dead implementation forever.
* **Round 2** gave `createDoc` an `adopt` flag defaulting to `true` — so AM-3's duplicate guard survives untouched on the ordinary create path — and passed `adopt: false` from the conflict and replacement branches, naming the new Doc `X (new copy)`.
* **Round 3** found that the suffix **protected the wrong file**. The preserved original keeps the plain name `X`; the adopting call site composes and looks up the plain `X`; so an ordinary later save that reached the create path would find and overwrite the very Doc the user chose to preserve. Now resolved by keying on a stored file id — the durable row, or failing that the client's session-local `knownRef` — rather than on a name the app deliberately allows to diverge. The by-name lookup remains only where there is, by definition, no id for anyone to key on.

**THE RESIDUAL — it is not closed, and it is written here so nobody reads the three rounds as an all-clear.** If the Drive create succeeds but the `drive_documents` persistence write then fails, **and** the user returns in a fresh context with no stored row and no session-local reference, there is no id anywhere to key on, and the name-based fallback can still adopt and overwrite a preserved Doc. All three conditions are required. The remedy is either to persist the preserved Doc's identity, or to refuse adoption of any Doc the app cannot prove it wrote — and the latter collides head-on with the duplicate guard, which exists precisely for the no-row case. Comments at both call sites (`createDoc`'s doc comment, and `save/route.js`'s `knownRef` fallback) record this; do not delete them while the hole is open.

**THE WIRE TEST IS REAL, AND IT ASSERTS BYTES NOW.** It runs the REAL route handler against the REAL `googleapis` client with only the transport stubbed. The shape it pins is the one R-279 established and this wave now exercises through a route: `files.export` takes `mimeType` as a genuine TOP-LEVEL parameter, `files.update` does **NOT** — a misplaced key falls through to `options.params` (`googleapis-common/apirequest.js:232`) and becomes a query-string parameter, whereupon the absent `requestBody` downgrades the call to `uploadType=media` (`:213`) and the conversion target is silently stripped. **It does not throw.** Correct and defective shapes are both pinned, side by side, with the negative control asserting `requestBodyOf` is `undefined` for the body-less form. **And record the gap this wave closed:** an **EMPTY** upload previously passed all 43 save tests including the wire test, because the wire test asserted the media part's content-**TYPE** and never its content. The byte comparison now catches a wrong-but-nonempty, same-length buffer — mutating the read to `Buffer.from((await file.arrayBuffer()) && [9,9,9,9,9])` reds three tests, and the `file.size === 0` guard alone cannot catch that class at all, because the payload is neither empty nor the wrong length.

**THREE GUARANTEES THAT EXISTED ONLY ON PAPER.** Each was green, and each was worth nothing:

* **`stripSecrets` never had to fire.** Deleting the call entirely — `Response.json(stripSecrets(body), init)` → `Response.json(body, init)` — left **all 118 route tests green**, because every route picks its response fields by hand, so the strip was never the reason a secret was absent. It is now tested directly: per key, through nesting, and through array elements, with a positive control on near-miss names (`secretNote`, `tokenCount`) asserting a byte-identical round trip **so a `stripSecrets` that returns `{}` cannot satisfy the suite** — which is the failure mode a pure "no secrets present" assertion invites.
* **Disconnect's fail-loudly guarantee was discarded by its only consumer.** The route was correct and proved correct; `DriveButton.js` then ignored `res.ok` entirely and flipped to "disconnected" regardless, telling a user their Drive was disconnected while the credential survived in the database. That is **the exact `lib/gmail/gmailClient.js` `deleteTokens` defect the route was written to avoid**, re-created one layer up by the caller. A correct producer plus an indifferent consumer is a lie with extra steps; the guarantee belongs to the pair, and only a test that spans both can hold it.
* **A `.catch` that could not fire.** `saveDriveConnection` wraps its whole body in try/catch and **RETURNS** `{connection: null, error}`, so the promise **resolves** on every realistic storage failure and rejects only if something outside those try blocks throws. The token write-back's `.catch(…)` therefore logged nothing in the case it was added for, and its test passed **solely because the mock threw — a shape production cannot produce.** Both sites now handle the resolved-`{error}` case as well as the throw. Whenever a helper's contract is "returns an error field", a `.catch` on it is decoration.

**TWELVE, NOT TEN — and the count itself is the lesson.** Fifteen distinct `reason` values can reach the OAuth callback's response (five route literals, one from `lib/drive/oauthState.js`, nine from the shared `lib/oauth/state.js`). **Twelve of them had no entry in the copy table at all**, so those failures produced no user-facing message whatsoever. The security review said three near-misses plus ten missing; the remediating agent **counted rather than trusting the number it was handed** and found twelve, and the re-verifier independently confirmed 15/3/12. All twelve route to the existing `tokenUnreadable` bucket — no new copy was invented — and the guard is a membership test that enumerates the reasons **FROM SOURCE**, so a thirteenth added anywhere in those three files reds. It is proved non-vacuous by renaming a reason in `lib/oauth/state.js` that the route never spells out: exactly one test fails, and it is that one.

**A HARNESS THAT LIED, AND HOW IT WAS CAUGHT — required practice for any future mutation pass in this repo.** The re-verifier's first mutation run reported **all 16 mutations RED** and was **entirely invalid**: `execFileSync("npx.cmd", …)` never spawned on this platform, every per-mutation log was **0 bytes**, and vitest never executed once — the harness was reading a non-zero exit code as "caught". The corrections are the durable part. **(1)** Spawn `process.execPath node_modules/vitest/vitest.mjs` directly. **(2)** Classify a run whose output contains no `Test Files` line as `INVALID (runner did not run)`, never as RED. **(3)** Add a **no-op control edit per mutated file** — a comment change, run against that file's own suites — and require every one to come back GREEN before any RED is believed; eight were run here and all eight passed. **From the outside, a malformed sabotage and a test that cannot fail are indistinguishable**, and both present as a satisfying wall of kills. A mutation report without a live control set is not evidence.

**SECURITY — what holds, and the one thing that does not.** The R-277 attack and its mirror both fail, each with a mutation proving it: the user id comes only from the session and never from `state` (the payload does not even carry a userId field), the state cookie is cleared on **every** exit path including the 503, `postMessage` targets this request's exact origin and never `"*"`, and a Gmail-provider state is rejected at the Drive callback. **Not stopped, and recorded as a known limitation with its remedy: an attacker who can read an UNCONSUMED state can complete consent with their own Google account and bind the victim's app account to the ATTACKER's Drive** — the victim's documents then save into a stranger's Drive. The fix is PKCE. This is the same residual the Gmail flow already shipped with; expanding the wave to add PKCE to both providers mid-flight was deliberately declined, and it is filed rather than silently inherited.

**AC-C21's ASYMMETRY IS DELIBERATE AND FRAGILE.** `GET /api/drive/status` **alone** returns a normal 200 `{connected: false, configured: false}` when the Google client credentials are unset; the other six routes 503 `drive_unconfigured`. Status is the probe a client uses to decide whether the feature renders at all, so a 503 there would hide the feature entirely on an unconfigured deploy rather than showing a "Connect Drive" affordance. Anyone tidying the seven routes into a uniform config gate will re-break this and every test will still pass but the feature will vanish. Separately and just as load-bearing: **any Supabase error other than "no rows" maps to 503, never to "not connected"** — otherwise a user who just completed Google's consent screen is told they are not connected, and the obvious next thing they do is reconnect against a store that is still down. Both are pinned by mutation.

**WHAT IS LEFT OPEN, recorded so the mounting wave does not rediscover it.** The residual adoption path above is the one that can still lose data, under its three simultaneous conditions. `DriveButton.js` renders its disconnect-failure sentence as a component-local string with **no `aria-live` region**, so a screen-reader user who clicks Disconnect and keeps focus on the button hears nothing and sees a button still offering to disconnect — a fifth component-local copy string in a feature whose declared single source of copy is `driveMessages.js`. Two route-local oversize strings (`save/route.js:40`, `export/route.js:30`) duplicate copy the canonical table should own, which is the third recurrence of that class in this feature. And PKCE. None of these is fixed here; none of them is an oversight.
