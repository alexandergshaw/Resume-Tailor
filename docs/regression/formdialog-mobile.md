### R-303 | area: formdialog-mobile | parallel-safe: yes | automatable: partly

**Summary:** `app/components/FormDialog.js` -- the shared scaffold behind nine dialogs (AddApp, EditApp, Stage, AddCommunication, AutofillProfile, SlotReview, BatchTailor, experience/DeletePage, experience/BulkActionsBar) -- keeps `DialogContent`, not the Paper, as the scrolling region on a fullScreen phone dialog; renders a reachable "Close" control when there is no backdrop pixel and no Escape key; keeps every exit live while a save is `busy` -- Escape, the backdrop, the phone close control, AND the Cancel button itself, not just the first three -- while the submit button stays blocked; and wraps a caller's multi-button action row onto multiple lines with a visible gap between them, via the shared `WRAP_ROW_SX` contract, instead of letting wrapped rows sit flush.

**Steps:**
1. From `hello-world`, run `npx vitest run --no-file-parallelism app/components/FormDialog.mobile.test.js`.
2. Read `app/components/FormDialog.js`: the form-wrapper flex column (`:65-69`), the phone Close `IconButton` (`:87-103`), `requestClose`/`handleSubmit` (`:46-54`), and the action row's `sx={{ ...WRAP_ROW_SX, ...actionsSx }}` (`:111`, `:120`).
3. In a real browser at 375x812, with `BatchTailorDialog` open (it passes three buttons and no `actionsSx`): confirm the three buttons wrap onto at most two rows with a visible vertical gap -- no two buttons, or their focus rings, touch -- confirm `.MuiDialogActions-root`'s bottom edge stays inside the viewport, and confirm `.MuiDialogContent-root` scrolls internally (`scrollHeight > clientHeight`) when its content overflows.

**Expected:** All tests pass. Cancel is enabled and functional while the dialog is `busy` -- matching `FormDialog.js`'s own comment ("only the submit itself stays blocked"), which the code used to contradict: Cancel carried `disabled={busy}` even after Escape, the backdrop and the phone close control were all already fixed to stay live, so it was the one VISIBLE control still claiming the user could not leave. The submit button stays disabled while busy regardless (verified independently by this file's own GUARD case). The default action row's `flexWrap: "wrap"` now ships with `rowGap: 1` (8px, `theme.spacing(1)`) from `app/theme/mobileSx.js`'s shared `WRAP_ROW_SX`, rather than bare `flexWrap` with no vertical spacing -- MUI's `DialogActions` only spaces siblings horizontally (`marginLeft: 8`), so a wrapped second row used to sit flush against the first. That matters beyond cosmetics now that the app paints a keyboard focus ring (R-305): two vertically flush buttons would put each ring several pixels into its neighbour's box on Tab.

**Browser-only checks this suite cannot perform (jsdom has no layout engine)**, per `FormDialog.mobile.test.js`'s own header: the action row's real position relative to the viewport bottom, `DialogContent`'s real scroll overflow, the close control's real on-screen position at rest, and the real row count of the three-button BatchTailor row. Step 3 above is that check; run it by hand after any future change to this file.
