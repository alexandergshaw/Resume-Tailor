**THE SEAM THAT NEARLY SHIPPED UNDER A GREEN TEST — this is the centrepiece; read it before trusting any test that carries the name of the property it is meant to hold.** `saveToDrive({activeText})` exists for one reason: so the text a user is currently editing reaches the uploaded document. A test asserted exactly that, by name, and **passed. It passed only because its fixture set `entry.resultLines: []`.**

The real chain, all three links verified: `previewBlobArgs` always threaded `lines` from the stored `resultLines` and **never re-derived them from a supplied `text`** — pinned deliberately at `previewBlob.test.js:87-97`, so the wrong behaviour was not merely untested, it was *guarded*. `buildDocxFromUploadedTemplate` prefers `generatedLines` whenever there are any, falling back to splitting `text` only when that array is empty. So with a **populated** `resultLines` — which is the common case, every generated entry has one — a save carrying the draft flipped `edited` true, took the rebuild branch, and wrote the **stale pre-commit paragraphs** into the .docx. The draft reached `meta.contentHash` but not a single byte of the file. An empty-array fixture takes the fallback and cannot see any of it.

**The mechanism is the part worth keeping.** `saveDocumentPreview` sets `entry.result` and `entry.resultLines` together — but through `setTailoringMap`, an **asynchronous** React state update. The next wave's wiring calls `commitDraft()` and then `saveToDrive(...)` **synchronously in the same tick**, before that update flushes, so `entry.resultLines` is still the pre-edit array at the moment the bytes are built. `activeText` exists precisely to carry the fresh value around that lag — and the lines were being read from the stale side of it. Fixed by deriving `lines` from a divergent `text` with `normalizeResultLines(text)`, performing synchronously the identical split the state update performs moments later, so the rebuild and the eventual React state agree instead of racing.

**The pin was NARROWED, not weakened**, and the distinction is the whole difference between a fix and a deletion: the stored array is still expected when `text` is omitted or matches what is stored, and only the divergent case expects the derived value. The guarding test computes that expected value **independently** rather than by calling the module under test, and a second join test hands `previewBlobArgs`' literal return value to the real `resolveDocumentBlob` — because a hand-built args object could just as easily pin the wrong contract between two real functions.

**A TEST THAT INJECTS A STATE PROVES NOTHING ABOUT WHETHER THE APP CAN PRODUCE IT.** `deriveDriveStatus` checked `configured === null` **before** `statusCheckFailed`, and the only place that sets the flag (`:358`, the mount effect's failed `checkStatus`) leaves `configured` at its initial `null`. So the earlier branch won every time, status resolved to `"checking"`, and `DriveActions` renders `null` for `"checking"` — **a connected user whose `/api/drive/status` returned a 500 saw no Drive feature at all**, byte-identical to an unconfigured deploy, with no retry and no error. That is AC-C26 violated verbatim and `UX.md:431` describing the shipped behaviour rather than forbidding it, in a repo where `GmailButton.js:19` already carries `.catch(() => setConnected(false))` for exactly this reason. **Three tests asserted `statusFailed` behaviour by handing the value straight in** — `useDriveDocuments.test.js:52`, `DriveActions.test.js:157`, `driveMessages.test.js:50` — so all three passed against a state the product could never enter, and a mutation that stopped recording the failure at all was GREEN against 432 files. The general form: a test that constructs the input proves the function's table, never the caller's ability to reach that row. Every enum member wants one test that arrives through the real producer.

**And reordering ALONE would have introduced a new bug.** The focus listener (AC-C23's cross-tab self-heal) refreshed `configured` and `connected` but never reset `statusCheckFailed` — harmless while the flag was dead code, permanent once it was checked first. `statusFailed` would have stuck forever after a later *successful* check. The reset at `:385` is not tidying; it is the other half of the fix, and it has its own test.

**A SAVE THAT COULD HANG FOREVER, SILENTLY.** `performSave` had a `finally` but **no `catch`**, so a throw rejected out of `saveToDrive` and left the polite live region announcing *"Saving to Google Drive…"* with no rows, no alert and no leading line — permanently, and reproducibly on retry. Two reachable sources, neither exotic: `resolveDocumentBlob` hands bytes to `JSZip.loadAsync`, which throws on a corrupt or unusual .docx — reached on the *normal* path for any hand-edited document; and **`crypto.subtle` is undefined on any non-secure origin**, so every save over `http://<LAN-ip>:3000`, which is exactly how this app gets tested on a phone, hung. The currency-hash effect also lacked the `.catch` its immediate neighbour had, raising an unhandled rejection on every entry change in the same conditions. The local download path already had the right shape — `downloadDocxFiles` catches and returns a message that renders as a scope error — so the Drive path was the inconsistent one, and the fix routes the throw through that same per-scope error vocabulary. **Record how the fix is tested:** the crypto case drives `crypto.subtle` **genuinely absent** (`vi.stubGlobal("crypto", {getRandomValues})`) rather than making a mock throw, because a mock that throws proves nothing about an API that simply is not there.

**THE HASH AGREEMENT WAS PINNED BY NOTHING — in either direction, which is why it read as covered.** The content-hash tuple's *shape* was pinned. That the **stored** hash and the **compared** hash come from the **same formula** was not. Measured: changing only the sent side to `sha256Hex(text)` left all 432 files green; changing only the compare side to a divergent tuple also left all 432 green; only changing the shape on **both** sides reds. So the currency badge could have lied in either direction and nothing would have noticed — permanently reading *"differs from Drive"* after every clean save, or permanently reading *"current"* over a genuinely stale copy. **No code change was needed. The test was the fix:** save known content, read `meta.contentHash` off the FormData, and assert the hook's own `isStale`/`stale` are still false immediately afterwards — i.e. that the value the hook *sends* is the value the hook would *compare against*. A shape assertion and an agreement assertion are different tests, and only the second one is about the bug.

**MUTATION HARNESSES THAT LIED, TWICE MORE — the practice from R-281 is now mandatory, not advisory.** One reviewer's first run produced **15 INVALIDs**, and another agent's `npx` invocation silently failed on Windows with `'C:\Program' is not recognized`, writing empty logs. Standing practice, all three parts required: **(1)** treat a run whose output contains no `Test Files` line as **INVALID**, never as RED — that classification is the only thing that caught either failure; **(2)** require a **no-op control edit per mutated file** to come back GREEN before believing any RED from that file; **(3)** **scrutinise a RED before banking it.** One RED here was red for a *timing* reason and not because the property was pinned at all: a shallower hash function settled in fewer microtask hops, which let a second writer of `currentHashByScope` clobber the first. **Deferred here, with reasons, so none is mistaken for an oversight.** `useDriveDocuments.js` holds ~145 lines of pure, node-testable logic — the hash tuple, the status derivation, the download-result builders — inside a `"use client"` file, all of it already exported and already tested without jsdom; the repo rule is to extract into `lib/` rather than spend a 1000-line cap, and this should happen **before** the next change to the file rather than after. And the download path re-derives its filename with `override: ""` (`:844`) while the save path uses the entry's stored per-scope name (`:606`), so after a reload a user who renamed their résumé downloads a file named after the job posting while the Doc in Drive still carries their name — real, user-visible, a one-line fix, and nothing pins download filenames at all. **Sharpened (manual regression pass): this is not a "can", it is an "always".** `:844` reads `ref.name || driveDocName({override: "", …})`, so the re-derivation is skipped whenever `ref.name` is present — and `ref.name` is present only on a reference minted by a save in this same session (`:637`, `:649`, off the route's response body). A reference **hydrated after a reload never carries one**: `app/api/drive/documents/route.js`'s `toReference` emits exactly `{fileId, contentHash, version, webViewLink}`, and `drive_documents` has no name column for it to emit (`supabase/migrations/20260901000000_drive.sql:57-72`). So the fallback is not a fallback after a reload; it is the only branch. Every post-reload download of a renamed document mismatches, unconditionally. Same one-line fix, considerably worse odds than recorded — and note that the persisted-shape half is why "just read `ref.name`" is not the fix on its own.
