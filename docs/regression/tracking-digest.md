### R-223 | area: tracking-digest | parallel-safe: yes | automatable: partly

**Summary:** The tracking table carries a "Company & role" column holding a researched digest of what the job posting does NOT tell you — auto-filled for a newly tracked row, filled on demand by a Research button for older ones, and opened as formatted markdown with its sources in the existing row dialog. Specific claims carry numbered footnotes that link out to the real page each claim came from, and the row records what the citation pipeline actually received from Google and what it kept, not just what ended up on screen.

**Steps:**
1. From `hello-world`, run
   `npx vitest run lib/tracking lib/llm/interactionCitations.test.js app/api/application-digest app/components/tracking app/components/TrackingTab.digest.test.js`.
2. Manual (`automatable: no` — the discriminator below needs a real grounded search; no fixture can stand in for what Google's live search actually returns): with the Gemini engine selected, track a new job (or press Research on an existing row) and open the digest. Read the prose for small bracketed numbers set as superscript beside specific claims (e.g. "raised a Series C¹"), and confirm a list beneath it headed "Sources for the numbered claims above", with one real, clickable entry per number. Click one — it must open the source's own page (a news site, a company blog, Crunchbase, an SEC filing), never a `vertexaisearch.cloud.google.com` address. That click is the one observable this case exists to protect: for the life of this feature before this fix, that list was silently empty on every digest ever produced, and nothing on screen, in a server log, or in the test suite said so.

   **Three outcomes look alike at a glance and must not be confused:**
   - **Citations present** (healthy) — numbered markers in the prose, a non-empty "Sources for the numbered claims above" list, every link real.
   - **The model genuinely searched and found nothing to cite** (a legitimate empty, not a bug) — the panel says the research is *unsourced*: no numbered markers, no source list, no failure banner.
   - **The pipeline received citations and dropped every one of them** (the defect this case exists to catch) — the panel instead says citations were found but *could not be placed*, with a count. One digest saying that, over one genuinely hard-to-place citation, is expected: this feature refuses rather than guesses at where a footnote belongs. **Every digest saying it is the anomaly.**

   When step 2 fails, or the on-screen wording is ambiguous, read the stored record rather than guessing from the screen: `select citation_outcome, researched_at from application_digests where application_id = '<id>'` in the Supabase dashboard (or the row's own downloadable research log, once built). `citation_outcome.searched: false` with `counts.annotations: 0` is the legitimate empty. `searched: true` with `counts.annotations` greater than zero but `counts.placed: 0` is the anomaly — a non-zero input becoming a zero output, which `app/api/application-digest/route.js` also logs server-side as a `console.warn` the moment it happens, so the server function logs are the other place to look. `citation_outcome` being SQL `NULL` (not an object with zero counts) means neither of the above: the row predates this fix entirely, its links were destroyed at write time with nothing left to recover, and it must not be read as "found nothing."
3. Manual (`automatable: no`): find a row tracked more than a day ago with an empty cell. Confirm it did NOT auto-research, that a Research button is offered, and that pressing it fills the cell.
4. Manual (`automatable: no`): switch to the embedded engine in Settings and press Research. Confirm a clear refusal and that no empty or half-written digest is stored.
5. Manual (`automatable: no`): narrow the window below the `md` breakpoint. Confirm the digest is present in the stacked card layout too — it is a separate render path from the table.

**Expected:** 1 passes. 2-5 as described.

**Why this exists:** the user asked for a column listing the pertinent information about the company and role that cannot be gleaned from the posting, auto-populated on a new row, opening a formatted preview on click, with a Research button for existing rows.

Load-bearing specifics:

- **Nothing hooks row creation, deliberately.** Nine separate code paths create a tracked `applications` row — manual add, Job Search track, applied toggle, three tailor flows, feed apply, the auto-apply queue and `useManualTailor` — and seven are inside `app/page.js`, which is 3300 lines and far over this repo's cap. Instead the table asks for a digest for any row that lacks one, which covers every path without touching any of them and makes a tenth path work for free.
- **`selectAutoDigestTargets` is a SPEND control, not a completeness filter**, and it is pure so that decision is testable without a network. Auto-research fires only for a row with no digest row at all whose `tracked_at` is within `AUTO_DIGEST_MAX_AGE_HOURS` (24), newest first, `AUTO_DIGEST_CONCURRENCY` at a time. Opening the table on sixty untouched rows must not bill sixty grounded searches; the Research button is what covers the backlog, which is exactly the split the user described.
- **A `failed` digest is never auto-retried.** Without that, a permanently failing row burns a model call on every page load forever with nothing changing on screen. Retrying is the button's job.
- **An existing digest short-circuits the route with no model call.** The table asks on every load; re-researching would bill a grounded search per page view. `force: true` — what the button sends — is the only way past it.
- **A failure is PERSISTED as `status: "failed"` and returned as 200.** An empty cell reads as "nobody has looked yet"; the user has to be able to tell a failure from an untried row, and the auto path has to be able to tell them apart too.
- **Digests live in a NEW `application_digests` table, not a column on `applications`.** That table predates this repo's migration set and is written by six call sites; a join-side table with `application_id` as primary key and `on delete cascade` cannot break any of them. RLS on, four owner-scoped policies; the `insert ... with check (auth.uid() = user_id)` is what makes an upsert safe without a redundant `user_id` filter.
- **Existing digests are read straight from Supabase by the browser's RLS-scoped client**, not through a GET route. RLS already grants exactly the caller's rows, and a route would exist only to re-wrap that — while turning one query into one request per row. The API route exists for one reason: the grounded model call needs a server-side key the browser never sees.
- **The digest cell must be a real `<button>`.** The table row already has an `onClick` opening the edit dialog, guarded on `e.target.closest("a, button, ...")` — anything else is swallowed by the row.
- **The table has a second, stacked-card layout below `md`.** A column added only to the `<Table>` is invisible on a phone.
- **Rendered with the real markdown parser** (`MarkdownPreview` + `lib/experience/markdown.js`), not `FormattedContent.js`, which is a plain-text heuristic shaped for job ads and resumes.
- **The preview reuses `AppViewDialog`'s existing `kind` mechanism**, already opened from a tracking cell as `{ open, rowIndex, kind: "jd" }` — one dialog for row content rather than two competing ones.
- **An ungrounded link never reaches storage.** `parseDigestAnswer` demotes any `[text](url)` whose host is not in the model's own grounding metadata to plain text, keeping the sentence; an empty grounding list demotes everything.
  **Amended: this was recorded as the mechanism working correctly, and it was actually the entire defect, silently, for the life of the feature.** "The model's own grounding metadata" is `groundingChunks[].web.uri`, and on `models.generateContent` that value is always a `vertexaisearch.cloud.google.com` redirect proxy, never the publisher's own host (`lib/llm/grounding.js:23-51`). So the gate above never saw a host any real citation's URL could match, and "an empty grounding list demotes everything" fired on **every digest ever produced**, genuine citations included, not only invented ones — `sources` was `[]` on every row, forever, indistinguishable on screen from "the model found nothing." Swap the shipped test's fixture for that documented redirect shape and exactly 1 of 22 assertions in `lib/tracking/applicationDigest.test.js` notices, and 0 of 10 at the route (`app/api/application-digest/route.test.js`) — measured, and it is the reason this shipped and stayed green through every prior run of this suite. The fix moves the digest off that host-matching gate entirely, onto `client.interactions.create`, whose `url_citation` annotations carry the real publisher URL directly on the annotation itself — there is no host to compare, so this exact class of failure cannot recur on this call the way it did.
- **A test-mock shape bug found by an implementer, not by the suite.** `listDigests` returns an OBJECT keyed by `application_id`; the route test mocked it as an array, so every assertion ran against a shape production never produces. The route survived only because it defensively handled both. The mock now matches the accessor.
- **The invariant that would have caught this is now covered by step 1, not left to step 2 alone.** Repo-wide there was exactly one assertion anywhere requiring `sources` to be non-empty, fed by a fixture production never produced. Step 1 now also runs the citation pipeline's own unit suites (`lib/tracking/citationHref.test.js`, `citationMarker.test.js`, `citationSpans.test.js`, `citationResidue.test.js`, `renderCitedMarkdown.test.js`, `digestCitations.test.js`, `lib/llm/interactionCitations.test.js`) plus a route-level assertion that a response carrying citation annotations can never be stored with zero placed — the exact shape of the historical defect. What remains manual in step 2 is only the part no fixture can stand in for: whether Google's live search actually returns something to cite, and whether the link on screen goes to a real page.
- **Deploy this in two pushes, migration first, and confirm it went green before the code merges.** `citation_outcome` and `researched_at` are added by `supabase/migrations/20260905000000_application_digest_citation_outcome.sql`. `upsertDigest` (`lib/supabase/applicationDigests.js:53-68`) sends an explicit column list, and PostgREST rejects the *whole row* — markdown, status and sources included — over one column it does not recognize. Landing the code before the migration is confirmed live therefore writes **no row at all** on every research attempt; because `selectAutoDigestTargets` only excludes an application once a digest row exists for it, every eligible row then re-fires a full **billed** grounded search on every page load, silently, for up to `AUTO_DIGEST_MAX_AGE_HOURS` (24 hours). Confirm the *Supabase Migrations* GitHub Actions workflow is green and both columns exist before merging the app change — there is deliberately no runtime fallback for this, because sniffing PostgREST's error string would turn a schema mistake into a silent partial write instead of a loud one.
