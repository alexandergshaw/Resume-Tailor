### R-311 | area: autofill-a11y | parallel-safe: yes | automatable: partly

**Summary:** The Auto Fill bookmarklet in `AutofillProfileDialog` used to be reachable only by dragging a link to the bookmarks bar -- the entire ATS form-filling feature was gated behind a mouse drag. The dialog now offers the real equivalent for a keyboard user: a "Copy bookmarklet" `Button` that writes the SAME `javascript:` string to the clipboard, a visible confirmation that the invisible write happened, and instructions saying to paste it as the URL of a new bookmark.

**Steps:**
1. From `hello-world`, run `npx vitest run --no-file-parallelism app/components/AutofillProfileDialog.keyboard.test.js`.
2. Read `handleCopyBookmarklet` in `app/components/AutofillProfileDialog.js` and the `copied` / `copiedTimeoutRef` pair that drives its confirmation.
3. In a real browser: open the Autofill profile dialog, fill at least one field, Tab to "Copy bookmarklet" and press **Enter**. Confirm the label changes to "Copied!" and reverts after ~1.5s. Create a new browser bookmark by hand, paste the clipboard contents as its URL, open a real job posting, and run the bookmark -- the form fills from the saved profile.

**Expected:** All 6 tests pass. The copy control is a `BUTTON` carrying `.MuiButtonBase-root`, is in the tab order, and on activation calls `navigator.clipboard.writeText` exactly once with a string starting `javascript:` whose percent-decoded body contains the saved profile values. The dialog's caption matches both `/bookmark/i` and `/paste|new bookmark/i`. The drag `<a>` is untouched and separately asserted (R-312).

**Why the fix is a copy button and not a simulated keyboard drag.** A bookmarklet fundamentally reaches the bookmarks bar by being dragged there or by being pasted into a new-bookmark dialog; there is no keyboard drag to build. The copy route is the equivalent, not a workaround -- and `app/components/LiveFeedTab.js`'s per-card Auto Fill already used the clipboard for the same string, so this makes the dialog match a route the feature already had.

**Browser-only, per the test file's own header:** the real clipboard write (`navigator.clipboard.writeText` is stubbed here; a browser also gates it on a user gesture and a secure context), and that the pasted bookmarklet actually fills a live ATS form -- the feature's own end-to-end check, which is step 3's second half.

### R-312 | area: autofill-a11y | parallel-safe: yes | automatable: yes

**Summary:** React 19 runs every `href` through `sanitizeURL` and replaces a `javascript:` value with a fixed **throwing stub** before it reaches the DOM, so the Auto Fill dialog's `<Link href={bookmarklet} draggable>` shipped a bookmark that throws on every posting it is run against. `AutofillProfileDialog.js` now writes the real bookmarklet with a manual `setAttribute` from a `useLayoutEffect` keyed on `bookmarklet`. **This case exists in its own right because the obvious assertion -- `href.startsWith("javascript:")` -- passes against the stub, and reported the feature healthy for however long it was broken.**

**Steps:**
1. From `hello-world`, run `npx vitest run --no-file-parallelism app/components/AutofillProfileDialog.keyboard.test.js`.
2. Read the `bookmarkletLinkRef` + `useLayoutEffect` pair in `app/components/AutofillProfileDialog.js` and the comment above it explaining why it must be a LAYOUT effect and why its dependency array must contain `bookmarklet`.
3. In a real browser: open the Autofill profile dialog, drag the "Auto Fill ⤳" link to the bookmarks bar, then open the created bookmark's edit dialog and read its URL. It must be the real `javascript:`-prefixed bookmarklet, not `javascript:throw new Error('React has blocked a javascript: URL as a security precaution.')`.

**Expected:** All 6 tests pass. Both the *"the drag affordance survives"* guard and the *"keeps the real bookmarklet on the DOM anchor after an edit re-renders the dialog"* case percent-decode the anchor's live `getAttribute("href")` and require the saved profile values inside it -- the decode is what makes them fail for the right reason. Reverting to a plain `href={bookmarklet}` JSX prop turns both red (verified by mutation: `expected 'throw new Error(\'React has blocked a…' to contain 'Alex Shaw'`).

**THE TRAP, stated so nobody re-introduces it.** React's stub *also* begins with `javascript:`. Any assertion of the form `expect(href.startsWith("javascript:")).toBe(true)` is **vacuous** against this component and always will be; the same goes for `toMatch(/^javascript:/)`. An assertion on this anchor is only meaningful if it decodes the payload and requires data that could only have come from `buildBookmarklet` (`hello-world/lib/autofill/buildBookmarklet.js`, which emits `javascript:` + `encodeURIComponent(JSON.stringify(profile) ...)`).

**The dependency array is load-bearing in one direction and the ref is load-bearing in the other.** `[bookmarklet]` is required because editing any field produces a new `bookmarklet`, a new `href` prop, and a fresh React re-sanitization of that commit -- with `[]` only the first render's value would ever be real. The effect must be `useLayoutEffect`, not `useEffect`, or the sanitized stub is live and draggable for one paint. **The complementary case -- a re-render that does NOT change `bookmarklet`, where the effect deliberately does not re-run -- was measured while writing this entry and holds:** React's reconciliation writes an attribute only when the prop value changes between renders, so both a parent re-render with an identical `bookmarklet` and the dialog's own `copied`-state re-render (clicking "Copy bookmarklet") leave the manually written `href` intact. **What would break it is a REMOUNT of that anchor without `bookmarklet` changing** -- React would build a fresh node carrying the stub while the effect, seeing unchanged deps, never runs. Nothing in the current JSX can cause that (the `<Link>` is an unconditional, unkeyed first child), but adding a key, a conditional wrapper, or a sibling that changes element type above it would, and no test in this file would notice. Step 3 is the only check that would.
