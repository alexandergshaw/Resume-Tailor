### R-279 | area: drive-foundation | parallel-safe: yes | automatable: partly

**Summary:** The foundation layer of the Google Drive integration — 23 modules under `lib/drive/`, two Supabase stores, two tables and a settings control — built by six agents over disjoint files, then twice reviewed and remediated by independent agents. **It is inert on arrival.** `DriveButton` is mounted nowhere, no `/api/drive/*` route exists, and nothing a user can reach changes; the only production effect of this push is the migration creating two empty tables. So this entry is not really about behaviour. It is about three things the wave proved — a real-client wire probe on the one call shape that fails silently, a cross-provider OAuth join that previously *could not exist*, and a two-table schema whose access rules are unusual on purpose — and about the seam defects that were found, each of which is the shape of the next one.

**Amended (Drive mount, R-282/R-283) — the Expected's second half was true of this push and must not be run against today's tree.** It read: *"No user-visible behaviour changes anywhere in the app, before or after — if anything Drive-shaped appears in the UI after this push, something was mounted that this wave did not intend to mount."* That was the correct assertion for an inert foundation wave and it is retained here as the record of what this wave pinned. It is now false by design, in two deliberate steps: R-282 mounted `DriveButton` in the settings menu (`SettingsMenu.js:106`), and R-283 mounted the save/download controls in the preview modal (`DocumentPreviewDialog.js:898`, `:933`). Drive-shaped UI is therefore expected, and its absence is the failure. Run steps 1-5, which are unaffected; for the live check that replaces the inertness assertion, see R-283 steps 11-13.

**THE KEYSTONE IS THE WIRE PROBE, and an injected fake client cannot replace it.** `files.export` takes `mimeType` as a genuine TOP-LEVEL parameter while `files.update` does NOT: only `media`/`requestBody`/`auth`/`headers` are consumed specially, and everything else falls through to `options.params` (`googleapis-common/apirequest.js:232`) and becomes a query string. With no `requestBody` present, `apirequest.js:213` downgrades the call to `uploadType=media` — a bare .docx PATCH with no conversion target, which replaces the user's Google Doc with a binary blob. **It does not throw.** A fake client injected at the boundary sees whatever object the caller hands it and can never detect this, which is why the probe drives the real `googleapis` with only the transport stubbed. Both shapes are pinned: correct is `uploadType=multipart` with `requestBody.mimeType = application/vnd.google-apps.document` and a media part declaring the .docx type; defective is `mimeType` demoted to a QUERY parameter, `uploadType=media`, raw bytes and no metadata part, asserted side by side with `expect(correctReq.params.uploadType).not.toBe(req.params.uploadType)`. **The best property of the design is that the negative control doubles as a canary on the instrument:** making the probe's own `requestBodyOf` / `mediaContentTypeOf` lie unconditionally was caught, because the negative control requires them to return `undefined` for a body-less shape, and a helper that always returns a value cannot satisfy both cases.

**THE JOIN THAT COULD NOT EXIST.** `lib/drive/oauthState.js` was written to compose with the already-shipped `lib/oauth/state.js`, but that module accepted no caller nonce and returned no payload — so Drive's only replay protection was unwireable, and **a test actively PINNED the decoupling**, meaning the suite would have stayed green forever with the join absent. Fixed additively: `createOAuthState` takes an optional `nonce`, `verifyOAuthState` returns `nonce` and `provider` on success. **All 15 rejection branches of `verifyOAuthState` were enumerated exhaustively — not sampled — and every one is literally `{ok:false, reason}` with no third key**, so there is no path on which the new fields leak alongside a rejection. Gmail is unchanged because it never passes a nonce and therefore still takes the mint-its-own branch; that is pinned by a positive control asserting two separately-minted states get different 32-hex nonces, so a hardcoded or omitted one fails. Four mutations turn the join red from both sides, including dropping `nonce` from the shared half's return (16 red).

**GMAIL'S SECURITY SUITE SURVIVED THE API CHANGE — re-proven, not assumed.** `lib/oauth/state.js` is live code guarding the R-277 OAuth CSRF flaw, so the change was re-run against R-277's own evidence: with `state.js` kept and both Gmail route files reverted, all eight required tests still go red — **T12, T13, T14, T15, T16, T19, T22, T23**, 16 red in total. **Note the trap the verifier corrected, because R-277's own wording invites it:** reverting the routes "to HEAD" is a NO-OP, since both route files are unmodified relative to HEAD. The meaningful revert is to the **pre-fix commit `a78a07a`** (the one before `6a2dce7`). Anyone re-validating R-277 after this wave must use that commit, or they will prove nothing and believe they proved everything.

**THE MIGRATION.** `drive_documents` is keyed `(user_id, position_id, scope)` — `user_id` must be IN the key because `public.positions` is a SHARED table with no `user_id` column, so two users tailor the same position row; `user_id` leading the PK is also why there is no separate `user_id` index. `drive_file_id` is **NOT NULL**: an earlier draft made it empty-able to express a claim-before-calling-Drive protocol, and that design was **withdrawn** — recorded here so nobody re-derives it, because a column with no protocol behind it invites the next implementer to build half of one. `check (scope in ('resume','cover'))` matches `DOCX_SCOPES` by hand. `drive_connections` is **the first table in this migrations directory with NO `authenticated` grant at all**: RLS enabled with no policies, plus an explicit `revoke`, reachable only through `createAdminClient()`. The shouting warning comment above it exists for one specific reason — copying a neighbouring migration's grant block, which every other table in the directory has, would expose every user's Google refresh token to any browser session.

**THE PROPERTIES THAT WOULD SILENTLY RE-BREAK THIS.** Two independent passes ran 22 and 12 mutations against the real implementation. The seam defects they found are the ones worth carrying forward:

* **`"coverLetter"` where the schema says `"cover"`.** Nine fixtures pinned a value the migration's CHECK rejects. It would have failed **in production only**, with every unit test green, because `driveSaveBatch` never touches the database and the store module never sees `driveSaveBatch`'s vocabulary. Now guarded by importing the REAL `DOCX_SCOPES` from `lib/tailor/documentScopes.js` — **a locally re-declared list would be the same bug one level up**, and the guard is worthless without that import.
* **User-facing strings re-derived instead of imported.** Rewording `driveSaveBatch`'s private `gone` message left all 79 tests green, because only four of the six error kinds had content assertions. Then, after the first fix, rewording `dismissedRow` **and its own test together** — the natural shape of any copy update — left all 271 green while `buildRow` kept emitting the old sentence from its own copy. Both are closed now, and **the guard must survive the reword-both-together mutation specifically**, since that is the one that walked straight through the first attempt.
* **Two `[src]` sweeps were claimed in comments and did not exist** — that `driveMime.js` is the only file naming a `vnd.google-apps` MIME type, and that `driveClient.js` is the only module calling `drive.files.*`. Both invariants held by luck. They are now written in `lib/drive/driveSourceSweep.test.js`, each with a planted-violation proof. **The trap:** a sweep must strip BOTH `//` lines and `/** */` blocks before searching, because a legitimate JSDoc quoting `drive.files.*` trips a naive `//`-only stripper — `driveWireProbe.js` is exactly such a file, and a `[pinned]` case now asserts it matches raw and does not match stripped, so the strip cannot quietly stop working. This repo has a documented history of source-scan tests going red against correct code because they matched their own prose.
* **Two false coverage comments were found and deleted in this wave** — one claiming a companion wiring test for `DriveButton` that did not exist, one claiming every user-facing string was imported when five were not. **A comment overstating coverage is worse than no comment, because it stops the next reviewer looking.** Both sat directly above real, demonstrated-unguarded gaps.

**WHAT IS DELIBERATELY LEFT OPEN, recorded so the next wave does not rediscover it.** Two obligations belong to code that does not exist yet, and neither can be caught by any module-level test:

* **`verifyDriveOAuthState` deliberately does NOT clear the state cookie.** That is the callback route's job, and Drive's entire replay protection rests on it happening unconditionally on use. **No module-level test can catch its omission** — the module documents the obligation and correctly declines to take it.
* **`DriveButton` reads the connected account from a status field named `email`, while the column is `google_email`.** The route that must perform that rename does not exist. If it is written to emit `google_email` — the obvious thing, since that is what it will be reading — `DriveButton` renders no account line and **nothing goes red**: its own test supplies an `email` fixture, and its "absent email" test passes happily for the broken case. `GET /api/drive/status` must return the field as `email`, with a route test asserting the name.

**Amended (R-281) — both obligations above are DISCHARGED, and they are kept rather than deleted because they are the record of what this wave declined to take on.** Read them as satisfied, not as open. The callback exists and clears the state cookie on **every** exit path, not merely the happy one: `app/api/drive/oauth2callback/route.js:119, 123, 128, 146, 151, 164, 186, 189`, all through the one `clearStateCookie` helper at `:27`, which appends the header rather than using `NextResponse#cookies.delete()` so it works on a bare `Response` too. And `GET /api/drive/status` performs the rename in the direction this bullet demanded — `email: connection.google_email` at `app/api/drive/status/route.js:53` and `:70`, read back as `data?.email` at `DriveButton.js:60`. The obligation that could not be caught by any module-level test was caught by writing the module the obligation belonged to; that is the outcome this paragraph was betting on, and it is worth noting that it took a named next wave, not a comment.

**One live oddity that was safe only by accident of scope — now guarded, not accidental.** `"email"` remains a deliberate fixture value in `driveSaveBatch.test.js` — a real `SCOPES` member but NOT a `DOCX_SCOPES` one, and the migration's CHECK rejects it. It was safe when this was written only because `driveSaveBatch` is pure decision logic that never touches the database, and the fixture only exercises row ordering. **The predicted trigger has since arrived:** R-281's save route does carry a scope through to `upsertDriveDocument`. What closed the hazard is not luck holding — it is an explicit guard one step earlier, `app/api/drive/save/route.js:147` (`if (!DOCX_SCOPES.includes(scope)) return badRequest("Invalid scope.")`), rejecting any scope the schema would reject before a single byte is written. The fixture is still a `SCOPES`-not-`DOCX_SCOPES` value on purpose; delete that guard and it goes back to being a lie about what the schema accepts.
