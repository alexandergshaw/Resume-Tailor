### R-296 | area: chat-a11y | parallel-safe: yes | automatable: no

**Summary:** Chunk A2 fixes two accessibility defects in the size-refusal path — a screen reader hearing nothing on a second, byte-identical refusal (the announcement defect), and keyboard focus falling to `<body>` when the composer is disabled mid-send (the focus defect) — and they live in **disjoint fixtures** that the automated suite cannot fully witness together in a real browser. **Two runs, and the entry states plainly why they are two, not one:** each run's fixture is the ONLY one that can witness its half, and each is measurably green with or without the other half's fix, so collapsing this into one run would certify a build with either fix silently deleted.

**Steps — Run 1, a REAL résumé FILE uploaded (fixture B):**
1. Open the app in a real browser with a screen reader running, keyboard only.
2. Upload an actual `.docx` résumé (a real file picked through the OS file dialog — not a stub, not a pasted string). This matters structurally, not cosmetically: what forces the composer to render `disabled` before the refusal fires is `buildTemplateLinesForUpload` (`hello-world/lib/document/docx.js:153-164`) crossing a real **macrotask** — a Blob read — not merely the presence of an `await`. 4. Confirm the composer was never rendered `disabled` at any point during the send, and confirm focus never moves at all once the refusal has settled — no restore fires, because a refused send skips `restoreComposerFocusIfLost` entirely. Confirm the refusal itself is heard through the live region (`role="status"` / `aria-live="polite"`, `ChatPanel.js`) rather than through any focus change. *(This anchor read `chatbot.js:922` — **past that file's last line**, and it named the wrong file besides: the focus helpers were extracted to `composerFocus.js`. **Amended (rev 6 — AC-31/AC-32/AC-35 revised):** this step originally required confirming focus is **in the composer, not on `<body>`**, once the refusal had settled about 80 ms after the send resolved — i.e., that a restore had fired and landed correctly. **Steps — Run 2, NO résumé uploaded (fixture A):**

**Expected:**

- **Run 1 is the ONLY run that can witness the focus restore.** [jsdom-MEASURED, this repo, jsdom 29.1.1] jsdom does **not** move `document.activeElement` when an already-focused element becomes `disabled` — so a green jsdom suite is not evidence that a real browser's focus-drop-to-`<body>` behaviour is actually handled; only a real browser proves it. With no résumé uploaded, the composer is **never** rendered disabled in the first place (fixture A has no macrotask between the send starting and the size gate firing), so this run's fixture is the only one where there is anything to lose focus FROM.

- **THE MECHANISM CHANGED, and this run is now the only instrument that can judge it.** A2 shipped a `flushSync` that forced a second React commit of `"" → msg`; the remediation pass replaced it with **node identity** — the error text renders inside the always-mounted region as an element whose `key` is an announcement counter, so each announcement destroys and recreates that node (what `@react-aria/live-announcer` does). The reason is that `flushSync` forces a React commit but **not** a second accessibility-tree serialization: that work is bound to the rendering lifecycle, a text change is not an immediate-processing event, serialization is deferred ~150 ms, and the Send click itself restarts that window — so `msg → "" → msg` can collapse inside one serialization to `msg → msg`, i.e. no change and no announcement. **Every automated test of this behaviour observes the React/DOM layer, which is the layer where BOTH mechanisms work; only a real screen reader can tell them apart.** If step 7 reports silence on the second refusal, the mechanism is the first thing to suspect, not the fixture.

If a tester observes focus leaving the composer, or the announcement being truncated by a focus change, on either run, that is a REGRESSION of this fix, not the known, accepted gap the paragraph above once described.

**Expected:** All 14 tests pass. **No candidate work is lost on any dismissal route.** `chatInput` and `chatMessages` are owned by `app/hooks/useChat.js`, not by `ChatPanel`, so an Escape mid-sentence unmounts the panel without discarding the draft or the thread. That is what step 3's last sentence checks by hand.

**Known coverage gap in the focus-return seam.** The chain is `page.js`'s `chatFabRef` -> `ChatFab`'s `forwardRef` -> the DOM button -> `ChatPanel`'s `returnFocusRef?.current?.focus()`. `ChatPanel.dismiss.test.js` substitutes a hand-made `<button>` for the launcher and `ChatFab.keyboard.test.js` never passes a `ref` at all, so **no test crosses that seam**: dropping the `forwardRef` wrapper from `ChatFab.js` leaves both files green while the optional chaining silently turns the restore into a no-op and focus falls to `<body>` -- exactly the defect this case exists to prevent. ### R-307 | area: chat-a11y | parallel-safe: yes | automatable: partly

**Summary:** Moving the AI Help launcher's toggle from `onPointerUp` to `onClick` (R-306) had to keep the reason the toggle was on `onPointerUp` in the first place: the launcher is user-draggable, and **dragging it must not also open or close the chat**. It also must not do the opposite -- a drag whose trailing `click` never lands on the launcher must not leave a suppression flag armed that eats the NEXT activation, including the keyboard Enter that R-306 exists to make work. **These two are one case because a fix for either, written alone, breaks the other, and the jsdom suite can only see one of them.**

**Steps:**
1. From `hello-world`, run `npx vitest run --no-file-parallelism app/components/ChatFab.keyboard.test.js`.
2. Read `app/components/ChatFab.js`'s file header and its `onClick` / `onPointerDown` / `onPointerUp` handlers together -- the header states the lifetime rule the three implement between them.
3. In a real browser, mouse only: **drag** the launcher a visible distance and release **on the launcher itself**. The chat panel must NOT open.
4. Still in a real browser: drag the launcher hard into a viewport edge so the clamp (`Math.max(8, Math.min(window.innerWidth - 80, ...))`) stops the button while the pointer keeps travelling off it, and release. The panel must not open. Then Tab to the parked launcher and press **Enter**: the panel MUST open on that first press.
5. Repeat step 4 on a touch device, where the browser suppresses the compatibility `click` after a moved touch sequence outright.

**Expected:** All 9 tests pass, including *"still suppresses the toggle when the user DRAGS it"* and *"does not swallow the NEXT activation after a drag whose trailing click never lands on the Fab"*. Steps 3, 4 and 5 all hold in the browser.

**What ships today, and why it is a keyboard/pointer discrimination rather than a race against the event loop.** `onPointerUp` arms `suppressClickRef` only when the gesture crossed the 4px move threshold, and leaves it armed -- no timer, no `queueMicrotask`, nothing self-clearing. `onClick` checks `event.detail` FIRST: `detail === 0` is what a native `<button>`'s keyboard activation (Enter/Space) produces, and that branch calls `onToggle()` and resets the flag unconditionally, before ever looking at it -- a keyboard click is therefore NEVER suppressible, whatever the flag's state. Only a `detail > 0` click (a real pointer) falls through to the flag check, where an armed flag is consumed (cleared) and swallows exactly that one click; an unarmed flag lets the click reach `onToggle()` same as ever. The flag's lifetime is bounded by consumption in either of two places: the suppressed pointer click itself, or the next `onPointerDown`, which resets it unconditionally so a fresh gesture never inherits suppression armed by a previous one. Measured directly, real Chrome, CDP-injected trusted input, against **react-dom 19.2.4 -- this repo's exact version**: a completed drag's trailing pointer `click` carries `detail: 1` and is swallowed; a subsequent keyboard Enter on the parked launcher produces a `click` with `detail: 0` and opens the panel on that first press, regardless of the flag. Step 3 held; step 4's second half (the Enter) held.

**The previous mechanism this replaced, kept here because it is the part a future reader most needs.** An earlier version armed `suppressClickRef` in `onPointerUp` and cleared it again in a `queueMicrotask` callback, on the stated premise that *"a same-element trailing `click` ... always arrives synchronously as part of the same gesture, before any queued microtask runs."* That premise was false and inverted the bug it was meant to prevent: `pointerup`, `mouseup` and `click` are three separate event dispatches, and the HTML spec performs a microtask checkpoint whenever the JavaScript stack empties, which happens after each listener returns -- so the queued microtask ran and cleared the flag BEFORE the trailing `click` arrived, meaning every completed drag also toggled the chat, the opposite of what the suppression exists for. **jsdom could not see this in either direction, and still cannot -- this is structural, not a gap that was closed.** A test drives `element.dispatchEvent(...)` from JavaScript, so the stack is never empty between a synthetic `pointerup` and a synthetic `click`, and no microtask checkpoint can run in between; jsdom simply cannot express the event-loop ordering either mechanism depends on. A green *"still suppresses the toggle when the user DRAGS it"* case was never evidence about the `queueMicrotask` version, and it is not evidence FOR the current `detail`-based one either -- the reason today's mechanism is trustworthy is that it does not race the clock at all, not that the suite went green. Do not "fix" a future regression here by reaching for a timer-based self-clear on the strength of a passing jsdom suite: that is exactly the reasoning that shipped the defect this entry used to describe.
