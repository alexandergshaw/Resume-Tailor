## 0. The requirement I am building to (owner, final — not re-opened)

- The user ALWAYS wants an example project. MODEL-generated examples STAY (the quality wanted).
- The problem is TIMING + role-fit. The example must appear in **milliseconds** when a question
  is detected.
- A live **per-question model call on the answer path is OUT** (it is the current seconds-long wait).
  Every model example must be **generated AHEAD, CACHED, and served instantly**.
- The deterministic archetype is **only** the not-yet-ready fallback.

This last point is load-bearing and **reconciles a tension in my brief**: the cause-(A) text says
"wire `generatedProjectPromise` into the streaming done-frame aids." That describes the BUG
(streaming never gets the model example); it is NOT the fix, because wiring the promise inline
re-introduces exactly the per-question **blocking** answer-path model call the owner ruled OUT. The
fix below replaces the inline promise with a **cache peek fed by an ahead-of-time prefetch**, on
every answer branch. I flag this interpretation for the checker as the one most expensive to get
wrong.

### 0.1 OWNER REFINEMENT (2026-10-06, folded in): TWO ideal projects, progressive
Each answer surfaces **two** examples, not one:
1. **READY (cached, instant)** — the prefetched, posting-grounded pool example, served in
   milliseconds by a cache peek. Shown immediately. (What §3.1–§3.5 build.)
2. **TAILORED (on-the-spot, seconds)** — generated live for THAT exact question ("the topmost ideal
   one for this specific question"). It is allowed to take the seconds a live model call costs,
   **because the READY one already showed instantly** — the user is never left waiting with nothing.

So the delivery is **PROGRESSIVE**: show READY first (ms), then add/swap in TAILORED when it
arrives, both present in the final surface, clearly distinguished. This changes "no per-question
model call" from an absolute to a precise rule: **no BLOCKING per-question call on the answer serve
path** (the answer path still only PEEKS). The on-the-spot per-question call is sanctioned, lives on
its **own non-blocking channel**, and never gates the READY example or the streamed answer. Both
examples go through `normalizeIdealProject` (every real guard kept; the loosened digit rule + R-135
of §4 applies to both).

## 2. LATENCY BUDGET (the headline)

Two budgets, one per example.

**READY (cached) — < 10 ms server-side, ZERO model calls on the serve path.** The READY example
(model-if-pool-warm, deterministic-if-not) is assembled by a synchronous in-process cache `peek()`
(a `Map` lookup, sub-millisecond) plus `idealProjectFor()` (pure, no I/O, sub-millisecond). The
model call happens only on the **prefetch** path, off the critical path, and is never awaited by
any request that serves the READY example.

**TAILORED (on-the-spot) — its own budget: one live `generateContent` (~1–4 s typical,
model-dependent, real-env only), NON-BLOCKING.** It is issued on a separate channel (a post-points
stream frame for live; a second `tailored` fetch for non-streaming), AFTER the READY example is
already on screen, so its seconds never leave the user waiting. It is deadline-bounded (server-side
`settleWithin`, ~6 s) and **degrades to nothing** on timeout/failure — the READY example then stands
alone. The TAILORED call is the ONLY per-question model call, and it is never on the answer serve
path nor awaited by the READY example.

**End-to-end to "example shown":**
- Lower bound / guarantee we own and TEST: one request's existing round trip, with the example
  riding it at no added model latency. With the optional early NDJSON `ideal` frame (§4.5), the
  example is the **first frame**, ≈ 1 RTT, ahead of any model token.
- On a prefetch miss ("not ready yet"): the **deterministic archetype shows instantly**, same
  budget — never a wait, never a spinner for the example.

The wall-clock RTT itself is network-bound and **cannot be measured in this checkout** (no
`GEMINI_API_KEY`; see §9). The testable invariant that stands in for it: **no `generateContent`
is invoked on the path that serves an example** (assert the Gemini mock's call count is 0 for the
peek/serve path), and the fallback is pure/synchronous.

## 3. PREFETCH + CACHE architecture

### 3.1 New cache — `lib/copilot/answerSessionCache.js`
```js
// Key: `${userId}::${applicationId}::ip:${questionKey}` (see idealProjectResolver.js).
// Holds { project, resolvedAt }, where `project` is normalizeIdealProject's output or null.
export const idealProjectCache = createTtlCache({ ttlMs: 30 * 60 * 1000, maxEntries: 200 });
```
**Addresses this module's own header invariant head-on.** The header (`:33-42`) forbids caching
anything "ranked/scored against THIS question's text," with two application-scoped exceptions
(`companyFactsCache`, `codeLanguageCache`). The ideal project is **question-scoped**, so it does not
fit either exception — it is made safe a *different* way: the **question is part of the key**, so
question-two has a different key than question-one and the "answer question two with question one's
selection" hazard is **structurally impossible** (stronger than the exceptions, which share a key
across questions). The one deliberately question-independent key is the **posting-pool key**
(`questionKey === ""`), reused across questions on purpose: it is posting-only by construction (the
loader is built with `question: ""`), i.e. the "benchmark biased only by KIND" the owner sanctioned
for the live path. 30 min TTL / 200 entries match the two existing model-result caches.

### 3.2 New module — `lib/copilot/idealProjectResolver.js` (server-only; imports the Gemini client)
Mirrors `answerCodeLanguage.js` exactly (gates-first, void start, explicit peek). Two key families:
the **pool** key (`""`, posting-only, question-independent — the READY example) and the
**per-question** key (`normalizeQuestion(question)` — the TAILORED example's optional cache).
```js
export function idealProjectKey(userId, applicationId, questionKey) {
  return `${userId}::${applicationId}::ip:${questionKey}`;   // questionKey "" == the posting pool
}

// Starts AT MOST one generation per key per TTL; returns nothing (an await is unwritable — CONF-4).
// Gemini-only: embedded never reaches a model call (the standing engine invariant). `question` is
// "" for the pool (READY) prime, or the exact question for a per-question (TAILORED) prime.
export function startIdealProjectResolution({ engine, description, question, cacheKey }) {
  if (wantsEmbedded(engine)) return;                       // embedded gets no model example, ever
  if (!String(description || "").trim()) return;           // no posting -> nothing to ground / no key written
  try {
    const { geminiModel } = getServerEnv();
    const client = getGeminiClient();
    idealProjectCache.get(                                  // SYNCHRONOUS — never deferred (codeLanguage precedent)
      cacheKey,
      async () => ({ project: await generateIdealProjectExample({ client, geminiModel, description, question }), resolvedAt: Date.now() }),
      { now: Date.now() },
    );
  } catch { /* no key / sync client-construction failure -> nothing resolved, nothing thrown */ }
}

// Pure. Starts nothing. Returns the model `project` or null (null covers miss, pending, and a
// resolved-but-rejected generation). `hit?.project || null` is safe: `project` is an object or null,
// never a truthy sentinel, so the `|| fallback` ban that bites codeLanguage does not apply here.
export function peekIdealProject(cacheKey) {
  const hit = idealProjectCache.peek(cacheKey);
  return hit?.project || null;
}

// The TAILORED (on-the-spot) generation: a live, per-question model call, AWAITED by its own
// non-blocking channel only (never by the answer serve path). Same guards as the prefetch loader
// (it calls the same generateIdealProjectExample -> normalizeIdealProject). Resolves to the model
// `project` or null; never rejects. Deadline-bounded by the caller via settleWithin.
export async function generateTailoredIdealProject({ engine, description, question }) {
  if (wantsEmbedded(engine)) return null;                  // embedded: no model, ever
  if (!String(description || "").trim()) return null;
  try {
    const { geminiModel } = getServerEnv();
    const client = getGeminiClient();
    return await generateIdealProjectExample({ client, geminiModel, description, question });
  } catch { return null; }
}
```

### 3.6 DELIVERY — the two examples, progressive and non-blocking (CORE)
AnswerAids renders inside the answer card on all three surfaces (`AnswerAids.js`, rendered by
`SampleAnswer.js`, `QuestionFeed.js`, `CurrentAnswerPanel`). The two-example model needs its own

**Endpoint `app/api/copilot/ideal-project/route.js`** — POST `{ applicationId, question, mode, engine, tailored }`:
- Auth (`getUser`) → 401. `applicationId`/`question` capped as in the answer route. Posting loaded
  via `loadAnswerContext` (SAME `answerContextCache`, warm after the session's first answer/question).
- `deterministic = idealProjectFor(posting, { question })`.
- **READY path (`tailored` falsy):** `start`+`peek` the POOL key (§3.2/§3.3), return
  `{ tier: "ready", source: model ? "model" : "fallback", idealProject: enrich(deterministic, model) }`.
  < 10 ms serve, zero model calls, self-priming. Embedded → deterministic, `source:"fallback"`.
- **TAILORED path (`tailored: true`):** `const live = await settleWithin(generateTailoredIdealProject({ engine, description: posting, question }), 6000, { fallback: null });`
  return `{ tier: "tailored", source: live ? "model" : null, idealProject: live ? enrich(deterministic, live) : null }`.
  Seconds OK (its own budget, §2); null on timeout/failure/embedded. Optionally cache `live` under the
  per-question key so an exact repeat is instant. `enrich(d, p)` is the one shared helper
  `d ? (p ? { ...d, project: p } : d) : null` — identical to `answerAids`' line 232-234, so the
  endpoint and the answer path can NEVER disagree on content, only on which `project` they carry.

**Hook `useIdealProject({ applicationId, question, mode, engine })`** — the single display source:
- On a new question: fire the READY call → set `ready` state immediately (shows in ms). Then fire the
  TAILORED call → when it resolves non-null, set `tailored` state. Both held independently; a pending
  or failed TAILORED NEVER sets an error and NEVER clears `ready`.
- State: `{ ready: aid, tailored: aid|null, tailoredStatus: "idle"|"loading"|"done"|"failed" }`.
  `ready` is always present (model-or-deterministic). `tailoredStatus` drives only an optional small
  "tailoring…" affordance, never an error banner.

**Live streaming may instead carry TAILORED as a post-points frame** (equivalent, saves one HTTP
call): order `ideal`(READY, from pool peek, first frame) → `points`… → `idealTailored`(from
`settleWithin(generateTailoredIdealProject…, 6000)`, started at producer open, awaited after the
points stream) → `done`(terminal, carries final `idealProject` + `idealProjectTailored`).
`draftAnswerStreaming` gains `onIdeal`/`onIdealTailored`. The bullets and READY example are already
on screen before the producer waits on TAILORED, so the wait is never user-blocking.

**AnswerAids layout (both present):** the existing "Ideal project for this posting" row renders the
READY worked example first, labelled **"A ready example"** (instant, posting-grounded), with its
existing "Not from your resume. …numbers are invented…" disclosure. When `tailored` is non-null, a
SECOND worked example block renders below it, labelled **"Tailored to this question"**, same
disclosure, visually grouped under the same accent row. Prop change: `AnswerAids` gains an optional
`idealProjectTailored` prop ({shape,summary,metrics,project}|null); the existing `idealProject` prop
is the READY one. When `tailored` is pending or failed → only the READY block renders (today's exact
single-example layout — never a gap, never an error). The READY block NEVER moves or disappears when

eye mid-question.

**Practice queue-freeze is dissolved by this:** display no longer reads the frozen answer-cache
`idealProject`; it reads `useIdealProject`, whose READY call peeks the (warm) pool live and whose
TAILORED call runs per-question at reveal. `useSampleAnswer` stops carrying `idealProject` for

## 4. (B) Digit-guard new rule + R-135 proof

Replace the blunt "any posting digit run" reject (`idealProjectPrompt.js:209-211`) with a reject
scoped to the posting's **significant / compensation** numbers only:

```js
const SIGNIFICANCE_FLOOR = 1000; // salary bands, large headcounts, large figures
function significantPostingNumbers(description) {
  return digitRuns(description).filter((run) => Number(run) >= SIGNIFICANCE_FLOOR);
}
// ...in normalizeIdealProject, replacing lines 209-211:
const postingNumbers = new Set(significantPostingNumbers(description));
const exampleNumbers = digitRuns(allText.join(" "));
if (exampleNumbers.some((n) => postingNumbers.has(n))) return null;
```

Why this is correct and provable:
- `digitRuns` (`:132-135`) already strips thousands separators, so `"$78,496.00"` → `"78496"`
  (78496 ≥ 1000 → significant), `"$105,974.00"` → `"105974"` (significant), while a decimal like
  `"4.1"` splits into runs `"4"` and `"1"` (both < 1000 → not significant). The magnitude rule
  therefore composes exactly with the existing normalization.
- **R-135 holds (provable):** a posting salary/comp band is, by its nature, ≥ 1000, so its runs are
  always in `postingNumbers`; an example echoing `$78,496` → `digitRuns` → `"78496"` ∈ set → rejected.
  This is `idealProjectGenerated.test.js:119-121`'s existing regression (`$78,496` as an outcome
  figure must return null) — it **still passes** under the new rule. Large headcounts
  (e.g. 1,200 employees) stay protected for the same reason.
- **Incidental small integers no longer collide:** a posting's "3 years", "2 teams", "40%" are
  < 1000 → not in the set → an example's "3", "2", "40%" survive. The fallback no longer dominates.
- **Stated tradeoff (honest):** small posting integers (e.g. "team of 8", "9 campuses") are no longer
  protected. The owner explicitly sanctioned this ("NOT incidental small integers (2,3,4,5, a
  percent)"); the real R-135 harm — a candidate reading the **salary band** back as a project metric —
  is a large-number event and stays blocked.
- Every other `normalizeIdealProject` guard is untouched (3rd-person `:197`, leftover junk `:198`,
  metric-has-no-digit / figure-has-a-digit `:201-204`, exact label+order `:172`, word bounds
  `:185-191`, shape/arity `:160-163`).

Optional strengthening (not required for R-135): also treat a small number as significant when it sits
adjacent to a currency/comp marker (`$`, `k`, "salary", "compensation", "/yr", "per year"). Magnitude
alone meets the requirement; I leave the marker rule as a note, not a commitment, to keep the rule
one line and trivially testable.
