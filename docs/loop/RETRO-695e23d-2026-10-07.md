### R1 — 0e triage trigger: an owner-perceived MODEL-CONTENT quality complaint the loop cannot instrument (no `GEMINI_API_KEY`) must batch candidate causes behind ONE owner-probe discrimination pass, not grind one mechanical hypothesis per chunk

- **Ready-to-file title:** "0e risk-triage trigger + loop-ac/loop-architect brief: when a complaint is about MODEL-GENERATED CONTENT QUALITY and no in-checkout instrument can measure it, author a single owner-env probe set that DISCRIMINATES among the candidate causes and run it BEFORE shipping serial mechanical fixes."

- **Concrete change:** when the trigger fires, triage does NOT open a chunk per hypothesis. It opens ONE chunk whose first deliverable is an owner-env probe set (question set + expected first-point/first-sentence behavior, the shape N134 §10 eventually produced) enumerating ALL current candidate causes (latency, prefetch warmth, archetype selection, digit guard, cache poisoning, answer-shape directive). The owner runs it once; the result tells the loop WHICH cause(s) are live. Only then are the confirmed causes implemented — ideally batched into one wave, since they touch adjacent modules (`idealProject*.js`, `answerPrompts.js`). The mechanical fixes that CAN be unit-verified (regex, cache keys, deadlines) still land with tests; what changes is that they stop being dispatched speculatively one-per-owner-round-trip.

It RAISES quality against the owner's actual complaint by forcing the one measurement that discriminates real cause from plausible guess BEFORE code is written — the speculative chunks were the quality risk (a plausible-but-wrong fix ships green and the real defect persists to the next round).
