## 1. Owner decisions surfaced (do NOT let design silently resolve these)

**OD-1 — Email in scope now, or résumé + cover letter first?** The email needs infrastructure that does
not exist: a `resume_templates.kind` CHECK migration to admit `'email'` (F1), and email persistence
(there is none — F5). It is also read-only and not docx-backed. **AC recommends: résumé + CL only in
this chunk; email deferred** as a separate item unless the owner wants the new email infra now. The
criteria below are written for résumé + CL; AC-1 makes the email tab's *absence* of the control a
checkable requirement so "email later" is enforced, not assumed.

**OD-2 — Named-template collection (N64's model) vs a singular default-per-type?** The owner said *"the
template to use going forward"* — singular, a per-type default. N64's shipped table is a **named
collection** keyed unique on `(user_id, kind, lower(name))` (F1). **AC recommends: "save the current
document as a `resume_templates` row AND set that row as the per-type default,"** so N97 reuses N64's
store rather than forking it (brief: do not build a rival store). The durable default pointer is NEW and
needs a home — recommend a `tailor_profile` column (F10), which requires a migration + live-schema check
(schema drift is confirmed in this repo; see BL-1). If the owner wants a *pure* single-slot-per-type
(overwrite in place, no collection), say so — that changes AC-5's "prior row is kept" clause.

**OD-3 — Does N97 subsume N64's unshipped Steps 3-7, or depend on them?** N97 needs a template store, a
route, and the generation-consumes-a-stored-template wiring — exactly N64's unshipped Steps 3-7 (F2).
This is an **orchestration** decision (merge the two chunks, or land N64's picking half first, then N97's
promote-from-modal + default-pointer on top). It affects file ownership and sequencing across chunks and
so is the owner's / orchestrator's, not mine.

## 2. Scope boundary (so design does not widen and the verifier does not file phantom misses)

**In scope:** a control in the preview/edit modal on the résumé and cover-letter tabs that (a) stores the
currently-shown document as a `resume_templates` row and (b) sets it as that type's durable per-user
default; and the last hop — a subsequent **interactive/manual** generation of that type uses that stored
template as its formatting source.

**Out of scope (design must NOT build; verifier must NOT file as missing):**
- The hiring **email** as a template (OD-1; needs new infra).
- The **auto-tailor cron** path. N64 kept cron on the legacy slot (owner ruling 1). "Going forward" here
  means the user's interactive/manual generations (where the modal and the promote live), NOT the cron,
  unless the owner says otherwise. Adding cron consumption is a separate item.
- **Per-posting** template selection / the industry-condition auto-match (N64 half B — deferred).
- **Retention / cleanup** of stored template docs (owner standing ruling: filed separately, not inline).
- Persona / tone bundling (N64 owner ruling 2: formatting only).
- Persisting the **Gemini uploaded File** in general (N89 Part 2) — N97 captures the *rendered current
  doc* at promote time, it does not solve File persistence.

**Cumulative-surface note (rule 6b, for the 8b re-judge):** the modal toolbar/`DialogActions` already
carries Download, "Combine both", "Research company", the framing toggle, and the view/edit toggle
(`DocumentPreviewDialog.js:614-696,725-741`), and N92 is concurrently adding up to ~5 per-fact controls
to the cover surface. This chunk **ADDS** one more top-level control ("Set as default template") to an
already-dense toolbar and **DISPLACES** nothing. 1c/1e must weigh the composite legibility cost; the
control should not crowd out Download (the primary action) or the N92 strip.

## 3. Acceptance criteria

Every criterion is **RED on HEAD** unless explicitly marked otherwise, because none of the plumbing exists
(F2, F9). "Instrument: NEW" means the test does not exist and must be built; a criterion whose instrument
cannot yet be evaluated is named as such, never left to look like coverage.

### AC-1 — The control appears on résumé + cover tabs, and is ABSENT on the email tab
When the preview/edit modal is open on the **résumé** tab or the **cover** tab, a discoverable,
keyboard-reachable control (e.g. "Set as default template") is present. On the **email** tab the control
is **absent** (or present-but-disabled with an honest reason — 1c's call), and there is **no path** by
which promoting the email writes any template row.
- **Instrument (NEW):** mount `DocumentPreviewDialog` with each scope available; assert the control is
  reachable (by accessible name, keyboard-focusable) on `resume`/`cover`; assert it is not actionable on
  `email` and no `resume_templates` write occurs from the email tab.
- **RED on HEAD:** yes — no such control exists anywhere (F2).
- **Failure direction:** the email tab must NOT get a working promote (the `kind` CHECK would reject
  `'email'` — F1/F5). The safe/passing state is the control's **absence** on email. A criterion that only
  checked "control exists on resume" would let an email-tab control slip through — hence the explicit
  absence assertion.

### AC-2 — Promote captures the CURRENTLY-SHOWN document, not the pristine template
Using the control stores, as the template for that type, bytes representing the document the user is
looking at **right now** — including any in-modal edits and the current formatting — i.e. the same bytes
the Download path would produce for the current view (`entry.docxB64`/`docxPath` rebuilt with current
edits, F6), **not** the original uploaded/base template the document was generated from.
- **Instrument (NEW):** edit the shown document in the modal, promote, then fetch the stored template's
  bytes and assert they correspond to the *edited-download* output (a marker present in the edited view
  must be present in the stored template), and are **distinct** from the pristine pre-edit template.
- **RED on HEAD:** yes — no capture path (F2).
- **Failure direction (load-bearing):** capturing the ORIGINAL template instead of the current view
  silently discards the user's edits/formatting from the template they just promoted. The passing
  direction is "the stored template reflects the current view." One error (store pristine) is strictly
  worse than its opposite here.

### AC-3 — Per-engine capture is defined, and promote FAILS SAFE when the bytes can't be obtained
Capture is defined for each engine: **embedded/external** → the server docx (`entry.docxB64` or the N59
`docxPath`, F6); **Gemini** → the client-side-rendered current document bytes (built via `previewBlob`
from the live uploaded File, F7). When the current document's bytes **cannot** be obtained — the Gemini
uploaded File is gone after a reload (F8, N89 case C) — the control **refuses with an honest message and
writes no `resume_templates` row and sets no default.**
- **Instrument (NEW):** (a) embedded/external: promote → stored bytes equal the served docx. (b) Gemini,
  File live: promote → stored bytes equal the client-rendered doc. (c) Gemini, reloaded/no File: attempt
  promote → assert refusal AND **zero** rows written AND default pointer unchanged.
- **RED on HEAD:** yes — no path (F2). Sub-case (c)'s refusal instrument is NEW.
- **Failure direction (load-bearing):** storing **empty/placeholder** bytes as a template is the worst
  outcome — every future generation of that type would then produce a broken document. Refuse-and-store-
  nothing is the safe/passing direction. Over-claim safety: if in doubt whether the bytes are the real
  current doc, refuse.

### AC-4 — LAST HOP: the next generation of that type actually USES the stored default
After promoting a document as the default for a type, a subsequent **interactive/manual** generation of
that same type uses the stored default template as its formatting source, **provably in the output the
user can see/download** — not merely that a DB row or pointer was written.
- **Instrument (NEW):** promote template T (which carries a detectable formatting marker); run a fresh
  generation of that type through the real generation path; assert the generated/downloadable document's
  formatting derives from T (the marker survives into the output) and differs from the pre-promote
  default. A DB-row/pointer assertion **does not** discharge this criterion.
- **RED on HEAD:** yes — generation consumes no stored template today (F9); this hop does not exist.
- **Why load-bearing:** this is the nine-instance "mechanism present, user-facing hop gone, suite still
  green" class this repo keeps shipping. The instrument must exercise the reachable output, not an
  internal flag.

### AC-5 — Singular default semantics: replace the pointer, keep the prior template's bytes
Setting a new default for a type **replaces** that type's default pointer; the **previously-promoted
template row and its stored bytes are NOT deleted or overwritten** (it remains a named template in the
collection — OD-2). Only the pointer moves. The default is **per-user and per-type** (a résumé default and
a cover default are independent).
- **Instrument (NEW):** promote A (resume), then promote B (resume); assert the resume default now
  resolves to B, A's row + bytes are still retrievable, and the cover default is untouched.
- **RED on HEAD:** yes — no default concept (F3).
- **Failure direction:** overwriting/deleting A's bytes on re-promote is silent data loss. Keeping A is
  the safe/passing direction. (If OD-2 is decided as pure single-slot overwrite, this clause is revised
  to "the prior slot's bytes are replaced deliberately" — flagged, not assumed.)

### AC-6 — Per-user isolation on both the row and the default pointer
The promote write and the default-pointer write are scoped to the acting user: `resume_templates` RLS +
an explicit `.eq("user_id", userId)` on every statement (mirroring the shipped policies, F1), and the
default-pointer home (`tailor_profile` column or equivalent) is RLS-scoped the same way. A caller can
never set or read another user's template or default.
- **Instrument (NEW):** assert every store/pointer statement carries the user filter; a cross-user id is
  refused (RLS + filter). The `resume_templates` RLS policies already exist (F1) — but the **default
  pointer's** RLS must be confirmed for whatever home OD-2 picks.
- **RED on HEAD:** yes — no store/pointer code exists (F2). The table RLS is a shipped non-regression
  guard; the pointer's isolation is genuinely new.
- **Failure direction:** a filter derived from a request body is not authorization; a missing filter is a
  cross-tenant leak, not a convenience bug.

### AC-7 — Kind is derived from the active tab, never defaulted
Promoting from the **cover** tab sets the **cover** default and stores `kind='cover'`; promoting from the
**résumé** tab sets the **résumé** default and stores `kind='resume'`. The kind is derived from the
modal's active scope (F4), never hard-defaulted to `'resume'`.
- **Instrument (NEW):** promote from the cover tab; assert `kind='cover'` stored and the cover default
  updated while the résumé default is untouched; symmetrically for résumé.
- **RED on HEAD:** yes — no path (F2).
- **Failure direction:** writing the wrong kind silently mis-templates the *other* document type — a
  defect that only surfaces on a later generation. The passing direction ties kind to the active tab.

### AC-8 — Zero behaviour change for a user who never promotes (non-regression guard)
A user who has set no default for a type generates exactly as today: the legacy uploaded File / legacy
slot is used, and the null default pointer changes nothing (F9).
- **Instrument (NEW):** existing-user simulation with a null default; assert the generation path and its
  output are byte-for-byte today's behaviour.
- **RED on HEAD:** **NO — this is vacuously true today** because no default concept and no consumption hop
  exist (F3, F9). It is a **non-regression guard** that becomes load-bearing the moment AC-4's consumption
  hop lands (the hop must be gated on "a default is set", or it changes every existing user's output). I
  state this plainly rather than counting it as coverage.

### AC-9 — One action, sensible default name, duplicate-name handled (minimize-clicks)
Promoting is a single action with a sensible default name (derived, e.g., from job title/company, or a
fixed "My résumé template") — no multi-step wizard. Because N64's unique `(user_id, kind, lower(name))`
constraint (F1) can collide on a repeated promote, a duplicate name is **handled** (reuse/replace the
same-named row's bytes, or auto-disambiguate) and never surfaces a raw unique-violation error to the user.
A confirmation prompt is warranted **only** when the promote replaces an existing default (the standing
change), consistent with [[minimize-clicks]].
- **Instrument (NEW):** promote twice producing the same derived name; assert no unhandled
  unique-constraint error reaches the UI and the outcome is well-defined (one row reused, or two
  distinctly-named rows).
- **RED on HEAD:** yes — no path (F2).
- **Failure direction:** a raw DB error shown to the user, or a silent no-op that leaves the default
  unchanged while claiming success, are both failures; the passing state is a defined, surfaced outcome.

### AC-10 — If a decision-ledger entry is added, it carries enums/counts only (no PII)
Setting a default template is a **standing change that alters future egress** (the formatting of documents
the candidate will send). Recommendation: record it in the activity log so the downloadable log can
explain why future documents changed formatting (consistent with N92 Control C recording a standing
preference; contrast N64 §6.8 which recorded nothing for template CRUD — this differs because it changes
future *output*, not just stored inputs). **Whether to record at all is an owner/design call.** The
checkable constraint: **if** a `recordDecision` entry is added, it must carry only closed-vocabulary
enums/counts (kind; replaced-yes/no) and **no** template bytes, template name, company, job title, or
document text (the N77 rule), and `decisionCoverage.sweep.test.js`'s both-direction wiring must stay green.
- **Instrument:** `decisionCoverage.sweep.test.js` (EXISTS) for the wiring; a NEW assertion that the
  logged payload contains no disallowed field, if an entry is added.
- **RED on HEAD:** conditional — vacuously satisfied if no entry is added (the sweep is green today). The
  PII-exclusion assertion is only red once an entry exists to violate it. Stated plainly.
- **Failure direction:** logging the template name/company/bytes is a disclosure defect (the log has a
  download button); the passing direction is enums/counts only.

### AC-11 — The default-pointer migration is authored safely against a drift-confirmed live schema
If the durable default lives on a new `tailor_profile` column (or a new table — OD-2), the migration
auto-deploys to prod, and this repo has a **confirmed** case of live-schema drift, so the live
`tailor_profile` shape MUST be confirmed before the migration is authored, and the migration follows
N64's loud-failure idiom for anything authored on assumption (plain `add column`, no silent
`if not exists`, per N64 owner ruling 6).
- **Instrument:** migration-text assertion (NEW) + a **live-schema check the owner/1d runs** before
  authoring (`information_schema.columns` / `pg_policies` for `tailor_profile`).
- **RED on HEAD:** yes — no migration exists. The live-schema check is **INVALID-until-run**, not
  "probably fine" (see BL-1).
- **Failure direction:** authoring a column on an unverified shape can collide with an existing column
  meaning something else; the loud-failure idiom makes a wrong guess stop the deploy rather than corrupt
  data silently.
