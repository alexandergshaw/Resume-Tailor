## 2. Attack-by-attack

### Attack 1 — THE LAST HOP (AC-4), exhaustive per-surface mutation proof

**The mechanism itself is correct and well-defended.** `lib/document/docx.defaultTemplateOverride.test.js`
drives the REAL `resolveDocumentBlob`/`downloadDocxFiles` (not `buildDocxFromUploadedTemplate` directly —
rule 6c satisfied) with real JSZip-built `.docx` fixtures carrying a **formatting** marker (run font +
justification, never a content string — correctly avoids a zero-power text-based marker since the
generation's text always overwrites the template's placeholder text). Confirmed by execution (§5 below):
override wins over verbatim-serve AND the edited-rebuild branch; each kind's template lands on its own
document with no cross-contamination; a paragraph/line-count mismatch drops no content (R7); a null or
non-docx template is provably inert (byte-identical NO-OP controls, both present and green).

**But the census that is supposed to prove every EGRESS SURFACE threads this mechanism has a real
granularity gap, proven live by mutation — twice.**

`lib/document/defaultTemplateEgress.census.test.js` checks, per file, whether the literal token
`formattingTemplate` appears anywhere in that file's stripped source (`hasParam()`, a whole-file regex).
Two of its three "current-session egress" rows collapse **multiple real call sites** into one file-level
check:

- **G1 (page.js: `handleTailorJob` `:2074` vs `handleTailorFeedPosting` `:2591`).** Both call sites
  currently pass `formattingTemplate`/`coverFormattingTemplate` correctly. But the census's `app/page.js`
  row is ONE `hasParam("app/page.js")` check. I mutated a scratchpad copy of the real committed
  `app/page.js` text, removing ONLY the `:2591` call site's `formattingTemplate: feedResumeTemplate,` /
  `coverFormattingTemplate: feedCoverTemplate,` lines (the exact N64 failure class the brief names — "a
  page.js download" silently dropping the override) while leaving `:2074` untouched, then re-ran the
  census's own `stripComments` + `/\bformattingTemplate\b/.test(...)` logic against both versions:
  ```
  REAL page.js -- hasParam: true (expect true)
  MUTANT page.js (2591 site's override args removed, 2081 site untouched) -- hasParam: true
  CONFIRMED GAP: the census's whole-file check STILL PASSES on this mutant.
  ```
  No other test in the suite references `formattingTemplate` in a way that would catch this (see §3 — only
  3 test files anywhere reference the literal token, and the docx-level test bypasses `page.js` entirely
  by calling `downloadDocxFiles` directly with hand-built args). **A silent regression to just the
  `handleTailorFeedPosting` download would ship undetected by the entire 16,734-test suite.**

- **G2 (useDriveDocuments.js: the SAVE-producing `buildPreviewBlob` call `:633` vs the two
  `computeCurrentHash` calls `:487-488`/`:646`, which only affect staleness detection, not the uploaded
  bytes).** Same instrument, same result:
  ```
  REAL useDriveDocuments.js -- hasParam: true (expect true)
  MUTANT (save-blob call site's override dropped, hash call sites untouched) -- hasParam: true
  CONFIRMED GAP: the census's whole-file check STILL PASSES on this mutant -- a Drive save that silently
  ignores the default template would ship undetected.
  ```
  This one is the more dangerous shape: the mutant leaves the *staleness-hash* call sites wired, so the UI
  would still correctly detect "this needs re-saving" — while the re-save itself silently produces a
  document with the OLD (engine-native) formatting. A user would see no error, no stale indicator, and get
  the wrong file in Drive.

Both are real, executed, reproducible findings against the actual committed source — not hypothetical.
Note `useDocumentPreview.js`'s row is genuinely fine: `formattingTemplate` appears in real code exactly
once (`:533`), plus once more only inside a comment (which `stripComments` correctly blanks), so that
file's census check is precise. The gap is specific to the two files with more than one real call site.

**Fix needed (not authored here — read-only role):** split the census's `page.js` and
`useDriveDocuments.js` rows into per-call-site checks (e.g. assert the token appears in the text
surrounding each named function/line, not just anywhere in the file), or add a behavioral test per call
site (mock `resolveDefaultTemplateFile`, drive `handleTailorFeedPosting`/the Drive save handler, assert
the resolved File reaches `downloadDocxFiles`/`buildPreviewBlob`).

### Attack 2 — NULL = NO OVERRIDE (AC-8)

Solid. `docx.defaultTemplateOverride.test.js`'s "R6 guard" describe block: `formattingTemplate: null`
serves the engine doc verbatim (byte-identical marker check); a non-`.docx` `formattingTemplate` (a

and are green (both on HEAD and post-impl, confirmed by running the suite).

### Attack 3 — CAPTURE

The CURRENT-view / engine-native capture property (AC-2) and the null-fail-safe signal (AC-3c) are proven
at the **primitive** level by `lib/document/previewBlob.captureContract.test.js` — green, and its own
header honestly discloses it does NOT prove the handler uses the primitive correctly.

**Gap confirmed:** the actual promote handler, `setDefaultTemplateFromPreview` in
`app/hooks/useDocumentPreview.js:541-545`, and the entire capture/consumption glue module
`lib/document/defaultTemplateClient.js` (`resolveDefaultTemplateFile`, `promoteDefaultTemplateBlob`), have
**zero direct test coverage**. Confirmed exhaustively:
`Grep pattern "formattingTemplate" glob *.test.js` → exactly 3 files (the census, the capture-contract
test, and the docx override test) — none of them exercise `defaultTemplateClient.js` or the handler.
`Grep pattern "setDefaultTemplateFromPreview"` across the whole repo → exactly 2 hits, both production
(`useDocumentPreview.js`, `DocumentPreviewMount.js`); zero test files. `Grep pattern "promoteDefaultTemplateBlob|resolveDefaultTemplateFile"` →
production files only. Canary: the same search method finds `saveDefaultTemplate`/`getDefaultTemplate`
correctly mocked/imported in `defaultTemplateStore.test.js` and `route.test.js`, so the method is not
blind — this is a real absence, not a search miss.

On manual read the handler and the glue module are correct (the handler omits `formattingTemplate` from
its `buildPreviewBlob` call — non-circular, satisfies AC-2/R2; it returns early on `!blob` via
`promoteDefaultTemplateBlob`'s own `if (!blob) return {error...}` — zero fetch/POST occurs, satisfies
AC-3c/R4; `resolveDefaultTemplateFile`'s URL/`bytes=1` param and content-type check
(`wordprocessingml`) match the route's own `GET` handler exactly). But this is a code-review claim, not a
test-defended one — a future regression to either function would be invisible to the whole suite,
including N97's own 6 files.

### Attack 5 — INERT-BUT-SAFE (BL-A)

`defaultTemplateStore.js`'s reads use `const { data } = await supabase...` without checking `error`,
relying on Supabase's postgrest client resolving (not throwing) on a query error such as a missing table.
This exact `const { data } = await supabase...` idiom (error silently dropped, `data` falls back to
null/"not found") is already used elsewhere in this codebase — `documentVersionLoad.js`, `factStore.js`,
`upsertApplication.js`, `driveDocuments.js` — so it is established, previously-shipped behavior, not a new
assumption specific to N97. `getDefaultTemplateBytes` explicitly checks `error || !data` before
downloading. Combined with the AC-8 NO-OP controls (Attack 2), a store/route failure resolves to
`formattingTemplate: null` at every consumer, which is proven byte-identical. **Not independently tested
as a "table literally missing" integration case**, but grounded in an established, already-shipped
pattern rather than a fresh unverified assumption — I judge this adequately covered, not a fresh gap.

## 5. Verdict

**SHIP.**

The feature is correctly implemented: every acceptance criterion in `N97.ac.r1.md` is functionally
satisfied on the committed code, the mechanism at the center of the brief's headline attack (AC-4's
override precedence, AC-8's null-guard) is proven correct by executed tests against real `.docx` fixtures
at the real production choke points, the email guard is structural in three independent places, the
reserved-name/duplicate/isolation/retroactivity properties are all directly tested, and the full
16,734-test regression suite confirms zero behavioral regressions beyond the three pre-existing,
unrelated known reds the brief predicted exactly.

The four findings (G1-G4) are coverage gaps, not live defects, and I could not construct a mutant that
actually reaches production with wrong behavior undetected by ALL instruments (the docx-level tests do
correctly defend the override mechanism itself; the gap is specifically in whether a FUTURE regression to
one of several call sites in the same file, or to the client-fetch glue module, would be caught). G1 and
G2 are the more serious of the four because they sit exactly where the brief said N64 died, and I
confirmed them by execution rather than argument. They should be filed as required fast-follow work before
N97 is considered fully closed against its own AC-4 standard — not as a reason to hold or revert the
already-shipped commit.
