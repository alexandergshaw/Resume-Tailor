## 0. The contract — AMENDED ADDITIVELY this round (the F1 fix)

**Why amend a FROZEN contract.** The check's F1 (BLOCKER) proved the frozen return shape (N105.design.r2 §7) is unsafe as the sole carrier of the reviewer's honesty: on the embedded/no-LLM path, a draft that is mechanical-floor-clean but carries a defect in an LLM-only category (`employer-plausibility`, or the semantic depth of `unsupported-authority`/`consistency`) returns `{flags:[], unresolvedQualifications:[]}` as a SUCCESS value of the frozen shape. A consumer (N103/N104) reads that as "reviewed — no weaknesses found" over a draft that was never semantically analyzed — the exact "looks done, analyzed nothing" failure, and the stated safety basis for deferring LLM-category DEPTH to the second slice. The check offered three fix directions; its option (c) ("the frozen contract needs a coverage signal") is the one the orchestrator ruled for, because it is ADDITIVE (adds a field; changes nothing existing) and keeps the mechanical findings useful instead of throwing them away.

**AMENDMENT (additive) to the frozen `reviewDocuments(...)` return from `docs/loop/N105.design.r2.md` §6/§7.** The return gains ONE field, `coverage`. `drafts`, `posting`, `realMaterial`, `flags`, and `unresolvedQualifications` are UNCHANGED (same shapes, same meanings). This amendment propagates to the N106 card and must be noted for N105 step-6 (which consumes the amended shape).

```
reviewDocuments({
  drafts: [
    { kind: "hypothetical",     spans: [{ id, text, section, contextKey }], authorityReference: "internal-consistency" },
    { kind: "applicationReady", spans: [{ id, text, section, contextKey }], authorityReference: "user-material" },
  ],
  posting:      { requirements: [{ id, text }] },
  realMaterial: { spans: [{ id, text, contextKey }] } | null,   // null unless some draft's authorityReference === "user-material"
}) => {
  flags: [{
    draftKind,                 // which draft the offending span is in
    spanId,                    // app-MINTED id of the offending span (EXACTLY ONE; never a union) — UNCHANGED
    category: "missing-keyword" | "vague-unsupported" | "repetition"
            | "unverifiable-metric" | "employer-plausibility" | "consistency"
            | "unsupported-authority",
    evidenceRef?: { origin: "posting" | "real-material" | "draft",
                    draftKind?,                                  // required iff origin === "draft"
                    spanId },                                    // the single evidence span (never a union) — UNCHANGED
    message,
  }],
  unresolvedQualifications: [{ requirementId, text }],           // UNCHANGED
  coverage: {                                                    // *** NEW — the F1 additive field ***
    evaluatedCategories: category[],   // subset of the 7-member enum this invocation evaluated to FULL contract depth
    engineMode: "full" | "mechanical-only",  // "mechanical-only" = embedded/no-LLM path; "full" = LLM judgment seam ran
    complete: boolean,                 // true IFF evaluatedCategories contains ALL seven contract categories
  },
}
category ∈ { missing-keyword, vague-unsupported, repetition, unverifiable-metric, employer-plausibility, consistency, unsupported-authority }
```

**`coverage` semantics, pinned (checkable — see AC-3, AC-15):**
- `evaluatedCategories` = the categories this invocation evaluated to their FULL contract depth. The embedded path evaluates only `{missing-keyword, repetition, unverifiable-metric, vague-unsupported}` + the date/title-contradiction skeleton of `consistency`; it does NOT evaluate `employer-plausibility` nor the LLM semantic depth of `unsupported-authority`/`consistency`, so those are ABSENT from `evaluatedCategories` on embedded.
- `engineMode === "mechanical-only"` on the embedded/no-LLM path (P3); `"full"` only when the injected LLM-judgment seam (AC-12) evaluated the LLM categories.
- `complete === true` IFF `set(evaluatedCategories) ⊇ { all 7 contract categories }`; `false` otherwise. The embedded path ALWAYS sets `complete:false` and `engineMode:"mechanical-only"`.
- **Honesty coupling (strict, AC-15):** `complete === (set(evaluatedCategories) ⊇ 7-enum)` AND `engineMode==="mechanical-only" ⟹ complete===false`. **Failure direction (load-bearing):** overclaiming (`complete:true` while a category was not evaluated) is the fabrication-shipping direction — it lets a consumer render false-clean; underclaiming (`complete:false` when actually complete) is safe (a needless partial-review caveat). The passing direction is the one where `complete:true` requires positive evidence that all seven categories were evaluated.

**Consequence for the first slice (honest, not a defect).** While `employer-plausibility` DEPTH and the LLM depth of authority/consistency are second-slice (§1), NO first-slice invocation can truthfully set `complete:true` on real input — the first slice is a genuinely PARTIAL (mechanical + deterministic-skeleton) reviewer, and `coverage` makes that partiality honest instead of silently clean. This is exactly why F1/F5 are resolved: `employer-plausibility`'s first-slice non-evaluation is now ACCEPTABLE because `coverage.complete===false` + its absence from `evaluatedCategories` makes the non-evaluation legible to every consumer, not disguised as a clean review. The `complete:true` branch is still REACHABLE and TESTED now via the AC-12 seam supplying a judgment across all seven categories (AC-3 positive control below), so the field is not a dead/always-false zero-power signal.

### AC-11 — Determinism and STABLE TOTAL ORDER — **F2 fix folded (multi-flag shuffle fixture named)**
On the no-LLM path, `reviewDocuments(I)` called twice is deep-equal (same `flags`, same `unresolvedQualifications`, same `coverage`, element-for-element). AND output order is a stable total order determined by output CONTENT (e.g. `draftKind`, then `spanId`, then `category`), NOT by input array position: `reviewDocuments(I)` deep-equals `reviewDocuments(I')` where `I'` is `I` with each `drafts[*].spans` array SHUFFLED (same ids/text, different index).
- **Instrument (NEW):** repeated-call equality + shuffle-invariance equality. **The shuffle fixture MUST be the AC-3 multi-defect draft (one defect in each of the four floor categories ⇒ ≥4 flags across distinct spans) — F2.** Assert FIRST that the result carries ≥2 flags, and that at least two of them appear in a content-key order DIFFERENT from their input-span-index order (so an index-ordered impl would emit them in a different sequence). Only then is the shuffle-invariance equality non-vacuous: a 0-or-1-flag fixture (or Stub E) satisfies it trivially and never reds the iteration-order stub.
- **Stub control:** an impl emitting flags in span-iteration order (or from a `Set`/object-key order) fails the shuffle test — but ONLY because the fixture now guarantees ≥2 content-order≠input-order flags.
- **RED on HEAD:** yes, by absence. **Failure direction:** order depending on input array position makes three consumers render differently from the same facts; the safe direction is a content-keyed total order.

### AC-12 — Purity of the deterministic core; any LLM judgment enters through an INJECTED seam — carried verbatim
The deterministic core is a pure function of its arguments: no network, no filesystem, no `globalThis`/module-state mutation, no wall-clock/`Math.random` dependence. If a category's judgment is LLM-backed, it is supplied through an INJECTED dependency (a seam parameter / injected client), so (a) the core stays pure and node-testable and (b) tests can stub the seam for determinism.
- **Instrument (NEW):** call the core with no seam injected and assert it returns without any network/fs access (spy `globalThis.fetch` with a recording positive control per `loop-traps-spec` egress rule; assert zero calls on the deterministic path). Assert no import in N106's own graph monkeypatches `globalThis.fetch`. A seam-mapping test injects a fixed fake judgment and asserts the core maps it to valid `flags` (AC-1/AC-15 shape) AND sets `coverage` honestly (seam covering all 7 ⇒ `engineMode:"full"`, `complete:true`; no seam ⇒ `engineMode:"mechanical-only"`, `complete:false`).
- **RED on HEAD:** yes, by absence. **Failure direction:** burying the LLM call inside the core (no seam) makes the authority-split (AC-2), ordering (AC-11) and coverage-mode (AC-3) untestable and the "pure/deterministic" claim false; the seam keeps them verifiable.

### AC-13 — `realMaterial` contract: null legal with no `user-material` draft; a `user-material` draft with null `realMaterial` FAILS CLOSED — carried verbatim (coverage interaction noted)
(a) When no draft has `authorityReference==="user-material"`, `realMaterial` MAY be null and the primitive runs normally (no throw/crash). (b) When a `user-material` draft is present with `realMaterial` null (precondition violation), the primitive MUST NOT crash and MUST NOT return a clean result: it either fails closed by flagging every support/authority-requiring claim on that draft as unsupported, OR refuses honestly (distinguished signal / throw). The FORBIDDEN outcome is a result a consumer reads as "this user-material draft's authority claims are all supported" — i.e. `flags:[]` with `coverage.complete===true`.
- **Default (DECIDED HERE, matching N105 §5 L1 "empty corpus ⇒ everything drops"):** fail-closed-by-flagging is the default; refuse-with-signal is the admissible alternative. 1b picks; the invariant + direction are fixed.
- **Instrument (NEW):** (a) drafts={internal-consistency only}, `realMaterial=null` → well-formed result, no throw (shared with AC-2 Run B). (b) drafts include a `user-material` draft carrying an authority claim, `realMaterial=null` → assert NOT a clean success: count of `unsupported-authority` flags on that draft ≥ 1 (fail-closed) OR an honest refusal; assert it is never `flags:[]` with `coverage.complete===true`. Failable = 1.
- **Stub control:** Stub E (`flags:[]`, `complete:true`) on (b) fails.
- **RED on HEAD:** yes, by absence. **Failure direction:** with no corpus, passing a user-material draft's authority/support claims as clean is the fabrication-shipping direction; over-flag / refuse is safe.

### AC-14 — `unresolvedQualifications` — carried verbatim
A posting requirement that wording alone cannot resolve (a substantive gap — nothing in the drafts addresses it and no rewording of existing draft content would) appears in `unresolvedQualifications` with its `requirementId` and text. A requirement satisfied by a draft span does NOT appear. A requirement whose keyword is merely absent from the drafts but present in `realMaterial` (phrasing gap) does NOT appear here (AC-4 `missing-keyword`).
- **Instrument (NEW) — three rows:** R1 `"5+ years Python"` satisfied by a draft span → NOT listed. R2 `"active TS/SCI security clearance"` addressed by no draft span and absent from `realMaterial` → listed with R2's `requirementId`. R3 a keyword absent from drafts but present in `realMaterial` → NOT listed (surfaces as AC-4). Failable (must-list) = 1 (R2); must-exclude = 2 (R1, R3).
- **Power / stub controls:** a "list everything" stub includes R1 → fails; a "list nothing" stub omits R2 → fails.
- **RED on HEAD:** yes, by absence. **Failure direction:** omitting a genuine gap (R2) lets a consumer leave the user believing they qualify — the worse error; listing a resolved requirement (R1) is noise the must-exclude rows bound.

### AC-15 — Output well-formedness (universal post-condition over every fixture) — **STRENGTHENED to cover `coverage`**

### AC-17 (SAFETY, USAGE CONTRACT) — Consumers MUST distinguish a COMPLETE review from a PARTIAL one; "no weaknesses found" is FORBIDDEN when `coverage.complete===false` — **NEW this round (the F1 part-3 fix)**
