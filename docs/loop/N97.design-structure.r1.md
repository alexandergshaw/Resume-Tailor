## 1. The decision that is expensive to reverse: WHAT "the template to use going forward" means, and WHERE the seam is

This is the load-bearing boundary and F6 forces it. The app produces the final `.docx` three different
ways per engine, so "use the stored default as the formatting source" (AC-4) cannot be one substitution
at generation. The three engines give the docx its formatting from three different places (F6), and only
one of them (Gemini) is the user's own uploaded template.

### The wrong architecture (rejected): swap the uploaded File at generation
Feeding the stored template as the `resume` File / `templateLines` into `/api/tailor` (replacing
`resumeFile`) does NOT work: the **embedded** engine ignores both and always renders the bundled template
(F6a), and the **external** engine ignores both and renders the remote service's template (F6b). Only
Gemini would honour it. So this satisfies AC-4 for one engine and silently fails the other two — exactly
the "mechanism present, hop gone, suite green" class this seat exists to prevent.

### The chosen architecture: a render-into-template FORMATTING OVERRIDE at the single client doc-build choke point
`resolveDocumentBlob` (F7) is the one place, for **all three engines and every output surface**, where
tailored `text`/`lines` become a `.docx`. `buildDocxFromUploadedTemplate` (F8) already renders arbitrary
generated text into an arbitrary template's styling. So the default template is applied as a
**formatting override**: when a per-type default is set, the generated text/lines are rebuilt onto the
stored template's `.docx` shell, taking precedence over whatever the engine produced. This is
**engine-uniform** because it operates on the generated TEXT that every engine returns, not on the
engine's own docx — it even lets an embedded/external user render into a template captured from a Gemini
doc, which a server-side approach could never do.

- **Formatting-only, by construction.** Content still comes from the existing pipeline (upload / library
  / posting / project pages); the stored template supplies only the docx shell. The FORMATTING marker on
  the template survives (F8, styling preserved); the old template's text is overwritten by the new
  generation's text. This is the correct domain meaning of "template" (layout, not content).
- **The seam is a single new explicit input** `formattingTemplate` (a `.docx` `File`/bytes) on
  `resolveDocumentBlob`, threaded through the two pure arg-builders. When absent (no default set) every
  branch is byte-identical to today (AC-8 holds).

### Ruling on WHERE the override is applied (surfaces), and the one property that makes it safe
- **Egress surfaces APPLY it** (this is the AC-4 minimum): the **download** path (`downloadDocxFiles`,
  F10) and the **Drive save** path (`useDriveDocuments`, F11). A fresh generation's downloaded/saved
  document therefore carries T's formatting — AC-4's instrument (download → marker present) passes.
- **The CAPTURE (promote) path NEVER applies it** — it calls the doc-build with `formattingTemplate`
  omitted, so it always captures the engine-NATIVE rendering of the current document. This is the
  property that keeps the design non-circular and un-trappable: a user can always promote the document as
  the engine actually produced it, and re-promoting never re-captures the active default.
- **The in-modal PREVIEW render** (`loadPreviewModel`, F11) applying the override is a **1c/UX decision**,
  not a structural one. Applying it there gives WYSIWYG (preview matches download) but means the preview
  reformats other in-session docs of that type once a default is set; omitting it keeps the preview
  native. The structural contract is identical either way — one call site passes the param or does not.
  I recommend 1c apply it at preview for WYSIWYG **and** ship a "clear default" affordance (below) so a
  user is never stuck unable to see a candidate replacement template.

### Consequence the AC and orchestrator must see (surfaces a domain truth, does not resolve a product call silently)
Because capture reflects the engine-NATIVE formatting (F6): for a **Gemini** document the captured
template is the user's own uploaded formatting (meaningful); for an **embedded** document it is the
bundled template, and for **external** the remote service's template. So "set current as template" is
most meaningful for Gemini / uploaded-template documents, and for embedded/external it captures that
engine's stock formatting. This is inherent to how those engines work (F6a/F6b) and is NOT something N97
can change without engine changes (out of scope). **Flagged for 1c** to communicate in the control's
affordance; **flagged for the owner** as OD-A below.

## 2. The store & the default home — NO MIGRATION, reserved-row-is-the-default

Owner ruling: **single default per type, not a named collection.** That collapses the store to its
simplest possible form and — critically — needs **no new migration**, which removes the AC's BL-1
(`tailor_profile` live-schema check) and AC-11 (migration authoring) from N97 entirely.

### Ruling: the default IS the row; enforce single-per-kind with the shipped unique index + a reserved name
N97 only ever writes DEFAULTS (there is no named collection), so at most one row per `(user_id, kind)`
should ever exist. Reuse the shipped table (F1) with:
- a **reserved fixed name per kind** — `"Default résumé template"` / `"Default cover-letter template"`
  (exact strings are 1c's, but they are FIXED, not user-typed). The shipped **unique index
  `(user_id, kind, lower(name))`** (F1) then makes a second default of the same kind a hard DB error, so
  "two defaults for one type" is structurally IMPOSSIBLE, not merely avoided.
- a **fixed storage path per kind** — `${userId}/templates/default-${kind}.docx` in the existing
  `resumes` bucket, uploaded with `upsert:true`. This bounds storage to **≤1 object per (user,kind)** (2
  per user max): re-promote overwrites in place, so there is nothing to clean up. The AC's storage-growth
  concern is answered by construction; no cleanup item is needed. (Contrast N64's per-id path, which
  accumulated rows — that model was for a collection; a single default does not need it.)
- "**the default for kind K**" = the one `resume_templates` row where `(user_id=?, kind=K)` — or,
  belt-and-braces, `and name = <reserved>`. Read directly; no pointer, no `tailor_profile` column.

**Why not a `tailor_profile` pointer / `is_default` column (the AC's recommendation)?** A pointer or flag
needs a migration that auto-deploys to prod and re-opens BL-1 (drift). The reserved-row model needs none
and is strictly simpler. The only cost is that provenance FKs (below) point at a row whose bytes can
change on re-promote — which is a non-issue because N97 does not write provenance and past outputs are
frozen bytes (§5). If the orchestrator later wants durable per-template rows for a collection, that is
N64 half B, not N97.

### The one live-DB dependency that remains (BL-A)
That `resume_templates` and the `resumes` bucket are actually LIVE. The migration is committed (F1) but I
cannot confirm read-only from the tree that `supabase db push` applied it, and this repo has confirmed
drift. **BL-A**: before implementation, confirm `resume_templates` exists live
(`select 1 from information_schema.tables where table_name='resume_templates'`) and the `resumes` bucket
exists. If the migration never applied, N97's whole substrate is absent. INVALID-until-run.

## 4. Contracts (full signatures)

### 4.1 `lib/document/defaultTemplateStore.js`
```js
// All functions take the AUTHED supabase client; RLS + explicit .eq("user_id") both enforce ownership.
// Bucket is always "resumes"; the storage object is at `${userId}/templates/default-${kind}.docx`.
// kind is 'resume' | 'cover' (never 'email' — resume_templates.kind CHECK excludes it, F1).

/** Upload the captured bytes to the fixed per-kind path (upsert:true), then upsert the reserved-name
 *  row. select-then-update-or-insert; the shipped unique (user_id,kind,lower(name)) index is the
 *  backstop that turns a concurrent double-insert into a caught unique-violation (AC-9), not a raw
 *  error to the user. Returns the row, or { error } if bytes are empty / kind invalid.
 *  @param supabase, {userId:string, kind:'resume'|'cover', bytes:Uint8Array|ArrayBuffer|Blob, fileName:string}
 *  @returns {Promise<{ row: {id,name,kind,storage_path,updated_at}, replaced: boolean } | { error: string }>} */
export async function saveDefaultTemplate(supabase, { userId, kind, bytes, fileName }) {}

/** The reserved-name default row for this kind, or null. @returns {Promise<{id,name,kind,storage_path,updated_at}|null>} */
export async function getDefaultTemplate(supabase, { userId, kind }) {}

/** Download the default template's docx bytes (by storage_path) for the consumption override.
 *  @returns {Promise<{ bytes: Uint8Array } | null>} null when no default is set or the object is gone. */
export async function getDefaultTemplateBytes(supabase, { userId, kind }) {}

/** Row delete (id+user_id gated) + best-effort storage remove. @returns {Promise<{ ok: true } | { error }>} */
export async function clearDefaultTemplate(supabase, { userId, kind }) {}
```
Load-bearing ordering in `saveDefaultTemplate`: **upload the object first, then upsert the row**, so a row
never names a path with no bytes (`storage_path NOT NULL`, F1, makes a byte-less row impossible). Because
the path is fixed per kind and `upsert:true`, re-promote overwrites the same object — no orphan
accumulation.

### 4.2 `app/api/templates/default/route.js` (idiom = `saved_searches`)
- `GET ?kind=` → `{ hasDefault: boolean, updatedAt?: string }` (metadata; bytes only if a reader needs
  them). 401 if no user.
- `PUT`/`POST` (multipart: `file` + `kind`) → validate `.docx` and `kind ∈ {resume,cover}`; reject email
  loudly (`kind='email'` → 400, mirrors AC-1's "no path writes an email template"); `saveDefaultTemplate`
  → `{ row, replaced }`.
- `DELETE ?kind=` → `clearDefaultTemplate` → `{ ok: true }`.
Every handler: `getUser()`→401→ pass `userId` to the store, which `.eq("user_id", userId)` on every
statement (defense-in-depth atop RLS). **Never** derives `userId` from the request body (AC-6).

### 4.3 `lib/document/docx.js` — the consumption override (the AC-4 seam)
```js
export async function resolveDocumentBlob({
  engineDocxB64 = "", docxPath = "", edited = false, text = "", lines = [],
  uploadedTemplate = null, spacing = null,
  formattingTemplate = null,   // NEW: a .docx File; when set, the default template for this scope
}) { ... }
```
Contract: **when `formattingTemplate` is a docx File, it takes precedence — the verbatim-serve branches
are skipped and the blob is `buildDocxFromUploadedTemplate(formattingTemplate, text, lines)`** (the same
rebuild primitive the edited path already uses, F7/F8), with the `spacing` post-pass applied after as
today. When `formattingTemplate` is null, behaviour is byte-identical to today (every existing branch
unchanged) — this is the AC-8 guarantee. `downloadDocxFiles` passes `formattingTemplate` into BOTH the
résumé and cover `resolveDocumentBlob` calls (F10), taking the value from its args.

### 4.4 `lib/document/previewBlob.js` + `lib/tailor/documentScopes.js`
`previewBlobArgs(entry, scope, { resumeFile, coverLetterFile, text, formattingTemplate })` and
`buildPreviewBlob(entry, scope, opts)` pass `formattingTemplate` straight into the returned args /
`resolveDocumentBlob` (previewBlobArgs stays PURE — it receives a resolved File, it never fetches).
`buildDownloadArgs({ …, formattingTemplate })` adds it to the returned args object so `downloadDocxFiles`

### 4.5 `DocumentPreviewDialog` — the promote control (presentational)
New prop `onSetAsDefaultTemplate?.(tab, activePayload())`, mirroring `onDownload` (F5). The control is


## 5. Replace semantics & provenance (brief step 5)

- **Replace = overwrite in place.** Re-promoting a kind overwrites the reserved row (same `id`) and the
  fixed storage object (`upsert:true`). Single default; no accumulation. Confirmation is shown **only**
  when a default already exists for that kind (the standing change) — first-time promote is one click,
  no dialog (minimize-clicks). AC-9 duplicate-name is a non-issue: the name is reserved/fixed, so the
  unique index (F1) never surfaces a raw error to the user; a concurrent double-insert is caught and
  treated as "update the existing default."
- **Past applications do not retroactively change — structurally, without touching provenance columns.**
  A past application's downloadable document is FROZEN bytes (`generated_resumes`/`generated_cover_letters`
  `content`/`docx_path`/in-session `docxB64`), read independently of any template. The default template is
  consulted only at generation/egress time, never to re-derive a past output. So replacing or clearing a
  template cannot alter any past application's document. **Ruling: N97 does NOT write or read
  `applications.{resume,cover}_template_id`/`_label`** (those columns remain N64's unshipped concern).
  Writing them under a single-default model is actively harmful: a same-`id` overwrite would leave the
  FK pointing at changed bytes, and there is no display half to read them anyway (F2). The non-retroactivity
  requirement is met by the frozen-output invariant, not by a provenance FK.
- **Interaction flagged for the orchestrator (OD-B):** if the orchestrator wants N97 to ALSO record which
  template each application used, that forces the keep-old-rows-plus-pointer model (a migration, BL-1
  re-opens) and re-orders this chunk. I recommend against; the frozen-output invariant already answers
  brief step 5.

## 10. Blockers & owner/orchestrator decisions

- **BL-A (must-run-before-implementation, not a design defect):** the live check in §9.1. No migration is
  authored by N97, so there is no auto-deploy risk; the risk is the opposite — building on a substrate
  that may not have deployed.
- **OD-A (owner, product framing):** capture reflects engine-native formatting (§1), so the feature is
  most meaningful for Gemini/uploaded-template documents; for embedded/external it captures that engine's
  stock formatting. Accept as-is (recommended — it still delivers a cross-engine formatting lock), or
  scope the control to specific engines. Does not block design.
- **OD-B (orchestrator):** N97 does NOT write `applications` template provenance (§5). If the orchestrator
  wants it recorded, that forces keep-old-rows + a pointer migration (BL-1 re-opens) and re-orders the
  chunk. Recommend against.
- **OD-C (1c/UX):** apply the override at the in-modal preview (WYSIWYG) as well as egress, and ship a
  "clear default" control so a user can always see/promote a replacement. Structural contract is the same
  either way.
- **No design-defect blockers in the criteria.** Two AC items are DISCHARGED by this design's shape and
  should be updated by the orchestrator: **AC-11 (migration authored safely) is moot** — N97 needs no
  migration; and the AC's **BL-1 (`tailor_profile` live-schema check) is dropped** for N97. **AC-5's
  "keep the prior template row + bytes"** clause is superseded by the owner's single-default ruling
  (overwrite-in-place, §5) and must be re-worded to "the prior default's bytes are deliberately replaced;
  past applications are unaffected because their outputs are frozen bytes."
