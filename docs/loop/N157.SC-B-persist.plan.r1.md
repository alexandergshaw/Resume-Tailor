## 2. Contradictions resolved (mechanism choices are mine; proofs named)

**(1) Client-side store — INCLUDED as a second module, scoped to not foreclose SC-C.**
The task mandates "the client-side store" and cites the copilot **detail stores** (`techTermDetailStore.js`
/ `expansionStore.js`) for the pattern; AC's test strategy names "the store's read-modify-render". The
arch §3 module table omits it. **Decision:** SC-B-persist ships `studyPlanProgressStore.js`, a module-scope
in-memory state store (`subscribe`/`getSnapshot`/version counter, LRU-bounded Map keyed by `applicationId`),
mirroring `techTermDetailStore.js`. **Its scope is strictly:** hold the loaded plan record, apply a single
reveal/grade to the in-memory `progress` (read-modify-render), and delegate the durable write to an
**injected** writer. It does **NOT** own the walkthrough reducer (cursor advancement, next-due selection) —
that stays SC-C (arch §9). **Proof it does not foreclose SC-C:** the store exposes `getStudyPlanRecord`
(state) and `recordProgress` (persist one card); it imports no scheduler and makes no next-card decision.
*Hedge recorded honestly:* if the orchestrator intended only the DB wrapper, `studyPlanProgressStore.js`
folds cleanly into SC-C with zero rework to `studyPlanStore.js` (the DB layer is independent).

**(2) `writeStudyPlan` write idiom — column-wise upsert on the PK, mirroring `upsertDigest`.**
`study_plans` is 1:1 to `applications` with `application_id` as the PK, exactly like `application_digests`.
`applicationDigests.upsertDigest` (`:105-109`) uses `.upsert(row, { onConflict: "application_id" })
.select().maybeSingle()` with a **column whitelist** (a field not named is dropped silently). **Decision:**
`writeStudyPlan` does the same. **Critical divergence from a naive mirror:** the whitelist MUST NOT include
`progress` (the migration comment `:18-20` and arch §5.2 make `progress` RPC-write-only). Column-wise upsert
means an omitted `progress` keeps the existing value — so a create starts `progress` at the column default
`'{}'`, and a knob-only rebuild preserves accumulated progress. **Proof:** store test asserts the upserted
row's key set never contains `progress`; a knob-rebuild fixture (pre-seeded `seen`) reads back with `seen`
intact. (Risk R2, SILENT — see §6.)

**(3) S8 in-statement tenant filter — per-function, because the three statements differ.**
AC-N157-S8 wants an in-statement `user_id`/`auth.uid()` filter on every read and write **in addition to**
RLS. **Decision + proof per function:**
- `readStudyPlan`: `.eq("application_id", applicationId).eq("user_id", userId)` — both filters asserted.
- `writeStudyPlan`: upsert cannot chain `.eq`; `user_id` is carried **in the row payload**, and the RLS
  `with check (auth.uid() = user_id)` + `using` on the UPDATE branch are the live boundary. Test asserts the
  payload carries `user_id`. (Live cross-user refusal is owner-run, §8 — a PK collision/`using` miss fails
  loudly at the DB; it is NOT provable in-repo. Risk R6, partly SILENT.)
- `writeStudyPlanProgress`: **no `user_id` argument at all** — identity is `auth.uid()` inside the RPC's
  WHERE (migration `:115`), the exact `recordModelCallIssued` discipline. Test asserts the `.rpc()` payload
  is exactly `{ p_application_id, p_cursor, p_seen_delta }` and carries no user id.

**(4) M3 guard placed at BOTH boundaries (defence in depth).** `isSingleItemSeenDelta` is asserted in
`studyPlanProgressStore.recordProgress` (before it calls the writer) AND re-asserted in
`studyPlanStore.writeStudyPlanProgress` (before the `.rpc()`), failing closed on a >1-key / empty / non-object
delta. **Proof:** both tests feed a whole-`seen`-map and assert the `.rpc()` is never issued. (M3 / AC-N157-7
node half; Risk R1, SILENT at runtime.)
