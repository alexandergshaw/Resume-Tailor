## 1. Data model — `public.application_project_pool`

### 1.1 This IS a migration this chunk ships; it is additive-only

Confirmed: `applications` has no `create table` anywhere under `supabase/migrations/` (stated and grepped in `20260906000000_applications_user_position_key.sql:11-18`). This migration adds a NEW join-side table only — it never alters `applications`. The tree's latest migration is `20260930000000_n64_saved_templates.sql` (Glob of the directory, 39 files). The new file must carry a timestamp strictly later than that and later than the tree's actual latest at implement time. **Do not reuse a stamp; check the directory again at implement time** (another chunk may land first). Proposed name (today = 2026-10-08): `supabase/migrations/20261008000000_application_project_pool.sql`.

**Never edit this file in place once applied** (`db push` keys on the version stamp; an edited applied file is silently skipped — see the standing migration rule and the `20260906…` header). Every statement idempotent (`create table if not exists`, `create index if not exists`, `drop policy if exists`/`create policy`), exactly like `application_digests`.

### 1.2 DDL contract (modeled verbatim on `application_digests`)

```sql
create table if not exists public.application_project_pool (
  application_id uuid primary key references public.applications (id) on delete cascade,
  user_id        uuid not null references auth.users (id) on delete cascade,
  projects       jsonb not null default '[]'::jsonb,
  status         text not null default 'pending',
  error          text,
  engine         text,
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now(),
  constraint application_project_pool_status_check
    check (status in ('pending', 'ready', 'failed'))
);

create index if not exists application_project_pool_user_idx
  on public.application_project_pool (user_id);

alter table public.application_project_pool enable row level security;
-- four owner-scoped policies: select/insert/update/delete, each auth.uid() = user_id
-- (drop policy if exists … / create policy … — the exact four-policy block from
--  20260817000000_application_digests.sql:58-72, table name swapped)
grant select, insert, update, delete on table public.application_project_pool to authenticated;
grant all on table public.application_project_pool to service_role;
```

**Divergences from the digest table, each deliberate:**
- `status` default is `'pending'`, not `'ready'`. The digest default is `'ready'` because a digest row is only ever written with real content. A pool row's honest default is "not warmed." The CHECK set **must include `'pending'`** (AC-N143-1 failure direction; a CHECK of only `('ready','failed')` is a blocker). `'pending'` is in the set so (a) the column default is legal, (b) a future explicit in-flight marker needs no migration, (c) AC-N143-8's not-yet-warmed state is a nameable value.
- Payload column is `projects jsonb` (array), not `markdown`/`sources`.

**Diff-applicable invariant (AC-N143-1):** a reviewer applies this to any later edit of the migration — the CHECK literal set must contain all three of `'pending'`, `'ready'`, `'failed'`; removing `'pending'` is a blocker. Instrument: the migration-shape test asserts the three-element CHECK set textually.

### 1.3 Schema-drift note (standing rule)

I read this table's shape from the migration I am *authoring*; it does not exist in the live DB yet, so there is no drift to reconcile for this table. I did NOT and cannot read the live `applications` constraints from here (no DB reachable); the one confirmed live-only constraint, `applications_user_position_key`, is irrelevant to this additive table — the FK `references public.applications(id)` targets the PK, which every migration-provisioned and live DB has. **CITED, NOT VERIFIED against a live DB:** that `applications.id` is a selectable PK target. It is relied on identically by `application_digests` which is in production, so the risk is nil, but it is not something I instrumented this round.

### 1.4 Stored JSONB shape of a pool entry (AC-N143-3)

`projects` is a JSON array of 0..N entries. Each entry:

```
{
  competency:   string   // the distinct competency area this project demonstrates,
                         //   e.g. "incident response", "curriculum design", "patient triage".
                         //   DOUBLES AS THE STABLE PER-ENTRY IDENTITY (see §4, §7): entries
                         //   span DISTINCT competencies (AC-N143-5), so competency is the key
                         //   logged and the key the mis-selection discriminator (AC-N143-Q (d))
                         //   reads. No separate id field.
  domain:       string   // the role-domain framing, e.g. "SRE", "K-12 teaching", "ICU nursing".
  title:        string   // short hypothetical project name.
  body:         string   // 2-4 sentence hypothetical narrative, THIRD-PERSON / hypothetical
                         //   framing ("A strong candidate might describe…"), invented figures only.
  hypothetical: true     // provenance marker. ALWAYS true. Never absent, never false.
}
```

- **No field may hold a posting figure verbatim** (AC-N143-3 / AC-N143-15). This is enforced at generation time by the number-safety guard (§3.4) BEFORE the pool is persisted — the schema cannot enforce it, so it is a generation-pass invariant, not a column constraint. I state plainly: the table has no mechanism that prevents a bad writer from storing a posting number; the only control is the guard in the generation module, checkable by a unit test over that module (AC-N143-15 instrument), not by the DB.
- **One row per application** (PK = `application_id`): "does this application have a pool" is a PK lookup; cascade-deletes with the application (AC-N143-3 deletion test, assertable via the FK/cascade shape test when no live DB is available).
- `hypothetical: true` on every entry is the provenance half of the honesty trio (AC-N143-14 i); the row-level `status` + `engine` are the completeness/provenance markers.

### 1.5 Storage lib — `lib/supabase/applicationProjectPool.js` (AC-N143-2)

Modeled on `applicationDigests.js`. Two functions, both take the caller's own `supabase` + `userId` (never resolve a session), scope every query by `user_id` in addition to RLS, and **never throw** (return a result object).

```
getProjectPool(supabase, userId, applicationId)
  -> { pool: row | null, error: string | null }
  // single-row read: .from(TABLE).select("*").eq("user_id", userId)
  //                 .eq("application_id", applicationId).maybeSingle()
  // a missing/empty applicationId returns { pool: null, error: null } with no round trip.

upsertProjectPool(supabase, userId, applicationId, fields = {})
  -> { pool: row | null, error: string | null }
  // COLUMN-WISE WHITELIST upsert on onConflict "application_id", exactly like upsertDigest:
  //   row = { application_id, user_id, updated_at: new Date().toISOString() }
  //   if Array.isArray(fields.projects) row.projects = fields.projects
  //   if typeof fields.status === "string" row.status = fields.status
  //   if typeof fields.error === "string" || fields.error === null row.error = fields.error
  //   if typeof fields.engine === "string" || fields.engine === null row.engine = fields.engine

  // the `applicationDigests.js:66` lesson. Anything added to `fields` must be added here,
  // spelled exactly as the column.
```

The hook (§2) also needs a multi-id read for the tracking-table fan-out:
```
listProjectPools(supabase, userId, applicationIds)

```

**Diff-applicable invariant (AC-N143-2):** the upsert `row` object is built only from the explicit whitelist arms above; a reviewer flags any `row[x] = fields[x]` added without a matching migration column, and any `...fields` spread. Instrument: lib test — a field not on the whitelist never reaches the fake client; a transient PostgREST error returns `{ error }` not a throw; an upsert omitting `projects` leaves it unchanged.

## 2. Prewarm trigger (D2) — DECISION: digest-style lazy, NOT the tailor-flow hook

### 2.1 The decision

**(b) digest-style lazy prewarm.** Reject (a) the tailor-flow hook in `app/page.js`.

### 2.2 Why (a) the tailor-flow hook loses

- It touches `app/page.js` (the god-component the [[page.js consolidation]] effort is actively shrinking), in THREE handlers (`handleUrlSubmit:2142`, `handleTailorJob:1877`, `handleTailorFeedPosting:2386`), each of which already does its own `upsertApplication(... STATUS.TAILORED)`. Three new fire-and-forget call sites in the most-contended file in the repo.
- It **misses coverage**: the `20260906…` header notes `applications` is written by six separate call sites; a user who TRACKS a posting without tailoring (or whose row is created by one of the other writers) never gets a pool. The owner's bar is "warm by interview time," not "warm only if you tailored."
- A client fire-and-forget at tailor time is fragile against navigation/unmount, and it duplicates the dedupe/no-poison/limiter logic the digest idiom already has solved.

### 2.3 Why (b) wins, and how it stays "warm by interview time"

The digest idiom (`useApplicationDigests` + `selectAutoDigestTargets` + the route's gates) is a proven lazy-prewarm-with-cost-gate. Reusing it gives, for free: once-per-id-set fetch (`loadedKeyRef`), per-id in-flight dedupe (`inFlightIdsRef`), failure-merge-not-blank, the module-scope limiter, the already-`ready`/`failed` short-circuit, and the no-poison failed row.

The owner's phrasing "generated when I first applied" is a *lead-time* requirement, not a literal "on the apply handler" requirement. Lead time is bought by WHERE the lazy hook mounts, and I mount it in two places, earliest-first:

1. **Primary — the tracking tab.** `useApplicationDigests` already fans out on tracking-table load. A sibling hook `useApplicationProjectPool(applications)` (same file-level neighbour, same shape) fires pool prewarm on the SAME window digests use. Users review the tracking table well before an interview, so this is the main warm-up window and matches the digest's own "warm by the time you need it" track record.
2. **Secondary — copilot posting-selection.** `CopilotClient.js` already knows the selected posting (`posting.id` = applicationId; seen threaded through `useDraftAnswer`'s `postingRef`). Mounting the same lazy prewarm there (fire once per selected applicationId, same dedupe) covers the straight-to-copilot path and the copilot SessionSetup phase that precedes the first live question. Exact wiring inside CopilotClient is 1c/plan's to place; the SEAM is: on a posting with an id becoming selected, call the same `runOne(applicationId)` the hook exposes.

The residual race — user goes straight to copilot AND asks question 1 before generation settles — is covered by AC-N143-8's honest pending state (Row 1 renders neutral/absent, never stale/fake, never blocks the answer).

I considered and rejected adding BOTH (a) eager tailor-time AND (b) lazy as a belt-and-suspenders hybrid: the extra coverage from (a) is marginal over mounting (b) at the tracking tab, and it reintroduces the `page.js` cost. I am **not** escalating this to the owner — AC D2 assigns it to 1b. (If the owner later wants the absolute-earliest warm at apply time, (a) can be added as a thin call to the same `runOne`, no contract change — noted, not built.)

### 2.4 The prewarm route — `app/api/application-project-pool/route.js` (AC-N143-4, AC-N143-17)

Placed to parallel `app/api/application-digest/route.js` (prewarm concern, fired from tracking, not from the answer path). POST, `runtime="nodejs"`, `dynamic="force-dynamic"`, and a `maxDuration` chosen to clear the generation worst-case (see §3.5 for the retry/timeout budget — the `application-digest` route's `maxDuration=120` mid-retry-kill lesson applies: a function killed mid-retry writes no `failed` row and re-arms the stampede).

**Gate order, mirroring `application-digest` exactly:**
1. `auth.getUser()` → `unauthorized()` if no user.
2. **module-scope rate limiter** (AC-N143-17): `const projectPoolLimiter = createRateLimiter({ limit: 12, windowMs: 600_000, prefix: "application-project-pool" })` built at MODULE scope (the `application-digest` header states why a per-request limiter permits everything and counts nothing). Checked ahead of body validation, keyed on the authed user id via `identify(request, { userId })`, denied-still-increments. 12/10min is the digest number; each miss is one billed generation. Owner may retune the ceiling (D1-adjacent, non-blocking).
3. body parse → `badRequest` on bad JSON.
4. `applicationId` present + capped.
5. ownership: `.from("applications").select(... positions(...)).eq("id").eq("user_id", userId).maybeSingle()` — scoped in the query, not post-hoc; `notFound` if absent.
6. embedded-engine refusal (§3.6): `wantsEmbedded(body?.engine)` → 503, no generation.
7. **failed-read-is-not-a-miss**: `getProjectPool` returning `{ error }` → 500, never treated as "no pool."
8. **already-`ready`-and-not-`force` short-circuit**: a `ready` pool returns as-is unless `body.force === true`. A `failed` pool is likewise not regenerated unless `force` (no auto-retry — AC-N143-4). The hook's auto path never sends `force`; a future explicit "regenerate" control sends it.
9. generate (§3) → number-safety guard (§3.4) → `upsertProjectPool({ status: "ready", projects, engine: "gemini", error: null })`.

**No-poison failure path (AC-N143-9, = N130):** a generation throw is caught and persisted as `upsertProjectPool({ status: "failed", error: message, engine: "gemini" })`, returning 200 (the failure is the answer, not a broken route). `projects` is NOT overwritten on failure (column-wise upsert leaves a prior `ready` pool standing if one somehow existed). A failed failure-write is `console.error`-logged, never swallowed (a missing row re-arms the stampede).

**Cost gate (AC-N143-4):** one generation per application until `ready` or `failed` exists; the hook's `selectAutoProjectPoolTargets` (sibling of `selectAutoDigestTargets`, in a pure module `lib/tracking/applicationProjectPool.js` or reusing the digest selector's shape) returns only rows with NO pool row at all, newest-first, bounded by a max-age window and `AUTO_*_CONCURRENCY`. A `ready` OR `failed` row is excluded either way.

**Diff-applicable invariant (AC-N143-17):** `projectPoolLimiter` is declared at module scope and its `.check()` precedes the body parse in `POST`; a reviewer flags any move of the `createRateLimiter(...)` call inside `POST`. Instrument: the behavioural over-limit test (fire 13, assert the 13th denied) + the static `adoption.test.js`-style check that the declaration precedes the handler.

### 2.5 The hook — `app/hooks/useApplicationProjectPool.js` (AC-N143-4)

Byte-for-byte the `useApplicationDigests` shape: `loadedKeyRef` (once per distinct id-set), `inFlightIdsRef` (per-id synchronous dedupe), `requestProjectPool(applicationId,{force})` POSTing to the route, a `runOne` that MERGES failure fields over existing data on a network-level throw (never blanks — the C-6 lesson), reads stored pools first via `listProjectPools`, then fans out `selectAutoProjectPoolTargets` through `runWithConcurrency`. Returns `{ poolsById, prewarmingIds, regenerateOne }`.

## 3. Generation contract + the quality-critical prompt (the crux)

v1 died because it shipped a generic "owned a problem end-to-end, here are process metrics" skeleton with the posting's domain slotted in. The structural job here is to make the wrong-kind project HARD to produce, and to make the parts that CAN be checked mechanically checkable, while being honest that content domain-relevance is owner-env only (AC-N143-Q).

### 3.1 Module boundary

One shared generation module, imported by BOTH the prewarm route (pool) and the Row-2 sub-route (on-the-spot):

`lib/copilot/projectExampleGen.js` — pure prompt assembly + output parsing + the number-safety guard. No Supabase, no fetch; takes a Gemini client as an argument (the `answerAids.js`/`projectStories.js` precedent of "pure, client handed in"). Exports:

```
PROJECT_POOL_SIZE = 5                      // AC-N143-5 / D1: named, owner-surfaced, owner-tunable constant.
buildPoolPrompt(posting)                   // -> { system, user } for the N-entry pool
buildOnTheSpotPrompt(posting, question)    // -> { system, user } for ONE question-matched project
parsePoolResponse(rawText)                 // -> { projects: Entry[] } | throws on unusable
parseOnTheSpotResponse(rawText)            // -> Entry | throws on unusable
stripPostingFigures(entry, posting)        // the number-safety guard (§3.4); returns a safe Entry
```

This shared module is the one thing two routes import — per [[disjoint-subagents]] it lands in its OWN earlier wave, before the two routes that consume it (plan note).

**Do NOT resurrect `idealProjectPrompt.js`** (deleted N141). This is a clean build applying its lessons; the deleted file is not a template.

### 3.2 Engine path and engine-selection flow

Generation goes through the EXISTING Gemini client, `models.generateContent` with `config: { systemInstruction, responseMimeType: "application/json" }` — the same shape the answer route's non-streaming branches use. **Not** `interactions.create` (that is grounded search, used only by `application-digest`; these projects are invented, never web-grounded — grounding one would risk copying a real company's real project). Engine selection flows via `wantsEmbedded(body?.engine)` at each route's gate (§2.4 step 6, §5), exactly as every other aux feature does.

### 3.3 The prompt approach — forcing question/role-domain relevance

**System instruction (both generators) establishes, in this order:**
1. The task is to invent a HYPOTHETICAL, illustrative example project a strong candidate in this role COULD describe — explicitly third-person/hypothetical framing ("A strong candidate might describe a project where…"), NEVER phrased as the candidate's own experience, NEVER "I did X."
2. **Domain anchoring is mandatory and is the whole point.** Each project's `competency` and `domain` must be derived from the ROLE (pool) or the QUESTION (on-the-spot), and the `body` must name domain-specific artifacts, tools, stakeholders and outcomes — a curriculum and learning objectives for a teaching role, a runbook and an SLO/error-budget for an SRE role, a care plan and triage protocol for nursing — never generic "a process," "a workflow," "stakeholders," "KPIs."
3. **Explicit negative constraints** (the v1 autopsy, turned into rules): do NOT produce a one-size-fits-all "owned a problem end-to-end with process metrics" skeleton; do NOT reuse the posting's own numbers (salary, comp, headcount, any figure); invent plausible, domain-appropriate figures instead; two projects must not share a skeleton.
4. Output STRICT JSON, no prose, matching the contract in §3.4.

**Pool user prompt (`buildPoolPrompt`)** — forces competency SPREAD so per-question matching has real variety (AC-N143-5, and the AC-N143-Q (c) "pool too narrow" cause):
- Step 1: from the posting (title + description), enumerate the role's `PROJECT_POOL_SIZE` MOST DISTINCT competency areas — areas a candidate for THIS role would be asked about, as different from each other as the role allows.
- Step 2: for EACH competency, invent ONE project demonstrating it, each with a distinct `domain` framing where the role spans sub-domains.
- Output a JSON array of exactly `PROJECT_POOL_SIZE` entries with distinct `competency` values.

**On-the-spot user prompt (`buildOnTheSpotPrompt`)** — forces QUESTION fit (the AC-N143-Q (a) "ignores the question" cause):
- Given THIS question plus the role, identify the competency the question probes, then invent ONE project that directly demonstrates answering THAT question well in THIS role's domain. One JSON object.

The posting description is passed to the generator for ROLE/domain grounding only; it is NEVER echoed and its numbers are stripped (§3.4). (This mirrors `buildDigestPrompt`'s "shown for reference, do not restate" posture.)

### 3.4 Output JSON contract + invented-figure safety (AC-N143-3, AC-N143-15)

Pool: `{ "projects": [ Entry, Entry, … ] }`. On-the-spot: a single `Entry`. `Entry` = the §1.4 shape, with `hypothetical` forced to `true` by the parser regardless of what the model returns (the parser sets it; the model is not trusted to).

**Number-safety guard — `stripPostingFigures(entry, posting)`** (the R-130/R-135/R-138 class):
- Extract the posting's SIGNIFICANT numbers (compensation/salary bands, headcount, and other significant figures) with a dedicated extractor — reuse an existing significant-number/comp extractor if one is already in the repo; else a small one in this module (the plan/3b must confirm which exists; I did not locate one this round, so this is a **build-or-reuse decision flagged to the plan**).
- Reject or strip any benchmark `body` number that collides with a posting significant number (the R-135 invariant: posting salary/comp/headcount never appears as a project figure).
- Do NOT over-reject incidental small integers (AC-N143-15 failure direction — "cut deploys from 5 to 1" must survive; "$145,000" matching the posting band must not).
- Runs BEFORE persist (pool) and BEFORE return (on-the-spot), so no posting figure ever reaches storage or the wire.

**Diff-applicable invariant (AC-N143-15):** every entry returned by `parsePoolResponse`/`parseOnTheSpotResponse` passes through `stripPostingFigures` before it leaves the module; a reviewer flags any return path that skips it. Instrument: the normalize-guard test with a salary-band posting (collision stripped; invented small integers kept) + a positive control.

**Diff-applicable invariant (AC-N143-5):** pool size is `PROJECT_POOL_SIZE` (the named constant), not a literal buried in the prompt string; entries carry distinct `competency` values. Instrument: the constant-driven size assertion + distinct-competency structural check. Spread QUALITY is owner-env (AC-N143-Q).

### 3.5 Timeout / retry budget

`models.generateContent` makes ONE attempt (unlike the Interactions transport's 3) — the `application-digest` header's retry math does not apply. Still set a per-call `{ timeout }` and a route `maxDuration` that clears it, so a slow generation is caught and written as `failed` rather than killing the function mid-call and leaving no row (the stampede-rearm lesson). I propose `maxDuration = 120` (the digest number, ample for one non-streaming call) and a per-call timeout well inside it; **this is a guess flagged owner-tunable per the [[round-2-escalation]] / RETRO-695e23d owner-tunable-threshold rule** — surface it as a named constant, route its retune into the AC-N143-Q probe sitting.

### 3.6 Embedded engine — refuse, never template (flagged to checker)

## 4. Selection seam — per-question best-match from the pool (AC-N143-6, AC-N143-7)

### 4.1 Where and how

A new pure function in `lib/copilot/projectExampleSelect.js` (kept separate from the generation module so the browser-safe selector does not drag a Gemini client into any bundle; it only needs the tokenizer):

```
selectPoolProject(pool, { question }) -> Entry | null
```

- `pool` is the stored `projects` array (0..N entries) for the application.
- Reuses `significantTerms` + `overlapScore` from `lib/copilot/projectStories.js` (already browser-safe, already imported client-side). Score each entry's `${competency} ${domain} ${title} ${body}` against `significantTerms(question)`; keep the strictly-higher scorer; ties keep array order. This is the SAME ranking class as `selectBestStory`/`buildKnowledgeBaseBlock` (AC-N143-6).
- **Deterministic, zero model calls** (AC-N143-6). No honesty gate (unlike `selectBestStory`): every pool entry is explicitly `hypothetical: true`, so there is no "decline to speak the candidate's own page" concern — we always return the best match when the pool is non-empty, and `null` only when the pool is empty/absent.
- Returns `null` for an empty/absent pool → Row 1 renders the pending/absent state (§6).

### 4.2 Computed in the ANSWER route, fresh, never cached

The route computes `const projectExample = selectPoolProject(pool, { question })` AFTER the capped `question` is read, on the SAME line-class as `const story = selectBestStory(pages, { question, points: [] })` (route.js:529). `pool` arrives from the context fan-out (§4.3). The pick rides the done-frame (§6); it is NEVER written into `answerSessionCache.js`, the pool row, or any per-session store (AC-N143-7).

This is the exact parallel to `pages` (cached, question-independent) → `selectBestStory` (fresh, question-ranked). The cache header (answerSessionCache.js:32-42) forbids caching "the selected story"; the selected POOL ENTRY is the same category and is forbidden the same way. The POOL itself is cacheable (question-independent, app-scoped) — §4.3.

**Diff-applicable invariant (AC-N143-7):** `selectPoolProject`'s result is assigned to a route-local const and spread onto the done frame only; it never appears as an argument to `answerContextCache.set`/`.get`, never as a field in the cached raw object, never in `upsertProjectPool`. A reviewer flags any write of the selected entry into a cache or the pool row. Instrument: mirror `route.latency.test.js` — two different questions in one session select two different entries (no stale carry); plus a static assertion the pick never enters the session cache. This is ALSO a standing non-regression guard on the cache invariant.

### 4.3 Pool read placement — add `pool` to `answerContext.js`'s cached fan-out (flagged to checker)

The route needs the stored pool per question. Add a 6th member to `fetchRawContext`'s `Promise.all` (`answerContext.js:69`): `getProjectPool(supabase, { applicationId, userId })` (adapt the arg shape — the storage lib takes positional `userId, applicationId`; wrap or adjust), return `pool` in the raw object (`answerContext.js:92`), and pass it through `loadAnswerContext` with NO cap (structured JSONB, not a string). The route destructures `pool` alongside `resume, coverLetter, posting, employer, pages` at route.js:419.

**Why here, not a separate read:** the pool is app-scoped and question-independent — exactly the data this cache exists for (the module header: "raw fetch results … no dependency on the question"). A separate per-question read would defeat the cache and add a round trip per question.

**Blast radius of the `answerContext.js` edit — enumerated (AC-N143-7, cache correctness):**
- `route.latency.test.js` reads `call[1].userId` POSITIONALLY on `fetchApplicationDocs` (the Promise.all member at index 0). Adding the new member at the END of the array does not shift index 0, so that positional read stays valid — **the new member must be appended last, not inserted**. Diff-applicable: reviewer flags any insertion ahead of `fetchApplicationDocs`.
- The cached raw shape gains `pool`; every test that asserts the exact raw-object keys (answerContext's own tests) must add `pool`.
- The cache invariant is preserved BECAUSE `pool` is a raw fetch result, not a ranked value. The ranked `projectExample` stays in the route.

## 5. On-the-spot Row 2 wiring (AC-N143-10, AC-N143-11)

### 5.1 Mechanism — separate fetch, NOT a post-`done` stream frame

**Decision: a separate fetch to a new sub-route**, fired by the client AFTER the answer (and Row 1) resolve.

The alternative — a second streamed frame after `done` on the answer stream — is **structurally blocked** and I verified why in source: `answerClient.js`'s `draftAnswerStreaming` sets `settled` on the FIRST `done` frame and immediately `break`s the read loop (`if (settled) return;` in `consume`, `if (settled) break;` in the reader loop, lines 107-128), then resolves with that frame. A frame after `done` is never consumed. The documented contract is "resolves with the terminal `done` frame's payload." Changing that is a large blast radius (the streaming client, `answerClient.streaming.test.js`, `useDraftAnswer`'s resolve path) AND it helps ONLY the live streaming path — practice mode and the embedded engine use non-streaming `draftAnswer` (single JSON), so they would get no Row 2 at all. A separate fetch covers all three surfaces and both engines uniformly, is truly non-blocking, and matches the retired pattern.

### 5.2 The sub-route — `app/api/copilot/answer/project-example/route.js`

Placed UNDER `app/api/copilot/answer/` so the on-the-spot generation call site is in `app/api/copilot/answer/` and ABSENT from `app/api/copilot/question/` (AC-N143-10 instrument (a), a static route-graph check). POST, takes `{ applicationId, question, engine }`.

- Gates: auth → **own module-scope rate limiter** (D3; see §5.4) → body/question cap (reuse `MAX_QUESTION_CHARS`) → ownership query scoped by user_id → embedded refusal (§3.6, returns `{ projectExample: null }` not a hard error) → generate ONE on-the-spot project via `buildOnTheSpotPrompt` + `models.generateContent` → `stripPostingFigures` → return `{ projectExample: Entry, status: "ready" }`.
- **Never persisted, never cached server-side** (AC-N143-10 "generated live per question"). The pool table is not touched by this route.
- **No-poison (N130):** a generation throw returns `{ projectExample: null, status: "failed", error }` with 200 — never a 5xx, never a thrown error that the client surfaces as a torn-down answer.

The question route (`app/api/copilot/question/route.js`) gains NO model call for this feature (AC-N143-10, scope).

### 5.3 Client wiring — fire after the answer resolves, swap in

New client fn in `lib/copilot/answerClient.js`: `fetchProjectExampleLive({ applicationId, question })` → POST the sub-route → return the parsed `{ projectExample, status }`.

In `useDraftAnswer.js`, AFTER the answer resolves and the `done` setQuestions write lands (the point where `aids` are set, ~line 296), fire `fetchProjectExampleLive(...)` NON-BLOCKING (not awaited inline with the answer). On resolve, a SECOND `setQuestions` sets `it.projectExampleLive` on the same entry, guarded by the SAME `it.id === id && it.draftToken === token` check every post-await write uses (so a superseded draft's Row 2 cannot repaint a card the user moved on from). On reject/timeout, set `it.projectExampleLive = { status: "failed" }` — the answer and Row 1 are untouched.

Practice mode (`useSampleAnswer` / `PracticeClient`) and the dashboard (`useCopilotDashboard`) get the same post-answer fire + swap. (The precise hook internals for practice/dashboard are plan/1c's; the SEAM is identical: fetch after the answer, set `projectExampleLive` on the entry/state.)

**Diff-applicable invariant (AC-N143-10/11):** the `fetchProjectExampleLive` call is NOT awaited before the answer's `done` setQuestions write; the answer's first content and Row 1 are emitted independent of Row 2 settling. Instrument: (a) static route-graph check (call site under `answer/`, absent from `question/`); (b) an answer-route test that a Row-2 rejection/timeout still yields the answer + Row 1; (c) an ordering/latency test (first content independent of Row 2).

### 5.4 Row 2 rate limit (D3)

The Row-2 sub-route is NEW, so it gets its OWN module-scope limiter mirroring `digestLimiter` — this is not the "meter the existing answer route" posture the AC scoped OUT. Keyed on the authed user id, denied-still-increments. Each Row-2 request is one billed generation per question, so a modest ceiling is warranted (I propose the digest 12/10min as a starting number; **owner may set the ceiling — D3, non-blocking**, surfaced as a named constant). ## 6. UI data threading (AC-N143-12, 13, 14, 8, 9, 18)

### 6.1 Two new fields on the dashboard answer entry / done-frame

Row 1 (server-computed, rides the answer done-frame) and Row 2 (client-fetched async) become two new fields alongside `buzzwords`/`anchor`/`pageSources`:

- `projectExample` (Row 1): `{ status: "ready", competency, domain, title, body, hypothetical: true, engine } | { status: "pending" } | { status: "failed" }`. Never `null`-as-ready; `null`/`undefined` is coerced to pending by the component.
- `projectExampleLive` (Row 2): same shape; `{ status: "pending" }` until the §5 fetch resolves, then ready/failed.

**Status derivation for Row 1 on the done-frame (honesty, AC-N143-14):** the route sets `projectExample` from BOTH `selectPoolProject` and the pool row's `status`:
- pool absent or `status==='pending'` or empty `projects` → `{ status: "pending" }`.
- pool `status==='failed'` → `{ status: "failed" }`.
- pool `ready` and a pick exists → `{ status: "ready", ...pick, engine: pool.engine }`.
This is the no-overclaim contract: a pending/failed/empty pool is NEVER sent as a ready benchmark.

### 6.2 Threading path

Done-frame (route `streamAnswer` done object + all four JSON branches) gains `projectExample`. `answerClient.js` returns the body verbatim (no plumbing). `useDraftAnswer.js` destructures `projectExample` from the resolved payload, normalizes it into `aids` (default `{ status: "pending" }` when missing — same defensive normalization `buzzwords`/`anchor` get), caches it in `answerCacheRef` (keyed by normalized question — this is the CLIENT per-question cache, NOT the forbidden server session cache; reusing q1's pick for q1-again is correct), and sets it on the entry. `projectExampleLive` is set by the separate §5.3 write. QuestionFeed/dashboard read `q.projectExample` / `q.projectExampleLive`; practice `SampleAnswer` reads them as props.

The `answerAids({...})` server helper (`lib/copilot/answerAids.js`) stays as-is for `buzzwords`/`resumeAnchor`; `projectExample` is spread onto the done object by the route NEXT TO `...aids` (it needs the `pool` + `question`, which the aids helper is not given — keep it in the route, like `pageSources`).

### 6.3 The component — two new `<Aid>` rows (AC-N143-12, 13, 14, 8, 9)

`AnswerAids.js` gains two props: `projectExample`, `projectExampleLive`. It renders each as an `<Aid>` row INSIDE the résumé group, BESIDE (after) the existing "Project to talk about" row (:229), reusing the `Aid` row shape and `AID_GRID_SX` (so the single-column `dt,dd` collapse + `BREAK_LONG_WORDS_SX` carry over — AC-N143-18 DOM contract). The component stays purely presentational: it fetches nothing, decides no content — it only maps status→render (AC-N143-12 static no-fetch/no-model-import check).

Render rules (the honesty consumer, AC-N143-14 ii / AC-N143-8 / AC-N143-13):
- `status==='ready'`: render `title` + `body`, under a label like **"Example project to borrow from"** PLUS a visible disclaimer in the spirit of the deleted feature's wording — "Not from your resume. This example and its numbers are invented." The disclaimer is REAL TEXT (survives flattening, like the BUG-K2 bullet char), with an accessible marker.
- `status==='pending'` (or prop missing): a neutral placeholder/pending state (e.g. "Preparing an example…") or nothing — NEVER a stale/fabricated benchmark. Never blocks the answer or the other rows.
- `status==='failed'`: a degraded, non-blocking signal (e.g. "No example available") — never a crash, never a fake benchmark.
- **Provenance-ambiguity rule (AC-N143-13):** if a row's content is present but its provenance/`hypothetical` marker is absent or ambiguous, it renders AS hypothetical (with the disclaimer), NEVER as the candidate's real experience. The existing "Project to talk about" (real) row carries NO hypothetical disclaimer and is thereby visually/textually distinct from the two invented rows.

**Diff-applicable invariant (AC-N143-13/14):** the branch that renders a project-example `body` is reachable ONLY when `status==='ready'`, and that branch always renders the disclaimer text; a reviewer flags any render of `body` outside a `status==='ready' && disclaimer` guard. Instrument: jsdom fixtures — `status:'failed'` and `status:'pending'` red if a benchmark renders as ready; a fixture dropping the `hypothetical`/label reds the render; a ready fixture asserts both rows carry the disclaimer and an accessible invented-marker.

### 6.4 Composite-surface note (rule 6b, for 8b / N144)

This takes `AnswerAids` from up to 3 rows to up to 5, three of them now "projects" (one real, two hypothetical). The real-vs-invented legibility risk inside the height-locked live wrapper is real. THIS chunk's mitigations are AC-N143-13 (clear distinction) + AC-N143-18 (layout non-regression, single-column + break-long-words at `xs`). ## 9. Alternatives considered and why they lost

- **Tailor-flow hook trigger (D2 option a):** rejected — touches the god-component `page.js` in 3 handlers, misses non-tailored tracked applications, duplicates the digest idiom's solved dedupe/no-poison/limiter. (§2.2)
- **Post-`done` stream frame for Row 2:** rejected — the stream client treats `done` as terminal and stops reading (verified, answerClient.js:107-128); large blast radius and helps only the live streaming path, leaving practice/embedded with no Row 2. (§5.1)
- **Separate uncached per-question pool read in the route:** rejected — defeats the per-session cache the pool is a textbook fit for; adds a round trip per question. (§4.3)
- **Embedded deterministic template:** rejected — a canned template is the exact v1 failure that got the feature deleted; the honest offline equivalent is nothing. (§3.6)
- **Explicit `pending` row written at generation start:** rejected for v1 — a stuck `pending` row needs a TTL to recover (the digest `maxDuration` mid-retry-kill class). Absent-row = pending is simpler and matches the proven digest posture; `'pending'` stays in the CHECK set for the column default and future use. (§1.2)
- **Caching the per-question pick anywhere:** rejected — it is the exact "answer question two with question one's selection" hazard the cache header names. (§4.2)
- **Grounded (Interactions API) generation:** rejected — these projects are invented; grounding risks copying a real company's real project, and the invented-figure safety would be meaningless. (§3.2)
- **`competency` + a separate per-entry `id`:** rejected — competency is distinct across the pool by construction (AC-N143-5), so it is already a stable identity for logging and the mis-selection discriminator; a second id is dead weight. (§1.4)
