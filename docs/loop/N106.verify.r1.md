## Adjudications requested

**(i) `authorityReferenceSpans` — §7 (`draft.spans`) vs §2 (`[]`) for internal-consistency.** The code (`buildJudgeRequest`, reviewDocuments.js:84-99) sets `authorityReferenceSpans = referenceSpans` = `draft.spans` via `selectAuthorityReference` — i.e. it follows **§7**, which is the correct intent (the judge needs the draft's own spans as the internal-coherence yardstick; `[]` would starve it). §2's "`[]` for internal-consistency" is **stale design text**; §7 is authoritative. **Does NOT affect AC-2's slice-1 guarantee**: the deterministic `detectAuthoritySkeleton` uses `selectAuthorityReference` directly (never `judgeRequest`), and no slice-1 judge consumes `authorityReferenceSpans`. **No slice-1 test covers it, and none is needed for slice-1** (no judge reads it); a slice-2 test should pin it when `geminiJudge.js` ships. → **M1 (minor, doc + slice-2 test).**

Secondary observation while adjudicating (i): `buildJudgeRequest` passes the WHOLE `realMaterial` at `judgeRequest.realMaterial` (reviewDocuments.js:97). So design §4's claim that the judge is "physically scoped away from `realMaterial` on internal-consistency drafts" is **not literally true** — `realMaterial` is globally present in the request; only `authorityReferenceSpans` is per-draft scoped. No slice-1 impact (no judge), but it is a real slice-2 risk: a misbehaving judge COULD read `realMaterial` for an internal-consistency draft. → **M2 (minor, slice-2).**

## Findings

- **M1 (minor, doc/slice-2):** design §2 says `authorityReferenceSpans=[]` for internal-consistency; code+§7 use `draft.spans`. §7 is correct; §2 is stale.
