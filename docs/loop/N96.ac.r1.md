## 1. The domain distinction this chunk turns on: `null` (source-default) is NOT `{1, 0}`

The single most important correctness point, and the one an indicator gets wrong by default:

- `spacing === null` ⇒ the document keeps its **own** line-height and paragraph margins as parsed
  from the source docx (`docxPreview.js` reads real `spaceBeforePt`/`spaceAfterPt` per paragraph;
  the preview's uniform fallback is `lineHeight: 1.3`). The app does **not** know these are "1x"
  or "0pt" — they are whatever the candidate's template specifies, and vary per paragraph.
- `spacing === {lineSpacing:1, paragraphSpacingPt:0}` ⇒ the app **forces** single line-height and
  zero paragraph space on every `<p>`/`<li>`.

**Therefore a readout that renders `null` as "1x line, 0pt paragraph" is a LIE** — it claims the
app is applying values it is not, and claims to know spacing it does not. **Failure direction
(governs AC-1 and AC-3):** when `spacing===null`, the indicator must say "Default / your document's
own spacing", never assert specific numbers; the safe direction is under-claiming (show "Default")
over over-claiming (show fabricated "1x/0pt"). This is the analogue of the egress rule "prefer
wording that over-claims what leaves the machine" — here, prefer wording that under-claims what the
app has changed.

## 2. Acceptance criteria

Each is written so the SAFE direction is the passing one. "RED on HEAD" = fails today before any
implementation, with the current-tree fact that makes it red. Every value assertion is against the
RENDER (an attribute/textContent on the mounted real dialog), never "the source file contains a
string" (anti-zero-power). The instrument for the mountable criteria is a jsdom vitest that mounts
the REAL `DocumentPreviewDialog` and reads its output — exactly the harness
`DocumentPreviewDialog.spacing.test.js` already uses (mount real dialog; MUI Dialog portals to
`document.body`; query the whole document). jsdom does layout-free rendering, so declared
attributes and textContent are readable; geometry is not (see AC-8).

### The current value is legible — as a number, not only a highlight

**AC-1 — the control shows the CURRENT line multiplier AND paragraph points explicitly, matching
the applied `spacing`; `null` reads as source-default, not fabricated numbers.**
When `spacing = {lineSpacing:1.5, paragraphSpacingPt:12}`, the mounted control MUST render a
human-readable readout whose text conveys **both** the active line multiplier (`1.5`) and the
active paragraph points (`12`) — e.g. a `data-testid="spacing-current"` region whose textContent
contains "1.5" and "12". When `spacing = null`, that region MUST convey a **default/source** state
(e.g. text containing "Default" or "your document") and MUST NOT contain a fabricated numeric
claim (no "1x", no "0pt", no "1.0").
- Instrument: mount the dialog with each of `{lineSpacing:1.5,paragraphSpacingPt:12}`,
  `{lineSpacing:2,paragraphSpacingPt:6}`, and `null`; assert the readout's textContent for each.
  DISCRIMINATOR (guards against a hardcoded label): the `1.5/12` and `2/6` cases must produce
  **different** text — a readout that prints a constant fails. The `null` case must NOT match
  `/\b1(\.0)?x?\b|\b0\s*pt\b/`.
- RED on HEAD: **YES.** No textual readout exists — the only indicator is the button variant
  (`SpacingControl.js:52,68`), and `null` renders as all-outlined with no numeric readout at all.
  Read directly.
- Failure direction: fail toward "Default" for `null`; a criterion satisfied by printing "1x, 0pt"
  for the source-default state is WRONG (§1) and must be reported as such by the checker.
- Note: the active-preset **highlight** (contained variant) already exists and is fine to keep;
  AC-1 requires the **explicit value readout** on top of it, which is the new work. This is not a
  request to remove the highlight.

**AC-2 — the active/current value is PROGRAMMATICALLY DETERMINABLE and ANNOUNCED, not only drawn
(N84).**
The active state MUST be exposed to assistive tech, by BOTH of: (i) the active preset control
carrying a machine-readable selected state (`aria-pressed="true"` or `aria-current`, with inactive
peers carrying the false/absent counterpart), AND (ii) a change being announced through a polite
live region (reusing the dialog's `[role="status"]` pattern, `DocumentPreviewDialog.js:883-886`) OR
the readout of AC-1 living inside such a live region so a value change is spoken.
- Instrument: (i) mount with `{lineSpacing:1.5,...}`; assert the `spacing-line-1.5` control has
  `aria-pressed="true"` and, as a canary, that `spacing-line-1` has `aria-pressed="false"` (a scan
  that finds the active one but never a false one is not discriminating). (ii) drive a click that
  changes the value and assert the live region's textContent updated to reflect the new value
  (using the real-control-operation harness, not a direct setter).
- RED on HEAD: **YES.** MUI `Button` with `variant="contained"` sets no `aria-pressed`/
  `aria-current` (verified: `SpacingControl.js` passes none), and there is no live region for
  spacing. The active state is invisible to a screen reader today. Read directly.
- Failure direction: an implementation that adds `aria-pressed` to ONLY the active button, or that
  announces on EVERY render (noise), fails the canary / a "announced once per change" sub-check —
  prefer the ToggleButton-style paired state (a structure/craft call for 1b/1e; the mui-a11y memory
  notes MUI's non-native Select breaks 2.5.3 and native breaks label-shrink — a `ToggleButtonGroup`,
  which sets `aria-pressed` natively, is the low-risk shape, but AC pins the observable, not the widget).

### Default vs custom — the candidate can see they have overridden the document

**AC-3 — a clear, distinct indication of DEFAULT (source) spacing vs CUSTOM (overridden) spacing.**
When `spacing===null` the control MUST present a DEFAULT state (a marker/text distinct from the
custom state, e.g. `data-testid="spacing-state"` reading "Default"). When `spacing` is a non-null
object (any axis set) it MUST present a CUSTOM/overridden state (distinct marker/text, e.g.
"Custom"). The two states MUST be distinguishable by an assertion, not merely by which preset
button is filled.
- Instrument: render `null` ⇒ assert the default marker present and the custom marker absent;
  render `{lineSpacing:1.5, paragraphSpacingPt:null}` ⇒ assert the custom marker present (a
  single-axis override still counts as custom). Rows that can fail = 2 (default-shows-default,
  partial-override-shows-custom) — state this in the test.
- RED on HEAD: **YES.** No default/custom marker exists; `null` and a set value differ today only
  by button fill. Read directly.
- Failure direction: showing "Custom" when `spacing===null` is a false override claim — the safe
  direction is that `null` reads as Default. A partial override (`{lineSpacing:1.5}` with paragraph
  unset) MUST read as Custom, not Default, so the candidate is never told "you're at default" while
  a value is being applied.

**AC-4 — a discoverable, reachable way back to source-default, and it restores `null` (NOT `{1,0}`).**
When a custom spacing is set, the control MUST offer a reachable affordance (a "Default"/"Reset"
control, present and enabled) that, when operated, calls `onSetSpacing(scope, null)` and returns
the control to its Default state (AC-3) and the readout to source-default (AC-1). It MUST reset to
`null`, NOT to `{lineSpacing:1, paragraphSpacingPt:0}`.
- Instrument: mount with a custom spacing via the reachability host (real control operated, per the
  N69 test's `SpacingHost` pattern — a direct setter call does not prove the affordance is
  reachable, the repo has shipped unreachable controls before); operate the reset affordance;
  assert `onSetSpacingSpy` was called with `(scope, null)` and the preview `<p>` inline style
  returns to its source margin/line-height (no forced `line-height:1`, no `margin:0pt 0 0pt`
  imposed by the control). Canary: the reset affordance is absent/disabled when `spacing===null`
  already (nothing to reset).
- RED on HEAD: **YES.** No affordance produces `null`; the presets can only set explicit values.
  Read directly (`SpacingControl.js:14-24,53,69`).
- Failure direction (the N82 one-way-door trap made concrete): a reset that writes `{1,0}` LOOKS
  like a reset but silently forces single-spacing/zero-gap onto a document whose real spacing was
  something else — it destroys source fidelity while claiming to restore it. The passing direction
  is `null`.
- PRODUCT-CALL NOTE (surfaced to owner, not blocking): a pure reading of "indicators" might not
  include a reset control. I require it because the N82 lesson is explicit — indicating an override
  without a way to undo it is the one-way-door defect. If the owner wants the indicator only and no
  reset this round, AC-4 drops to "the default/custom indicator (AC-3) ships; a reset is deferred to
  its own item" — but I recommend shipping the reset, since AC-3 without AC-4 tells the candidate
  they are overridden and gives them no exit. Flagged for the owner; downstream is not blocked either way.

### Whole-document scope, and it governs both documents

**AC-5 — the indicator reflects that spacing is WHOLE-DOCUMENT (not per-paragraph) and that ONE
setting governs both the résumé and the cover letter.**
(a) The control MUST carry text conveying the whole-document scope (e.g. a "Whole document" label/
hint near the presets), so the candidate does not read it as per-paragraph. (b) The value shown on
the résumé tab and the cover-letter tab MUST be the SAME (the shared `entry.spacing`), so switching
tabs does not misrepresent one document as differently spaced.
- Instrument: (a) mount; assert a label/hint element whose text conveys whole-document scope is
  present. (b) mount the dialog, operate a preset on the résumé tab, switch to the cover tab, and
  assert the readout (AC-1) / active state (AC-2) reflects the SAME value on the cover tab.
- RED on HEAD: (a) **YES** — no whole-document framing exists (`SpacingControl.js:44,60` are bare
  "Line"/"Paragraph"). (b) **NOT RED — invariant/non-regression guard.** The shared single
  `entry.spacing` object already makes both tabs reflect one value (`useDocumentPreview.js:495-504`);
  (b) pins that the new indicator does not accidentally introduce a per-tab value that diverges from
  what is applied. State it as a guard, not as new-work RED.
- Failure direction: the indicator must NOT imply per-paragraph control (none exists) nor
  per-document-independent spacing (the store is shared). Over-implying granularity the app does not
  have is the failure; the safe direction is the honest "one setting, whole document, both files."

### The change indication — synchronous, so no fake spinner

**AC-6 — the indicator updates SYNCHRONOUSLY on a spacing change (the update IS the confirmation);
NO pending/working spinner is shown at preview time.**
Operating a preset MUST update the AC-1 readout / AC-2 active state / AC-3 state marker within the
same interaction (synchronously with the preview re-render), with no intervening "applying…" state.
The control MUST NOT display a spinner, progress indicator, or "changing…" pending state around the
preview spacing change.
- Instrument: operate a preset via the reachability host; assert (in the same `act`, no extra
  await) that the readout AND the preview `<p>` inline style both reflect the new value — matching
  the synchronous update N69's suite already relies on. Negative assertion: no element matching a
  pending/progress role (`[role="progressbar"]`, a spinner testid) appears in the control during/
  after the change.
- RED on HEAD: **YES, by absence** — the AC-1/AC-2/AC-3 targets do not exist yet, so their
  synchronous update cannot be observed. The negative half (no spinner) is **vacuously true today**
  and stated as a guard so no one adds fake latency later.
- FINDING / correction to the brief: the brief hypothesised an async preview re-render (spacing
  "re-runs resolveDocumentBlob") and asked for a pending indicator while it re-renders.
  `applySpacingToHtml` is **synchronous** (`docxPreview.js:355-373`); the preview transform has no
  async step. `resolveDocumentBlob` runs on **download**, not preview, and the download already has
  its own `downloadStatus`. A spinner on the preview spacing change would therefore be **fabricated
  latency** — a "correct fix that adds a lie" — and is OUT of scope (see §4). If a future async
  re-render is introduced, a genuine pending indicator (appears on start, clears on completion,
  announced) would then be warranted; that is a new item, not this one.

### Do not regress how spacing is applied (N69)

**AC-7 — N69's spacing APPLICATION is unchanged.**
The existing `DocumentPreviewDialog.spacing.test.js` suite MUST stay green: operating the presets
still moves `<p>` AND `<li>` inline `margin`/`line-height` on the read-only render;
`applySpacingToHtml` still returns `html` untouched for `null`/all-null; the download still threads
`entry.spacing` (`useDocumentPreview.js:532`); the control stays present-and-disabled (never absent)
on an unavailable scope (N69 CB-D-3 clause ii). This indicator chunk adds display/a11y only.
- Instrument: run `DocumentPreviewDialog.spacing.test.js` and the spacing wiring/persistence tests
  (`useDocumentPreview.spacing.test.js`, `page.spacingPersistence.wiring.test.js`) — all stay green.
- RED on HEAD: **NO — non-regression guard.** Passes today; must keep passing.
- Failure direction: any indicator change that alters the applied `spacing` object shape (e.g. a
  reset writing `{1,0}` instead of `null`, AC-4) would break source fidelity — this guard plus
  AC-4's `null` assertion catch it.

### Owner-judged in a real browser (not a jsdom criterion)

**AC-8 — the rendered lines actually LOOK more/less spaced (visual acceptance) is OWNER-JUDGED in a
real browser.**
That a `1.5x`/`12pt` selection visibly increases the on-screen gap between lines and paragraphs —
and that the indicators (readout, default/custom, whole-document label) are legible and not
cramped at both desktop and mobile widths — is confirmed by the owner in the running app.
- Instrument: **owner-judged, real browser.** jsdom does NO layout
  (`getBoundingClientRect` returns zeros — measurement-instruments memory), so no automated test may
  assert the lines are visually more spaced; a jsdom test that appeared to would be a false clean.
  The jsdom criteria above assert the *declared* values and *announced* state; the *rendered
  geometry* is out of automated reach and is named here explicitly so the verifier does not file it
  as a missing test.
- RED on HEAD: n/a — owner-judged acceptance, not a falsifiable automated criterion.

## 3. Composite surface cost (for the 8b re-judge — legibility is cumulative)

This chunk ADDS to two surfaces:
- **`app/components/SpacingControl.js`** (84 lines today, one flex row: "Line" + 4 buttons +
  "Paragraph" + 3 buttons + a disabled hint). The additions: a value readout (AC-1), a default/

Minimize-clicks: AC-1/AC-2/AC-3/AC-5 are **passive display** (zero added clicks). AC-4 (reset) is
**one** click. No wizard, no menu, no confirmation dialog — a reset is a single button, and the

## 4. Explicitly OUT of scope (do not widen; do not file as missing)

- **A pending/working spinner on the preview spacing change.** The transform is synchronous
  (AC-6); a spinner would be fabricated latency. Not built.
- **Any change to HOW spacing is applied** — `applySpacingToHtml`, the download threading, the
  preset values, the whole-document (not per-paragraph, not per-document-independent) model. N69
  owns these; AC-7 guards them.
- **Free numeric entry of spacing values.** N69 deliberately chose presets (minimize-clicks); this
  chunk indicates the preset value, it does not add a spinner input.
- **A per-paragraph or per-document-independent spacing capability.** Does not exist; not added.
  The indicator reflects the shared whole-document model as-is.
- **Page-break / overflow indicators** ("does this spill to page two"). That was N69's *other*
  half (the measurement problem) and its own owner-decision; unrelated to spacing-change indicators.
- **Real-page-geometry or Word-fidelity claims.** No indicator asserts what Word will render; the
  readout reports the *setting*, not a pagination outcome.
- **Persisting a new indicator state.** The indicator is derived from the existing `entry.spacing`;
  no new persisted field. (AC-4's reset writes `null` through the existing `setDocumentSpacing`.)
