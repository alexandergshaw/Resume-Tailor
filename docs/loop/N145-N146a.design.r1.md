## 0. The two features, in one paragraph

**N146a (stale-serve):** when the pre-warmed project pool's latest regeneration FAILED but the row still carries previously-good projects, the answer route must serve the last-good pick FLAGGED STALE (never as a fresh `ready` benchmark) instead of discarding it as `failed`. This is a pure change to `buildProjectExample` (one new outcome) plus a render case; no new question of transport, no DB.

**N145 (retry):** the failed/stale Row-1 example gains a `Try again` control that calls the already-existing `useApplicationProjectPool.regenerateOne(applicationId)` (OBSERVED at `useApplicationProjectPool.js:188`, a `useCallback` → `runOne(id, { force: true })`, with NO current UI consumer — both clients discard it today). This is a wiring change: destructure the hook's existing output and thread two props down to `AnswerAids`.

Neither feature invents a new server surface. The retry route (`POST /api/application-project-pool`, `force:true`) and the pool table already exist.

## 4. N146a — the stale-entry CONTRACT

### 4.1 `buildProjectExample` — the new sixth outcome (full signature unchanged)

Signature unchanged: `buildProjectExample({ pool, pick, applicationId, engine, now, poolError }) -> undefined | { status, ... }`.

Insert a stale arm at the `pool.status !== "ready"` gate (`projectExampleSelect.js:233`). Exact proposed shape:

```js
if (pool.status !== "ready") {
  // N146a: a FAILED pool may still carry last-good projects (the prewarm
  // route's 'failed' upsert omits `projects`, so the column-wise merge keeps
  // them -- lib/supabase/applicationProjectPool.js). Serve the pick FLAGGED
  // STALE, never as a fresh 'ready' benchmark. A pending pool carries no content.
  if (
    pool.status === "failed" &&
    Array.isArray(pool.projects) && pool.projects.length > 0 &&
    pick && pick.outcome === "match" && pick.entry && isShownEntry(pick.entry)
  ) {
    const entry = pick.entry;
    return {
      status: "stale",
      competency: entry.competency,
      domain: entry.domain,
      title: entry.title,
      bullets: [...entry.bullets],
      hypothetical: true,
      engine: pool.engine ?? null,
    };
  }
  return { status: "failed" };
}
```

**Load-bearing contract decisions:**

1. **A distinct `status:"stale"`, NOT a `stale:true` flag on `status:"ready"`.** Every downstream reader that whitelists `status === "ready"` (`rowOneView` `case "ready"`, the no-overclaim test, any future reader) then treats a stale pick as fresh UNLESS it also remembers to check a flag — the exact overclaim R-N146a bans. A separate status makes the overclaim **impossible by construction** for any `"ready"`-keyed path: the stale pick simply is not `ready`. This is the "wrong thing impossible, not merely absent" choice. **Diff-checkable property:** no code path emits `status:"ready"` for a pool whose DB `status !== "ready"`; a reviewer flags any new `status: "ready"` literal not guarded by `pool.status === "ready"`.
2. **Stale requires the SAME floor as ready:** `pick.outcome === "match"` AND `isShownEntry(pick.entry)`. A failed pool does NOT serve an off-domain or malformed stale pick — it falls through to `{status:"failed"}`. So the honesty floor (`POOL_FIT_THRESHOLD`, the v1-failure guard) applies identically to stale.
3. **Empty failed pool stays `failed`.** `projects.length > 0` is required; the existing `{status:"failed", projects:[]}` fixture is unaffected.
4. **Pending is excluded.** A `pending` row is handled by the earlier arm (`:230-232`, `isStalePending` → `failed`|`pending`) and never reaches this branch. A stale-*pending* (crashed generation past max-age) therefore still renders `failed`, NOT stale — see §4.4 alternative (b).

### 4.2 `withPoolTags` — stale carries the probe's evidence

`withPoolTags` (`projectExampleSelect.js:264-274`) today augments only `ready`/`no_match`. A stale pick is probe evidence too (the owner probe reads `fitScore` + `poolTags` from the session log). Extend the whitelist:

```js
if (!example || (example.status !== "ready" && example.status !== "no_match" && example.status !== "stale")) return example;
```

No other change to the function. `usePracticeSessionLog.js:342-352` logs `projectExample.shown` for ANY `projectExample` (no status filter), so a stale status flows into the downloadable log automatically with `status:"stale"` recorded — no change there.

### 4.3 Transport — no change

`startProjectExampleField` (`projectExampleRead.js:75-97`) derives via `buildProjectExample` then `withPoolTags`; a truthy `"stale"` fragment passes straight through the `projectExample ? {projectExample: withPoolTags(...)} : {}` gate and spreads onto the done frame exactly like `ready`/`no_match`. The route census test (`route.projectExample.test.js`) is unaffected (G13). **No change to `route.js`, `projectExampleRead.js`, or the transport.**

### 4.4 Render — `rowOneView` + `RowOne` gain a stale case

`rowOneView` (`AnswerAids.js:283-295`) — add a case BEFORE `default` (today `"stale"` would fall to `default → failed`, silently hiding a servable pick):

```js
case "stale":
  return isShownEntry(example) ? { kind: "stale", entry: example } : { kind: "failed" };
```

`RowOne` renders `kind:"stale"` with the **same `ExampleBody withCompetency`** as `ready` (accent rule + invented lead + content) PLUS a **stale flag** that makes it distinguishable from a fresh `Ready example`. Two structural requirements (the exact strings are 1c/owner copy — §8):

- The row must NOT present as `EXAMPLE_DT_READY` ("Ready example") alone. Proposed: a distinct dt (`EXAMPLE_DT_STALE`, placeholder `"Earlier example"`) and/or a short `--text-secondary` caption (`R1_STALE_NOTE`, placeholder `"From an earlier run; the latest refresh failed."`) rendered above the content.
- The invented lead (`EXAMPLE_LEAD_BOLD` + `EXAMPLE_LEAD_REST`) and the accent rule (`INVENTED_DD_SX`) still render — a stale pick is still invented content.

**Alternatives considered:**
- **(a, chosen)** stale scoped to DB `status === "failed"`. Tight to the ruling's literal "a FAILED regeneration"; leaves the `pending` arm untouched (smaller blast radius, one fewer timing-dependent branch).
- **(b)** also serve stale for a stale-*pending* row with good projects (a crashed `force` regeneration also keeps `projects`). Better user value, but restructures the `pending` arm around `isStalePending(pool, now)` and widens the timing surface. **Flagged as a micro-decision for the checker/owner.** If adopted, the branch condition becomes `failedEquivalent = pool.status === "failed" || (pool.status === "pending" && isStalePending(pool, now))` evaluated before the existing pending arm — a larger, order-sensitive change.

## 5. N145 — the retry wiring CONTRACT

### 5.1 `AnswerAids` gains two optional props (presentational, no new state)

New props on `AnswerAids({ ..., onRetryRowOne, rowOneRetrying })`:

- `onRetryRowOne?: () => void` — when present AND the Row-1 view is `kind:"failed"` or `kind:"stale"` (NOT `warming`/`no_match`/`ready`: a per-question `no_match` is not fixed by regenerating the pool; a `warming` row is already in flight), `RowOne` renders a native MUI `Button` (text variant, `TOUCH_TARGET_SX`), accessible name exactly `Try again`, **no Tooltip**.
- `rowOneRetrying?: boolean` — when true the button STAYS mounted and focusable, text becomes `Trying again`, `aria-disabled="true"`, click ignored (not native `disabled`, not unmounted — a disabled/unmounted focused control drops focus to `<body>`; UX §4.2).

Both arrive as props because `AnswerAids` is presentational (G7). The in-flight fact is `prewarmingIds.has(applicationId)` computed at the client, never inside `AnswerAids`.

**Diff-checkable:** `onRetryRowOne` is consumed only inside `RowOne`'s `failed`/`stale` branches; a reviewer flags a `Try again` button rendered for `ready`/`warming`/`no_match`.

### 5.2 Hook return — destructure what already exists

Both clients already call the hook; change only the destructure (0 net new lines in the client call itself):

- `CopilotClient.js:384`: `const { noteRowOneStatus, regenerateOne, prewarmingIds } = useApplicationProjectPool({ selectedApplicationId: posting?.id || null, logEvent });`
- `PracticeClient.js:262`: `const { noteRowOneStatus, regenerateOne, prewarmingIds } = useApplicationProjectPool({ selectedApplicationId: posting?.id || null });`

`app/page.js:138` (tracking-tab auto-prewarm) has NO answer surface and is **UNTOUCHED** — it keeps discarding the return. (This is the brief's "trace how the retry reaches regenerateOne" answer: it reaches it only through the two copilot clients, never through the page.js mount.)

### 5.3 Threading path (current surface only)

The retry handler is an opaque callback the surface creates; only the client knows the `applicationId`:

```
client:  onRetry = () => regenerateOne(posting?.id)
         retrying = prewarmingIds.has(posting?.id)
```

- **Live (CopilotClient):** pass `onRetryRowOne={onRetry}` + `rowOneRetrying={retrying}` to `CopilotDashboard` → forwarded to `CurrentAnswerPanel` → `AnswerAids` (the current glance panel). `HistoryItem` (`CopilotDashboard.js:774`) and live `QuestionFeed` cards forward **neither** (non-current; UX §4.2: one retry per application serves every later question).
- **Practice (PracticeClient):** pass the same two props to `QuestionCard` → `SampleAnswer` → `AnswerAids`, and (decision below) optionally to the practice `CopilotDashboard` `CurrentAnswerPanel`. `PracticeHistory` and room-question `QuestionFeed` forward neither.

`CopilotDashboard` must thread the two props to `CurrentAnswerPanel` only (same pattern as the existing `answerHidden`/`onRevealAnswer` pass-through), never to `HistoryItem`.

**Open UX micro-decision (for 1c/checker):** practice shows the current answer twice (dashboard `CurrentAnswerPanel` + `SampleAnswer` card, same visibility gate). Passing the retry to both yields two `Try again` buttons for one action. Recommend: pass to the `SampleAnswer` card only (the primary practice surface). The contract supports either; both just receive the same two props.
