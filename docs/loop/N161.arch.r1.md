## 1. Module & contract boundaries

### 1.1 `lib/copilot/detectCodingChallenge.js` — NEW, pure (D2)

```
detectCodingChallenge(question: unknown): boolean
```

Total, never throws (stringify + guard, like `classifyQuestionType`). NARROWER than
`classifyQuestionType`'s `technical`; does NOT import or widen either `VALID_TYPES`. Sibling of
`questionType.js` under the shared client/server `lib/copilot/` dir, so it is reachable from the three
loci in §2 and from the client render gate without a server import.

**Predicate design (OWNER sub-decision — recommended default; AC-1's corpus is the oracle, not this
text).** The load-bearing structural insight: a coding challenge is an **instruction to PRODUCE a
concrete solution/algorithm/code**, which a conceptual technical question never is. So the predicate is
a PRODUCTION signal, and an algorithm/data-structure token counts **only in combination with a
production verb**, never alone — that combination is what separates "write a function to reverse a
linked list" from "what is a hash map". Recommended composition (disjunction):

1. production-verb + generic artifact:
   `/\b(write|code|implement|design)\b[^?]{0,20}\b(function|method|program|algorithm|routine|script|query|class|regex)\b/i`
2. `write` a SQL query: `/\bwrite\b[^?]{0,20}\bsql\b/i` (also covered by (1) via "query")
3. explicit pseudocode (covers AC-5 step 1's pseudocode case for detection): `/\bpseudo[\s-]?code\b/i`
4. production-verb + named algorithm/DS:
   `/\b(write|code|implement|give)\b[^?]{0,30}\b(binary search|linked list|hash (map|table)|bfs|dfs|breadth-first|depth-first|quicksort|merge ?sort|fibonacci|palindrome|anagram|two ?sum|stack|queue|tree|trie|graph)\b/i`
5. self-contained problem statement:
   `/\bgiven\b[^?]{0,80}\b(return|print|output|find|compute|determine|produce)\b/i`
6. canonical challenge names: `/\bfizz\s?buzz\b/i`

Walk-through against AC-1's corpus (all seven positives fire: #1/#4/#2/#4/#3/#6/#2; all seven negatives
stay false — the three `technical` negatives carry NO production verb paired with their DS/algo token,
and "code review" is "code"+"review" with "review" not an artifact). The three `technical` negatives
are what the **alias-to-`classifyQuestionType==="technical"` mutation** reddens (AC-1 mutation), and a
**constant-false** mutation reddens the positives.

**Diff-check (load-bearing property — "narrower than technical"):** any change that lets an algorithm /
data-structure token match WITHOUT a paired production verb (i.e. drops the AND-combination in #1/#4),
or that routes the predicate through `classifyQuestionType`, breaks AC-1 on the three technical
negatives. The reviewer applies: "does a negative-corpus item gain a `true`?"

**Out of scope (owner/runtime):** real-world recall on live machine-transcribed questions (AC "OUT of
scope"). The fixed corpus bounds behaviour; the token lists in #1/#4 are extendable by the plan/TDD seat
**never shrinkable**, and the AND-combination invariant must survive every extension.

### 1.2 `lib/copilot/codingSolution.js` — NEW, pure (the response contract, D3/D4/D5/D6)

Three exports, all pure, node-testable (no React/DOM/network):

```
// The validated response field. Four parts (AC-3) + the display language.
// shape: { approach: string, language: string, code: string,
//          complexity: string, edgeCases: string[] }
normalizeCodingSolution(parsed: unknown, { languageFallback: string }): CodingSolution | null
```
- Returns `null` (so the route degrades to the ordinary non-coding answer — AC-3 "never a half-built
  object") unless the parsed model payload carries a conformant 4-part object: non-empty string
  `approach`, non-empty string `code`, non-empty string `complexity`, and a string[] `edgeCases`
  (coerced to `[]` if absent — edgeCases is the one part allowed empty, since a trivial problem may
  genuinely have none; `code`+`approach`+`complexity` are the hard gate). **OWNER sub-decision:**
  whether `edgeCases: []` counts as "present" — recommend YES (empty list is a valid answer; the four
  parts are STRUCTURALLY present as fields). Flag for the checker.
- `language`: the model-reported language token validated via `normalizeLanguageToken`
  (`codeLanguages.js`, which admits an out-of-vocab well-formed token like "Rust" verbatim and folds
  junk to `Pseudocode`), falling back to `languageFallback` (the deterministic steps-2-4 label, see
  below) when the model omits/malforms it. This is what lets a question naming Rust display "Rust"
  (AC-5 step 1, model-driven) while an unset session displays "Pseudocode" (step 4).
- **The code string is NEVER passed through** `sanitizeTechTermDetail`/`isFirstPersonClaim`/
  `deriveAnswerFromPoints`/`answerLines` (AC-7). It is validated for SHAPE only and returned verbatim.

```
// The deterministic language DIRECTIVE for the coding prompt branch (AC-5 steps 1-4),
// the codeBearing-INDEPENDENT sibling of answerPrompts.codeLanguageLines (D5).
codingLanguageDirective(codeLanguage: {override, resolved} | undefined): string[]
```
- Steps 2-4 deterministic over `{override, resolved}`, label via `codeLanguageLabel` (never the slug),
  pseudocode when `override === "pseudocode"` or nothing resolves — **with NO `descriptor.codeBearing`
  gate** (D5). Also returns the plain-language label the route uses as `normalizeCodingSolution`'s
  `languageFallback` (recommend a second export `resolveCodingLanguageLabel(codeLanguage): string` so
  the prompt directive and the fallback label share one computation and cannot drift).
- **Diff-check (AC-5 teeth):** emitting the slug instead of `codeLanguageLabel(...)`, defaulting to a
  real language when unset instead of pseudocode, or re-introducing a `codeBearing` early-return, each
  reddens the unit. The reviewer applies: "does this helper read `descriptor.codeBearing`? does it emit
  a `CONTROL_OPTIONS.value` slug?"

```
// The embedded engine's honest fallback marker (AC-10 / D6). No code, ever.
embeddedCodingFallback(type: string): { codingFallback: string, type: string }
```
- Returns a marker field (e.g. `codingFallback: "Switch to the AI engine for a worked code
  solution."`) and NO `codingSolution`/`code` field. The embedded route branches return this WITHOUT
  calling the drafters for code — so the embedded drafters (`answerLocal.js`, `sampleAnswerLocal.js`)
  are **left untouched**, and the honesty is structural: a path with no model and no code producer
  cannot fabricate code. **Diff-check (AC-10 teeth):** any embedded coding branch that emits a `code`
  field reddens the unit.

### 1.3 `app/copilot/CodeSolution.js` — NEW render primitive (AC-4 / B1)

```
export default function CodeSolution({ solution, buzzwords }): JSX
```
Renders, in order: `approach` (plain `<Typography variant="body2">`), the **code block**, `complexity`
(`<Typography variant="caption">` or body2), and `edgeCases` (a `<ul>`). The code block is the only
B1-critical element:

```
<Box component="pre" style={{ whiteSpace: "pre-wrap", fontFamily: "<monospace stack>", ... }}>
  {solution.code}
</Box>
```
- The style MUST be the inline `style={{...}}` attribute, NOT `sx` — jsdom's cascade does not apply
  emotion/author classes (`CitationDetail.test.js:266-270`), so only `element.style.whiteSpace` /
  `element.style.fontFamily` resolve (AC-4). Any purely-visual styling (padding, border, background,
  overflow) MAY go through `sx`; only `whiteSpace` and `fontFamily` are the inline, asserted ones.
- `whiteSpace: "pre-wrap"` (not `"pre"`) is the recommended default so long lines wrap at phone width
  without horizontal page scroll; AC-4 accepts either. Phone geometry (≥44px targets, 320px overflow)
  is out of jsdom — owner/browser-pane.
- `buzzwords` is the one aid D1 lets a coding card keep (posting vocabulary, not a provenance claim).
  Recommend `CodeSolution` renders buzzwords-only via the existing `<AnswerAids buzzwords={...} />`
  (all other aid props omitted) OR its own chip row — **OWNER sub-decision**, recommend reusing
  `AnswerAids` with only `buzzwords` set so the chip styling stays identical. Experience aids
  (`resumeAnchor`, `projectExample`/`projectExampleLive`, per-point `pageSources`, bullet expansion)
  are NOT rendered for a coding card (D1).

**Diff-check (AC-4 property):** the code element's `style` attribute object must contain literal
`whiteSpace` and `fontFamily` keys; a reviewer greps the new component for `sx={{` wrapping the code
element (defect) vs `style={{` (correct).

## 2. Detection loci (where the detector runs)

Detection is re-derived from `question` at THREE independent points, never passed as state between them
(same discipline as `roleTerms`), so each surface and engine reaches the same decision:

**Locus 1 — Gemini prompt branch, inside both builders (`answerPrompts.js`).** `buildPointsPrompt`
(live/points) and `buildAnswerPrompt` (practice/answer) each call `detectCodingChallenge(question)`
internally — **no new positional argument** (preserving `buildPointsPrompt.length === 7` and the
options-object shape of `buildAnswerPrompt`), exactly the `roleTerms(question).length > 0` pattern at
360/521. When FALSE: the builder emits today's output byte-for-byte (AC-2). When TRUE: the builder (a)
appends the worked-solution directive (approach + code + complexity + edge cases, AC-3) and the
`codingLanguageDirective(codeLanguage)` block (AC-5, §1.2), and (b) emits a DIFFERENT "Return ONLY
JSON" shape line requesting the `codingSolution` object — which does NOT touch the frozen non-coding
shape line (D3: separate field, `type` enum unchanged). `systemInstruction` (`POINTS_SYSTEM`/
`ANSWER_SYSTEM`) stays a CONSTANT (the coding directive rides the user-turn branch only).

**Locus 2 — answer route, all five branches (`answer/route.js`).** The route re-derives
`const isCoding = detectCodingChallenge(question)` once (beside `questionRoleTerms` at 397) and threads
it, like `codeLanguage`, into `streamAnswer` and the non-streaming branches. See §3 for per-branch
wiring.

**Locus 3 — client render gate.** The render sites gate on the PRESENCE of the `codingSolution` field
on the card/state (not by re-running the detector), because the server already decided and carried the
field. (A revealed PAST answer re-renders from its stored entry, so the stored field is the authority —
AC-9.)

**Why re-derivation, not a new builder arg (binding, from AC-2):** a non-coding question must take no
new branch so the frozen `FROZEN_*_NO_PAGES` oracles (`answerPrompts.test.js:86-112`) hold byte-for-byte;
a new positional argument would also break `buildPointsPrompt.length === 7`.

## 3. Data flow (request → response → render), both surfaces

### 3.1 Response contract (shared)

A detected coding question's response carries, IN PLACE OF the spoken answer:
```
{ codingSolution: { approach, language, code, complexity, edgeCases },
  type,
  ...(buzzwords only, per D1) }     // NO points, NO cues, NO answer, NO pageSources/resumeAnchor/projectExample
```
A non-coding question's response is **key-for-key today's shape** with `codingSolution` **absent** (not
`null`, not `[]`) — the `...(isCoding ? {codingSolution} : {})` spread, mirroring `factSources`
(route.js:907). `codingSolution` rides the terminal `done` frame only in the streaming path (D4; safe
per §0's `pointsFromPartialJson` finding).

**REPLACE is structural (AC-11).** The coding response carries NO `points`, so there is no spoken list
for any surface to render beside the code — augment-instead-of-replace is impossible at the response
boundary, not merely absent. The route's `if (points.length === 0)` error guard (275/673/751/825/878)
must be widened on each branch to `if (points.length === 0 && !isCoding)` (or `&& !codingSolution`) so a
valid coding response is not mistaken for a failed draft.

## 4. The render change at all five sites (AC-4 / AC-9 / AC-11)

Every site today renders `done && lines.length ? (<AnswerLines/> + <AnswerAids/>) : <noPoints>`. The
change inserts a `codingSolution` branch **before** the `lines.length` check so that, when present, the
code block renders and `<AnswerLines>` is never mounted (points suppressed — AC-11 structural):

```
codingSolution
  ? <CodeSolution solution={codingSolution} buzzwords={buzzwords} />
  : lines.length
    ? (<AnswerLines lines={lines}/> + <AnswerAids .../>)
    : <noPoints/>
```

- **CopilotDashboard.js CurrentAnswerPanel** (:442): `current.codingSolution`. Also the aria-live
  `currentAnswerStatusText` (272) uses `answerStatusMessage({status, bulletCount: lines.length})` —
  for a coding answer `lines.length === 0`, so this must announce readiness, not "no points" (see
  wrinkle below).
- **CopilotDashboard.js HistoryItem** (:699/:745): `entry.codingSolution`, computed only when
  `expanded` (same cost discipline as `lines`). A revealed PAST coding answer shows the code block
  (AC-9 history reveal).
- **QuestionFeed.js QuestionCard** (:144/:203): `q.codingSolution`.
- **QuestionFeed.js latest status** (:85): `latestLines` feeds `latestStatusText`/`latestRegionText`
  (the aria-live region, not a visible answer). Same readiness wrinkle.
- **SampleAnswer.js** (:124/:220): new `codingSolution` prop; `canRegenerate` (128) must become
  `visible && status === "done" && (lines.length > 0 || !!codingSolution)` so Regenerate stays
  offered for a coding answer. The `answerStatusMessage` call (161) has the same readiness wrinkle.

**Status/readiness wrinkle (OWNER, scoped to the render sub-chunk, jsdom-decidable).**
`lib/copilot/answerStatus.js` `answerStatusMessage({status, bulletCount})` must not announce a done
coding answer as empty. Recommended default: pass a `hasCodingSolution` flag (or a non-zero synthetic
count) so the "done" message reads "Answer ready" rather than "0 points". This is a11y polish, not a
contract; flag for the checker. (D4's "drafting solution" loading state is the SAME `status:

**Diff-check (AC-11 REPLACE property):** every one of the five sites must render `<AnswerLines>` ONLY
