# N143 -- AC-N143-Q owner quality probe (the gating deliverable)

**Status:** shipped with the feature; **run by the owner, in a Gemini environment, once, before any quality claim is accepted and before any mechanical quality fix.** Nothing in this checkout can measure whether the invented examples are good: there is no `GEMINI_API_KEY` here, so the unit suites prove the plumbing (selection, status, caps, figure guard, prompts as text) and say nothing about the content. A probe that could not run, or ran against the wrong engine, is **INVALID, not zero** (see "A run is invalid if", below).

The probe exists so that "the examples are wrong" is attributed to ONE cause in one sitting instead of becoming a chunk per hypothesis (the N135 rule). Every candidate cause below has a distinct, pre-stated observable.

## What changed in this build that the probe now sees

- **Row 1 selection** no longer forces a pick and no longer matches on the question's interview scaffolding ("tell me about a time", "describe", "handle", "project", "problem"); it compares word STEMS ("teach" meets "teaching"). It can say **"No close match for this question."** (`no_match`).
- **The session log records the evidence.** Every `projectExample.shown` event carries, besides `status`, `competency` and `domain`, the **`fitScore`** the pick won (or missed) with and **`poolTags`**: every entry of the pool the pick was made from, as `{competency, domain, title}`. Without `poolTags`, causes (c) and (d) cannot be told from (a).
- The prompt now forbids naming a real employer, school or person in an example.

## Before you start (setup)

1. Engine = **Gemini** (not Embedded; Embedded shows no example rows at all, by design).
2. Three postings, one per domain, tracked in the app so each has an application row: a **teaching** role (middle-school math), an **SRE / infrastructure** role, a **nursing** role (ICU). Use real postings, with real descriptions.
3. Wait for each application's pool to be **ready**. Open the copilot for that posting and ask any question: the Row 1 line must read "Ready example" or "No close match for this question.", never "Still being prepared. Shows from your next question." or "Couldn't prepare examples for this posting." If it stays on either of those, stop: that is a prewarm finding, not a content verdict (see "A run is invalid if").
4. **Press Start session before the first question.** The log records nothing until then.
5. Use **live mode and the "Type a question the interviewer asked" box**, so the questions below are asked verbatim. Ask each question once (a repeat is served from the client cache and does not re-pick).
6. Check once that the log carries the evidence: after the first question, download the log and confirm a `projectExample.shown` line with a `poolTags:` list. If it has no `poolTags`, this build's surface does not record them: use practice mode instead, or read the pool straight from the `application_project_pool` table (`projects` column) in the Supabase table editor, and note which you used. Causes (c) and (d) are unanswerable without the pool.

## Capture sheet (one row per question; 9 in-domain rows plus 6 controls)

For each question, fill in. Items 1 to 3 are read from the app and the downloaded log; item 4 is yours.

| # | Question | 1. Row 1 shown (status, competency, domain, title) | 2. The full pool (every `poolTags` entry) and the `fitScore` | 3. Row 2 (the project written for this question) | 4a. Row 1 domain-relevant? Y/N | 4b. Row 1 template-generic? Y/N | 4c. Row 2 domain-relevant? Y/N | 4d. Row 2 template-generic? Y/N | 4e. Any named employer, school or person in a row? |
|---|---|---|---|---|---|---|---|---|---|

"Domain-relevant" means: a person in that field would recognise the project as the kind of thing their field does and as an answer to THIS question. "Template-generic" means: it reads as "owned a problem end to end and improved process metrics" with the field's words swapped in; the same skeleton would fit any role.

## Discriminators: which cause produced a bad row

Work down the table for every row you marked N in 4a or 4c, or Y in 4b or 4d. Each cause has a distinct cell; one run attributes the cause.

| Cause | The observable that identifies it (and where to read it) |
|---|---|
| **(a) The prompt ignores the role's domain** | The pool's own tags (`poolTags`) are **not about this role**: ops, process or stakeholder words for a teaching or nursing posting. Every question in that domain gets an off-domain row or "No close match for this question.", **and no entry in the pool is on-domain for the question**. Off-domain entirely. |
| **(b) The prompt takes the domain but writes a generic skeleton** | The tags ARE on-role, but 4b / 4d are **Y across domains**: the teaching, SRE and nursing examples share one skeleton ("owned X end to end, here are process metrics"). Visible only because you captured three domains. |
| **(c) The pool is too narrow** | `poolTags` is on-role but **clustered**: three or more of the five entries share one competency or one domain, so questions outside that cluster have nothing to match and read "No close match for this question." (or a forced stretch) even though selection worked. On-domain but clustered. |
| **(d) Selection picks the wrong entry** | `poolTags` contains an entry **you judge clearly better** for the question than the one Row 1 showed (or than "No close match for this question."). Generation is fine; matching is not. Compare your best entry's tag against the question: the picked row's `fitScore` is in the same log line. |
| **(e) Row 1 and Row 2 diverge** | For the same question 4a and 4c disagree (pool entry generic, live project relevant, or the reverse). Points at the pool prompt versus the on-the-spot prompt (`buildPoolPrompt` versus `buildOnTheSpotPrompt` in `lib/copilot/projectExampleGen.js`). |
| **(f) Names** | 4e is Y anywhere. The instruction is a prompt, not a guarantee; this is the only place it is measured. |

Tie-breakers, in the order to apply them: (a) before (c): if the tags are off-role it is (a), however clustered they are. (c) before (d): if the pool has no on-domain entry for the question, selection cannot be at fault. (d) only when an on-domain entry exists in the pool and was not chosen.

## Pass condition

Across the nine in-domain rows: every shown row is **domain-relevant = Y** and **template-generic = N**, no (d) mis-selection, no (f). Across the six controls: every control reads "No close match for this question." (a shown example on an off-domain or scaffolding-only question is a selection failure, cause (d) in the opposite direction). Any N or Y routes to the one cause above; it does not route to "another round".

## A run is invalid if (record it as INVALID, never as a pass or a zero)

- The engine was Embedded, or no Gemini key was present (no example rows exist to judge).
- A pool never reached ready for a domain (Row 1 stayed on "Still being prepared" or "Couldn't prepare examples" for all of its questions): report that as a prewarm failure with the application id's pool row, and do not score its content.
- The log was not started before the first question, or was downloaded from a different session than the one that was judged.
- The log has no `poolTags` and the pool was not read from the table either: (c) and (d) cannot be attributed, so those cells are INVALID, though (a), (b), (e) and (f) can still be scored.
- A question was edited, or asked twice (the second is a client-cache reuse and does not re-pick).

Paste the filled capture sheet and the downloaded log(s) into the N143 row of `docs/BACKLOG.md`, with the engine, the date, and which of the six causes the run attributed. The owner's verdict, not a unit suite, closes AC-N143-Q.
