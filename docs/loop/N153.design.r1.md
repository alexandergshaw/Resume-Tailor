## 2. The prefetch trigger (requirement 1)

### Decision: a per-item **mount effect** at the render leaf, keyed on the resolved store key — NOT a central scope effect.

**Why render-site, not the scope.** "As soon as they come up on screen" *is* mount. The scope holds the whole `questions` list and cannot distinguish the current answer from history without re-deriving it; the render leaf gets "on screen / newly shown" for free from React mounting (history leaves mount only on expand — §5). This also keeps the scope's "one subscription per surface" invariant untouched: a mount effect is not a store subscription.

**Why keyed on the resolved key (the loop-safety property).** A store write bumps `storeSnapshot.version`, which gives the api memo a new identity, which re-renders every consumer leaf (this is the N149 fix, pinned by `useAnswerExpansions.storeWrite.test.js`). If the warm effect depended on the api object it would re-run on every write. It therefore depends on a **stable string** — the resolved key — and reads the (latest) api through a ref. The key changes only when the question/point/request changes, so the effect fires **once per distinct resolvable item**, never per re-render, never in a loop.

**Idempotence is defence in depth, not the mechanism.** Even if the effect over-fired, `beginExpansion`/`beginTechTermDetail` issue at most one network request per key, and the queue (§4) dedupes a second enqueue. The key-stable dep is what prevents effect *churn*; the store guard is what prevents double *fetch*.

### New reusable hook — `app/copilot/useWarmOnMount.js`

```js
import { useEffect, useRef } from "react";
/**
 * Fire warmFn() exactly once per distinct non-empty warmKey, reading the
 * LATEST warmFn via a ref so a store-write re-render cannot re-run it.
 * warmKey === null | "" => no-op (item not resolvable yet / no api).
 */
export function useWarmOnMount(warmKey, warmFn) {
  const fnRef = useRef(warmFn);
  useEffect(() => { fnRef.current = warmFn; });          // latest closure, every render
  useEffect(() => { if (warmKey) fnRef.current?.(); }, [warmKey]);
}
```
The ref is updated in an effect (not during render) so the pattern is concurrent-safe; the ref-update effect is declared first, so `fnRef.current` is fresh before the key-gated effect runs on the render where the key changes.

## 3. Collapse interaction ruling (requirement 2 — load-bearing)

**RULING: option (a) — prefetch buzzword details only while the section is OPEN (chips mounted); bullets prefetch on answer render regardless.**

- Because `CollapsibleAid` unmounts its body, `TechTermChip` does not exist while collapsed, so the per-chip warm hook simply does not run — no code gates it, the structure does. When the candidate opens the section, all chips mount together and their warm hooks fire together (throttled by §4). This is exactly "as soon as they come up on screen": a collapsed section's terms are **not** on screen.
- **Mobile default (`<600px`) is collapsed**, so on a phone no buzzword detail is prefetched until the candidate expands the section — which is the correct, cheapest behaviour and still instant once expanded (expanding mounts the chips → warms → by the time they read a term and tap it, it is warm).
- **Desktop default (`>=600px`) is open**, so chips mount with the answer and prefetch immediately.
- **Bullets are always visible** (not inside any `CollapsibleAid`), so they prefetch on answer render in every viewport.

**Tradeoff, stated:** option (b) (warm buzzwords even while collapsed, driven from `TechTermsGroup` which stays mounted) would make a phone tap instant without an expand first, but it spends model calls on terms the candidate may never reveal and contradicts "on screen". Rejected. If the owner later wants (b), the seam is identical — `TechTermsGroup` already has `view.terms` and the api above the `CollapsibleAid`; it would call `api.prefetch(term)` in a single effect there instead of per chip. Noted, not built.

### 4c. Keep a client-side concurrency throttle (owner update 1b)

Removing the server cap means "don't refuse", not "hammer". On answer render, bullets (<=6) + buzzwords (N) could enqueue ~12 warms at once. A **shared, module-scope** throttle bounds total in-flight prefetches across all expanders on the surface (bullets + buzzwords + future N154 ideal-project bullets), so a render never fires a burst.

**New primitive — `lib/copilot/prefetchQueue.js` (no React; module scope, like the stores):**
```js
export const PREFETCH_CONCURRENCY = 3; // tunable, not load-bearing; 3 warms a 6-bullet answer in ~2 waves while leaving a browser connection free for a real click

export function createPrefetchQueue({ concurrency = PREFETCH_CONCURRENCY } = {}) {
  let active = 0;
  const waiting = [];                  // Array<{ key, run }>
  const pendingKeys = new Set();       // keys waiting OR in flight -> queue-layer dedupe
  function pump() {
    while (active < concurrency && waiting.length > 0) {
      const { key, run } = waiting.shift();
      active += 1;
      Promise.resolve().then(run).catch(() => {}).finally(() => {
        active -= 1;
        pendingKeys.delete(key);
        pump();
      });
    }
  }
  return {
    /** Enqueue run() under key. A key already waiting/in-flight is ignored. */
    enqueue(key, run) {
      if (!key || typeof run !== "function" || pendingKeys.has(key)) return;
      pendingKeys.add(key);
      waiting.push({ key, run });
      pump();
    },
    activeCount: () => active,          // test-only introspection
    pendingCount: () => waiting.length, // test-only introspection
  };
}

export const copilotPrefetchQueue = createPrefetchQueue();
```

**Two-layer dedupe, deliberate** (the N151c OR-3 precedent): `pendingKeys` stops a duplicate *task* piling up while a warm waits; `beginExpansion`'s loading-record guard stops a duplicate *network call* once it runs. After a run settles, its key leaves `pendingKeys`; a later re-enqueue of the same key is allowed but `begin` no-ops on the settled record, so it is cheap.

**A real click always has priority — structurally.** A click is `toggle()`/`retry()`, which call `beginExpansion` **directly**, never through the queue. The queue throttles only *prefetch* issuance, so a click is never stuck behind warms; its request goes out immediately. If the queue later reaches that key, `begin` dedupes it. Property §P4.

**Module-scope lifetime:** the queue (like the stores) survives the live/practice transcript subtree remount. A warm enqueued for a leaf that then unmounts still runs — it only writes to the bounded, LRU module store (no React state, no content leak). Acceptable; noted.

## 6. No-poison / failure (requirement 4)

A prefetch that fails writes an `error` record (enumerated `code`) exactly as a failed click would (`expansionStore.js:141-152`). Consequences, all acceptable and all already reachable today:
- The item stays **retryable on click**: opening an error record shows the error + Retry, and Retry re-issues (`retry:true` path). Unchanged.
- Prefetch errors are **silent**: `beginExpansion` never throws to the caller, the queue's `.catch(() => {})` swallows anything, and nothing renders because prefetch does not set `open`. No alert, no layout change.
- **Deliberate, documented nuance:** if a prefetch failed, the candidate's *first* open shows the cached error immediately (with Retry) rather than a fresh loading spinner. This matches "retryable on click exactly as today" (the retry path is identical); we do **not** auto-retry on open (that would re-spend, and could loop on a persistent failure). Property §P5.
- **Kill switch:** if an operator disabled the feature, prefetch pre-populates the `disabled` state (no Retry), identical to what a click would show. No poison.

## 7. Tech-term session-log semantics — the ONE flagged ruling

**Problem.** Today `onDetailOutcome` (the session log's `techTerms.detail` event) fires **once per issued request**, gated by `issues = before === "idle"`. Prefetch issues the request *before* any click, so by the time the candidate opens a term the record is already `loading`/`done` -> `issues` is false -> **no log event ever fires**. With prefetch warming (almost) every shown term, the feature-log would silently go empty. The memory note frames this log as recording terms the candidate **expanded** (opened) — prefetch is not a user open.

**RULING (recommended): prefetch never logs; log the outcome on the candidate's FIRST user-open of a term, deduped per key for the scope's lifetime.** This restores the "terms the candidate opened" signal and keeps it from being inflated by auto-prefetch.

Contract change in `useTechTermDetails`:
- Add `const loggedRef = useRef(new Set());` (keys already reported).
- `prefetch(term)` (§2) calls `beginTechTermDetail` **without** any outcome reporting.
- `start(term, options)` (the toggle-open / retry path) issues via `beginTechTermDetail` as today, then, if `!loggedRef.current.has(key)`, marks it and reports the **observed terminal outcome** — read from the store when terminal, else on the next terminal write, via a small local helper:
```js
function reportWhenSettled(key, term) {
  const emit = (r) => onOutcomeRef.current?.({ term, status: r.status, code: r.code });
  const cur = getTechTermDetail(key);
  if (cur.status !== "idle" && cur.status !== "loading") { emit(cur); return; }
  const unsub = subscribe(() => {
    const r = getTechTermDetail(key);
    if (r.status !== "idle" && r.status !== "loading") { unsub(); emit(r); }
  });
}
```
(`subscribe`/`getTechTermDetail` are already imported.) The existing `pending.then` reporting is replaced by this open-driven path because `pending` resolves immediately when `begin` dedupes a prefetched request and therefore cannot observe the terminal state.

**Why this keeps the existing callback test green** (`useTechTermDetails.test.js:174-188`): first open logs once; collapse+reopen finds the key in `loggedRef` and logs nothing -> still exactly 1. (That test asserts callback counts, not fetch counts, so prefetch-on-mount does not disturb it.)

**Alternatives, with cost:**
- **L2 (do nothing):** prefetch no-log, keep issue-gated logging. Simplest, but the log goes empty — a real regression. Rejected.
- **L3 (prefetch logs too):** every shown term logs a `done`/`empty`/`error` outcome whether opened or not. Trivial (prefetch uses the same reporting path). But it changes the log's meaning from "explored" to "available+fetched" and floods it. Cheaper than L1; I recommend L1 but **the checker/owner may choose L3** if an availability-log is acceptable. This is the flagged call.

Bullets have **no** logging (the expansion api has no `onDetailOutcome`), so none of this applies to them.

## 8. Reusable seam for N154 (owner update 2)

No expansion-only assumption is baked into `prefetchQueue.js` or `useWarmOnMount.js`.
