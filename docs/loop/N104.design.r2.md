## 2. THE F1 fix — the pinned-analysis seam (chosen over term-matching)

**Decision: PINNED ANALYSIS.** The seam is feasible (one optional param, one branch at the single grounding site V1), so per the brief's preference it is chosen over the position-independent term-match fallback. Term-matching is still used WITHIN the key (§5.2) because the MEDIUM collision requires the term there regardless; but cross-run stability is bought structurally by the pin, not by hoping two gemini calls mint the same ids.

### 2.1 Pipeline contract change (additive, opt-in — AC-8 safe)

```
runIdealPipeline({ engine, args, realMaterial, pinnedAnalysis }) -> <unchanged output shape>
```

New optional field:

| Field | Type | Meaning |
|---|---|---|
| `pinnedAnalysis` | `{ postingAnalysis, keywordMap }` or absent | when present and valid, the pipeline uses THIS grounded analysis for the reviewer's `posting` input and for the returned `ideal.postingAnalysis`/`ideal.keywordMap`, instead of grounding `chain.postingAnalysis`. The engine still runs (`engine.tailorIdeal(args)`) and still produces a fresh DOCUMENT; **only the requirement universe the review scores against is pinned.** |

**The single-site change (V1), stated precisely.** `idealPipeline.js:162-165` becomes:

```
const grounded = isValidPinnedAnalysis(pinnedAnalysis)
  ? { postingAnalysis: pinnedAnalysis.postingAnalysis, keywordMap: pinnedAnalysis.keywordMap }
  : groundToPosting({ postingAnalysis: chain.postingAnalysis, keywordMap: chain.keywordMap }, args?.jobPosting);
```

`isValidPinnedAnalysis` = `pinnedAnalysis` is an object with `Array.isArray(postingAnalysis?.requirements)` and `postingAnalysis.requirements.length > 0` and every requirement has a string `id` + `text`. An invalid or absent pin falls to today's grounding (never silently to a half-pinned state).

**Why this is the right seam (rule 4 — wrong thing impossible, not absent).**
- The before run and the regenerate's after run now literally share the same `postingAnalysis` OBJECT (the entry's `ideal.postingAnalysis`, reused). Req ids are identical, so a missing-keyword gap that is still missing produces the SAME `(origin, requirementId, term)` key in both reviews → it is reported `stillOpen`, never falsely `closed` (the F1 blind-closure the AC-4 mock could not catch).
- Only the DOCUMENT varies between before and after, which is exactly what AC-4 measures.
- The gate (AC-1) is downstream and unaffected: pinning changes the review's requirement universe, not what the gate judges candidate spans against (real material). The no-fabrication invariant holds under a pin exactly as without one.

**AC-8 non-regression (the check's explicit requirement).** Every FIRST-RUN caller (`idealBranch.js` → `runIdealPipeline`) omits `pinnedAnalysis`, so the grounding branch is byte-identical to today. The pin is reached ONLY by `regenerateToAddress` for the re-review. **Diff-check:** grep `pinnedAnalysis` in `idealBranch.js` → **0** (the first-run route never pins); grep `pinnedAnalysis` in `regenerateToAddress.js` → **≥1**. Canary: grep `pinnedAnalysis` in `idealPipeline.js` → the branch + the param.

### 2.2 Where the pin comes from (Ideal-only makes this always available)

Because the regenerate is Ideal-jobs-only (§3), the before run is the on-screen `entry.ideal`, which already carries `postingAnalysis` and `keywordMap` (`idealPipeline.js:216-217`, grounded, stable `q${n}` ids). `regenerateToAddress` passes `pinnedAnalysis: { postingAnalysis: beforeIdeal.postingAnalysis, keywordMap: beforeIdeal.keywordMap }`. No fresh analysis is needed to obtain the pin; it is read off the entry. (This is the second reason the owner ruling (b) is clean: option (a) would have had no pinned analysis to reuse for a level 1-5 job, which is the comparability hole UX §11 and the check both flagged.)

## 5. The before/after comparison seam (AC-4) — pinned, term-keyed, guarded

```
compareReviewGaps({ before, after, resolvable, beforeRequirementIds, afterRequirementIds }) -> ClosureReport
```

Pure function. No analyzer, no gate (AC-3b).

### 5.1 Inputs

| Field | Type | Meaning |
|---|---|---|
| `before` | `ReviewOutcome` | the pre-regenerate review (the summary's review of what currently ships). |
| `after` | `ReviewOutcome` | the regenerate's `out.ideal.review`, computed over the KEPT spans (what ships), scored against the **pinned** analysis (§2). |
| `resolvable` | `Flag[]` | the named resolvable set from `classifyWeaknesses(before).resolvable` (§8) — the only gaps whose closure is measured. |
| `beforeRequirementIds` | `string[]` | the before run's `ideal.postingAnalysis.requirements.map(r => r.id)`. |
| `afterRequirementIds` | `string[]` | the after run's `ideal.postingAnalysis.requirements.map(r => r.id)` (= the pinned set in the happy path). |

The orchestrator supplies `beforeRequirementIds`/`afterRequirementIds` from the two runs' `postingAnalysis` directly — `compareReviewGaps` does NOT dig requirement lists out of a `ReviewOutcome` (the outcome does not reliably carry them).

### 5.2 Gap identity (the MEDIUM collision resolved)

- **Posting-anchored (`missing-keyword`):** key = `(category, evidenceRef.origin, evidenceRef.spanId /* = requirement id */, term)`. **`term` is REQUIRED** (one requirement emits one flag per term, all sharing the id — V3 — so without the term the key collides). `term` is parsed from the flag message under this documented contract: **the substring inside the FIRST pair of double quotes of `flag.message`** (the message is `The posting asks for "${term}" (...)`, V3), normalized (trim, lowercase, collapse whitespace). **Canary (required test):** assert the parse of a real `detectMissingKeyword` message yields the exact term; a message that does not match the `"…"` shape yields no key and the flag falls to the count-delta path (never a silent merge). The bare-`spanId` fallback from r1 §12.3 is **removed** — it would merge distinct terms (the MEDIUM).
- **Draft-anchored (`vague-unsupported`, `repetition`):** no stable id across a rewritten draft → **category count delta only**, never a per-line "closed" (G-2).

### 5.3 The runtime CORRESPONDENCE GUARD (F1 defense-in-depth)

```
const correspond = setEqual(beforeRequirementIds, afterRequirementIds);
```

- **`correspond === true`** (the pin held): compute per-gap closure on the §5.2 key. `closed` = a resolvable posting-anchored key present in `before` and **absent** from `after.flags`. `stillOpen` = present in both.
- **`correspond === false`** (the pin was NOT applied — a future edit removed it, or `pinnedAnalysis` was invalid and the pipeline re-grounded fresh): **fall back to category count-deltas only.** `closed = []`, `stillOpen = []`, `correspondenceUnavailable = true`. The report UI (UX §6.2 / UXW-3) renders ONLY the count deltas and **never a per-gap "no longer flagged" row** — closure is never asserted on drifted ids (G-5 escalated from a passive precondition to this runtime guard).

This guard is why F1 is impossible, not merely absent: even if the pinned-analysis seam is later broken, `compareReviewGaps` cannot emit a false "no longer flagged" because the id sets would not be equal and the per-gap branch is skipped.

### 5.4 Output — `ClosureReport`

```
{ correspondenceUnavailable: boolean,              // true => per-gap closure suppressed (guard fired)
  closed:   [{ category, requirementId, term, label }],    // [] when !correspond
  stillOpen:[{ category, requirementId, term, label }],    // [] when !correspond
  countsBefore / countsAfter: { missingKeyword, vague, repetition },  // always present (G-2, G-6)
  lineCountBefore / lineCountAfter,                 // for the Length line (G-6 closure-by-deletion)
  genuinelyUnqualifiedStillOpen: [...] }            // pass-through from after.unresolvedQualifications (AC-2)
```

- `countsBefore/After` + `lineCount*` make closure-by-deletion visible (G-6: the UX Length and Set-aside lines).
- `genuinelyUnqualifiedStillOpen` is the after review's `unresolvedQualifications` — always reported open (AC-2); the regenerate never targets them.
- The confirm bucket is NOT a closure target; its after-count may be shown ("Still listed: … to confirm") but no confirm flag is ever reported `closed`.

**AC-4 instruments:** mock-engine positive (improved draft → key gone → `closed` + count down); mutant (same draft → key persists → `stillOpen`, never "closed"); **guard mutant** (feed non-corresponding id sets → `correspondenceUnavailable:true`, `closed=[]`, only count deltas); **LIVE leg** (§A AC-4, owner-env). Failable-row count (resolvable posting-anchored gaps that could close) > 0.

## 8. `classifyWeaknesses` — the 3-bucket contract (G-1)

```
classifyWeaknesses(reviewOutcome) -> { resolvable: Flag[], confirm: Flag[], genuinelyUnqualified: Entry[] }
```

Pure function of the `ReviewOutcome`; no analyzer, no gate. The bucket of each flag is derived from the **shipped** `presentFlag(DRAFT_KIND.APPLICATION_READY, flag.category).tier` (V5), NOT a local category list (so it cannot drift from the panel and adds no second classifier — AC-3b):

- `unqualifiedReqIds = new Set(reviewOutcome.unresolvedQualifications.map(u => u.requirementId))`.
- For each `flag` in `reviewOutcome.flags`, by `presentFlag(APPLICATION_READY, flag.category).tier`:
  - **`TIER.CONFIRM`** (`unsupported-authority`, `unverifiable-metric`, `consistency`, `employer-plausibility`, **and any unknown category** — V5 default) → **`confirm`**. Never a regenerate target: changing an unverifiable figure or an authority claim to "close" it IS fabrication.
  - **`TIER.IMPROVE`** (`missing-keyword`, `vague-unsupported`, `repetition`) → candidate resolvable, then:
    - `missing-keyword` whose `evidenceRef.spanId` ∈ `unqualifiedReqIds` → **folded into the genuinely-unqualified presentation** (NOT resolvable, kept out of `weaknessSteering`).
    - otherwise → **`resolvable`**.
- `genuinelyUnqualified` = `reviewOutcome.unresolvedQualifications`.

**Invariants (checkable):**
- `resolvable`, `confirm`, `genuinelyUnqualified` are pairwise disjoint; `weaknessSteering` receives `resolvable` ONLY.
- A `confirm`-tier flag is **never** in `resolvable` and never reaches `weaknessSteering` — **diff-check:** the steering builder reads `classifyWeaknesses(...).resolvable` and no other bucket (grep the builder for `.confirm`/`.genuinelyUnqualified` → 0).
- Defense-in-depth: even a mislabel that fed a confirm/unqualified gap to the engine is dropped/flagged by the gate (AC-1).
- The UI renders the 3-way split via the existing three panel groups (UX §4.1): Improve = resolvable, Confirm = confirm, Unresolved = genuinelyUnqualified.

**Failable-row requirement (AC-2/AC-7):** the fixture must carry ≥1 resolvable AND ≥1 genuinely-unqualified AND (for the G-1 power) ≥1 confirm-tier flag, or the 3-way split has no power. (The confirm tier needs an injected judge to populate `unsupported-authority` etc.; the fixture supplies a judge stub or a pre-built review carrying one confirm flag — the mechanical floor alone emits none, so a mechanical-only fixture proves only the resolvable/unqualified split and the test note must say the confirm row is INVALID-until a judge-bearing fixture exists.)
