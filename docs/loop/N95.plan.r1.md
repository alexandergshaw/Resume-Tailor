## 1. Contradictions / mechanism choices routed to this seat — resolved

The AC held the bar and handed the mechanism down; the design specified most of it. Two mechanism calls remained genuinely open and I resolve them here, both with instruments:

### D-PLAN-1 (LOAD-BEARING, silent-failure): the strip's `useCopyFeedback` clearKey must NOT include `previewReloadKey`

The design (§5.3) proposes clearKey `` `${insertedFactsJobId}|${previewReloadKey}` ``. That is wrong for this feature and would produce a **silent a11y failure**: `CopyFeedback.js:75-78` resets the feedback state to `EMPTY` **during render** whenever clearKey changes. But the MOVE success path *itself* bumps `previewReloadKey` (`useCompanyResearch.js:694`; and optimism adds a second bump at click), and the Mount's `announce({polite:"Fact moved."})` fires in `onMove` **after** `await research.moveInsertedFact` returns — i.e. after the reload bump. So the clearKey changes on the move's own reload, the render-phase reset wipes the just-set polite text, and the screen reader is never told the fact moved. Nothing looks broken on screen.

**Resolution: clearKey = `` `${insertedFactsJobId}` `` (job identity only), not the reload key.** A job switch still clears stale feedback; a move's own reload bump no longer clobbers the move's announcement. Cross-tab staleness is bounded by the existing 3 s self-clear (`CopyFeedback.js:25`), so dropping the reload key costs nothing here. **Instrument (4b):** AC-M3 must assert the polite region carries "Fact moved." **after** the move's reload bump settles (i.e. after `moveInsertedFact` resolves and the preview re-parses), not merely transiently on click — a test that only checks the text at click time would pass against the clobbering clearKey and miss the defect.

### D-PLAN-2: reuse the two live regions WITHOUT the visible chip

`CopyFeedbackStrip` (`CopyFeedback.js:107-131`) renders the two hidden live regions **and** a visible chip with a persistent `minHeight:"20px"` (`:116-128`). Design §5.3 chose to ship only the two regions for strip actions. Rendering the whole `CopyFeedbackStrip` would add an always-present 20px box to an already-dense row (a 6b/AC-C1 pressure, though not an interactive control).

**Resolution: render only the two live regions** — reuse the exact `Box component="span" role="status" data-copy-status="polite"` / `role="alert" data-copy-status="alert"` markup and the `seq`-keyed `<span>` idiom (`CopyFeedback.js:110-115`) with `visuallyHidden` (already importable from `@/lib/copilot/answerStatus`) and the `regionProps` from `useCopyFeedback`. No new export, no chip. **Note for 4b test selection:** the dialog already carries a FIRST `role="status"`/`role="alert"` (DriveResultRegion; see `CopyFeedback.js:101-106`). Tests MUST select the strip's regions by `data-copy-status`, never by `role`/`aria-live` alone, or they will assert against the wrong region (a silent false-green). The visible-chip option stays OPEN for 1c (§6).
