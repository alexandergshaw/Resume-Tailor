## 0. Executive summary (the binding decisions)

1. **The height-lock stays desktop/tablet-only; mobile stays single-page-scroll.** This is not a default to revisit — it is a documented ruling (`app/theme/mobileSx.js:244-268`, `PHONE_PANE_SX`) and R-142. Do NOT introduce a nested scroll container at `xs`. The mobile scroll marathon is fixed by (a) a sticky current question [already shipped], (b) collapsing/deferring the control stack above the answer, and (c) default-collapsing the SECONDARY answer aids — never by bounding a scroll region on a phone.

2. **The crowded answer area is fixed with progressive disclosure (accordion / collapsible groups), not tabs.** The answer + talking points stay always-visible (0 clicks); the invented example projects and the tech buzzwords collapse to a labelled one-tap disclosure on mobile. Mechanism: a shared `CollapsibleAid` primitive extending the existing `createChoiceStore` pattern (`examplesCollapse`), with a breakpoint-aware *effective default* (`choice ?? (isMobile ? "closed" : "open")`). Tabs are rejected for domain reasons (§2.3); this is nonetheless flagged as **OWNER-DECISION-1**.

3. **The shared mobile primitive ALREADY EXISTS** at `app/theme/mobileSx.js` (app-wide), contrary to the ground map and the `copilot-mobile` memory (both say "no mobileSx.js" / "app/copilot/mobileSx.js"). The design EXTENDS it; it does NOT create a new one, and must not create `app/copilot/mobileSx.js`. (§6, §1 correction C1.)

4. **One restructure of `AnswerAids.js` propagates to all four answer surfaces** (dashboard current card, dashboard history item, live feed card, practice sample answer). That single seam is the highest-leverage, highest-blast-radius edit in this chunk (§7, §8 blast radius).

5. **Chunk into three independently-landable slices** (N144a answer-area progressive disclosure; N144b control-stack + mobile ordering; N144c visual tokens/polish), with N144a's `CollapsibleAid` + token additions landing FIRST as a contract wave because b and c both consume it (§8).

## 1. Verified ground map (with corrections to the stale map)

### Breakpoints (verified `app/hooks/useResponsive.js:15-23`)
- `useIsMobile()` → `down("sm")` → **< 600px** (phones = `xs`).
- `useIsTablet()` → `down("md")` → **< 900px** (phones + small tablets).
- `CopilotClient.useIsRailBelowMd()` → `down("md")` (`CopilotClient.js:53-56`).

MUI default breakpoints: `xs` 0, `sm` 600, `md` 900. "Mobile-first / phone" in this chunk = the `xs` band, 320-599px, with 375/390/360 as the owner's real targets.

### The height-lock / nested-scroll today (verified)
- `CopilotClient.js:488`: `const { liveWrapperRef, liveHeight } = useLiveColumnHeight(live && !isMobile);` — the bounding **runs only when `live` AND not `isMobile`**, i.e. only at `sm`+.
- `CopilotClient.js:713-721`: the bounded wrapper's `sx`:
  - `height: { xs: "auto", sm: live && liveHeight ? liveHeight : "auto" }`
  - `overflow: { xs: "visible", sm: live ? "hidden" : "visible" }`
- `useLiveColumnHeight.js:32`: `liveHeight = calc(100dvh|vh - (rect.top + scrollY)px)`, re-measured on resize + a `ResizeObserver` on `document.body`.
- Inside the wrapper, the dashboard+rail row (`:866`) is `flex:1; minHeight:0; flexDirection:row`. Its first child (`:877`) is `flex:1; minHeight:0; overflow:"auto"` **unconditionally at every width**; the rail child (`:908`) is `overflowY:"auto"` and only renders here when `!isRailBelowMd` (md+). Below `md` the rail renders OUTSIDE the wrapper at `:915` (`mt:2`).

**Consequence (the escape hatch, confirmed):** at `xs` the wrapper is `height:auto; overflow:visible`, so the inner `overflow:"auto"` (`:877`) has no bounded height to scroll against and is **inert** — the page is the sole scroller. "Just scroll" is real and is the current `xs` behaviour. At `sm`+ while live, the wrapper fills `calc(100dvh - top)`, the dashboard scrolls internally, the rail scrolls internally (md+) or sits below the fold reached by page scroll (sm band).

**No NEW hidden fold is introduced by the N143/N150 rows.** The new rows render INSIDE `AnswerAids`, inside `CurrentAnswerPanel`, inside the dashboard's `overflow:auto` container — reachable by internal scroll at `sm`+ and by page scroll at `xs`. The historical hidden-fold defect (R-216, `5578f0a`) was content placed AFTER the bounded wrapper; the new rows are not there. (This is the brief's "second hidden fold" worry answered: the rows do not create one; the risk is the control stack ABOVE them, §3.)

## 2. Information architecture for the crowded answer area (the core)

### 2.1 The hierarchy (domain recommendation; UX/owner may tune)
Under live pressure on a phone, the candidate needs, in strict priority:
- **PRIMARY (always visible, 0 clicks):** the current question (sticky strip, already shipped) and the direct answer + talking points (`AnswerLines`). These must never sit behind a disclosure or a tab.
- **NEAR-PRIMARY (visible, compact):** the resume anchor — "Closest role" + "Project to talk about" (the candidate's own real material, ~2 rows). Low height, high trust value. Keep visible by default even on mobile.
- **SECONDARY (one-tap disclosure, default-collapsed on mobile):** the posting words chips, the **Tech buzzwords** group, the **Example projects** group. These are the height offenders and the "aware of / invented" material — useful on reflection, not while first answering.

Recommended mobile default: collapse the two tallest/riskiest groups (Example projects — already collapsible; Tech buzzwords — made collapsible), keep resume + posting-words visible. Posting-words is a borderline call (compact chip row); whether it collapses too is **UX/owner's** to tune via the same primitive. The exact set that defaults collapsed on mobile is **OWNER-DECISION-2**.

### 2.2 The mechanism (binding structural seam): `CollapsibleAid`
A shared collapsible-group wrapper, so every `AnswerAids` group discloses the same way, with a breakpoint-aware default, without CSS `order`, and without remounting `aria-live` regions in a way screen readers miss.

Proposed location: `app/copilot/CollapsibleAid.js` (a `"use client"` component — it uses hooks). The React-free store stays in `lib/`.

**Contract:**
```
// app/copilot/CollapsibleAid.js
export default function CollapsibleAid({
  label,        // string: the always-visible disclosure-button text (carries provenance, e.g. "Example projects (invented)")
  choiceStore,  // a createChoiceStore instance (lib/copilot/choiceStore.js), crossWindow:true, normalize open|closed|null
  defaultOpenOnMobile = false, // effective default when stored choice is null and isMobile is true
  children,     // the group body (a <dl> or chip stack); UNMOUNTED when collapsed
}): JSX
```
Behaviour / invariants (checkable):
- Reads the store via `useSyncExternalStore(store.subscribe, store.get, store.getServerSnapshot)` and `useIsMobile()`.
- **Effective open** = `choice === "open" ? true : choice === "closed" ? false : (isMobile ? defaultOpenOnMobile : true)`. Stored value stays `null` until the user taps — so the breakpoint default can change per release with no migration (exactly the extension `examplesCollapse`'s own comment anticipated, `AnswerAids.js:216-219`).
- Renders a native `<button>` (MUI `Button variant="text"`) as the single tab stop, `aria-expanded`, `aria-controls` pointing at the body `id` (`useId`), visible text = `label`, `...TOUCH_TARGET_SX`. The collapsed state keeps the honest provenance word in the label ("invented", "Suggestions") — matching `ExampleProjectsGroup`'s existing a11y shape (`AnswerAids.js:370-413`).
- Collapsing UNMOUNTS `children` (out of a11y tree + tab order), matching the existing examples pattern. It must NOT use CSS `order` or breakpoint-keyed `order` to hide content (the `copilot-mobile` WCAG 2.4.3 trap: "CSS order moves pixels, not focus").
- Any `aria-live` region inside `children` (e.g. the tech-terms detail region, `AnswerAids.js:600`) is only live while the group is open; a collapsed group has no open terms, so nothing is announced-then-hidden. The region must NOT be mounted-empty-then-populated-on-open in a way NVDA/JAWS miss — but because expanding mounts both the region and (at most) zero open terms, and a term is opened by a later explicit tap (its own live-region write), this is safe. (Checker: verify no `aria-live` region holds final text at the instant it mounts on expand.)

**The per-group stores** (each `createChoiceStore`, `crossWindow:true`, `normalize` → `open|closed|null`), module-scope in `AnswerAids.js` beside `examplesCollapse`:
- `examplesCollapse` — EXISTS (`AnswerAids.js:221-228`); reuse. Add `defaultOpenOnMobile={false}` at its `CollapsibleAid` call site.
- `techTermsCollapse` — NEW, key `"copilot-tech-buzzwords"`.
- (optional, UX/owner) `postingWordsCollapse` — NEW, key `"copilot-posting-words"`.

Module-scope stores are SHARED across all mounted `AnswerAids` instances on the page (one choice per group for the whole surface) — this is the existing `examplesCollapse` behaviour and is correct for a per-session "I keep examples collapsed" preference. History items retain their own per-item `expanded` useState (`CopilotDashboard.js:696`), which gates whether their `AnswerAids` mounts at all; the group-collapse choice applies inside whichever cards are expanded. (Checker: a collapsed group in the current card and an expanded history item share the group choice — verify that is acceptable, it matches examples today.)

### 2.3 Why accordion/disclosure, not tabs (domain reasoning) — OWNER-DECISION-1
- **The answer must never be behind a tab.** The primary content (points) must be always-on; a tabbed answer area would at best put aids in sibling tabs while points stay out — i.e. still a disclosure for the aids, with a worse interaction.
- **Mode-switch loses your place under pressure.** Tabs/segmented controls show one group at a time and demand a deliberate switch; a candidate mid-answer who taps "Examples" loses the points from view. Independent accordions let points stay while one aid opens.
- **Reading order + a11y.** Accordions preserve DOM reading order and one-tab-stop-per-group; tabs need ARIA tabpanel wiring and risk the `aria-live`/remount traps the memory records. Disclosure is the pattern already shipped here (examples group, per-term tech detail, history items) — consistent, low-risk.
- **Minimize-clicks.** Primary = 0 clicks (always visible); any secondary = exactly 1 tap. Tabs are also 1 tap but cost a persistent tab bar (height) and the "which tab" cognitive load.

**Recommendation: collapsible groups (accordion).** This is nonetheless the UX-defining call the brief flags; recorded as OWNER-DECISION-1 with the above tradeoff.

### 2.4 Desktop unchanged
At `md`+ the effective default is open for every group (stored `null` → open), `AID_GRID_SX` goes two-column, and the dashboard is a bounded internal scroller — the aids render exactly as today. The disclosure buttons are present but the groups start open, so a desktop user sees no regression (R-142 dual-screen no-scroll is about the wrapper height, not the aids; adding collapse buttons that start open does not change desktop height materially — MEASUREMENT, verify §9).

## 3. Height-lock / nested-scroll rework per breakpoint (my core deliverable)

### STRUCT-A (binding): keep the height-lock gated on `live && !isMobile`; mobile = single page scroller.
- **`xs` (< 600px):** wrapper `height:auto; overflow:visible` — UNCHANGED. The page is the sole scroller. Do NOT add `overflow:auto`/a fixed height to any content pane at `xs`. Rationale: `PHONE_PANE_SX` ruling (`mobileSx.js:244-268`, §1 C3) — a nested touch scroller steals the page swipe, and `100dvh/vh` panes clip under the iOS URL bar. The mobile fix for the marathon is §2 (collapse aids) + STRUCT-B (control stack), not bounding.
- **`sm` band (600-899px):** wrapper bounded to `calc(100dvh - top)`, dashboard scrolls internally (`:877`), rail renders below the wrapper (`:915`, reached by page scroll). UNCHANGED. This is the half-window dual-screen case (R-142) and must not regress.
- **`md`+ (≥900px):** as `sm` but the rail sits INSIDE the wrapper beside the dashboard with its own scroller (`:907-911`). UNCHANGED.

The new N143/N150 rows add height INSIDE the dashboard's internal scroller (`sm`+) or the page flow (`xs`) — both reachable, no new structural fold (§1). **The design's only change to the height-lock is: nothing.** The lock is already correct; the mobile problem is above/around it, not in it. Stating this explicitly is a deliverable: the checker should confirm no edit to `useLiveColumnHeight.js` or the wrapper `sx:713-721` is warranted or made.

### STRUCT-B (binding seam): reduce and reorder what sits ABOVE the answer on mobile.
The marathon is the control stack (§1). Two structural moves, both `xs`-only, both honouring "reorder the array, never CSS `order`" (`copilot-mobile`):

- **B1 — collapse SessionControls into the sticky strip region on mobile, OR compact it.** Today SessionControls is a full wrap row that, at `xs` (spacer hidden), wraps Start/Stop + pill + clock + Auto-draft + Copy + Clear + Download into several lines above the answer. Proposal (structural options, UX to choose):
  - (preferred) At `xs`, render only Stop/Start + StatusPill + clock inline; move Auto-draft, Copy, Clear, Download session log behind a single "Session options" disclosure (one `CollapsibleAid`-style toggle or an overflow menu). This keeps the one urgent control (Stop) and the status visible, defers the rest. Copy/Clear/Download are not needed mid-answer.
  - This is a prop/branch change to `SessionControls.js` (add an `isMobile`-driven compact branch); no new state crosses the CopilotClient boundary (SessionControls stays stateless — its header rule, `SessionControls.js:28-35`).
- **B2 — defer `ManualQuestion` below the dashboard on mobile.** `ManualQuestion` (`:836`) is a secondary affordance (type a missed question). On `xs`, render it AFTER the dashboard (reorder the rendered children array, with a stable `key`, not CSS `order`). Pre-session there is no answer, so order is irrelevant then; during a session the answer should lead.
- **B3 — the sticky question + ask box already lead on `sm`+.** On `xs`, confirm (MEASUREMENT) the strip is sticky for portrait phones so the question stays pinned while the candidate scrolls to the answer. If the strip falls back to static on short geometries, the question scrolls with the page — acceptable degraded mode (it is at the top).

SpeakerBar is self-gated (in-person only) and compact; leave as-is. shareInstructions is a short paragraph; UX may shorten or move it below SessionSetup on mobile (token/wording, not structural).

**Ordering mechanism (binding):** any mobile reorder is done by building the children in a different ARRAY order under an `isMobile` branch with stable `key`s, so focus/reading order moves with the pixels. Never `order`/breakpoint-keyed `order`. (Pinned by the `copilot-mobile` WCAG 2.4.3 lesson.)

## 4. Click / distance reduction (the control stack audit) — deliverable 3

Concrete target layout, mobile (`xs`), during a live session, top → bottom:
1. LiveHearingStrip (hearing proof — keep, it is the "am I alive" signal, R-216).
2. Sticky question strip + ask box (keep; sticky when hostable).
3. Dashboard: answer + points (PRIMARY) → resume anchor (near-primary) → collapsed secondary aids.
4. Compact SessionControls: Stop + status + clock; "Session options" disclosure for Auto-draft/Copy/Clear/Download (B1).
5. Collapsed SessionSetup header (already collapses on Start).
6. ManualQuestion (deferred here on mobile, B2).
7. TranscriptDisclosure (collapsed, as today).

Click budget outcome (checkable against the design, not pixels): primary answer = 0 clicks; any one secondary aid = 1 tap; starting a session pre-session = the existing Start (1 tap) with SessionSetup defaults (posting/mic/source remembered via their stores — `minimize-clicks`). No new nested menus for the primary path.

Open gap (OWNER-DECISION-3): the ask box is absent pre-session (child of the strip, `StickyQuestionStrip.js:237-249`). Pre-session is exactly when a candidate wants to ask about the application. Fixing it means mounting `AskAiBox` as a SIBLING of the strip in CopilotClient (and PracticeClient), not a child. That is a structural move with its own small blast radius (the strip's `applicationId`/`engine` props already exist on CopilotClient). Recommend folding it into N144b; flag to owner since it changes where the box lives.

## 5. Visual system — deliverable 4 (token vs structural)

Classify every visual change so the plan/TDD seats know what is unit-testable (declared `sx`) vs browser-only (geometry):

- **Chip rows** (posting words, tech buzzwords) — already `flexWrap:"wrap"` + `BREAK_LONG_WORDS_SX` + `height:"auto"` label wrapping (`AnswerAids.js:583-592, 748-771`). No structural change; UX may adjust `gap`/`fontSize`. **Token.**
- **Spacing/typography consistency** — the aids already share `AID_GRID_SX`, `LINE_GAP`, and the `--text-secondary`/`--text-primary`/`--bg-soft` palette with measured contrast (R-228). - **Expanders (`ExpansionPanel`, per-line "More detail") and per-term tech detail** — unchanged; they are already disclosures. Visual polish only.

Structural (not token): the `CollapsibleAid` wrapper and the per-group stores (§2.2), the SessionControls compact branch (§3 B1), the mobile child-reorder (§3 B2), and (if adopted) the ask-box sibling move (§4). Everything else is tokens/wording the UX seat owns.

## 7. Scope across the three surfaces — deliverable 5 (shared vs surface-specific)

**Shared (one edit, four surfaces):** `AnswerLines.js` and `AnswerAids.js` are the answer-area renderers for ALL of:
- dashboard current-answer card — `CopilotDashboard.CurrentAnswerPanel` (`CopilotDashboard.js:442-459`), used by LIVE and PRACTICE (both mount `CopilotDashboard`).
- dashboard history item — `CopilotDashboard.HistoryItem` (`:743-759`), LIVE.
- live feed card — `QuestionFeed.QuestionCard` (`QuestionFeed.js:203-216`), LIVE (inside TranscriptDisclosure).
- practice sample answer — `SampleAnswer` (`SampleAnswer.js:220-234`), PRACTICE.

So the §2 progressive-disclosure restructure of `AnswerAids` propagates to live + practice + history + feed automatically — the highest-leverage seam. **This is also the highest blast radius: a regression in `AnswerAids` hits every surface.** The module-scope group stores mean the collapse choice is shared across all four on one page (as examples already is).

**Surface-specific (not shared):**
- The control stack (SessionSetup/SessionControls/SpeakerBar/ManualQuestion) is LIVE-only (`CopilotClient.js` else-branch). PRACTICE has its own `PracticeControls.js`; ROLES has `RoleDrillControls.js`. The §3 control-stack work must be applied per mode where it applies; live first (owner scope includes practice + dashboard, so a parallel practice-controls pass is in scope but is a different file set).
- The sticky strip (`StickyQuestionStrip`) is shared between live and practice (both mount it), so B3/ask-box changes touch one component but two call sites.
- The height-lock (`useLiveColumnHeight`) is LIVE-only (`live && !isMobile`); practice uses `PHONE_PANE_SX`-style panes, not the bounded wrapper.

**Consistency guarantee:** because the answer area is one component, live/practice/history/feed cannot drift. The overhaul must NOT fork `AnswerAids` per surface (the whole reason it was consolidated — `AnswerAids.js:16-24`).

## 8. Chunking — deliverable 6, with seams and blast radius

Three slices; **N144a lands first as the contract wave** because b and c consume its primitive and tokens.

### N144a — Answer-area progressive disclosure (the core, highest leverage/blast)
- New: `app/copilot/CollapsibleAid.js` (+ its hook usage), new per-group `createChoiceStore`s in `AnswerAids.js` (`techTermsCollapse`, optional `postingWordsCollapse`), token additions in `app/theme/mobileSx.js` if any.
- Edit: `AnswerAids.js` — wrap the Tech buzzwords group (and optionally Posting words) in `CollapsibleAid`; apply `defaultOpenOnMobile={false}` to it and to the existing `examplesCollapse` call site.
- **Seam / contract:** `CollapsibleAid` (§2.2). `AnswerAids`'s public props are UNCHANGED (`{buzzwords, anchor, projectExample, projectExampleLive, techTerms, finalOnly}`) — the four call sites need NO edit. This is the load-bearing boundary: keep the `AnswerAids` prop signature frozen so b/c and the four surfaces are untouched.
- **Blast radius (enumerated):** callers of `AnswerAids` = exactly 4 (CurrentAnswerPanel, HistoryItem, QuestionCard, SampleAnswer) — all OWNED by this chunk's verification, none edited (checked-safe: prop signature frozen). The module-scope stores are new (no existing caller). `examplesCollapse` behaviour changes only in its mobile default (adopted, pinned by `AnswerAids.projectExample*` tests — check they do not assert desktop-open as mobile-open).
- Tests: declared-value (the `CollapsibleAid` renders button + `aria-expanded`; collapsed unmounts body; effective-default logic as a pure function given `(choice, isMobile)`); mutation controls per loop-traps-tests. Geometry deferred to §9.

### N144b — Control-stack reduction + mobile ordering (LIVE; parallel PRACTICE pass)
- Edit: `SessionControls.js` (compact `isMobile` branch, B1 — stays stateless), `CopilotClient.js` (mobile child-reorder B2; optional ask-box sibling move §4). Parallel: `PracticeControls.js`/`PracticeClient.js` for the practice equivalent.
- **Seam:** SessionControls stays prop-only (no state across the boundary — its header rule). The reorder is an array-order branch in CopilotClient's render, stable keys.
- **Blast radius:** `SessionControls` has 1 caller (CopilotClient); `CopilotClient` render order change affects focus order — must be verified against `copilotHeadingOrder.test.js` and the F7 focus-move effects (`CopilotDashboard.js:298-348`) and `CopilotClient.*wiring*.test.js`. The ask-box sibling move (if adopted) changes `AskAiBox`'s mount site — adopt `StickyQuestionStrip`'s existing `applicationId`/`engine` props; `AskAiBox.test.js` pins the current child limitation and will need updating (planning defect to surface, not silently edit).
- Depends on N144a only for the shared `isMobile` reorder discipline, not its code — can land after a.

### N144c — Visual tokens / polish
- Token/wording: spacing, typography, chip `gap`/`fontSize`, shareInstructions shortening, chevron/accent polish. Edit `app/theme/mobileSx.js` + the component `sx` + copy.
- **Blast radius:** token changes in `mobileSx.js` touch every consumer app-wide — any new token must follow the `sm`-initial-value rule or it silently changes desktop. Lowest-risk slice; lands last.

**Argument for three chunks, not one:** the answer-area restructure (a) is independently valuable and independently verifiable, and it is the one edit that must be right (four surfaces). The control stack (b) is a different file set (CopilotClient/SessionControls) and a different risk (focus order). Tokens (c) are app-wide and lowest-risk. Splitting isolates the blast radii and lets a go to the owner's phone for the decisive mobile verification before b/c pile on. Disjoint file sets per `disjoint-subagents` (a touches AnswerAids + new files; b touches CopilotClient/SessionControls; c touches mobileSx + sx) — `AnswerAids.js` is a's alone, `CopilotClient.js` is b's alone, `mobileSx.js` is a-then-c (so a's token additions land before c edits it — contract-wave ordering).

## 9. Verification split — deliverable 7

### Unit-testable (declared structure / `sx` value / pure logic) — permanent tests
- `CollapsibleAid` renders a native button with `aria-expanded` matching open; `aria-controls` names the body id; collapsed state unmounts `children` (query returns null); label text present in both states.
- Effective-default as a pure function: `(choice="open")→open`, `(choice="closed")→closed`, `(choice=null, isMobile=true)→defaultOpenOnMobile`, `(choice=null, isMobile=false)→open`. Mutation control: flip the `isMobile` branch and assert a test goes red.
- Group stores: `createChoiceStore` normalize/encode/decode/crossWindow per `choiceStore.test.js` precedent; FD-1 per-instance isolation if a second store is added.
- Touch-target tokens applied to new controls: `getComputedStyle(...).minHeight` resolves to `44px` at `xs` and to the initial value at `sm` (the `mui-sx-numeric-traps` / `InterviewTypePicker.test.js` "computed cascade" technique). Positive control required (a scan that finds zero because it asked the wrong question is indistinguishable from absence — `measurement-instruments.md`).
- `AnswerAids` prop signature unchanged (the four call sites compile and render); reading order (dt/dd, lead-before-content) preserved per `AnswerAids.test.js`.
- Focus order / heading order for the control reorder: `copilotHeadingOrder.test.js`, `CopilotClient.*wiring*.test.js` stay green; reorder done by array not CSS `order` (assert the rendered DOM order equals the intended order at `xs`).

### Browser-only (geometry) — owner/browser-pane checklist at 320/360/375/390px, both themes
1. **No horizontal overflow:** `getBoundingClientRect().right <= innerWidth` per element (NOT a scrollbar check — `html{overflow-x:hidden}` clips silently, `measurement-instruments.md`). Positive control: a known-wide element.
2. **Touch targets ≥44px:** `getBoundingClientRect().height/width` of every interactive control (disclosure buttons, chips, Stop, Session-options toggle) — jsdom returns 0, so browser-only.
3. **The answer + points are the first substantial content below the sticky question** during a live session on a phone — i.e. the marathon is gone: measure the scroll distance from the top of the dashboard to the first `AnswerLines` bullet; it should be ≤ ~one control row, not the full stack.
4. **Sticky question strip:** is `isHostable` true at 375×812 / 390×844 portrait (strip pinned)? Confirm it does not clip the question and does not flip stickiness mid-scroll (it reads the LARGE viewport deliberately). Short landscape may fall back to static — acceptable.
5. **No nested scroller on `xs`:** scrolling the answer area scrolls the PAGE, not an inner box (swipe-gesture test — the page must not feel "stuck"). Confirm the dashboard's `overflow:auto` stays inert at `xs`.
6. **Desktop unchanged (R-142):** at 1280 and a ~720px half-window, the live column still fits without page scroll; the aid disclosure buttons start open and do not add a fold.
7. **Window must be visible** when measuring (`measurement-instruments.md`): check `document.body.innerText.length > 0` before trusting any rect; a minimized pane fabricates a clean zero.

### What I could NOT verify (failed/absent instruments — INVALID, not zero)
- **All geometry above is browser-only and was NOT measured** in this design pass (no browser pane driven here; jsdom has no layout). Every pixel/overflow/sticky/touch claim is a HYPOTHESIS for §9's checklist, not a result. The `measurement-instruments.md` rule applies: a design round must not estimate a number a harness could measure — so this design proposes mechanisms and defers all geometry to the owner's phone / the browser pane.
- **`isHostable` at the owner's real phone geometries** — computed by hand it suggests portrait phones host the sticky strip, but the root font-size, real header height and exact viewport are runtime values; treat "sticky on phone" as MEASUREMENT, unconfirmed.
- **Whether collapsing the aids on mobile actually removes the marathon** depends on real rendered heights of the control stack and the answer — browser-only (§9 item 3). The design's claim that the stack is the marathon is a structural reading (what renders above the answer), not a pixel measurement.
- **Content quality** (whether the aids are worth showing at all) is owner/Gemini-env per the standing N135/0e rule and is out of scope for this chunk (it is N143/N150's probe).

## 10. Owner-facing decisions

- **OWNER-DECISION-1 (UX-defining):** the crowded answer area — collapsible groups (accordion) vs tabs vs segmented control. My strong recommendation is collapsible groups (§2.3): the answer stays always-visible, each aid is one tap, reading order and the existing disclosure patterns are preserved, and tabs would hide the points or demand a mode-switch under live pressure. Owner may prefer tabs for a cleaner look; if so, the points must stay OUT of the tab set and the `aria-live`/remount traps must be handled.
- **OWNER-DECISION-2:** which aid groups default-collapsed on mobile. Recommendation: collapse Example projects (already collapsible) + Tech buzzwords; keep the resume anchor and (borderline) the posting-words chips visible. The mechanism supports any choice with no migration.
- **OWNER-DECISION-3:** move the Ask-AI box to a strip SIBLING so it exists pre-session on all surfaces (fixes the known limitation in `StickyQuestionStrip.js:237-249`). Recommend yes, folded into N144b. It is a structural move (new mount site), hence owner-visible.
- **OWNER-DECISION-4 (scope confirm):** is the practice-mode control-stack pass (PracticeControls/PracticeClient) in N144b, or deferred? Owner scope says practice is in scope; confirm it rides with live in b or gets its own slice.
