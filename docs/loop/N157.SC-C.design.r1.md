## 0. The design in one paragraph, and the five things that changed the brief

**Design.** A new "Study plan" sub-view inside practice mode, mounted by a thin `PracticeSurface` that also owns a two-button
sub-view toggle. The sub-view shows ONE focused card at a time (ChatGPT's one-thing-at-a-time pacing, Quizlet's
prompt / reveal / self-grade loop). A card with a stored `reveal` is a self-test (primary "Show answer", then "Missed it" /
"Got it"); a card without one is read-through (primary "Next"). One progress write per card, optimistic, through the shipped
`recordProgress` -> `writeStudyPlanProgress`. Missed cards come back inside the same plan after the first pass, derived purely
from the persisted `grade`, so resume works across sessions and devices with no ephemeral queue. Create is a two-phase,
module-scope orchestration (research awaited, then generate) that survives the user leaving the tab mid-build. A rebuild can
never silently destroy a good plan: a server-side guard (a required prerequisite, section 4.3) plus a client-side
last-good guard.

**What the tree contradicts or adds (each is a section-2 finding with evidence):**

1. **F3 - `POST /api/study-plan` returns no plan, ALWAYS writes a row (including an empty `unavailable` over a good plan), and
   REPLACES `knobs` with defaults if the body omits them.** The SC-gen footgun is real and the client cannot fully guard it
   alone: by the time the response arrives the database row is already destroyed. A server-side preserve-last-good guard is a
   hard prerequisite for any Rebuild affordance (section 4.3).
2. **F4 - the digest route answers a research failure with HTTP 200 and `digest.status === "failed"`, and under the embedded
   engine it refuses (503) BEFORE it reads the cache.** So `ensureStudyDigest` does not throw on failure, and it can never be
   used to "reuse a ready digest" for an embedded user. Phase 1 must branch on `digest.status`, and on `engine`.
3. **F5 - cards have two shapes.** Gemini cards carry `text` (prompt) + `reveal` (answer); embedded cards are digest lines with
   NO `reveal` and, as built, carry the digest's ENTIRE citation list on every card. Neither `reveal` nor `sourced` is declared
   by `normalizeItem`; they survive only through its `...item` spread.
4. **F1/F2 - the "own posting picker" precedent is not RoleDrillClient** (it owns a ROLE picker, no posting). The real precedent
   is `PracticeSetup` -> `PostingPicker`. And `PostingPicker` cannot be reused unmodified for a REQUIRED selection: its
   empty-account helper text appends "You can also <blankHint>", which is false advice here.
5. **F9/F10 - two cheap-to-miss collisions with landed tests:** `CopilotClient.roles.test.js` finds the mode button with
   `buttonNamed(/^practice$/i)` (a sub-view button named "Practice" would double-match), and seven suites that mount `CopilotClient`
   `vi.mock("./practice/PracticeClient")` (they keep working through `PracticeSurface` only if it imports that exact module).

## 2. Findings that correct or extend the brief (each changes the design)

**F1. The "own picker" precedent is mis-attributed.** Arch r2 section 8 calls the study picker "the RoleDrillClient pattern".
RoleDrillClient owns a role select. The accurate precedent is the practice setup path (`PracticeSetup` -> `PostingPicker`
over `normalizePostingRows`). The arch's DECISION (StudyPlanClient owns its own selection; PracticeClient is not edited)
stands; only the citation was wrong. *Consequence:* the plan seat cites `PracticeSetup`/`PostingPicker`.

**F2. `PostingPicker` is not reusable as-is for a REQUIRED selection, and offers no preselect.** (a) With zero tracked
postings and nothing selected it renders "... You can also <lowerFirst(blankHint)>" - for the study view that reads
"You can also pick a tracked application ..." (false: there is no optional alternative); passing `blankHint=""` leaves a
dangling "You can also ". (b) Options live inside the component, so "restore the last-used application" cannot be done from
outside. *Consequence:* see decision PD-2: add two OPTIONAL props to `PostingPicker` (`required`, `initialId`) with
byte-identical defaults (precedent: AC-H1.1/H1.2 added `label`/`blankHint` the same way), or accept re-pick and a garbled
empty-account message. There is NO `PostingPicker` test file today (`app/copilot` has only `PostingPicker.js`), so the
byte-identical-default guard is a new test the plan seat must add.

**F3. `/api/study-plan` is destructive on failure and silently resets knobs.** OBSERVED: the route responds
`{ status, partial, reason, error? }` and never the plan (client must re-read through RLS); `generateStudyPlan` ALWAYS calls
`writeStudyPlan`, and on `unavailable` writes an empty-but-valid plan, which REPLACES the stored `plan` column (its own
header: "the caller that wants to keep a previous plan across a failed rebuild has to decide that before calling");
`writeStudyPlan` also always writes `knobs` (normalized from the body, so an omitted `knobs` becomes `DEFAULT_KNOBS`).
*Consequences:* (i) preserve-last-good needs a server guard (section 4.3), because a browser cannot "decide before calling"
what the server will overwrite; (ii) every client rebuild MUST send the stored `record.knobs`, never omit them (a rebuild
that omits knobs silently resets SC-D's customization); (iii) `progress` is safe - it is RPC-write-only (`writeStudyPlan`
does not destructure it).

**F4. Digest semantics the create flow must respect.** OBSERVED in `application-digest/route.js`: a failed research is
persisted and returned as `Response.json({ digest })` with `digest.status === "failed"` and 200; the only non-2xx are
401/404/429/500/503. `wantsEmbedded(body?.engine)` is checked at :220, BEFORE `listDigests` (:235) and the ready
short-circuit (:244). *Consequences:* (i) `ensureStudyDigest` resolving is not "research is ready": check
`digest.status === "ready"`; (ii) for `engine === "embedded"` skip phase 1 entirely (it can only 503) and go to phase 2, which
reads any digest already stored and builds a deterministic partial plan (SC-gen section 2.3) - or returns `unavailable /
no-research`, which the UI must render as "needs research" rather than a generic failure; (iii) `status: "disabled"` (kill
switch, `{status:"disabled"}` with no `error` key) and the missing-key 503 (`{error}`) need their own copy.

**F5. Two card shapes, and an unbounded citation list.** OBSERVED: `STUDY_PLAN_SYSTEM` defines `text` = the question shown
first, `reveal` = the answer shown afterwards; `shapeItem` writes `reveal` only if non-empty, plus `sourced`.
`buildEmbeddedStudyPlan` emits cards with only `text` (one digest line each), `citations` = the evidence item's whole list.
`normalizeItem` does not list `reveal` or `sourced` (they ride the spread). *Consequences:* the UI reads both defensively
(`typeof item.reveal === "string" && item.reveal.trim() !== ""`); read-through cards are first-class, not an error; sources
under a card must be bounded (3 inline hosts + a disclosure); a one-line schema pin for `reveal` is a small cross-seat item
for SC-B-schema's file (flagged, not done here). Also observed, unexecuted: `splitSections` turns any non-empty digest line
into a card, so a digest section reading "Not found" becomes a card - a generator-quality note for the owner-env probe.

**F6. Progress-write semantics shape the interaction.** (i) One write per card advance (at grade, or at "Next" for a read
card), not at reveal: a reveal with no grade has no meaning for done-ness, and writing at both halves RPC volume. (ii) The
grade write must carry the full entry `{ revealedAt, grade }` because the merge replaces the item's whole entry
(`seen || delta`). (iii) The cursor is always the card just recorded (same `itemId` feeds both), so "resume" is "next pending
AFTER the cursor". (iv) There is no reset path in the data layer (merge only adds), so "start over" cannot be a persisted
action in SC-C (decision OD-5 / section 3.3).

**F7. Content-derived keys are stable only for IDENTICAL text.** `itemKey` = hash(`topicHint`, `text`). An LLM rebuild rewords
nearly every card, so after a rebuild nearly all `seen` entries are orphans (they stay in the row, addressing nothing).
*Consequences:* counts must iterate the PLAN's cards, never the keys of `seen`; Rebuild is destructive-in-effect for progress
and earns a confirmation ONLY when there is progress to lose (section 4.3, minimize-clicks: confirmations only where
irreversible); a cursor that matches no card must fall back to "first pending", not crash or restart silently.

**F8. Two surfaces in the same screen disagree.** `TabHeader` (rendered by `CopilotClient`, above `PracticeSurface`) says, in
practice mode, "Practice speaking out loud with your camera and mic" then "see the notice below for what's sent ..." (abridged), and
`CopilotClient.roles.test.js` ("keeps practice mode's own description") pins it. When Study is the active sub-view that
sentence is stale. It cannot be fixed from inside `PracticeSurface` without lifting sub-view state into `CopilotClient`
(more edits to a 947-line file and a landed test). *Consequence:* accepted wart, flagged OD-7; the Study view carries its own
intro line and its own egress notice so the page is never silent or false about what the study tool does.

**F9. A label collision with a landed suite.** `CopilotClient.roles.test.js` queries `buttonNamed(/^practice$/i)` and
`clickMode(/^practice$/i)` (:201, :240, :355) to find the MODE button. A sub-view button whose accessible name is exactly
"Practice" would make that query match twice in practice mode. *Consequence:* pinned labels are "Answer aloud" and "Study plan"
(section 7); a hard constraint, not taste.

**F10. The mount seam's real blast radius.** Seven suites mock the practice client by path:
`vi.mock("./practice/PracticeClient", ...)` in `askAiPreSession`, `copilotHeadingOrder`, `CopilotClient.wiring`,
`CopilotClient.roles` (returns a `practice-stub` div it later queries), `CopilotClient.mobileStack`, `CopilotClient.downloadLog`,
`CopilotClient.confirmGate` (grep with `head_limit: 0`, 7 hits; canary: the multi-line form in `roles` is among them). Vitest
mocks by resolved module id, so they keep intercepting when `PracticeSurface.js` imports `./PracticeClient` - but those suites
will now also (a) load `StudyPlanClient`'s import graph and (b) render the sub-view toggle in practice mode. Separately, at least 7
suites READ `PracticeClient.js` as SOURCE TEXT (`glossaryMount`, `askAiPreSession`, `predictionsRemoved`,
`projectExampleSelfHeal.wiring`, `StickyQuestionStrip`, `AskAiBox`, `useTechTerms.gate`; `AnswerAids.projectBulletDetail.sites`
lists it too, and the count is a floor, not an enumeration); they are unaffected because `PracticeClient.js` is not edited. *Consequence:* the plan/TDD seat's G1 instrument is "run those seven mock-sites after the
rename", listed in section 13.

## 3. The experience (PROPOSAL)

### 3.1 Reading of the owner's intent

"Walk you through the plan interactively, ChatGPT/Quizlet-style" is read as: **guided, one focused step at a time, you respond
with one tap and it moves on (ChatGPT's pacing), on prompt / reveal / self-grade cards (Quizlet's loop), with missed cards
coming back.** It is NOT read as a scrolling chat transcript, and NOT as typed-answer AI feedback (that is a new model route
and a new egress leg; the spoken-answer critique already exists in the other sub-view). Both alternatives are flagged OD-1.

### 3.2 The card step (the screen the user lives in)

Mobile-first, single column, one primary action per step, no nested scroller (the page is the scroller, `PHONE_PANE_SX`
thinking), no animation, no gesture (the app disables pixel-drag on phones; swipe would need a non-gesture twin anyway).
Top to bottom, DOM order = visual order (reorder the array, never CSS `order`):

```
[ provenance banner (only partial/unavailable-derived plans) ]
caption:  <Topic title>                          [New|Review] [No source]
caption:  Card 3 of 8 in this topic  .  12 of 40 done   [progress bar, labelled]
h4:       <prompt text>                          (read card: the topic label; the text is body copy)
(first card only, once) hint: "Answer it out loud or in your head, then show the answer."
[ Show answer ]                                  <- the one primary action
secondary row:  [ Previous card ]  [ Plan outline ]
```

State table (every row is a distinct render; `quiz` = card has a non-empty `reveal`, `read` = it does not):

| Step state | What is on screen | Primary / secondary | Writes |
|---|---|---|---|
| Q0 quiz front | prompt, chips, progress | **Show answer** / Previous, Outline | none |
| Q1 quiz revealed | prompt + answer group (`h5` "Answer", the `reveal` text, sources) | **Got it** (contained) + **Missed it** (outlined), equal width, side by side, each >= 44px / Previous, Outline | one `recordProgress`: `{ revealedAt, grade }` |
| R0 read | topic label as `h4`, `text` as body, sources | **Next** / Previous, Outline | one `recordProgress`: `{ revealedAt }` (no grade) |
| Revisit (after Previous) | the earlier card already revealed, a text line "You marked this: Got it" / "Missed it" | **Got it** / **Missed it** (re-grade overwrites the entry); a third text button "Back to where I was" is NOT added - grading advances | one `recordProgress` |
| Second pass | same Q0/R0 plus a caption "Going back over cards you missed or skipped" | same | same |
| Complete | `h4` "All cards done", `You've been through all N cards.` | **Review all again** (session-local, 3.3) / Outline | none |
| Save failed (overlay on any step) | `Alert` "Your last answer wasn't saved. It's kept on this device for now." | **Retry saving** | re-send the last failed card |

Advance is OPTIMISTIC and instant: the click calls `recordProgress` (not awaited for navigation) and the next card renders
from the store's already-merged `progress`. A failed write does not rewind the card (the store's stated stance); it raises the
save-failed alert. **Advance guard:** controls are inert for `STUDY_ADVANCE_GUARD_MS` after an advance (named constant, 300,
a seat-flagged GUESS: owner retunes on a phone, routed into the owner probe) because a double-tap lands on whatever now sits
under the thumb - for a READ card that is "Next", which would silently skip an unread card. (Quiz cards are naturally safe:
the control under the thumb after an advance is "Show answer".)

**Cold reveal (C2).** The `reveal` string is not in the DOM before activation (conditional render, not CSS-hidden), is never
inside any `aria-live` region, and the status region never contains it. Focus moves to the answer group (`tabIndex=-1`,
`role="group"`, `aria-labelledby` its `h5`) on reveal so a screen-reader user reads it next; focus moves to the new card's
heading (`tabIndex=-1`) on every advance, and never on mount (the `prevSignalRef` guard in `RoleDrillControls.js`).

**Sources under a card (C6/S2/S6).** Rendered by `StudyEvidenceCitation`, after reveal for quiz cards (cold), always for read
cards. Distinct hosts via `citationHost` (deduped by host, first URL kept), at most `MAX_INLINE_SOURCES = 3` inline, the rest
behind "Show all sources (N)" (`aria-expanded`). Every anchor's `href` is recomputed with `safeExternalHref` at render (a
persisted row is untrusted at the render boundary) and a failing one renders as inert text "source link unavailable"; a
`servesGroundingRedirect` host is never a link. Each source row is `TOUCH_TARGET_SX` + `BREAK_LONG_WORDS_SX`. A card with zero
citations carries the text chip "No source" (not colour alone), on a `ready` plan too.

### 3.3 Order, resume and the missed-card return - a PURE model (`lib/studyPlan/studyWalkthroughModel.js`)

No scheduling invented. "Spaced" in SC-C means: persisted grades, and cards you missed or skipped return inside the plan.
Time-based spacing (`dueAt`) is SC-D's `studyPlanSchedule`; the schema's `grade`/`dueAt` slots are left untouched for it.

```
GRADE = { AGAIN: "again", GOT_IT: "got-it" }          // the shared writer/reader vocabulary; SC-D reads it
flattenPlan(plan)  -> cards[] in module->topic->item order:
                      { id, item, moduleId, topicId, moduleTitle, topicTitle, indexInTopic, topicSize, hasReveal }
isDone(card, entry)-> hasReveal ? entry?.grade === GRADE.GOT_IT : typeof entry?.revealedAt === "string"
nextCard(cards, seen, afterId, { reviewAll, sessionDone })
                   -> { id: string|null, wrapped: boolean, complete: boolean }
summarize(cards, seen) -> { total, done, missed, perTopic: { [topicId]: { done, total } } }
planSignature(cards)   -> the ordered ids joined (the remount key; stable across identical reloads)
```

`nextCard`: pending = cards not done (under `reviewAll`, "done" means `sessionDone.has(id)` instead, so a review pass
re-asks everything without needing a persisted reset). No pending -> `{ id: null, complete: true }`. Else the first pending
card AFTER `afterId` in plan order; if none after, the first pending card overall with `wrapped = true` (when `afterId` was
set). Resume on mount = `nextCard(cards, progress.seen, progress.cursor.itemId)`; a cursor that matches no card (rebuilt
plan, null cursor) is treated as "before the start". Counts come from `summarize` over the PLAN's cards (F7), never from the
keys of `seen`.

**Oracle table the TDD seat encodes (each row can fail; I authored these, so they are correlated with the rule - the plan
seat should add one property test over generated plans/seen/cursors: the result is `null` or a PENDING id, never a done
one, and the function terminates):**

| # | Situation | Expected |
|---|---|---|
| 1 | cursor null, nothing seen | first card |
| 2 | cursor mid-plan, later cards pending | next pending after the cursor, `wrapped: false` |
| 3 | cursor at last card, an earlier card graded `again` | that earlier card, `wrapped: true` |
| 4 | cursor card itself graded `again`, nothing after, no other pending | the same card, `wrapped: true` |
| 5 | cursor id not in the plan (rebuilt) | first pending card, `wrapped: false` |
| 6 | every card done | `{ id: null, complete: true }` |
| 7 | quiz card with `revealedAt` but no `grade` | pending (a reveal without a grade is not done) |
| 8 | read card with `revealedAt` only | done |
| 9 | `seen` holds keys of cards no longer in the plan | ignored by `summarize`; `done` <= `total` always |
| 10 | `reviewAll` with some persisted `got-it` | everything pending until `sessionDone` fills; persisted entries are overwritten as graded |

**Completion action, honestly limited (OD-5):** "Review all again" is a session-local mode (one boolean + a `Set`). It is lost
on reload (everything reads done again) because the data layer has no reset. A persisted "start over" needs a new RPC or N
single-card writes; not invented here.

### 3.4 Progress write contract (how the store is used)

Per card advance: `recordProgress(applicationId, { moduleId, topicId, itemId, revealedAt, grade? }, writer)` where `writer`
is bound by `lib/studyPlan/studyPlanBrowser.js` to `writeStudyPlanProgress(supabase, { applicationId, cursor, seenDelta })`
and `revealedAt` is the ISO time of the reveal click (kept in the walkthrough's local state; "Next" uses the click time).
No `dueAt` in SC-C. `userId` is not passed to the writer (identity is `auth.uid()` inside the RPC).
The reader is `() => readStudyPlan(supabase, { applicationId, userId })` with `userId` resolved ONCE per binding
(`auth.getUser()` memoised), not per call: `getUser()` makes a network request, so resolving it per progress write would add a
round trip to every card (`supabase-auth-probes`). Why a new lib file and not "the same way sibling clients do": siblings
reach Supabase through `lib/copilot/*Client.js` wrappers (`postings.js` `fetchPracticePostings`, `applicationDocsClient.js`
`loadApplicationDocs`), not from `app/copilot/*` components (no `createClient(` appears under `app/copilot` non-test files;
Grep, `head_limit: 0`); arch r2 section 8's "no new mechanism" is satisfied by following that wrapper convention.

### 3.5 Plan outline (the "how much of the plan at once" answer)

Default: ONE card at a time; the whole plan is behind one disclosure, "Plan outline" (`aria-expanded`, `aria-controls`, a
local `useState`, NOT `CollapsibleAid` whose open state is a shared persisted choice - the `RegenerateControl` rationale).
Open, it lists modules (`h4`) and topics (`h5`) with `done/total` per topic, an "Unsourced" text chip per topic in
`unsourcedTopicIds`, and each topic is a >= 44px button that jumps to its first pending card (jumping writes nothing; the next
grade records the cursor as usual). The low-frequency actions live at the bottom of the open outline, off the card screen:
"Rebuild plan" (4.3) and, only on an unsourced banner, the remedy button (3.6). At `md` and up the same single column is
used, capped to a readable measure; a side-by-side outline rail is a 1e/owner call, not designed here.

### 3.6 Provenance honesty (S6) - banners and chips, with reachable remedies

A persistent, non-dismissible one-sentence `Alert` above the card, chosen by the persisted facts
(`plan.engine`, `isPartialPlan(plan)`, `record.cachedResearch?.reason`). **Each remedy is checked reachable** (loop-traps-spec:
"does any criterion mandate naming a remedy without requiring it to work?"):

| Persisted facts | Banner text (pinned in section 7) | Remedy control | Reachable because |
|---|---|---|---|
| `ready`, `provenance.research === "complete"` | none; a quiet line "Based on research from <relative date>." (`formatRelative(record.researchedAt)`) | none | - |
| gemini, partial, `reason === "no-research"` | "This is a general plan. It is not based on research about this company." | **Research and rebuild** = `ensure` (no force) then rebuild | `ensureStudyDigest` researches a missing OR failed digest (route :244 short-circuits only a READY one) |
| gemini, partial, `reason === "unsourced"` | "Research for this company found no sources you can open, so this plan is unsourced." | **Refresh research** = `refreshStudyDigest` (`force:true`) then rebuild | `ensure` would be a no-op on an already-ready digest and loop to the same plan; only `force` re-searches |

### 4.2 Create-time ordering - two awaited phases, owned by a module, not a component

The orchestration is a plain async module with a module-scope, per-`applicationId` state store
(`lib/studyPlan/studyPlanBuild.js`), shaped like `studyPlanProgressStore` (`subscribe` / `getSnapshot` /
`getBuildState(applicationId)`), with its effects INJECTED so the ordering is node-testable. The React hook only subscribes
and calls `run`. Reasons: the digest call can run ~90-120 s (`maxDuration = 120`), phones background tabs and users switch
sub-views; a component-owned `await` chain dies with the component and a remount would offer a second "Create" that
double-bills and double-consumes the 12/10min limiter. A per-application in-flight guard (`Set`, checked synchronously, the
`inFlightIdsRef` precedent in `useApplicationDigests.js`) makes a second `run` a no-op.

```
run({ applicationId, engine, intent, knobs, hadGoodPlan })   // intent: create | rebuild | research-rebuild | refresh-rebuild | general
  1. guard: already running for this application -> return
  2. snapshot the last good record BEFORE any request            (4.3)
  3. PHASE 1 (skipped for engine === "embedded" and for intent === "general" / plain "rebuild"):
       digest = await ensureStudyDigest | refreshStudyDigest({ applicationId, engine })   // refresh only for intent refresh-rebuild
       throws -> fail(kind from F4 table);  digest.status !== "ready" -> fail("research failed", digest.error)
  4. PHASE 2 (only after phase 1 resolved):
       res = await POST /api/study-plan { applicationId, engine, knobs }     // knobs = stored record.knobs, never omitted (F3)
       non-2xx -> fail; res.status in {ready, partial} -> reload the record (loadStudyPlanRecord) and clear the entry
       res.status === "unavailable" -> do NOT overwrite a good on-screen plan (4.3)
```

Plain "Rebuild plan" (no research) skips phase 1 on purpose: the digest is unchanged, the arch's knob-only rebuild "spends
nothing" on research (D-2), and the route reads the stored digest itself. "Research and rebuild" and "Refresh research" run
phase 1 first. **Intents that bill:** only `refresh-rebuild` spends a fresh grounded search (the `ensure` path never sends
`force:true`; `ensureStudyDigest.wire.test.js` already pins `force:false`/`true`). A new thin wrapper
`lib/studyPlan/studyPlanBuildClient.js` (`requestStudyPlanBuild`, mirroring `requestStudyDigest`, mapping the 503 `disabled`
shape) is the only new network call surface; it needs its own wire test (stub `globalThis.fetch`, body carries `engine` and
the stored knobs).

### 4.3 Rebuild and the SC-gen footgun - preserve-last-good, two layers

**Layer 1 - server (REQUIRED, a prerequisite; PD-1).** In `generateStudyPlan`, when the computed status is `unavailable` and
the stored row for this application has status `ready` or `partial` and >= 1 module, do NOT call `writeStudyPlan`; return
`{ status: "unavailable", preserved: true, written: false, error }`. The route special-cases `preserved` to respond
`200 { status: "unavailable", partial: false, preserved: true, reason, error }` instead of the current 500 "Could not save the
study plan." for `!written`. With no prior good plan the current behaviour (write the honest `unavailable` row) is unchanged.
*Why server-side:* the response already arrives after the row is overwritten; a browser-side "restore" write would be a
second non-atomic round trip that a closed tab or a second device can interleave with. *Why no landed test breaks (to be
verified at plan):* the `unavailable` cases in `studyPlanGenerate.test.js` (:193-199, :215-220, :264-274) run against a fresh
in-memory store with no prior row, which the guard does not touch; this is an AMENDMENT to a specified behaviour in the file's
own header, so it needs a ledger ruling (standing rule 3) even if no test is edited.

**Layer 2 - client (defence in depth, always).** `useStudyPlanRecord` keeps a `lastGood` reference (the last record whose
`plan.modules.length > 0`). On any build failure, and on any reload that comes back empty or errored, the display record is
`lastGood`; the failure alert is shown ABOVE it (S8); `loadStudyPlanRecord` is NOT called on an `unavailable` response when a
good plan exists. The store's `loadStudyPlanRecord` replaces the in-memory record wholesale (a reload that fails settles to
`{ plan: null, error }`), so a naive "reload after every outcome" would blank a good plan on a transient read error - the
same class of defect one layer up, closed here by the display rule rather than by trusting the reload.

**Hard rule:** SC-C ships NO Rebuild / Research-and-rebuild / Refresh affordance on an existing plan until Layer 1 has landed.
Without it the honest copy "Your previous plan is unchanged" would be false after a reload. If Layer 1 slips, SC-C ships
create / retry-on-empty only (S0-S6) and the walkthrough, and the banners show their text without the remedy buttons.

**Rebuild confirmation (minimize-clicks).** "Rebuild plan" is armed (N156 pattern: same button, label -> "Confirm rebuild?",
timed window, announced in an always-mounted status span) ONLY when `summarize(...).done > 0`. With no progress it is a
single click. Armed announcement over-states: "Rebuilding writes new cards, so most of your progress on this plan will not
carry over. Activate again to confirm."

### 4.4 Egress disclosure (C6) - route x engine, over-stated

Always visible (never collapsed to shorten the scroll) in S3 and inside the open outline next to the rebuild/refresh controls.
Built by a pure `buildStudyPlanNotice({ engine })` (`lib/studyPlan/studyPlanNotices.js`, the `practiceNotices.js` shape):

| Engine (client choice) | What leaves | Notice states |
|---|---|---|
| gemini / external | phase 1: company name, job title, location, posting text -> Google (Gemini, live web search); phase 2: company, role, the research text with its source URLs, and any weak-topic / excluded-area words you typed -> Gemini | both legs, named separately; "Your resume and cover letter are not sent."; "The plan and your progress are saved to your account." |

## 9. The app-vs-chat claim and its removal ACs (S11)

**Class and claim.** Corpus (durable, structured, cross-device memory) plus Guaranteed (argued half). **What the user does
instead today:** pastes the posting into a fresh chat each time, gets a one-off wall of text, loses it when the tab closes,
has no record of which questions they missed, and cannot tell which claims were sourced. **Inherited vs earned (the app-vs-chat
check):** bare persistence is INHERITED (the app-vs-chat card's 2026-09-15 measurement: 65 of 79 routes import Supabase; I did
not recount it). The earned halves here are (a) resume
by content-derived key with a lost-update-safe per-card merge (`merge_study_plan_progress`, migration
`20261011000000_n157_study_plans.sql`), (b) the missed-card return derived from persisted grades, and (c) provenance the
chat cannot give: the `study_plans_ready_has_modules` CHECK, citations restricted to the research's own URLs
(`shapeCitations`), and an honest unsourced flag. The removal tests make each non-decorative:

| Removal AC | Remove | Observable change that must go RED |
|---|---|---|
| R-persist | the writer (`writeStudyPlanProgress`) | grade cards 1-3, unmount, reset the store (new device), remount from the fake DB: it resumes at card 4, not card 1 |
| R-missed | the grade (treat every revealed card as done) | a card marked `Missed it` does not reappear after the first pass |
| R-ground (already SC-gen's removal AC) | the digest evidence | the plan is flagged partial, the banner shows, and no card shows a source |

8b re-judges the SHIPPED diff against this claim; a "no" there is a finding appended to the backlog, never a refusal.
