## Design decision (orchestrator ruling settled here): **Design A — inline two-step confirm**

The ruling was: prefer the minimize-clicks-aligned guard; recommend **(A)** unless the wiped state is
*trivially* restorable, in which case **(B)** is viable. I read the wiped state and it is **not**
trivially restorable:

`clearAll` wipes **seven** things, three of which are **mutable refs that are live STT-pipeline
internals** (`recentRef`, `pendingRef`, `lastQNormRef`), plus the confirm gate. Design B (immediate
clear + Undo snackbar) would have to snapshot and restore all seven, and — because this is the
**live** session — a new final or question arriving from the running stream *during the undo window*
would race the restore (clobbered, or merged into a buffer that was supposed to be empty). That is a
genuine correctness hazard against a live pipeline, and it forces changes into `useLiveSession.js`.

Design A needs **none** of that: the guard lives entirely in the `SessionControls` UI layer, retains
**zero** wiped state, and leaves `clearAll` (`useLiveSession.js:712-720`) **byte-unchanged**.

**Cost comparison (stated so the 8b re-judge can weigh it):**

| | Added clicks, common case (NOT clearing) | Added clicks, actually clearing | Blast radius | Live-stream race |
|---|---|---|---|---|
| **A (chosen)** | **0** | +1 (arm → confirm) | `SessionControls` only; `useLiveSession` untouched | none |
| B (rejected) | 0 | 0 | `SessionControls` + `useLiveSession` snapshot/restore of 7 pieces incl. 3 live refs + a snackbar surface | yes — undo window races the live stream |

A is both safer and smaller, and honours minimize-clicks: zero added cost on the overwhelmingly
common case of *not* clearing; one extra deliberate activation only on the rare destructive path.

**The "no state of its own" comment is not violated.** That rule (SessionControls.js:30-38) forbids
moving `CopilotClient`'s *existing* `useState`/`useEffect` across the extraction boundary, because
that would change `CopilotClient`'s hook call order. A brand-new local arm-state hook *inside*
`SessionControls` does not touch `CopilotClient`'s hook order at all. The design seat (1c) owns the
exact mechanism (local `useState` + a timer is the obvious one); the AC below constrains **behaviour**,
not the mechanism, except where structure is the only way to make the wrong thing impossible.

**Composite-surface note (rule 6b):** this chunk ADDS a two-state affordance (idle "Clear" ↔ armed
"Confirm clear?") and a persistent polite live region to the `actions` fragment. It DISPLACES nothing
— Copy and Download are untouched, and the N144b tuck/disclosure structure is unchanged. Net addition
to the `actions` fragment is the arm state, its timer, and one visually-hidden live region.

## Failure direction (binding on every criterion below)

The dangerous error is **wiping on a single activation** (irrecoverable data loss). The safe error is
**requiring the confirm even when the user did not strictly need it**. Every criterion is written so
the **passing** direction is "a single activation does NOT wipe," and so a mutation that restores the
direct `onClick={clearAll}` (or otherwise lets one activation through) turns a test **red**.

## Acceptance criteria

Instrument for AC-1..AC-7 unless noted: the existing jsdom harness
(`SessionControls.compact.test.js` pattern) — real `SessionControls` mounted, clicks via `act`,
lookups **by accessible name**. "Both surfaces" = mounted twice: desktop inline (`compact:false`) and
compact tuck (`compact:true, live:true`, disclosure opened first, as the existing C-tests do).

### AC-1 — A single activation of Clear does NOT wipe the session. **[CORE]**
Mounting `SessionControls` with `clearAll: vi.fn()` and performing **one** activation of the Clear
control (enabled state: `finals` or `questions` non-empty) results in **`clearAll` called 0 times**.
Holds on **both surfaces**.
- **RED on HEAD:** yes. HEAD wires `onClick={clearAll}` (SessionControls.js:103), so one click calls
  it once; a test asserting 0 calls fails on HEAD. How I know: re-read of line 103.
- **Failure direction / mutation:** this is the safety criterion. A mutation that reverts the Clear
  `onClick` to `clearAll` directly (removing the arm step) must make this test red.

### AC-2 — A completed confirm wipes **exactly once** (Clear stays reachable). **[CORE — minimize-clicks guard]**
After a first activation arms the control, a **second** activation **within the arm window** calls
`clearAll` **exactly once**. Holds on both surfaces.
- **RED on HEAD:** yes. On HEAD two activations call `clearAll` **twice** (no arm gate); a test
  asserting "two activations → exactly one call" fails on HEAD (gets 2). How I know: line 103 fires
  the raw handler on every click.
- **Failure direction / mutation:** guards the *opposite* failure — a guard so strict that Clear
  becomes unreachable, or that double-fires. A mutation that drops the confirm branch (Clear never
  wipes) must make this test red; so must one that calls `clearAll` twice.

### AC-3 — The arm auto-reverts; an expired arm does NOT wipe and re-arms on the next activation. **[CORE]**
With fake timers: one activation arms the control; advancing timers **past the named arm-window
constant** (see note) with no second activation leaves `clearAll` **uncalled** and restores the idle
affordance (idle accessible name, live region cleared — AC-4/AC-6). A subsequent **single** activation
then **re-arms** (still `clearAll` 0 calls), it does not wipe.
- **RED on HEAD:** yes. No arm/timer exists on HEAD, and the one activation on HEAD already called
  `clearAll` — so "uncalled after the window" is false on HEAD. How I know: line 103 wipes on the
  first click; there is no timer to advance.
- **Note for the design/TDD seats:** the arm window must be a **named constant** (a few seconds;
  3–5s is the expected range, exact value is the design seat's call) that the test can advance past
  deterministically. If it is not referenceable from the test, the test cannot be written without a
  magic sleep — so the design must name/expose it.

### AC-4 — The armed state is announced to screen-reader users via a **persistent** polite live region. **[A11y]**
`SessionControls` renders a polite live region (`aria-live="polite"` or `role="status"`) that is
**present in the DOM in both the idle and the armed states** (not mounted fresh on arm). Its text
content is **empty while idle**, becomes **non-empty when armed** (e.g. announcing that another
activation will clear / that the arm will auto-cancel), and returns to **empty on auto-revert and
after the confirmed wipe**. The announcement must **not** rely on a Tooltip and must **not** rely
solely on a silently-changed visible label.
- **RED on HEAD:** yes. Re-read of SessionControls.js shows **no** `aria-live`, no `role="status"`,
  no live region anywhere; a test querying for it finds nothing.
- **Failure direction / mutation:** a mutation that (a) removes the live region, (b) newly-mounts it
  on arm instead of keeping it persistent (copilot-mobile: a remounted region holding text is never
  announced), or (c) leaves its armed text empty, must make this test red.

### AC-5 — The guard is keyboard-operable with no pointer-only path. **[A11y — partly regression guard]**
The Clear control is a native `<button>` whose **single `onClick` handler performs the arm/confirm
logic** (so platform keyboard activation — Enter/Space on a native button — exercises the same path
as a pointer). There is no `onMouseDown`/pointer-only branch that bypasses the arm.
- **RED on HEAD:** **mixed.** "Is a native button" is a **regression guard — passes on HEAD**
  (HEAD's Clear is already a MUI `Button` → native `<button>`); its teeth are on the mutant (a
  mutation to a non-button or to a pointer-only handler must fail it). The "onClick performs arm not
  wipe" half is the RED teeth and is already covered by AC-1. Disclosed as a guard, not padding.

### AC-6 — Clear's **idle** accessible name remains "Clear". **[constraint / regression guard]**
In the idle (un-armed) state the control's accessible name is exactly "Clear" (so it stays
identifiable, existing `byName("Clear")` lookups resolve, and the confirm affordance does not orphan
the control's name-in-label). The armed-state visible/accessible text may differ (e.g. "Confirm
clear?"); AC-4 carries the announcement.
- **RED on HEAD:** no — **regression guard**, passes on HEAD (idle name is "Clear" today). Teeth on
  the mutant: a mutation that renames the idle control, or that leaves it permanently showing the
  armed label, must fail it.

### AC-7 — The `disabled` rule is unchanged; a disabled Clear cannot arm. **[regression guard]**
When there is nothing to clear (`finals.length === 0 && questions.length === 0`) the Clear control
stays **disabled** and cannot be armed or activated. Holds on both surfaces.
- **RED on HEAD:** no — **regression guard**, passes on HEAD (disable rule already at line 104).
  Teeth on the mutant: a mutation that lets a disabled Clear arm, or that drops the disable
  predicate, must fail it.

### AC-8 — `useLiveSession.clearAll` is unchanged; zero wiped state is retained. **[scope / structural]**
The fix adds **no** snapshot/restore and **no** change to `useLiveSession.js`'s `clearAll`
(lines 712-720). The guard is confined to `SessionControls` (and, if the design seat chooses, a
small helper it imports). This makes Design B's live-stream race **structurally impossible** for this
chunk — there is no retained copy of the transcript/questions/refs to race.
- **RED on HEAD:** vacuously true today (nothing retains state); stated as a **scope fence** so the
  design seat does not drift toward B and the verifier does not file B's absence as a miss. Checkable
  as a non-regression: `clearAll`'s body is byte-identical to HEAD after the chunk.

## Explicitly OUT of scope

- **Touch-target geometry (≥44px).** jsdom has no layout (`getBoundingClientRect` is zeroes —
  SessionControls.compact.test.js:10-12). The idle "Clear" and the **armed** "Confirm clear?"
  affordance must **both** meet the ≥44px floor, and the armed label is **wider**, so this is an
  **owner / phone-pane** check (the browser-pane geometry pass, not a jsdom AC). Flagged for the
  owner pass precisely because the width changes between states. Instrument: the throwaway
  `app/auth/<name>/` harness + browser-pane device emulation described in `copilot-mobile`.
- **Practice mode.** `practice/PracticeControls.js` has its own controls; the backlog item and OD-B3
  name the **live** Clear only. No practice-mode criterion here.
- **Copy and Download.** Non-destructive; untouched. No guard added to them (minimize-clicks).
- **The N144b tuck/disclosure structure itself.** Unchanged; this chunk only adds the guard to the
  `actions` fragment that the tuck already places.
- **Changing what `clearAll` wipes** (the seven pieces). Out of scope — see AC-8.

## Blast radius — existing tests that pin the buggy single-tap behaviour (report, do NOT silently edit)

This is the `loop-traps-spec` "a faithful test pins the buggy rule and goes red" case. The TDD/plan
seats own updating these; flagging so no one silently weakens them:

- `SessionControls.compact.test.js:307-317` — "each action calls its own handler exactly once
  (tucked, all enabled)" clicks **"Clear" once** and asserts `clearAll` **called once**. Under
  Design A a single activation must call it **zero** times (AC-1), so this test **will go red**. It
  must be updated to a two-step (arm, then confirm) to assert the new contract — not deleted, not
  weakened to accept either. This red is **expected and correct**.
- Any lookup that does `byName("Clear")` **after** a first activation will not find the control if
  the armed label replaces the visible text (AC-6 keeps the **idle** name "Clear"; the armed affordance
  needs its own name/lookup). The TDD seat must look the confirm step up by its armed name, not by
  "Clear".
- `SessionControls.compact.ssr.test.js` and `SessionControls.extraction.test.js` — re-check after the
  change: the SSR smoke test must still render (the persistent live region must be SSR-safe, empty on
  the server); the extraction source-scan asserts the `clearAll={clearAll}` wiring from CopilotClient
  (SessionControls.extraction.test.js:144) which is unchanged by Design A.

## What I could NOT verify (and the instrument for the next seat)

- **The exact arm-window duration** is a design-seat (1c) decision; I require only that it be a named,
  test-referenceable constant (AC-3 note). Instrument: fake timers advancing past that constant.
- **Geometry (≥44px) for the armed affordance** — cannot be measured in jsdom; owner/phone-pane.
  Instrument: browser-pane device emulation per `copilot-mobile`.
- **Whether any non-grep path (e.g. a global keyboard handler) fires `clearAll`** — grep over
  `hello-world/` for `clearAll` found only the CopilotClient→SessionControls prop wiring and the
  `useLiveSession` definition; blind spot is a handler that reaches the setter functions by another
  name. Low risk, but the plan seat should confirm the Clear button is the sole trigger before
  declaring the surface fully guarded.
- **That a local `useState` in `SessionControls` is acceptable** given the "no state of its own"
  comment — I reasoned it is (it does not alter CopilotClient's hook order), but the 1c/1b seats
  should confirm and record the deviation in the component doc rather than leaving the comment reading
  as an absolute.
