# N105 - EXPERIENCE design (seat 1c, round r1)

Backlog N105: new HIGHEST tailoring level - a hypothetical ideal resume plus a truthful application-ready resume.
Binds to `docs/loop/N105.ac.r2.md` (FINAL, 17 ACs, OD-1..OD-4) and `docs/loop/N105.design.r2.md` (FINAL structure, D-1..D-16). Experience only: no source edited, no git writes, no structure re-opened. Pairs with 1e (craft); where this file names a token or a component it names what to REUSE, not how it should look.

Where a UX need implies an additive response field or a lifecycle rule on the settled structure, it is listed in section 12 as an INPUT to the plan. None of them changes a settled D-line.

**Decisions at a glance**
1. Level: the existing Slider gets a sixth stop "Ideal" (label renamed "Tailoring level"); a caption states what it builds, and if the engine cannot run it, says so calmly with a one-click "Switch to Gemini". Persists under its own key (section 2).
2. Refusal: info-toned pre-click caption plus a server 422 carrying the same sentence; empty resume text refuses BEFORE generation; any failed run produces zero artifacts (section 3).
3. Two outputs: two tabs, "Application-ready" first and default, "HYPOTHETICAL" last; the hypothetical is read-only with a non-dismissible banner, a read-only forced file name and its own download button (section 4).
4. Flags: one shared, draft-agnostic review panel (N103/N104 reuse it); gate-flagged lines carry the unverified marker INSIDE the file; unresolved requirements and "Left out" are their own groups (section 5).
5. Safety hazards found and closed in the UX: Revise/Focus/Framing would bypass the gate (4.6); an unscoped run wipes the cover letter (U12); silent auto-download skips the review (2.3); a `visibleScopes` default of `SCOPES` shows "Hypothetical (none)" everywhere (4.2); a raw text compare falsely reports `other-version` (5.8).
6. Owner calls: OC-1 cover letter in the same action; OC-2 inline marker vs panel-only; OC-3 filename marker position (section 11).

## 1. The experience in one view

1. **Pick the level** (Materials tab, "Show options"): the existing slider now has a sixth stop, "Ideal". Selecting it is the whole configuration. A short caption says what it builds and, if the active engine cannot run it, says so calmly and offers a one-click switch.
2. **Press the existing Generate/Tailor control.** One action produces BOTH documents. It is expected to take longer than other levels (more AI passes); the control says so without inventing a duration.
3. **The preview opens on the Application-ready tab** (the one to send), never on the hypothetical. A review band sits above the document: what to confirm before sending, requirements wording cannot cover, and what the app left out because it could not support it.
4. **A second tab, "HYPOTHETICAL",** holds the best-case document. Every surface that shows it says HYPOTHETICAL: the tab, a non-dismissible banner, the file name, the download button, copy feedback, the chat label.
5. **Downloads:** the existing "Download .docx" delivers the Application-ready file. The hypothetical has its own read-only file name and its own download button inside its banner. Neither is ever downloaded automatically.

### Click cost (levels 1-5 baseline vs Ideal), URL flow

| Task | Baseline (1-5) | Ideal | Delta |
|------|---------------|-------|-------|
| Get the file to send | Generate (1) + Download .docx (1) = 2 | Generate (1) + Download .docx (1) = 2 | 0 |
| Get BOTH documents | n/a | same Generate; the second tab is already loaded | 0 extra to obtain; 2 extra only if the user wants the hypothetical FILE (tab + download) |
| Change level (any level) | Show options (1, only if collapsed) + drag/arrow (1) | same | 0 |
| Fix "needs the AI engine" | header engine `Select`: open (1) + choose (1) = 2 | "Switch to Gemini" in the caption = 1 | -1 |
| Resolve a marked (unverified) line | n/a | Tier A: Edit (1) + delete the marker or line by typing; Tier B (section 5.4): 1 click per line | see 5.4 |

Surface replaced: pasting the posting and the resume into a chat, reading one blob, deciding line by line what is true, rebuilding a one-page Word file (section 9).

## 2. Level selection (brief item 2, OD-1, AC-1, AC-15)

### 2.1 Decision - extend the existing Slider to six stops; the sixth is "Ideal"

Alternatives considered:
- **A. Six-stop Slider (chosen).** Honors OD-1 literally ("one selector, N105 is its highest entry"). Keyboard End reaches the top. Smallest new surface.
- **B. Leave the Slider at 1-5 and add an "Ideal" switch beside it.** Rejected: two controls, and the slider's meaning while the switch is on is undefined; violates "one selector".
- **C. Replace the Slider with a segmented 6-option control.** Better value names than unlabeled ticks 2 and 4, but replaces a control users already know and changes what is persisted. Possible later; out of scope.
- **D. A `Select`.** Rejected: `[[mui-a11y-traps]]` items 9-10 (non-native Select fails label-in-name; native breaks label shrink and stale values).

### 2.2 Specification (C-ids refer to the copy deck in section 13)

- **L1 Single source.** The stops, marks, aria text, captions and refusal copy come from ONE table in `lib/tailor/tailorLevel.js` (D-2 already gives that module "a label/ordering table"). `ApplyingControls` renders from it. The numeric slider value 6 is UI-only: it is mapped by `levelToRequestFields` to `{ tailorMode: "ideal" }` and is NEVER sent as `aggressiveness` (D-1, U3: six send sites).
- **L2 Label.** The visible label changes from "Aggressiveness" (`ApplyingControls.js` :186-190) to **"Tailoring level"**: the scale now ends in a mode, not an intensity, and "more aggressive than Strong" is the wrong reading of Ideal (the application-ready file is the MORE truthful of the two outputs). No landed test pins the old visible word: a case-insensitive Grep of every `hello-world/**/*.js` for "aggressiveness" finds the visible word only at `ApplyingControls.js` :187-188 (the label); test hits are prop/field fixtures, never label text. One other user-visible mention remains and is not a pin: the library help text "only used at high aggressiveness" (`app/components/library/schemas.js` :32) - reword it to "high tailoring levels" or leave it, since the 1-5 range keeps its Light/Balanced/Strong names.
- **L3 Name and value text (fixes the measured hole U4 on the way past).** The label gets an `id`; the Slider is named with `aria-labelledby` pointing at it (or `slotProps.input`); `getAriaValueText` returns: 1 "Light", 2 "Level 2 of 5", 3 "Balanced", 4 "Level 4 of 5", 5 "Strong", 6 "Ideal, builds two resumes". Without this a six-value slider whose top value is a mode would announce a bare "6".
- **L4 Marks.** Light, Balanced, Strong, **Ideal**. The sixth mark is visually a different KIND of stop (1e decides how) - not a continuation of the ramp - and uses the accent family, not warning or danger: choosing Ideal is not a hazard. Whether four mark labels fit at phone width is a MEASUREMENT for 1e/8d at 375/768/900 px (no pixel estimates are made here; `[[measurement-instruments]]`).
- **L5 One caption region under the slider**, programmatically associated with the slider (`aria-describedby` resolving to a real, non-empty node - the `[[mui-a11y-traps]]` item 8 assertion). Not a live region. Contents by state:

| State | Caption | Extras |
|-------|---------|--------|
| level 1-5 | C4 (helper): "Ideal, the top level, builds two resumes: a best-case one to study and a truthful one to send." It deliberately avoids the word "hypothetical" so no sweep for that word outside the Ideal path can trip on it. | none |
| Ideal + engine can run it | C5: what it builds, resume-only, expected to take longer | none |
| Ideal + engine cannot run it (embedded; external unless the plan flips D-3b) | C6, `role="status"`, info tone (not danger, no `role="alert"`): "Ideal needs the Gemini AI engine. You are on {engine label}, which cannot build it." | one plain **Button "Switch to Gemini"** |

- **L6 "Switch to Gemini" is one click, no confirm.** It calls the module-level `setEngine("gemini")`. The button unmounts when the state flips, so **focus is moved to the slider thumb** and a `role="status"` line (C7) announces "Engine switched to Gemini (AI)". A control that vanishes under focus drops the keyboard user to `<body>` (precedent: `DriveOverwriteDialog` focus-restore). No `Tooltip` on this button (`[[mui-a11y-traps]]` 1, 2); its reason is the visible caption.
- **L7 Visible when the Accordion is collapsed.** The level lives in a panel that defaults to closed (U1), so a saved Ideal would be invisible. When (and only when) Ideal is selected, the Accordion summary reads "Show options - Ideal level" / "Hide options - Ideal level". Levels 1-5 keep today's summary text unchanged.
- **L8 Visible at the point of action, only when Ideal.** One shared note component renders a single line (C11) beside the existing generate controls: `PostingUrlTab.js` :39-42, the manual-tailor tab's Generate row `JobDescriptionTab.js` :345-353 (which already runs a multi-posting queue, "Tailoring {completed} of {total}"), and `BatchTailorDialog.js` :43-47 where the cost multiplies (C12). At levels 1-5 nothing is rendered (byte-identical, AC-17). The note is plain text, not a `Tooltip`.
- **L9 Persistence.** Ideal persists across reloads like levels 1-5 (the standing "remember the last choice" rule in `[[minimize-clicks]]`), under its OWN key (`tailorMode`), restored independently of the `aggressiveness` restore at `page.js` :314-317. Storing 6 in `aggressiveness` is a trap: the guard (`<= 5`) would silently drop it on every reload. The alternative (session-only) was considered and rejected: its failure (a normal single-file run when the user wanted Ideal) is also cheap and visible, but the standing rule favors remembering, and L7/L8 remove the invisibility that made persistence risky. The batch cost risk is handled by C12 and by 2.3.
- **L10 No wizard, no confirmation.** Selecting the level is the entire configuration; the existing Generate click yields both documents (AC-15). No "are you sure", no second "generate the application-ready" action.

### 2.3 Other entry points under Ideal

- **Single-job tailor from a chip / feed posting** (`handleTailorJob`, `handleTailorFeedPosting`): under Ideal the result is delivered by OPENING THE PREVIEW, not by silently downloading (U11). Reason: the second file, the review band and the unresolved-requirements list exist only in the modal; AC-13 says delivery must surface them so the user is not left with a false impression of fit. A silent download would deliver a file with none of that.
- **Batch** (`startBatchTailor`): under Ideal the dialog hides "Tailor & download" and keeps "Tailor only (no download)", with a visible sentence saying why (C12) - a reason as visible text, not an `aria-label` on a missing control. Results are reviewed per job from the existing chips. Concurrency 3 times a multi-call chain is a rate-limit risk the plan must evaluate (research A9: up to 9-12 requests per click at default retries).
- **Every Ideal run is `scope = resume`** (never `both`), so the existing cover letter and hiring email on that job are untouched (U12).

### 2.4 Keyboard path (selector)

Tab reaches the Accordion summary (existing), then the slider thumb (native range semantics: arrows step, Home/End jump, End = Ideal), then the caption's "Switch to Gemini" button when present. No pointer-only step exists: dragging is optional.

## 3. Refusals and failures (brief items 4 and 5)

### 3.1 Design stance

"Needs the AI engine" is a requirement, not a fault. It is stated before the user spends a run, in an info tone, with a one-click remedy, and the same sentence is what the server returns if the run is attempted anyway.

### 3.2 Layers (cheapest first; the server is the guarantee)

1. **Pre-click (selector caption, 2.2 L5/L6).** Prevents most refusals and costs no request.
2. **Run entry fast-fail (optional, plan decides where it fits the 7-line `page.js` budget, U6).** A single check before any request shows the same message once. Most valuable at `handleTailorAllVisible` (`page.js` :2096-2117, which already reports through `setJobSearchError`) so a batch of N never becomes N refusals.
3. **Server refusal (authoritative, D-3).** HTTP **422** with `{ error: <the sentence>, refusal: { level: "ideal", code: "engine-unsupported", engine, requires: "gemini" } }` and none of the output keys. Why 422 + `error` and not 200 + a `refusal` field: every client throws `payload.error` on `!ok` (U16), so an entry point written before this feature, or one that forgets to check `refusal`, fails CLOSED with the right sentence; a 200 would fall into `payload.result?.trim() || "No output returned from Gemini."` (`page.js` :2214) and store a fake result. The `refusal` object lets a surface that wants to restyle it as info do so (for example `PostingUrlTab.js` :58 `severity`), but nothing depends on that.
4. **One sentence source.** `idealRefusalMessage(code, ctx)` in `tailorLevel.js` produces C6, C8 and C9; the caption, the server body and any fast-fail call it. No copy drift between three surfaces.

### 3.3 Tone rules for the refusal (checkable)

- Leads with the requirement ("The Ideal level needs ..."), never "Error", "Failed", "Sorry", "Unable".
- Names the user's CURRENT engine by its `ENGINE_OPTIONS` label ("Embedded (no AI)", "Resume Tailor API").
- States a remedy that is reachable: the caption button (1 click) or, in the red channels, "Switch the engine in the top bar" (`AppHeader.js` :139 is on every page) "or pick another level".
- Produces no artifact: no Hypothetical tab, no review band, no `done` result, no download, nothing persisted (AC-2).
- In the existing red channels the sentence renders in whatever severity that channel has; that is acceptable because the sentence itself reads as a requirement and the selector caption already told the user.

### 3.4 Empty or unreadable resume text (structure plan input D-7b)

- **Decision: refuse BEFORE generation.** The route reads the resume text at `route.js` ~:339 (`readResumeText`); if the trimmed text is empty on an Ideal request it returns 422 `refusal.code = "empty-resume"` with C9, zero artifact, and spends no AI request. (The client MAY pre-empt using an empty `templateLines` array from `buildTemplateLinesForUpload`, `docx.js` :216; the server stays authoritative.)
- **Why not proceed to a drop-everything output:** it would cost a full multi-call chain to produce a skeleton-only file the user cannot tell from a working run, and the cause (the file) would be invisible. The structure confirms either choice is safe (the gate fails closed, D-7b); refusing is the honest one.
- **C9 copy** names the file, says why Ideal needs the text ("to keep the application-ready version truthful"), and gives the reachable remedy (re-upload a `.docx`/`.txt`/`.md` with selectable text, not a scan or image, on the Materials tab - where the resume upload control lives, `ApplyingControls.js` :70-89).
- **Thin corpus (text exists, nothing can be matched).** A SUCCESS state, not a refusal: when the gate keeps no accomplishment spans (`counts.keptAccomplishments === 0`, a plan input, section 12 UXR-1), the Application-ready band shows C21 ("None of the hypothetical's claims could be matched to your resume, so this version has only your employers, dates and education. Add detail to your resume and run again."). The file is still delivered and still honest.

### 3.5 Run failure is atomic

- A run that cannot finish (a stage fails, a timeout, a rate limit, a truncated structured response - research R-5 treats truncation as a hard failure) produces **zero artifacts**: never the hypothetical alone, never an application-ready without its review. The hypothetical alone is the dangerous half; the pair is all-or-nothing.
- Copy (C10): "The Ideal level could not finish, so nothing was produced. Your resume and settings are unchanged." + a cause clause only when the cause is known ("The AI service took too long." / "The AI service is rate-limiting requests right now.") + "Try again, or pick another level." Retry is the existing Generate control; no new button.
- **In flight:** the existing button already switches to "Generating..." (`PostingUrlTab.js` :41). Under Ideal, C11 adds "Building your best-case and application-ready resumes. Expect this to take longer than other levels." **No duration is stated**: chain latency is unmeasured (U18). If the plan measures it, a number may be added then.
- **A review that did not run** is a different state from a failed run; see 5.8.

## 4. The two-output presentation (brief item 1; AC-3(d), AC-7, AC-13, AC-15)

### 4.1 Decision - two tabs in the existing tab bar

Alternatives considered:
- **Two tabs (chosen).** Reuses the one navigation the user already knows; the structure already models the hypothetical as a scope with its own bytes (D-9, D-9b).
- **Side-by-side panes.** Rejected: the dialog is `maxWidth="md"` and full-screen on phones (`DocumentPreviewDialog.js` :572); two readable pages do not fit, and it doubles an already dense toolbar.
- **One scroll with both documents.** Rejected: merges what AC-7 says must never be merged, and makes "which one am I downloading" ambiguous.
- **A chooser before the modal, or a separate modal.** Rejected: an extra click and a second surface.
- **A confirmation ("I understand this is not for submission") before the hypothetical can be downloaded or copied.** Considered and rejected under `[[minimize-clicks]]`: downloading is not destructive or irreversible; the filename marker (D-8), the banner and the tab already state it. The safety device is structural (the name), not a click.

### 4.2 The tab bar

Tab set (supplied by the mount as `visibleScopes`, D-10; a pure helper in `lib/tailor/` computes it so it is testable without React):

| Situation | Tabs shown |
|-----------|-----------|
| No Ideal result (every level-1-5 run, every reload) | `["resume","cover","email"]` exactly as today, including "(none)" tabs - byte-identical (AC-17) |
| Ideal result, application-ready available | `resume`, then `cover` and `email` ONLY IF available, then `hypothetical` last. Unavailable scopes are omitted - an Ideal run does not generate a cover letter or email, so "Cover letter (none)" / "Hiring email (none)" would be dead tabs |
| Ideal result, application-ready NOT available | no hypothetical tab (the pair is atomic; the hypothetical never appears without its truthful counterpart) |

- **Order:** the document to act on first, the hypothetical always last.
- **Default tab:** the Application-ready one (`finishByOpeningPreview` already selects "resume" when no cover letter exists, hook :894-903; Ideal runs are resume-only).
- **Tab text** is supplied per tab by the mount (`scopes[scope].tabLabel`, falling back to the existing label expression so ordinary runs are unchanged): the resume tab reads **"Application-ready"**, the new tab reads **"HYPOTHETICAL"** (the literal capitals in the string, not CSS `text-transform`, so the DOM text, the accessible name and the filename token agree). `SCOPE_LABEL.hypothetical = "Hypothetical resume"` is the SENTENCE label (copy feedback, Ask AI, copy button name - U9).
- **The "Application-ready" tab text is a claim**, so it is derived: if the shown resume text is a different saved version (not the reviewed text and not hand-edited) the tab reverts to "Resume" (state `other-version`, 5.8). A hand-edited application-ready keeps its tab text (the user took responsibility; the band says so).

## 5. Flagged-span rendering and the shared review surface (brief item 3; AC-4, AC-5, AC-13)

### 5.1 Two sources, one panel

The user sees two kinds of "check this" and must not have to learn two surfaces:
1. **Gate flags** (AC-4): application-ready spans the gate could not fully support, emitted with an explicit `unverified — confirm before use` flag (D-6b). Application-ready only.
2. **Reviewer flags** (AC-5): `flags[]` from the shared `reviewDocuments` for either draft, plus `unresolvedQualifications[]`.

Both render in ONE `ReviewFlagsPanel`, grouped by what the user must do. The panel is draft-agnostic (`draftKind` is a parameter) because N103 (on-demand adversarial review of the current document) and N104 (weakness summary, "resolvable by wording vs genuinely unqualified") consume the same primitive. N105-specific parts - the HYPOTHETICAL banner, the hypothetical download, "Left out" - are separate components so N103/N104 inherit none of them.

### 5.2 Category presentation table (keyed by draft AND category - AC-5 splits the authority reference per draft, so the same category means different things)

Tiers: **Confirm** = a truth risk to the user before sending (application-ready only). **Improve** = quality. **Note** = information about the hypothetical (nothing is "sent" from it).

| Category (reviewer) | Application-ready: label / tier | HYPOTHETICAL: label / tier |
|---|---|---|
| (gate) `unverified` | "Unverified" / Confirm | n/a |
| `unsupported-authority` | "Role or seniority not in your resume" / Confirm | "Seniority does not add up" / Note |
| `unverifiable-metric` | "Figure cannot be checked" / Confirm | "Unsourced figure" / Note |
| `consistency` | "Does not line up" / Confirm | "Does not line up" / Note |
| `employer-plausibility` | "Unlikely for this employer" / Confirm | "Unlikely for this employer" / Note |
| `vague-unsupported` | "Vague claim" / Improve | "Vague claim" / Note |
| `repetition` | "Repeats another line" / Improve | "Repeats another line" / Note |
| `missing-keyword` | "Posting keyword missing" / Improve | "Posting keyword missing" / Note |

This table is pure data in `lib/review/flagPresentation.js`; N103/N104 add their own rows to it, not a second table. The reviewer's `message` is the specific detail under the label; the label is the stable vocabulary.

### 5.3 Row anatomy and ordering

One row per SPAN (several flags on the same span merge into one row with several labels - the contract allows it and listing one line three times is noise):
- the offending line quoted (clamped to ~2 lines, `BREAK_LONG_WORDS_SX`);
- one label per flag (text, never colour alone), then the reviewer `message`;
- **evidence**, when `evidenceRef` is present: a quoted snippet prefixed by its origin - "From the posting: ...", "In your resume: ...", or for a cross-draft consistency flag "In the other draft (HYPOTHETICAL / Application-ready): ..." (5.5).
Order: tier (Confirm, then Improve), then document order. Show at most 8 rows per group before "Show all (n)".

### 5.4 The unverified marker travels INSIDE the application-ready file (decision; owner call OC-2)

Gate-flagged lines are emitted with the literal suffix **` [unverified — confirm before use]`** (AC-4's own string, with its em dash U+2014, in brackets; one exported constant, appended by `recomposeFromSpans` when it emits a flagged span, D-6b "emitted but carrying their flag"; every other string in this file uses a plain hyphen for typing convenience, this one must be copied exactly). Why inside the text and not only in a side panel:
1. **Persistence.** The application-ready resume is persisted like any resume (U11, `page.js` :2004) and the review panel is session-only (D-14): after a reload a panel-only flag would leave a flagged claim in the saved file as a plain bullet - the exact AC-4 failure.
2. **Paths that never open the preview**: `handleTailorJob` downloads immediately (U11), batch "Tailor & download", and later chip downloads.
3. **Every egress** (copy text, Drive, combine, download) carries the text.
This is unrelated to OD-4, which removes only the HYPOTHETICAL content label.

Consequences designed in:
- **Live count from the text itself.** The band's "N to confirm" is the number of lines in the CURRENT resume text containing the marker (a pure `countMarkedLines(text)`), not a snapshot. Deleting the marker ("I confirm this is true") or deleting the line ("remove it") lowers it in place with no spanId mapping and no stale state for this class. At zero the row group reads "All marked lines resolved."
- **Preview highlight.** Marked lines get a render-only highlight in the preview using the `markInsertedFacts` pattern (U13) with the warning token family, never the yellow already used for version-diff and inserted facts, so the three are not conflated; combine/download never see it.
- **Resolution, Tier A (slice 1):** the existing Edit mode: delete the bracketed text or the line (autosave exists). **Tier B (recommended if the plan can afford it):** per-row "Confirm" (strip the marker) and "Remove" (delete the line) - one click each, no confirm dialog, same reasoning as `InsertedFactsStrip` (removal only reduces what reaches an employer; "Confirm" only removes a warning the user has just read). Tier B needs the plan to verify a text-only `saveDocumentPreview` payload (hook :442-447 takes `html` optionally) rebuilds the download correctly; that is unverified here (section 13).

### 5.5 Cross-draft consistency (`evidenceRef.origin === "draft"`)

The flag sits on the draft that holds the offending span; the evidence span lives in the OTHER draft. The row shows BOTH quotes inline, labelled by draft, so the user never has to switch tabs to understand it (the band cannot switch tabs: tab state is dialog-local, and adding a request-tab prop would spend dialog lines for little gain). Example reading: "Does not line up - This line: 'Senior Engineer, Acme'. In the other draft (HYPOTHETICAL): 'Staff Engineer, Acme'." A flag raised on the hypothetical about the application-ready is a Note; raised on the application-ready about the hypothetical is Confirm.

### 5.6 Unresolved qualifications (AC-13)

Application-ready band, own group "Requirements your resume cannot meet by rewording", one row per `unresolvedQualifications[].text` (a posting requirement span), capped at 8 with "Show all". One sentence under the heading: "Rewording cannot supply these - they need real experience or a different story." Counted in the band summary line. On the HYPOTHETICAL tab a single cross-reference line gives the count ("N requirements here go beyond your record - listed on the Application-ready tab"); the list is not duplicated.

### 5.7 "Left out" (what the app refused to say for the user)

Collapsed disclosure "Left out because your resume does not support them (n)" listing each dropped hypothetical claim with its reason ("No matching fact in your resume" / "Belongs to a different employer"). This is the visible half of the fail-closed gate: without it a thinner application-ready file looks like a defect. It is a UX-added advantage with no AC of its own; a ledger line (UX-25) makes it removal-testable. Needs `review.dropped` (count at minimum) in the response (UXR-1).

### 5.8 States of the Application-ready band

| State | Trigger | What shows |
|-------|---------|------------|
| fresh, items to confirm or gaps | normal | header chip + summary line (counts) + groups, expanded on desktop |
| fresh, nothing flagged | zero flags, zero gaps | "No issues flagged. The automated review is not a guarantee - read it once before you send." (never "verified", never "safe to send": over-claiming is the lie) |
| `no-review` | `ideal.review` absent/null | "The review did not run for this result. Treat every line as unchecked." (warning tone; the file is still delivered) |
| `edited` | shown text differs from the reviewed text and the scope is hand-edited | "You have edited this resume since the review ran. The notes below describe the version that was generated." (`role="status"`, announced once on the transition) |
| `other-version` | text differs and the scope is NOT hand-edited (a saved version was selected) | tab text reverts to "Resume"; band says "A different saved version is showing. The notes below do not apply to it." |
| `thin` | no kept accomplishments | C21 above the groups |
| mobile | `useIsMobile()` | summary line only, collapsed; the Confirm count is in the summary so it is visible without expanding; tap target >= `MOBILE_TAP_MIN` |

State is computed by a pure `idealBandState({ ideal, currentText, handEdited })` comparing the shown text with `ideal.applicationReady.result` (the signals `scopes.resume.text` and `scopes.resume.html` already reach the mount). **The comparison must normalize both sides the way the client stores the text** (`trim()`, CRLF to LF): the entry is stored from `payload.result?.trim()` (`page.js` :1952, :2214), so a raw `===` against the untrimmed reviewed text would report `other-version` on a FRESH result and wrongly demote the tab to "Resume" and hide the review. Density: the expanded band has a capped height with its own scroll (the repo's `vh`/`dvh` pair, `[[measurement-instruments]]`: read the raw `<style>` text, not CSSOM) so it cannot push the document off a short screen.

### 5.9 Residual risk (stated, not hidden)

Reviewer-only flags (AC-5) on the application-ready are advisory and session-only; only gate flags (AC-4) are persisted as text. A reviewer-only "unsupported authority" or "unverifiable figure" therefore disappears on reload while the line stays. The gate already requires every authority/metric token to trace to one real span (AC-4.1), so these should be rare; escalating reviewer truth-risk flags into marked lines would close it but feeds the reviewer back into recompose (a structure change) - raised in section 12 (UXR-8), not decided here.

## 7. Keyboard, focus and accessibility

- **Tab order follows the DOM:** tab list (roving, arrows, existing MUI `Tabs`) -> toolbar (existing) -> band disclosure buttons -> (hypothetical: banner download button) -> document -> action bar. Escape closes the dialog (MUI default).
- **Disclosures** are real buttons with `aria-expanded` and `aria-controls` resolving to a real node; decorative caret glyphs are `aria-hidden` (`[[mui-a11y-traps]]` 7).
- **No `Tooltip` on any new control** (items 1, 2); reasons are visible text (item 8). **No `Select`** anywhere in this feature (items 9, 10). The existing `EngineSelect`/`VersionControl` Select+Tooltip defects are pre-existing and out of scope; the in-caption "Switch to Gemini" button also avoids them for this one task.
- **Live regions:** none streams. The caption's engine-needed variant and the stale transition are `role="status"` once each; nothing re-announces on typing (`[[mui-a11y-traps]]` 4). If an MUI `Alert` is used for the info caption it must set `role="status"` explicitly (item 5: an Alert defaults to `role="alert"`).
- **Label-in-name (WCAG 2.5.3):** visible text must be a substring of the accessible name for the new tab, the download button, "Switch to Gemini" and the disclosure buttons (assert with the name resolver in `[[mui-a11y-traps]]` item 3, not a naive `aria-label || textContent`).
- **Focus:** after "Switch to Gemini" focus moves to the slider (2.2 L6). Closing/opening the dialog uses MUI's existing focus trap and restore.
- **Colour is never the only signal:** every tier, tab and state has text; tokens come from `app/theme/tokens.js` (`--warning`, `--warning-soft`, `--danger`, `--accent-soft`), no raw hex, light and dark both first-class. Contrast of body copy on `--warning-soft` is a 1e computation, not asserted here. Any numeric `sx` width/margin in the new leaves follows `[[mui-sx-numeric-traps]]` (a bare number is usually a multiplier).
- **jsdom can assert** structure, names, roles, attributes, text, declared `getComputedStyle` values. **Only a real browser can assert** tab-bar fit at 375/768/900 px, band height behaviour, overlap and the focus ring; those are manual measurements for 1e/8d, reported INVALID until measured, never as zero.

## 9. App-vs-chat claim (`[[app-vs-chat]]`; AC-16)

**Class:** Guaranteed (earned, with the mechanism named below), with Corpus as the enabling input and the Word-on-your-template property as a second Guaranteed (byte fidelity).

**What the user does instead today, and what it costs:** paste the posting and the resume into a chat for each application; get one undifferentiated blob that mixes "what a perfect candidate would say" with "what is true of me"; audit every bullet by hand for invented numbers, titles or scope; copy the result into Word and rebuild the one-page layout; and carry the standing risk of submitting a line that was never true. Repeated across dozens of applications, the cost is the re-paste, the manual truth audit and the reformat on every one, plus the cost of the one time it goes wrong.

**What this UX gives that the chat does not (each removal-tested by an existing AC):**
1. The two-file split with a STRUCTURAL marker - a filename token that cannot be stripped by renaming and a banner that cannot be dismissed (AC-7 + AC-3). Remove it and the hypothetical is just another resume file.
2. A fail-closed grounding gate against the user's own stored resume, with a visible account of what it refused to say ("Left out", 5.7) and marked lines that survive reload (AC-4 + AC-10; UX-22, UX-25). A chat will not tell you what it declined to claim for you.
3. The output on the user's own template as a real `.docx` (AC-12a), saved and downloadable in one click.
**REMOVAL test mapping:** delete the HYPOTHETICAL marker surfaces -> UX-15/AC-3(d) red; delete the review band -> UX-21..26/AC-13 red; delete "Left out" -> UX-25 red; delete the gate -> AC-4 red; route output through a bespoke generator -> AC-12a red. If any of these can be removed with every test green, the feature has collapsed to chat-equivalent.
