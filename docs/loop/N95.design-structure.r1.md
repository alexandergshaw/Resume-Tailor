## 0. The one thing a reviewer must understand first — the bytes-first preview collides with optimistic-move

The felt "jump/lag" on a move has **two independent causes**, and the fix for each is different. Getting this wrong is the expensive mistake this seat exists to prevent.

1. **Latency** — nothing changes on screen until the async commit (up to three IO ops: `resolveCoverEngineBytes` storage fetch + `applyCoverDocxEdits` splice + `uploadCoverDocx` + PUT) resolves. This is the dominant felt jank. Optimistic-on-click fixes it.
2. **Re-parse flicker** — on the local state change, `setPreviewReloadKey((k)=>k+1)` (`useCompanyResearch.js:694`) drops the cached body HTML (`DocumentPreviewDialog.js:296-316` deletes `docState[cover]`), the body renders blank/loading, then `ensureLoaded` (`:325-345`) re-parses and refills. This is AC-O2.

**The collision (LOAD-BEARING):** the preview body is rendered **bytes-first, verbatim**. `loadPreviewModel` (`useDocumentPreview.js:411-424`) calls `buildPreviewBlob` first and only falls back to `linesToModel(coverLetterResultLines)` when that returns `null`. `buildPreviewBlob`→`previewBlobArgs` (`previewBlob.js:97-112`) passes `engineDocxB64: e.coverLetterDocxB64` and `docxPath: e.coverLetterDocxPath` with `edited: editedForScope(e,"cover")`, and `resolveDocumentBlob` (`docx.js:652-657`) returns the engine bytes **verbatim** when `!edited && engineDocxB64` (and next, fetches `docxPath` verbatim when `!edited && docxPath`).

Consequence: after a move, the new position is on screen today **only because the commit re-splices the docx and writes the fresh bytes into state before the reload** (`useCompanyResearch.js:681` `coverLetterDocxB64: commit.coverDocxB64`). The freshly-spliced bytes **do not exist at click time**. So an optimistic update that writes only `coverLetterResultLines = moved.lines` and bumps the reload key would re-parse the **stale** bytes and show the **old** position — the optimism would be invisible or wrong.

**Therefore the optimistic on-click write must defeat the verbatim serve** by nulling the state's byte sources so the body rebuilds from `moved.lines`. This is the crux of section 2 and is exactly the already-shipped, already-tested "no-bytes move rebuilds from lines" path (`moveInsertedFact.rc.test.js:272-302`, AC-A9) — pulled forward to click time.

## 2. The optimistic-move seam + rollback contract

Restructure `moveInsertedFact(jobId, factId, direction)` (`useCompanyResearch.js:635-697`). The plan, the resolved splice input, the commit, the store reconcile and the `recordDecision` calls all keep their current shape. Three things are added: a snapshot, an optimistic pre-await write, and a rollback branch.

### 2.1 Capture the exact pre-move snapshot (before any state write)

`entry` is already captured as a const at `:637` (`const entry = tailoringMap[jobId] || {}`). Snapshot exactly the cover-scoped fields a move touches or that the verbatim-serve reads:

```
const preMove = {
  coverLetterResultLines: entry.coverLetterResultLines,
  insertedFacts:          entry.insertedFacts,
  coverLetterDocxB64:     entry.coverLetterDocxB64,
  coverLetterDocxPath:    entry.coverLetterDocxPath,
  coverLetterPreviewHtml: entry.coverLetterPreviewHtml,
};
```

Rollback restores this **cover-scoped set only** (merged over current state), never a wholesale entry replace — a wholesale restore would clobber any unrelated concurrent change to the same entry (e.g. a résumé-scope edit). AC-M5's byte-equality is on `coverLetterResultLines` and `insertedFacts`, both captured by reference here; `planMoveFact` never mutates its inputs (`factMove.js:256` `noop` returns same refs; a real move builds `[...arr]`), so the captured references stay byte-identical to the pre-move arrays.

### 2.2 Resolve the splice input from the SNAPSHOT, not live state (preserves AC-X1)

Keep `resolvedCoverDocxB64 = await resolveCoverEngineBytes(entry)` computed against the captured `entry`. Because `entry` is a captured const, the optimistic state write in 2.3 does not change what the server splice sees. `commitFactMove` therefore produces byte-identical `moved.lines` / `moved.records` / PUT body with optimism on or off → **AC-X1 holds by construction.**

### 2.3 Optimistic apply — synchronous, before the first await visible to the click stack

Immediately after the `moved.changed` check (`:641`), before awaiting the commit:

```
setTailoringMap((current) => {
  const cur = current[jobId] || {};
  return { ...current, [jobId]: {
    ...cur,
    coverLetterResultLines: moved.lines,
    insertedFacts:          moved.records,
    coverLetterPreviewHtml: undefined,
    coverLetterDocxB64:     undefined,   // defeat the verbatim serve (docx.js:653)
    coverLetterDocxPath:    undefined,   // defeat the verbatim path-serve (docx.js:654)
  }};
});
setPreviewReloadKey((k) => k + 1);       // re-parse NOW, from moved.lines
```

With both byte sources nulled and `edited` unchanged (still false), `previewBlobArgs` hands `engineDocxB64:"" , docxPath:""`; `resolveDocumentBlob` falls through the verbatim branches; `buildPreviewBlob` returns a lines-rebuild when an uploaded template is present, else `null`, and `loadPreviewModel` then uses `linesToModel(moved.lines)` (`useDocumentPreview.js:414-422`). Either way the body renders the **new** position, highlighted via `markInsertedFacts(model, moved.records)` (`:424`, `versionDiff.js:154`). The write is synchronous within the click handler's stack up to `resolveCoverEngineBytes`'s await, so the shift is on screen on click (AC-M5).

### 2.4 Reconcile on success / roll back on failure

- **Failure** (`commit.ok === false`, `:668`): keep the existing `recordDecision("fact-position","failed",{reason:"save-failed",code:"save-failed"})` (`:669`, no ledger change → AC-X3). Then restore `preMove` over current state and `setPreviewReloadKey((k)=>k+1)` so the body re-parses the restored bytes. Return `{ok:false, reason}` unchanged.
- **Success**: the existing `setTailoringMap` (`:673-685`) already writes `moved.lines` / `moved.records` and the fresh `commit.coverDocxB64` (or leaves `cur` bytes when `!hasCoverBytes`); the existing `setAcceptedFactsByJob` (`:686-693`), `setPreviewReloadKey` (`:694`) and `recordDecision(...,"acted",...)` (`:695`) are unchanged. This overwrites the nulled byte sources with the reconciled ones, so steady state is byte-identical to HEAD.

### 2.5 Testable observables (jsdom/RTL)

- **AC-M5 present-before-settle:** stub the commit to hang; assert `tailoringMap[job].coverLetterResultLines` / `insertedFacts` equal `planMoveFact(...).lines` / `.records` before the promise settles.
- **AC-M5 exact rollback:** resolve the commit as failure; assert `coverLetterResultLines` and `insertedFacts` are `toEqual` the pre-move snapshot. Pin against the N81/N90 coalesced class with a two-facts-same-paragraph fixture (`relocateAffected`, `factMove.js:355`), asserting BOTH records' `{lineIndex,offset}` restore exactly.
- **AC-X1:** diff the PUT body (`putBodies` in `moveInsertedFact.rc.test.js`) with optimism on vs a pinned expected; `coverVersion.lines` / `insertedFacts` / `docxPath` unchanged from HEAD.

## 3. AC-O2 ruling — keep the full re-parse; do NOT build a targeted DOM patcher

**Ruling: the smoothness lever is optimistic-on-click (section 2), NOT replacing `setPreviewReloadKey` with a targeted in-place body update.** Reasons, with evidence:

- The re-parse is only *felt* as jank because today it fires **after** the multi-second commit. Once the state (and reload) happen synchronously on click, the re-parse runs against local data. For the common lines-render path (`linesToModel`, `useDocumentPreview.js:416`) that is cheap and local — no network. So optimistic-on-click already removes the dominant latency.
- A targeted DOM patch (mutate only the two changed paragraphs' nodes instead of dropping `docState[cover]`) is a **large-blast-radius re-architecture**: it would have to replace `DocumentPreviewDialog`'s cache-drop-and-`ensureLoaded` machine (`:296-345`), teach the model→HTML pipeline (`loadPreviewModel` → `renderModelToHtml`) to patch a subtree, and re-run `markInsertedFacts`' `(text, offset)` matching for only the patched paragraphs while keeping every other fact's highlight offset correct. That reaches three modules the N95 smoothness pass otherwise never touches and risks the byte-faithful highlight matching the whole feature rests on. **Out of proportion to scope; rejected.**

**Residual, surfaced honestly (OWNER-JUDGED, AC-O2/O1):** an intrinsic transition remains that optimism cannot remove. During the in-flight window the body renders from **lines / template-rebuild**; on commit success it re-parses from the **canonical spliced docx bytes**. For a lines-only (Gemini / version-switched) cover this is visually identical. For a docx-bytes cover the in-flight render may differ in docx-level formatting fidelity, then "snap" to the canonical render on commit. This snap is inherent to doing an optimistic move over a bytes-backed preview (the canonical render cannot exist until the splice runs, which is the very op being masked). It is the owner's real-browser call whether the snap reads as smooth; the design's lever to soften it is the CSS transition in section 6. **No jsdom test measures this** (see section 9).

## 4. Double-fire guard — one operation per fact at a time

### 4.1 Where the in-flight state lives

`DocumentPreviewMount.js` (already the owner of `removeError`, `pendingSmooth`, `appliedSmooth`). Add one state:

```
const [factOpPending, setFactOpPending] = useState(null);
// null | { factId, kind: "move" | "smooth-produce" }
```

Rule: **while a fact has an in-flight op, that fact's entire row is `aria-busy` and every one of its controls (both arrows, Smooth, Undo, Remove) is disabled.** This is the strongest form of AC-M2 ("cannot launch a second operation") and is deliberately **independent of `movability`** (AC-M2's explicit requirement — `movability` legitimately recomputes under optimistic UI as the arrow's boundary state changes, so it can never double as the guard).

Set it around the awaited call in the Mount's handlers:

- `onMove` (`:468-473`): `setFactOpPending({factId, kind:"move"})` before `await research.moveInsertedFact(...)`; clear in a `finally`.
- `handleSmooth` (`:370-386`): `setFactOpPending({factId, kind:"smooth-produce"})` before `await requestSmoothTransition(...)`; clear in a `finally`.

The SMOOTH-APPLY guard is separate (section 5.2) because it lives on the confirm surface, not the row.

### 4.2 New props on `InsertedFactsStrip` (consumed in-wave by the Mount)

```
busyFactId?: string | null   // the factId whose row is in flight, or null
```

Render: on the row whose `fact.id === busyFactId`, set `aria-busy="true"` on the row `<Box>` (`:78`) and add `disabled` to the back/forward/smooth/undo/remove `IconButton`s for that row (OR the existing `disabled` OR `busyFactId === fact.id`). The move arrows keep their existing `!movability[...]` driver AND gain the busy driver — the two are independent.

### 4.3 Testable observables

- **AC-M2:** stub `research.moveInsertedFact` to count calls and hang; fire the forward arrow twice synchronously; assert exactly one call and that the arrow is `disabled` after the first click.
- **AC-S1 no-double-produce:** stub `requestSmoothTransition`'s fetch deferred; click Smooth twice; assert one `requestSmoothTransition` and the Smooth control disabled after the first.

### 5.3 Announcement — reuse `useCopyFeedback`'s region idiom (AC-M3 / AC-S3)

## 6. Animation hook + reduced-motion (OWNER-JUDGED quality; 1e/9b decision)

The design provides the **hook**, not a testable quality gate. On the fact's highlight span (rendered by `markInsertedFacts`) add a CSS transition on the properties that change position/emphasis (e.g. `background-color` / `transform`), sized to a short duration in line with the shipped `CopyFeedback.js:124` 180ms precedent, gated:

```
@media (prefers-reduced-motion: reduce) { /* transition: none */ }
```

`prefers-reduced-motion` has **zero guards in the repo today** (`page.module.dupFlag.test.js:143`, `knowledgeSafety.sweep.test.js:142` pin zero motion; `CopyFeedback.js:124` ships an unguarded 180ms fade — CITED from the AC, re-confirmed at `CopyFeedback.js:124`). So this is a **1e/9b decision**: either (a) this is the first `@media (prefers-reduced-motion: reduce)` guard in the repo, or (b) 1e/9b rules a sub-200ms opacity/background fade exempt on the `CopyFeedback` precedent. **The acceptance of smoothness itself (AC-O1/O2/O3/O4) is the owner's real-browser call** — no jsdom criterion measures it (section 9).

### 10.1 The one test that must change (report, do not silently edit)

`moveInsertedFact.rc.test.js:259-269` clicks forward, waits for `coverLines()` to change, then clicks backward, asserting byte-identical round-trip. Its helper `clickMove` (`:210-224`) breaks its wait loop as soon as the lines change — which, **under optimism, happens synchronously on the click**, before the forward COMMIT has settled. This is a required 4b/plan hand-off, flagged here for the orchestrator — a green suite that "passes" only because the guard was weakened to per-direction would defeat AC-M2 (two concurrent splice+PUTs against one fact is the exact harm). The guard stays per-fact; the test's wait extends.
