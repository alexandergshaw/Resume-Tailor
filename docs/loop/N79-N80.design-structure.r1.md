## 0. The one decision this design turns on

The refusal has to carry **two codes with different blast radii**, produced at one seam
and never merged:

- a **coarse client cause** (`not_connected` / `reauth_required` /
  `temporarily_unavailable`) — safe to serialize into the response body, the activity
  log and the DOM;
- a **fine operator logCode** (`no_tokens` / `invalid_grant` / `invalid_client` /
  `network` / `unrecognized`) — server-only, logged, and it **must never reach the
  route body, the client, or the activity log** (AC-4, AC-11).

The structural choice that makes the leak *impossible* rather than merely *absent*: the
raw `GaxiosError` and the fine logCode **die inside `lib/gmail`**. The route receives
only `{ ok: false, cause }`. A route that never holds the provider error cannot leak it,
no matter how a later edit rewrites the 403 body. This is the direct structural answer to
the AC's warning about `route.js:80`'s existing `detail: err?.message`.

## 2. The classifier — `lib/gmail/authFailure.js` (N1)

```js
/**
 * The COARSE, client-facing cause. Closed set. Safe to serialize.
 * @typedef {"not_connected" | "reauth_required" | "temporarily_unavailable"} GmailAuthCause
 */

/**
 * The FINE, server-only discriminant. Closed set. NEVER serialized to a response
 * body, the client, or the activity log.
 * @typedef {"no_tokens" | "invalid_grant" | "invalid_client" | "network" | "unrecognized"} GmailAuthLogCode
 */

export const GMAIL_AUTH_CAUSES = ["not_connected", "reauth_required", "temporarily_unavailable"];

/**
 * classifyAuthFailure(input) -> { cause, logCode }
 *
 * PURE. No I/O. No throw, for ANY input (total). Maps a token/refresh failure to a
 * coarse client cause and a fine server-only logCode.
 *
 * Discriminant rules, verbatim from research R-1/R-2 (do NOT re-derive):
 *   - provider rejection  <=>  Boolean(err?.response) is truthy
 *       (google-auth-library's own convention, oauth2client.js:377 — NOT `err.code`,
 *        NOT `'response' in err`, which is always true)
 *   - OAuth code          =    err.response.data.error  (a STRING)
 *       NEVER err.code (that is the numeric HTTP status) and NEVER err.message
 *       (google-auth-library rewrites it to JSON under the /ReAuth/i case — R-4)
 *   - network failure     <=>  err.response is falsy
 *
 * @param {{ kind: "no-tokens" } | { kind: "refresh-error", error: unknown }} input
 * @returns {{ cause: GmailAuthCause, logCode: GmailAuthLogCode }}
 */
export function classifyAuthFailure(input) { /* ... */ }
```

**The mapping table the unit test (AC-3) pins — one failable row per line:**

| input | read | logCode (server) | cause (client) | AC |
|-------|------|------------------|----------------|----|
| `{ kind: "no-tokens" }` | — | `no_tokens` | `not_connected` | AC-3(i) |
| refresh-error, `err.response.data.error === "invalid_grant"` | `err.response.data.error` | `invalid_grant` | `reauth_required` | AC-3(ii) |
| refresh-error, `err.response.data.error === "invalid_client"` | `err.response.data.error` | `invalid_client` | `temporarily_unavailable` | AC-3, F-2, AC-4 |
| refresh-error, `err.response` falsy (network) | `Boolean(err.response)` | `network` | `temporarily_unavailable` | AC-3(iii) |
| refresh-error, `err.response` present but `data.error` is any other/absent string, OR a non-Gaxios throw | fall-through | `unrecognized` | `reauth_required` | AC-3(iv) |

Two rulings the fall-through encodes, both from the AC:

- **Fail toward a visible remedy.** Any refresh-error that is not positively identified as
  a network failure or `invalid_client` defaults to `reauth_required` — a visible
  reconnect, never silence and never `temporarily_unavailable`. This includes
  `admin_policy_enforced` and every other unrecognised provider code (research R-6 flags
  these exist). Rationale is AC-3's: the dominant harm is the original swallow bug.
- **`invalid_client` splits by axis.** Its *client* cause is `temporarily_unavailable`
  (the user's reconnect cannot fix a rotated secret — F-2), but its *logCode* stays
  `invalid_client` so the operator is alerted (AC-4). This is the only place the two axes
  diverge, and it is the reason they are two fields, not one.

**Checkable property (apply to a diff of N1):** grep the classifier body — it must read
`err?.response?.data?.error` and `err?.response` (or `err && err.response`) and must
contain **no** read of `err.code` and no read of `err.message` for classification. A diff
that introduces `err.code ===` or `err.message ===` in the mapping is the R-1/R-4 trap and
fails review. (Canary for the reviewer's grep: the string `err.response` must appear; if
the grep returns nothing the classifier was renamed and the check is invalid.)

**Why a pure shape check, not `instanceof GaxiosError`:** research R-3 gives a
no-new-dependency path to the real class, but a shape check (`Boolean(err?.response)` +
`typeof err?.response?.data?.error === "string"`) needs no import at all, so N1 stays
dependency-free and its unit test uses plain objects. `instanceof` is available if the TDD
seat wants a second belt; it is not required and must not be the primary discriminant.

## 3. `getAuthenticatedClient` — the seam (M1)

**Old contract** (`gmailClient.js:78-98`):
`getAuthenticatedClient(userId, redirectUri) => Promise<OAuth2Client | null>` — returns
`null` on both the no-tokens path (`:80`) and the refresh-failure path (`:91-94`), which
is the exact information loss this chunk exists to end.

**New contract:**

```js
/**
 * @typedef {{ ok: true, client: import('googleapis').Auth.OAuth2Client }
 *         | { ok: false, cause: import('./authFailure.js').GmailAuthCause }} GmailClientResult
 *
 * getAuthenticatedClient(userId, redirectUri) => Promise<GmailClientResult>
 *
 * On success:            { ok: true, client }
 * On no stored tokens:   { ok: false, cause: "not_connected" }
 * On refresh failure:    { ok: false, cause } where cause comes from classifyAuthFailure
 *
 * The raw error and the fine logCode NEVER leave this function. On a refresh failure the
 * fine logCode is written to the server log HERE (console.error, the existing idiom) and
 * discarded; only `cause` is returned.
 */
```

Two internal responsibilities the seam now owns:

1. **No-tokens path** (was `:79-80`): `classifyAuthFailure({ kind: "no-tokens" })` →
   `{ ok: false, cause: "not_connected" }`. This is an ordinary state, not an operator
   alert — do **not** `console.error` it.
2. **Refresh-failure path** (was `:87-94`, the `catch`): capture the error,
   `const { cause, logCode } = classifyAuthFailure({ kind: "refresh-error", error: err })`,
   then log **only** the logCode server-side and return `{ ok: false, cause }`.

**The operator log line (AC-4), exact content discipline:** log the `logCode` string and
`userId` only — e.g. `console.error("[gmail auth] refresh failed", { userId, logCode })`.
It must **not** interpolate `err.message`, `err.response.data`, the token, or a stack.
`logCode` is the whole point: it separates `invalid_client` (operator must rotate the
secret) from `network` (self-heals) without disclosing anything (AC-4 + AC-11).

**Checkable property (apply to a diff of M1):**
- The `catch` block must no longer `return null`. A diff where `gmailClient.js`'s
  refresh-failure `catch` still returns `null` (or where the no-tokens branch returns
  `null`) has not landed AC-1.
- The `console.error`/`console.warn` added on this path must reference `logCode` and must
  **not** reference `err.message`, `err.stack`, `err.response`, or `credentials`/`tokens`.
  Grep the added log call for those identifiers; any hit fails AC-4/AC-11.

**Blast radius (owned):** the return-type change from `null`-or-client to a result object
touches exactly one caller, `route.js:37` (§5 census). Nothing else in the tree destructures
or truthiness-tests the return of `getAuthenticatedClient`.

## 4. `POST /api/gmail/messages` — the route contract (M2)

The auth gate (`:16-23`) is unchanged and stays FIRST. The `cause` is produced strictly
downstream of it, so an unauthenticated caller can never receive one (AC-2/AC-11 by
construction — the 403+cause branch is physically after the 401 return).

```
POST /api/gmail/messages

401  { error: "Unauthorized" }                         // UNCHANGED. No cause field.
403  { error: <canned human string>, cause: GmailAuthCause }   // CHANGED: adds cause
200  { messages: Array<...> }                          // UNCHANGED (incl. the {messages:[]}
                                                        //   early return at :59-61)
500  { error: "Failed to fetch Gmail messages." }      // detail:err?.message REMOVED
                                                        //   (or left AS-IS — see note)
```

Refusal branch, replacing `:37-43`:

```js
const result = await getAuthenticatedClient(user.id, redirectUri);
if (!result.ok) {
  return NextResponse.json(
    { error: HUMAN_BY_CAUSE[result.cause], cause: result.cause },
    { status: 403 },
  );
}
const auth = result.client;   // downstream unchanged
```

- `HUMAN_BY_CAUSE` is a small route-local (or shared-with-client) map from the closed
  cause set to a canned human string. It carries **no** interpolated provider text. The
  client keys on `cause`, never on this string (AC-5/AC-6) — the string is for
  backward-compat and non-cause consumers only.
- `cause` is drawn only from the closed set. The route never invents a cause and never
  forwards a logCode.

**On `route.js:80`'s existing `detail: err?.message`:** that is on the **500** path
(Gmail *call* failed after auth), not the 403 path this chunk changes. The AC flags it as
"the pattern NOT to copy." This design does not copy it onto the 403. Whether to *also*
remove it from the 500 is a pre-existing leak outside AC-11's named surface (AC-11 governs
the refusal/403 body and the log). I recommend removing `detail: err?.message` from the
500 in this chunk since M2 edits this file anyway and it is the same disclosure class — I
flag it as a **plan decision**, not a mandate, because no AC row makes it RED.

**Checkable property (apply to a diff of M2):**
- The 403 body must contain a `cause` key whose only possible values are the three coarse
  strings, and must not contain `detail`, `err.message`, `logCode`, or `err.response`.
- The `cause`-bearing return must appear textually **after** the `if (error || !user)`
  401 return. A reviewer confirms the 401 branch has no `cause` key.

## 6. Client data flow and the connection state (N2, M3, M4, N3)

### The domain fact that shapes the surface

**Gmail connection is one-per-account, not per-application.** The per-app email chips
(`emailClassificationsByAppId`) are a different axis. Therefore the Connect/Reconnect
affordance is a **single surface-level notice**, never rendered inside `ApplicationCard`.
Rendering it per-app would show N identical "Connect Gmail" controls and cry wolf N times
on one transient blip. This is a load-bearing structural decision, not a styling choice.

### The connection-state shape (hook → page → TrackingTab → notice)

```js
/**
 * @typedef {null | { cause: GmailAuthCause }} GmailConnectionState
 *   null                                  -> connected, OK, or not-yet-checked: render nothing
 *   { cause: "not_connected" }            -> banner + one-click Connect
 *   { cause: "reauth_required" }          -> banner + one-click Reconnect
 *   { cause: "temporarily_unavailable" }  -> quiet "couldn't reach Gmail" note, NO control
 */
```

`null` covers both "ok" and "not yet determined" because both render nothing; the
*distinct observable state* AC-5 requires is `{ cause }` present vs absent, which is
independent of `gmailMessages` being `[]`. On a successful fetch the hook sets
`gmailConnection = null` (clearing any prior refusal); on a refusal it sets `{ cause }`.
A `{ messages: [] }` success and a `not_connected` refusal are therefore two different
states: one has `gmailConnection === null`, the other `{ cause: "not_connected" }` — AC-5.

### `useGmailMessages` (N2) contract

```js
/**
 * useGmailMessages({ currentUser, applicationData }) => {
 *   gmailMessages: Array<MatchedMessage>,          // was page.js gmailMessages state
 *   emailClassificationsByAppId: Record<string, "rejection"|"interview"|"confirmation">,
 *   gmailConnection: GmailConnectionState,         // the NEW state (AC-5)
 * }
 *
 * Owns: the fetch (was page.js:914-929), the 30-min poll (was :934-940) with
 * cause-conditioned stop (AC-8), body parsing keyed on `cause` (AC-5), and the
 * recordDecision call (AC-10). Mirrors useDuplicateApplyCheck.js's shape exactly:
 * a hook that owns a decision, calls recordDecision, and IS the DECISION_LEDGER module.
 */
```

Moving the `emailClassificationsByAppId` reduce (currently inline JSX at `page.js:2803-2815`)
into the hook as a `useMemo` removes those lines from the god-component and gives the
derived map one home. `page.js` passes both `emailClassificationsByAppId` and
`gmailConnection` down.

### The fetch → state mapping inside `loadGmailMessages` (N2)

Replaces the `if (!res.ok) return;` swallow at `page.js:921` and the bare `catch {}` at
`:928`:

| response | `gmailConnection` | poll (AC-8) | recordDecision (AC-10) |
|----------|-------------------|-------------|------------------------|
| 200, `messages` parsed | `null` | keep | `("gmail-fetch","acted",{reason:"fetched",count:N})` |
| 403 with `cause` ∈ {`not_connected`,`reauth_required`} | `{ cause }` | **stop** | `(...,"refused",{reason:"refused",cause})` |
| 403 with `cause` = `temporarily_unavailable` | `{ cause }` | keep | `(...,"failed",{reason:"unreachable",cause})` |
| any other non-ok (500, or 403 with no recognised cause) | `{ cause: "temporarily_unavailable" }` | keep | `(...,"failed",{reason:"unreachable",cause:"temporarily_unavailable"})` |
| `fetch` itself throws (offline) | `{ cause: "temporarily_unavailable" }` | keep | `(...,"failed",{reason:"unreachable",cause:"temporarily_unavailable"})` |

The last two rows are the robustness contract: the client keys on `cause` only when it is
one of the three known strings; every other shape collapses to the transient bucket
(no remedy, keep polling), so an unexpected body can never crash the hook or strand a false
"disconnected." This is the client mirror of the server's fail-toward-visible rule.

### AC-8 poll mechanism

The hook holds a `pollStopped` boolean state. `loadGmailMessages` sets it `true` **only**
for `not_connected`/`reauth_required`; `temporarily_unavailable` leaves it untouched. The
interval effect (was `page.js:934-940`):

```
useEffect(() => {
  if (!currentUser || applicationData.length === 0 || pollStopped) return;
  loadGmailMessages();
  const id = setInterval(loadGmailMessages, 30 * 60 * 1000);
  return () => clearInterval(id);
}, [currentUser, applicationData.length, pollStopped]);
```

When `pollStopped` flips true, the effect re-runs, cleanup **clears the interval**, and the
body early-returns without scheduling a new one (AC-8's instrument asserts the interval is
*cleared*, so gating inside the tick would fail — it must actually `clearInterval`).
`temporarily_unavailable` never flips the flag, so the interval survives a transient blip
(AC-8's named failure direction).

**Resume after (re)connection is by remount, and that is the only path.** Verified: the
Connect control is a full-page navigation to `/api/gmail/connect` (§below), which redirects
to Google and back to `/?gmail_status=connected` — a full page load. `page.js` has **no**
reader of `gmail_status` (Grep for `searchParams|useSearchParams|gmail_status` in
`page.js` returned nothing), so the refused state clears purely because the fresh page
mounts the hook with `pollStopped=false`. AC-7's "successful return clears the refused
state and re-enables fetch" is satisfied by this remount, over a real seam
(`gmail_status=connected` already emitted by `oauth2callback/route.js:79`), not an invented
one. No new query-param reader is required; if the plan wants an in-tab SPA reconnect later
that is a separate enhancement.

### `GmailConnectionNotice` (N3) contract

```js
/**
 * <GmailConnectionNotice cause={GmailAuthCause | null | undefined} />
 *
 * cause == null/undefined                -> renders null
 * cause == "not_connected"               -> "Connect Gmail to see application updates"
 *                                            + <a href="/api/gmail/connect">Connect Gmail</a>
 * cause == "reauth_required"             -> copy: access expired/was revoked
 *                                            + <a href="/api/gmail/connect">Reconnect Gmail</a>
 * cause == "temporarily_unavailable"     -> quiet "Couldn't reach Gmail" note, NO control
 */
```

The Connect/Reconnect control is an **`href` link to `/api/gmail/connect`** — the exact
idiom `GmailButton.js:41` already uses. `href` (not `onClick`+`router.push`) makes the
control user-initiated *by construction*: it cannot auto-navigate the tab to Google's
consent screen (AC-6's explicit prohibition) because nothing fires until the user clicks.
Both connectable causes point at the same endpoint (`/api/gmail/connect`), matching the
AC's "same endpoint, different copy." `temporarily_unavailable` renders no control at all
(offering reconnect on a self-healing failure is the wrong remedy — AC-6).

`TrackingTab` renders exactly one `<GmailConnectionNotice cause={gmailConnection?.cause} />`
above the application list (M4). It is **not** threaded into `ApplicationCard`.

**Checkable property (apply to a diff of N3/M4):**
- The connect control's `href` must resolve to `/api/gmail/connect` (AC-6 checks the
  target, not merely that a button exists). A control rendered with `onClick` that calls
  `router.push`/`window.location` to Google directly fails the "user-initiated, no
  auto-navigate" rule.
- `GmailConnectionNotice` must be rendered by `TrackingTab`, not by `ApplicationCard`
  — grep `ApplicationCard.js` for `GmailConnectionNotice`; any hit is the per-app
  cry-wolf regression.

## 7. `GmailButton` three-state (M5, AC-9)

Current defect (`GmailButton.js:15-20`): a non-OK status response (`r.ok ? … : null`) and
a thrown fetch (`.catch(() => setConnected(false))`) both land on `connected=false`, which
renders the "Connect Gmail" (disconnected) affordance — a false "disconnected" when the
account is fine but the status check hiccuped.

**New state:** replace the boolean-with-null with a discriminated status:

```js
/** "loading" | "connected" | "disconnected" | "check-failed" */
const [status, setStatus] = useState("loading");
// r.ok && json.connected      -> "connected"
// r.ok && !json.connected      -> "disconnected"
// !r.ok  OR fetch throws       -> "check-failed"
```

- `"check-failed"` renders a distinct line (e.g. "Couldn't check Gmail") — **not** the
  `Connect Gmail` button and **not** the connected view.
- `"disconnected"` keeps the existing `Connect Gmail` button.

**Checkable property (apply to a diff of M5):** the `.catch` and the non-ok branch must set
the check-failed state, not the disconnected one. A diff where either still routes to
`setConnected(false)` / the disconnected view has not landed AC-9.

**Blast-radius note (out of scope, flagged):** `DriveButton.js:18` *deliberately mirrors*
`GmailButton.js:19`'s `.catch(() => setConnected(false))` and shares the identical swallow
defect. The AC scopes AC-9 to `GmailButton` only, so this design does **not** mandate
fixing `DriveButton` — but the checker/orchestrator should know the same class of bug lives
one file over, unaddressed, and `DriveButton.test.js:481` currently *pins* the flawed
posture as intended. Fixing Drive would require changing that test and is a separate item.

## 8. Decision-ledger entry (M6, AC-10)

New entry appended to `DECISION_LEDGER` (`activityChannels.js:215-233`):

```js
{
  module: "app/hooks/useGmailMessages.js",   // MUST byte-equal N2's path (sweep binds it)
  id: "gmail-fetch",                          // no collision with duplicate-check/fact-auto-insert
  label: "Gmail message fetch decisions",
  fields: ["reason", "cause", "count"],       // closed; cause in {not_connected,reauth_required,temporarily_unavailable}
  outcomes: ["acted", "refused", "failed"],   // includes negatives -> declaresRefusal passes
}
```

All four field values are safe by the closed vocabulary: `reason` is a canned string
(`"fetched"`/`"refused"`/`"unreachable"`), `cause` is the coarse code, `count` is the
integer message count on success. **Never** a subject, sender, body, token, or raw provider
error — the same discipline as the `fact-auto-insert` entry's `code` field
(`activityChannels.js:224-232`), and `recordDecision` itself drops any field not in this
list (`appActivityLog.js:182-201`).

**Outcome ↔ cause pairing** (from the §6 table):
`acted` (success, `count`, no `cause`) · `refused` (`not_connected`/`reauth_required`) ·
`failed` (`temporarily_unavailable`).

**How the guards bind this:**
- `decisionCoverage.sweep.test.js:262-269` (`toEqual` both directions) goes RED the instant

## 9. End-to-end data flow (one refusal, one success)

```
refusal:
  loadTokens -> null  OR  refreshAccessToken() throws GaxiosError
        |                        |
        v                        v
   classifyAuthFailure({no-tokens})   classifyAuthFailure({refresh-error, error})
        |                        |         -> { cause, logCode }
        |                        +-- console.error(logCode, userId)   [server-only, AC-4]
        v
   getAuthenticatedClient -> { ok:false, cause }          [raw error dies here, AC-11]
        v
   route -> 403 { error: canned, cause }                  [after auth gate, AC-2]
        v
   useGmailMessages.loadGmailMessages: parse cause
        |-- connectable -> gmailConnection={cause}, pollStopped=true, recordDecision(refused)
        |-- transient   -> gmailConnection={cause}, poll kept,        recordDecision(failed)
        v
   page.js -> TrackingTab gmailConnection prop
        v
   <GmailConnectionNotice cause> -> Connect/Reconnect href="/api/gmail/connect" (connectable)
                                    OR quiet note (transient)
        v
   user clicks Connect -> full-page nav -> Google -> /?gmail_status=connected
        v
   remount: hook mounts pollStopped=false, fetch succeeds -> gmailConnection=null   [AC-7]

success:
  getAuthenticatedClient -> {ok:true, client} -> route 200 {messages}
        -> gmailConnection=null, recordDecision(acted, count) -> chips render as today
```
