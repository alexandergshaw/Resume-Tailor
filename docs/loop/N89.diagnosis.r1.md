## Verdict

**The hypothesis is CONFIRMED as a real, live, checkable defect**: an explicit accept (manual, via the research
dialog) never clears a fact's url/id from the persisted removed log, even when that same fact is the one being
accepted. This is not a maybe — it is provable by reading three files with no execution needed. Separately, the
specific "cycle 1 acted, cycle 2 nothing-eligible" symptom is **plausibly, but not provably from what this seat can
see, explained by the same removed-log mechanism working exactly as its own code comments say it should** (a
retracted fact never silently returns) — which may mean the owner's specific repro is not itself a bug, while the
accept-never-clears defect underneath it is. Both readings are laid out below with the evidence that distinguishes
them, and Spec 1 (logging) is exactly what would let a future repro tell them apart without a diagnostic session.

## 1. Confirmed mechanism: the removed log is write-only from the client's perspective

**`removeInsertedFact` is the only path that ever adds to the removed log.**
`useCompanyResearch.js:677-678`:
```
const removedKey = record.url || record.id || "";
const removedLog = removedKey && !priorRemoved.includes(removedKey) ? [...priorRemoved, removedKey] : priorRemoved;
```
This is sent as `declinedUrls: removedLog` in the PUT body two lines later (`:689`).

**Neither of the two paths that could plausibly reverse it ever does.**

- `acceptFacts` (manual accept), `:445`:
  ```
  const declinedUrls = acceptedFactsByJob[jobId]?.removed || [];
  ```
  This reads the CURRENT removed log and resends it **completely unchanged** at `:528` (`declinedUrls,` inside the
  PUT body), regardless of what `facts` (the selection being accepted, built at `:438`) contains. There is no
  filter, no set-subtraction, nothing that drops an entry from `declinedUrls` because the same key now appears in
  `facts`. The comment directly above (`:440-444`, "M3") explains why `declinedUrls` is resent verbatim instead of
  the dialog's placeholder `[]` — the dialog has no removal UI, so echoing back the current value is what stops an
  accept from silently wiping the log — but that comment addresses "how do we avoid deleting everything," not "how
  does an explicit accept un-decline the fact it's accepting." The un-decline case was never written.

- `autoInsertFactsForJob`, `:910`:
  ```
  declinedUrls: removedLog,
  ```
  `removedLog` here is `seeded.removed || []` (`:835`), read fresh via `fetchAcceptedFactsInto` at `:821` and
  passed straight through. Same pattern: resend unchanged. This one is arguably *correct* to never clear anything,
  because the eligibility filter (`:845-850`, see below) already refuses to auto-insert anything whose key is in
  `removedSet` in the first place — so auto-insert's own successful inserts are, by construction, never a member of
  the removed set it is echoing back. **Answering the brief's specific question: auto-insert's own success path
  never needs to clear the removed log, because it can never reach a state where it just inserted something the log
  still calls removed — the two sets are disjoint by construction at every call.** The defect is entirely on the
  accept side.

**The server has no compensating logic.** `app/api/accepted-facts/route.js:69` forwards `removed: body?.declinedUrls`
verbatim into `acceptFactsForJob` (`lib/acceptedFacts/factStore.js:103`, `p_removed: Array.isArray(removed) ?
removed : []`), and the RPC (`supabase/migrations/20260923030000_application_accepted_facts.sql:256`) does a
straight replace: `retracted = coalesce(p_removed, '[]'::jsonb)`. There is no server-side reconciliation against
`p_facts` that would strip a url out of `retracted` because it also appears in the facts being accepted. Whatever
the client sends as `declinedUrls` is exactly what gets stored, forever, until a client sends something different —
and no client code path ever does.

**Conclusion, stated precisely**: once `record.url` (or `record.id`) enters the removed log via `removeInsertedFact`,
it stays there through every subsequent `acceptFacts` and every subsequent `autoInsertFactsForJob` call for that
application, including one that explicitly re-accepts the exact same fact. This is confirmed by reading the three
call sites above; it required no execution or mutation to establish, only tracing where `declinedUrls`/`removedLog`
values originate and where they are consumed.

## 2. The eligibility filter reads that log unconditionally

`useCompanyResearch.js:845-850`:
```js
const eligible = articles.filter((a) => {
  if (!a || articleUrlKey(a.url) === null) return false;
  if (!String(a.suggestion || "").trim()) return false;
  if (removedSet.has(a.url) || removedSet.has(a.id)) return false;
  return true;
});
if (eligible.length === 0) {
  return { ok: false, reason: "No eligible facts to insert.", severity: "info", code: "nothing-eligible" };
}
```
`removedSet` (`:836`) is built from `seeded.removed` (`:835`), the exact log discussed above. So an article whose
url is stuck in the removed log is excluded from `eligible` on every future run, regardless of whether the
candidate has since tried to re-accept it through the dialog.

`DocumentPreviewMount.js:194-198` confirms the brief's framing that `nothing-eligible` implies articles were
present, not that research came back empty:
```js
const autoInsertResearchResolved =
  !!autoInsertResearchEntry && !autoInsertResearchEntry.loading &&
  Array.isArray(autoInsertResearchEntry.articles) && autoInsertResearchEntry.articles.length > 0;
```
and `autoInsertFactsForJob` is only ever invoked (`:251-254`) when `autoInsertResearchResolved` is true. So
`fact-auto-insert.skipped reason:"No eligible facts to insert." code:nothing-eligible` is only reachable when
`articles.length > 0` going in and `eligible.length === 0` coming out — i.e., every single article this run saw was
rejected by one of the three filter branches. Confirmed exactly as the brief states.

## 3. The manual dialog can reach the "simultaneously accepted and removed" state

The brief's "ALSO DETERMINE" question — can an accepted fact's url end up simultaneously in the removed log — is
answered **yes, and it is reachable through the shipped UI, not just in principle**:

`CompanyResearchDialog.js` never reads `acceptedFactsByJob`, `removed`, or any removed/declined state at all — the
only occurrence of `declinedUrls` in that file is the always-empty placeholder at `:139`
(`acceptSelection()`'s `declinedUrls: []`). The dialog's card list (`chosen()`, `:117-124`) is built from
`researchByJob[jobId].articles` with no filtering against the removed log. **A previously-removed article's card
still renders and is still selectable** in a reopened research dialog, because removal (`removeInsertedFact`) never
touches `researchByJob` — it only edits `entry.coverLetterResultLines`, `entry.insertedFacts`, and the server-side
`facts`/`removed` columns.

So the concrete, reachable sequence is:
1. A fact is inserted (auto or manual) — its url enters `facts`, not `removed`.
2. The candidate clicks the preview's one-click removal (`removeInsertedFact`) — the url moves: out of `facts`
   (`:679`, `storedFacts = ... .filter((f) => f?.id !== factId)`), into `removed` (`:677-678`).
3. The candidate reopens the research dialog. The same article's card is still there (step above). They check it
   again and click Accept.
4. `acceptFacts` runs: `facts` now includes this url again, `mergedFacts` (`:519`, via `mergeAcceptedFacts`) puts it
   back into the accepted set — **but `declinedUrls` at `:445` still reads the stale `removed` array, which still
   contains this exact url**, and resends it unchanged at `:528`.
5. The PUT persists a row where the SAME url is simultaneously present in `facts` and in `removed`.

This is a genuine data-integrity anomaly (the two arrays are supposed to be disjoint — a fact is either currently
accepted or currently declined, never both), and it is what silently defeats the "explicit accept overrides a
removal" intent the brief describes, because nothing about step 4 clears the stale entry.

One nuance worth recording precisely: the re-accept in step 4 **does correctly reinsert the fact's text into the
letter** — `planCoverFacts`'s "already present" guard keys off `priorRecord` (built from `priorFacts`, which no
longer contains this id after step 2's removal), so the text-insertion path is not broken. **Only the removed-log
bookkeeping is broken.** The visible symptom is deferred: the letter looks correct immediately after the re-accept,
and the defect only surfaces on the *next* fresh research + auto-insert cycle for the same application, which is
exactly the two-cycle shape in the owner's log.

## 4. The minted-id / stable-key question

Confirmed **not** a source of flakiness here, for the specific case that matters. `mintArticleId`
(`useCompanyResearch.js:168-172`):
```js
function mintArticleId(article, runStamp, index) {
  const key = articleUrlKey(article?.url);
  if (key !== null) return `art-${hashString(key).toString(36)}`;
  return `art-run${runStamp}-${index}`;
}
```
An article with a usable url gets a **deterministic, run-independent** id (a hash of the normalized url) — the
`runStamp`/`index` fallback only fires when `articleUrlKey` is null (no usable url at all). And `removedKey` at
`:677` prefers `record.url` over `record.id` (`record.url || record.id`); every article that could ever have been
auto-inserted or manually accepted already passed the `articleUrlKey(a.url) !== null` gate (`:846`, and the
dialog's own `chosen()` only surfaces suggestion-bearing cards), so `record.url` is populated and is what actually
gets stored as `removedKey` in the ordinary case. So: the key that persists across research runs and matches in the
eligibility filter is the stable url, not a volatile per-run id — the mechanism matches reliably, which is
precisely why the suppression is *permanent* rather than *flaky*. A volatile id would have produced intermittent
false negatives (removal "wearing off" on some runs); what's observed instead is a removal that never wears off,
consistent with url-keyed, deterministic matching.

## 5. Same application or a new one? (conditional, as the brief requires)

This cannot be settled from what this seat can see (no raw log, no ids), but one code fact narrows it
substantially: **`DocumentPreviewMount.js`'s auto-insert attempt is deduped per `jobId` for the lifetime of the
mounted component** (`:183`, `autoInsertAttemptedRef`; `:249`, `if (autoInsertAttemptedRef.current.has(autoInsertJobId)) return;`),
and that component "stays mounted for the app's whole lifetime" per its own header comment (`:81`). So if cycle 1
and cycle 2 in the log share the same `jobId`, the effect could not have fired `autoInsertFactsForJob` a second time
for it within one continuous browser session — a full page reload (which remounts the component and resets the
in-memory `Set`) must have happened in between. The server-persisted `removed` column survives a reload untouched,
so this is fully consistent with the diagnosis: reload, then a fresh tailor + fresh research on the same job,
re-triggers auto-insert against a removed log that still carries the earlier removal.

If instead cycle 1 and cycle 2 are genuinely different `jobId`s (a new application), the removed-log hypothesis
still requires *that specific jobId's own* removed log to already contain the matching url — which would only be
true if the "fresh" application actually reuses an existing `accepted_facts` row (same underlying application /
position, re-tailored under what looks like a new session) rather than being a first-ever tailor of a brand-new
job. A truly first-ever application has an empty removed log (`getFactsForJob`, `factStore.js:74`, returns
`removed: []` when no row exists), so the hypothesis cannot explain `nothing-eligible` for a genuinely virgin
application — in that case the cause would have to be no-url/no-suggestion on every article, which the brief
already flags as unlikely given cycle 1 proved this company's research is insertable.

**Stated as the brief asks**: it is plausible either way, but the per-jobId dedup ref means "same application" is
only reachable via an intervening page reload, while "different application" is only reachable if it is a
re-tailor of an existing position rather than a brand-new one. Both are consistent with "a fresh tailor reusing a
position vs a new one" in the brief's own phrasing — this seat cannot pick between them without the actual jobIds
from the log, which are redacted.

- **Not a research/engine defect.** Cycle 1's successful insert already proves this company's research produces a

- **Not the minted-id volatility** (section 4) — matching is url-keyed and deterministic for any article that could
  ever reach this filter.
- **Not `applyCompanyResearch`** (the arrange-step "Insert into cover letter" button, `CompanyResearchDialog.js:364`
  → `app/hooks/useCompanyResearch.js:388-408` → `weaveSources`). That path never calls `/api/accepted-facts` at all
  and never reads or writes the removed log — it is a separate, already-tracked defect (backlog N85, zero dedupe)
  and is untouched by, and irrelevant to, this diagnosis.
- **Not N89 Part 1's own fix regressing.** `resolveCoverEngineBytes`, `coverFactStrategy`, and the Shape B
  line-rebuild path are all unrelated to the eligibility filter or the removed log; the log's own evidence (an
  `acted count:1` before the `nothing-eligible`) shows the byte/template resolution succeeded in cycle 1 and would
  have had to succeed again in cycle 2 to even reach the eligibility filter (the `no-engine-bytes` refusal happens
  earlier in the function, at `:777-779`, and did not fire).

## Spec 1 — logging enrichment

**Goal**: the next `nothing-eligible` repro should be conclusive on its own, without a diagnostic session, and
should be able to expose the accept-does-not-clear-removed defect directly (a nonzero
"dropped-because-removed-but-also-currently-accepted" count is direct proof of the anomaly in section 3).

**Where the counts are computed** — `useCompanyResearch.js`, inside `autoInsertFactsForJob`, replacing the
`eligible = articles.filter(...)` block at `:845-850` with a single pass that tallies as it goes, preserving the
exact same per-article short-circuit order (no-url → no-suggestion → removed) so the reported reason for each drop
is the same reason the filter itself used — never a re-derived, possibly-different reason:

```js
let droppedNoUrl = 0;
let droppedNoSuggestion = 0;
let droppedRemoved = 0;
let droppedRemovedAlsoAccepted = 0;
const eligible = articles.filter((a) => {
  if (!a || articleUrlKey(a.url) === null) { droppedNoUrl += 1; return false; }
  if (!String(a.suggestion || "").trim()) { droppedNoSuggestion += 1; return false; }
  if (removedSet.has(a.url) || removedSet.has(a.id)) {
    droppedRemoved += 1;
    // Direct exposure of the section-3 anomaly: this article is excluded as
    // "removed" while the SAME key is sitting in the accepted facts this
    // application already has -- proof the removed log was never cleared on
    // an accept that should have cleared it.
    if (priorFacts.some((f) => f?.id === a.id || (a.url && f?.url === a.url))) droppedRemovedAlsoAccepted += 1;
    return false;
  }
  return true;
});
if (eligible.length === 0) {
  return {
    ok: false,
    reason: "No eligible facts to insert.",
    severity: "info",
    code: "nothing-eligible",
    articleCount: articles.length,
    droppedNoUrl,
    droppedNoSuggestion,
    droppedRemoved,
    droppedRemovedAlsoAccepted,
  };
}
```
`priorFacts` is already in scope at `:834` (`const priorFacts = seeded.facts || [];`) — no new fetch needed. Counts
are mutually exclusive by construction (each article hits exactly one `return false` or falls through), so
`droppedNoUrl + droppedNoSuggestion + droppedRemoved === articleCount - eligible.length` always holds and is itself
a cheap invariant a future unit test can assert. Only the `nothing-eligible` return carries the new fields — every
other return of this function (success, no-cover-letter, no-engine-bytes, already-edited, nothing-new, verify-failed,
save-failed, no-open-surface) is byte-identical to today, which is the smallest change that answers exactly what
the brief asked for.

**Where the fields become loggable** — `lib/activityLog/activityChannels.js:230`, the `fact-auto-insert`
`DECISION_LEDGER` entry's `fields` array, widened from:
```js
fields: ["reason", "count", "code"],
```
to:
```js
fields: ["reason", "count", "code", "articleCount", "droppedNoUrl", "droppedNoSuggestion", "droppedRemoved", "droppedRemovedAlsoAccepted"],
```
This stays inside N77's privacy rule already documented at that entry's own comment (`:227-229`, "never the fact
text, the company, the article title or a byte of the letter itself") — every new field is a plain count, never a
url, id, title, or suggestion string. `recordDecision`'s allowlist mechanism
(`appActivityLog.js:182-201`, `allowedFields`/`picked`) is what actually enforces this: a field not listed here is
silently dropped even if a caller passes it, so widening this array is the one and only place that has to change
for the new counts to survive onto the record.

**Where the fields are forwarded** — `DocumentPreviewMount.js`'s `recordAutoInsertOutcome` (`:44-51`), gated on the
`nothing-eligible` code specifically so every other outcome's field shape is unchanged (no `key: undefined` noise,
since `recordDecision`'s `hasOwnProperty` check would otherwise write `undefined` into the record for outcomes that
never set these fields):
```js
function recordAutoInsertOutcome(result) {
  if (!result) return;
  const outcome = autoInsertDecisionOutcome(result);
  const fields = result.ok
    ? { count: typeof result.count === "number" ? result.count : 0 }
    : { reason: result.reason || "", code: result.code || "unknown-refusal" };
  if (result.code === "nothing-eligible") {
    fields.articleCount = typeof result.articleCount === "number" ? result.articleCount : 0;
    fields.droppedNoUrl = typeof result.droppedNoUrl === "number" ? result.droppedNoUrl : 0;
    fields.droppedNoSuggestion = typeof result.droppedNoSuggestion === "number" ? result.droppedNoSuggestion : 0;
    fields.droppedRemoved = typeof result.droppedRemoved === "number" ? result.droppedRemoved : 0;
    fields.droppedRemovedAlsoAccepted = typeof result.droppedRemovedAlsoAccepted === "number" ? result.droppedRemovedAlsoAccepted : 0;
  }
  recordDecision(AUTO_INSERT_DECISION_ID, outcome, fields);
}
```
**Result**: the next `nothing-eligible` line in a downloaded activity log reads, e.g.,
`fact-auto-insert.skipped reason:"No eligible facts to insert." code:nothing-eligible articleCount:3 droppedNoUrl:0
droppedNoSuggestion:0 droppedRemoved:3 droppedRemovedAlsoAccepted:1` — which by itself proves (a) research was not
empty, (b) every article was excluded specifically as "removed," not for missing url/suggestion, and (c) at least
one of those "removed" articles is simultaneously sitting in the accepted facts for this application, which is only
possible if the accept path failed to clear it. That last field turns "we suspect the accept-never-clears bug" into
"the log states it happened," with no further diagnostic session required.

## Spec 2 — the fix

**Scope**: `acceptFacts` only (`useCompanyResearch.js`). No change to `autoInsertFactsForJob`'s eligibility filter,
no change to `removeInsertedFact`, no change to the server/RPC — all of which are already correct for what they are
responsible for (see section 1's conclusion on auto-insert, and the standing "a genuinely removed fact must not
silently return" rule, which this fix must not weaken for any path OTHER than an explicit accept).

**Change**: at `useCompanyResearch.js:445`, replace the pass-through read of the removed log with one that drops
any entry the current click is explicitly (re-)accepting:

```js
const priorRemoved = acceptedFactsByJob[jobId]?.removed || [];
// An explicit accept is the candidate asking for this fact -- that request
// overrides a prior removal of the SAME fact (never a removal of anything
// else). Un-declining is scoped to exactly the keys this click is
// accepting; every other entry in the removed log is left untouched, so a
// fact the candidate has not touched stays suppressed exactly as before.
const acceptedKeys = new Set(facts.flatMap((f) => [f?.url, f?.id]).filter(Boolean));
const declinedUrls = priorRemoved.filter((key) => !acceptedKeys.has(key));
```

`facts` (bound at `:438`, `Array.isArray(selection?.facts) ? selection.facts : []`) already carries `.url` and
`.id` for every card the dialog can produce — confirmed at `CompanyResearchDialog.js:130-138`
(`acceptSelection()` maps `chosen()` to `{ id: c.id, text: c.suggestion, url: c.url, title: c.title, source: c.source,
placement: c.target, textOrigin: "template" }`) — so no new plumbing is needed to reach the keys at the point
`declinedUrls` is built. `removedKey` at `:677` in `removeInsertedFact` stores `record.url || record.id`, so
checking both `f.url` and `f.id` in `acceptedKeys` matches whichever form was actually stored, symmetrically.

Everything downstream of `:445` (`mergedFacts`, the PUT body, `setAcceptedFactsByJob`) is unchanged — `declinedUrls`
is already threaded through to the PUT body at `:528` and to the reconciled local state at `:576-579`; the fix only
changes the VALUE assigned at `:445`, nothing about how it is used afterward.

**Why this is the smallest correct change, and not a broader one**:
- It does not touch `autoInsertFactsForJob`'s eligibility filter, so an article still in the removed log is still
  correctly excluded from an *unrequested* auto-insert — the "genuinely removed fact must not silently return"
  rule stays intact for every path except an explicit accept, which is exactly the brief's own stated distinction.
- It does not touch `removeInsertedFact` — removal still works exactly as today; only the accept side gains the
  ability to reverse it.
- It clears ONLY the keys in this click's `facts`, never the whole removed log — so accepting fact A while fact B
  is separately still removed does not resurrect B. (Contrast with naively resetting `declinedUrls: []` on every
  accept, which the `:440-444` comment already explains was rejected for exactly this reason — wiping unrelated
  retractions.)
- It requires no server/RPC change: the RPC already replaces `retracted` with whatever `p_removed` the client sends
  (`20260923030000_application_accepted_facts.sql:256`), so a client that sends the correct, already-filtered array
  is sufficient.

**Interaction to verify once implemented** (worth stating so a future TDD round tests the right seam): after this
fix, re-accepting a previously-removed fact clears it from `removed`. If the candidate then triggers ANOTHER fresh
tailor + research on the same application and the article resurfaces, `autoInsertFactsForJob`'s eligibility filter
will no longer drop it as "removed" — but `planCoverFacts`'s own id+text "already present" guard
(`factInsertion.js:166`) will still correctly treat it as already-inserted (it is now back in `facts`), yielding
`nothing-new`, not `nothing-eligible` and not a duplicate insertion. That is the correct end state: an un-declined,
already-accepted fact is neither wrongly reported as removed nor duplicated.

- The exact user actions between cycle 1 and cycle 2 (whether a manual re-accept was attempted, whether a page

- Whether `hashString` (used by `mintArticleId`) could ever collide for two genuinely different normalized urls —

## Proposed ledger lines

1. **CONFIRMED**: `acceptFacts` (`useCompanyResearch.js:445`, `declinedUrls = acceptedFactsByJob[jobId]?.removed ||

   removes an entry from the removed log. Evidence: read of `:434-592` in full: no filter/subtraction against
   `declinedUrls` anywhere in the function.
2. **CONFIRMED**: `autoInsertFactsForJob` (`:910`, `declinedUrls: removedLog`) also resends the removed log
   unchanged, but this is not a defect for that path — its own eligibility filter (`:845-850`) already excludes
   anything in the removed set before it is ever inserted, so the set it echoes back and the set it just inserted
   are disjoint by construction. Evidence: `removedSet.has(a.url) || removedSet.has(a.id)` gate precedes the
   `facts`/`plan` construction at `:855-865`.
3. **CONFIRMED**: the server has no compensating logic — `route.js:69` forwards `declinedUrls` verbatim, and the
   RPC does a straight replace (`retracted = coalesce(p_removed, '[]'::jsonb)`,
   `20260923030000_application_accepted_facts.sql:256`). Evidence: migration text quoted above.
4. **CONFIRMED, reachable via shipped UI**: `CompanyResearchDialog.js` never filters its card list against the

   `CompanyResearchDialog.js:117-140`; `useCompanyResearch.js:679` (removal strips the id from `facts`),

5. **CONFIRMED not the cause**: minted-id volatility. `mintArticleId` (`:168-172`) derives a deterministic,

7. **SPEC (logging)**: add `articleCount`, `droppedNoUrl`, `droppedNoSuggestion`, `droppedRemoved`,
   `droppedRemovedAlsoAccepted` (all plain counts, no content) to the `nothing-eligible` return of
