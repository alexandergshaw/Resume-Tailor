## 2. THE gated-regenerate seam (AC-1 — the safety-critical structure)

**Thesis (rule 4 — make the wrong thing impossible, not merely absent).** The submittable text the user can download/send must be the **gate's `kept` output**, so a fabricated or unsupported span has **no route to a plain bullet**. The only existing unit that guarantees "emitted text = `recomposeFromSpans(layout, kept)` and nothing else" is `runIdealPipeline` (`idealPipeline.js:141`, and the K2 safety note at `:12-20`: "Nothing downstream of the engine reads `applicationReadyCandidate.result` again"). N104's regenerate therefore **routes its submittable output through `runIdealPipeline`**, not through a hand-rolled gate call and not through the standard route.

```
regenerateToAddress({ engine, args, realMaterial, beforeReview })  ->  RegenerateOutcome
```

**Input contract:**

| Field | Type | Meaning |
|---|---|---|
| `engine` | resolved engine | must be Ideal-capable (gemini); non-gemini is refused upstream by `gateIdealRequest` (reuse, §7) |
| `args` | the Ideal `args` (`route.js:427-434` shape) | `jobPosting`, `resumeText`, `templateLines`, etc. — SAME posting the summary reviewed (comparability, §5) |
| `realMaterial` | `{spans, chronology}` | from `buildIdealRealMaterial(args.resumeText)` — the same corpus the gate judges against |
| `beforeReview` | `ReviewOutcome` | the pre-regenerate review of what currently ships (the summary's review); its **resolvable** set (§8) becomes `weaknessSteering` AND the "before" side of the closure delta |

**Behaviour (fixed order):**
1. `{ resolvable, genuinelyUnqualified } = classifyWeaknesses(beforeReview)` (§8). `weaknessSteering` is built from **`resolvable` only** (AC-2: the regenerate never targets a genuinely-unqualified gap).
2. `out = await runIdealPipeline({ engine, args: { ...args, weaknessSteering }, realMaterial })`. **This is the only generation call; it is the gated path.** The emitted `out.result`/`out.resultLines` is `recomposeFromSpans(kept)` by construction (F-C5). `out.ideal.review` is the after-review, computed over the KEPT spans (`idealPipeline.js:173-180`) — i.e. over exactly the lines that ship.
3. `closure = compareReviewGaps({ before: beforeReview, after: out.ideal.review, resolvable })` (§5).
4. Return `{ regenerated: out, closure, genuinelyUnqualified }`.

**Output contract — `RegenerateOutcome`:**
```
{ regenerated: <runIdealPipeline output>,   // gated application-ready + hypothetical + removed/leftOut + review
  closure: { closed, stillOpen, counts },   // AC-4 before/after
  genuinelyUnqualified }                     // AC-2 still-open, reported "your materials don't support this"
```

**Why AC-1 Mutant B is structurally impossible in this seam:** `regenerateToAddress` imports `runIdealPipeline` and **never** imports `activeEngine.tailorResume`, `resubmitDocumentPreview`, or `/api/tailor`'s standard branch. The modal wires the regenerate control to this seam's client action, not to `preview.resubmitDocumentPreview` (which stays nulled for Ideal jobs, F-C7). **Diff-check (load-bearing):** grep `regenerateToAddress.js` + the modal's regenerate handler for `tailorResume|resubmitDocumentPreview|resubmitDocument` → must be **0** (canary: the same grep over `route.js` returns `:472`). grep `regenerateToAddress.js` for `runIdealPipeline` → must be **1**.

**Why AC-1 Mutant A (fabrication) is impossible:** the presented submittable text is `out.result` = kept spans only; a fabricated bullet the engine wrote is `dropped` (→ `out.ideal.leftOut`) or `flagged` (→ `out.ideal.removed`, carrying `UNVERIFIED_FLAG`) by the gate at `idealPipeline.js:136-160`, so it never appears as a plain bullet. **Diff-check:** the WeaknessSummaryPanel renders the submittable document from `regenerated.resultLines` (never from any candidate/raw field); grep the panel for `applicationReadyCandidate|candidate.result|chain.` → 0.

## 3. Standard-vs-Ideal scope — the real fork (recommendation + owner fork)

**The question (brief item 3).** For a STANDARD (level 1-5) job, does N104's regenerate (a) always route through the gate so the regenerated output becomes gated application-ready text, (b) apply only to Ideal jobs, or (c) gate standard-engine output in a new seam?

**Key structural fact that collapses most of the fork:** the regenerate needs an engine that can produce a *gate-cleanable truthful reframe*. Per F-C6/AC-5 that is **gemini only** — `external` never receives résumé text (cannot ground), `embedded` has no LLM reframe. So regardless of the job's original tailoring level, the regenerate is a **gemini Ideal-path** operation. A standard job tailored on embedded/external must switch to gemini or be refused — which is exactly what `gateIdealRequest` already does (`idealBranch.js:56-77`). Reuse it; do not re-derive the refusal.

**Recommendation: option (a) — the regenerate ALWAYS produces gated output by re-entering `runIdealPipeline`.** A standard job's regenerate yields a gated, Ideal-shaped application-ready result (kept/removed/leftOut + re-review). This is the AC-named safe default (AC §1 safety thesis; AC-1 "re-enters the gated path, never the standard ungated route") and it makes the F-C7 hazard **unreachable**: the regenerate output *is* gated text, so there is no ungated-replacement path to protect against.

**What changes under each:**

- **(a) always gated via `runIdealPipeline` — RECOMMENDED.** Any job's regenerate = a gated Ideal output. Zero new gate/recompose/reconcile code (full reuse). Download handling is inherited (the Ideal path already builds bytes from recomposed `resultLines`; `idealPipeline.js:17-20`, and matches the `download-rebuild-formatting` rule). Cost: a standard job *gains* the denser Ideal surface (hypothetical tab + removed/leftOut bands) after a regenerate — a real surface shift. Engine: gemini required; else honest refusal.
- **(b) Ideal-jobs-only.** The regenerate control appears only when `idealSurface` is present; standard jobs get the weakness SUMMARY but no regenerate. Smallest blast radius and modal-density impact. **But it denies the single biggest differentiator (truthful regenerate) to level 1-5 jobs — the majority** — and AC-9 names the truthful regenerate as *the* app-vs-chat advantage. Materially narrows scope.
- **(c) gate standard output in a NEW seam** (tailorResume-with-steering → `decomposeToSpans` → `applicationReadyGate` → recompose). Rejected: it **reimplements the pipeline's internals outside the one audited unit** — it would have to re-do chronology reconciliation (`reconcileChronology`, `idealPipeline.js:137`) and the `recomposeFromSpans(kept)` discipline, and a future edit could let the two gate-wirings drift (e.g. a skipped chronology reconcile → an invented-employer line ships). This is precisely the "wrong thing becomes POSSIBLE" structure rule 4 forbids. The AC-3(b) census permits reusing the *same* gate but a second composition path is a standing hazard. Do not build.

**OWNER FORK (materially changes scope): (a) vs (b).** Option (a) upgrades standard jobs to a gated Ideal-shaped output on regenerate (broad reach, denser modal, gemini-gated); option (b) keeps the regenerate to jobs that already ran Ideal (narrow, simplest). Both satisfy AC-1 (neither uses the ungated route; (b) simply offers the control less often). This seat recommends **(a)**; the owner may choose (b) to bound modal density and keep level 1-5 output simple. **This fork does not re-open any AC criterion** — the no-fabrication invariant and refusal direction hold under either.

## 5. The before/after re-review comparison seam (AC-4 — closure never claimed blind)

```
compareReviewGaps({ before, after, resolvable })  ->  ClosureReport
```

- `before` / `after` are `ReviewOutcome`-shaped (flags + unresolvedQualifications). `after` comes from the regenerate's `runIdealPipeline` run (`out.ideal.review`), computed over the KEPT spans (what ships) — so closure is measured against the shipped document, never the raw engine draft.
- `resolvable` is the pre-regenerate resolvable set (§8) — the **named** addressable weaknesses whose closure is being measured.

**Gap identity — the load-bearing contract.** Flags split into two identity classes:
- **Posting-anchored (`missing-keyword`):** identity = `(category, evidenceRef.origin, evidenceRef.spanId, message)`. `evidenceRef.spanId` is the **requirement id** (`mechanicalDetectors.js:198`), and `message` names the exact keyword term + requirement text (`:197`) — both are **independent of the draft's spans**, so the same gap produces the same key across regenerations. `closed` = the key present in `before.resolvable` and **absent** from `after.flags`. `stillOpen` = present in both.
- **Draft-anchored (`vague-unsupported`, `repetition`):** these point at a specific draft line (`flag.spanId` is a draft span), and a regenerated draft has **different lines**, so a specific-line "fixed" claim is unsound. For these the report gives a **count delta per category** (fewer vague/repetition flags), never a per-line "closed." This prevents a false "closed" when a vague line was merely rewritten into a different vague line.

**Output — `ClosureReport`:**
```
{ closed:  [{ category, requirementId, label }],       // posting-anchored, keyed identity gone
  stillOpen: [{ category, requirementId, label }],     // posting-anchored, persists
  countsBefore / countsAfter: { missingKeyword, vague, repetition },  // category deltas (draft-anchored honesty)
  genuinelyUnqualifiedStillOpen: [...] }               // pass-through from after.unresolvedQualifications
```

**Comparability constraint (checkable):** `before` and `after` MUST be computed over the **same posting requirements and the same real material**, else a "closed" claim is not sound. The regenerate re-grounds the posting from `args.jobPosting` (`idealPipeline.js:162-165`); the summary must have reviewed the **same** posting text. Requirement ids are stable when grounded from the same text — the checker should canary that `before` and `after` requirement ids overlap before trusting a "closed" row. The AC-4 "blind closure" mutant (same/unimproved draft) is caught because the identity key persists in `after.flags` ⇒ reported `stillOpen`, not closed.

## 6. The feedback channel (I2) — `weaknessSteering` contract

No `tailor*`/`tailorIdeal` method accepts feedback today (F-C6), so one optional field is added, threaded Ideal-path only:

- **Shape:** `weaknessSteering?: { resolvable: [{ category, text }] }` — a list of **resolvable gaps as emphasis guidance**, built from `classifyWeaknesses(...).resolvable` (AC-2: resolvable set only, never genuinely-unqualified).
- **Where it enters:** `route.js:427-434` args → `tailorIdeal(args)` → `runIdealChain(options)` → `buildApplicationReadyPrompt`/`buildHypotheticalPrompt` (`idealChainPrompts.js:160,130`), rendered as a **distinct block framed "emphasis guidance — surface these supported-but-under-weighted points more prominently; NOT new facts; introduce no number/scope/tool/authority the source lacks"** (mirroring the existing non-negotiable truthfulness rules at `idealChainPrompts.js:175-189`).
- **Why it is safe even if mis-worded (rule 4):** the gate runs **downstream** of whatever the engine returns (`idealPipeline.js:136`). `weaknessSteering` can only influence *which truthful content* the engine emphasises; any span it induces that the real material does not support is `dropped`/`flagged` before presentation. - **Bounded:** absent `weaknessSteering` ⇒ the Ideal path behaves exactly as today (AC-8 non-regression). It is additive-optional on every call.

## 8. Resolvable vs genuinely-unqualified (AC-2) — `classifyWeaknesses` contract

```
classifyWeaknesses(reviewOutcome) -> { resolvable: Flag[], genuinelyUnqualified: Entry[] }
```
Pure function of the `ReviewOutcome` (no analyzer, no gate). Rules, derived entirely from reviewer output (F-C2):
- `unqualifiedReqIds = new Set(reviewOutcome.unresolvedQualifications.map(u => u.requirementId))`.
- **resolvable** =
  - every `missing-keyword` flag whose `evidenceRef.spanId` (requirement id) is **NOT** in `unqualifiedReqIds` (the requirement is supported by real material; the draft merely omitted the keyword), PLUS
  - every `vague-unsupported` and `repetition` flag (draft-internal phrasing problems — addressable by rewording).
- **genuinelyUnqualified** = `reviewOutcome.unresolvedQualifications` (the posting wants X; the materials don't support it). A `missing-keyword` flag whose requirement id **IS** in `unqualifiedReqIds` is folded into the unqualified presentation, not listed as resolvable (avoids double-listing and, critically, keeps it out of `weaknessSteering`).

**Invariant (AC-2 safety):** only `resolvable` feeds the regenerate; `genuinelyUnqualified` is always reported open after a regenerate (it is pass-through from `after.unresolvedQualifications` in `compareReviewGaps`), and — defense-in-depth — even if a mislabel fed an unqualified gap to the engine, the gate (AC-1) drops the unsupported span. **Failable-row requirement (AC-2/AC-7):** the test fixture must carry ≥1 resolvable AND ≥1 genuinely-unqualified gap (both > 0) or the separation has no power. The `examplePair.js` corpus supplies both: `merchant onboarding`/`PCI compliance` keywords sit in real material shapes (resolvable candidates), while the invented `Terraform`/`Five years of Terraform and Go` requirement (`examplePair.js:83,91`) is genuinely-unqualified.

## 10. Data flow (one safety-critical path)

```
SUMMARY (offline, no key):
  modal/chat builds request -> runDocumentReview(request)  [or reuse idealSurface.ideal.review]
    -> ReviewOutcome -> classifyWeaknesses -> { resolvable, genuinelyUnqualified }
    -> WeaknessSummaryPanel (clean/partial keyed on verdictKind)

REGENERATE (gemini only; the ONE gated path):
  client regenerate action
    -> gateIdealRequest(...)                      [refuse external/embedded, zero artifact]
    -> regenerateToAddress({ engine, args:{...,weaknessSteering(resolvable)}, realMaterial, beforeReview })
         -> runIdealPipeline(...)                 [decompose -> applicationReadyGate -> reconcileChronology
                                                   -> recomposeFromSpans(KEPT) -> reviewDocuments(after)]
         -> compareReviewGaps({ before, after:out.ideal.review, resolvable })
    -> RegenerateOutcome { regenerated(gated), closure, genuinelyUnqualified }
    -> WeaknessSummaryPanel renders submittable doc from regenerated.resultLines (KEPT only)
       + closed/still-open (closure) + genuinely-unqualified-still-open
```

The submittable bytes are built from `regenerated.resultLines` (= kept spans). A `dropped`/`flagged` span is never on this path to a plain bullet (AC-1). The ungated `tailorResume` route is never called by any regenerate step (AC-1 Mutant B / AC-8).
