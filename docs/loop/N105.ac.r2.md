### AC-3 (SAFETY) — The hypothetical's FILENAME carries a "HYPOTHETICAL" marker on EVERY file egress, PER CALL-SITE; the UI marks it (OD-4)
The hypothetical output is distinguished by **two markers only** (OD-4 — there is NO content/bytes label): **(a)** every file egress of the hypothetical produces a **filename containing the token `HYPOTHETICAL`** (case per 1b), and **(b)** the UI presenting the hypothetical shows a visible HYPOTHETICAL marker. There is **NO path** by which the hypothetical's FILE leaves the app under a name lacking the marker.
- **Enumerated egresses that MUST carry the filename marker (A2/F5):** `downloadDocxFiles` (docx.js:725), `downloadAutoTailoredResume` (docx.js:809), `downloadResumeForChipJob` (docx.js:842), the Drive save (useDriveDocuments), and **copy-filename** (`resolveActiveDocumentTitle`, documentScopes.js:119-121). Any additional file egress 1b introduces inherits the same obligation.
- **Paths with NO filename of their own MUST REFUSE the hypothetical** (because the marker lives only in the filename/UI, a markerless combined/adopted artifact would carry fabricated content with no warning): **set-as-default-template** and **combine-into-another-document** must not accept the hypothetical as input. The exact routing/refusal mechanism is a **1b input** (§5-I3); this AC fixes the invariant (no markerless submittable artifact derivable from the hypothetical).
- **Preferred structural form (rule 4 — make the wrong thing hard):** mint the `HYPOTHETICAL` token into the hypothetical's **canonical title/filename at generation**, so every downstream egress that reads that title inherits it, rather than each egress re-adding it. 1b picks; this AC fixes the invariant.
- **Instrument (NEW):**
  - **(a) BEHAVIORAL, per call-site:** produce the hypothetical; drive EACH enumerated egress (each of docx.js:725/809/842, Drive, copy-filename) through its real filename resolution; assert the resolved filename contains `HYPOTHETICAL` at each one separately.
  - **(b) MUTANT CONTROL, per call-site:** a mutant that drops the marker on **ONE** egress (e.g. one download path derives its own name ignoring the marked title — the N83-F1 "download derives default" shape) must turn that egress's assertion RED while the others stay green.
  - **(c) CENSUS — PER CALL-SITE, NOT whole-file:** because all three download egresses are co-located in `docx.js` (A2), a whole-file regex is a PROVEN false-clean (A3 — N101 G1: a single-site mutant survives all tests). The census MUST assert the marker near EACH named egress function, or be a behavioral per-call-site test (adopt the N101 G1/G2 fix, not the pre-N101 `defaultTemplateEgress.census.test.js` model). Keep that file's instrument canary.
  - **(d) UI:** assert the hypothetical's presentation renders a visible HYPOTHETICAL marker (jsdom-renderable per [[measurement-instruments]]).
- **RED on HEAD:** yes — no hypothetical, no filename marker, no UI marker (F6).
- **Failure direction (load-bearing):** the hypothetical's file leaving under a name lacking `HYPOTHETICAL` (so it is indistinguishable from a submittable résumé) is the exact failure; over-marking is safe. A whole-file census that greens while one call-site drops the marker is the N101 trap this AC must not re-inherit.

### AC-4 (SAFETY) — Application-ready carries ONLY truthful, SUPPORTED claims (defined), fail-closed, AND retains supported content (liveness)
Every claim in the application-ready résumé (each **bullet-sized span**, the app mints ids) must satisfy **two rules**, evaluated against **exactly one** source span (never a union, never a document — [[loop-traps-spec]]):
1. **SUPPORT (defined, per F-3 fix; modeled on AC-10's title rule):** a claim is SUPPORTED by exactly ONE span of the user's OWN real material iff **every FACTUAL TOKEN in the claim traces to that one span** — each quantity/metric, each named entity (employer/tool/scope), and each authority/seniority/leadership assertion. **Rewording or strengthening phrasing that introduces NO new factual token is PERMITTED** (this is the spec's step-5 "aggressive-but-truthful reframe"). A reframe that introduces a new number, a new scope, or a new authority/seniority claim absent from the span is NOT supported. (This makes the gate neither literal-substring over-tight nor "semantically consistent" zero-power.)
2. **MEMBERSHIP / ELIGIBILITY:** that source span must belong to the context the claim appears in — a metric/accomplishment/skill under employer/project/role X must trace to the user's real material *about X*. A real metric from employer A may NOT support a bullet under employer B.
A claim satisfying neither is **dropped, or surfaced under an explicit `unverified — confirm before use` flag — never emitted as a plain truthful bullet.** This gate applies to whatever the engine produces.
**LIVENESS (NEW, per F-4 fix) — grounded-or-dropped must NOT degrade to drop-everything:** at least one SUPPORTED claim present in the user's real material about employer/project X **MUST be RETAINED** under X in the application-ready output. A degenerate impl emitting only the AC-10 chronology skeleton with zero accomplishments FAILS this.
- **Instrument (NEW) — four fixture rows built so support/membership provably cannot collapse into one span:**
  - **(i) MUST-DROP (fabrication):** the hypothetical contains a fabricated accomplishment absent from the user's real material (e.g. "scaled to 10M users") → assert absent from, or flagged in, the application-ready output.
  - **(ii) MUST-DROP (membership):** a real metric under employer A is NOT emitted under employer B.
  - **(iii) MUST-SURVIVE (truthful reframe):** a legitimate reframe of a real claim that introduces NO new factual token (e.g. source "helped reduce support tickets" → "cut support-ticket volume") MUST PASS the gate and appear in the application-ready output — so step-5 output is not unreachable.
  - **(iv) MUST-KEEP (liveness):** a supported accomplishment from the user's real material about X MUST appear under X.
  - Report the fixture's **failable-row count** (claims that could fail the gate — guards against zero-power) AND **keepable-row count** (supported claims that must be retained — guards against drop-everything). Both > 0.
- **RED on HEAD:** yes — no application-ready output, no support relation, no liveness assertion exist.
- **Failure direction (load-bearing):** emitting an unsupported claim as truthful is the worst outcome (fail closed — if in doubt, drop). But a fail-closed gate with no liveness is the escape hatch F-4 names; the MUST-KEEP row closes it. Both directions are pinned.

### AC-5 (SAFETY) — Step-6 reviewer flags authority (reference split PER DRAFT) + unverifiable metrics on BOTH drafts
The step-6 reviewer (the OD-3 shared dependency, consumed per AC-6) runs over **both** drafts and flags: missing keywords, vague/unsupported claims, repetition, **unverifiable/ambiguous metrics**, employer/domain plausibility, and **consistency** across dates/titles/seniority/leadership (including between the two drafts where they reference the same real fact). It also emits the list of posting requirements **wording alone cannot resolve** (genuine qualification gaps, distinct from phrasing gaps).
**Authority reference is SPLIT PER DRAFT (per F-2 fix — "not in user material" is degenerate on the hypothetical, which by design EXCEEDS user material):**
- **Application-ready** → **unsupported authority = claimed seniority/leadership/scope not evidenced in the user's REAL material.**
- **Hypothetical** → **authority is checked against posting-plausibility + INTERNAL CONSISTENCY** (dates/titles/seniority/leadership coherence WITHIN the hypothetical), **NOT against the user's material.** A strong-but-coherent hypothetical authority claim is legitimate; an internally-incoherent one (e.g. "CTO leading 200 engineers" over a chronology showing 3 years / associate-level dates) is flagged.
The **unverifiable-metric half applies to BOTH drafts** (verifiability is draft-internal).
- **Instrument (NEW):** use **held-out drafts** (not authored from the reviewer's own template/rules — avoids the self-authored-corpus zero-power trap, [[loop-traps-spec]]):
  - Application-ready draft with a planted unsupported-authority claim ("Directed a 50-person org" with no such real role) → flagged; a clean application-ready control → no false flags.
  - Hypothetical draft with a planted INTERNALLY-INCONSISTENT authority claim → flagged; a **strong but internally-coherent** hypothetical control → **no false flags** (this control is now satisfiable, which it was not under r1's user-material reference).
  - A planted unverifiable metric ("+300% revenue", no source) → flagged on BOTH drafts.
- **RED on HEAD:** yes — no document reviewer consumed (F8); N105 step-6 unwired.
- **Failure direction:** silently passing an unsupported-authority or unverifiable-metric claim is the failure; over-flagging is safe. On the hypothetical, flagging legitimate ambition as "unsupported" (the r1 degeneracy) is ALSO a failure the coherent-control assertion now guards against.
