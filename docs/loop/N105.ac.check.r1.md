## Findings

### F-1 (major) — AC-3's census leg is modeled on a KNOWN call-site-blind instrument; its three export targets are co-located in one file
AC-3 instrument (c) specs the forward-looking backstop census "modeled on `lib/document/defaultTemplateEgress.census.test.js`". That model's discriminator is a **whole-file regex**: `const hasParam = (relPath) => /\bformattingTemplate\b/.test(code(relPath))` (census file :31). **Backlog N105-neighbour N101 (BACKLOG.md:172, still open) documents this exact instrument as a proven false-clean** (G1/G2: a mutant dropping ONE call site's param in a file survives because another site in the same file satisfies the regex). The three N105 export entry points (`downloadDocxFiles`/`downloadAutoTailoredResume`/`downloadResumeForChipJob`) are **all in `lib/document/docx.js`** — so a file-level label census over that file is satisfied by any one of them, blind to a sibling that drops the label. This is the forward-looking leg that is supposed to catch exactly the N64/N101 "wires one surface, misses another" class on the single highest-severity safety AC.
- Mitigation that keeps this major rather than blocker: AC-3's behavioral leg (a) ("drive EACH export/copy path, assert the label in bytes") and the preferred choke-point structural form (inject at generation, preserve at docx.js:653) give real per-path power today. The weakness is strictly in the leg meant to police NEW/forgotten paths.
- Fix direction: AC-3 must require the census to assert the label token **per call-site** (near each named export function), not whole-file presence — i.e. adopt the N101 G1/G2 fix, not the pre-N101 model. Cite N101 so the next seat does not re-inherit it.

### F-2 (major) — AC-5 defines "unsupported authority" against the user's real material but applies it to the HYPOTHETICAL draft, where that predicate is degenerate
AC-5 defines unsupported authority as "claimed seniority/leadership/scope **not evidenced in the user's real material**" and then requires it "flagged on BOTH drafts" with a "clean control draft produces no false flags" sub-assertion. But the hypothetical is BY DESIGN "the strongest plausible candidate, NOT limited to the user's actual experience" (N105 card / AC §Feature). Against the user's-material reference, **essentially every authority claim in the hypothetical is "unsupported"** — the planted "Directed a 50-person org" is indistinguishable from the legitimate hypothetical content, and a genuinely clean hypothetical still trips the flag, so the "clean control → no false flags" assertion is **unsatisfiable on the hypothetical side**. The reviewer's authority check needs a DIFFERENT reference per draft: user-material membership for the application-ready; posting/market plausibility + internal consistency + verifiability for the hypothetical (which is what the spec's separate "employer/domain plausibility" item is for). As written, the hypothetical-side authority instrument is zero-power / self-contradictory.
- Note: the unverifiable-metric half ("+300% revenue, no source") IS meaningful on both drafts (verifiability is draft-internal), so only the authority half breaks.
- Fix direction: split AC-5's authority predicate by draft, or restate "unsupported authority" on the hypothetical as implausible/internally-inconsistent authority rather than not-in-user-material, and fix the control assertion accordingly.

### F-3 (major) — AC-4's SUPPORT predicate ("the claim is contained in ONE span") is undefined for the step-5 "aggressive-but-truthful reframe" the spec mandates
AC-4 requires every application-ready claim be "contained in ONE span of the user's OWN real material … evaluated against exactly one source span." Step 5 of the owner spec is an "application-ready **aggressive-but-truthful reframe**" — reworded/strengthened phrasing that will frequently NOT be literally contained in any single source span. The AC leaves "contained in / supported by" undefined, so it resolves two bad ways: (a) literal substring/containment → truthful reframes fail the gate and get dropped, making the feature's own step-5 output unreachable (over-strict); or (b) a loose "semantically consistent with" reading applied without definition → the gate loses power and a fabrication can pass as "consistent." The most safety-critical gate must not rest on an undefined support relation. AC-10 already set the pattern by defining the allowed transform for titles ("truthful standard equivalents"); AC-4 needs the equivalent for claims/metrics/skills.
- Fix direction: define the support relation (e.g. every quantitative/authority token in the claim must trace to the one source span; rewording that introduces no new fact is permitted), and make the contamination fixtures include a truthful-reframe row that MUST survive, not only a fabrication row that must drop.

### F-4 (major) — No AC mandates that a SUPPORTED claim is RETAINED: the truthfulness gate is fail-closed with no liveness
AC-4 is explicitly fail-closed ("if in doubt, drop"), which is correct for safety but leaves a hole: **nothing asserts the application-ready output keeps genuine supported content.** A degenerate implementation that emits the real chronology skeleton (names/employers/dates — pinned by AC-10) with ZERO accomplishment bullets passes AC-4 (no claim violates), AC-10 (skeleton exact), and AC-14 (whose demonstrated chain item is "grounded-**or-dropped**", so the dropped branch satisfies it and the mandatory adversarial element is itself a drop). AC-17 cannot catch it (N105 is net-new, nothing to regress). Result: the feature could go fully green while producing a useless bare résumé. A fail-closed gate with no companion liveness assertion is a standard zero-value escape hatch.
- Fix direction: add a positive "kept-row" assertion — AC-14's fixture (or AC-4) must require at least one SUPPORTED claim from the user's real material about employer/project X to be RETAINED under X in the application-ready output (a must-keep, distinct from the must-drop fabrication), with its own failable count.

### F-5 (minor) — AC-3 mis-attributes the `engine.js:330` injection hint to F5, and that point is embedded-only
AC-3's "Preferred structural form" cites "the label is injected at generation (`serializeDocx`, engine.js:330, **F5**)". The ref itself is real — `tailor-lite/engine.js:330` is `docxB64: await serializeDocx(proposal.doc)` — but (a) it is in **F7/F4 territory (serializeDocx = docxModel.js:375), not F5** (F5 is resolveDocumentBlobBytes/docx.js:653), and (b) engine.js:330 is the **embedded** engine's serialize point, while per OD-2 embedded may not even produce the hypothetical (gemini/external are the supporting engines, which serialize elsewhere). Pointing design at the embedded serialize line as THE generation-time injection site is misleading. Non-binding (AC says "1b picks; this AC fixes the invariant"), hence minor.
- Fix direction: drop the specific engine.js:330 cite or relabel it as "the embedded path's serialize point, one of several per-engine"; the invariant (label in bytes, preserved at docx.js:653) is what binds.

### F-6 (minor) — AC-2's fail-honest instrument is falsifiable only under OD-2(a) refuse
AC-2's non-negotiable is "embedded must NEVER emit a level-5 fill relabeled as the two-output result." Under OD-2(a) (honest refusal, no artifact) this is cleanly checkable (assert refusal shape, zero output). Under OD-2(b) (a "deliberately reduced, clearly-scoped hypothetical") embedded DOES emit output, and the AC supplies **no instrument to distinguish a legitimate reduced hypothetical from a relabeled level-5 fill** — both are deterministic template fills (F4). The distinction becomes unfalsifiable exactly where it matters. AC acknowledges OD-2 is an open owner call (BL-1), so this is a dependency to resolve, not a defect in isolation — minor.
- Fix direction: if the owner picks (b), AC-2 must name the observable that separates the reduced hypothetical from a level-5 relabel (e.g. the reduced output must itself carry AC-3's label AND must NOT be routed to the application-ready output at all), or (a) should be preferred.

### F-7 (minor / cosmetic) — binding-source label and a step-8 scope narrowing
- The AC header names the binding source `docs/backlog.yml`; the checker brief names `docs/BACKLOG.md`. Both files carry byte-identical N105 card text (verified), so there is no fidelity loss — but the two artifacts should name one canonical source.
- Spec step 8 says "flag unresolved **nontechnical** quals"; AC-13 generalizes to all unresolved quals. This is a safe superset (surfacing more gaps), not a miss — noted only so it is not mistaken for drift later.
