## Amended criteria

### AC-N143-3 (AMENDED) — stored shape, `bullets` not `body`

The stored pool-entry shape is `{ competency, domain, title, bullets, hypothetical: true }`, where **`bullets` is a JSON array of 2–3 short strings** (not a narrative `body` string), each a discrete claim, generated and parsed **as an array** — never produced by splitting a string client-side (a split breaks on `"$1.2M"`, `"e.g."`; UX A2). Length caps are named, owner-tunable constants: `POOL_TITLE_MAX_WORDS` (~10), `POOL_BULLETS_MAX` (3), `POOL_BULLET_MAX_WORDS` (~15); an over-length or wrong-count entry is **rejected server-side, never truncated** (truncating a figure is a worse lie than dropping the entry; UX A3). No field holds a posting figure verbatim (guard-enforced, AC-15). One row per application (PK), cascade-delete.
*Instrument:* a shape test asserting `bullets` is an array of 2–3 strings within caps; a parser test that a non-array/empty/over-count/over-length `bullets` is rejected (entry dropped); the cascade shape test from r1. *Failure direction:* a `bullets` built from `string.split(...)` is a blocker. *RED on HEAD:* shape undefined (no table/parser).

### AC-N143-6 (AMENDED) — best-match selection WITH a fit threshold and a no-close-match outcome

At question time the pool entry best-matching the question is selected, **and the selection can honestly return no close match** — it must NOT force a pick when no entry fits (ORCH R3; a forced off-domain pick is the exact v1 failure). The selector returns a pick **and a fit signal**: `selectPoolProject(projects, { question }) -> { outcome: "match" | "no_match", entry, fitScore }`. The fit signal is `fitScore = overlapScore(significantTerms(question), competency+domain)` — overlap of the question's significant terms against the entry's **competency/domain tag** (not title/bullets, which as invented prose would make the threshold never bite). `outcome` is `"no_match"` (entry null) when the pool is empty/absent **or** the best `fitScore` is below a named, owner-tunable `POOL_FIT_THRESHOLD` (default 1 = at least one distinctive competency/domain term shared; below it = clearly off-domain). The selection adds **zero model calls** on the answer path for Row 1.
*Instrument:* a selector unit test — an off-domain-only pool returns `no_match`; one on-domain entry at/above threshold returns `match` with that entry; an empty pool returns `no_match`; a fixture with a clearly better-fitting entry than the one returned fails (isolates mis-selection). Plus the answer-route `generateContent`/`interactions.create` spy showing 0 added Row-1 calls, with a positive control. *Failure direction:* returning a non-null `entry` while `fitScore < POOL_FIT_THRESHOLD`, or forcing an off-domain pick, is the harm; the safe direction is an honest `no_match`. *RED on HEAD:* no selector exists. *Threshold default is a flagged owner-tunable guess, retuned via AC-N143-Q.*

The done-frame status union for Row 1 gains a **`no_match`** state (the honest "no close example" render), alongside the r1 pending/ready/failed and the NA omission (1b r2 §4.4). The not-yet-warmed and failure states (AC-8, AC-9) are unchanged.

### AC-N143-7 (AMENDED) — the per-question pick is never cached in a QUESTION-INDEPENDENT store; the question-keyed client cache is PERMITTED

The per-question pick is **never** written into a question-**independent** server cache — specifically **not** into `answerContextCache` (keyed `userId::applicationId`, the session-duration raw fan-out) and **not** into the `application_project_pool` row. It is computed fresh in the answer route per question. **It is EXPLICITLY PERMITTED to ride the client `answerCacheRef`**, which is keyed by the **normalized question**: reusing question one's pick when the same question is re-asked is correct, and this matches the existing `anchor`/`selectBestStory` precedent cached at `useDraftAnswer.js:293`. The pool itself (question-independent, app-scoped) remains cacheable/persisted. The two-questions-two-picks guard is kept: two different questions in one session must select two different picks (no stale carry of question one's pick to question two).
*Instrument:* the `route.latency.test.js`-style guard (two questions → two picks) + a static assertion the pick never enters `answerContextCache` or the pool row + a positive assertion the pick MAY be carried in `answerCacheRef` under a normalized-question key. *Failure direction:* a question-independent cache of the question-dependent pick is the "answer question two with question one's selection" hazard; the safe direction is fresh-per-question with only the question-keyed client cache reusing an exact re-ask. *RED on HEAD:* no selection/cache interaction. *Standing non-regression guard on the cache invariant.*

### AC-N143-12 (AMENDED) — FOUR surfaces, including HistoryItem

`AnswerAids.js` renders the two new rows (as a separate bottom group per ORCH R1 / UX 7.1) in **all FOUR** call sites, not three: `CurrentAnswerPanel` (`CopilotDashboard.js:452`), **`HistoryItem` (`CopilotDashboard.js:742`)**, `QuestionCard` (`QuestionFeed.js:209`), and `SampleAnswer` (`SampleAnswer.js:214`). The new data arrives as props computed server-side (Row 1 `projectExample` on the done-frame) and client-fetched (Row 2 `projectExampleLive`), preserving the component's purely-presentational contract. History entries are the actual question entry objects (no field projection in `questionConfirm.resolveConfirmedView`), so a site that forgets the props renders a silent NA indistinguishable from "feature off" with every test green — therefore each site's test must **mount the real parent and assert off the rendered examples DOM**, not a prop-forwarding assertion (UX A6; [[measurement-instruments]]).
*Instrument:* one real-parent mount test per site asserting the examples DOM; the four-site grep is the census; a static check that `AnswerAids` gained no fetch/model import. *RED on HEAD:* component takes only `{buzzwords, anchor}`; four sites render neither row.

### AC-N143-16 (AMENDED) — feature log scope: in-session prewarm + server console; pre-session failure not required in the downloadable log

The feature records three event kinds on the existing copilot `sessionLog` (prewarm requests with outcome, per-question selection decisions, on-the-spot outcomes), identity only, no raw posting/résumé/user-id. **Scope clarification:** `logEvent` is a no-op until `startLog()` runs at "Start session", so the **downloadable** log covers prewarm outcomes only for prewarms that occur **within a copilot session** (a cold pool warmed on copilot-open) plus `projectExample.shown`'s status at question time. A **tracking-time (pre-session) prewarm failure is NOT required to appear in the downloadable log** — it is a server-console event only, observable in the copilot log via `projectExample.shown`'s status at the next question. No pre-session event buffer is required in N143 (accepted gap with reason; 1b r2 §7). AC-16 does not claim the downloadable log is complete for pre-session prewarm.
*Instrument:* a log-snapshot test asserting the three kinds appear for in-session events and the excluded substrings (user id, raw posting/résumé text) do not, with a positive control; no assertion that a pre-session failure reaches the downloadable file. *RED on HEAD:* no such events logged.
