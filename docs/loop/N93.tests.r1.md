## Contract pinned (design N92.design-structure.r1.md section 3.3 "Post-apply undo (AC-B6)")

New export `undoSmoothTransition(applied, { persist })` in `lib/coverFacts/smoothTransition.js`
(the smoothing seam's own module, where every `recordDecision("fact-smooth", ...)` already lives):

- a genuinely applied ("proposed" -> confirmed) candidate: hands `persist` EXACTLY the pre-smoothing
  snapshot the candidate already carries -
  `{ lines: applied.before.lines, records: applied.before.records, edits }` where `edits` is
  `applied.after.edits` with `before`/`after` SWAPPED (so the byte-splice path re-splices the stored
  docx back to the original, not only the visible lines); then
  `recordDecision("fact-smooth", <closed outcome>, { code:"undo", ... })` (text-free, N77); `{ok:true}`.
- a null / non-"proposed" candidate: NO persist, `{ok:false}` (undo of nothing is a no-op).

UI seam: `DocumentPreviewMount` stashes the applied candidate after a successful Apply, renders an Undo
control (aria-label `"Undo the smoothing"`) on that fact's row via `InsertedFactsStrip`, and clears the
stash on any later change (move / remove / a fresh smooth) so undo can never clobber later work. The undo
persists through the same `commitSmoothedFact` -> `commitFactMove` path Apply/Move use (coverVersion PUT,
re-splice or drop-to-lines-rebuild) - so byte handling is the already-tested shared path, not a new one.

Ledger: undo reuses the existing `fact-smooth` entry (outcomes/fields unchanged), so
`decisionCoverage.sweep.test.js` needs no ledger change and stays green both ways (verified at HEAD, below).

## Honest limits / what I could not independently isolate

- **No single undo-ONLY mutant leaves stale smoothed bytes.** By design the undo delegates byte handling
  to the shared, already-tested `commitSmoothedFact`->`commitFactMove` path, which on any bad/empty edit
  set DROPS the bytes (forcing a safe lines-rebuild) rather than keeping the smoothed splice. So a
  lines-only revert leaving stale docx bytes is structurally prevented, not merely tested. The splice
  byte-read test's role is a last-hop regression guard: it is GREEN in the reference (undo genuinely
  reverts the bytes), and M-stale-bytes proves the instrument reads real bytes and bites when stale bytes
  are stored. Its own `not.toContain(SMOOTHED_FRAGMENT)` after undo is therefore proven by construction +
  M-stale, not by an undo-isolated mutant.
- **Interaction pin = invalidation (the safe direction).** Per AC-B6/design, a move (or any later change)
  after an applied smoothing WITHDRAWS the Undo affordance rather than restoring the pre-smoothing snapshot
  over the later change (which would silently clobber the move). Pinned in the UI test; "restore relative
  to current position" was rejected as unsafe.
- jsdom: MUI Dialog portals to `document.body` (queries go through `document`); asserted DOM state, PUT
  bodies, and stored docx text, never `scrollWidth`/visual layout.
