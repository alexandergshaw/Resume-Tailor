## 1. What the audit actually found (this reframes the problem)

Contrary to the "everything is broken" prior, **most surfaces already order the loading branch
before the empty branch, so on-screen empty-but-done is visually distinct from in-flight.** The
recurring, cross-cutting defects are narrower and sharper:

1. **Loading is drawn but NOT ANNOUNCED** almost everywhere (§2.1: 93 of 94 `CircularProgress`
   have no accessible name). Two surfaces already do it right and are the references.
2. **Failures on SECONDARY / background fetches are swallowed silently** — the exact
   "looks empty when it actually failed" class — on the tracking table's sub-fetches and the
   live feed's secondary fetches.
3. **Retry is missing at the failure site** on several surfaces.
4. A few **specific state bugs**: an auto-apply-queue first-mount empty *flash* and a
   co-rendered error+empty; a preview-render first-paint *blank* and an empty-model blank; a
   tracking-table refresh that discards a good table for a full-screen spinner.

## 2. Key measured facts

### 2.1 Loading is drawn, essentially never announced (verified, with canary)
Grep census (root `hello-world/app`, non-test): **94** `CircularProgress` uses; **exactly 1**
carries `aria-label` (`app/meeting/MeetingInsightList.js:156` "Finding sources"). Canary: the
same grep restricted to the labelled line returns that 1 known positive, so the instrument
sees names when present; the 93 without are a real absence. Blind spot: counts only
`CircularProgress` — `Skeleton`/`LinearProgress`/text loaders are additional un-announced
cases, so the true un-announced count is higher, not lower.

### 2.2 The activity-log seam (verified)
`recordDecision(id, outcome, fields)` (`appActivityLog.js:297`) writes the `act` channel via a
CLOSED `DECISION_LEDGER`/`DECISION_OUTCOMES` vocabulary (`activityChannels.js:213-233`);
`decisionCoverage.sweep.test.js` binds ledger↔call-sites `toEqual` both ways and requires ≥1
negative outcome. The automatic `net` channel records THAT a fetch returned a status, never
WHICH of loading/empty/failed the user ended on, and server internals are invisible to the
browser log (`activityChannels.js:82-86`). Surface H already does the right thing here:
distinct outcome + a content-free `code`, never the raw research error (which could carry the
company name or a source URL — `DocumentPreviewMount.js:62-65`).

## 3. Acceptance criteria

Written so the SAFE direction passes. A criterion's scope is "in-scope surface" = the ten rows
of §1.1 (J is inherited from N79-N80). Each names its instrument and RED-on-HEAD status.

**AC-1 — the enumeration is complete and kept honest.** §1.1 IS the required enumeration; the
design seat MUST (a) re-read every **[agent]** row it pins a test to, and (b) confirm no
in-scope background-loading surface is missing, via a canaried grep census of `await fetch(`,
busy/loading flags, and bare `catch`/`if (!res.ok) return` across `app/hooks/*` and
`app/components/*`. Instrument: the table + the census with a known-positive canary. RED on
HEAD: n/a (this is the audit deliverable itself; it is DONE for the named surfaces and is a
non-regression guard against a new un-enumerated surface).

**AC-2 — on a WAITED-ON surface, empty-but-done renders observably distinct from in-flight,
with no transient wrong state.** For every §1.1 surface the user is actively looking at
(A,B,C,D,F,G,I — not H, see AC-3 scope), the "finished, zero results" state MUST differ
observably from "still running," AND MUST NOT briefly show the wrong one during mount/refresh.
Named failing instances that MUST turn green:
  - **C first-mount flash:** `AutoApplyQueueTab.js:70` inits `loading=false`, so before the
    `setTimeout(0)` load fires, "Nothing queued yet" paints over an empty list — the surface
    looks *finished* while it is about to work. Fix: init the loading/first-load state so the
    empty copy cannot appear before the first load resolves (surface B's `loading` init true
    is the pattern).
  - **F first-paint blank + empty-model blank:** `DocumentPreviewDialog.js:538`
    (`docState[tab] || {}`) renders an empty box before `ensureLoaded` flips `loading` true;
    and an available-but-empty rendered model paints a blank doc (branch :842) with no "empty"
    message. Both look *finished/empty* while nothing has resolved or when nothing rendered.
  - **A refresh regression:** `applicationLoadedOnce` exists (`page.js:204`, its comment states
    the intent) but `TrackingTab.js:355` gates only on `applicationLoading`, so every
    `applicationsRefreshKey` bump discards a good table for the full-screen spinner. A refresh
    of a populated table MUST refresh in place, not blank to a spinner.
- Instrument: per-surface test rendering (a) fetch-pending and (b) resolved-empty and asserting
  distinct DOM, PLUS a mount/refresh test asserting the empty/blank state does not appear before
  the first load resolves. Count of failable rows = one per named instance.
- RED on HEAD: yes for C, F, A-refresh (verified for C/A; F is **[agent]**, re-read before
  pinning). The steady-state empty≠loading ordering already PASSES on A,B,C,D,F,G,I — credit it;
  do not "fix" what passes.
- Failure direction: a surface that looks *finished/empty* while still working is the harm;
  the passing state shows the loading indicator until the first load resolves.

**AC-3 — a failure the user is WAITING ON is never rendered as (or silently collapsed into)
empty; a background nicety the user did NOT request is LOG-ONLY, not a banner.** This is the
central criterion and it has two directions that must both hold:
  - **(a) Waited-on failures must be visible and distinct from empty.** No bare `catch {}` or
    `if (!res.ok) return;` on a waited-on path may leave the surface in its empty/normal state.
    Named failing instances: the tracking table's sub-fetch swallows (`page.js:1122,1138,1160`
    — résumé/cover/stage failures leave a normal-looking table with missing data and no
    indication) and the live feed's secondary swallows (`LiveFeedTab.js:144,166,445,269`).
    These MUST surface a distinct "some data could not be loaded" state (an inline notice is
    enough; a full error page is not required for a partial failure).
  - **(b) An unrequested background enhancement must NOT show an on-screen empty/failed banner.**
    Surface H (`DocumentPreviewMount.js:60-76`) is the ruling precedent: research the candidate
    never asked for that finds nothing or errors is recorded to the log (AC-6), NOT shown, because
    a banner over "we found nothing" reads as a fault with no action attached. Any criterion that
    forces an on-screen empty/error state onto such a surface FAILS this clause. The design seat
    MUST classify each surface as waited-on vs background-nicety and apply (a) or (b) accordingly;
    the DocumentPreviewMount ruling is the test for "background nicety."
  - Also fix the C **co-render**: `AutoApplyQueueTab.js:300` renders the error Alert outside the
    `:321` loading/empty ternary, so a failed load shows the red Alert AND "Nothing queued yet."
    On failure the empty state MUST NOT co-render with the error.
  - Also fix the E **chip**: `StatusBar.js:367-371` gives a text badge only for `done`/`tailoring`,
    so a failed generation is distinguished by COLOR ALONE. Add a text label for the error state
    (color-only fails contrast/colour-blind users).
- Instrument: per-surface test driving (i) a rejected fetch and (ii) a 200-empty, asserting they
  differ AND that (i) is not silent; plus a bare-`catch`/`!ok`-return census over the in-scope
  files, canaried; plus, for clause (b), a test asserting the background-nicety surface renders
  NOTHING new on empty/fail (mirror the existing RED test the DocumentPreviewMount header cites).
- RED on HEAD: yes for A-subfetch, B-secondaries, C-co-render, E-chip (A/C verified; B/E
  **[agent]**). Clause (b) is a GUARD (surface H already passes) that prevents an
  over-correction — say so.

**AC-4 — a loading state is ANNOUNCED, not only drawn.** Every waited-on surface's in-flight
indicator MUST be reachable by assistive tech, following the surface-I / `answerStatus.js`
precedent: a visually-hidden `role="status"` region mounted UNCONDITIONALLY (so
idle→loading→done→empty are text changes on one node — a region that mounts already carrying
final text is not announced, `answerStatus.js:14-28`), announcing a CATEGORY ("Loading…",
"Checking…", "Generating your documents"), NEVER streaming progress text (mui-a11y-traps trap 4).
The empty-but-done transition is announced via the same region ("No … found"); the FAILED
transition via a separate `role="alert"`/MUI `Alert`, never the status region (mui-a11y-traps
traps 4/5 — no double/contradictory announcement). A `<Tooltip>` is NOT an acceptable name
source (mui-a11y-traps traps 1/2 — Tooltip steals or renames the accessible name).
- Named failing instances: A `TrackingTab.js:357`, B skeletons + load-more spinner, C skeletons +
  refresh spinner, F `DocumentPreviewDialog.js:825`, G `CompanyResearchDialog.js:337`, and the D
  primary sentence (`PrepPackPanel.js:427` is a plain Box; only `WholePackStatus` :605 is
  announced). Surfaces already passing: I (Drive), E (generation progress region :409). Credit
  them.
- Instrument: per-surface jsdom test asserting an accessible loading announcement exists and that
  resolved-empty and failed announce distinctly (the repo already runs `role="status"`/`aria-live`
  queries in tests, e.g. `DocumentPreviewMount.test.js`, `DriveResultRegion` tests). Use the
  a11y name resolver from `FeedToolbar.test.js` (mui-a11y-traps trap 3), never a naive
  `aria-label || textContent`.
- RED on HEAD: yes — census 93/94 unannounced (§2.1); canary `MeetingInsightList.js:156`.

**AC-5 — a failed WAITED-ON load offers a one-click, keyboard-reachable retry at the failure
site (or the cause-correct remedy where retry cannot help).** Where the failure is
transient/self-fixable, the failed state MUST expose a retry reachable in ONE action at the
point of failure — not down a menu, not only in a distant toolbar, not a full page reload
(minimize-clicks: fewer clicks never means fewer routes, so it must stay keyboard-reachable).
Where retry cannot help, offer the correct remedy instead of a generic "retry" (mirrors
N79-N80 AC-6's cause-conditioned remedy — do not cry wolf).
- Named failing instances: A (no retry), B (only toolbar refresh, not at the error Alert), F
  (none), G known-company error (`CompanyResearchDialog.js:342`, no retry). Already passing: C
  (`AutoApplyQueueTab.js:305`), D, I. Credit them.
- Instrument: per-surface test asserting the failed branch renders an activatable control whose
  handler re-invokes the load, and that it is keyboard-reachable.
- RED on HEAD: yes for A, F, G-known-company (A verified; B/F/G **[agent]**).

**AC-6 — a background load that resolves to nothing leaves a decision trace, distinguishing
empty from failed, in the downloaded log.** For every in-scope surface that fetches from a
provider/external service or does non-trivial background work (A sub-fetches, B, E, G/H research,
I Drive, D prep; J Gmail is N79-N80's), the outcome MUST be recorded via `recordDecision(...)`
(the `act` channel, `appActivityLog.js:297`) so the log distinguishes "loaded, empty" from
"load failed" from "still running when closed." Each needs a `DECISION_LEDGER` entry
(`activityChannels.js`) with ≥1 negative outcome and a CLOSED `fields` set carrying only a
coarse cause + count — NEVER résumé/cover/posting/email/company text, a token, a URL, or a raw
provider error (surface H's `code` discipline, `DocumentPreviewMount.js:62-67`;
input-and-content is uncaptured by design, `activityChannels.js:112-116`).
- This is exactly the trace the owner's last three debugging sessions lacked. Surface H already
  satisfies it and is the template; the silent-swallow paths in AC-3(a) (tracking sub-fetches,
  feed secondaries) are the clearest gaps — a swallowed failure must at least record a `failed`
  decision even if it renders only a small inline notice.
- Instrument (behavioural): per surface, a test asserting an empty resolution records a negative
  decision distinct from a failure resolution. Instrument (structural, EXISTS):
  `decisionCoverage.sweep.test.js` binds ledger↔call-sites both ways — a half-wired entry ships
  RED.
- RED on HEAD: yes — `DECISION_LEDGER` holds only `duplicate-check` and `fact-auto-insert`
  (`activityChannels.js:215-233`); no per-loading-surface entry beyond H's research one exists.
- **Overlap:** N79-N80 AC-10 owns the Gmail decision entry — do not duplicate it.

**AC-7 — the tests pin the LAST HOP to the user, not an internal flag.** Every test proving
AC-2–AC-6 MUST mount the real parent that supplies the state to the screen and assert on rendered
DOM / announced text, not on a hook's flag in isolation (measurement-instruments: "the parent
forwards it to the child" and "one level too deep" — assert off the wire/DOM from the mount
site). This is the guard against the repo's recurring "complete mechanism, missing user-facing
hop, green suite" class (now eight instances). Failure direction: a green test over a correct
hook whose value never reaches a rendered element FAILS.
- Instrument: each per-surface test mounts the parent surface. RED on HEAD: n/a — a constraint on
  HOW AC-2–AC-6 are tested, honoured by 4b/9; stated so the checker does not file it as
  unfalsifiable.

## 5. Composite surface cost (for the 8b re-judge)
This chunk ADDS, across up to nine surfaces: a visually-hidden announced status region, an
explicit empty/failed announcement, a failed-state retry/remedy, and (for provider/background
work) a `DECISION_LEDGER` entry + `recordDecision` call. It DISPLACES current silent/ambiguous
states and color-only signals. The natural home for the shared status+announce+retry primitive
is a small reusable component/hook modelled on `DriveResultRegion`, NOT nine inline copies and
NOT more lines in `app/page.js` (already under a ceiling — page-js-consolidation). Note for the
structure seat: several targets are large (LiveFeedTab 869, AutoApplyQueue 736, useDriveDocuments
930, useCompanyResearch 822, PrepPackPanel 854 lines) and may be over/near a ceiling.
