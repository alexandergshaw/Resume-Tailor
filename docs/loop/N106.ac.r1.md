## 2. Acceptance criteria

Run tests from PowerShell in `hello-world/`: `.\node_modules\.bin\vitest.cmd run <path>`. "Instrument: NEW" = the test must be built. Every corpus-scored AC states its **failable-row count** (rows that could produce a flag — guards zero-power) and, where retention matters, its **clean-row count** (rows that must NOT flag — guards flag-everything). Both must be > 0.

### — HIGHEST-RISK ACs —

### AC-1 (SAFETY) — Single-span containment: every flag names EXACTLY ONE app-minted span that EXISTS in its draft; the reviewer never re-chunks or invents a span
For every element of `flags`: `spanId` is a single value (never an array/union) and `spanId ∈ { s.id : s ∈ drafts[draftKind].spans }`; and if `evidenceRef` is present, `evidenceRef.spanId ∈` the id-set of the origin it names (posting ⇒ `posting.requirements[].id`; real-material ⇒ `realMaterial.spans[].id`; draft ⇒ `drafts[evidenceRef.draftKind].spans[].id`). The reviewer consumes only app-minted ids and emits only ids drawn from that input set — it mints no id of its own.
- **Why "impossible" not "forbidden" (rule 4):** the output `spanId` must be *selected from* the input id-set, so a reviewer tempted to flag a fabricated sub-phrase that spans two input bullets has no id to name — it must choose ONE existing span or not flag. This is the `loop-traps-spec` single-span rule: a contamination claim that borrows a real figure from an unrelated bullet cannot be expressed as one valid span.
- **Instrument (NEW):**
  - **(a) Universal post-condition** run over the output of EVERY fixture in the suite: assert each `flag.spanId` resolves in its `drafts[draftKind]`, is scalar, and each `evidenceRef.spanId` resolves in its named origin. A single unresolved/array id fails.
  - **(b) Adversarial union fixture:** a draft whose defect naturally spans TWO bullets (e.g. an unsupported metric split "grew the team" / "by 300%" across spans `s1`,`s2`). Assert the resulting flag's `spanId` is exactly one of `{s1,s2}` present in the draft — NOT a minted `s1+s2`, NOT a value absent from the draft.
- **Stub controls:** a "flag-everything" stub that emits a synthesized `spanId` (e.g. `"gen-0"`) fails (a) at once; a stub minting a union id fails (b).
- **RED on HEAD:** yes, by absence (P1). Post-condition has no output to validate until the module exists.
- **Failure direction (load-bearing):** minting/merging a span — letting a cross-span fabrication pass as one "supported" unit — is the worst outcome; the safe direction is to name one real span or emit no flag. Over-containment (declining to flag a genuinely multi-span defect) is acceptable here; silent span-invention is not.

### AC-2 (SAFETY) — Per-draft authority reference is SPLIT and the selection is DETERMINISTIC: `unsupported-authority` on a `user-material` draft is judged against `realMaterial`; on an `internal-consistency` draft it is judged against posting-plausibility + the draft's OWN internal coherence, NEVER against `realMaterial`
This is the N105 AC-5 fix this primitive inherits (P4). The REFERENCE SELECTION (which corpus a draft's authority is judged against) must be a deterministic, independently testable layer, even if the plausibility JUDGMENT within the selected reference is later LLM-augmented (AC-12 seam).
- **The control that was unsatisfiable before the split:** a strong-but-internally-COHERENT `internal-consistency` draft (authority that EXCEEDS anything in `realMaterial`) produces **ZERO** `unsupported-authority` flags.
- **Instrument (NEW) — differential invariance + held-out coherent control (not authored from the reviewer's own rules):**
  - **Fixture H** = an `internal-consistency` draft: span `"Led a 200-engineer platform org"` with its date/title spans internally consistent with that seniority. Drafts set = **{H only}** so `realMaterial` may legally be null.
    - Run A: `realMaterial = R_contradict` (associate-level, 3 yrs — evidences no such role). Run B: `realMaterial = null`.
    - Assert: the set of `unsupported-authority` flags with `draftKind === H.kind` is **IDENTICAL** in Run A and Run B (H's authority judgment is INVARIANT to `realMaterial`), and is **empty** in both (coherent control — no false authority flag).
    - **Mutant control:** an impl that judges H against `realMaterial` (the pre-split bug) flags H in Run A but not Run B → sets differ → RED.
  - **Fixture H'** = an `internal-consistency` draft with an INTERNALLY-INCOHERENT authority claim (`"CTO leading 200 engineers"` over date/title spans in the SAME draft showing 3 yrs / associate dates) → MUST be flagged `unsupported-authority`, with `evidenceRef.origin="draft"`, `draftKind=H'.kind`, `spanId` = the contradicting date/title span.
  - **Fixture U** = a `user-material` draft, claim `"Directed a 50-person org"`: with `realMaterial` evidencing no such role → flagged `unsupported-authority` (`evidenceRef.origin="real-material"`); with `realMaterial` evidencing it → NOT flagged. (Pins that `realMaterial` IS U's reference.)
  - Failable rows: H′ (1 must-flag) + U-unsupported (1 must-flag) = 2. Clean rows: H in both runs + U-supported = 3.
- **RED on HEAD:** yes, by absence.
- **Failure direction (load-bearing):** on the `internal-consistency` draft, flagging legitimate ambition as "unsupported" (the pre-split degeneracy) is a failure the coherent control guards; on the `user-material` draft, PASSING an unsupported authority/seniority claim as clean is the worse failure (over-flag is safe). Both directions pinned.

### AC-3 (SAFETY) — The no-LLM (embedded) path returns a MEANINGFUL deterministic SUBSET or REFUSES honestly; it NEVER returns a clean-looking empty result when a mechanical-floor defect is present
On the deterministic path (P3, `wantsEmbedded ⇒ true`, no LLM call), for a draft set that CONTAINS at least one mechanical-floor defect (a missing posting keyword, a repeated phrase, an unverifiable metric, or a vague-unsupported opener), the primitive MUST either (a) return `flags` that is non-empty and contains at least the mechanical-floor categories the defect belongs to, OR (b) refuse honestly in a way a consumer **cannot** mistake for "reviewed and clean" (a thrown error / a distinguished out-of-band signal — NOT a `{flags:[], …}` success value). The one outcome FORBIDDEN on such input is a success return with `flags:[]`.
- **Honest-refuse definition (contract-preserving):** because the return shape is frozen (no "coverage" field), "refuse honestly" means the no-LLM invocation does not RETURN a success value of the frozen shape (throws / is gated absent via the `wantsEmbedded` capability), so no consumer can render it as a completed clean review. The exact mechanism (throw vs capability-gated absence) is a 1b input; this AC fixes the invariant and the forbidden outcome.
- **Instrument (NEW):**
  - **Positive (defect-laden):** a draft carrying one defect in each mechanical-floor category, run on the deterministic path → assert `flags` non-empty AND contains ≥1 flag in each of `{missing-keyword, repetition, unverifiable-metric, vague-unsupported}` (OR the call refuses per (b)). Failable rows = 4 (one per floor category).
  - **Negative (clean control):** a genuinely clean draft (no floor defect) on the deterministic path → `flags` contains no false mechanical-floor flag. Clean rows > 0. (This is why "empty" is only forbidden when a defect is present — a clean draft legitimately returns empty.)
  - **Stub controls:** the "returns `{flags:[]}` always" stub fails the positive; the "flag-everything" stub fails the negative.
- **RED on HEAD:** yes, by absence.
- **Failure direction (load-bearing):** silently returning clean-empty — a review that looks done and finds nothing while nothing was analyzed — is the worst outcome (a consumer presents "no weaknesses"); the safe directions are over-flagging the mechanical floor or an unmistakable refusal.

### — CATEGORY ACs (each: ≥1 positive + ≥1 clean control, so none passes vacuously) —

### AC-4 — `missing-keyword` (mechanical floor)
A posting requirement keyword absent from a draft's spans is flagged on that draft (`category="missing-keyword"`, `draftKind` = the draft lacking it, `evidenceRef.origin="posting"`, `spanId` = the requirement).
- **Instrument (NEW):** posting requires `"Kubernetes"`, draft has no span containing it → flag with `evidenceRef` to that requirement. Clean control: posting requires `"Python"`, a draft span contains `"Python"` → no missing-keyword flag for it. Failable = 1, clean = 1.
- **Separation from AC-14:** a keyword absent from the draft but PRESENT in `realMaterial` is a *phrasing* gap → `missing-keyword`, NOT an unresolved qualification (AC-14 pins this boundary).
- **RED on HEAD:** yes, by absence. **Failure direction:** missing a genuinely absent required keyword (false-clean) is worse than over-flagging.

### AC-5 — `repetition` (mechanical floor)
The same phrase/lemma repeated across multiple spans in one draft is flagged (`category="repetition"`, `draftKind`, `spanId` = one repeated span, `evidenceRef.origin="draft"`, same `draftKind`, `spanId` = another repeated span).
- **Instrument (NEW):** two spans both open `"Spearheaded cross-functional initiatives…"` → repetition flag whose `evidenceRef` points to the sibling span (same draft). Clean control: all spans lexically distinct → no repetition flag. Failable = 1, clean = 1.
- **RED on HEAD:** yes, by absence. **Failure direction:** false-clean on obvious repetition is worse than over-flagging.

### AC-6 — `unverifiable-metric` on BOTH draft kinds (mechanical floor; verifiability is draft-INTERNAL)
A metric claim whose magnitude cannot be verified from WITHIN the draft itself (no baseline, no unit, or implausible precision — e.g. `"+300% revenue"` with no source/baseline) is flagged `unverifiable-metric`. This applies IDENTICALLY to the `internal-consistency` and `user-material` drafts (it does NOT consult `realMaterial` — that is support/authority, not verifiability).
- **Instrument (NEW):** plant `"improved performance by 300%"` (no baseline) on the hypothetical draft → flagged; the same metric on the application-ready draft → flagged. Clean controls (one per draft): a metric with a baseline/unit, or a span with no numeric claim → not flagged. Failable = 2 (one per draft), clean = 2.
- **Vocabulary-separation note (rule from `loop-traps-spec`):** `unverifiable-metric` (draft-internal) and `unsupported-authority`/support-against-`realMaterial` (corpus-relative) must use SEPARATE definitions — do not let one keyword/threshold drive both, or widening it tightens one and loosens the other.
- **RED on HEAD:** yes, by absence. **Failure direction:** passing an unverifiable metric as fine (false-clean) is worse than over-flagging.

### AC-7 — `vague-unsupported` (mechanical floor)
A vague, unsupported claim (e.g. `"Responsible for various strategic initiatives"` — weak opener, no concrete object) is flagged `vague-unsupported` on the draft carrying it.
- **Instrument (NEW):** a span opening with a `WEAK_OPENERS`-style vague construction and no concrete outcome → flagged. Clean control: a concrete, specific span → not flagged. Failable = 1, clean = 1.
- **RED on HEAD:** yes, by absence. **Failure direction:** false-clean on a vague bullet is worse than over-flagging; but over-flagging specific bullets as "vague" would make the primitive noisy — the clean control bounds that.

### AC-8 — `unsupported-authority` JUDGMENT (category behavior; reference selection pinned by AC-2)
Given the correct per-draft reference (AC-2), an authority/seniority/leadership/scope claim not supported by that reference is flagged `unsupported-authority`; a supported/coherent one is not.
- **Instrument (NEW):** reuses AC-2 fixtures U (user-material, unsupported vs supported) and H′ (internal incoherence). The first-slice depth is the deterministic reference-split + date/title coherence skeleton; semantic DEPTH beyond that is SECOND SLICE (gated on AC-3/AC-12). Failable = 2, clean ≥ 1 (via AC-2's H/U-supported).
- **RED on HEAD:** yes, by absence. **Failure direction:** passing an unsupported authority claim on the user-material draft as clean is the worst (over-flag safe); falsely flagging a coherent hypothetical claim is the pre-split degeneracy AC-2 guards.

### AC-9 — `consistency`, including CROSS-DRAFT, with the typed `evidenceRef` shape
An inconsistency across dates/titles/seniority between two drafts referencing the same real fact is flagged `consistency` on one draft, with `evidenceRef:{origin:"draft", draftKind:<the OTHER draft>, spanId:<the contradicting span in that other draft>}`. `draftKind` is REQUIRED iff `origin==="draft"` and FORBIDDEN otherwise.
- **Instrument (NEW):** hypothetical span `"Acme, 2018–2022"` and application-ready span `"Acme, 2019–2022"` (contradictory dates, same employer) → a `consistency` flag whose `evidenceRef.origin="draft"`, `draftKind` = the other draft, `spanId` = the contradicting span there. Clean control: two drafts agreeing on all shared facts → no `consistency` flag. Failable = 1, clean = 1. (First slice uses an unambiguous date contradiction so the shape is deterministically testable; semantic consistency DEPTH is second slice.)
- **Shape sub-assertion (universal, see AC-15):** on EVERY flag, `(evidenceRef.origin==="draft") ⟺ (evidenceRef.draftKind is present)`.
- **RED on HEAD:** yes, by absence. **Failure direction:** a cross-draft contradiction going unflagged is the failure; a `consistency` flag that cannot name the other draft's span (missing/invalid `draftKind` or `spanId`) is the N105 M4 defect this field exists to prevent.

### AC-10 — `employer-plausibility` (SECOND SLICE depth; first-slice ENVELOPE only)
A claim implausible for the stated employer/domain is flagged `employer-plausibility`. Because robust judgment needs world-knowledge, the DEPTH is LLM-backed and DEFERRED to the second slice. First-slice obligation: the ENVELOPE only — if the deterministic path does not compute this category, that is acceptable PROVIDED AC-3 holds (never clean-empty on a mechanical defect) and any emitted `employer-plausibility` flag satisfies AC-1/AC-15 (valid single span, valid `evidenceRef`). A first-slice wiring test MAY exercise the envelope via the AC-12 seam with a stubbed judgment.
- **Instrument (NEW, second slice):** held-out drafts — a bullet claiming regulated medical-device work under an employer the posting/corpus establishes as unrelated → flagged; a plausible bullet → not. Deferred; its first-slice stand-in is the AC-12 seam-mapping test.
- **RED on HEAD:** yes, by absence. **Failure direction:** a false-clean on an implausible employer claim is the failure; deferring DEPTH is acceptable only because AC-3 forbids the embedded path from looking clean while unanalyzed.

### — STRUCTURAL / CONTRACT ACs —

### AC-11 — Determinism and STABLE TOTAL ORDER (no ordering-dependent output)
On the no-LLM path, `reviewDocuments(I)` called twice is deep-equal (same `flags`, same `unresolvedQualifications`, element-for-element). AND output order is a stable total order determined by output CONTENT (e.g. `draftKind`, then `spanId`, then `category`), NOT by input array position: `reviewDocuments(I)` deep-equals `reviewDocuments(I')` where `I'` is `I` with each `drafts[*].spans` array SHUFFLED (same ids/text, different index).
- **Instrument (NEW):** repeated-call equality + the shuffle-invariance equality. Any path (if LLM-augmented later) must still apply the stable sort to a given raw judgment (tested via the AC-12 seam with a fixed stubbed judgment).
- **Stub control:** an impl emitting flags in span-iteration order (or from a `Set`/object-key order) fails the shuffle test.
- **RED on HEAD:** yes, by absence. **Failure direction:** order that depends on input array position makes three consumers render differently from the same facts; the safe direction is a content-keyed total order.

### AC-12 — Purity of the deterministic core; any LLM judgment enters through an INJECTED seam
The deterministic core of `reviewDocuments` is a pure function of its arguments: no network, no filesystem, no `globalThis`/module-state mutation, no wall-clock/`Math.random` dependence. If a category's judgment is LLM-backed, that judgment is supplied through an INJECTED dependency (a seam parameter / injected client), so (a) the core stays pure and node-testable and (b) tests can stub the seam for determinism.
- **Instrument (NEW):** call the core with no seam injected and assert it returns without any network/fs access (spy `globalThis.fetch` with a recording positive control per `loop-traps-spec` egress rule; assert zero calls on the deterministic path). Assert no import in N106's own graph monkeypatches `globalThis.fetch`. A seam-mapping test injects a fixed fake judgment and asserts the core maps it to valid `flags` (AC-1/AC-15 shape).
- **RED on HEAD:** yes, by absence. **Failure direction:** burying the LLM call inside the core (no seam) makes the authority-split (AC-2) and ordering (AC-11) untestable and the "pure/deterministic" contract claim false; the seam is what keeps them verifiable.

### AC-13 — `realMaterial` contract: null is legal with no `user-material` draft (no crash); a `user-material` draft with null `realMaterial` FAILS CLOSED (never clean)
(a) When no draft has `authorityReference==="user-material"`, `realMaterial` MAY be null and the primitive must run normally (no throw, no crash) — it must not require the corpus. (b) When a `user-material` draft is present with `realMaterial` null (a precondition violation), the primitive MUST NOT crash and MUST NOT return a clean result: it either fails closed by flagging every support/authority-requiring claim on that draft as unsupported, OR refuses honestly (distinguished signal / throw). The FORBIDDEN outcome is a `{flags:[], …}` success that reads as "this user-material draft's authority claims are all supported."
- **Default (DECIDED HERE, matching N105 §5 L1 "empty corpus ⇒ everything drops"):** fail-closed-by-flagging is the default; refuse-with-signal is the admissible alternative. 1b picks; the invariant + direction are fixed.
- **Instrument (NEW):** (a) drafts = {internal-consistency only}, `realMaterial=null` → returns a well-formed result, no throw (this is exactly AC-2 Run B, shared). (b) drafts include a `user-material` draft carrying an authority claim, `realMaterial=null` → assert the result is NOT a clean success: count of `unsupported-authority` flags on that draft ≥ 1 (fail-closed) OR an honest refusal; assert it is never `{flags:[]}` success. Failable = 1.
- **Stub control:** a stub returning `{flags:[]}` on (b) fails.
- **RED on HEAD:** yes, by absence. **Failure direction (load-bearing):** with no corpus to support them, passing a user-material draft's authority/support claims as clean is the fabrication-shipping direction; over-flag / refuse is safe.

### AC-14 — `unresolvedQualifications`: a genuine qualification gap is listed with its `requirementId`; a requirement a draft span resolves is NOT listed; a mere phrasing gap is NOT an unresolved qualification
A posting requirement that wording alone cannot resolve (a substantive gap — nothing in the drafts addresses it and no rewording of existing draft content would) appears in `unresolvedQualifications` with its `requirementId` and text. A requirement satisfied by a draft span does NOT appear. A requirement whose keyword is merely absent from the drafts but present in `realMaterial` (a phrasing gap) does NOT appear here (it is AC-4 `missing-keyword`).
- **Instrument (NEW) — three rows:** R1 `"5+ years Python"` satisfied by a draft span evidencing Python → NOT listed. R2 `"active TS/SCI security clearance"` addressed by no draft span and absent from `realMaterial` (genuine gap) → listed with R2's `requirementId`. R3 a keyword absent from drafts but present in `realMaterial` → NOT listed in `unresolvedQualifications` (surfaces as AC-4 instead). Failable (must-list) = 1 (R2); must-exclude = 2 (R1, R3).
- **Power / stub controls:** a "list everything" stub includes R1 → fails; a "list nothing" stub omits R2 → fails. (This is the brief's exact power requirement.)
- **RED on HEAD:** yes, by absence. **Failure direction:** omitting a genuine gap (R2) lets a consumer leave the user believing they qualify — the worse error; listing a resolved requirement (R1) is noise the must-exclude rows bound.

### AC-15 — Output well-formedness (universal post-condition over every fixture)
On the output of EVERY fixture: each `flag.category ∈` the 7-member enum; each `evidenceRef.origin ∈ {"posting","real-material","draft"}`; `evidenceRef.draftKind` is present iff `origin==="draft"`; `unresolvedQualifications[].requirementId ∈ posting.requirements[].id`. (Containment of `spanId`s is AC-1.)
- **Instrument (NEW):** a schema/validity sweep applied to every fixture's result.
- **Stub control:** a flag with an out-of-enum `category`, or `draftKind` set on a `origin="posting"` ref, fails.
- **RED on HEAD:** yes, by absence. **Failure direction:** an out-of-vocabulary category or a malformed `evidenceRef` breaks all three consumers uniformly; strict shape is the safe direction.

### AC-16 — Single exported analyzer; the shared-consumption contract (the N106 side of N105 AC-6)
N106 exports exactly ONE document-weakness analyzer, `reviewDocuments`, with the frozen input/output signature above. It is the single primitive N103/N104/N105 import; N106 introduces no second analyzer.
- **Instrument (NEW):** (a) an export/signature test pins `reviewDocuments`'s argument shape and return keys (`flags`, `unresolvedQualifications`) to the frozen contract. (b) A census over N106's OWN module(s) asserts no second exported document-weakness analyzer, canaried against the known `reviewDocuments` export (per `loop-traps-search`, assert the token near the export, not a whole-file regex). The reciprocal "N105 grows no analyzer" belongs to N105 AC-6, not here.
- **RED on HEAD:** yes, by absence. **Failure direction:** shipping a second analyzer (or a signature that drifts from the frozen contract) forces each consumer to adapt divergently; one frozen export is the safe direction.
