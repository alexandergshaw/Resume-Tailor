## Bug 1 — substring false positive (`lib/acceptedFacts/factInsertion.js:134`)

`if (fact.id != null && recordIds.has(fact.id) && priorText.includes(text)) continue;`
compares the INCOMING fact text (`text`, user-editable with no length floor)
against the whole joined letter. A candidate who accepts an article, edits its
suggestion down to a short fragment that coincidentally occurs elsewhere in the
letter, and re-accepts, is suppressed with "already present" though that fragment
was never inserted.

**Fix direction pinned:** the presence check must consult the RECORDED fact's text
(the `.text` stored in `record` for this `fact.id`), NOT the incoming text.
Suppress only when the recorded fact's own text is still present. Tests FAIL when
the guard compares incoming text, PASS when it compares recorded text.

- **Seam RED** (`factInsertion.substringFalsePositive.test.js`): id in record,
  recorded text absent from v2 lines, incoming edited to a fragment present only
  in unrelated intro prose and absent from the 'current' target line → HEAD
  suppresses (0 edits), fix inserts. Discriminates compare-incoming from
  compare-recorded (they disagree ONLY when recorded absent + incoming present).
- **Reachability RED** (`acceptFactSubstringFalsePositive.rc.test.js`): real
  mounted `CompanyResearchDialog` + real `useCompanyResearch`. Accept #1 (real
  button) → reproduce the version-switch state (letter now lacks the recorded
  fact; store keeps its id+text) via `setTailoringMap` (selectDocumentVersion is
  owned by another agent this round; its RESULTING STATE is reproduced, the
  behaviour-under-test is still the real re-accept) → edit the real suggestion
  textarea to a short colliding fragment → real re-accept. HEAD leaves the letter
  unchanged and shows the "already present" lie; fix changes the letter and does
  not.
  - **Why layered, not a bare accept→edit→reaccept**: a bare edit leaves the
    recorded (long) text still in the letter, so BOTH buggy and fixed builds
    suppress — that scenario is not a false positive the fix flips, and a red
    asserting insertion there would be UNSATISFIABLE. The fix flips only when the
    recorded text is absent while the edited fragment coincidentally is present.
    The verifier's own dialog probe used the non-discriminating (recorded-present)
    fixture and only demonstrated the message reaches the user; it does not flip
    under the correct fix. This is called out so a future reviewer does not
    "simplify" the reachability test back into an unsatisfiable red.
- **Controls (green both builds)**: (a) no over-fire — a re-accept whose recorded
  text is still present is suppressed (a genuine duplicate stays deduped, the fix
  is not "always insert"); (b) no under-fire — a NEW-id fact whose text coincides
  with prose is still inserted (guard stays id-scoped, never text-only dedupe).

## Bug 2 — wrong notice when there is no cover letter (`app/hooks/useCompanyResearch.js:459-461`)

`else if (!coverChanged) { notice = ALREADY_PRESENT_NOTICE; }` fires whenever
nothing changed, including when `coverLetterResultLines` is empty because the job
has NO tailored cover letter yet (`planCoverFacts` always no-ops then, so
`coverChanged` is false). The candidate is told "That fact is already in your
cover letter" when there is no cover letter. The dialog is reachable for such a
job (StatusBar's Research item is gated only on the company name). Confirmed:
verifier's `_checkerProbeResult.json` shows `{ok:true, acceptNotice:"That fact is
already in your cover letter."}`.

**Fix direction pinned:** distinguish "no cover letter exists" from "genuinely
already present"; give the no-cover-letter case its own honest message mirroring
the sibling AUTO path (`useCompanyResearch.js:702-703`,
`{reason:"No cover letter to insert into.", severity:"failure"}`) — a
failure/absence, not an info "already present".

- **RED test A** (`acceptFactNoCoverLetterNotice.rc.test.js`): job with no cover
  letter, real accept → HEAD shows ALREADY_PRESENT; fix must NOT, and must surface
  an honest `/no cover letter/i` message (state + DOM last-hop + `result.reason`).
- **RED test B**: the no-cover-letter accept must be a FAILURE (`result.ok ===
  false`), not the silent `ok:true` info HEAD returns — mirrors the auto path's
  severity.
- **Control (green both builds)**: a cover letter that already carries the fact →
  re-accept still shows the ALREADY_PRESENT info notice with `ok:true` (the fix
  must not over-fire and route genuine dedupes through the no-cover-letter path).
