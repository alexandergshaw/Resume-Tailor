## 1. The domain distinction this chunk turns on: three engine/state shapes, not two

The refusal gate conflates two independent axes — *has engine docx bytes* and *has an in-session
template File*. Split them:

| Shape | `coverLetterDocxB64` / resolvable `docxPath` | in-session `coverLetterFile` | Can a faithful (styled) doc be produced? | Correct behaviour |
|---|---|---|---|---|
| A. Byte engine (embedded/external), fresh or restored | present (bytes, or path that resolves) | irrelevant | Yes — splice bytes | **Splice** (unchanged today) |
| B. **Gemini, fresh in-session** (the owner's bug) | empty | **present** (template just uploaded/used) | Yes — rebuild template from lines | **Insert into lines, let template-rebuild produce the doc** (NEW) |
| C. **Gemini, reloaded** (or pre-migration upload that never happened) | empty | **absent** (File never persisted) | **No** — the template is gone; only `content_lines` survive | **Refuse honestly** (see AC-8) — NOT today's misleading message |

The current code sees only "bytes vs no bytes" and sends B and C both to the same misleading
refusal. **B must succeed; C must refuse with a distinct, honest message.** The discriminator
between B and C is the presence of the in-session template File — which the hook cannot currently
see (AC-9).

**Failure direction (governs the whole chunk):** the worst outcome this feature can produce is an
unsourced/unstyled document reaching an employer while the candidate believes it is their tailored
letter. So: never silently ship a document with no template behind it (C refuses, not silently
rebuilds a blank/plain letter unless the owner explicitly chooses option (a)); and never insert a
fact the candidate cannot see and remove (the fact must reach the rendered preview, AC-2).

### Do NOT regress the byte engines — the direction guard

**AC-5 — when engine bytes resolve, the splice path is still taken; the line path is a fallback
only.**
When `resolveCoverEngineBytes(entry)` returns non-empty (Shape A: in-session bytes OR a
`coverLetterDocxPath` that resolves), both `acceptFacts` and `autoInsertFactsForJob` MUST apply
`applyCoverDocxEdits` and set `coverLetterDocxB64` to the spliced result — they MUST NOT drop to
the line-only fallback. The line-only path is entered **only** when no bytes resolve.
- Instrument: the existing byte-path rc tests MUST stay green — `acceptResolvesCoverDocxPath.rc.test.js`,
  `autoInsertResolvesSavedCoverDocx.rc.test.js` (both drive the docxPath→bytes resolve) — plus a
  test asserting that with bytes present, `coverLetterDocxB64` is set on the entry after accept
  (proving the splice ran, not the line fallback).
- RED on HEAD: **no — this is a non-regression guard.** Stated as such per the brief: it passes
  today and must keep passing; it guards the fix from cannibalising the working byte path.
- Make-the-wrong-thing-impossible framing: the branch selector MUST be `hasCoverBytes`
  (`resolvedCoverDocxB64.length > 0`), so "bytes present ⇒ splice" and "bytes absent ⇒ lines" are
  mutually exclusive by construction, not by two independent conditionals that could both fire or
  both miss.

### N81 dedupe and N62 placement must carry to the line path

**AC-6 — the line path routes through the shared planner, so N81 id+presence dedupe applies.**
The no-bytes insert MUST derive its new lines from `planAcceptForEntry`/`planCoverFacts`
(`factInsertion.js:99-193`) — the SAME planner the byte path uses — never a parallel hand-rolled
line insert. Observable consequences that MUST hold on a Gemini letter:
  - a fact whose **id is already recorded AND whose recorded text is still present** in the letter
    is NOT inserted a second time (N81 guard, `factInsertion.js:135-148`): after two accepts of
    the same fact, its text occurs **exactly once** in `coverLetterResultLines`, and the second
    accept reports the "already present / nothing new" outcome, not a duplicate;
  - a fact **genuinely absent** from THIS letter (e.g. after a version switch that dropped it) IS
    inserted.
- Instrument: an rc test on a Gemini letter — accept fact X; accept fact X again; assert X's text
  count in the lines === 1 and the second result is the already-present/nothing-new outcome. A
  second row: a distinct fact Y still inserts (count of Y === 1). Rows that can fail = 2 (the
  dedupe of the repeat, and the admission of the distinct fact) — state this in the test.
- RED on HEAD: **yes** — the FIRST accept refuses (AC-1/AC-4), so X's occurrence count is 0, not 1;
  the dedupe cannot even be reached today. Read directly. (Once AC-1 lands, this criterion is what
  proves the fix didn't bypass the seam.)

**AC-7 — placement (N62 / "Let the app decide") is honored when inserting into lines.**
The auto path MUST place each fact at the saved `defaultPlacement` (falling back to
`DEFAULT_PLACEMENT`), and the manual path at each fact's chosen `placement`, resolved via the same
`resolvePlacement`/`findTargetIndex` in `planCoverFacts` — not always "intro", not always
paragraph-end.
- Instrument: an rc test with a saved non-default placement whose anchor matches a specific
  paragraph; auto-insert a fact; assert the fact text lands in **that** paragraph (that line index)
  of the resulting lines, and at the position the placement specifies (end vs after-first-sentence,
  per `insertFactText`).
- RED on HEAD: **yes** — no insert happens today. Because `planCoverFacts` already implements
  placement, AC-6's routing requirement delivers this; AC-7 pins the observable so a line path that
  hard-coded "intro" would fail.

### The HARD EDGE — Shape C (reloaded Gemini letter). RECOMMENDATION + falsifiable criteria.

**Recommendation: option (b) — refuse Shape C, with an honest message distinct from today's.**
Rationale, weighed against the failure-direction rule:
1. **Safe direction.** For Shape C there is no template and no bytes; a faithful styled document
   cannot be produced. Option (a) (rebuild onto a plain document) needs NEW code —
   `resolveDocumentBlob` returns **null** when `uploadedTemplate` is null (`docx.js:682`), so there
   is no plain-doc builder today — and it risks shipping an unstyled letter the candidate mistakes
   for their tailored one. Refusing never ships a wrong document.
2. **Minimal, and it unblocks the owner.** The owner's reported bug is Shape B (fresh, `#76`
   fresh `/api/tailor`), fully fixed by AC-1–AC-4. Shape C is the secondary edge.
3. **Honest.** Today's `NO_ENGINE_BYTES_REASON` ("its saved file is missing. Regenerate the cover
   letter in this session, then try again.") is a lie for Gemini: there never was a saved server
   file, and regenerating a Gemini letter never creates one — so "regenerate then try again" loops
   forever. The new message must not say that.

**This is a genuine product call and I flag it to the owner:** option (a) delivers the fact (the
feature's value) in a plain letter at the cost of the original template formatting. If the owner
prefers that, swap AC-8 for an (a)-variant (insert into lines + a plain-doc rebuild + a clear
"original template formatting needs a re-upload/regenerate" notice) — but that is more code and a
new N54-adjacent render path. **I recommend (b) and write (b)'s criteria so downstream work is not
blocked waiting on the ruling.**

**AC-8 — a reloaded/template-less Gemini letter refuses honestly, without inserting, with a
message distinct from `NO_ENGINE_BYTES_REASON` that does not promise a regenerate-fix.**
When `coverLetterResultLines` is non-empty, no engine bytes resolve, AND no in-session template
File is present (Shape C), accept/auto MUST refuse with **no write of any kind**, and the message
MUST (i) differ from `NO_ENGINE_BYTES_REASON`, and (ii) NOT instruct the user to "regenerate … then
try again" (nor otherwise claim a saved file exists or can be recreated for Gemini). It SHOULD name
the real remedy (re-upload the cover-letter template / re-tailor to restore formatting).
- Instrument: an rc test with `coverLetterDocxB64:""`, no `coverLetterDocxPath`, `coverLetterFile:
  null`; assert refusal (no `coverLetterResultLines` change, no PUT), message ≠ `NO_ENGINE_BYTES_REASON`,
  and message contains neither "regenerate" nor "try again".
- RED on HEAD: **yes.** This shape today returns `NO_ENGINE_BYTES_REASON` verbatim
  (`useCompanyResearch.js:21-23,430-432,731-732`). `factAutoInsertMessage.rc.test.js:298` currently
  *pins* that message for this shape — see §5 for the report-not-edit note.
- Failure direction: refusing Shape B by mistake (over-refusal) is a bug caught by AC-1; inserting
  into Shape C and producing a null/blank/unstyled document (under-refusal) is the worse bug this
  criterion prevents.

**AC-9 — the hook can distinguish Shape B from Shape C (the discriminator must be threaded in).**
`useCompanyResearch` currently receives `{tailoringMap, setTailoringMap, setPreviewReloadKey,
defaultPlacement, supabase, currentUser}` (`:179-186`) — it has **no** access to the cover-letter
template File, so it cannot tell B from C. The fix MUST thread the in-session cover template File
(or a truthful boolean of its presence) into the hook, and the B/C decision MUST key on it.
- Instrument: AC-1 (File present ⇒ success) and AC-8 (File absent ⇒ honest refuse) can BOTH pass
  only if this discriminator exists; a test that runs both fixtures through one hook instance proves
  it.
- RED on HEAD: **yes** — the parameter does not exist; today both shapes refuse identically.
  Read directly (`:179-186`).
- Structure note for 1b: the template File lives at the `DocumentPreviewMount` /
  `createDocumentDownloaders` level as `coverLetterFile` (`docx.js:699`, `DocumentPreviewMount.js:108`);
  thread the same value, do not invent a new source.

### Decision logging — the activity log must finally show a Gemini success or an honest refusal

## 3. Composite surface cost (for the 8b re-judge — legibility is cumulative)

This chunk ADDS to `app/hooks/useCompanyResearch.js`, already a large, heavily-commented hook
carrying acceptFacts / autoInsertFactsForJob / removeInsertedFact and ~15 named refusal/notice
constants. The additions:
- one new branch in each of `acceptFacts` and `autoInsertFactsForJob` (bytes-present ⇒ splice;
  no-bytes+template ⇒ line insert; no-bytes+no-template ⇒ refuse);
- one new hook parameter (the template File / presence flag, AC-9);
- one or two new message/notice constants (Shape-B success notice, Shape-C honest refusal) and one
  new decision `code`.
It DISPLACES nothing — the existing byte path and all existing constants stay. The three-way branch
in two sibling functions is a duplication risk (the same B/C selection written twice); the
structure seat should consider a single shared helper that returns the chosen strategy
(`splice` | `lines` | `refuse`) so the two callers cannot drift — the same "derive the answer once
for every consumer" lesson the codebase already learned for `resolveCoverEngineBytes`. Note for 1b,
not a mandate. No cross-file surface (no new UI panel) is added; the preview/download already render
the result.
