## 4. The D-8 research-reuse seam — REDESIGNED (fixes B1, M1)

**Decision: SC-A issues NO grounded call of its own. Its grounded evidence is the persisted
`application_digests` row (produced by the existing `/api/application-digest` Interactions route). The
"Refresh research" control and create-time "ensure research" both go through that route's existing
`force`/no-force path. N157 adds no transport and no Additional Terms (D-5).** This is exactly AC-S4's
"satisfied by reuse — name the entry point": the entry point is `POST /api/application-digest`, whose
grounded call is already wire-tested by `app/api/application-digest/route.wire.test.js`.

### 4.1 Read seam (every plan build; no spend) — `studyPlanEvidence.js`

```
gatherEvidence({ readDigest, readPrepPack? }, { applicationId, userId }) -> Promise<EvidenceSet>
```
- PRIMARY: reads the `application_digests` row (`{ markdown, sources, status, researched_at }`). The
  `sources` are **real publisher URLs** (Interactions API, route.js header:27-29) — no vertexaisearch
  redirect to strip. Each rendered citation still passes `safeExternalHref` (S2 defence: reject
  `javascript:`/`data:` etc.), reusing `lib/url/safeExternalHref.js` and the digest's own citation
  render (`lib/tracking/renderCitedMarkdown.js` / `lib/tracking/digestCitations.js`:`buildCitedDigest`).
- OPTIONAL enrichment (only if a ready `interview_prep_packs` row happens to exist): per stage item via
  the **exported** `stageItemSources(provenance,snapshot)`→`[{index,url}]` and
  `stageItemLabel(provenance,snapshot)`→`{kind,text}` ONLY. Redirect hosts are dropped inside
  `stageItemSources` (`servesGroundingRedirect`, `stageResearchView.js:232`). **No** use of the
  module-local `publisherKey`/`verifiedPublisherCount` (M1). `sourced` is derived from
  `label.kind !== "unsourced"`, not from a publisher integer.
- **Refusal-honest empty (S3):** digest absent or `status!=="ready"` ⇒
  `{ complete:false, items:[], reason:"no-research" }`. Never trusted-by-default.

`EvidenceSet` (SC-A → generation contract — trimmed to the exported surface):
```
{
  complete: boolean,                 // false ⇒ plan flagged partial/unsourced (S6)
  researchedAt: string|null,         // the digest's researched_at (recency the plan is based on)
  postingFingerprint: string,        // from the posting at build time (staleness basis)
  items: [ { topicHint, text, citations:[{ url }], sourced:boolean } ],
  reason: null | "no-research" | "unsourced"
}
```

### 4.2 Create-time ordering — RACE RESOLVED (fixes B1b, honors R-IP3-21)

R-IP3-21 forbids a grounded search AND a generation in one request (exceeds platform maxDuration). So
create is a **two-phase client orchestration** owned by `StudyPlanClient`, each phase its own request:

1. **Ensure grounded research (phase 1).** Read the digest. If not `ready`, `POST
   /api/application-digest {applicationId}` and **await it** (N157 awaits — it is *not* the
   fire-and-forget caller IP3 is; the route returns `{digest}` with `status:"ready"`, maxDuration 120).
   Render a "Researching the company and interview…" state meanwhile. On digest failure/`unavailable`
   (incl. embedded engine, which the route refuses at :220-225): render the failure; offer retry, or an
   explicit opt-in to build an **unsourced** plan (`provenance.research:"partial"`, all items
   `sourced:false`), never a silent unsourced plan (S3/S6).
2. **Generate + persist (phase 2).** `POST /api/study-plan {applicationId, knobs}` → reads the
   now-ready digest, builds `EvidenceSet`, runs the **non-grounded** plan generation, persists via
   `writeStudyPlan`. Render a "Building your plan…" state. Then render the walkthrough.

**"Refresh research"** (D-2 manual spend): `POST /api/application-digest {applicationId, force:true}`
(the existing Research-button path), await, then re-run phase 2. This is the ONLY path that spends a
fresh grounded call.

### 4.3 Caching & staleness (D-2) — semantics matched to the above

`writeStudyPlan` stores `cached_research` (the `EvidenceSet`), `researched_at` (copied from the digest
row at build time), and `posting_fingerprint`. A knob-only rebuild (SC-D) reuses `cached_research` and
spends nothing. **Staleness offer** = live `application_digests.researched_at` is newer than
`study_plans.researched_at`, OR the posting fingerprint changed → surface "Refresh research". Reuses the
**concept** (fingerprint + researched-at), not the unimplemented `packIsStale`/`packRenderState`
(`prepContract.js:9-23`, still noted unimplemented this round).

**S1 is RETIRED on the N157 path (minor m2).** SC-A issues no fresh grounded `generateContent`, so the
"stub `resolveGrounded` → claim dropped" behavioral fixture has **no target here**; the grounded
corroboration lives inside the reused digest route and is already covered by
`application-digest/route.wire.test.js`. No downstream seat should restate S1 as testable against
N157's own code. S4 is satisfied-by-reuse (named entry point + its existing wire test).

## 6. Migration sketch — `supabase/migrations/20261011000000_n157_study_plans.sql`

Self-contained, idempotent, stamp verified later than the tree's latest (`20261008010000`). One table
(as r1 §6: PK `application_id` → `applications(id) on delete cascade`, `user_id`→`auth.users(id)`,
`plan`/`knobs`/`progress`/`cached_research` jsonb, `status` CHECK `('ready','partial','unavailable')`,
`study_plans_ready_has_modules` CASE-guarded CHECK, `posting_fingerprint`, `researched_at`, `user_id`
index, RLS on + 4 owner-scoped policies + explicit grants) **plus one function** for M3:

```sql
-- Progress merge: lost-update-safe by construction. SECURITY INVOKER (stated
-- explicitly, per claim_prep_pack_slot's convention) so it runs as the caller
-- under RLS; the WHERE also carries auth.uid() for defence in depth (S8). No
-- p_user_id parameter -- identity is auth.uid() server-side.
--
-- WHY THIS IS NOT A LOST UPDATE under READ COMMITTED: the single UPDATE takes a
-- row lock; a concurrent second call blocks on it, and when the first commits
-- the second RE-EVALUATES its SET expression against the newly committed tuple
-- (EvalPlanQual), so `seen || p_seen_delta` is computed over the first writer's
-- merged value. Distinct itemId keys both survive; this is the property a
-- whole-object read-modify-write in application code cannot give.
create or replace function public.merge_study_plan_progress(
  p_application_id uuid, p_cursor jsonb, p_seen_delta jsonb
) returns boolean
language plpgsql
security invoker
as $$
declare v_rows integer;
begin
  update study_plans
     set progress = jsonb_set(
                      jsonb_set(coalesce(progress, '{}'::jsonb), '{cursor}', p_cursor, true),
                      '{seen}',
                      coalesce(progress -> 'seen', '{}'::jsonb) || coalesce(p_seen_delta, '{}'::jsonb),
                      true
                    ),
         updated_at = now()
   where application_id = p_application_id and user_id = auth.uid();
  get diagnostics v_rows = row_count;
  return v_rows > 0;
end;
$$;

grant execute on function public.merge_study_plan_progress(uuid, jsonb, jsonb) to authenticated;
```

**Alternative (owner may prefer, flagged not re-opened):** a per-item child table
`study_plan_progress(application_id, item_id, revealed_at, grade, due_at, PK(application_id,item_id))`,
each reveal an upsert of one row — no RPC, no jsonb merge, join on read. Chosen the RPC-merge here
because it preserves the 1:1 single-table model and needs no join; the child table is the better choice
only if progress writes are expected to be extremely high-frequency. **Decision owned here; the owner
confirms direction before SC-B freeze.**

**Schema-drift caution** unchanged from r1: FKs only to `applications(id)` (its PK) and `auth.users`;
the live `applications UNIQUE(user_id,position_id)` does not touch `study_plans`; the S7 shape test
proves declared SQL only, never live enforcement (§13).

## 7. Store contracts (SC-B) — defence-in-depth (S8/S9)

`readStudyPlan` / `writeStudyPlan`: as r1 §7 — injected `supabase`, named projections, never
`select("*")`, never throws, **both `.eq("application_id")` AND `.eq("user_id")`** on every statement.

**`writeStudyPlanProgress` changes (M3):** it no longer updates the `progress` column directly. It
calls the RPC:
```
writeStudyPlanProgress(supabase, { applicationId, cursor, seenDelta })
  -> supabase.rpc("merge_study_plan_progress", { p_application_id, p_cursor, p_seen_delta })
  -> { written: boolean, error }
```
`seenDelta` is the ONE item just revealed/graded, never the whole `seen` map — so two devices never
overwrite each other (M3). `userId` is not passed (identity is `auth.uid()` inside the RPC, the same
discipline as `recordModelCallIssued`).

**S9:** `applicationId`/`userId`/`engine` are passed explicitly from `StudyPlanClient`'s own selected
posting; **no `=""` default on any id**. `app/api/study-plan/route.js` rejects an empty `applicationId`
with 400 (mirroring `application-digest/route.js:201-202`) and 404s a non-owned application
(mirroring :207-214), so "nobody passed it" can never become a well-formed write for the wrong thing.
