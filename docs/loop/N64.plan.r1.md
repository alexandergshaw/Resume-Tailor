## 2. Contradictions routed to me — resolved (rule 5)

**C-1 — Loud vs idempotent migration (owner ruling 6 vs design §7.2).** Design §7.2 writes the
`applications` columns with `add column IF NOT EXISTS` and the FKs behind a `do $$ … if not exists … $$`
guard (idempotent). Owner ruling 6 overrides this: because we author on ASSUMPTION (ruling 3, live-schema
query waived), the migration must FAIL LOUDLY on a wrong guess, not silently no-op.
- **RESOLVED:** the new columns use **plain `alter table public.applications add column <c> <type>;`**
  (NO `if not exists`), and the FKs use **plain `alter table … add constraint … ;`** (NO `do $$ if not
  exists` guard). If the name already exists in the live schema the migration ERRORS and STOPS the
  deploy — the desired outcome, because a silent skip would leave app code writing into a column that
  means something else. The **new table** keeps `create table if not exists` (ruling 6 permits it; safe).
  **State in the migration's header comment that the missing `if not exists` is DELIBERATE (owner ruling
  6, 2026-09-28) so no later reader "fixes" it back to idempotent.** Supabase runs each migration once
  keyed by stamp, so re-run safety is not needed and would defeat the loud-failure design.

**C-2 — BL-1 "INVALID-until-run" gate (design §11) vs owner ruling 3 (do not wait on the live-schema
query).** RESOLVED: ruling 3 wins. **BL-1 is downgraded from a blocker to a POST-DEPLOY verification
step** (Step 2 below, per ruling 7). Author on the design's stated assumptions; the loud migration (C-1)
plus the post-deploy check plus a follow-up-migration recovery path replace the pre-deploy gate.

**C-3 — BL-2 (Arch B deviates from AC literal §4).** RESOLVED by orchestrator ruling 4: **Arch B
adopted.** AC amendments recorded in §3.

**C-4 — CRUD reuse (AC §1.4 vs design §2).** RESOLVED: mirror `saved_searches`, per design/owner (see
§1.6).

## 4. Ordered steps — each independently landable and verifiable

**Global sequencing rule (owner):** the migration lands ALONE and FIRST; its deploy is CONFIRMED before
any app code that writes the new columns. `app/page.js` is touched LAST and SMALL. Steps 3–6 (new
files + one funnel edit) are landable in either order after Step 2; Step 7 (page.js + display) is last.

### Step 1 — Author and land the migration ALONE (DB step; no app code)
- **File (new):** `supabase/migrations/20260930000000_n64_saved_templates.sql`.
  **At authoring time, run `ls supabase/migrations | sort | tail -1` and pick a stamp STRICTLY GREATER**
  (recommended `20260930000000`; if a later sibling appeared, exceed it). Never reuse or edit an applied
  stamp (`db push` keys on the stamp — an edited applied file is silently skipped).
- **Contents, in this order (one file):**
  1. `create table if not exists public.resume_templates (` `id uuid primary key default
     gen_random_uuid()`, `user_id uuid not null references auth.users(id) on delete cascade`,
     `name text not null`, `kind text not null check (kind in ('resume','cover'))`,
     `storage_path text not null`, `created_at timestamptz not null default now()`,
     `updated_at timestamptz not null default now()` `);` — NO `sort_order` (that was a `makeCrudHandlers`
     artefact). Then: `create index if not exists resume_templates_user_idx on … (user_id);`; a
     **unique index `(user_id, kind, lower(name))`**; `enable row level security`; the **four**
     `auth.uid() = user_id` policies (select/insert/update/delete); `grant select,insert,update,delete …
     to authenticated`; `grant all … to service_role` — copied in SHAPE from `tailor_personas.sql`.
  2. **Provenance columns on `public.applications`, PLAIN `add column` (loud — C-1), each nullable:**
     `resume_template_id uuid`, `resume_template_label text`, `cover_template_id uuid`,
     `cover_template_label text`.
  3. **Two FK constraints, PLAIN `add constraint` (loud — C-1), each `on delete set null`:**
     `applications_resume_template_id_fkey` on `resume_template_id`, and
     `applications_cover_template_id_fkey` on `cover_template_id`, both referencing
     `public.resume_templates(id)`. (Table created in step 1.1 before the FK — same file, this order.)
  - Header comment states: authored on assumption (owner ruling 3); missing `if not exists` on columns
    and constraints is DELIBERATE (owner ruling 6); nullable throughout so every pre-migration row keeps
    NULL and degrades gracefully.
- **Landable/verifiable:** the migration file exists, is DB-only, and touches no app code — it can ship
  by itself. **This step must be its own commit/push** (orchestrator pushes; migrations auto-deploy).
- **Files touched:** the one new `.sql` file.
