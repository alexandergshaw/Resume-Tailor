## 0. The design in one paragraph, and what changed the brief

**Design.** One collapsed disclosure, "Customize your plan", between the egress notice and the "Create study plan" button
(and, once a plan exists, "Plan settings" inside the open "Plan outline", beside "Rebuild plan"). Closed, it shows a
one-line summary of what the plan will use ("7 days. Even mix. All areas."), so a user who sets nothing sees the defaults and
still has ONE primary action. Opened, it holds exactly the four knobs the schema already has, as three controls: a **numeric
"Days until your interview" field** (`pace.daysUntil`), a **three-preset "Mix of new and review cards" segmented control**
(`newReviewRatio` 0.75 / 0.5 / 0.25), and one **"Areas" list with a Focus toggle and a Skip toggle per area**
(`weakTopicIds` and `topicScope.excludedAreas`, mutually exclusive by construction). Post-plan, the Areas list offers a
one-tap "Focus on these" built from the learner's OWN missed cards. The knob state is a per-application DRAFT held in the
shell (`StudyPlanClient`); `startBuild` sends it on every build; a change after a plan exists is STAGED and applies on the next
explicit rebuild (the armed "Rebuild plan" already shipped), never silently.

**Five things the tree says that change the brief:**

1. **The schema has no hours-per-day.** Shipped `DEFAULT_KNOBS.pace` is `{ daysUntil: 7 }` and `normalizeKnobs` reads only
   `pace.daysUntil`; any other `pace` key is DROPPED. A control that sent `hoursPerDay` would look saved and persist nothing.
   SC-D ships days-until only and names hours-per-day a decision (OD-SD-4).
2. **`weakTopicIds` is consumed only as fenced free text.** The prompt prints it verbatim under "weak topics the candidate
   flagged"; nothing matches it against `topic.id`; topic ids are content-derived hashes (`t_...`) that change when a rebuild
   re-titles a topic. A control that wrote topic ids would hand the model noise. SC-D writes AREA LABELS (PD-SD-1).
3. **Two of the four knobs are inert under the embedded engine, and one is prompt-only under Gemini.** The honest effect table
   (section 2, F3) drives per-engine caption copy so no control silently does nothing.
4. **There is no knobs-only write path.** `writeStudyPlan` writes `knobs` only as part of a build; `record.knobs` changes only
   when a build succeeds. So an edit made after a plan exists CANNOT be saved without a rebuild: the draft is session state, and
   "the knob change applies on the next rebuild" is not a UX choice but a consequence of the data layer (F4).
5. **Pre-first-plan topics exist after all.** `DIGEST_SECTIONS` (`lib/tracking/applicationDigest.js`) is the fixed, exported
   seven-heading vocabulary of the research digest; the embedded builder turns those exact headings into topics, and the Gemini
   path reads the same headings in its evidence. The pre-plan "Areas" list is that constant (F5).

## 2. Findings that correct or extend the brief (each changes the design)

**F1. Time budget = days-until only.** Section 0 item 1. The owner's "hours-per-day OR days-until-interview" is satisfied
by the second half with zero schema change. Hours-per-day needs `studyPlanSchema.js` (`normalizeKnobs` + test), one bounded
clear-half line in `studyPlanPrompt.js`, and an item cap in the embedded builder. Not invented here: OD-SD-4.

**F2. The value domain of `weakTopicIds` must be decided, and "ids" is the wrong thing to write.** OBSERVED: the only consumers
are `normalizeKnobs` (string coercion) and `buildStudyPlanUserTurn` (printed under a heading, fenced). SC-gen's own plan calls
both arrays "arbitrary user-typed strings (free text)" (`docs/loop/N157.SC-gen.plan.r1.md` section 2.2). A topic id is a hash
the model cannot read and that changes when a rebuild re-titles a topic. *Consequence:* the control writes the topic's AREA
LABEL (the same vocabulary as `excludedAreas`). The key name stays `weakTopicIds` (renaming it is a schema migration event for
every stored row and out of scope); the mismatch between name and content is documented in the pure module and ledgered.

**F3. What each knob actually changes TODAY, by engine (the honesty table the controls must respect).**

| Knob | Gemini engine | Embedded engine | Walkthrough |
|---|---|---|---|
| `newReviewRatio` | prompt steering ("about X% new"); model compliance is unverifiable here | deterministic: `kindAt` spreads `review` evenly (tested) | only the New / Review chip |
| `weakTopicIds` | prompt steering ("extra cards", fenced); unverifiable here | NOT applied (builder header says so) | none |
| `pace.daysUntil` | prompt steering ("Spread the plan over N days") | NOT applied (no `pace` read) | none: no per-card day exists and no anchor date exists |
| `topicScope.excludedAreas` | prompt steering ("leave out entirely"); unverifiable here | deterministic: substring filter on section titles | none |

*Consequence:* the panel carries an engine-aware caption (section 3.5) and a pure `knobEffects(engine)` selector, so the
"focus" and "days" controls never claim an effect the engine cannot deliver. `daysUntil` is stated as "sizes the plan", never as
a schedule or a reminder (there is none).

**F4. No knobs-only write.** A knob edit has no persistence step until a build. The draft therefore lives in the shell, is
keyed to the application AND to the stored knobs it was edited against, and retires itself when a successful build changes
the stored knobs. A failed or preserved rebuild leaves the stored knobs alone, so the draft MUST survive it (the user's
"Try again" must send what they set). This also answers the brief's rebuild question (section 3.7).

**F5. The pre-plan area list is `DIGEST_SECTIONS`.** It is deterministic, instant (no request), identical to the embedded
engine's future topics, and matches how the Gemini evidence is organised. Post-plan the list becomes the plan's own areas
(section 3.8). The first-plan user is therefore never shown an empty or hidden Areas control.

**F6. A plan-derived list loses excluded areas.** After a rebuild with "Size and stage" skipped, the new plan has no such
topic; an option list built only from the plan would drop the row and make the area impossible to re-include. The option
list is `plan areas UNION currently-selected labels`, so a Focus or Skip selection can always be undone.

**F7. Skipping every area yields no plan.** The embedded builder returns zero modules (`NO_CARDS_ERROR`) and a Gemini model
told to leave everything out returns none; a FIRST plan then ends "The plan could not be built." and a rebuild is preserved
(Layer 1). The invalid state is made UNREACHABLE: the Skip toggle of the last non-skipped area is disabled with a visible
reason (section 3.3). `isBuildableKnobs` is the belt for knobs that arrived from outside the UI.

**F8. The scheduling half of `pace` is a different piece of work.** Turning `daysUntil` into a daily target needs an anchor
date (none exists: F-evidence above) and a consumer in the walkthrough. The arch's `studyPlanSchedule.js` and the SC-C design's
"staleness offer" and "standing refresh control" were left with SC-D by SC-C (PD-3 moved only the unsourced-banner button); the
brief for this seat excludes Refresh research and scopes SC-D to the customization controls. Verified not shipped: Grep of
`app/copilot/study` non-test files for `refresh-rebuild|stale` finds only the banner mapping and an unrelated comment. PD-SD-4
files the three as follow-ups with a recommendation (NOT in SC-D).

**F9. Typed numbers are silently rewritten by the normalizer.** `normalizeKnobs` turns `daysUntil` 0, negative, NaN or text
into the DEFAULT 7. A text field that commits raw input would SHOW "0" while the stored knob is 7. The days control validates
before it commits (section 3.3); it never hands the normalizer garbage.

**F10. No server bound on knob size.** `normalizeKnobs` caps nothing, so a tampered request can carry thousand-element
arrays into the prompt fence and the jsonb column. The UI caps (`MAX_AREA_OPTIONS`, `MAX_AREA_LABEL`) are a convenience, not a
boundary. Flagged for the security reviewer (PD-SD-5), not fixed here (the route and schema are not in this chunk).

## 3. The experience (PROPOSAL)

### 3.1 Knob to control to schema field (the whole contract on one screen)

| Owner knob | Control | Writes (exact schema field) | Values | Default | Honoured by |
|---|---|---|---|---|---|
| (3) time budget / pace | Numeric field "Days until your interview" | `pace.daysUntil` | integer 1..`MAX_PLAN_DAYS` (90, GUESS) | 7 (`DEFAULT_KNOBS`) | Gemini prompt only (F3) |
| (1) new-vs-review | 3-preset segmented "Mix of new and review cards" | `newReviewRatio` | 0.75 "Mostly new", 0.5 "Even mix", 0.25 "Mostly review" | 0.5 | both engines |

### 3.3 Each control (states, semantics, copy keys)

**Disclosure.** A plain `Button` (`variant="outlined"`, `TOUCH_TARGET_SX`) with `aria-expanded` and `aria-controls` resolving to
the panel id; local `useState`, NOT `CollapsibleAid` (its open state is a shared persisted choice - the same reason
`StudyPlanOverview` avoids it). Never `variant="contained"` (the "one contained button per step" rule). The panel is
conditionally rendered (absent from the DOM when closed, like the outline), and the panel root is `role="group"` with an
`aria-label`. The panel contains NO headings (it is mounted under h3 in the create step and under the h4/h5 outline); each
knob is a `fieldset` + `legend` (the `FormControl component="fieldset"` + `FormLabel component="legend"` idiom), so heading
levels cannot skip (C1).

**Days field.** `TextField size="small"` with `TOUCH_FIELD_SX`, `type="text"`, `inputMode="numeric"`, `pattern="[0-9]*"`,
`autoComplete="off"`, a real `<label>` ("Days until your interview"), helper text wired by `aria-describedby`. Local string
state so the user can clear the box while typing. COMMIT RULE (F9): the text is parsed with the pure `setDaysUntil`; a whole
number in 1..`MAX_PLAN_DAYS` commits `pace.daysUntil` immediately; anything else (empty, 0, negative, decimal, text, > max)
commits NOTHING, marks the field `error`, and swaps the helper to "Enter a whole number from 1 to 90."; on blur the visible
text snaps back to the last committed value. A leading/trailing space or leading zeros ("007", " 7 ") parse to 7 and commit.
Why a field and not presets: arbitrary days are the real answer ("my interview is Thursday"), a stored value that is off a
preset list would need an extra "custom" segment, and a native `<select>` has the stale-value and label-shrink traps recorded
in [[mui-a11y-traps]] items 9-10. Presets are the alternative (OD-SD-2).

**Mix control.** Three standalone options as an exclusive `ToggleButtonGroup` (the `PracticeSurface` pattern: `size="small"`,
`textTransform: "none"`, `TOUCH_TARGET_SX`), `fullWidth` so the segments share the width and a label may wrap INSIDE its button.
Selected value = the preset whose value EQUALS `knobs.newReviewRatio` exactly; a stored off-preset ratio (only possible from a
foreign write) selects NOTHING and the caption reads "Custom mix: 60 percent new." A tap on an already-selected segment yields
`null` and is swallowed, as `PracticeSurface` and `ModeSwitch` do. Caption (always visible) states the resulting split.
GEOMETRY RISK (owner row): [[copilot-mobile]] records that a `ToggleButtonGroup` never wraps internally; the longest label
"Mostly review" must be measured at 320px. If it does not fit, the fallback is a `RadioGroup row` of three radio labels
(wraps natively, arrow-key navigation, a custom ratio simply selects none).

**Areas list.** One row per area from `areaOptions` (section 3.8): the label (`BREAK_LONG_WORDS_SX`, `flex: 1`,
`minWidth: "0"`) and an exclusive `ToggleButtonGroup` of exactly TWO buttons, "Focus" and "Skip", where "neither pressed" IS the
include state and a re-tap on the pressed one yields `null` and means "back to include" (here `null` is NOT swallowed). The row
is `role="group"` labelled (`aria-labelledby`) by its label element; the buttons are named by their visible text only (no
`aria-label` override, so WCAG 2.5.3 holds, [[mui-a11y-traps]] item 2); their pressed state is `aria-pressed`. Two toggles per
row, not three segments, so a row is one 44px line even at 320px (the label wraps; the toggles do not). Mutual exclusivity of
weak and excluded is STRUCTURAL: one state per area, and `setAreaState` removes the area from the other list. Precedence for a
foreign write that has an area in both lists: Skip wins (the prompt says "leave out entirely"), and the next edit cleans it.
**Last-included guard (F7):** when exactly one area is not skipped, that row's "Skip" button is `disabled` and a visible caption
("At least one area stays included.") wired by `aria-describedby` to it explains why; the explanation never lives in an
`aria-label` (item 8). Caps: at most `MAX_AREA_OPTIONS` rows (24, GUESS) with every currently-selected area always kept, and
labels sliced to `MAX_AREA_LABEL` (80, GUESS) so a model-supplied 400-character "area" cannot wreck the column or the request.

**Disabled while building.** The whole panel is `disabled` (a `fieldset disabled`) while a build runs for the application, so
an edit can never be made against knobs a running build has already captured (such an edit would be retired by the success
reload and silently lost).

### 3.4 The remediation interaction ("mark weak areas; the plan weights them")

Three ways in, all writing the same field, in order of how often a learner reaches them:

1. **Per-area Focus toggle** (pre-plan and post-plan). Tapping Focus on "Interview process" sets that label in
   `weakTopicIds`. Pre-plan the labels are the seven digest headings (F5); post-plan they are the plan's areas.
2. **"Focus on these"** (post-plan only; renders only when at least one card is graded "Missed it"). `suggestFocusAreas({ plan,
   seen })` maps each card graded `GRADE.AGAIN` in the CURRENT plan to its topic's area, counts, sorts by count descending (ties
   in plan order), and one tap sets Focus on all of them. Orphan `seen` keys (cards a rebuild dropped) never count
   (`flattenPlan` ids only). This is the app-over-chat part of the knob: a chat has no record of what the learner missed.
3. **(Deferred, OD-SD-6)** a "Rebuild with extra focus on what I missed" shortcut on the "All cards done" screen, and a
   "Focus" chip on outline topics built from the STORED knobs. Both widen `StudyWalkthrough` again and are separable.

How the mark reaches the knob: Focus toggle or suggestion -> `setAreaState` -> new normalized knobs object -> the shell draft
-> `startBuild` -> `run({ ..., knobs })` -> the request body. The label (not an id) is what the prompt receives.

### 3.5 Per-engine honesty

A pure `knobEffects(engine)` returns which knobs the engine honours: `engine === "embedded"` (the same predicate as
`skipsResearch` and `buildStudyPlanNotice`) honours the mix and skipped areas only; every other engine, including "external"
and an unknown value, is treated as Gemini (the over-state direction the notices module already takes). Under embedded the
panel keeps all four controls usable (so a choice is stored and applies when the user switches engine) and adds ONE caption
(a plain `Typography`, not a live region): "The embedded engine ignores focus areas and the number of days. It does use the mix
and skipped areas." Under Gemini a one-line helper says "Gemini is asked to follow these; the result can vary." The server may
force embedded without the client knowing; the Gemini wording then over-states, which is the safe direction.

The shell builds the panel element once and hands it to both mounts, so the controls are a presentational component

### 3.7 Knob state and data flow

```
PostingPicker                      -> posting.id = applicationId
useStudyPlanRecord(applicationId)  -> record { knobs (stored | null), plan, progress.seen, status }
useStudyKnobs(applicationId, record.knobs)
    base      = normalizeKnobs(record.knobs)              // null -> defaults
    baseKey   = stable JSON of base
    live      = draft && draft.applicationId === applicationId && draft.baseKey === baseKey ? draft.knobs : null
    effective = live ?? base                              // ALWAYS an object, never undefined
    dirty     = live !== null && !knobsEqual(live, base)
    setKnobs(next) -> setDraft({ applicationId, baseKey, knobs: normalizeKnobs(next) })
areaOptions({ plan: record.plan, knobs: effective, seedAreas: DIGEST_SECTIONS })
<StudyPlanControls knobs={effective} onChange={setKnobs} areas suggestions engine disabled={busy} />

   -> requestBuild({ applicationId, engine, knobs }) -> POST /api/study-plan { applicationId, engine, knobs }
   -> generateStudyPlan(normalizeKnobs(body.knobs)) -> writeStudyPlan({ knobs }) -> reload
   -> record.knobs == the knobs sent -> baseKey changes -> the draft retires itself (no effect needed)
```

Rules this pins (each is a test row):

- **Always send the effective knobs.** `knobs: effective` replaces `knobs: record.knobs ?? undefined`. The first create now
  carries an explicit default-equal object instead of omitting the key; server behaviour is identical (omitted normalizes to
  defaults) and no landed component test asserts the omission (section 1, last-but-two row). This also retires the
  "rebuild omits knobs and resets customization" risk (SC-C R2) structurally.
- **Per-application, per-base draft.** A draft for application A is ignored when `applicationId` differs and when the stored
  knobs changed since it was started (another device rebuilt). One slot: switching A to B and back drops A's draft. Stated, not
  hidden.
- **Survives UI churn, not unmount.** Closing the panel, closing the outline, and a remount keyed on `planKey` do not lose the
  draft (it lives above the remount key). Leaving the Study sub-view unmounts the shell and loses it - the same wart the
  selected posting already has (BACKLOG N160). Accepted; persisting a second copy of the knobs per viewer would give two sources
  of truth.
- **Failure keeps the draft.** A failed or preserved rebuild writes nothing server-side, `record.knobs` is unchanged, so
  `live` stays valid and "Try again" sends what the user set.
- **Never alias the defaults.** Every emitted object is a fresh `normalizeKnobs` clone; `DEFAULT_KNOBS` (frozen) is never
  returned or mutated.
- **Spend, stated honestly.** A knob-only rebuild runs no new web research (`rebuild` skips phase 1) but it IS one
  non-grounded plan-writing model call and one of the 12-per-10-minutes tokens on `/api/study-plan`. The arch's "spends
  nothing" meant no grounded search. The Gemini egress sentence covers the call.

### 3.8 The topic list: where it comes from, and the pre-first-plan case

`areaOptions({ plan, knobs, seedAreas })` returns, in order:

1. the distinct areas of the CURRENT plan (`areaOf(topic)` = trimmed `topic.area`, else trimmed `topic.title`, else skipped),
   first-seen order, de-duplicated case-insensitively, first-seen casing kept;
2. then every label currently in `knobs.weakTopicIds` or `knobs.topicScope.excludedAreas` that is not already listed (F6);
3. if the plan contributed NO area (no plan, an `unavailable` row with zero modules, the S3 and S5/S6 states), `seedAreas`
   (`DIGEST_SECTIONS`, in its fixed order) comes first, followed by (2).

Then the `MAX_AREA_OPTIONS` cap, never dropping a selected label. Pre-first-plan therefore shows the seven digest headings with
no request and no spend; nothing about the list depends on research having run. Under a "general plan without research" the
seed list is slightly off (the model writes its own areas), which is harmless and is replaced by the plan's own areas after the
build.

### 3.9 Change after a plan exists: STAGED, not forced (recommended default; alternatives in OD-SD-3)

Changing a knob never rebuilds. Reasons: a rebuild re-words nearly every card so most progress is orphaned (SC-C F7), it costs
a model call and a limiter token, and users change several knobs before applying them. The panel inside the outline shows the
summary and, when `dirty`, a visible note: "Settings changed. Rebuild the plan to apply them." The one action is the existing
"Rebuild plan" (armed on `summary.done > 0`, with the existing armed announcement), which now carries the draft. When the
Skip guard or `isBuildableKnobs` blocks a build, "Rebuild plan" and "Create study plan" are `disabled` with a visible sibling
reason wired by `aria-describedby` (the S0 pattern); never a Tooltip.

Click audit (taps beyond what SC-C already costs): zero-touch first plan = **0 extra** (Create stays one tap). Setting one
knob pre-plan = 1 (open) + 1 to 2 (set) = 2-3 extra. Remediation post-plan = Outline 1 + Plan settings 1 + "Focus on these" 1
+ Rebuild 1 + confirm 1 = 5 (the existing rebuild is 3 with progress).

are themselves model or web derived), sent to Gemini inside the fence. No free text is typed (OD-SD-8), so no new typed-text
