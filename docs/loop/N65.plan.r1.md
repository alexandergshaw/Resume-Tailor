  the required design** (P-R1 below). The decision log (recordDecision, S10, all outcomes) is the usage-readback

## 1. Rulings this plan makes (mechanism choices — the AC/design handed these down)

**P-R1 — No rate limiter on `/api/salary-estimate`.** OWNER-2 forbids inventing a cap. The route ships with
`getUser()` → 401 as its only spend gate; there is no module-scope `createRateLimiter`. Gate order becomes
auth → validate → embedded → stated → grounded (design gate 2 deleted). *Residual, stated:* an authenticated
user can issue many grounded calls; the owner accepted this via OWNER-2, and per-decision usage is readable
from the activity log. The limiter seam remains a documented future insertion point (the `application-digest`
module-scope precedent) if the owner later sets a number.

**P-R2 — Export only the two symbols with production importers; keep the three helpers module-private.**
The `exportReachability.sweep.test.js` LIVE assertions are `ORPHAN_EXPORTS` **71** (`:402`) and
`TEST_REFERENCED` **364** (`:688`) — VERIFIED this round; the in-file comments that say 56 are stale (brief
confirmed). Exporting `parseEstimateRange` / `usableCitations` / `deriveBasisKind` purely so tests can import
them would bump `TEST_REFERENCED` to 367 and force that assertion edited in the same step. Instead they stay
**non-exported** inside `lib/salary/salaryEstimate.js`; the 4b tests exercise them through the public
`buildSalaryEstimate` seam (every S3/S5/S6/S7 behaviour is reachable that way — see §5). Only
`buildSalaryEstimate` (importer: the route) and `postingSalaryStated` (importer: StatusBar) are exported. Net
effect on the sweep: **ORPHAN_EXPORTS and TEST_REFERENCED both unchanged**; no sweep edit in any step. This
narrows design §2's stated export surface and is a reversible mechanism call: if the TDD seat needs a helper
exported, it exports it AND bumps `TEST_REFERENCED` to 367 with a ledger-comment line in the same step.

**P-R3 — JobDescriptionTab is CHECKED-SAFE (does NOT adopt the affordance).** Design §7 marked it "adopt,
conditionally." Re-triage kills the condition: (a) `JobDescriptionTab.js:359` calls `askAiAbout(pin)` where
`pin = { label:"Pasted Job Description", content:"Pasted Job Description:\n<text>" }` — **no title/company**,
so `buildSalaryEstimateInput` would get an empty `title` and the route 400s (title required); the affordance
would be functionally dead. (b) `JobDescriptionTab.test.js:521-524` asserts `askAiAbout` was called with an
**EXACT** `toHaveBeenCalledWith({ label, content })` (two keys) — adding a `posting` key turns that test RED
for zero functional gain. So JobDescriptionTab leaves `posting` unset (the safe default: no affordance), like
PostingUrlTab. The only adoption site this chunk wires is **StatusBar** (a full job object with title/company/
location/salary). This keeps `JobDescriptionTab.test.js:521-524` untouched.

**P-R4 — Sequencing is driven by two green-both-directions sweeps.** Each new export must land with a
production importer, and each `recordDecision(` call must land with its `DECISION_LEDGER` entry, or a sweep
goes RED mid-implementation. This dictates the step bundling in §4 (it is why `postingSalaryStated`'s export is
deferred to the StatusBar step, and why the ledger entry + orchestrator + ChatPanel import are one step).
