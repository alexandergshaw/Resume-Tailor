## 2. Q1 — the exact thrown shape (provider rejection, e.g. Google returns 400)

`refreshTokenNoCache` (`oauth2client.js:238-269`):

```js
try {
    ...
    res = await this.transporter.request(opts);   // opts.method = 'POST'
}
catch (e) {
    if (e instanceof gaxios_1.GaxiosError &&
        e.message === 'invalid_grant' &&
        e.response?.data &&
        /ReAuth/i.test(e.response.data.error_description)) {
        e.message = JSON.stringify(e.response.data);
    }
    throw e;
}
```

`this.transporter` is a `gaxios` `Gaxios` instance. Its `_request`
(`node_modules/gaxios/build/cjs/src/gaxios.js:137-156`), on a non-2xx status:

```js
if (!opts.validateStatus(translatedResponse.status)) {   // validateStatus: 200<=s<300 (oauth2client.js:446-448)
    const errorInfo = GaxiosError.extractAPIErrorFromResponse(
        translatedResponse, `Request failed with status code ${translatedResponse.status}`);
    throw new GaxiosError(errorInfo?.message, opts, translatedResponse, errorInfo);
}
```

`extractAPIErrorFromResponse` (`node_modules/gaxios/build/cjs/src/common.js:147-209`)
branches on whether `res.data.error` is a string or an object. **Google's OAuth token
endpoint body is `{ error: "invalid_grant", error_description: "..." }` — `error` is a
STRING**, so it takes the string branch (`:158-164`):

```js
if (typeof res.data.error === 'string') {
    return { message: res.data.error, code: res.status, status: res.statusText };
}
```

So `errorInfo.message` IS the raw OAuth error code (`"invalid_grant"`,
`"invalid_client"`, …) and `errorInfo.code` is the HTTP status **number**.

`GaxiosError`'s constructor (`common.js:99-134`) then does, given
`(message=errorInfo.message, config=opts, response=translatedResponse, cause=errorInfo)`:

```js
this.config = config;
this.response = response;                 // the real Response, with .status and .data
...
this.status = this.response.status;       // Google's HTTP status
...
else if (cause && typeof cause === 'object' && 'code' in cause &&
         (typeof cause.code === 'string' || typeof cause.code === 'number')) {
    this.code = cause.code;                // = errorInfo.code = res.status — a NUMBER
}
```

**Verified exact property paths for a provider rejection:**

| Path | Value | Verified via |
|---|---|---|
| `err instanceof GaxiosError` | true | `common.js:29` class decl + `refreshTokenNoCache`'s own `e instanceof gaxios_1.GaxiosError` check at `oauth2client.js:262` |
| `err.message` | the raw OAuth code string, e.g. `"invalid_grant"` — **UNLESS** the ReAuth special case fires (see hazard box below), in which case it is rewritten to `JSON.stringify(err.response.data)` | `common.js:154-155,197-201`; `oauth2client.js:261-269` |
| `err.response.status` | Google's HTTP status (400 for `invalid_grant`/`invalid_client` in practice) | `common.js:99-121` (`this.status = this.response.status`, and `this.response = response` is the real translated Response) |
| `err.response.data.error` | the raw OAuth code string, e.g. `"invalid_grant"` — **NOT rewritten by the ReAuth special case**, only `.message` is | `common.js:112-114` (`this.response.data = translateData(...)`, preserves parsed JSON body); `oauth2client.js:264-266` only reassigns `e.message`, never touches `e.response.data` |
| `err.response.data.error_description` | Google's human-readable description | same; read directly by `oauth2client.js:265` |
| `err.code` | the HTTP status **as a number** (e.g. `400`) — **NOT** the OAuth code string. A classifier that reads `err.code` expecting `'invalid_grant'` gets `400` instead. | `common.js:129-134` (`cause` here is `errorInfo` whose `.code = res.status`) |

**Recommendation for the design/implementer (not binding, but load-bearing given
C-0.2):** read `err.response?.data?.error`, never `err.message` and never `err.code`, as
the primary field. Reasons: (a) `err.code` aliases the numeric HTTP status, not the
OAuth code — a same-named trap; (b) `err.message` can be silently rewritten by
`google-auth-library` itself (see next box) — `err.response.data.error` is the one field
neither gaxios nor google-auth-library ever mutates.

### Hazard verified this round: the library rewrites `err.message` under a narrow condition

`oauth2client.js:261-269` — if (and only if) `e.message === 'invalid_grant'` **and**
`e.response.data.error_description` matches `/ReAuth/i`, the library itself replaces
`e.message` with `JSON.stringify(e.response.data)` before the error ever reaches
`gmailClient.js`. This is a real, narrow GCP re-auth/session-control feature (see §5),
not a bug — but it means:
- A classifier keyed on `err.message === 'invalid_grant'` will silently misclassify the
  (rare, GCP-policy) ReAuth case, because by the time it sees the error, `.message` is a
  JSON string, not `'invalid_grant'`.
- A **test fixture** for AC-3 that happens to put the substring "reauth" (any case) in
  its `error_description` will trigger this rewrite even though the test author did not
  intend to exercise the GCP-policy path — an easy way to accidentally write a flaky or
  misleading fixture.
- `err.response.data.error` is untouched either way, which is the concrete reason to
  prefer it over `err.message` as the read path.

## 3. Q3 — network failure (no response) vs provider rejection: the structural difference

`gaxios.js:159-186` (`_request`'s catch, wrapping whatever the fetch layer threw):

```js
catch (e) {
    let err;
    if (e instanceof GaxiosError) { err = e; }
    else if (e instanceof Error) { err = new GaxiosError(e.message, opts, undefined, e); }  // response: undefined
    else { err = new GaxiosError('Unexpected Gaxios Error', opts, undefined, e); }
    const { shouldRetry, config } = await getRetryConfig(err);
    if (shouldRetry && config) { ...; return this._request(opts); }   // internal retry, see below
    ...
    throw err;
}
```

A genuine network failure (DNS, connection refused, timeout — nothing ever answers)
never reaches the `!opts.validateStatus(...)` branch at all; it throws from the fetch
call itself, lands in this `catch`, and is wrapped with the **third constructor argument
(`response`) passed as `undefined`**. `GaxiosError`'s constructor then does
`this.response = response` unconditionally (`common.js:101`), so **`err.response` is
`undefined`** for every network-shaped failure and a real object for every
provider-shaped one. This is the single reliable discriminant, and it is not
speculative: `google-auth-library`'s own code already branches on it, at
`oauth2client.js:375-381` (`getRequestMetadataAsync`'s refresh-error handling):

```js
catch (err) {
    const e = err;
    if (e.response && (e.response.status === 403 || e.response.status === 404)) {
        e.message = `Could not refresh access token: ${e.message}`;
    }
    throw e;
}
```

— i.e. the vendor SDK's own convention for "did we get an HTTP response at all" is
`Boolean(e.response)`, not a key-existence check (`response` is always a defined class
field, so `'response' in err` is true either way and is NOT a valid check — only
truthiness distinguishes them) and not `err.code`.

**What `err.code` looks like on the network path (Node runtime specifically):**
`gaxios.js:526-531` (`#getFetch`) uses the **`node-fetch` package** under Node
(`typeof window === 'undefined'` → `(await import('node-fetch')).default`), not the
native/undici global `fetch`. `node-fetch@3.3.2`'s low-level failure path
(`node_modules/node-fetch/src/index.js:108`):

```js
reject(new FetchError(`request to ${request.url} failed, reason: ${error.message}`, 'system', error));
```

and `FetchError`'s constructor (`node_modules/node-fetch/src/errors/fetch-error.js:17-25`):

```js
if (systemError) {
    this.code = this.errno = systemError.code;      // e.g. 'ECONNREFUSED', 'ENOTFOUND', 'ETIMEDOUT'
    this.erroredSysCall = systemError.syscall;
}
```

`FetchBaseError extends Error` (`node_modules/node-fetch/src/errors/base.js`), so
gaxios's `e instanceof Error` branch matches, and `GaxiosError`'s constructor copies
`cause.code` onto `err.code` (`common.js:129-134`, same code path as §2) — here `cause`
is the `FetchError`, whose `.code` is a **string** OS-level code, not a number. So:

| Signal | Provider rejection | Network failure |
|---|---|---|
| `err.response` | defined object (`.status`, `.data`) | `undefined` |
| `err.code` | number (HTTP status, e.g. `400`) | string (`'ECONNREFUSED'`, `'ENOTFOUND'`, `'ETIMEDOUT'`, or `'AbortError'`/`'TimeoutError'` for a timeout — `gaxios/build/cjs/src/retry.js:95-96` checks exactly these two string codes) | 
| `err.message` | the OAuth code or `Request failed with status code N` | `node-fetch`'s `"request to <url> failed, reason: <sysMsg>"` |

**Caveat, stated honestly:** the exact OS code strings (`ECONNREFUSED` etc.) are a
property of Node's `net`/`dns` layer via `node-fetch`, not documented/guaranteed by
`gaxios` or `google-auth-library` themselves — do not build the classifier's pass/fail
on enumerating specific OS codes. `Boolean(err.response) === false` is the verified,
stable signal; treat any falsy-`response` GaxiosError uniformly as the network/transient
case, which is exactly what AC-3 asks for (row iii, "network-level error (no HTTP
response)").

**Internal retries already happen before your code ever sees a network failure.**
`gaxios/build/cjs/src/retry.js:16-134` (`getRetryConfig`/`shouldRetryRequest`), combined
with `AuthClient.RETRY_CONFIG` (`node_modules/google-auth-library/build/src/auth/authclient.js:276-283`,
which the refresh call spreads in at `oauth2client.js:252`) —
`{ retry: true, retryConfig: { httpMethodsToRetry: ['GET','PUT','POST','HEAD','OPTIONS','DELETE'] } }`
— means: POST is retried (it's in the list), default `retry: 3` attempts, and for a
no-response error specifically `noResponseRetries: 2` (`retry.js:32-35`) before giving
up. Retryable HTTP status ranges are `[100-199],[408],[429],[500-599]`
(`retry.js:50-64`) — **400/401/403 are never retried**. Net effect: by the time
`gmailClient.js`'s catch sees a network-shaped error, gaxios has already retried it
internally a couple of times; what surfaces to app code is already a "persisted past a
couple of retries" failure, not a single blip. This is useful context for AC-8's
"don't stop polling on one transient blip" — the SDK itself already absorbs the single
blip before your code is even invoked.

## 4. Reaching the real `GaxiosError` class without a new dependency

`gaxios` and `google-auth-library` are **not** direct dependencies of
`hello-world/package.json` (only `googleapis` is, `:34`). But:
- `node_modules/google-auth-library/build/src/index.js:36` —
  `exports.gaxios = require("gaxios");`
- `node_modules/googleapis/build/src/index.js` —
  `exports.Auth = require("google-auth-library");`

So `require('googleapis').Auth.gaxios.GaxiosError` (or the ESM equivalent
`import { Auth } from 'googleapis'`) reaches the exact same singleton class used
internally — confirmed a singleton because only one copy of `gaxios` exists under
`node_modules` (checked above). No `package.json` change needed. `GaxiosError` also
carries a version-checked `Symbol.hasInstance` (`common.js:82-98`) so `instanceof`
stays correct even across duplicate installs, as a second layer of safety.
**Recommendation:** use this path for an `instanceof` check if the design wants one; a
pure shape check (`Boolean(err?.response)` + `typeof err?.response?.data?.error ===
'string'`) also works and needs no import at all.

## 5. Q2/Q4 — which codes mean what, and is `invalid_grant` really overloaded

**Primary source: RFC 6749 §5.2** (fetched 2026-09-28,
`https://www.rfc-editor.org/rfc/rfc6749.txt`), verbatim:

> **invalid_client**: "Client authentication failed (e.g., unknown client, no client
> authentication included, or unsupported authentication method)."
>
> **invalid_grant**: "The provided authorization grant (e.g., authorization code,
> resource owner credentials) or refresh token is invalid, expired, revoked, does not
> match the redirection URI used in the authorization request, or was issued to another
> client."

**This is the direct answer to Q4: `invalid_grant` is ONE error code defined by the spec
itself to cover at least FIVE distinct root causes** (invalid / expired / revoked /
redirect-URI-mismatch / wrong-client). The redirect-URI-mismatch and wrong-client
readings don't apply to a refresh (those are authorization-code-exchange failure modes);
for a refresh specifically it collapses "invalid, expired, revoked" — three causes, one
code, by spec design, not an implementation shortcut. **They are not distinguishable
from the code alone.** This matches — and now backs with a primary spec citation — what
the AC already asserted as F-1/AC-3 row (ii)'s premise.

**Primary source: Google's own web-server OAuth guide** (fetched 2026-09-28,
`https://developers.google.com/identity/protocols/oauth2/web-server`), paraphrased
content confirmed present on the page:
- On `invalid_grant`: "the token may have expired or has been invalidated ... Authenticate
  the user again and ask for user consent to obtain new tokens" — i.e. Google's own
  guidance is reauth, unconditionally, regardless of which of the RFC's sub-causes fired.
- On `invalid_client` (client-secret mismatch): "The OAuth client secret is incorrect.
  Review the OAuth client configuration" — an operator/config action, never something
  the end user's reconnect can fix (confirms AC's F-2 exactly: the *user's* reconnect
  hits the same bad credentials at `oauth2callback/route.js` and fails again).

**Primary source: Google's identity/oauth2 overview page** (fetched 2026-09-28,
`https://developers.google.com/identity/protocols/oauth2`) lists concrete reasons a
refresh token stops working, ALL of which surface as the same `invalid_grant`:
user revoked access; refresh token unused for six months; user changed password while
holding Gmail-scoped tokens; account exceeded its live-refresh-token limit; time-based
access grant expired; admin set a scope to Restricted (this one has its own code,
`admin_policy_enforced`, per the page — a possible SIXTH value worth a defensive
"unrecognised → reauth_required" fallback, which AC-3 row (iv) already mandates); for
GCP-session-controlled accounts, session length exceeded. This corroborates, from the
vendor directly, that the "no tokens" three-way (never/disconnected/TTL) is not the only
place indistinguishable causes collapse — `invalid_grant` itself is a six-or-more-way
collapse by design, and the AC's decision to not attempt finer distinction (F-1) is the
right call for this code too, not just the no-tokens path.

**One narrow discriminant exists but is verified NOT applicable here.** The overview
page also documents an `error_subtype` field (e.g. `"invalid_rapt"`) that separates a
revoked token from a GCP session-control failure — but this is scoped to Google Cloud
Platform / workforce-identity session policies. `gmailClient.js:5-8` requests only
`https://www.googleapis.com/auth/gmail.readonly` and `.../userinfo.email` through a
standard end-user consent flow (`createOAuth2Client` + `generateAuthUrl`,
`gmailClient.js:15-38`), not a GCP-managed identity — there is no evidence this repo's
OAuth client is subject to session control. **Do not build a classifier branch on
`error_subtype` without first confirming GCP session control is actually enabled for
this app's OAuth client** (out of scope for this research round to confirm either way).

## 6. Direct answers, summarized

1. **Shape (provider rejection):** `err instanceof GaxiosError` (from `gaxios@7.1.4`,
   reachable via `require('googleapis').Auth.gaxios.GaxiosError`, no new dependency).
   Read `err.response.data.error` for the OAuth code (a string: `"invalid_grant"`,
   `"invalid_client"`, etc.) and `err.response.data.error_description` for the message.
   Do not read `err.code` (it is the numeric HTTP status, not the OAuth code) or
   `err.message` (can be silently rewritten by google-auth-library for a narrow
   GCP-ReAuth case — §2 hazard box).
2. **Which codes mean what:** `invalid_grant` → grant is gone, reauth required (RFC
   6749 §5.2 + Google's own guide, both quoted above). `invalid_client` → operator/config
   failure (bad client secret), never user-fixable (RFC 6749 §5.2 + Google's guide).
   Everything else (no `err.response` at all) is transient/network.
3. **Network failure structural difference:** `err.response` is `undefined` (vs. a
   defined object with `.status`/`.data` for a provider rejection) — this is the one
   stable, vendor-precedented (`oauth2client.js:377`) discriminant. `err.code` becomes a
   string OS/abort code (`ECONNREFUSED`, `ETIMEDOUT`, `AbortError`, `TimeoutError`)
   rather than a numeric HTTP status, but do not gate correctness on enumerating those
   strings — gate on `Boolean(err.response)`.
4. **Is `invalid_grant` genuinely overloaded:** Yes, confirmed at the RFC-spec level
   (not just Google's implementation) — at least three sub-causes for a refresh
   (invalid/expired/revoked) collapse to one code, and Google's own docs list at least
   six real-world triggers that all surface as `invalid_grant`. They are **not**
   distinguishable from the thrown error alone. This is a valid, honestly-reported
   non-distinction, consistent with the AC's F-1 finding for the sibling "no tokens"
   case.
