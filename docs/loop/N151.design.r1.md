## 1. The decision that is expensive to reverse: **what IS a "template" here** (the ruling the whole chunk rests on)

**Ruling (recommended, strong evidence): a template is the FORMATTING / LAYOUT — the `.docx` shell
(styles, fonts, section structure, bullet/heading formatting) — into which résumé CONTENT is poured.
It is NOT a content base, and NOT a set of tailoring preferences.**

Why this is forced by the code, not a preference:
- The one primitive that applies a template, `buildDocxFromUploadedTemplate(file, text, lines)` (F8),
  takes the template's `.docx` and **replaces its paragraph text with the generated content while
  preserving run/paragraph styling**. The template contributes styling; the content comes from
  elsewhere. That is "formatting, not content," by construction.
- The existing override (F7) already treats a stored template exactly this way, for all three engines.
- This matches the standing `download-rebuild-formatting` rule: edited downloads rebuild the engine's
  content onto a docx shell; the template IS that shell.

Consequences that fall out of this ruling and that the AC/plan/TDD seats must honour:
- **"Regenerate into another template X" = re-run `resolveDocumentBlob` on the document's EXISTING
  content (`text`/`lines`) with `formattingTemplate = X`.** No engine call is needed; this is a pure
  client re-render through the already-shipped override (F7, F13). This is why capability 3 is cheap.
- **A template must be a `.docx`.** `isDocxResume` gates the override (F7); a PDF/image material can be
  stored but cannot serve as a formatting template. See OR-2.
- **Per-engine "template bytes" plumbing is NOT needed** (see §2 reconciliation). The engine produces
  content; the chosen template's formatting is applied uniformly at egress on the client.

## 2. Reconciliation: per-engine behaviour, N89 Part 2, and why N151 adds no engine plumbing

The coordinator asked for per-engine (embedded/external/gemini) behaviour for template bytes, reconciled
with N89 Part 2. The honest structural answer:

- **Formatting-template application is engine-independent and already engine-uniform** (F6 + F7). The
  engine only yields CONTENT (text/lines) and, for byte engines, its own native docx. The *chosen
  template's* formatting is applied afterward, on the client, at `resolveDocumentBlob`, regardless of
  which engine produced the content. So N151's "which template formats the output" does **not** branch
  per engine. This is the single most important reconciliation point: **do not build per-engine
  template pipelines; ride the existing client override.**
- The only genuinely per-engine fact is what a *capture-from-a-generated-document* reflects (F6:
  embedded→bundled shell, external→remote shell, gemini→user's uploaded shell). That nuance belongs to
  N97's existing preview-modal "capture current doc" path, NOT to N151's materials-library path —
  because N151's library templates are the user's **own uploaded `.docx` files**, whose bytes are
  unambiguous and engine-free. (If N151 keeps the preview-modal capture control, F6/OD-A still apply to
  it; see OR-6.)
- **N89 Part 2 (F14)** stores a per-ENTRY `coverLetterTemplatePath` so one specific generated letter
  rebuilds across reloads. That is per-application provenance. N151's library is **per-user, reusable,
  chosen**. They touch the same bucket but are disjoint key spaces (`${userId}/materials/…` and the
  template paths below vs. an entry's own stored path). **No duplication; do not merge them.**

## 3. Capability 1 — MARK A MATERIALS RÉSUMÉ AS A (LIBRARY) TEMPLATE

### 3.1 The data: the library already exists in `resume_templates`; N97 used it degenerately
F1 shows the shipped table permits many named rows per `(user_id, kind)` — the unique index is on
`(user_id, kind, lower(name))`, not on `(user_id, kind)`. So **the library needs NO schema change.**
N151 writes ordinary named rows; N97's single reserved-name row simply becomes one library entry among
many (backward-compat in §6.1). **This retires N97's "single default per type" ruling as the
coordinator directed** — the reserved-name hack (F3) is generalised into named entries.

### 3.2 The write: `registerMaterialAsTemplate`
"Mark this materials file as a template" copies the material's bytes to a per-template storage object
and inserts a named `resume_templates` row:
- **Storage path: `${userId}/templates/${id}.docx`** (per-template, N64's original per-id model —
  NOT N97's fixed per-kind path, which only fits a single default). Copy the bytes (do not point at the
  material's own `${userId}/materials/${name}` path): decoupling means deleting/renaming the material
  never breaks a template, and a template is an immutable snapshot of the formatting at mark time.
- **Name**: default to the material's filename minus extension; user-editable; uniqueness per
  `(user,kind)` enforced by the shipped unique index — a collision is caught and surfaced as a friendly
  "you already have a template named X" (never a raw 23505), exactly as F3's store already catches
  unique violations.
- **kind**: `'resume'` from the materials section (owner's words: "resume"). Cover letters: see OR-3.

### 3.3 The constraint that must be structural, not incidental
Only a `.docx` material can become a template (F7 gate). The "Mark as template" control must be
**absent/disabled for non-`.docx` materials** with a clear reason, and the route must reject non-docx
bytes — so a PDF can never enter the library and later produce an empty render at the override (F7's
`isDocxResume` would silently skip it, which is a worse failure than refusing up front). See OR-2.

## 4. Capability 2 — SELECT WHICH TEMPLATE, WHEN (the switcher + remembered choice)

### 4.1 The one new data decision: a per-(user,kind) SELECTION pointer (needs a small additive migration)
The library is "many rows"; consumption (F7/F9) resolves "the one template to format with." Something
must record **which** library template is active for the next generation, remembered across sessions
(minimize-clicks: don't re-ask). The shipped table has no such column (F1). Three options:

| Opt | Mechanism | Verdict |
|-----|-----------|---------|
| **A (recommended)** | New table `public.template_selections(user_id uuid, kind text, template_id uuid null → resume_templates(id) ON DELETE SET NULL, updated_at)`, **PK(user_id,kind)**, RLS `auth.uid()=user_id`, 4 policies. | "One selection per (user,kind)" is structural (the PK). Flip = one `upsert`. `ON DELETE SET NULL` means deleting the selected template cleanly falls back to "no selection" (→ today's native rendering, AC-8). Additive, low blast radius. |
| B | `boolean selected` + partial unique `(user_id,kind) where selected` on `resume_templates`. | Also structural, but a flip is two writes (clear old + set new) or a trigger; more moving parts than A. |
| C | Client-only (localStorage) last choice. | No cross-device, and consumption is server-mediated via the route (F9) — the server can't read localStorage. Rejected. |

**Recommend A.** Migration stamp **later than `20261008000000`** (F15), e.g. `20261008010000_…`;
additive-only; modelled on the RLS-loop shape N97 cites. This is the chunk's one expensive-to-reverse
data choice — flagged as **OR-4** for an owner/orchestrator ruling before the plan encodes it.

### 4.2 The consumption generalises N97's resolver (OWNED blast radius)
`resolveDefaultTemplateFile(userId, kind)` (F9) evolves from "fetch the reserved-name default's bytes"
to "fetch the **selected** template's bytes": the route's `GET ?kind=&bytes=1` resolves
`template_selections → resume_templates.storage_path → bytes`. **The client signature `(userId, kind)`
and all four call sites stay unchanged** (F9) — only what the server resolves changes. That keeps the
blast radius to the route + store, not the four consumers.

### 4.3 Where the switcher lives (UX seam — 1c owns the exact surface; structure fixes the contract)
The selection write is a single route call (`PUT ?kind=` with `template_id`, or a new
`/api/templates/select`). Recommended surface: a **template picker in the materials section** (next to
the library list) and/or the generate controls, showing the current selection and the library; choosing
one writes the pointer. Minimize-clicks: the picker defaults to the current selection; no confirmation.
The structural contract (a `(user,kind)→template_id` upsert + the resolver reading it) is identical
wherever 1c puts the control.

## 5. Capability 3 — REGENERATE EXISTING CONTENT INTO ANOTHER TEMPLATE

This is the cheapest capability because the mechanism is F7 + F13, already shipped.

**"Re-render document D's content into template X" = call `resolveDocumentBlob` with D's existing
`text`/`lines` and `formattingTemplate = X` (a `.docx` File).** The override (F7 `:700-702`) rebuilds
the content into X's formatting via `buildDocxFromUploadedTemplate`, ignoring `engineDocxB64`/
`templateDocxB64` (F13). X is resolved either from the **library** (bytes via the route, as §4.2) or
from an **on-the-spot upload** (a `.docx` File passed straight through — no storage needed).

What N151 adds for capability 3 (minimum meaningful):
- A preview/edit-modal action **"Re-render in a different template…"** that opens a picker (library +
  "upload a .docx") and sets that document's `formattingTemplate` for its preview + download. Because
  the preview and download already thread `formattingTemplate` (F9, `useDocumentPreview.js:520`), this
  is state + a picker, not new rendering.
- **Fidelity ceiling (flag, not blocker):** F8's `alignLinesToSlots` aligns by content and clones for
  extra lines, so cross-structure renders degrade gracefully rather than positionally; but a template
  whose paragraph structure is very unlike the content (e.g. a one-column template fed two-column
  content) can still render awkwardly. This is an inherent property of the text-swap rebuild, not a
  N151 regression. AC/TDD must test with structurally-reasonable templates and treat gross
  structural mismatch as a known limitation (future: placeholder-keyed mapping). See §9.3.

**OR-5:** does "regenerate into X" PERSIST (replace the stored/generated output + record provenance via
F2's unused `applications.*_template_id` columns), or produce a one-off preview/download only?
Recommend **one-off preview+download** for the first slice (matches N97's egress-only model, writes no
provenance, zero retroactive-change risk); persisting is a clean follow-up that finally uses F2's
columns. Flagged for the owner.

## 6. Backward-compat, replace semantics, scope boundary

### 6.1 N97 reserved rows keep working
Existing users may have an N97 reserved-name row (F3). Under the library model it is just a named entry.
**Initialisation**: when `template_selections` is introduced (§4.1), the resolver falls back to the
reserved-name row for a `(user,kind)` with no explicit selection yet — i.e. the consumption reads
`selection ?? reserved-name-row ?? null`. So a current user's default keeps formatting their output with
zero action. This fallback is removable once selections are universally written.

### 6.2 Replace / delete
- Marking a new template = a new row + new object; it does NOT overwrite others (the library grows;
  bounded only by the user's own deletes — a library CRUD delete removes row + object, RLS-gated).
- Deleting the selected template → `template_selections.template_id` goes NULL (A's `ON DELETE SET
  NULL`) → consumption resolves null → today's native rendering (AC-8). No dangling bytes render.
- Past applications: frozen output bytes are read independently of any template (N97 §5 CITED), so
  marking/selecting/deleting templates never retroactively changes a past download.

### 6.3 Explicitly OUT of scope
- **Email templates** — `resume_templates.kind` CHECK excludes `'email'` (F1); the route rejects it
  (F5). N89 territory. Structurally impossible here; keep it so.
- **Industry/condition auto-apply** (N64's owner request half B) — auto-selecting a template by the
  posting's industry. Not requested here; needs a condition→template map. OUT.
- **Server-side engine template injection** — rejected in §2; the override is client-side and uniform.
- **Per-application provenance writes** (F2 columns) — OUT unless OR-5 chooses persistence.
