### 1.1 The deleted feature, as a precedent (OBSERVED from git: `git show 5b9d79f^:hello-world/app/copilot/AnswerAids.js`)

- Bold lead "Not from your resume." opening the dd, NOT only the dt. The comment records why: both `dl`s are `display: grid`, which drops description-list semantics in WebKit, so an orphaned `dt` has no programmatic tie to its value; the warning has to live in the `dd`.

- No em dash in labels (not spoken at default screen-reader punctuation).
- Pending cue was plain text, never `role="alert"`, never an `Alert`.

Avoid:
- The block was a title + four labelled sections + three outcomes + a two-sentence disclosure. The code comment on that row records the owner's reaction: far too verbose; keep the core with the project details and numbers, "much shorter and bulleted". That is the owner's stated taste for THIS kind of content on THIS surface, and I design to it (section 9).
- It hid a failed tailoring entirely. AC-N143-9/-10/-14 require a visible, honest failed state, so that choice is reversed on purpose.

## 2. The design in one paragraph (PROPOSAL)

The two hypothetical rows form a THIRD group in `AnswerAids`, placed LAST (after the posting's words), under its
own separator, with a one-line group header "Example projects (invented)". This follows the component's own rule:
groups are "whose material it is", and invented material is a third provenance that must not sit in the same
list as the candidate's real project. Inside the group, "Ready example" (pre-warmed, picked for this question, never
a spinner) comes first and "Example for this question" (written now, arrives later) comes second, so the late
arrival is appended below everything already on screen and never shifts what the candidate is reading. Every piece
of invented content opens with a bold "Not from your resume." in the `dd`, unconditionally. The default shows the
content with zero clicks; the header is a native disclosure button that hides the whole group, remembered across reloads.
Pending, warming and failed states are one quiet line each; none blocks the answer and none uses `role="alert"`.

## 3. Labels and copy (PROPOSAL; strings in the pin table are exact)

### 3.1 What each label has to do in one glance

A candidate on camera takes in roughly one phrase per row. The left column must answer, in order: (a) is this mine?
(b) which of the two is this? The `dd` lead answers (a) a second time and survives the WebKit orphaned-`dt` case.

| Row | dt (what it is) | Why the candidate looks at it | How it reads against the real row |
|---|---|---|---|
| Real, unchanged | "Project to talk about" | It is yours; say it. | no rule, no lead |
| Row 1 | "Ready example" | Already there when the answer lands; picked from a set made for this posting to fit this question. The "Fits" signal is the competency prefix on its title line. | accent rule + bold lead |
| Row 2 | "Example for this question" | Written just now for exactly this question; arrives a beat later. Use it when the ready one is a weak fit. | accent rule + bold lead |

"Ready example" is the owner's own name for the instant one (BACKLOG N141 text: "'ready example' feature") and the
deleted feature's label. I deliberately do NOT reuse "Tailored to this question": "tailored" is this product's word
for résumé tailoring, and that label never named its noun. "On-the-spot" (the owner's word for Row 2) says how it was
made, not why to look; "for this question" says why.

| R1_FAILED | `Couldn't prepare examples for this posting.` | Row 1 failed |
| R1_RETRY | `Try again` (in flight: `Trying again`) | the only control in a row |
| R2_PENDING | `Writing one for this question…` | Row 2 pending (U+2026, matching the existing visible "Drafting…" / "Tailoring to this question…" style; never inside an `aria-label`) |

Copy rules (checkable): no em dash or en dash in any of the above (spoken-punctuation precedent, R-136); no emoji;

instruction that the deleted copy buried in its second sentence ("Replace them with your own"), in 6 words instead
of the old 2 sentences. The header says "(invented)" so a collapsed group is still honest on its own, and so a screen
reader landing on the button hears it. The three signals (header, bold lead, accent rule) are deliberate redundancy
for the single lie that ends an interview; they cost one short line, not one per row beyond the lead.

## 4. Row 1 - "Ready example" (pre-warmed pool, picked per question)

Row 1's pick is synchronous with the answer's `done` frame (AC-N143-6: zero model calls). Therefore Row 1 NEVER shows
a spinner or skeleton in any state. Its only genuinely asynchronous state is the application-level "pool not ready yet".

### 4.1 State table

| ID | When (observable data) | dt | dd shows | Notes |
|---|---|---|---|---|
| R1-NA | No application id on the draft, OR engine is embedded, OR feature unavailable | row absent | row absent. If Row 2 is also absent, the whole group (header, separator) is absent | Not an error and not a tease. Matches "no posting selected means no posting group" in the existing component. |
| R1-W (warming) | Pool row absent or `pending`, AND a prewarm is known in flight (or `pending` is younger than POOL_PENDING_MAX_AGE) | `Ready example` | `R1_WARMING`, regular weight, `--text-secondary`. No accent rule, no lead (nothing invented is on screen) | A bare absence with NO request in flight must NOT claim "being prepared": it renders as R1-F (the lie would otherwise outlive the cause). `pending` older than POOL_PENDING_MAX_AGE (guess; named, owner-tunable) renders as R1-F so a crashed generation cannot say "preparing" forever. |
| R1-R (ready, matched) | Pool `ready`, the selected entry passes the render guard (non-empty title and at least one bullet/body) and the selection reports a close fit | `Ready example` | accent rule; lead; `{competency}: {title}` in 600 weight; bullets | The competency prefix doubles as the visible "why this one" and lets the owner see a mis-selection at a glance (probe cause d). Prefix omitted if the competency is blank. |
| R1-N (no close match) | Pool `ready`, selection reports no close fit, OR the selected entry fails the render guard | `Ready example` | `R1_NO_MATCH`, `--text-secondary` | One quiet line. Mirrors the repo's own honesty rule for the real project: `answerAids.js` suppresses an unmatched page ("the first eligible one on file, not the one this question is about") and `roleLabel` refuses to call an unmatched role "Closest". | R1-F (failed) | Pool `failed`; OR `ready` with zero usable entries; OR `pending` past POOL_PENDING_MAX_AGE; OR absent with nothing in flight | `Ready example` | `R1_FAILED` + a `Try again` text button when the surface can retry (4.2) | `ready` with zero usable entries is R1-F, never R1-N: "no close match" would claim a pool was searched. The answer and every other row are untouched. Plain text; no `role="alert"`, no `Alert`. |

### 4.2 Retry control (the only control inside a row)

- Rendered only when the surface passes a retry handler (prop present). `HistoryItem` and any non-current card
  pass none, so they show `R1_FAILED` as text only. Reason: the failure is per application, so one retry on the
  current surface serves every later question; N buttons across N cards would be N duplicate controls.
- It is a native `<button>` (MUI `Button`, text variant, `TOUCH_TARGET_SX`), accessible name exactly `Try again`.
  No Tooltip (mui-a11y-traps 1 and 2).
- In flight it STAYS MOUNTED and focusable, text becomes `Trying again`, and it is `aria-disabled="true"` with its
  click ignored. It is not natively `disabled` and is not removed: a disabled or unmounted focused control drops
  keyboard focus to `<body>`. When the pool then lands the row re-renders as R1-W/R1-R/R1-F; if the button unmounts
  at that point, focus moves to the row's `dd` (`tabIndex={-1}`), the same programmatic-focus pattern `CurrentAnswerPanel` uses
  for its revealed container.
- Rate-limit denial from the prewarm route (AC-N143-17) returns the row to R1-F with the same text; the 429 is not
  surfaced as a separate message (nothing actionable for the candidate; the session log carries it).

### 4.3 Rendering invariants for any hypothetical content (both rows)

1. The lead renders for ANY content in these two rows, regardless of the entry's `hypothetical` field. A missing or
   `false` flag cannot remove it (AC-N143-13: ambiguous provenance renders AS hypothetical). The flag is never read to
   decide the label.
2. The lead is the first child of the `dd`, before the title (reading order: warning, then content).
3. Nothing from a `pending`/`failed`/empty/malformed entry renders as a title or bullet (AC-N143-14 ii). Anything
   that fails the render guard is dropped, and if that empties the row the state is R1-N (selected entry) or R1-F (empty pool).

### 5.2 Announcement policy (a11y)

Row 2's arrival is NOT announced. Reasons: it is supplementary, it arrives mid-read, `polite` is one shared queue and
the screen already has several polite regions (mui-a11y-traps 4: a live region starves its neighbours), and the
existing answer-status regions are keyed to the answer, not to a supplementary row. The pending text is ordinary
content in reading order; `aria-busy="true"` marks it. A screen-reader user who reaches the row reads its current
state. This must be re-judged at 9b.

## 7. The 3-to-5 row composite: hierarchy decision

### 7.1 Decision (PROPOSAL; ruling R1 requested because it departs from the owner's word "beside")

Five possible rows, three of them project-flavoured (one real, two invented). Hierarchy, top to bottom:

1. The drafted answer bullets (unchanged; the primary content, above the aids).
2. YOURS: role, "Project to talk about" (unchanged group, first).
3. THE POSTING'S: "Words from the posting to work in" (unchanged group, second; short, chip row).
4. INVENTED, subordinate: "Example projects (invented)" group, LAST: "Ready example", then "Example for this question".

Three reasons the invented group goes last and separate rather than directly under "Project to talk about":

- Confusion control. The component's own grouping rule is provenance. Adjacent "Project to talk about" / "Ready example"
  / "Example for this question" stacks three project rows in one list, distinguished only by a 2px rule. Interposing the
  words row and a separator makes "mine" and "not mine" two different places, which is the AC-N143-13 mitigation done structurally.
- No layout shift for what the candidate is reading. Row 2 arrives late. Anything placed above the words row would push
  the words (and, in the bounded dashboard scroll area, the candidate's reading position) down when it lands. Appended last, its
  arrival moves nothing that was already on screen. This is checkable: Row 2 is the last element in DOM order.
- Failure containment. If the owner's quality probe (AC-N143-Q) shows the content is weak, the weakest, newest, riskiest content is the lowest and the easiest to hide.

Alternatives considered and rejected:

| Alternative | Why it lost |
|---|---|
| A. Flat insertion: role, project, Ready, For-this-question, words (literally "beside" the real project) | Highest confusion risk; Row 2's arrival pushes the words row. Kept as the fallback if the owner rules "beside" is literal (R1): same states and copy, the two `Aid`s join the first `dl` after "Project to talk about", the separator and header drop, and the accent rule becomes the only structural differentiator. |
| B. Tabs or a segmented control "Ready / For this question" | One click to see one of two, hides the second, adds a tab stop pair, and a `tabpanel` inside a `dl`. Violates minimize-clicks for no gain. |
| C. Per-row collapse | Two controls for one decision; the useful row would be buried by default or the state doubled. |
| D. Merge both into one row with two entries | Loses independent state and label per source; the late one and the instant one need different treatments. |
| E. Hidden until asked ("Show examples") | Breaks the zero-click default. |
| F. Replace "Project to talk about" when a pool entry matches | Forbidden by AC-N143-12 ("beside, not replacing"); also removes the candidate's truth. |

### 7.2 Collapse (PROPOSAL; ruling R2 requested)

- ONE group-level disclosure, default OPEN, remembered. Never per row.
- The header is a native button: text `Example projects (invented)`, `aria-expanded`, `aria-controls` -> the group's `dl`,
  the open/closed glyph inside an `aria-hidden` span (mui-a11y-traps 7; copied from `HistoryItem`), `TOUCH_TARGET_SX`, no Tooltip.
- Collapsed: only the header remains (one line), still honest ("invented" is in its text). The collapsed `dl` and its
  `Try again` button are out of the accessibility tree and the tab order (unmounted or `hidden`).
- Persisted through `createChoiceStore` (the `useCodeLanguage.js` pattern): proposed key `copilot-example-projects`,
  values open/closed, default open, a storage failure falls back to open without throwing. This is the only new persisted fact.
- Why bother in N143 when N144 will rework presentation: the owner already removed this feature once, scorched-earth, over
  content they disliked. A one-click, remembered hide is the cheap hedge that makes "I don't want these" a setting rather
  than a deletion, and it is also a user-side kill switch if the quality probe comes back poor.
- If R2 rules it out: the header becomes a static non-heading caption with the same text (same `role="group"` naming); nothing
  else in this document changes except section 8's rows marked (toggle).
- Considered and deferred: "hidden = do not generate Row 2" (saves a billed call per question and answers part of AC D3).
  It multiplies the state machine (hidden so not generated, opened later, needs a "generate now" action) and needs a request
  flag. Not N143.

### 7.3 Semantics and reading order

Structure outline (a design of the DOM contract, not an implementation):

```
AnswerAids root (existing wrapper)
  dl  (group 1: role + project)                 existing
  separator                                     existing
  dl  (group 2: posting words)                  existing
  separator                                     NEW, rendered iff any earlier group rendered
  div role="group" aria-labelledby=<header id>  NEW
    button#header  "Example projects (invented)"  aria-expanded, aria-controls=<dl id>   (toggle)
    dl#<dl id>  AID_GRID_SX                     NEW, its own dl (first-of-type reset)
      dt "Ready example"                  dd  [accent rule] lead / competency: title / ul>li bullets  | state line
      dt "Example for this question"      dd  [accent rule] lead / title / ul>li bullets             | state line
```

- Reading order = DOM order = visual order. No CSS `order` anywhere (copilot-mobile: `order` moves pixels, not focus).
- No heading is added (the header comment forbids a new heading level under the three parent headings). The group name comes
  from a labelled `role="group"`, not from `h*`.
- Each row is a real `dt`/`dd` pair inside a `dl`, as today. The honesty lead is inside the `dd` (WebKit orphaned-`dt` rationale, section 1.1).
- The early return must count the new group: `AnswerAids` returns `null` only when ALL of role/project, words and the
  examples group are absent. The existing test "renders nothing at all when there is nothing to show" stays green because
  the new group is absent whenever its data is absent (R1-NA/R2-NA).
- Accessible names: header button = its visible text (WCAG 2.5.3, visible text is the whole name); rows are named by their `dt`;
  `Try again` = its visible text. No `aria-label` overrides, no Tooltip anywhere in the group.
- All new text uses `--text-primary` or `--text-secondary`. `--text-muted` is not used for any new text (3.90:1 on `--bg-soft`).
- The accent rule is decorative reinforcement of the text lead, never the only carrier of "this is invented".

| Download the log covering this feature | 1 | The existing "Download session log" (section 9). |
| The same content in the deleted feature | 0 | Parity; nothing here costs more than what it replaces. |

No wizard, no confirmation, no menu. The only choice the user is asked to make is the optional hide.

### 8.2 Keyboard path and focus order

New tab stops, in DOM order: the group header button (toggle), then `Try again` ONLY while a row is in R1-F on a current
surface. Nothing else is interactive. Enter and Space activate both (native buttons). Focus order matches visual order
because nothing is reordered with CSS. Focus is never moved by a state change except the single documented case in 4.2
(retry button unmounting).

### 8.3 What persists

| Thing | Persists? | Where |
|---|---|---|
| Group open/closed (toggle) | across reload and tabs of the same browser | localStorage via `createChoiceStore`, key `copilot-example-projects` |
| The pool | across reload and new sessions | server (AC-N143-1/-4) |
| Row 1 pick, Row 2 content | no | per question, in the in-memory question entry like the answer itself |

## 9. Feature-log control: placement and copy

Ruling proposed (R6): the feature does NOT add a download button inside `AnswerAids`. Its events (AC-N143-16) go to the
EXISTING copilot session log, whose visible download control already exists in both modes and already satisfies the
standing rule's shape (visible text button, exact accessible name, disabled with a visible sibling caption and
`aria-describedby`, no Tooltip, one click, no format menu):

| Mode | Control | Where | Disabled caption (existing copy, unchanged) |
|---|---|---|---|
| Live | `Download session log` | `SessionControls.js`, in the Start/Stop row beside Copy and Clear | `Available once the session has recorded something.` |
| Practice | `Download session log` | `PracticeControls.js`, same pattern | same pattern |

Why not a second button inside the aids: the log is session-scoped, not row-scoped; the rows render at four call sites,
so a row-level button would be up to N identical controls per card list; and the aids are the densest glance area on the
page. The failure copy deliberately does not say "see the session log" (clutter in the worst moment); the support path
is the existing visible control.

One gap to hand to 1b/1h (OBSERVED, not fixed here): `useSessionLogRecorder.logEvent` is a no-op until `startLog()`
runs at "Start session", and `hasEvents` (which enables the download button) flips only there. A prewarm that fails
BEFORE the session starts therefore leaves no trace in the downloadable file, and the user whose Row 1 shows R1-F cannot
produce evidence of why. Proposed resolution for 1b: buffer pre-session feature events (bounded) and replay them into the
log at `startLog()`. If not adopted, record it as an accepted gap with the reason; do not claim AC-N143-16 covers prewarm outcomes.
