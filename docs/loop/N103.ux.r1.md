# N103 - EXPERIENCE design (seat 1c, round r1)

Backlog N103: an adversarial-review button in the preview/edit modal AND in the Ask-AI chat. Binds to `docs/loop/N103.ac.r1.md` (11 ACs; AC-1/2/3 are the safety rows). REUSES the built presentation from N105 Step 8-UI: `ReviewFlagsPanel`, `flagPresentation`, `reviewVerdict`, `CappedList`, and the precedent consumer `IdealResultBands`. Experience only: no source edited, no git writes, no structure re-opened. Where the experience needs something the AC or the built code does not give, it is listed in section 9 as a RULING or a PLAN INPUT; none changes an AC criterion except the three named in 9.1 (A-1, A-2, A-3).

**Decisions at a glance**
1. **Modal.** ONE button in the dialog's EXISTING band slot (`{resultBands?.[tab]}`), named by the document on the active tab: "Review resume" / "Review cover letter" / "Review hypothetical resume". Zero dialog lines (978 of 980 stay 978). Not on the hiring-email tab and not on a "(none)" tab (2.1).
2. **Chat.** ONE quick-action row directly above the composer: the button "Review tailored resume" plus a visible caption that NAMES the subject. Same dimmed `aria-disabled` pattern as Send when there is nothing to review (a visible reason, never a hidden control). The in-flight guard is the chat's existing `chatSending` flag (2.2, 5.2).
3. **One result composition for both surfaces**: a thin shell `DocumentReviewResult` = subject header + headline/notice + the REUSED `ReviewFlagsPanel`. No new panel, no new label table (section 3).
4. **Honesty.** A partial review shows the shared partial notice naming the unchecked categories; the clean sentence is licensed in exactly ONE combination; empty, failed, stale and covered-by-the-Ideal-band are each their own state with their own copy (section 4). Three honesty gaps in the AC/inputs are named in 9.1.
5. **Not spammable.** The button never uses `disabled` (focus is not dropped); it is `aria-disabled` and dimmed while a review runs; a ref guard makes a double-click one review; a late result can never render over a different document (section 5).
6. **Announcement reuses existing live regions only**: the modal uses the mount's N95 pair, the chat uses its `data-chat-status="progress"` region. ZERO new `role=status` anywhere. The modal choice collides with ONE landed N105 test; that needs a ruling before 4b (R-1).
7. **Ideal jobs.** The review strip stacks BELOW the Ideal band and, while the text on screen still equals the generated text, answers with one "already covered above" line instead of a second verdict (6.2).
8. **Chat subject.** The "current document" is the pinned context's document, identified by (job, scope), never by job alone (a HYPOTHETICAL pin and a resume pin share a job id), and named twice: before the click and in the result (section 7). No implicit "latest" guess (the one product-shaped call, F-1).
9. **Read-only.** N103 adds findings, never fix buttons (no "insert keyword", no "accept"): the domain reason is in 8.5.

## 2. The control, in both surfaces (brief item 1; AC-4, AC-5, AC-9)

### 2.1 Modal: one strip in the existing band slot

**Decision.** The Review button lives in a thin strip rendered through `resultBands?.[tab]`, below any N105 band and above the file-name row. It is built by the mount (a leaf under `app/components/preview/`), so the dialog needs ZERO new lines (U1, U2).

| Rejected | Why |
|---|---|
| In the toolbar next to Ask AI | Needs `reviewControl` prop + slot = both remaining lines (978 -> 980), leaves N104 nothing, and joins nine wrapping controls; the toolbar is the densest row in the app. |
| In `DialogActions` | The AC-C12 census pins that bar's control count; the bar is for leaving the dialog (Close/Combine/Drive/Copy/Download), not for inspecting. |
| A tab or a second dialog | An extra click and a second surface for a one-action job. |

- **Which tabs.** `resume`, `cover`, `hypothetical`, when the scope is `available`. Not `email`: plain text pasted into a mail client (the dialog already says "Read-only - copy the text below"), no file name, no edit, no download; the detectors are resume-shaped and a "Partial review" over a four-line note invites a vetting claim nobody earned. Not an unavailable tab: the tab is disabled "(none)" and the body already states the absence ("No resume has been generated for this posting yet."). The strip appears on the SAME condition as Ask AI's enabling (`available(tab)`).
- **Name.** Visible text IS the accessible name (no `Tooltip`, no `aria-label`): `Review ${SCOPE_LABEL[tab].toLowerCase()}` -> "Review resume", "Review cover letter", "Review hypothetical resume". After a result exists the same node reads "Review again" (still matches `/review/i`; it never unmounts or loses focus). Anchor tests on `^review (resume|cover letter|hypothetical resume|again)$`: on a phone the Ideal band's own summary button is named "Partial review - n to check" (U6), so a bare `/review/i` is ambiguous on a mobile Ideal job (R-6).
- **Look.** `Button size="small"`, `textTransform: "none"`, `startIcon` `FactCheckOutlined` (same family and weight as Ask AI's `SmartToy` and Scan posting's `ManageSearchIcon`), `TOUCH_TARGET_SX`. Row root reuses the Ideal band's `ROOT_SX` tokens (export them from one module, do not copy the object). 1e decides craft.
- **Helper line.** Until a result exists, one muted sentence beside the button: "Checks this resume for weak, unsupported and repeated lines." (`aria-describedby` target, never empty). It states what the button does and says nothing about an engine: the review is mechanical and key-free on every engine (AC-9), and "needs the AI engine" would be a wrong remedy (see 4.3).
- **Engine.** No gating, no "Offline" badge, no engine-dependent copy. Embedded and Gemini render identical controls.

### 2.2 Chat: one quick-action row above the composer

**Decision.** First child of the composer container (above the attachments tray), always rendered while the chat is open:

```
[ FactCheck  Review tailored resume ]   Acme · Senior PM — Resume
```
(button, then a muted caption that wraps; on a 380 px panel the caption takes a second line rather than clipping.)

| Rejected | Why |
|---|---|
| In the pinned-context strip beside "Estimate salary" | That strip exists only while something is pinned, is `nowrap` with an ellipsized label, and already carries three controls at 380 px. A row that exists only when a document is pinned cannot show the "nothing to review" state. |
| In the header | Header is for panel chrome (title, engine chip, Clear, Close). |
| A slash command or typed phrase | Not discoverable; and "review my resume" already means something else (U18). |

- **Name.** "Review tailored resume" (cover pin: "Review tailored cover letter"; hypothetical pin: "Review hypothetical resume"; no target: "Review tailored resume"). The word "tailored" is deliberate: it separates this from the typed intent "review my resume", which critiques the UPLOADED base resume with a different analyzer (U18, R-6). No `Tooltip`, visible text is the name.
- **Enabled on embedded.** It is not gated by `isEmbedded`, shows no "Offline · no AI" reason, and the embedded-only header chip is unrelated to it (AC-5).
- **One action.** Click -> user turn "Review: {label}" appended, result turn appended, announcement (section 5). It does NOT read, clear or send the composer text, and does not move focus: `askAiAbout` pre-fills "I need help with ...: " and focuses the composer, and that draft must survive a review.
- **Unavailable look.** When there is no target, the button uses the Send pattern exactly: `aria-disabled="true"`, `opacity: 0.5`, `pointerEvents: "none"`, never `disabled`. The caption beside it is the visible reason and is the button's `aria-describedby` target (a disabled-looking control whose reason lives only in a label fails `[[mui-a11y-traps]]` 8). Keyboard/AT activation of an `aria-disabled` button still reaches the handler, and the handler answers with the nothing-to-review turn (7.3): no activation is ever silent.

### 2.3 Click cost (minimize-clicks)

| Task | Today (no feature) | With N103 |
|---|---|---|
| Review the tailored resume I am looking at | copy text, open a chat, paste resume + posting (+ real resume), type a prompt, read prose: 6+ actions | open preview (existing), **1 click** |
| Re-review after I edit it | repeat the paste | **1 click** ("Review again") |
| Review from the chat | same paste | chip menu -> Ask AI (existing 2) -> **1 click**; from the modal: Ask AI (1) -> **1 click** |
| Review the cover letter | repeat | switch tab (existing), **1 click** |

Nothing is asked first: no engine pick, no scope picker, no confirmation (a review changes nothing and spends nothing, so no dialog guards the wrong direction). The chat reviews the pinned document only; to review the other document the user opens it in the modal (a picker would be a second control for the rarer path; non-fork, 9.3).

## 3. Results presentation: ONE shared composition (brief items 2, 5; AC-7, AC-11)

`DocumentReviewResult` is a thin shell and the ONLY new presentational component. It contains no label table, no tier logic, no `blockquote` flag renderer: it renders, in order, (a) the subject header, (b) the state headline/notice (section 4), (c) additive notes, (d) `ReviewFlagsPanel` (flags + `unresolvedQualifications`, `draftKind` by scope: resume and cover -> `applicationReady`, hypothetical -> `hypothetical`, so the Note tier and the Unsourced-figure vocabulary come for free), (e) one footer sentence. Both surfaces mount THIS component from the ONE helper's output (AC-11); neither re-derives anything.

**Subject header (every `ran` state).** "Review of this resume - 14 lines" (modal) / "Reviewed Acme · Senior PM — Resume - 14 lines" (chat). The count is the number of spans the helper minted: it is how a reader sees that the whole document was read (a truncated review would say 12 lines of a 40-line resume, U17).

**Where it renders.**
- Modal: inside the strip's `section` (`aria-label` "Review of this resume"; distinct from the Ideal band's "Application-ready resume review"), under the button row, with a Hide/Show header button (`aria-expanded`, `aria-controls` -> the body id, caret `aria-hidden`). Expanded by default right after a run (the user just asked); md+ body capped (6.3) with its own scroll, below md not a scroll container (same rule as U6).
- Chat: as the ASSISTANT turn that follows the user turn, below an app-authored one-line bubble (the salary precedent, U13: the bubble is `content`, the structured card is a sibling field `documentReview` on the message). No cap, no collapse: the panel's own turn list scrolls and the groups cap at 8 rows + "Show all (n)". The turn keeps the `85%` turn container.

**No fix actions.** Findings are advisory and read-only (8.5).

**Document-level flags.** See R-4: a missing-keyword flag is a statement about the whole document, but it is anchored on line 1 (U10), so under the reused panel it reads "this first bullet lacks Kubernetes". The requirement (N103-UX-23) is that no missing-keyword item is ever presented as being about a specific line; the mechanism is the plan's call.

## 4. Coverage honesty (brief item 3; AC-1, AC-9, AC-10)

### 4.1 State matrix (every state a result region can be in)

A pure function (suggested home `lib/review/`, next to `reviewVerdict`, importing it) maps `{outcome, review, verdict, inputsComplete, reviewedText, currentText, coveredAbove}` to ONE state. It is total, never throws, and every unusable input falls to the not-clean side.

| State | Headline (exact copy in section 10) | Groups | Tone | Announced as |
|---|---|---|---|---|
| `empty` | Nothing to review - {this document} has no text yet. | none | info | polite: "Nothing to review." |
| `failed` | The review could not run, so nothing was checked. Try again. | none | warning | alert (persists) |
| `covered` (modal, Ideal tab only) | The review above already covers this text. Edit the resume, then review again to check your changes. | none | info | polite |
| `partial` | **Partial review - mechanical checks only.** + the Checked / Not fully checked line + closing | every non-empty group | warning | polite |
| `findings` (complete, n > 0) | `bandSummary(...)`: non-zero counts only | every non-empty group | info | polite |
| `clean` | No issues flagged. The automated review is not a guarantee - read it once before you send. | none | info | polite |
| `stale` (additive) | note: You have edited this {document} since this review ran. The notes below describe the earlier text. Review again to check your changes. | as the underlying state | - | NOTHING (static: it flips while the user types) |
| `stale-nothing-to-show` | This review ran on an earlier version of the text. Review again to check what is on screen now. | none | info | nothing |

**The clean license** `clean` is true in exactly ONE combination: `reviewVerdict(review).kind === "complete"` AND text fresh AND zero findings (no flags, no unresolved) AND the document is non-empty AND `inputsComplete` (4.2). The AC's own gate (AC-1) is the first conjunct; the others are strictly additional. In slice 1 `coverage.complete` is false on every mechanical run, so `clean` is unreachable on real input; its branch is kept live by an injected fixture (AC-1's complete case), exactly as N105's C17 is.

**Forbidden in chrome (sweep, quoted nodes excluded via `[data-quoted]`):** `/no issues flagged/i`, `/no weaknesses/i`, `/nothing (was )?(flagged|found)/i`, `/found nothing/i`, `/no (problems|concerns|issues)\b/i`, `/all clear/i`, `/looks good/i`, `/passed/i`, `/\bverified\b/i`, `/safe to send/i`, `/clean/i` - each allowed ONLY in the `clean` row (positive control: the clean fixture must render its sentence so the sweep is shown to fire). The sweep covers the headline, notes, footer, the one-line chat bubble AND every announcement string (they are rendered text too).
No zero count renders in any state (`bandSummary` names non-zero counts only), so "0 flags" can never read as a bill of health in a partial state.

### 4.2 Inputs withheld: the partial notice must name them (gap A-1, AC-1 delta)

`coverage` says which checks the reviewer RAN, not whether the surface gave it what each check needs (U10). With no posting requirements, `missing-keyword` is listed as evaluated over an empty list: a vacuous pass. With no real material, the authority skeleton fails closed (flags) and `unresolvedQualifications` lists every requirement the draft does not address, under a title ("cannot meet by rewording") that asserts a comparison nobody made. Once N110 lands `coverage.complete` can be `true`, and a surface that supplied no posting would then be licensed to print "No issues flagged" with keyword matching never having run.

UX requirements (the AC seat must adopt or reject, 9.1):
- The shared helper returns `inputs: { posting: boolean, realMaterial: boolean }` with its result. A false `inputs.*` (i) moves the check that needed it from "Checked" to "Not fully checked" in the displayed line (posting -> "posting keywords"; real material -> "role and seniority claims"), (ii) forces the verdict to `partial` for display and for the clean license (never `clean`), and (iii) adds one plain sentence: "No job posting was available, so keywords were not matched." / "Your uploaded resume was not available to compare against, so role and seniority claims could not be checked against it."
- With `realMaterial` absent the `Requirements your resume cannot meet by rewording` group is NOT rendered (its title is a claim about the resume).
- Posting keyword matching is supplied for resume-type documents (`resume`, `hypothetical`) only; for a cover letter the posting is withheld and the notice says so. Domain reason: a recruiter or an ATS keyword filter reads the RESUME for term coverage; flagging absent terms in a cover letter coaches the user to keyword-stuff prose, which recruiters read as padding, and the keyword flag is the one a user is most tempted to "fix" by inserting an untrue skill.

### 4.3 Partial copy: shared, parameterized, never "needs the AI engine"

- One sentence builder shared with N105 (`coverageLine` extracted from `IdealResultBands.js` into `lib/review/` beside `checkLabel`, and `BAND_COPY.partial/partialClosing/partialUnknownCoverage/clean/edited` moved with it; the N105 band imports it back, its tests unedited). Two copies of this sentence would drift on the first edit (plan input UXN-1).
- Names come from `checkLabel` (`CHECK_LABELS`): posting keywords, repeated phrasing, figures with no baseline, vague wording (checked in slice 1); dates and titles lining up, role and seniority claims, whether claims fit the employer (not fully checked).
- The closing takes the document noun: "Read the whole resume once before you send." / "... cover letter ..."; on the HYPOTHETICAL tab there is NO closing (nothing is sent from it; the banner above already says so) and the headline is unchanged.
- The headline suffix "mechanical checks only" is a statement about the ENGINE and is true only while `coverage.engineMode === "mechanical-only"`. When N110 lands with a judge that reports fewer than seven categories, that suffix would lie (R-3, A-2): derive it from `engineMode` (mechanical-only -> the current sentence; otherwise "Partial review." + the same data-driven line).
- No remedy sentence about switching engines: the deeper checks are not built yet, so the remedy does not exist (the same finding N105's UX recorded).

### 4.4 Empty is not clean

`empty` is its own state with its own sentence and role. It renders zero rows and no notice. Its sentence contains none of the forbidden phrases. "Nothing to review" (no document was read) is never rendered in any state where a document was read, and no clean phrase is ever rendered where none was (AC-10).

## 5. Loading, not-spammable, announcements (brief item 4; I4)

### 5.1 Modal

- **In-flight.** The button stays mounted and focusable and becomes `aria-disabled="true"` + `aria-busy="true"`, visible text "Reviewing..." with a `CircularProgress size={14}` start icon (precedent: Scan posting's "Scanning..."). Never `disabled`, never unmounted under focus.
- **Not spammable.** A per-(job, scope) in-flight REF (not only state) is checked and set synchronously in the handler, so two clicks in one tick start ONE review (the Send guard's idiom: the guard lives in JS). Re-activation while running is a no-op, not a queue.
- **Late result.** The result is stored under (job id, scope, reviewed text). It renders only while the dialog is open for that job and the active tab is that scope; a result that resolves after a tab switch, a job change or a close is discarded, never shown over another document. A result is dropped on close (nothing persisted).
- **Async from day one.** The mechanical reviewer is a pure function, but supplying `realMaterial` for a real document means extracting the uploaded resume's text (the chat already does this per send: `buildTemplateLinesForUpload`, `lib/chat/chatbot.js` ~:525), which is genuinely async. So "Reviewing..." is real now, not a future N110 concern. No fake progress bar and no duration is stated.
- **Edit race.** A click or Tab away from the editor blurs it and commits (`onBlur` -> `commitDraft`, U21), so the review reads the committed text. Requirement: edit, then click within the 600 ms window -> the review reflects the edit (N103-UX-9 instrument).

### 5.2 Chat

- **Guard = the existing `chatSending` flag.** The review sets it for its duration. Send and Resend are already guarded by it, the pending line already appears (it reads "Thinking..."; the plan should branch it to "Reviewing..." for a review, a two-line change), and the Review button reads the same flag for its `aria-disabled` look: ONE flag, no new state, and a user cannot interleave a send with a pending review (the interleave would let `runChatRequest`'s non-functional `setChatMessages(nextMessages)` overwrite the pending turn).
- Both turns are appended by functional updates; a Clear mid-review discards the pending result (checked against the same sequence the guard uses).

### 5.3 Announcements: reuse, add nothing

| Surface | Existing node reused | New live nodes |
|---|---|---|
| Modal | the mount's N95 pair: `announce({polite})` for done/empty/covered, `announce({alert, persist: true})` for failed | **ZERO**. The result region has no `role=status`, no `role=alert`, no `aria-live`; hidden regions are selected by `data-copy-status`, never role. |
| Chat | the `data-chat-status="progress"` region, a closed cue set today ("Sending..."/"Reply ready") widened by three cue states: "Review ready.", "Nothing to review.", "The review could not run." | **ZERO**. The card is inside the `aria-busy` wrapper, which is not live. |

- **Announce completion only.** The mechanical review resolves in one turn of the event loop; announcing "Reviewing..." immediately before "Review ready." would queue two messages for one action. A "Reviewing..." cue is added only if a review is genuinely long (N110), a threshold that belongs to that chunk.
- **Strings are category/count cues, never content, and pass the 4.1 sweep:** "Review finished. 3 to check. Partial review: some checks did not run." / "Review finished. Partial review: some checks did not run." (zero findings, partial: no "no issues" wording) / "Review finished. 2 to check." / "Review finished. No issues flagged." (the `clean` state only) / "Nothing to review." / "The review could not run."
- **The modal's pair must be mounted BEFORE the first click** (only a text change on an already-mounted region reliably announces, `CopyFeedback.js` header). The review strip is mounted whenever the dialog is open on a reviewable tab, so the pair's mount condition widens to `insertedFacts.length > 0 || idealSurface?.announces || reviewStripMounted` (still exactly ONE pair in the band slot). **That changes U5's baseline for an ordinary job**: R-1 below.
- **Failure/refusal in the chat** are assistant turns (the salary precedent), announced through the progress cue, NOT through `chatError` (AC-31f reserves that region for send refusals; "nothing to review" is not a send failure and is not danger-toned).

## 6. Modal composition with the N105 surfaces (brief item 5)

### 6.1 Order in the band slot (top to bottom)

2. 3. The review strip (this feature).

### 6.2 No double verdict (AC cumulative-surface note 6b)

The N105 band is the GENERATION-time review of the application-ready file (two drafts, the gate's removed/left-out lists, real material). The N103 strip is a review of the text on screen NOW. To keep one verdict per text version:
- **`covered` rule.** On an Ideal job's Application-ready tab, if `idealBandState({ideal, currentText, handEdited})` reports `freshness === fresh` AND `review !== none` (the band is showing a real review of exactly this text), activating Review renders the one-line `covered` state instead of a second flag list. It is derived from the band's OWN exported pure state, never re-derived. When the band is `none` ("the review did not run"), `other-version` or `edited`, the band does NOT cover the text and the full review runs.
- The value of the strip on an Ideal tab is therefore the case the band cannot serve: the user pasted a removed line back (Copy line, then Edit) or otherwise edited, and wants the new text checked. That pasted-back claim now gets the figure and vagueness checks it skipped.
- **Vocabulary is shared**, so even when both are visible the two never use different words for the same thing (shared partial notice, shared `flagPresentation`, shared `reviewVerdict`). Two regions with different accessible names ("Application-ready resume review" / "Review of this resume").
- **HYPOTHETICAL tab.** No review exists there today (`IdealResultBands` filters hypothetical flags out and `HypotheticalBand` renders only the notice, the file name, the download button and the footer; no flag list). The strip is the first review on that tab: `draftKind: hypothetical`, authority judged by internal consistency and NEVER against real material (AC-3), Note tier vocabulary ("Unsourced figure", "Seniority does not add up"), partial closing omitted. Read-only tab, so `stale` cannot occur there.

- Dialog: 0 lines. Mount: roughly +25 lines of wiring (this seat's estimate, to be counted by the plan; 723 -> well under 1000); the hook/leaf logic goes in new files, the review logic in `lib/review/`. `DialogActions` and the toolbar are untouched, so the landed control census and the first-status-is-DriveResultRegion test stay green unedited.

## 8. Keyboard, focus, accessibility, persistence, log, app-vs-chat

### 8.1 Keyboard and focus
- **Modal order (DOM):** tabs -> toolbar -> band slot (Ideal band controls, then the review button, then the result's Hide/Show and "Show all") -> file-name row -> document -> action bar. One new tab stop before the results, then the results' own controls in reading order.
- **Chat order:** header -> pinned strip -> turn list (each turn's Copy/Resend, the card's "Show all") -> **Review row** -> composer. After activation focus STAYS on the Review button in both surfaces; nothing moves focus, nothing unmounts under it.
- Escape closes the dialog / the panel exactly as today.

### 8.2 `[[mui-a11y-traps]]`
- No `Tooltip` anywhere in the new leaves (traps 1, 2): visible text is the name; reasons are visible captions linked by `aria-describedby` to a non-empty node (trap 8). No `Select` (9, 10). Carets/icons `aria-hidden` (7). No MUI `Alert` (5): plain `Box`es. No new live region (4, 5, 6).
- Label-in-name holds for "Review resume", "Review again", "Reviewing...", "Review tailored resume" and the Hide/Show toggle (name resolver of trap 3; assert, do not assume).
- Colour is never the only signal: tone boxes carry text; flags carry text labels (inherited from the panel).

### 8.3 What persists
Nothing. The modal result is per (job, scope, text), kept while the dialog stays open, dropped on close or job change, written nowhere (not the tailoring entry, not storage). The chat result is a transcript turn and lives exactly as long as the transcript (Clear removes it). A review is cheap and deterministic; persisting findings would manufacture stale verdicts.

### 8.4 Feature log (`[[feature-logs]]`)
One `DECISION_LEDGER` entry `document-review` bound to the module that owns the single `recordDecision(` call (the request wrapper; the ledger binds one entry per module, U19). Fields (closed list, counts and codes only): `surface` (`modal`/`chat`), `scope`, `kind` (`partial`/`complete`/`empty`/`failed`/`covered`), `flagCount`, `coverageComplete`, `reason`. Outcomes: `acted` (ran), `refused` (nothing to review), `failed`. NEVER document text, excerpts, labels, company or title. Download: the existing app-wide `ActivityLogButton` (Settings > Admin tools). No per-surface download button: N65 and N105 shipped the same way and a third button on a dense dialog/chat is the clutter minimize-clicks forbids; the owner can flip this (9.3, non-fork).

### 8.5 Read-only, by domain design
No finding has a one-click fix. Missing-keyword and unverifiable-metric are the two flags a user is most tempted to "resolve" by inserting an untrue skill or number; recruiters probe both (numbers in the screen, titles in the reference check). The Confirm tier tells the user to verify truth; N104 owns "regenerate to fix".

### 8.6 App-vs-chat claim (`[[app-vs-chat]]`)
**Class: Guaranteed (earned, mechanism named), with Corpus as the enabling input.**
**What the user does instead, and what it costs:** copies the tailored resume, the posting and their real resume into a chat for each application, asks "find weaknesses", and gets fluent prose that can itself invent a flaw, quote a line that is not in the document, or say "looks good" over checks it never made. Per application: the re-paste, the manual audit of the audit, and the one time the reassurance was wrong.
**What the button gives:** (1) every finding quotes a line that provably exists in THEIR document (the reviewer drops any flag without a contained span, `assertContainedFlag`); (2) it says what it did NOT check, and cannot print a clean verdict over an unchecked category (`reviewVerdict` fails closed); (3) the same input always yields the same flags and needs no key; (4) nothing re-pasted: document, posting and real resume already live in the app (Corpus, inherited).
**Removal map:** delete the partial notice or gate the clean copy on flags only -> N103-UX-4/5 red (AC-1); stop quoting the real line (canned/raw-text output) -> AC-6 differential red; drop the subject naming or review a substitute -> N103-UX-14 / AC-2 red.
