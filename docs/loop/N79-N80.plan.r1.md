## 1. Contradictions / mechanism choices routed to the plan

The AC held the bar and handed mechanism to design; design settled most and left three to
me. My rulings:

- **P-1 — remove `detail: err?.message` from the 500 path in `route.js`.** Design §4/§10
  flagged this as a "plan decision," not an AC row. Ruling: **remove it**, in the same step
  that edits `route.js` (Step A). Justification: it is the same disclosure class AC-11
  governs on the 403; Step A already edits this file; and no consumer reads it — the sole
  endpoint consumer (`page.js` `loadGmailMessages`) reads `data.messages` only (verified in
  the `:914-929` body). It is a one-line deletion, reversible, and not on any test's
  assertion path. This does not widen scope: it deletes a leak in a file already open.
- **P-2 — `HUMAN_BY_CAUSE` is route-local, not shared with the client.** Design left it
  "route-local or shared-with-client." Ruling: keep it a small const map inside `route.js`.
  The client keys on `cause` and never on the human string (AC-5/AC-6), so sharing buys
  nothing and adds a cross-module coupling. The three canned strings live once, in the
  route.
- **P-3 — pure shape check, no `GaxiosError` import, confirmed.** Design D-1 chose the
  dependency-free shape check (`Boolean(err?.response)` + `typeof
  err?.response?.data?.error === "string"`). I concur and do not reopen: it keeps N1 free
  of `googleapis` so its unit test uses plain objects, and R-3's import path stays an
  optional belt the 4b seat may add, never the primary discriminant.

## 5. The CITED-NOT-VERIFIED item: holding the fixtures to R-1, and the post-deploy reveal

The live googleapis error shape (R-1/R-2) rests on a read of installed
`google-auth-library@10.6.2` / `gaxios@7.1.4` source, **not** a live refresh. It is the
single load-bearing external fact of the chunk (design §10). How the plan holds it:

- **The 4b fixtures must be shaped per R-1 exactly:** a provider rejection is a plain object
  `{ response: { status: 400, data: { error: "<oauth code>", error_description: "..." } } }`
  — `error` a STRING; a network failure is `{ response: undefined, code: "<string>" }`
  (falsy `response`). The classifier reads `err.response.data.error` and
  `Boolean(err.response)` and nothing else. **R-4 hazard:** no fixture may put "reauth" (any
  case) in `error_description` unless it is deliberately exercising the google-auth-library
  message-rewrite path — because that rewrite mutates `err.message` (not
  `err.response.data.error`), and a fixture that trips it accidentally is misleading. Our
  classifier ignores `err.message`, so it is robust to the rewrite; the fixture discipline
  is to keep the tests honest.
- **What would reveal an R-1 mismatch after deploy:** the operator log (AC-4). If R-1's
  field path is wrong (e.g. the real error does not populate `err.response.data.error`),
  every production refresh failure falls through to `logCode:"unrecognized"`. The reveal
  instrument is a post-deploy scan of the server log for `[gmail auth] refresh failed`
  lines: a flood of `unrecognized` (rather than a mix of `invalid_grant`/`network`) means
  the read path is wrong. Cheaper pre-deploy option (design §10, optional, not gating): a
  PowerShell Node probe that constructs an `OAuth2Client` with a bogus refresh token, calls
  `refreshAccessToken()`, and dumps `err.response?.data?.error`, `typeof err.code`,
  `Boolean(err.response)`.
- **Why the risk is bounded, not catastrophic:** the fall-through defaults to
  `reauth_required` (AC-3(iv)). So even a total R-1 miss degrades to "always offer
  reconnect" — LOUD and safe (a visible, if sometimes unnecessary, reconnect), NOT the
  silent swallow bug the chunk exists to kill. The classifier's design converts an external
  fact-error into a visible over-prompt, which is the correct failure direction.
- **S-3 compounds this:** because the refresh `catch` only runs under the near-expiry guard,
  the `invalid_grant` branch runs in production only for tokens within 5 min of expiry, so
  the log-distribution reveal accumulates slowly. The verifier should treat AC-4's
  operator-log assertion as PROVISIONAL (per AC §5) until real traffic populates it.
