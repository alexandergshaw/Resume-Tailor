## 1. Decision 1 — WHERE the state lives: localStorage, built on `createChoiceStore`

**Recommendation: localStorage via `lib/copilot/choiceStore.js`'s `createChoiceStore`, NOT a fourth
hand-rolled `engine.js`-style store, NOT Supabase.**

### Why localStorage and not Supabase (v1)
A recency list of company **names** is a per-viewer convenience, not shared or
security-bearing state. It needs no auth, no row-level-security policy, no migration, and no
network round trip on the hot path (the picker already pays one round trip for
`fetchPracticePostings`). Company names in localStorage are not sensitive (BACKLOG N124 states this
explicitly). Cross-device sync is a **named follow-up**, not a v1 requirement — filed as a proposed
ledger line (§10, L9). This matches the owner's stated v1/follow-up split. **This is not an owner
decision to escalate**: the owner already picked localStorage-for-v1 in the N124 entry; Supabase is
not required by any AC here.

### Why `createChoiceStore` and not a 4th copy of `engine.js`
The brief says "mirror `answerAsMe.js`/`engine.js`." `createChoiceStore` **is** the repo's matured
mirror of exactly that pattern: `useInterviewType.js` (the direct sibling control in this same
component tree) was rebuilt onto it, and `choiceStore.js`'s own header names `engine.js` and
`useSaveRecordings.js` as the stores still carrying the storage-failure defect (`set` throws under
quota/private-browsing but a later read silently snaps the value back) that the factory was written
to close (`choiceStore.js:32-57`). Hand-rolling a fourth copy would reintroduce that defect class
for free. Reuse also gives us, already hardened and already tested by `choiceStore.test.js`:
SSR-safe `getServerSnapshot` returning a stable constant, cross-window `storage` sync,
a sticky `getStorageBlocked` boolean, a per-instance test reset, and the read-path-is-never-
authoritative discipline. **The AC in §6 binds behavior, not the substrate**, so a reviewer who
judges the factory too heavy may instead hand-roll an equivalent `engine.js`-style store that meets
the same behavioral contract — see §3's "Fallback" note. I recommend the factory.

**Open point for the checker (not a blocker):** `createChoiceStore` was built for scalar values;
holding an array is a legitimate but previously-unexercised use of it. See §9 (V1) for the exact
property the TDD seat must pin (array snapshot referential stability across renders with no write).

## 2. Decision 2 — WHAT is remembered: the entry shape, dedupe, cap, recency

### Stored value
A JSON array of entries, most-recent-first, persisted under one key.

```
// one entry
{ company: string,      // trimmed, original casing preserved for display
  lastUsedAt: number }  // Date.now() at the moment of selection
```

- **Dedupe key:** `company.trim().toLowerCase()` (`companyKey`, §3). Case- and
  whitespace-insensitive, so "Acme" and " acme " are one company.
- **Recency order:** array index. Index 0 is most-recent. A re-selection of an existing company
  **moves it to index 0** (remove-then-prepend), it does not duplicate.
- **Cap:** `RECENT_COMPANIES_CAP = 5`. Rationale: a recency list, not an archive; five covers a
  typical active search's recent targets while keeping the surfaced "Recent" group scannable and
  stopping it from dominating the options. Tunable; the number is a design call, not an AC.

### Why company name, not posting id
BACKLOG N124's own reasoning: a **company is more stable than a posting id** — the application row
(`option.id`) can be deleted, after which a remembered id resolves to nothing. We remember the
company string and **re-resolve it against freshly-fetched options at render time** (§4), so a
deleted posting can never be offered.

### `lastPostingId` considered and DEFERRED
A richer entry `{ company, lastPostingId, lastUsedAt }` was considered (to restore the exact posting
last used). It is **not in the v1 shape** because the chosen surfacing (§4, option b) resolves a
remembered company to *all* currently-matching options rather than to one — so `lastPostingId` would
be a stored field with **no v1 consumer a reviewer could check**. It earns its keep only in the
pre-select follow-up (§10, L9), and is specified there, not shipped dead now.

### When an entry is written — and when it is NOT
- **Written:** on a **non-null** selection whose `company` is a non-empty string. The write happens
  inside PostingPicker's `onChange` path (§4), the one place a selection is made.
- **NOT written:** (a) a **blank/clear** selection (`newValue` is null) — the write path is never
  reached; (b) a non-null selection whose `company` is `""` (a title-only posting — nothing to
  remember); `addCompany`/`recordCompany` no-op on a blank company as belt-and-braces beyond the
  call-site null gate (§3).

## 3. Data/structure contract — new modules, full signatures

### NEW `lib/copilot/recentCompanies.js` (React-free; pure; node-testable)
`lib/` imports no React (convention, `choiceStore.js:1-6`). All functions pure and total
(never throw). This is where the dedupe/cap/order logic lives so it is unit-testable without a render.

```js
export const RECENT_COMPANIES_STORAGE_KEY = "copilot-recent-companies";
export const RECENT_COMPANIES_CAP = 5;

// Normalized identity of a company for dedupe/match. Total; "" for nullish.
export function companyKey(company): string
  // = String(company ?? "").trim().toLowerCase()

// Store normalizer. Accepts anything (parsed JSON, or an already-built list).
// Returns an array of valid { company: nonempty-trimmed-string, lastUsedAt: finite-number|0 }
// entries, deduped by companyKey keeping the FIRST occurrence, capped to `cap`.
// Drops entries whose company is not a nonempty string. Never throws; non-array -> [].
export function sanitizeRecentCompanies(raw, cap = RECENT_COMPANIES_CAP): Entry[]

// Pure recency insert. Returns a NEW array: drop any existing entry with the same
// companyKey, prepend `entry`, cap to `cap`. If entry.company is blank/invalid,
// returns `list` UNCHANGED (same reference). Never mutates `list`.
export function addCompany(list, entry, cap = RECENT_COMPANIES_CAP): Entry[]

// Membership test used by the Autocomplete groupBy. True iff companyKey(company)
// equals the companyKey of some entry in `recentList`.
export function isRecentCompany(company, recentList): boolean

// Ordering for the "Recent" group. If NO option's company matches any recent entry,
// returns the ORIGINAL `options` reference unchanged (the "nothing to surface" signal).
// Otherwise returns a NEW array: options whose company matches a recent entry FIRST —
// ordered by that entry's index in `recentList` (most-recent first), ties broken by the
// option's original index — followed by every remaining option in its original order.
// Every input option appears EXACTLY ONCE. Pure; never mutates `options`.
export function orderRecentFirst(options, recentList): Option[]
```

Contract invariants a reviewer applies to a diff:
- `orderRecentFirst(opts, []) === opts` (same reference) — no recents means today's behavior exactly.
- `orderRecentFirst(opts, recents).length === opts.length` and is a permutation of `opts` (no drop,
  no duplicate) — check: sort both by `id`, assert deep-equal.
- After `orderRecentFirst`, the recent-matching options form a **contiguous prefix** — this is the
  property MUI `groupBy` depends on (§9 V2); a reviewer checks it by asserting the first
  `k = count(isRecentCompany)` options all satisfy `isRecentCompany` and the rest do not.
- `addCompany(list, {company:"Acme",...})` then `addCompany(result, {company:"acme",...})` yields a
  list of length 1 with "acme" at index 0 — dedupe is case-insensitive and reorders.
- `addCompany(list, {company:"   ",...}) === list` (same reference) — blank never written.
- `sanitizeRecentCompanies(anything).length <= RECENT_COMPANIES_CAP` — cap is a hard backstop even
  if storage was hand-edited past the cap.

### NEW `app/copilot/useRecentCompanies.js` ("use client"; thin store wrapper)
Mirrors `useInterviewType.js` structure (factory instance + `useSyncExternalStore` hook).

```js

import { RECENT_COMPANIES_STORAGE_KEY, RECENT_COMPANIES_CAP,
         addCompany, sanitizeRecentCompanies } from "@/lib/copilot/recentCompanies";

const EMPTY = Object.freeze([]);          // stable server-snapshot / default reference
const store = createChoiceStore({
  storageKey: RECENT_COMPANIES_STORAGE_KEY,
  defaultValue: EMPTY,
  normalize: (v) => sanitizeRecentCompanies(v),      // runs on set() and on decoded reads
  decode: (raw) => { try { return raw ? JSON.parse(raw) : []; } catch { return []; } },
  encode: (list) => JSON.stringify(list),
  crossWindow: true,
});
store.hydrate();

export function getRecentCompanies(): Entry[]            // = store.get()
export function __resetRecentCompaniesForTests(): void    // = store.__resetForTests()

export function useRecentCompanies(): {
  recentCompanies: Entry[];                 // useSyncExternalStore(store.subscribe, store.get, store.getServerSnapshot)
  recordCompany: (posting: Option|null) => void;
}
// recordCompany(posting):
//   const company = posting?.company;
//   if (!company || !String(company).trim()) return;      // blank company never written
//   store.set(addCompany(store.get(),
//               { company: String(company).trim(), lastUsedAt: Date.now() },
//               RECENT_COMPANIES_CAP));
// recordCompany is a useCallback(fn, []) — stable identity for the tab's life.
```

Why `recordCompany` lives in the hook, not the pure module: it stamps `Date.now()` and touches the
store. The pure `addCompany` takes `lastUsedAt` as an argument so tests supply a deterministic value;
`recordCompany` is the only impure stamping site.

**Fallback (if the checker rejects `createChoiceStore` reuse for an array):** hand-roll
`app/copilot/useRecentCompanies.js` as a direct `engine.js`-style store (module `let memoryList`,
`listeners` Set, `readRecentCompanies` with try/catch JSON.parse + `sanitizeRecentCompanies`,
`writeRecentCompanies`, `useSyncExternalStore`). It must meet the same §6 behavioral AC. The pure
`lib/copilot/recentCompanies.js` module is unchanged either way. I recommend the factory; the
fallback is fully specified so neither path is left unspecified.

## 4. Decision 3 — EXPERIENCE (1c, minimize-clicks): pin a "Recent" group, do NOT pre-select

Two concrete options were evaluated. **Chosen: (b) a "Recent" group pinned at the top of the
options.** Option (a) pre-select is rejected on correctness grounds.

### Why NOT (a) pre-select-most-recent-on-mount
Pre-select is the owner's stated ideal ("zero clicks"), but in **this** component it is a structure
where the wrong thing is merely *guarded*, never *impossible* — the opposite of what this seat owes
(standing rule 2):
1. **PostingPicker does not own `value`.** Both clients initialize `posting = useState(null)` and
   own `onChange`. Pre-selecting means either emitting `onChange` on mount or having the clients seed
   from the store. Either way the clients' `onChange` fires **selection side effects** — CopilotClient
   clears the answer cache and bumps `draftGenRef` (CopilotClient.js:210-214); PracticeClient resets
   the question flow and abandons the answer (usePracticeHandlers.js:149-158). A page load would
   silently trigger these for a selection the user did not make this visit.
2. **The match is inherently async**, so pre-select can only be a post-load reactive write. Options
   arrive from `fetchPracticePostings` after mount (PostingPicker.js:45-60), so the earliest a
   remembered company can resolve to an option is *after* the user may already have opened the field
   and chosen blank. The invariant "must never override an explicit blank choice this session" then
   requires a "has the user interacted yet?" flag racing async option load — a classic, hard-to-test
   bug surface, and a rule a reviewer cannot cheaply check on a diff.
3. **It makes the supported blank state a non-default.** Blank = generic questions is a first-class
   state (PostingPicker.js:26-27, :65-70). Pre-select lands the user in a posting-grounded state on
   load; generic then costs a clear-click *and* must survive the reactive re-apply.

### Why (b) "Recent" group is correct
- **The wrong thing is impossible, not guarded.** Nothing is ever auto-written to the parent's
  `value`, so an explicit blank choice can never be overridden — there is no code path that selects
  for the user. Blank stays the default and stays one click away (the field opens to nothing
  selected, exactly as today).
- **A dead (deleted-posting) option cannot be offered.** The Recent group is built *by filtering the
  freshly-fetched options* through `isRecentCompany` — it is a **subset of real options**. A
  remembered company whose postings were all deleted simply has no matching option, so it does not
  appear. There is no separate "render remembered companies as text" path that could show something
  resolving to nothing.
- **Minimize-clicks is satisfied relative to the safe baseline.** The directive forbids *burying*
  actions behind menus; the dropdown is the field's own native affordance. Today a user opens the
  field and scans all postings; with (b) their recent companies are the **first** options under a
  "Recent" header — strictly fewer clicks/less scanning than today, with **zero** added clicks to the
  pick flow. Zero-*click* resume is sacrificed only because the only way to get it here is the
  incorrect pre-select.

### How a remembered company maps to a selectable option
`orderRecentFirst(options, recentCompanies)` matches by `companyKey(option.company)` against the
remembered entries. All options for a remembered company surface in "Recent" (company-level, matching
the owner's "remember the companies" framing); within a company they keep their newest-`applied_at`
order (the order `normalizePostingRows` already returns). A remembered company with **no** matching
option is absent from the group. When **no** remembered company matches any option,
`orderRecentFirst` returns the original array and `groupBy` is `undefined` → the field renders
**byte-identical to today** (important for new users and for keeping the diff inert when there is
nothing to surface).

## 5. Decisions 4 & 5 — SHARED across modes; cap/dedupe/order (already specified)

### Decision 4: SHARED across both modes
**One store, one key, shared by live ("Interviewing for") and practice ("Practice for").** Rationale:
both modes render the **same** PostingPicker over the **same** `fetchPracticePostings` (the same
user's tracked postings) — the companies are one person's companies regardless of which tab recorded
them. A company interviewed for live is exactly one they would practice for. Per-mode would fragment
the memory (practice would not recall a company just used live) and would force a `mode` discriminator
prop into PostingPicker — a prop we otherwise avoid entirely (§6, the clients stay untouched). Shared
is both the owner's lean and the structurally simplest.

### Decision 5: cap + dedupe + recency order
Specified in §2 and §3: cap `RECENT_COMPANIES_CAP = 5`, dedupe by `companyKey` (case/whitespace
insensitive), recency = array order with re-selection moving to index 0. Enforced in pure
`addCompany`/`sanitizeRecentCompanies` and checkable without a render.

## 9. Could not verify (instrument the next seat needs)

- **V1 — array snapshot stability under `createChoiceStore`.** The factory was built for scalar
