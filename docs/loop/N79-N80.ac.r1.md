## 1. The domain analysis this chunk turns on: which causes are distinguishable

`getAuthenticatedClient(userId, redirectUri)` (`lib/gmail/gmailClient.js:78-98`)
returns `null` on two structurally different paths, and the route
(`app/api/gmail/messages/route.js:37-43`) turns both into the identical 403. The four
"causes" in the brief are really **two evidence classes**, and the honest
distinguishability picture is not four-way:

| # | Server-side evidence | Underlying cause(s) | Distinguishable from evidence? | Correct user remedy | One user action? |
|---|---|---|---|---|---|
| 1 | `loadTokens()` returned `null` (`:79-80`) | never connected **/** deliberately disconnected (`/api/gmail/disconnect`) **/** 30-day cache TTL expired (`:10`) on a once-connected account | **The three sub-cases are NOT distinguishable from each other.** Redis GET returns nil identically for a key never set, a key deleted, and a key evicted by TTL. No stored evidence separates them. | Connect Gmail (OAuth grant). Identical action for all three. | Yes — one click to `/api/gmail/connect`. |
| 2 | refresh threw; caught+discarded at `:91-94` | (a) revoked grant / dead refresh token → OAuth `invalid_grant`; (b) rotated/mismatched client secret → OAuth `invalid_client`; (c) transient network failure to Google's token endpoint | **YES, IF the thrown error is preserved.** (a) and (b) carry an OAuth error code in the HTTP response body; (c) has no HTTP response at all (network-level error). Today all are discarded, so none is distinguishable. | (a) Reconnect Gmail (re-consent). (c) nothing — retry later, it self-heals. (b) nothing the USER can fix — operator must fix env; user's reconnect will fail again at the callback. | (a) yes — one click. (c)/(b) no action. |

**Two findings the brief asked me to state plainly:**

- **F-1: The three "no tokens" sub-cases (never / disconnected / TTL-expired) cannot
  be told apart, and it does not matter for the remedy.** All three funnel to the same
  action (connect), which always restores access. Distinguishing them would require NEW
  storage (a "was ever connected" marker outliving the token, or a disconnect
  tombstone) — cost with no remedy payoff. **Do NOT write a criterion demanding the app
  tell never-connected from expired.** It cannot, and need not. (Copy MAY differ if
  such a marker is ever added; out of scope here — see §5.)

- **F-2: `invalid_client` (rotated secret) is an operator failure, not a user one.**
  The user's reconnect does not fix it (the token exchange in
  `oauth2callback/route.js` uses the same bad credentials and fails). So its
  *user-facing* outcome collapses into "temporarily unavailable," but its *operator*
  signal must stay distinct in the server log so someone can actually fix the env.

**Load-bearing behavioural distinction (this is what the code must act on):**
`{ connectable: not_connected | reauth_required }` (offer a remedy, stop the poll) vs
`{ transient: temporarily_unavailable }` (offer no remedy, keep polling, do not alarm).
The not_connected / reauth_required split within "connectable" is for **copy and log
fidelity**, not a different mechanism (both go to `/api/gmail/connect`).

**Closed client-facing cause vocabulary** (proposed; the route emits one of exactly
these in its body, the client keys on it, never on the human message):
`"not_connected"`, `"reauth_required"`, `"temporarily_unavailable"`.

## 2. Acceptance criteria

Each is written so the SAFE direction is the passing one. "RED on HEAD" = fails today,
before any implementation; "how I know" cites the current-tree fact that makes it fail.

### Server: preserve the evidence and emit a cause (N80 core)

**AC-1 — the refresh-failure error is preserved, not discarded.**
When `getAuthenticatedClient` hits the refresh-failure path, the thrown error's
discriminating information (at minimum: the OAuth error code if the failure carried an
HTTP response, or a network-error marker if it did not) MUST reach the route's refusal
decision. The bare `catch { return null }` at `gmailClient.js:91-94` that drops the
error is not acceptable.
- Instrument: a unit test that drives `getAuthenticatedClient` with a stored token
  whose refresh (a) rejects with an `invalid_grant`-shaped error, (b) rejects with a
  network-shaped error, and asserts the two produce **different** signals out of the
  function (return shape or thrown discriminant — design's choice), not an identical
  `null`.
- RED on HEAD: yes. `:91-94` discards `err` and returns `null` for every refresh
  failure; the "no tokens" path also returns `null` (`:80`). The function has exactly
  one failure output today. Read directly.

**AC-2 — the route's refusal body carries a machine cause code, gated behind auth.**
The `/api/gmail/messages` refusal response MUST include a machine-readable cause field
drawn from the closed set `{not_connected, reauth_required, temporarily_unavailable}`,
in addition to (not replacing) a human `error` string. The cause code MUST be produced
**only after** `supabase.auth.getUser()` succeeds (`route.js:16-23`), so it only ever
describes the authenticated caller's own account.
- Instrument: a route test asserting each of the three causes appears in the body for
  the corresponding upstream condition; and a test that an unauthenticated request
  (no/invalid user) returns the existing 401 with **no** cause field.
- RED on HEAD: yes for the cause field. `route.js:38-43` returns a fixed
  `{ error: "Gmail not connected…" }` with `status: 403` and no cause field for the
  null client. Read directly. (The 401 path already exists at `:21-23`; the
  "no cause on 401" half is a non-regression guard — say so.)
- Failure direction: the cause code must be COARSE. It must never contain token
  material, the client secret, Google's raw error body, or a stack. Over-coarse
  (collapsing to `temporarily_unavailable`) is a correctness bug caught by AC-3;
  leaking provider internals is a security bug caught by AC-11. Both are failures.

**AC-3 — the classifier is exercised against representative error shapes, and fails
safe toward a visible remedy.**
The mapping from upstream condition to cause code MUST be tested against, at minimum,
FOUR inputs: (i) `loadTokens` → null; (ii) refresh rejects with an `invalid_grant`-
shaped error; (iii) refresh rejects with a network-level error (no HTTP response);
(iv) refresh rejects with an **unrecognised** error. Required outcomes:
  - (i) → `not_connected`
  - (ii) → `reauth_required`
  - (iii) → `temporarily_unavailable`
  - (iv) → `reauth_required` (**not** `temporarily_unavailable`, **not** the empty
    success state)
- Rationale for (iv)'s direction: the dominant harm is the original bug — a genuinely
  broken connection rendered as "no job email," so the user never reconnects. An
  unrecognised persistent refresh failure defaulting to "retry silently" re-creates
  exactly that. Defaulting to "offer reconnect" is never silent; for the rare
  `invalid_client` case the reconnect fails visibly (better than silence) and the
  operator is alerted by AC-4. `temporarily_unavailable` (no remedy, keep polling) is
  permitted ONLY for a POSITIVELY-identified transient/network failure.
- Instrument: the classifier test above (four rows minimum). Count of rows that can
  fail = 4, one per branch — state this in the test.
- RED on HEAD: yes. No classifier exists; there is one output (`null` → one 403). Rows
  (ii)/(iii)/(iv) cannot even be distinguished today (AC-1). Read directly + C-0.2.

**AC-4 — the operator can tell a config failure from a transient one, server-side.**
On the refresh-failure path the route/client MUST log server-side a discriminant fine
enough to separate `invalid_client` (config/secret rotated — operator must act) from a
transient network failure. This is the ONLY place `invalid_client` is distinguished;
per F-2 it collapses to `temporarily_unavailable` for the user.
- Instrument: a test asserting the server log (or a server-only structured field)
  carries the specific discriminant on an `invalid_client`-shaped failure, distinct
  from the network case.
- RED on HEAD: yes. `route.js` only `console.error`s inside the *Google-call* try block
  (`:77-82`); the null path (`:37-43`) logs nothing at all. Read directly.
- Boundary note: this stays SERVER-SIDE. Per `activityChannels.js:82-86` the activity
  log (browser) sees only a route's request + status, so the fine discriminant must not
  need to reach the client to be useful to the operator — and must not, since the
  client log is downloaded and shared (AC-11).

### Client: distinct states and a REACHABLE remedy per cause (N79 core)

**AC-5 — a refusal produces a state distinct from "no messages," parsed from the body.**
`loadGmailMessages` MUST parse the refusal body and hold a connection state distinct
from the empty-results state, keyed on the cause code from AC-2. "Refused/disconnected"
and "fetched zero job emails" MUST be different observable states.
- Instrument: a component/hook test rendering the applications surface after (a) a 403
  with `not_connected`, (b) a 403 with `reauth_required`, (c) a 200 with
  `{ messages: [] }`, and asserting (a)/(b) are visibly different from (c).
- RED on HEAD: yes. `page.js:914-929` does `if (!res.ok) return;` at `:921` before the
  body is read, wraps all of it in bare `catch {}` at `:928`, and the only state it
  ever sets is `setGmailMessages(matched)` (`:927`). On refusal `gmailMessages` stays
  `[]` — byte-identical to zero results. Read directly.

**AC-6 — the remedy is REACHABLE at the point of failure, in one click, and is the
right remedy for the cause.** (loop-traps-spec: "does any criterion mandate naming a
remedy without requiring the remedy to be reachable?" — the answer here must be no.)
At the applications surface fed `emailClassificationsByAppId` (`page.js:2803-2815`):
  - cause `not_connected` → a **Connect Gmail** control, reachable in ONE click
    (a link/button to `/api/gmail/connect`), rendered inline at the failure site — NOT
    only inside the settings menu.
  - cause `reauth_required` → a **Reconnect Gmail** control, one click, same endpoint,
    copy naming that access expired/was revoked.
  - cause `temporarily_unavailable` → NO remedy control (there is nothing the user can
    do); at most a quiet "couldn't reach Gmail" note. Offering a reconnect button here
    would be the wrong remedy (crying wolf on a self-healing failure).
- The control MUST be user-initiated. It MUST NOT auto-navigate the user to Google's
  consent screen on its own (that hijacks the tab).
- Instrument: a test asserting, for each cause, the correct control is present/absent
  and that the connect/reconnect control's activation target resolves to
  `/api/gmail/connect` (verify the href/handler, not just that a button exists).
- RED on HEAD: yes. `page.js:2803-2815` passes only `emailClassificationsByAppId`; no
  connection state, no affordance reaches this surface. `GmailButton` renders only at
  `SettingsMenu.js:116` (CITED from N79; grep-confirmed as its sole site is N79's
  claim — I did not re-grep every render site this round, so treat "sole site" as
  CITED, but "no affordance at the chip surface" is VERIFIED from the read above).
- Minimize-clicks (`minimize-clicks` directive): the passing design is ONE inline
  action with a good default, not a path through settings and not a wizard. A remedy
  that takes four clicks to reach fails this criterion.

**AC-7 — reachability is real, not asserted: an integration test drives connect→return.**
There MUST be a test that, from the refused state, activating the inline
connect/reconnect control leads to the OAuth connect entry point, and that a successful
return (`/?gmail_status=connected`, the convention `oauth2callback/route.js` already
uses) clears the refused state and re-enables the fetch.
- Instrument: an integration/wiring test over the control → `/api/gmail/connect` →
  `gmail_status=connected` → state cleared path.
- RED on HEAD: yes — the control does not exist (AC-6), so nothing to drive. The
  `gmail_status` query convention DOES exist (verified in
  `oauth2callback/route.js`), so this builds on a real seam, not an invented one.

### Polling behaviour — conditioned on cause (N79 remedy, corrected by C-0.1)

**AC-8 — the poll stops on a persistent refusal and continues on a transient one.**
  - On cause `not_connected` or `reauth_required` (won't self-heal without user
    action): the 30-minute interval MUST stop after the refusal is received, and MUST
    resume only after a successful (re)connection.
  - On cause `temporarily_unavailable` (self-heals): the poll MUST NOT be permanently
    stopped by a single occurrence.
- Failure direction (named because a naive read of N79 gets it backwards): "stop
  polling on ANY refusal" is WRONG — it would permanently silence Gmail after one
  transient network blip, until a full page reload. The safe/passing behaviour stops
  only on the connectable causes.
- Instrument: a test asserting the interval is cleared after a `not_connected` /
  `reauth_required` response and NOT cleared after a `temporarily_unavailable` one.
- RED on HEAD: yes. `page.js:934-940` starts one 30-min interval and clears it only on
  effect teardown (`:938`); nothing inspects the response to stop it. Read directly.

### GmailButton — same swallow class, folded in per N79

**AC-9 — the settings-menu status control distinguishes "not connected" from
"couldn't check."** `GmailButton` MUST NOT render the "not connected → Connect Gmail"
state purely because a status fetch failed. A transient failure / non-OK status from
`/api/gmail/status` MUST render a distinct "couldn't check" state, not a false
"disconnected."
- Failure direction: showing "Connect Gmail" (implying disconnected) when the account
  is actually fine but the status check hiccuped is the failure to prevent — it is the
  same swallow-a-failure-as-a-negative-verdict defect as N79's main bug.
- Instrument: a `GmailButton` test with (a) `{connected:true}`, (b) `{connected:false}`,
  (c) a rejected/500 status fetch — asserting (c) is visibly distinct from (b).
- RED on HEAD: yes. `GmailButton.js:15-20` does
  `.then(r => r.ok ? r.json() : null).then(d => setConnected(d?.connected ?? false))`
  and `.catch(() => setConnected(false))` — a non-OK response and a thrown fetch both
  land on `connected=false`, identical to a genuine disconnect. Read directly.

### Activity log — a decision record with a cause (N80 obligation)

**AC-10 — the Gmail refusal records its own decision, with a coarse cause, through the
`act` channel; and the ledger is wired both ways.**
The Gmail fetch MUST record a decision via `recordDecision(...)` (the `act`-channel
seam, `appActivityLog.js:182-201`), because the automatic `net` channel can only show
THAT a 403 happened, never WHICH cause (`activityChannels.js:36-42, 82-86`). Required:
  - A new `DECISION_LEDGER` entry (`activityChannels.js`) whose `module` is the CLIENT
    module that actually calls `recordDecision` on the Gmail path (the activity log is
    browser-side; a server route cannot write to it — `activityChannels.js:82-86`).
    NOT a route file.
  - `outcomes` drawn from `DECISION_OUTCOMES` and including ≥1 negative — proposed
    `["acted", "refused", "failed"]` (`acted` = messages fetched; `refused` =
    connectable causes needing user action; `failed` = `temporarily_unavailable`).
  - `fields` a CLOSED set carrying the coarse cause and nothing sensitive — proposed
    `["reason", "cause", "count"]`, where `cause` ∈ the AC-2 vocabulary, `reason` is a
    canned string, `count` is messages fetched on success. NEVER a subject, sender,
    body, token, or raw provider error (mirrors the `fact-auto-insert` entry's `code`
    discipline at `activityChannels.js:224-232`).
  - A real `recordDecision` call on the actual refusal path (and, for the positive
    control, on success) with the matching `id` and correct outcome/cause per AC-3.
- Instrument (behavioural): a test asserting that a `not_connected` refusal records an
  `act` entry with outcome `refused` and `cause: "not_connected"`; a
  `temporarily_unavailable` refusal records outcome `failed`; a success records
  `acted`. Count of rows that can fail ≥ 3.
- Instrument (structural guard, ALREADY EXISTS): `decisionCoverage.sweep.test.js`
  binds `DECISION_LEDGER` to the tree's real `recordDecision(` call sites with
  `toEqual` in BOTH directions (`:262-288`) and requires a negative outcome
  (`:302-317`) and a non-empty closed field vocabulary (`:319-331`). This makes
  "listed but never called" and "called but not listed" both RED — so a half-wired
  Gmail decision cannot ship green.
- RED on HEAD: the behavioural test is RED — no Gmail entry in `DECISION_LEDGER`
  (verified: `activityChannels.js:215-233` holds only `duplicate-check` and
  `fact-auto-insert`) and no `recordDecision` call on the Gmail path. The structural
  sweep is GREEN at HEAD (2 consistent entries) and will go RED the instant either the
  ledger entry or the call is added without its partner — it is the guard, not the
  RED. Say both plainly.
- Non-regression note (not independently RED): `activityLogDocument.js:169-182`
  (`renderDecisions`) already prints every ledger entry's `label` under
  "### Decisions this app can report on" even in an empty session, so adding the entry
  auto-satisfies "the file names this reporter" — this is inherited, not new work, and
  I am not counting it as a fresh RED criterion.

### Security / backward compatibility

**AC-11 — no token material or provider internals cross to the client or the log; no
account-state probe for the unauthenticated.**
  - The refusal body (AC-2) and the activity-log `cause` field (AC-10) contain ONLY the
    coarse closed vocabulary — never access/refresh tokens, the client secret, Google's
    raw error body, or a stack.
  - The cause code is returned ONLY on the authenticated path; an unauthenticated
    caller gets 401 and learns nothing (AC-2). Because the route answers only about the
    caller's OWN account (`user.id` from `getUser`, `route.js:16-19,37`), the coarse
    codes cannot be used to probe whether some OTHER account exists or is connected.
  - Backward compatibility: existing 200 success shape `{ messages }` is unchanged; the
    401 shape is unchanged; existing callers reading `res.ok`/`messages` keep working.
- Instrument: a route test asserting the refusal body matches the closed vocabulary and
  contains none of a token/secret/stack fixture; an auth test asserting 401 carries no
  cause; a snapshot/shape test that the 200 body is unchanged.
- RED on HEAD: partially. The "no cause on 401 / own-account-only" and "200 unchanged"
  halves are non-regression guards (true today because there is no cause field at all)
  — they become meaningful once AC-2 lands and must not be violated then. The
  "coarse-only, no internals leaked" half is RED-relevant the moment AC-1/AC-2 thread
  an error through: the naive implementation (dump `err.message` into the body, as
  `route.js:80` already does on the 500 path with `detail: err?.message`) WOULD leak
  provider text and must be prevented. Flag `route.js:80`'s existing `detail:
  err?.message` as the pattern NOT to copy onto the 403 path.

  Cosmetic; leave to N78/cleanup unless the same block is edited anyway.
