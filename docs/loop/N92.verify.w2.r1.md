## Bug 1 (Sev-1, NOT-SHIP): the forward nudge never reaches the docx bytes -- preview AND
## download silently serve the UN-nudged position whenever the letter has real cover bytes

**Claim.** AC-C4 requires: "With the toggle ON, a newly generated letter that auto-inserts facts
positions them one forward-slot from placement, visible in the preview highlight AND at that
position in the download." This is false whenever `autoInsertFactsForJob` takes the `"splice"`
strategy (`hasCoverBytes === true` -- i.e. the entry already has real docx bytes, in-session or
via a stored `coverLetterDocxPath`). In that case the toggle changes the internal `lines`/
`insertedFacts` state but the PREVIEW and the DOWNLOAD both continue to show the fact at its
plain, un-nudged placement position. The toggle silently does nothing the user can see or
download in this case.

**Root cause, traced end to end (file:line):**

1. `hello-world/lib/acceptedFacts/factInsertion.js:432-453` (`applyForwardNudge`, called from
   `planAcceptForEntry:479` when `forwardNudge` is true) does `return { ...cover, lines, record:
   records, nudgedCount }` -- it patches `cover.lines` and `cover.record` with the nudged
   positions but **never touches `cover.edits`**. `cover.edits` stays exactly what
   `planCoverFacts` produced for the plain (un-nudged) insert. The function's own comment admits
   this ("KNOWN RESIDUAL... `edits` is left exactly as planCoverFacts produced it... reconciling
   the byte-splice path with a nudge is out of this wave's scope") -- a unilateral scope cut the
   AC does not authorize (AC-C4 names no carve-out for the byte-backed case; neither does
   `N92.design-structure.r1.md` section 4.3, which never mentions `edits` at all).
2. `hello-world/app/hooks/useCompanyResearch.js:832-857` (`autoInsertFactsForJob`): `plan =
   planAcceptForEntry(entry, { facts, coverRecord: priorRecord, forwardNudge: forwardPositioning
   })`, then when `strategy === "splice"` (true whenever `hasCoverBytes`, resolved at `:743-749`
   from `entry.coverLetterDocxB64` or a fetch of `entry.coverLetterDocxPath` -- i.e. any
   previously-generated or previously-saved letter): `spliced = await applyCoverDocxEdits(
   resolvedCoverDocxB64, entry.coverLetterResultLines, plan.cover.edits)` (`:857`). Because
   `plan.cover.edits` is the stale, un-nudged edit list from step 1, the spliced docx bytes place
   the fact at the ORIGINAL (un-nudged) position, not the nudged one.
3. `useCompanyResearch.js:938`: `if (!linesChanged && strategy === "splice") next.
   coverLetterDocxB64 = spliced.docxB64;` -- the stale-position bytes become the entry's
   canonical `coverLetterDocxB64`.
4. `useCompanyResearch.js:353-354` documents, as a load-bearing existing invariant (T17/PB1):
   "On success `edited` is NEVER assigned... an unedited accept keeps `resolveDocumentBlob`'s
   verbatim-serve branch [active]." Auto-insert (Wave 2's own call site included) never sets
   `entry.edited`, so this holds for the nudge too.
5. `hello-world/lib/document/docx.js:653` (`resolveDocumentBlobBytes`): `if (!edited &&
   engineDocxB64) return base64ToDocxBlob(engineDocxB64);` -- "Unedited: serve the finished doc
   verbatim." Two callers hit this with the stale bytes:
   - **Preview:** `hello-world/app/hooks/useDocumentPreview.js:412-425` (`loadPreviewModel`)
     calls `buildPreviewBlob(entry, scope, { resumeFile, coverLetterFile })` with **no `text`
     option**. In `hello-world/lib/document/previewBlob.js:92-113` (`previewBlobArgs`),
     `suppliedText = text !== undefined` is therefore `false`, so `textChanged = false` and
     `edited = editedForScope(e,"cover") || false = false` unconditionally. `resolveDocumentBlob`
     is called with `edited:false, engineDocxB64: entry.coverLetterDocxB64` (the stale bytes) and
     hits the verbatim-serve branch with **no dependency on whether the text "changed"** --
     the preview parses the stale docx directly, never `entry.coverLetterResultLines`.
   - **Download:** `hello-world/app/hooks/useDocumentPreview.js:506-533`
     (`downloadDocumentPreview`) computes `unchanged = text === scopeText(entry, scope)` where
     `scopeText` (`lib/document/previewBlob.js:59-65`) returns
     `entry.coverLetterResultLines.join("\n")` -- the SAME nudged lines the dialog's `text` was
     itself seeded from, so `unchanged` is `true` in the ordinary flow (generate, auto-insert,
     open preview, download -- no hand-edit in between). `serveFinished = !editedForScope(...) &&
     unchanged = true`. `hello-world/lib/tailor/documentScopes.js:49-53` (`buildDownloadArgs`)
     then sets `args.coverLetterDocxB64 = entry.coverLetterDocxB64` (the stale bytes) because
     `serveFinished` is true. `hello-world/lib/document/docx.js:752-762` (`downloadDocxFiles`)
     builds the cover blob with `engineDocxB64: coverLetterDocxB64, edited: !coverLetterDocxB64`
     -- `edited` is `false` (bytes are present) -- and again hits the verbatim-serve branch.

**So both the on-screen preview and the downloaded .docx are built from the stale, un-nudged
bytes whenever the letter has real docx bytes at auto-insert time -- which is the normal case
for any engine that produces docx output, and for any application that was ever saved (its
stored `coverLetterDocxPath` resolves `hasCoverBytes = true` on the next auto-insert too).**

**Direct execution proof (not just reading).** I copied the three unmodified production files
this bug lives in (`factInsertion.js`, `factMove.js`, `coverLetterWeave.js` -- byte-identical to
the working tree, confirmed no other imports) into an isolated scratchpad
(`%TEMP%\...\scratchpad\n92-verify\`) and ran the LOCAL project vitest against a new proof test
there (`proof.test.js`, not part of the working tree, never touches it):

```
 Test Files  1 passed (1)
      Tests  3 passed (3)
```

- Test 1: `planAcceptForEntry(..., {forwardNudge:true}).cover.lines` differs from
  `forwardNudge:false` -- the nudge does fire on `lines`. PASSED.
- Test 2: `planAcceptForEntry(..., {forwardNudge:true}).cover.edits` **equals**
  `forwardNudge:false`'s `cover.edits` -- the byte-splice input is blind to the nudge. PASSED
  (i.e. the defect is present).
- Test 3: applying `on.cover.edits` verbatim (the same substitution `applyCoverDocxEdits` does)
  reconstructs text that does **not** match `on.cover.lines` -- the bytes a real splice would
  produce disagree with the visible/persisted lines. PASSED (i.e. the defect is present).

**Blast radius beyond this generation.** Because `entry.coverLetterDocxB64` (stale) and
`entry.coverLetterResultLines`/`entry.insertedFacts` (nudged) now disagree inside the SAME
tailoring entry, any later operation that trusts the bytes (a further Control-A manual move via
`moveInsertedFact`, a Drive save, a second auto-insert run) inherits the inconsistency. I did not
chase this secondary path to a concrete outcome (it likely fails closed via `applyCoverDocxEdits`'s
`not-found` guard, `factDocx.js:44-46`, dropping bytes to `""` and forcing a lines-rebuild --
but that is inference, not verified execution, and is a should-check item for the next round).

**Why the shipped tests don't catch it.** `hello-world/app/hooks/autoInsertForwardNudge.rc.test.js:16-20`
states outright: "SHAPE B (no engine bytes, rebuildable template) is used on purpose... with no
docx splice to confound it." This is an honest disclosure in the test file, but:
- The AC (`N92.ac.r1.md` AC-C4) names no such carve-out -- "visible in the preview highlight AND
  at that position in the download" is stated without qualifying on which strategy the letter
  uses.
- The design (`N92.design-structure.r1.md` section 4.3) never discusses `cover.edits` or the
  splice path for Control C at all -- it was not a ratified, owner-visible scope cut, just an
  implementation gap the TDD/implementer seats made unilaterally and described only in a code
  comment.
- I confirmed (see "Full suite" below) that none of the ~14 other `autoInsertFactsForJob`-driving
  test files pass `forwardPositioning` with `hasCoverBytes: true`, so nothing in the existing
  suite exercises this composition either.

**Fix shape (not mine to build, but scoped for the next round):** `applyForwardNudge` needs to
also rewrite `cover.edits` to reflect the post-nudge span(s) -- e.g. by recomputing edits from
the original `coverLines` against the final nudged `lines`/`record` (mirroring how
`planMoveFact` itself builds `edits` for a single move), or by making `autoInsertFactsForJob`
fall back to `coverAlreadyEdited`-style bytes-drop-to-`""` (forcing a lines-rebuild, same as
AC-A9's own safety net) whenever `forwardNudge` actually moved a fact. Either closes the gap;
neither is implemented today.

## What needs the owner's real-browser check

Nothing in this feature is soundly verifiable by a human click-through as a SUBSTITUTE for Bug 1
above -- the bug is exactly the "toggle on -> generate -> look at the letter" scenario the owner
would naturally try, but it only reproduces when the letter has real docx bytes (i.e., most real
generations, not the bare-lines Shape B the shipped tests use). Concretely, the owner should:

1. Turn the "Position facts forward on future letters" toggle ON in Settings.
2. Generate (or auto-insert into) a cover letter using an engine that produces real docx bytes
   in-session (gemini, or any engine where the letter is not template-only), OR open a
   previously-saved application and let auto-insert run again.
3. Compare the fact's position in the rendered preview and in the downloaded .docx against the
   fact's position with the toggle OFF.

Per my trace, the two will be IDENTICAL (the toggle has no visible/downloadable effect) whenever
step 2 produces real bytes -- this is the check that would have caught Bug 1 before ship, and it
is exactly the check the shipped test suite deliberately avoided ("no docx splice to confound
it").
