## 1. What ALREADY EXISTS (the near-rebuild hazard — read this before designing)

**The uploaded formatting template is ALREADY PERSISTED per user. What is missing is MULTIPLICITY,
NAMING, and SELECTION — not persistence.** An implementer who builds "persist the template" rebuilds
what ships today. The genuinely-new work is turning a single overwritten slot into a named,
selectable collection, plus provenance.

### 1.1 The input template today: one overwritten slot per kind
- Upload writes React state **and** upserts a fixed storage key: `supabase.storage.from("resumes")
  .upload(\`${userId}/resume\`, file, { upsert: true })` (`ApplyingControls.js:84-86`) and
  `\`${userId}/cover-letter\`` (`:117-119`). `upsert:true` at a **fixed, non-parameterised key** means
  a second upload **overwrites** the first — there is exactly one resume template and one cover-letter
  template per user, ever. (This is why AC-1 is genuinely RED on HEAD, not vacuously.)
- Every reader hardcodes those two keys: cron re-tailor (`cron/tailor/route.js:142,146`), manual queue
  (`auto-apply-queue/tailor/route.js:114,121`), and `sourceResumePath` builders (`page.js:2015,2306,2566`,
  `useManualTailor.js:300`, `useDocumentPreview.js:731`). **Any feature that repoints generation at a
  collection must keep these working** (AC-8).

### 1.2 The output (generated) documents are stored as their own frozen bytes
- `generated_resumes.docx_path` → `<userId>/generated/<id>.docx` (`20260617000000_generated_resume_docx_path.sql`;
  written `saveGeneratedResume.js:71,75-79`). `generated_cover_letters.docx_path` → `<userId>/generated/<key>.docx`
  (`20260928000000_n59_cover_letter_docx_path.sql:29-30`; `coverDocxStore.js:71-79`).
- **Load-bearing for AC-4:** a past application's output is stored bytes captured at generation time,
  NOT re-rendered from the input template on read. So editing/deleting a template *structurally cannot*
  alter a stored output today — AC-4 exists to keep it that way under the new delete/edit paths.

### 1.3 Three DIFFERENT existing senses of "template" — do not rebuild or conflate
1. **Uploaded .docx formatting shell** — sense N64 means; single-slot today (§1.1). *The gap.*
2. **`tailor_edit_rules`** (`20260702000000_tailor_edit_rules.sql`) — per-user learned hand-edits,
   applied server-side to *every* generation. Persisted, unconditioned, not named/pickable.
3. **`tailor_personas`** (`20260703000000_tailor_personas.sql`) — per-user named tailoring-preference
   bundles (values/focus_area/cover_variant), per-posting selectable via `FocusPickerDialog`.
   *This is the RLS idiom to copy for the new table.*

### 1.4 Reuse map — what a designer/implementer should build ON, not reinvent
- **RLS + table idiom:** copy `tailor_personas.sql` verbatim in shape (§4).
- **Per-user CRUD route:** `makeCrudHandlers({ table, validate })` (`lib/llm/engines/tailor-lite/library/crudRoute.js:16-67`)
  — insert with `user_id`, update/delete gate on `id` AND `user_id`; wired e.g. `app/api/library/personas/route.js:6`.
  The saved-templates route should use this, not a bespoke handler.
- **Server auth+filter:** `saved_searches/route.js` — `getUser()` → 401 if none → `.eq("user_id", user.id)`
  on every read/write, on top of RLS.
- **Storage bytes:** the `resumes` bucket + `<userId>/templates/<id>.docx` key (mirroring the existing
  `<userId>/generated/<id>.docx` convention). Nothing new in storage plumbing.
- **Validity:** `isDocxResume` (`docx.js:73-75`) already gates the rebuild path (`buildDocxFromUploadedTemplate`
  requires a `.docx`); a saved template must satisfy it.

## 3. Acceptance criteria

Written so the SAFE direction is the passing one. Each names its instrument and its RED-on-HEAD
status, honestly labelled. **Honesty note (rule 1):** this is a NEW feature, so several criteria are
RED simply because the capability is absent — that kind of RED confirms only that the feature is not
built and carries little evidential power. I mark those **RED (absence — low power)**. The criteria
with real power are the CONSTRAINTS that make a wrong build impossible or caught: AC-1 (a live
overwrite defect), AC-2 (cross-user isolation), AC-4 (the delete/edit safety + FK direction), AC-8
(don't break the cron). Those are marked accordingly.

**AC-1 — A user can save MORE THAN ONE named template of each kind, and saving/replacing one never
destroys another.** The store models a collection (one row + one storage object per template), so N
resume templates and N cover-letter templates coexist per user; create, rename, and replace-bytes are
all supported; a saved template must be a valid `.docx` (`isDocxResume`).
- Instrument: a behavioural test — save template A (resume), save template B (resume), then list/fetch
  and assert BOTH exist and A's bytes are unchanged; plus a rename test and a replace-bytes test.
- RED on HEAD: **YES, with power.** Today `ApplyingControls.js:86` upserts the single fixed key, so
  saving B overwrites A; the two-template test loses A. Failable rows on HEAD ≥ 1.
- Failure direction: losing a previously-saved template (or silently overwriting) is the harm; the
  passing state preserves every saved template.

**AC-2 — Templates are per-user, RLS-isolated, and uniquely named per user.** Each row carries
`user_id` and a user-chosen `name`; a user can read/list/select/rename/delete only their OWN
templates; a duplicate name for the same user+kind is rejected (case-insensitive), so selection is
unambiguous. Storage objects are under the owner's `<userId>/` prefix.
- Instrument: (a) a cross-user test — user B cannot select, read, rename, or delete user A's template
  (both DB RLS `auth.uid() = user_id` and the route's `.eq("user_id", user.id)` enforce it); (b) a
  duplicate-name rejection test; (c) confirm the migration declares the four `auth.uid() = user_id`
  policies + grants (mirror `tailor_personas.sql`).
- RED on HEAD: **guard / vacuous today** — no table or policy exists, so the cross-user test cannot
  even run; it becomes a live guard once the table exists. State this plainly.
- Failure direction (SAFE = passing): the unsafe outcome is one user's template being visible, usable,
  or deletable by another; the criterion passes only when isolation holds. Over-refusing (a user
  denied their own template) is the less-bad direction but still a defect the duplicate/own-read test
  catches.

**AC-3 — At generation the user picks which template to use, in ONE action, defaulting to the
last-used; with ZERO saved templates the flow is exactly today's.** The generate flow lets the user
choose a saved resume template and a saved cover-letter template; the selection **defaults to the
last-used** (remembered across sessions) so the common case adds zero clicks; no nested menu, no
compulsory wizard ([[minimize-clicks]]). If the user has saved none, generation behaves exactly as
today (their existing single slot / upload), never forcing template creation.
- Instrument: a test that (a) with template T selected, the bytes/path threaded into
  `resolveDocumentBlob` / the tailor `formData` are T's — NOT the legacy `<userId>/resume` slot — asserted
  at the point they are handed to generation (last-hop, not an internal flag); (b) the zero-template
  path still generates; (c) the default equals the last-used across a simulated fresh session.
- RED on HEAD: **RED (absence — low power)** for the selection mechanism; there is no picker and
  generation reads the hardcoded slot.
- Failure direction: silently generating from the legacy/wrong template when the user selected another
  is the harm.

**AC-4 — Editing or deleting a template NEVER alters or breaks any already-generated document.**
A past application's stored output (`generated_resumes` / `generated_cover_letters` docx bytes at
`<userId>/generated/...`) must remain byte-identical and downloadable after its source template is
edited or deleted. **The provenance FK MUST be `on delete set null`, never cascade** — deleting a
template that produced past outputs nulls the provenance pointer (AC-5), it must never delete or
corrupt the output row.
- Instrument: generate output O from template T and record O's stored bytes; then (a) replace T's
  bytes, (b) rename T, (c) delete T — after each, assert O's stored bytes and its download are
  unchanged and still resolve; plus a schema assertion that the template→generated FK is
  `on delete set null` (or that no FK cascades a template delete onto a generated row).
- RED on HEAD: **vacuously true today, so a BUILD GUARD, not a current-defect catch.** No template
  entity can be edited/deleted yet, and outputs are already frozen bytes (§1.2), so the property holds
  by construction now. It becomes a live guard the moment delete/edit exist; the risk it forecloses is
  a future design that re-renders outputs from the live template on read, or a cascade FK. This is the
  single most important safety criterion — say so; do not let its non-RED status hide it.
- Failure direction: the migration must fail toward preserving the output (set-null / no-cascade), not
  toward deleting or re-deriving it.

**AC-5 — Provenance is recorded AND reachable by the user, and degrades gracefully when the template
is gone.** The `generated_resumes` / `generated_cover_letters` row records the `template_id` used; for
a past application the user can SEE the template's name at a surface they can reach (tracking / preview);
if that template was later deleted or renamed, the display reads a graceful label (e.g. "(template no
longer saved)") and nothing errors or blanks.
- Instrument: (a) a test that a generated row carries the selected `template_id`; (b) a **last-hop**
  render test mounting the real past-application surface and asserting the template name appears in the
  rendered DOM (not merely that a column holds a value — this repo's recurring "complete mechanism,
  missing user-facing hop, green suite" class, now nine instances); (c) a delete-then-view test showing
  the graceful label, no crash.
- RED on HEAD: **RED (absence — low power)** — no `template_id` column and no display exist.
- Failure direction: a broken/blank/errored provenance, or provenance recorded but never reachable by
  the user, is the harm; the last-hop clause is what forecloses the recurring defect.

**AC-6 — app-vs-chat REMOVAL test (Corpus).** A named template saved in one session is retrievable and
selectable in a LATER session, and more than one named template survives. The criterion goes RED if the
collection is held only in session/memory or collapses to a single overwritten slot.
- Instrument: save two named templates, simulate a fresh session with no in-memory carryover, assert
  both are listed and selectable.
- RED on HEAD: **YES** (single-slot upsert; no named collection survives).
- Note for 1c/8b: **1c owns the final advantage claim, not AC.** The class is **Corpus** ("across
  applications; the user never re-states what the app already holds"). Be honest: the *fact of
  persistence* is INHERITED (app-vs-chat card: Supabase persistence costs one line). The EARNED
  increment here is the named **multi-template collection** and cross-application reuse; the fullest
  form of the advantage (auto-pairing a template to a posting) lands with the DEFERRED matcher (§9).
  8b re-judges whether the shipped chunk still holds even the multiplicity increment.

**AC-7 — No new activity-log decision entry this chunk, and `decisionCoverage.sweep.test.js` stays
green.** Template CRUD is user-driven and its outcome is captured structurally by AC-5's provenance
column; it is not an app *decision* the user needs a downloadable trace of. So this chunk adds NO
`recordDecision(...)` call and NO `DECISION_LEDGER` entry.
- Instrument: `decisionCoverage.sweep.test.js` — it binds `DECISION_LEDGER` ↔ actual `recordDecision`
  call sites `toEqual` both ways, so adding a call without a ledger entry (or vice-versa) ships RED. It
  must remain green with no change.
- RED on HEAD: **n/a — a "do not add" constraint**, stated so the checker does not file it as
  unfalsifiable. It fails a build that adds a half-wired decision entry.
- Deferred hook (do NOT build now): the §9 matcher WOULD warrant an entry — id e.g.
  `template-auto-select`, `outcomes` including a non-`acted` value for "no condition matched → default"
  (`skipped`) and `failed`, `fields` a CLOSED coarse set (matched-condition code + candidate count),
  NEVER the template name, posting text, company, or a source URL (surface-H `code` discipline). Named
  so the deferred design starts from it.

**AC-8 — Existing single-slot readers keep working (non-regression).** Introducing the collection must
not break the paths that today read the fixed `<userId>/resume` / `<userId>/cover-letter` slots: the
auto-tailor cron (`cron/tailor/route.js:142,146`), the manual queue (`auto-apply-queue/tailor/route.js:114,121`),
and the client `sourceResumePath` builders (`page.js:2015,2306,2566`, `useManualTailor.js:300`,
`useDocumentPreview.js:731`). A user who never creates a named template still tailors from their
existing slot; the compatibility mechanism (seed one template row from each user's existing slot, or
treat the legacy slot as the implicit default) is a design/1d decision, but the behaviour must not
regress for any existing user.
- Instrument: an existing-user simulation (bytes present at the legacy slot, no template rows) that
  drives cron/manual tailoring and asserts it still produces output; plus a test that these readers
  resolve a source for a user with zero template rows.
- RED on HEAD: **guard / non-regression** — passes today (nothing changed yet); it becomes RED against
  a build that repoints generation at the collection and forgets the legacy readers.
- Failure direction: silently breaking auto-tailor for every existing user (an empty/failed
  generation) is severe; the safe build preserves the legacy read.

## 4. Migration (must be settled BEFORE code; migrations auto-deploy to prod on push)

This chunk NEEDS a migration. Exactly:
1. **New table** `public.resume_templates` (name TBD by design; kept generic across kinds), copying the
   `tailor_personas.sql` idiom verbatim in shape: `id uuid pk default gen_random_uuid()`;
   `user_id uuid not null references auth.users(id) on delete cascade`; `name text not null`;
   `kind text not null` (`'resume'|'cover'`, with a `CHECK`); `storage_path text not null` (the
   `<userId>/templates/<id>.docx` object); `created_at`/`updated_at timestamptz`. A per-user index; a
   unique index `(user_id, kind, lower(name))`. RLS enabled; four `auth.uid() = user_id` policies
   (select/insert/update/delete); grants to `authenticated` + `service_role`.
2. **Provenance columns:** `template_id uuid` on BOTH `generated_resumes` and `generated_cover_letters`,
   nullable, FK to the new table **`on delete set null`** (AC-4). Nullable so every pre-migration row
   and every generation without a chosen template keeps `NULL` and degrades gracefully (mirrors how
   `docx_path` was added nullable to both tables — `20260617...` and `20260928...`).
- **SCHEMA-DRIFT CAUTION (MEMORY schema-migration-drift):** `generated_resumes`' base CREATE TABLE is
  NOT in the repo, and the live DB is known to carry constraints no migration creates. The
  `generated_resumes` ALTER must be verified against the LIVE schema before push (an `add column if not
  exists` of a nullable FK is backward-safe, but the FK target/behaviour must be confirmed to exist and
  not collide). `generated_cover_letters` IS in-repo (`auto_apply_queue.sql:11`), so its ALTER is
  verifiable in-repo.
- **No RPC signature churn** (unlike N59): provenance is a plain column write at generation time. If a
  compatibility seed (AC-8) is done in SQL, it is a one-time backfill and must be idempotent.

## 5. Storage posture (templates are INPUTS — the growth profile differs from outputs)
- Templates are **user-managed inputs**, bounded by user action (a handful per user), each a small
  `.docx`. This is a DIFFERENT growth profile from generated OUTPUTS (one per application, unbounded),
  so **do not assume today's owner ruling on output retention/cleanup carries.** A template is removed
  only by explicit user delete; **no retention/cleanup policy is warranted this chunk.** I decide this
  (reversible); reasoning stated. A soft per-user cap to bound abuse is optional and not required — if
  the owner later wants a spend/storage cap it is a one-line addition, not a blocker. Bytes reuse the
  existing `resumes` bucket; no new bucket.

## 6. minimize-clicks (design constraint, checked at AC-3)
- **Save inline, not via a wizard:** offer "save this as a template" at the point the user already
  uploads a docx to generate, with a default name derived from the filename — one action.
- **Pick defaults to last-used**, remembered across sessions; the common case is zero extra clicks.
- **Confirm only on delete** (destructive/irreversible earns a dialog per the directive); saving,
  renaming, and picking do not.
- Fewer clicks never means fewer routes: the picker, save, and delete controls stay keyboard-reachable
  (the one standing tension in the directive).

## 7. Composite surface cost (for the 8b re-judge)
This chunk ADDS: a per-user template table + storage objects; a CRUD surface (built on
`makeCrudHandlers`, not bespoke); a template picker at generation; and a provenance display on the
past-application surface. It DISPLACES the single-slot upload-and-overwrite model (which becomes
"save/replace one of several") and the hardcoded single-slot generation reads. **Do not add these as
inline bulk in `app/page.js`** (already under a consolidation ceiling — MEMORY page-js-consolidation);
the picker and manage-list belong in their own small component, and the CRUD in a route reusing the
library handler. Targets to watch for size: `page.js`, `useDocumentPreview.js`, `useManualTailor.js`
are all large and already thread the single-slot path.

## 8. Explicitly OUT of scope
- **The industry/other-condition auto-apply matcher and its cron integration (owner half B)** — §9;
  deferred, named, not built.
- **Rebuilding template PERSISTENCE, the RLS plumbing, the storage bucket, or the CRUD handler** — all
  exist (§1.4); reuse them.
- **`tailor_personas` and `tailor_edit_rules`** — the two existing non-formatting "template" senses;
  not touched, not merged (bundling a persona into a template is a flagged design question, §0, not a
  build target here).
- **Changing how a generated OUTPUT is rendered or stored** — outputs stay frozen bytes (§1.2); AC-4
  forbids re-deriving them from the live template.
- **Output retention/cleanup policy** — a separate owner-filed concern; templates need none (§5).
- **Server-side auto-tailor SELECTION logic** — cron keeps reading the default/legacy slot this chunk
  (AC-8); per-posting selection is the deferred matcher.

## 9. DEFERRED — the auto-apply-by-condition matcher (owner half B), named precisely
So the follow-up starts from a spec, not a blank page:
- A condition→template mapping per user (industry, and the owner's "other conditions" — seniority,
  company size, remote, etc.; **which conditions are matchable is an owner product decision**).
- Auto-selection at generation AND in the cron (`cron/tailor/route.js` — today one buffer per user,
  regardless of posting; this is what the matcher rewrites).
- Precedence / tie-break when multiple conditions match, and the fallback when none match (→ the
  user's default template — must degrade to AC-8's behaviour).
- The `template-auto-select` decision-ledger entry (AC-7 hook) with a non-`acted` "no match → default"
  outcome and content-free fields.
- The strongest app-vs-chat Corpus claim (auto-pairing across many applications) lives here, not in (A).

## 10. Criteria I could not make fully falsifiable / could not fully verify, stated plainly
- **AC-4 and AC-8 are non-RED build guards, not current-defect catches.** They are vacuously true /
  passing on HEAD because the feature is absent (AC-4) or unchanged (AC-8). I have said so in each; they
  earn their place as the safety/regression fences a wrong build trips, and the checker should confirm
  the delete/edit and legacy-reader tests are constructed to actually exercise them once the feature
  exists (a test that never deletes a template, or never simulates an existing single-slot user, has
  zero power on these two).
- **AC-3's "default = last-used across sessions"** depends on where "last-used" is stored (a template
  column, `localStorage`, or a prefs row). I specify the behaviour, not the store; if the store is
  chosen as `localStorage` alone it will not survive a device change — a design/1d call, flagged.
- **The `template_id` provenance on `generated_resumes`** cannot be fully proven in-repo because that
  table's base schema is not in the repo (§2). The ALTER's safety rests on a live-schema check the
  design/1d seat must perform before push; I could not perform it read-only from the tree.
- **Whether a template should bundle a persona** (§0) is a design/owner nicety I left at a default (no
  bundle); it is the one place the scope could legitimately widen, so I flag it rather than fixing it.
