> **Headline.** The two machines this needs both already exist and are independently proven: the
> formatting override (`resolveDocumentBlob({formattingTemplate})`, F7) turns content + a template .docx
> into a formatted blob with no engine call, and the append-only version trail
> (`persistGeneratedDocuments` → `generated_resumes/_cover_letters` rows, read back by
> `fetchDocumentVersions`, reloaded + re-selected by `refreshDocumentVersions`) already grows by one row
> per generate/revise and never mutates or deletes an older row (F2, F3, F6). N151c **wires these two
> together**: build the blob locally from the CURRENTLY-DISPLAYED content + the chosen template, write
> those same bytes onto the entry for immediate display, and persist them as one more append-only row —
> the exact persistence block `resubmitDocumentPreview` already runs (F5), minus the `/api/tailor` call.
> **What is genuinely new is small:** (a) a way to fetch ONE library template's bytes by id (today only
> the ACTIVE selection's bytes are fetchable — F8, the one real gap), (b) a tiny extracted module that
> builds-blob-and-persists (the hook has ~13 lines of headroom — F11, a hard constraint), and (c) the
> modal control (a picker: the N151b library list + a .docx upload input). No new table is REQUIRED; a
> provenance column is an owner option, not a necessity (OR-1).

## 1. The decision that is expensive to reverse: **what a "regenerate into template X" version IS**

**Ruling (recommended, forced by the code): a template-regen version is an ordinary append-only
generation row whose stored bytes (`docx_path`) are the CURRENT content re-poured into template X's
formatting. It carries the SAME `content`/`content_lines` as the version it was produced from (template
regen changes formatting, never content — §1 of N151, OR-1 of N151 CITED), and it is reproducible-in-
OUTPUT because its formatted bytes are frozen in storage exactly like every other version's.**

Why this is forced, not a preference:
- `resolveDocumentBlob({formattingTemplate})` (F6) produces formatting-only output from content + a
  template; it is the SAME primitive the download already uses (F7). Nothing about it is engine-specific
  (N151 §2 CITED) — content in, template-formatted bytes out, on the client.
- The version trail is append-only by construction (F2/F3): a new row is the ONLY non-destructive way to
  add an output without touching the originals. The owner's three fixed requirements (new version; not a
  one-off; not an overwrite) map 1:1 onto `persistGeneratedDocuments` appending one row.
- A regen version's `content` is unchanged, so later editing it rebuilds correctly: `selectDocumentVersion`
  points `docxPath` at the regen row's `docx_path` (template-formatted engine doc), and an edited download
  rebuilds the edited text onto THAT (F4 + `docx.js:718-728`) — formatting survives the edit.

**Consequence the AC/plan/TDD must honour:** there is NO model call in this path. The regen builds its
blob with `resolveDocumentBlob` and persists it; `/api/tailor` is never fetched. This is the headline
property and the headline test (§7 T4).

**OR-1 (owner call — the one data-model decision): does a regen version need to RECORD which template
produced it?** Output-reproducibility is already guaranteed by the frozen `docx_path` with NO schema
change. A template *provenance* column (`generated_resumes.formatting_template_id uuid null →
resume_templates(id) ON DELETE SET NULL`, + the cover table) would let the version history LABEL a row
"via <template name>" and let a future "re-apply this template to new content" exist. **Recommend
DEFER the column for the first slice** (zero migration, satisfies all three owner requirements; the
regen version is distinguished from a revise version only by its timestamp in `VersionControl`, which is
honest — see §4). If the owner wants labeled history now, that is an additive migration (stamp >
`20261008010000`, F15) + threading one nullable field through `saveGeneratedResume`/`fetchDocumentVersions`/
`VersionControl` — a clean, self-contained follow-up. **Flagged; recommend defer.**

## 2. The data flow (the contract every downstream seat builds to)

For the active docx scope (`"resume"` or `"cover"`), a regenerate-into-template(X) does, in order:

1. **Flush edits.** The dialog calls `commitDraft()` immediately before invoking the handler — exactly
   as it already does before `onSelectVersion` (F1, `DocumentPreviewDialog.js:716-720`). So the handler
   reads the freshest entry content.
2. **Resolve X to a docx `File`:**
   - **on-the-spot upload:** the user's uploaded `.docx` File is X directly — no storage, no route
     (reuse `isDocxResume` gating; a non-`.docx` is refused in the control, §3).
   - **library pick:** fetch X's bytes by id via the NEW path (§3.1, closes F8) → a `File`.
3. **Build the blob LOCALLY (no model call):**
   `resolveDocumentBlob({ text: <current scope text>, lines: <current scope lines>, edited: true,
   formattingTemplate: X })` → a Blob. (`edited:true` is belt-and-braces; the override branch fires on
   `hasText || lines.length` regardless — F6.) Current text/lines come from the entry exactly as
   `previewBlobArgs` reads them (`entry.result`/`resultLines`; `coverLetterResultLines` — F6/`previewBlob.js`).
4. **Encode:** `docxB64 = bytesToBase64(new Uint8Array(await blob.arrayBuffer()))` (shared encoder, §3.3).
5. **Show it immediately** (mirror F5's `updateTailoringJob`): set this scope's `docxB64 = docxB64`,
   clear `docxPath` (a fresh in-session doc), clear the scope's preview html, set `edited:false` for the
   scope, `status:"done"`; then `setPreviewReloadKey(k=>k+1)` so the preview re-renders showing template
   X's formatting verbatim. (Cover: `coverLetterDocxB64`/`coverLetterDocxPath`.)
6. **Persist as a NEW VERSION** (identical to F5): `persistGeneratedDocuments(supabase, { userId,
   positionId, [scope]: { content, contentLines, docxB64 } })` — append-only row; `docx_path` set async
   by the upload (F3).
7. **Reload history + select the new version:** `refreshDocumentVersions(jobId, [scope],
   versionsRequestIdRef.current, positionId)` → the history grows by exactly one and `currentVersionId[scope]`
   becomes the new (newest) row (F4). `VersionControl` now shows it as current.

**What the version record stores (F2, unchanged by the recommended slice):** `content` + `content_lines`
(the current content, same as the source version) and, after the async upload, `docx_path` (the
template-formatted bytes — the reproducible output). It does NOT store the template id unless OR-1 adds
the column.

**Non-destructive (AC):** step 6 only INSERTs; no older row is updated or deleted (F3). The application
pointer update inside `persistGeneratedDocuments` moves `resume_used_id`/`cover_letter_id` to the new
row for THIS user+position only (`persistGeneration.js:84-104`) — past applications of OTHER postings are
untouched, and the user can still `selectDocumentVersion` back to any older row (F4). Frozen output bytes
of past downloads are read independently of any template (N97 §5 CITED).

## 3. What is genuinely NEW vs REUSED

### 3.1 NEW — fetch one library template's bytes by id (closes F8)
The only missing primitive. Two additive pieces, modelled exactly on the default-route bytes path (F7):
- **Store:** `getTemplateBytesById(supabase, { userId, id, kind }) → { bytes: Uint8Array } | null`
  in `templateLibraryStore.js` — reads the owned row (`id + user_id + kind`, `.maybeSingle()`), downloads
  `storage_path` from the `resumes` bucket, returns bytes; null (never throws) on missing/foreign/empty,
  same shape as `getSelectedTemplateBytes` (F9).
- **Route:** extend `GET /api/templates/library` to accept `?kind=&id=<id>&bytes=1` → that owned
  template's `.docx` bytes (`Content-Type` docx), `404` if not owned/absent; the existing `?kind=`
  metadata response is unchanged (backward-compatible — the N151a/b GET test asserts `{templates}`/
  `{selectedId}` only). `userId` ALWAYS from `requireUser`, never the query (AC/idiom pin).
- **Client:** `fetchLibraryTemplateFile(kind, id) → File | null` in `templateLibraryClient.js` —
  mirrors `resolveDefaultTemplateFile` (F7): fetches the bytes path, trusts only a `wordprocessingml`
  content-type, returns a `File` or null on any failure.

Rejected alternative: "temporarily select X, then read the active bytes" — mutates the user's persistent
selection as a side effect of a one-off regen (surprising, and races a concurrent switch). A by-id read
is the honest shape.

### 3.2 NEW — a thin regen module (forced by the F11 line ceiling)
`lib/document/regenerateIntoTemplate.js` (NEW) holds the steps-3-4-6 heavy lifting so the hook grows by
only a few lines (F11, ~13 lines headroom):
- `renderContentIntoTemplate({ scope, entry, templateFile }) → Promise<string>` (docxB64) — builds the
  blob via `resolveDocumentBlob` with the scope's current text/lines + `formattingTemplate` (F6) and
  encodes it (§3.3). PURE of React; node-testable; returns `""` when there is no content/blob.
The hook adds `regenerateActiveIntoTemplate(scope, templateFile)` — a thin wrapper that calls the module,
runs the `updateTailoringJob`/`setPreviewReloadKey` display write (step 5), then the EXISTING
`persistGeneratedDocuments` + `refreshDocumentVersions` block (reuse F5's code path; consider extracting
that block too if the hook would still breach 935 — the plan sizes this).

### 3.3 NEW — a shared Blob→base64 encoder
Extract `bytesToBase64` into a tiny shared `lib/document/docxBytes.js` (or export it from an existing
docx util) and have `coverDocxStore.js` import it (F10) — avoids a second copy. One small module; one
re-point of the existing local use.

### 3.4 NEW — the modal control (UX seam — 1c owns the exact surface; structure fixes the contract)
A control in the modal for the active docx tab: "**Reformat in another template…**" (NOT "Regenerate" —
F12 collision) opening a picker with (a) the N151b library list for this kind (REUSE
`listLibraryTemplates` / the `useTemplateLibrary` hook — N151b §Step 3 CITED) and (b) a `.docx` upload
input. Choosing a library row → `fetchLibraryTemplateFile` → `regenerateActiveIntoTemplate`; choosing an
uploaded file → the File straight into `regenerateActiveIntoTemplate`. **Must land OUTSIDE
`.MuiDialogActions-root`** (F13) — the N97 `SetDefaultTemplateControl` sibling slot
(`DocumentPreviewDialog.js:883-887`) is the precedent; place the new control adjacent to it, gated on
`DOCX_SCOPES.includes(tab) && available(tab)`. The upload input is `accept=".docx"`; a non-`.docx` is
refused in-control (isDocxResume), never reaching the override as empty bytes.

### 3.5 REUSED unchanged (signatures preserved)
- `resolveDocumentBlob` / `buildDocxFromUploadedTemplate` (F6) — no signature change.
- `persistGeneratedDocuments`, `saveGeneratedResume/_CoverLetter`, `fetchDocumentVersions`,
  `refreshDocumentVersions`, `selectDocumentVersion`, `VersionControl` (F2-F4) — no change.
- `listLibraryTemplates` / `useTemplateLibrary` (N151b) — reused by the picker.
- The four N97 consumption surfaces and the default/selection routes — UNTOUCHED.

## 4. The version-label question (owner brief asks explicitly)

`VersionControl` shows each row as `Version N of total — <timestamp>` and needs ≥2 rows to appear
(`VersionControl.js:40,59-66`). A template-regen row is therefore shown like any other generation,
distinguished only by its timestamp. **This is honest and sufficient for the first slice** — the user
regenerated just now, so the newest row is obviously the one they made. A richer label ("via <template
name>") REQUIRES the OR-1 provenance column (there is nowhere to read a template name from today — F2).
**Recommend: no label this slice; defer to the OR-1 follow-up.** Flag for AC: the "new version appears
and is selected" criterion must assert on the history COUNT growing by one and the new row becoming
current, NOT on a label string.

## 5. Scope / safety (owner requirements → structural guarantees)

- **Formatting-only, no model call** (owner): the path is `resolveDocumentBlob` + persist; `/api/tailor`
  is never called. Test asserts the fetch is absent (§7 T4). (OR-1 of N151 CITED: template = formatting.)
- **`.docx`-only template** (OR-2 of N151 CITED): the upload input is `accept=".docx"` and gated by
  `isDocxResume`; a library template is `.docx` by construction (N151a route validates ZIP magic —
  `library/route.js:126`). A non-docx can never reach the override as empty bytes.
- **Owner-scoped:** the by-id bytes read is gated `id + user_id + kind` + RLS; `persistGeneratedDocuments`
  takes `userId` from `currentUser`; the route takes `userId` from `requireUser`, never the request.
- **Preserve `download-rebuild-formatting` + per-engine (N89/N97 reconcile):** the override is applied
  on the client at the one choke point, engine-uniform; N151c adds no engine branch (N151 §2 CITED).
- **No regression to preview/version-switch:** `selectDocumentVersion`/`VersionControl`/`documentVersions`
  are reused unchanged; the new row is just another entry they already handle. The display write (step 5)
  uses the SAME per-scope fields `resubmitDocumentPreview` already writes, so the AC-3/AC-4 "never touch
  the other scope" invariants carry over (write only the active scope's fields).
- **Gating (F14):** the control is enabled only when `currentUser?.id` AND `positionIdRef.current` are
  present (otherwise a regen cannot become a persisted version). When signed out or no position row,
  the control is disabled with a clear reason (e.g. "Sign in and generate this resume to save
  reformatted versions"). **This gate is load-bearing** — without it, a signed-out regen would render in
  the preview but silently fail to append a version (the owner's whole requirement), a silent failure.
