## 1. Data model — `public.application_project_pool` (r1 §1 carried forward, two edits)

The DDL, storage lib, and RLS from **r1 §1.2 and §1.5 stand unchanged** except:

### 1.1 Entry shape (M4 — `bullets`, not `body`)

`projects` is a JSON array of 0..N entries. Each entry (final r2 shape, supersedes r1 §1.4):

```
{
  competency:   string      // distinct competency area, e.g. "incident response",
                            //   "curriculum design", "patient triage". STABLE PER-ENTRY
                            //   IDENTITY (entries span DISTINCT competencies, AC-5), logged,
                            //   read by the probe mis-selection discriminator. No separate id.
  domain:       string      // role-domain framing, e.g. "SRE", "K-12 teaching", "ICU nursing".
  title:        string      // short hypothetical project name; <= POOL_TITLE_MAX_WORDS (~10).
  bullets:      string[]    // 2..POOL_BULLETS_MAX (default 3) short bullets, each a discrete
                            //   claim. REPLACES r1's `body` string. Each bullet
                            //   <= POOL_BULLET_MAX_WORDS (~15). Invented figures only.
  hypothetical: true        // provenance marker; ALWAYS true (parser forces it), never absent/false.
}
```

Why an array, not a string (UX A2): a client splitting a narrative string on sentence punctuation breaks on `"$1.2M"` and `"e.g."`. The generator emits `bullets` as JSON array items; the parser rejects an entry whose `bullets` is not an array of 2–3 non-empty strings within the length caps (over-length → **reject server-side**, never truncate — truncating a figure is a worse lie than dropping the entry; UX A3).

New named, owner-tunable constants (surfaced per RETRO-695e23d), all in `lib/copilot/projectExampleGen.js`:
- `POOL_BULLETS_MAX = 3`
- `POOL_BULLET_MAX_WORDS = 15`
- `POOL_TITLE_MAX_WORDS = 10`

**Diff-applicable invariant (M4/AC-3):** `parsePoolResponse`/`parseOnTheSpotResponse` return no entry whose `bullets` is absent, non-array, empty, over-count, or over-length; a reviewer flags any entry construction that assigns `bullets` from a raw string `.split(...)`.

### 1.2 Migration — the `pending` value is now WRITTEN (M5)

The r1 §1.2 DDL is unchanged: PK `application_id`→`applications(id)` cascade, `user_id`→`auth.users(id)` cascade, `projects jsonb not null default '[]'`, `status text not null default 'pending'` **CHECK in `('pending','ready','failed')`**, `error`, `engine`, `created_at`/`updated_at timestamptz not null default now()`, `user_id` index, RLS + four owner policies + grants. Additive-only; never alters `applications`. Idempotent statements. Stamp strictly later than `20260930000000`.

r2 change in **usage**, not shape: the prewarm route now **writes a `pending` row** at generation start (M5 Option B, §2.2), so `'pending'` is an actively-written state, not merely reserved. The CHECK already admits it; **the diff-applicable invariant from r1 §1.2 stands** — the CHECK literal set must contain all three of `'pending'`, `'ready'`, `'failed'`; removing `'pending'` is a blocker (now doubly so, because a `pending` write would violate the CHECK).

### 1.3 Storage lib (r1 §1.5 unchanged) — now also a direct answer-route caller

`lib/supabase/applicationProjectPool.js`: `getProjectPool`, `listProjectPools`, `upsertProjectPool` exactly as r1 §1.5 (caller `supabase`+`userId`, user_id-scoped in addition to RLS, never throw, COLUMN-WISE whitelist upsert on `projects`/`status`/`error`/`engine` + keys). **New in r2:** `getProjectPool` is called **directly by the answer route** (M1, §4.3), not only by the hook and prewarm route. No signature change.

### 1.4 Schema-drift note (r1 §1.3 unchanged)

The FK target `applications.id` as a selectable PK is **CITED, NOT VERIFIED** against a live DB (none reachable here); relied on identically by the in-production `application_digests`. Not a blocker (additive FK to a PK). Instrument the next seat would need: a Supabase connection + `\d public.applications`.

## 2. Prewarm trigger + route (r1 §2 carried forward, one edit for M5)

Trigger decision unchanged from r1 §2: **digest-style lazy prewarm** (`useApplicationProjectPool`), primary mount on the tracking tab, secondary on copilot posting-selection; NOT the tailor-flow hook. Rationale in r1 §2.2–2.3 stands.

### 2.1 Route gate order (r1 §2.4 unchanged)

`app/api/application-project-pool/route.js`: auth → **module-scope `projectPoolLimiter`** (`createRateLimiter({ limit: 12, windowMs: 600_000, prefix: "application-project-pool" })`, built at module scope, keyed on authed user id, denied-still-increments) → body → `applicationId` present+capped → ownership (query-scoped by `user_id`) → **embedded refusal (503)** → failed-read-is-not-a-miss → short-circuit → generate → number guard → ready upsert. No-poison `failed` row on throw, 200. All as r1 §2.4.

### 2.2 M5 Option B — write a timestamped `pending` row at generation start (REVERSES r1 §10)

r1 §10 rejected an explicit `pending` row ("a stuck pending row needs a TTL to recover"). **r2 reverses this**, because M5 requires the server to distinguish WARMING from FAILED on the answer done-frame, and the done-frame is computed server-side on every surface (including `HistoryItem`, which has no client in-flight knowledge). Threading a client in-flight set to the component (Option A) cannot give a past/history entry a correct, frozen warming/failed status; only a server-side signal can. So:

**Prewarm route, revised step sequence after the embedded gate:**
1. short-circuit on an existing `ready`/`failed` row (unless `force`) — unchanged.
2. short-circuit on an existing `pending` row **younger than `POOL_PENDING_MAX_AGE`** (another request is genuinely in flight — do not double-fire).
3. otherwise write `upsertProjectPool({ status: 'pending', error: null })` **before** the model call (column-wise upsert bumps `updated_at`, leaves `projects` untouched).
4. generate → `stripPostingFigures` → `upsertProjectPool({ status: 'ready', projects, engine, error: null })`.
5. on throw → `upsertProjectPool({ status: 'failed', error: message, engine })`, 200 (no-poison).

**Cost gate (`selectAutoProjectPoolTargets`), revised:** returns apps with **no pool row** OR a **`pending` row older than `POOL_PENDING_MAX_AGE`** (crashed mid-generation — stampede-rearm recovery); excludes `ready`, `failed`, and **young `pending`** rows. This is the TTL recovery r1 feared, now accepted as the price of a server-authoritative warming/failed signal. It is bounded and owner-tunable.

New named, owner-tunable constant: `POOL_PENDING_MAX_AGE` (UX references it; proposed default **90_000 ms** — generous for one non-streaming call plus scheduling slack, well under the `maxDuration=120s` ceiling; a flagged guess, routed into the AC-N143-Q probe sitting per the owner-tunable-threshold rule).

**Diff-applicable invariant (M5):** the prewarm route writes `status:'pending'` strictly before the `models.generateContent` call and never leaves a row absent after a throw; a reviewer flags any generate call reachable without a preceding `pending` upsert, and any `selectAutoProjectPoolTargets` arm that excludes stale-pending rows from retry. Instrument: a route test that a `pending` row is written before the (spied) model call; that a stale `pending` row is selected for retry and a young one is not.

Residual ambiguity, stated plainly: a prewarm that fails **before** its first `pending` write (network drop, route 500 ahead of step 3) leaves **no row**. The answer route reads "no row" as **WARMING** (§4.4) — honest, because the lazy hook re-fires on the next tracking-tab load or copilot-open (no-row is a cost-gate target), so a retry is pending by construction. The only way no-row sticks is the hook never re-mounting, which reload/new-session always does.

### 2.3 Hook (r1 §2.5 unchanged)

`app/hooks/useApplicationProjectPool.js`: the `useApplicationDigests` shape — `loadedKeyRef`, `inFlightIdsRef`, `requestProjectPool(applicationId,{force})`, failure-merge, `listProjectPools` first then `selectAutoProjectPoolTargets` through `runWithConcurrency`. (`prewarmingIds` is still exposed — it drives the UX retry/warming cue for the CURRENT surface; it is **not** the warming-vs-failed authority, which is now the server per §2.2/§4.4.)

## 4. Selection seam (B1 — full rewrite of r1 §4)

### 4.1 `selectPoolProject` signature (B1)

Pure function in `lib/copilot/projectExampleSelect.js` (browser-safe; imports only `significantTerms`/`overlapScore` from `projectStories.js`, no Gemini client):

```
selectPoolProject(projects, { question }) -> {
  outcome:  "match" | "no_match",
  entry:    Entry | null,   // the picked entry when outcome === "match", else null
  fitScore: number          // the winning entry's fit score (0 when no entry/pool)
}
```

**The matching signal (B1, owner-ruled):** for each entry, `fitScore = overlapScore(significantTerms(question), `${entry.competency} ${entry.domain}`)` — the overlap of the question's significant terms against the entry's **competency/domain tag** (not the title or bullets). This follows the brief's explicit definition. Rationale: the competency/domain tag is the curated, distinctive signal the generation spreads across the pool; scoring the invented `bullets` prose instead would make almost every entry score `> 0` (domain words recur), so the threshold would never bite and an off-domain pick could never be refused — the exact v1 failure (an ops story for a teaching question). Scoring the tag is where off-domain-ness is detectable.

**Selection:** `entry` = the entry with the strictly-highest `fitScore`; ties keep array order (same stable-sort posture as `selectBestStory`). Deterministic, **zero model calls** (AC-6).

**The fit threshold + no-close-match outcome (B1 / ORCH R3):**
```
POOL_FIT_THRESHOLD = 1   // named, owner-tunable (exported from projectExampleSelect.js).
```
`outcome` is `"no_match"` (and `entry` is `null`) when:
- `projects` is empty/absent, OR
- the best `fitScore < POOL_FIT_THRESHOLD`.

Default `1` means no_match fires only when the best entry shares **zero** distinctive competency/domain terms with the question — the clear off-domain case (teaching tags vs an SRE question), which maps exactly to probe cause (a) "ignores domain". A pick is never forced off-domain (R3). The threshold is a flagged guess, surfaced owner-tunable, retuned via the AC-N143-Q probe.

**Diff-applicable invariant (B1):** `selectPoolProject` returns `outcome:'no_match'` on an empty pool and on a sub-threshold best; a reviewer flags any return path that yields `entry` non-null while `fitScore < POOL_FIT_THRESHOLD`, and any fit computed over `title`/`bullets` rather than `competency`/`domain`. Instrument: a selector unit test — off-domain-only pool → no_match; one on-domain entry above threshold → match with that entry; empty pool → no_match; a two-questions-two-picks check (fresh pick per question).

### 4.2 Never cached (AC-7 as amended)

The pick (`projectExample`, §6) is computed FRESH in the answer route per question, spread onto the done frame only. It is **never** written into `answerContextCache` (the question-independent server cache keyed `userId::applicationId`) nor into the pool row nor any other per-session **server** store. The **client** `answerCacheRef` (keyed by normalized question) **may** carry it — this is explicitly permitted by AC-7 r2 (it matches the existing `anchor`/`selectBestStory` precedent cached at `useDraftAnswer.js:293`): reusing q1's pick for q1-again is correct, because the cache key IS the question. The forbidden thing is a question-**independent** cache of a question-**dependent** value.

**Diff-applicable invariant (AC-7):** `selectPoolProject`'s result never appears as an argument to `answerContextCache.set`/`.get`, never as a field in `fetchRawContext`'s returned object, never in `upsertProjectPool`. It MAY appear in `answerCacheRef.current.set(norm, ...)`. A reviewer flags the former and permits the latter. Instrument: the `route.latency.test.js`-style two-questions-two-picks guard + a static assertion the pick never enters `answerContextCache`.

### 4.3 Pool read placement (M1 — REVERSES r1 §4.3)

r1 added `pool` as the 6th member of `answerContext.js`'s cached `fetchRawContext` fan-out. **r2 reverses this.** The answer route reads the pool **FRESH on every question** as a direct single-row PK lookup:

```
const { pool } = await getProjectPool(supabase, user.id, applicationId);   // cheap PK read, NOT cached
const pick = selectPoolProject(pool?.projects ?? [], { question });        // beside selectBestStory, route.js:529
```

Why reversed: `answerContextCache` is explicitly a **session-duration** cache ("does not change during an interview", module header). But the pool **does** change mid-session — the secondary copilot-posting-selection prewarm warms a cold pool **during** the session. If the pool rode that cache, a first-question cold read (`null`/`pending`) would be frozen for the whole session: Row 1 would show "preparing" forever even after the pool landed. A direct per-question read is a PK lookup on a one-row-per-application table (`application_id` is the PK) — cheap, and correct. The checker is right.

**Blast radius, now ELIMINATED:** by not editing `answerContext.js`, r2 removes the entire r1 §4.3 blast radius (the `route.latency.test.js` positional `call[1].userId` concern, the cached raw-shape key-set, the `loadAnswerContext` return shape). The new read is a standalone `await` in the route handler near `selectBestStory` (route.js:529), where `supabase`, `user.id`, `applicationId`, and `question` are all in scope (verified :400–:529). No existing answerContext test is touched. The plan does NOT need to sweep `answerContext*.test.js` for this feature.

### 4.4 Status derivation on the done-frame (M5)

The route builds `projectExample` server-side from `pool` + `pick` + the clock. Five outcomes:

| Condition (server-observable) | Emitted `projectExample` | UX state |
|---|---|---|
| `!applicationId` OR `wantsEmbedded(engine)` | **field OMITTED entirely** (not sent) | R1-NA (component renders nothing) |
| no pool row; OR `pool.status==='pending'` and `now - updated_at < POOL_PENDING_MAX_AGE` | `{ status: 'pending' }` | R1-W (warming) |
| `pool.status==='failed'`; OR `pool.status==='pending'` and `now - updated_at >= POOL_PENDING_MAX_AGE` (crashed); OR `pool.status==='ready'` with empty/unusable `projects` | `{ status: 'failed' }` | R1-F |
| `pool.status==='ready'` and `pick.outcome==='no_match'` | `{ status: 'no_match' }` | R1-N |
| `pool.status==='ready'` and `pick.outcome==='match'` | `{ status: 'ready', competency, domain, title, bullets, hypothetical:true, engine: pool.engine }` | R1-R |

This is the no-overclaim contract (AC-14 ii): a pending/failed/empty/no_match pool is **never** sent as a ready benchmark. The server is the single authority for warming-vs-failed; the component does no status derivation. The **OMIT** for NA is load-bearing: a missing `projectExample` field is how the component renders nothing (clean NA), distinct from a sent `{status:'failed'}`.

This supersedes the UX R1-W "known in flight" clause with the age-based path the UX doc itself allowed (UX 4.1: "or `pending` is younger than `POOL_PENDING_MAX_AGE`"). The hook's `prewarmingIds` is no longer the warming authority; it may still drive the CURRENT surface's retry affordance.

**Diff-applicable invariant (M5):** the route emits `projectExample` only when `applicationId` is non-empty AND the engine is not embedded; the `body`/`bullets` of a ready entry are emitted only under `pool.status==='ready' && pick.outcome==='match'`. A reviewer flags any done-frame that attaches `projectExample` for an embedded request or a missing applicationId, or that emits ready content for a non-ready pool. Instrument: a route test matrix over the five rows above (engine/applicationId/pool-status/age/outcome → emitted field).

### 5.1 M6 — cache-hit fires a fresh Row 2

Confirmed in source: `useDraftAnswer.js`'s cache-hit branch sets its fields and **`return`s at line 182**, before the done-frame write at ~:293–:302. The r1 Row-2 fire was placed after ~:296, so on a cache hit it would **never fire** → `projectExampleLive` stuck `{status:'pending'}` forever (the M6 hazard).

**Resolution (pick ONE, chosen):** on a cache hit, **fire a fresh `fetchProjectExampleLive`**. Row 2 is, by contract, a live per-question example (never cached); a re-asked question deserves a fresh one, and firing it keeps a cache hit from being a degraded card. Specify:

- Extract the Row-2 fire into one helper, called from **both** paths:
  - the cache-hit branch (right after its `setQuestions`, before `return`), and
  - the done-frame path (after the ~:296 write).
- The helper sets `projectExampleLive: { status: 'pending' }` on the entry, then fires `fetchProjectExampleLive({ applicationId: grounding.applicationId || null, question })` non-blocking; on resolve/reject it sets the entry's `projectExampleLive` under the **same `it.id===id && it.draftToken===token` guard** every post-await write uses (so a superseded draft's Row 2 cannot repaint a moved-on card).
- The cache-hit branch must **never** carry a stale non-final `projectExampleLive` from the cached aids — `projectExampleLive` is NOT part of the cached done-frame payload (it is the separate async field), so there is nothing stale to copy; the helper's fresh `{status:'pending'}` + fire is the only source. (This satisfies UX 6 "a reused card never replays a non-final state".)

If the engine is embedded or there is no applicationId, the helper is a no-op (Row 2 stays absent = R2-NA), matching the server's omission of Row 1.

**Diff-applicable invariant (M6):** every `runDraft` exit that resolves a card (cache-hit `return` and done-frame write) passes through the Row-2 helper (or the no-op gate); a reviewer flags a cache-hit branch that sets a `projectExampleLive` from cached data or leaves it at a non-final value without firing.
