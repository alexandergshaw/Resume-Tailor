## 3. S2 — the shared grounding contract (the disjoint-subagents seam)

### 3.1 `answerGrounding.js` — add `includeCodingSolution` as the fifth grounding field

Read this round: `groundingFor` (`:69-76`), `sameGrounding` (`:82-90`), `cachedAnswerFor` (`:117-125`), `codingFieldsOf` (`:136-143`), `normalizeField` (`:59-61`).

**Change `groundingFor` to accept and emit a fifth field, normalized by its OWN normalizer (not the generic `normalizeField`):**

```
export function groundingFor({ profile, interviewType, applicationId, codeLanguage, includeCodingSolution } = {}) {
  return {
    profile: normalizeField(profile),
    interviewType: normalizeField(interviewType),
    applicationId: normalizeField(applicationId),
    codeLanguage: normalizeField(codeLanguage),
    includeCodingSolution: includeCodingSolution === true,   // strict boolean; undefined/null/anything-else -> false
  };
}
```

**Extend `sameGrounding` with `&& a.includeCodingSolution === b.includeCodingSolution`.**

**Why strict-boolean normalization, not `normalizeField`:** `normalizeField` would fold `undefined -> ""`, making a pre-field entry compare `""` while a current OFF request compares `false` — a needless miss, and a type-mixed comparison. A dedicated `=== true` coercion makes an omitted field and an explicit OFF **both `false`**, so an entry written before this field existed (only reachable in a unit test — the caches are per-session in-memory `useRef` maps, §3.3) HITs an OFF request (same content: no coding), and ON-vs-OFF is always a MISS. This is the FD-3 guarantee, delivered the same way `codeLanguage` already delivers a language flip as a miss.

**`cachedAnswerFor` (`:117-125`) — do NOT change the admission gate.** Line `:122` (`points.length === 0 && !entry.codingSolution && !entry.codingFallback`) becomes **vestigial under additive** (a coding answer now carries non-empty `points`, so `points.length === 0` is false and the special-case never fires), but leaving it is harmless (it returns `null` = miss = the safe direction for a genuinely pointless entry). Per **AC-N162-22**, keep it; re-word its doc comment (`:99-108`) from "a coding answer REPLACES the spoken points, so such an entry is deliberately pointless yet complete" to note that under N162 a coding answer carries points and this clause is a defensive miss on a degenerate entry only. **Removing it is OUT of scope** (the empty-points-renders-blank hazard the comment names is real).

**`codingFieldsOf` (`:136-143`) — unchanged.** It already drops a missing/malformed field and is the OUTPUT extractor both hooks call. Under additive it keeps doing exactly that; `codingSolution`/`codingFallback` now coexist with `points` on the same record rather than replacing them. Its header ("the ONLY keys that should ride a cache entry or a card") stays accurate.

### 6.1 Capture discipline (the load-bearing invariant)

## 7. S6-render — append, don't replace; mount the control

### 7.1 The four render sites (AC-N162-12, FD-2)

Read this round: `CopilotDashboard.js` CurrentAnswerPanel (`:453-461`) + HistoryItem (`:769-773`); `QuestionFeed.js` QuestionCard (`:215-223`); `SampleAnswer.js` (`:243-247`). All four share the shape `done && codingSolution ? <CodeSolution> : done && codingFallback ? <CodingFallbackNote> : done && lines.length ? <AnswerLines + AnswerAids> : null`.

**New shape at every site — render the normal answer whenever there are lines, and APPEND the code section after `AnswerAids`:**

```
done && lines.length ? (
  <>
    <AnswerLines lines={lines} />
    <AnswerAids ...all existing props incl. buzzwords... />
    { codingSolution ? <CodeSolution solution={codingSolution} />
      : codingFallback ? <CodingFallbackNote message={codingFallback} />
      : null }
  </>
) : null
```

- The code block mounts **as a sibling AFTER `AnswerAids`** (which is itself after `AnswerLines`), i.e. after `AnswerAids`'s last group (Example projects). This is the "code after the normal answer" ordering AC-N162-12 requires.
- **Decision — CodeSolution mounts as a sibling of `AnswerAids`, NOT inside it.** Reasons (load-bearing): (a) `AnswerAids` is shared by three surfaces including history `finalOnly` and its contract is already large (`AnswerAids.js:703-712`, eight props) — widening it with a coding prop couples an unrelated concern into a hot shared component; (b) the code section is its own provenance block (Approach/Code/Complexity/Edge cases), structurally like `CodeSolution` already is; (c) a jsdom test can assert "a known spoken-point sentinel AND a known code sentinel both present, code after" against the render site without `AnswerAids` internals. The brief's phrase "mounts in AnswerAids relative to the existing groups" resolves to **immediately after the whole `AnswerAids` block** (after its Example-projects group), since `AnswerAids` owns no code group.
- **FD-2 at render:** `AnswerLines` renders whenever `done && lines.length`, independent of any coding field. Since the route now guarantees `points` for a coding answer, `lines.length > 0` always holds for a coding card, so the normal answer always shows. **R-S6a:** a diff that gates `AnswerLines` behind `!codingSolution` (restoring the replace) fails the no-op control AC §BLAST RADIUS mandates (both sentinels present). A diff where the code section is reachable when `!lines.length` reintroduces a code-only card — reject.

### 7.2 `CodeSolution.js` — drop the trailing aids (AC-N162-14, the no-double-aids decision)

Read this round in full (`:60-128`). `CodeSolution` currently renders `<AnswerAids buzzwords={buzzwords} />` at `:125` and takes a `buzzwords` prop. Under additive the normal answer's own `AnswerAids` already renders the "Words from the posting to work in" group (`AnswerAids.js:822-875`), so a CodeSolution appended after it would show buzzwords **twice**.

**Decision (AC-N162-14 leaves "how" to design): remove the trailing `<AnswerAids buzzwords>` (`:125`) and the `buzzwords` prop/`AnswerAids` import from `CodeSolution`.** CodeSolution becomes a pure code-block presenter (`{solution}` only). Render sites pass only `solution={...}` (drop `buzzwords={...}`). Buzzwords render exactly once, under the normal answer. This is correct because the normal answer is now always present, so there is never a code card without an `AnswerAids` above it to carry buzzwords.

- The inline-`style` `<pre>` (`:83-99` — `style={{ whiteSpace: "pre-wrap", fontFamily: MONOSPACE_STACK }}`) is **untouched** (AC-N162-13 guard). Removing the trailing `AnswerAids` does not touch the `<pre>`. **R-S6b:** a diff that moves `whiteSpace`/`fontFamily` from `style` to `sx` is a reject (jsdom resolves only the element's own style attribute; the memo at `:26-32` and `measurement-instruments` memory).
- Re-word CodeSolution's header prose (`:9-15`, `:34-38` the D1 paragraph) from "IN PLACE OF the spoken answer" / "a coding card keeps … and nothing else from AnswerAids" to additive. The D1 rationale (a worked solution is general knowledge, carries no experience claim) is preserved as the reason CodeSolution renders no aids of its own — but now because the aids belong to the normal answer above it, not because the spoken answer is suppressed.

### 7.3 Status region `answerStatus.js` (AC-N162-15)

Read this round in full. `answerStatusMessage` (`:55-62`) returns `"Code solution ready"` on `hasCodingSolution` and `"Code solution unavailable on this engine"` on `hasCodingFallback`, both to dodge the false "0 points" a replace-era points-less coding answer produced (`:48-54`).

Callers stop passing `hasCodingSolution`/`hasCodingFallback`. The "0 points" hazard the branch existed to avoid cannot occur because `bulletCount` is now the real (non-zero) point count. This is AC-N162-15's "re-stated guard": the existing test (`QuestionFeed.codingSolution :151`, `answerStatus.coding.test.js`) is rewritten to the additive count. **R-S6c:** after the change, no caller passes `hasCodingSolution`; grep `hasCodingSolution` in `app/copilot` should return only the (rewritten) tests, not render code.
