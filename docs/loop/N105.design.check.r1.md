## Part B — structural findings

### M1 (MAJOR, safety) — The gate operates on SPANS; the shipped application-ready document is never shown to be REBUILT from them. A dropped fabrication can survive in `result`/`docxB64`.
§3 step 2: gate returns `{kept, flagged, dropped}` (span-level; §4 contract `{kept:[{id,text}], flagged, dropped}`). §3 response emits `applicationReady: {result, resultLines, docxB64?, …}` (document text/bytes). **The span→document reassembly between them is unspecified.** Nothing in §3/§4/§8 states that `applicationReady.result/resultLines/docxB64` are REBUILT from `kept (+flagged)` with `dropped` provably absent. §8 (AC-12a) feeds the template path from `result`/text. If an implementer sets `applicationReady.result = applicationReadyCandidate.result` (the pre-gate text) and merely surfaces `dropped` in `review`, the fabrication ships in the downloadable .docx while the gate is cosmetic — defeating AC-4 ("dropped … never emitted as a plain truthful bullet") and AC-4 instrument (i) which asserts absence from the OUTPUT. This is the truthfulness-gate seam the brief names: a fabricated claim CAN reach application-ready output through the un-modelled reassembly.
**Fix:** §3/§4 must state that `applicationReady.result/resultLines` (and the bytes built from them in §8) are composed from the gate's `kept`(+`flagged`) spans only, and add a checkable invariant tying gate output to egress text — AC-4 (i) must assert absence from the emitted document bytes, not a span list. Name the decompose/recompose machinery (who splits candidate.result into `candidateSpans`, who re-joins) as an owned module, since both halves are a seam no single file sees.

### M2 (MAJOR) — §7 ("add `hypothetical` to `DOCX_SCOPES`") collides head-on with §5B ("exclude from combine/set-default") and regresses AC-17, because `DOCX_SCOPES` is ONE overloaded list.
`DOCX_SCOPES` is consumed by, verified this check:
- download/copy/filename/spacing per-scope controls (Dialog:735/751/777/791/950/954, FileNameRow:13, SpacingControl:52) — §7 WANTS hypothetical here.
- **combine**: `CombineDocumentsControl.js:55` `DOCX_SCOPES.filter(available).map(loadModel)`, and `canCombine = DOCX_SCOPES.every(available)` (Dialog:558).
- **set-default**: `SetDefaultTemplateControl` mounts iff `DOCX_SCOPES.includes(tab) && available(tab)` (Dialog:877).
- **Drive save**: client `useDriveDocuments.js:756/866/921-926`, server gate `drive/save/route.js:147 if(!DOCX_SCOPES.includes(scope)) badRequest`.

Consequences if `hypothetical ∈ DOCX_SCOPES`:
1. **§5B refusal is FALSE as written.** Combine iterates `DOCX_SCOPES` directly — there is no separate "combine scope set" to exclude it from. The hypothetical would be pulled into the combined .docx (markerless adoption — the exact AC-3 danger). The SetDefaultTemplateControl WOULD mount for the hypothetical tab (gate is satisfied); §5B's "not mounted/disabled" is not what the code does. The only backstop is `saveDefaultTemplate`'s `VALID_KINDS`, and only if the hypothetical scope maps to an INVALID kind — **the design never pins the hypothetical scope→kind mapping**; if it maps to `"resume"`, the store ACCEPTS it and adopts fabricated bytes as the default résumé template.
2. **AC-17 regression (concrete).** `canCombine = DOCX_SCOPES.every(available)`. In an ordinary levels-1-5 resume+cover run (no hypothetical), `every(available)` becomes false → combine is DISABLED where it is enabled today. That is a behavior change to non-N105 runs — exactly what AC-17 forbids.
3. New Drive-save egress for the hypothetical (server route :147 would accept `scope="hypothetical"`). Marker survives via driveDocName forcing (§5A) IF applied, but the design does not acknowledge Drive-batch as a hypothetical surface.

**Fix:** do not overload `DOCX_SCOPES`. Either (a) keep `DOCX_SCOPES` as the download-capable set and introduce narrower `COMBINABLE_SCOPES`/`DEFAULTABLE_SCOPES` (hypothetical joins only download), re-pointing combine, `canCombine`, set-default mount and the Drive route; or (b) give the hypothetical bespoke download wiring and keep it out of `DOCX_SCOPES` entirely. Pin the hypothetical scope→template-kind mapping so the `VALID_KINDS` backstop provably refuses. This is design work the §5B one-liner hides and must land before the plan.

### M3 (MAJOR, safety) — AC-3 single-choke-point is incomplete: a SECOND filename family bypasses `resolveDocumentFileName`.
Egress sweep found `getDownloadFileNameForTitle`/`getDownloadCoverLetterFileNameForTitle` → `buildDocumentFileName` (docx.js:48-62) — a name builder that does NOT pass through `resolveDocumentFileName`, used DIRECTLY at:
- `DocumentPreviewMount.js:561-563` / :569-571 — seeds each scope's default `fileName` (the exact surface the hypothetical scope is added to).
- `TrackingTab.js:292` `new File([blob], getDownloadFileNameForTitle(…))`, `StatusBar.js:409`, passed as props from `page.js:2783/2931`.

§5A places `ensureHypotheticalMarker` only on `resolveDocumentFileName`'s final return + both `driveDocName` branches. It does NOT cover `buildDocumentFileName`/`getDownloadFileNameForTitle`. For the hypothetical, the ONLY line of defense across this family is mint-into-title — the very mechanism §5A itself declares "necessary but NOT sufficient." The forcing-function backstop the design relies on is absent from this family. At the mount the file egress is re-resolved through `resolveDocumentFileName` (so the downloaded FILE is still forced), but (i) the user-visible default name seeded at :563 is markerless unless the title is minted (AC-3b UI-marker gap), and (ii) `TrackingTab:292`/`StatusBar:409` build Files directly with no forcing — unreachable by the hypothetical in slice-1 (session-only, no persistence) but live the moment persistence/tracking lands, and AC-3's "any additional file egress inherits the obligation" applies.
**Fix:** put the marker forcing on `buildDocumentFileName` (the common base of BOTH families), OR prove every hypothetical name flows through `resolveDocumentFileName` and forbid seeding the hypothetical scope's default via `getDownloadFileNameForTitle`. Name `TrackingTab:292`/`StatusBar:409` in §10 blast-radius with an explicit hypothetical-unreachability assertion.

### M4 (MAJOR) — §6 reviewer contract cannot express AC-5's cross-draft consistency; needs a field before the foundational chunk is scoped.
AC-5 requires consistency "across dates/titles/seniority/leadership **including between the two drafts where they reference the same real fact**." The §6 flag shape is `{draftKind, spanId, evidenceSpanId?, …}` where `evidenceSpanId` is "the single posting/real-material span it was checked against." A cross-draft inconsistency's evidence is a span in the OTHER draft — neither posting nor real-material — so the contract has nowhere to attach it. `category:"consistency"` exists but the evidence reference cannot point across drafts. As written the reviewer cannot emit the cross-draft flag AC-5 mandates.
**Fix:** before OD-3's chunk is scoped, extend the contract so a flag can reference a span in the other draft (e.g. `evidenceDraftKind` beside `evidenceSpanId`, or an `evidenceRef:{draftKind,spanId}`). The brief's question — "sufficient or needs a field" — answer: **needs a field.** (Separately, §4 gate's `realMaterial` carries `chronology`; §6 reviewer's `realMaterial` is `{spans}|null` with no chronology — adequate for internal-consistency on the hypothetical, but confirm date-coherence on the application-ready needs no chronology handle. Low.)

### L1 (LOW) — "resumeText always present (route.js:324)" overstates the guard.
:324 requires a resume FILE, not non-empty extracted text. A .docx with no extractable text yields an empty corpus; the gate then drops-everything (fail-closed, safe) and liveness holds vacuously (no contextKey present), so no SAFETY hole — but §4's "always-available primary corpus" should say "derived from the required file; may be empty" and the plan should decide behavior when the corpus is empty (refuse vs. proceed).

### L2 (LOW) — identity param must thread through `resolveActiveDocumentTitle`'s own signature.
§10 lists documentScopes.js:120 as a `resolveDocumentFileName` caller, but `resolveActiveDocumentTitle(fileNameDraft, committedFileName, jobTitle, company, kind)` (copy egress) needs its OWN `isHypothetical` param added and threaded from the Dialog copy control (Dialog:541). Within the named caller set but not called out as a signature change.

### Not worth doing (judged)
- candidate_identity.candidate_name is a server-authoritative source for the NAME field of AC-10. Noting it would not change P13 (it is not employer/date/education) and the résumé-derived corpus already covers the name; a bonus, not a gap. Skip.
- AutoApplyQueueTab:39 / docx.js:512 `link.download` are plain-text / materials-export egresses, not hypothetical-résumé reachable in slice-1. Covered by M3's blast-radius note; no separate finding.
