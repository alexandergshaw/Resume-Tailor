## 2. SCOPE / EGRESS (B1/B7) -- edge cases beyond the shipped fixtures

The shipped `guards.test.js` covers a 3-sentence paragraph at each edge
(first-in-paragraph, last-in-paragraph). I built three fixtures it does not:

- **A 4-sentence paragraph**, fact in position 2: confirmed `beforeText`/
  `afterText` grab only the IMMEDIATE neighbours, and the scoped region does
  not contain a sentence two away from the fact (probe: 1/1 pass, scratchpad).
- **A multi-sentence fact** (the fact's own recorded text contains an internal
  period, e.g. "Acme opened a Dublin lab in 2021. It now employs 200 people."):
  confirmed the internal boundary is never treated as a scope edge --
  `beforeText`/`afterText` are the real neighbour sentences, not a slice
  ending mid-fact -- and a faithful reword of that fact does not spuriously
  trip `checkAddedTokens` (probe: 2/2 pass). This mirrors Wave 1's AC-A11
  atomicity rule; Control B gets it via the same `sentenceBounds` import
  (`smoothTransition.js:31`, `factMove.js`), not a divergent copy.
- Re-verified the shipped negative control (`smoothTransition.confirmPersist.
  rc.test.js:164-183`): the fetch body is asserted to contain the fact + its
  two neighbour sentences and NOT an unrelated paragraph seeded with
  "ninety thousand"/"competing offer" -- ran this test standalone, green.

`checkScope` on the client reconstruction path is effectively a defensive
regression guard rather than a live gate: `buildProposal` (`smoothTransition.
js:154-172`) can only ever touch `lines[span.lineIndex]`, so the shipped
"reconstruction escaped the span" test (`confirmPersist.rc.test.js:226-243`)
cannot currently observe a genuine escape -- it pins a property that holds by
construction today, protecting future refactors rather than catching a live
defect. Not a flaw, just noting what the test actually exercises.

## 3. FAITHFULNESS LAYERS (B3/B5) and THE HONEST LIMIT

Re-ran `smoothTransition.guards.test.js` standalone (13/13 green) including
the pinned "does NOT catch a negation" control (`:179-186`) -- this is a
deliberately green test proving `checkAddedTokens` is blind to meaning, and I
confirmed by reading `checkAddedTokens` (`smoothTransition.js:123-148`) that
it only scans for numeric/currency/date tokens and non-sentence-initial
capitalized words absent from source -- there is no negation/inflection
detection of any kind. The claim in the code comments and the AC (B3b) is
accurate, not aspirational.

**Is the shown diff genuinely complete, not misleading?** Checked
`CoverFactSmoothConfirm.js:17-26`: both the struck-through "before" and the
"after" boxes render `preview.originalText`/`preview.smoothedText` verbatim,
full strings, no `noWrap`, no `textOverflow: ellipsis`, no `maxHeight` +
`overflow: hidden`. `preview.originalText` is the RAW span
(`lines[span.lineIndex].slice(start,end)` -- the actual 3-sentence-or-fewer

`proposal.middle` string that gets spliced into the applied line (traced in
Section 1). So a negation or inflation introduced anywhere in the 3-sentence
span -- not only inside the fact sentence itself -- is visible in the shown
diff verbatim; there is no truncation or re-summarization that could hide it.
This is what makes the confirm gate a real backstop rather than a rubber
stamp for the honest limit in B3b.

## 4. NO LEAK

Traced `recordDecision` (`hello-world/lib/activityLog/appActivityLog.js:180-
196`): it looks up the ledger entry by id and only copies fields present in
`entry.fields` onto the record -- `fact-smooth`'s entry declares
`fields:["reason","code"]` (`activityChannels.js:271-283`) -- so even if
`smoothTransition.js` passed something else, the server-side whitelist drops

discipline (I read every `recordDecision("fact-smooth", ...)` call site in
`smoothTransition.js`: all six pass only `{reason, code}` with canned short
codes -- "embedded", "stale-locator", "provider_error", "scope",

`route.test.js`'s "two codes / no leak" test and `confirmPersist.rc.test.js`'s
equivalent standalone: both green, both assert the raw thrown error string
("network exploded"/"model exploded", which each deliberately embeds the
secret paragraph text) never reaches the client envelope or the decision
fields.

## 5. EMBEDDED ENGINE (B9) -- falsifiable both ways

- **Client gate:** `smoothDisabled={tailorEngine === "embedded"}`
  (`DocumentPreviewMount.js:426`), same `tailorEngine` prop used for the
  produce call's `engine` field (`:352`) -- one source, no race. Mount test
  confirms both directions: disabled on embedded, enabled+false on gemini
  (`coverFactSmoothConfirm.rc.test.js:204-217`, ran standalone, green).
- **Server authority:** `wantsEmbedded(requested, env)`
  (`lib/llm/featureEngine.js:38-56`) honors an explicit `"embedded"` request
  always, and ALSO forces embedded when `env.RESUME_ENGINE === "embedded"`
  regardless of what the client asked for -- so a client that thinks it's on
  gemini but hits a server locked to embedded still gets `unavailable_embedded`
  honestly (`route.js:107-109`), never a silent paid call. Route test confirms
  no `create()` call fires under embedded (`route.test.js:121-129`, green).
- **Gap (minor, not blocking):** the disable reason is communicated ONLY via
  the native HTML `disabled` attribute on the IconButton
  (`InsertedFactsStrip.js:95-103`) -- no `title`, no visible reason text, no
  chip, unlike the `ChatPanel.js:174-183` "Offline · no AI" pattern used
  elsewhere in the app for the identical de-escalation. This matches Control
  A's own precedent for boundary-disabled controls and satisfies the AC's
  literal instrument (jsdom disabled-state assertion only), but is weaker than
  the design doc's own language ("disabled with a visible, honest reason",
  Section 3.4) and than the app's own established idiom elsewhere. Flagged for
  the 8b UX pass, not a ship blocker.

## 10. Gaps found (not safety-blocking; require an owner/orchestrator decision)

1. **AC-B6 (post-apply undo) is UNIMPLEMENTED.** `grep -rin "undo"` across
   `CoverFactSmoothConfirm.js`, `DocumentPreviewMount.js`,
   `smoothTransition.js`, `commitSmoothedFact.js` returns nothing. `N92.ac.
   r1.md` Section 3 states AC-B6 as a settled, unqualified criterion ("After a
   smoothing has been CONFIRMED and applied, the user can undo it with one
   click..."), and the commit message claims "Wave three of three -- the
   fact-positioning controls are complete." The 4b TDD hand-off
   (`N92.tests.w3.r1.md`, "Honest disclosures") explicitly scoped B6 out of
   this wave and flagged it as "gated follow-on work" -- but that scoping
   decision lives only in the test hand-off, not in the AC document itself,
   so the AC and the shipped commit now disagree about completeness. This
   needs an explicit ledger decision: either open a new backlog item for
   AC-B6 or formally amend the AC to defer it. It does not compromise the
   confirm-before-persist safety guarantee (a user can still avoid an unwanted
   smoothing by declining before confirming; they just cannot one-click revert
   one already applied).
2. **AC-B4 (provenance preserved) has no dedicated test**, unit or
   end-to-end, in the shipped suite -- confirmed by grep across all 6 new test
   files for `url`/`title`/`Remove` assertions after a confirmed smoothing
   (none found). I independently verified the actual behavior is correct with
   a scratchpad probe driving the real mount: the source link (`href`
   unchanged) and the Remove control both survive and function correctly
   after a confirmed smoothing. Functionally sound; a coverage gap worth a
   follow-up regression test, not a defect.
3. **Minor, not safety-relevant:** `confirmSmoothTransition` records "acted"
   unconditionally after calling `persist` (`smoothTransition.js:268-273`),
   even if `persist` internally fails (e.g. the PUT gets a stale-revision
   refusal) -- `handleApplySmooth` surfaces the failure via `removeError`
   text but the decision ledger still logs success. And clicking Smooth on a
   second, different fact while one candidate is pending silently replaces
   `pendingSmooth` without logging a decline for the first one. Neither
   allows anything unapproved to persist; both are minor audit-log accuracy
   gaps worth a follow-up, not a blocker.
