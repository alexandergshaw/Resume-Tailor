# N161 — Acceptance criteria (r1)

**Chunk:** N161 (owner request 2026-10-11). The **live** interview copilot AND interview **practice**
must DETECT a coding-challenge / pseudo-code question and REPLACE the main answer with a worked
solution (brief approach + real CODE in the session language + time/space COMPLEXITY + key EDGE
CASES), interview-ready. Non-coding questions are completely unchanged (byte-identical path).

**Seat:** AC (1). Artifact author only — no code written, no gates run. Read-only greps/reads used to
ground against the real pipeline at HEAD.

**Settled owner decisions (encoded below, NOT re-opened):** answer content = full worked solution
(approach + code + complexity + edge cases); placement = REPLACE the main answer for a detected coding
question (consistent with N134/N140 "answer the question asked"); language = existing session
`codeLanguage`, else PSEUDOCODE when the question explicitly asks for pseudocode OR no `codeLanguage`
is set; scope = live copilot + practice, both surfaces.

## Detection locus (pinned) and the shape of the fix

Three facts decide where detection must live:

1. The answer's SHAPE is decided by the PROMPT (Gemini) and by the embedded drafters (no-LLM) — N134
   and N140 both landed as prompt/shape changes. So detection must reach the prompt builders AND the
   embedded drafters.
2. "Non-coding byte-identical" + the frozen oracles mean the coding branch must be **gated and
   re-derived from `question`** exactly like `roleTerms(question).length > 0` already is — so a
   non-coding question takes no new branch and the frozen `toBe` holds unchanged.
3. The CODE must survive rendering verbatim (newlines + indentation) and render monospaced — which the
   `points`→`deriveAnswerFromPoints`→`answerLines`→`AnswerLines` prose path destroys today. So the code
   must travel as a **structured field on the response**, not as prose `points`, and render through a
   new whitespace-preserving primitive.

**Recommended structure (design/1b owns the final contract; AC constrains behaviour):** a single pure
`detectCodingChallenge(question)` module under `lib/copilot/` (sibling of `questionType.js` /
`questionVocabulary.js`), re-derived inside `buildPointsPrompt`/`buildAnswerPrompt` (no new builder
arg, mirroring `roleTerms`), reachable by the embedded drafters, and reachable by the client render
gate. It must be NARROWER than `classifyQuestionType`'s `technical` (D2). The worked solution rides a
new structured response field (e.g. `codingSolution: { approach, language, code, complexity, edgeCases }`)
on the terminal frame only (D4). These are recommendations; the criteria below bind behaviour.

---

## Failure direction (binding)

Two directions, both named by the owner as the primary defect, encoded as a positive + negative corpus:

- **False positive (worse of the two for the shipped answer):** giving a CODE solution to a
  behavioral or a conceptual-technical question corrupts the answer the candidate reads aloud (a worked
  solution where a STAR story or a spoken explanation was wanted). Every criterion is written so the
  passing direction is "a non-coding question gets the UNCHANGED answer shape," and a mutation that
  broadens detection to fire on the negative corpus turns a test red.
- **False negative:** a real coding/pseudocode challenge gets the old spoken-points shape instead of a
  worked solution. The positive-corpus criterion fails red if detection under-fires.

## Acceptance criteria

Unless noted, the detector/prompt/honesty criteria are **jsdom/unit-decidable** against pure modules;
render criteria use the existing copilot jsdom harness (real component mounted, computed style read,
as `CitationDetail.test.js:262` already reads `style.whiteSpace`). "Both surfaces" = live (via
`useDraftAnswer`/`AnswerLines` render sites) and practice (`useSampleAnswer`/`SampleAnswer`).

### AC-1 — Deterministic detection, both directions, on a FIXED held-out corpus. **[CORE]**
A pure `detectCodingChallenge(question)` (name is design's call) returns **true** for every item of a
positive corpus and **false** for every item of a negative corpus. Minimum corpus the TDD seat must
encode (extend, never shrink):
- **Positive (MUST detect):** "Write a function to reverse a linked list." / "Implement binary search."
  / "Given an array of integers, return the two indices that sum to the target." / "Code a function
  that checks if a string is a palindrome." / "Give pseudocode for a breadth-first search." / "FizzBuzz
  from 1 to 100." / "Write a SQL query that returns the top 3 earners per department."
- **Negative (MUST NOT detect):** "Tell me about a time you failed." / "Describe a conflict with a
  coworker." (behavioral) AND "Explain the CAP theorem." / "What is a hash map and when would you use
  one?" / "Walk me through how HTTPS works." / "How do you approach code review?" / "Why do you want
  this role?" (conceptual-technical + general — each contains a `TECHNICAL_RE` token yet asks for a
  spoken explanation, not code).
- **RED on HEAD:** yes — no such module exists (grep: no `detectCodingChallenge`/coding detector). The
  test cannot even import it. Report as INVALID-until-built, not pass.
- **Failure direction / mutation:** a mutation that aliases the detector to `classifyQuestionType(q)
  === "technical"` must turn this red on the conceptual-technical negatives ("hash map", "CAP
  theorem"). A mutation that returns a constant false must turn it red on the positives.

### AC-2 — Non-coding prompt is BYTE-IDENTICAL; the coding branch is gated and re-derived from `question`. **[CORE / regression guard + RED]**
`buildPointsPrompt` and `buildAnswerPrompt`, called for a non-coding question with no résumé / cover
letter / pages block, produce output **equal to `FROZEN_POINTS_PROMPT_NO_PAGES` /
`FROZEN_ANSWER_PROMPT_NO_PAGES`** (`answerPrompts.test.js:86-112`), unchanged. The coding shape lines
appear **only** when `detectCodingChallenge(question)` is true, and the builders take **no new
positional argument** (re-derive from `question`, as `roleTerms` does) so arity assertions and every
by-name builder call are unmoved.
- **RED on HEAD:** no for the frozen oracles themselves (they pass today — this is the regression
  guard that the coding work does not perturb them). The gating mechanism is RED-equivalent in that a
  naive implementation (an unconditional coding instruction) fails the frozen `toBe`, which is exactly
  what this criterion forbids.
- **Trap to encode (blast radius B1):** the JSON shape line in both frozen oracles includes the enum
  `"type": "behavioral" | "technical" | "general"`. The coding signal must therefore **not widen that
  enum in the non-coding shape line** (do not emit `"coding"` there), or every non-coding oracle
  breaks. A detected coding question may carry its own shape line.

### AC-3 — A detected coding question produces a worked-solution SHAPE with all four parts present. **[CORE / RED]**
For a detected coding question, the assembled prompt (Gemini) instructs, and the response contract
carries, a solution with **four parts structurally present**: (a) a brief **approach**, (b) real
**code** (or pseudocode per AC-5) in the session language, (c) time/space **complexity**, (d) key
**edge cases**. Pinned two ways, mirroring N134/N140's reconciliation:
- a **NEW frozen prompt oracle** (full-string `toBe`) for a representative detected coding question,
  so the coding prompt is pinned, not merely asserted by `contains`; and
- the response normaliser yields the structured solution fields for a model payload that supplies them,
  and degrades to a safe non-coding answer (not a half-built object) when it does not.
- **RED on HEAD:** yes — no coding branch exists in either builder (grep: `codeLanguageLines` is the
  only code-related prompt block and it is a language-choice block, not a worked-solution shape).
- **Failure direction / mutation:** dropping any one of the four parts from the shape instruction, or
  from the required response shape, must turn this red.

### AC-4 — The CODE renders in a code block: monospace + preserved whitespace, on BOTH surfaces. **[CORE / RED — rendering]**
A coding solution's code string containing newlines and leading indentation (e.g. a two-line
function with a 2-space-indented body) renders so that the newlines and indentation **survive to the
DOM** (`white-space: pre`/`pre-wrap`) and in a **monospace** font, in both the live render path
(`AnswerLines` / its new code sub-render) and practice (`SampleAnswer`). The code is NOT passed through
`deriveAnswerFromPoints` (which joins with a single space, `answerLocal.js:510`) nor rendered as a
plain `variant="body2"` `<li>` (which collapses whitespace, `AnswerLines.js:217`).
- **RED on HEAD:** yes — no render path preserves whitespace or sets monospace for an answer; a jsdom
  test asserting `getComputedStyle(codeEl).whiteSpace` is `pre`/`pre-wrap` and a monospace
  `fontFamily` finds no such element and fails. (Instrument proven: `CitationDetail.test.js:262` reads
  `style.whiteSpace` in this suite.)
- **Failure direction / mutation:** a mutation that routes the code through `answerLines`/plain
  `<Typography>` (whitespace collapsed) must turn this red. Geometry (≥44px targets, horizontal scroll
  on a phone) is OUT of jsdom — owner/phone-pane (see OUT-of-scope).

### AC-5 — Language selection: session `codeLanguage` wins; pseudocode when asked or when unset. **[CORE / RED]**
For a detected coding question, the solution's language is chosen in the owner's order: (1) a language
the **question itself names** (incl. an explicit request for **pseudocode** → pseudocode); else (2) the
session's `codeLanguage` override when the user set one (label via `codeLanguageLabel`, never the
stored slug — `codeLanguages.js:106`); else (3) the posting-resolved language when present; else (4)
**pseudocode**. This must hold **regardless of `descriptor.codeBearing`** (see D5): a coding question
under a `general` session must still get a language, not the empty `codeLanguageLines([])` of today.
- **RED on HEAD:** yes — `codeLanguageLines` returns `[]` for a non-`codeBearing` descriptor
  (`answerPrompts.js:200`), so a coding question asked in a `general` session emits no language
  guidance at all; and there is no worked-solution branch to attach a language to.
- **Failure direction / mutation:** a mutation that emits the stored slug (`"csharp"`) instead of the
  label, or that defaults to a real language instead of pseudocode when nothing is set, must turn this
  red. A mutation re-gating language on `descriptor.codeBearing` must turn the general-session case red.

### AC-6 — Non-coding answers are completely unchanged (response + render), both engines, both surfaces. **[CORE regression guard]**
For a non-coding question: the answer-route response shape is **key-for-key** what it is today on all
five branches (streaming Gemini, non-streaming Gemini answer, embedded answer, non-streaming Gemini
points, embedded points), no coding field present; and the render is the existing `answerLines`/
`AnswerLines` prose. The new coding field is **absent** (not `null`, not `[]`) when the question is not
a coding challenge — mirroring how `factSources` is omitted entirely when no employer is known
(`route.js:907`) so the existing exact-key-set assertions
(`route.test.js`, `roleTermsFlag.js` header lines 5-9) stay unmoved.
- **RED on HEAD:** no — regression guard (true today). Teeth on the mutant: any change that adds a
  coding key to a non-coding response, or alters non-coding `points`/`type`/`cues`, must fail it.

### AC-7 — The honesty/output transforms do NOT mangle or drop the code. **[CORE / structural]**
The code string reaches the render **verbatim** — it is NOT run through `sanitizeTechTermDetail` /
`isFirstPersonClaim` (`techTermDetailHonesty.js`), nor through `deriveAnswerFromPoints`, nor through
`answerLines`' STAR-label / sentence machinery. Specifically: a code block whose comment contains `I`
(e.g. `// I use two pointers here`) or an imperative line (e.g. `return left + right;`) must appear in
full, unchanged, in the rendered solution. Separately, the recruiter-vocab flags
(`roleTermsUnbacked`/`roleTermsClaimed`) must **not** cause the code or the solution to be suppressed,
stripped, or badged as a fabrication (a worked solution is general knowledge, not a first-person claim
about the candidate — `techTermDetailHonesty.js:5-18` states exactly this inversion for the sibling
feature).
- **RED on HEAD:** yes — today a code-shaped string delivered as `points` is joined/space-collapsed by
  `deriveAnswerFromPoints` and rendered as collapsed prose; a test feeding a two-line code string with
  an `I`-comment through the answer path and asserting byte-equality of the code fails.
- **Failure direction:** the dangerous direction is **dropping/altering** a line of correct code. The
  safe direction is leaving it untouched. A mutation that filters the code through any first-person /
  sentence-splitting transform must turn this red.

### AC-8 — The coding solution rides request→response→state→cache in BOTH client hooks. **[CORE / RED — wiring]**
The new coding field is carried through the full client round-trip on both paths so a cached/queued
reveal is not served stale:
- live `useDraftAnswer`: destructured from the response (alongside `points`/`type`/…,
  `useDraftAnswer.js:430`), written to the card, and written into `answerCacheRef` (line 503);
- practice `useSampleAnswer`: destructured on both `request` (line 258) and `queue` (line 424), written
  to `state`, written to `cacheRef` (lines 306, 430), and included in the `cachedSampleAnswerFor` /
  `needsRedraft` comparison so a reveal after a language change redrafts rather than replaying a
  wrong-language solution.
- **RED on HEAD:** yes — neither hook destructures or caches any coding field (grep of the two files).
- **Failure direction / mutation:** a mutation that drops the field from either cache write (so a
  reveal→hide→reveal loses the solution, the exact class `pageSources` was added to the cache to fix)
  must turn this red.

### AC-9 — Live AND practice both reach the coding path (scope). **[CORE]**
Both surfaces produce a worked solution for a detected coding question: live via the answer route's
points/streaming mode as reached by `useDraftAnswer`, and practice via `mode:"answer"` as reached by
`useSampleAnswer`. Neither surface is left on the old spoken-points shape for a detected coding
question.
- **RED on HEAD:** yes — no coding path exists on either surface.

## Decisions needed (recommended defaults — owner/design to confirm, do not invent past these)

- **D1 — Aids beside a coding answer.** Recommend: for a detected coding answer, **suppress the
  experience-oriented aids** — `resumeAnchor`, `projectExample`/`projectExampleLive`, per-point
  `pageSources` citations, and the per-bullet "More detail" expansion — because a worked solution is
  general knowledge, not drawn from the candidate's résumé/pages, and attributing it to "your Payments
  migration page" would be a false provenance claim (the exact class `SampleAnswer.js:44-54` and
  `answerAids.js:139-150` warn about). `buzzwords`/`techTerms` MAY remain (they are posting vocabulary,
  not a provenance claim). Owner to confirm.
- **D2 — Detector contract.** Recommend a NEW `detectCodingChallenge(question)` that is **narrower than
  `classifyQuestionType`'s `technical`** and does **not** widen the detect route's 3-value `type`
  contract (`detect/route.js:19`) nor `VALID_TYPES` in the answer route. Whether to also show a
  "coding" chip in live detection UI is a separate, deferrable UX call.
- **D3 — Response field for the coding signal.** Recommend a **separate** structured field (e.g.
  `codingSolution`) rather than a new `type: "coding"` value, so the shared JSON shape line's `type`
  enum stays byte-identical for non-coding (AC-2 / B1). Owner/design to confirm.
- **D4 — Streaming.** The structured solution fields ride the **terminal `done` frame only** (like
  `pageSources`/`factSources`), never the incremental `points` frames (`answerStream.js`'s
  `pointsFromPartialJson` anchors on the `points` array). Recommend the loading UI shows a
  "drafting solution" state rather than streaming half-parsed code. Design owns the loading UX.
- **D5 — Language under a non-codeBearing session.** Because `codeLanguageLines` returns `[]` for
  `general`/`phone-screen`/behavioral/etc. (`answerPrompts.js:200`, registry `interviewTypes.js`), the
  coding branch must source its language **independently of `descriptor.codeBearing`** (AC-5).
  Recommend reusing the existing precedence and `codeLanguage` object but gating on
  `detectCodingChallenge`, not on `codeBearing`. Owner/design to confirm reuse vs a dedicated helper.
- **D6 — Embedded (no-LLM) engine.** The embedded drafters (`draftAnswerLocal`/`draftSampleAnswerLocal`)
  cannot write a correct arbitrary algorithm deterministically. Recommend: for a detected coding
  question on the embedded engine, return an **honest fallback** (a labelled "switch to the AI engine
  for a worked solution" message or a generic approach-only skeleton), never a fabricated/incorrect
  code block. Owner to confirm the exact fallback copy; AC-10 pins only that it does not fabricate.

### AC-10 — Embedded engine does not fabricate code. **[CORE / RED-equivalent, honesty direction]**
On the embedded engine, a detected coding question yields EITHER an honest fallback (no code block) OR
code only where the engine can produce it deterministically — never an invented algorithm presented as
a working solution. The safe failure direction is "no solution / honest fallback"; the dangerous one is
"confident wrong code."
- **RED on HEAD:** vacuous today (no coding path), stated as a scope/honesty fence so the design seat
  does not have the embedded engine fabricate.

## Explicitly OUT of scope

- **Whether the model's CODE is correct / idiomatic / optimal.** Runtime, Gemini-dependent — owner/
  Gemini-env, not a jsdom AC. The AC pins that the four parts are present and render intact, not that
  the algorithm is right.
- **The detector's real-world RECALL on live machine-transcribed questions.** The fixed corpus (AC-1)
  bounds behaviour; recall against the long tail of spoken phrasings is an owner/runtime observation.
- **Touch-target geometry and horizontal-scroll of the code block on a phone.** jsdom has no layout
  (`getBoundingClientRect` is zeroes). A monospace pre-wrap block at 320px is a browser-pane/owner
  check (`copilot-mobile` harness).
- **A new interview-type.** N161 detects a coding QUESTION; it does not add an interview type or change
  `interviewTypes.js`.
- **Audio synthesis of a code answer** (`answer` prose field) — out; a worked solution is read, not
  spoken verbatim.
- **Changing `classifyQuestionType` / the detect route's 3-value contract** (D2) — out.
