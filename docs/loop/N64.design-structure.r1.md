## 1. The one decision that is expensive to reverse: WHERE provenance lives

This is the load-bearing boundary. AC-5 requires that for a **past application** the user can see the
template's name, and AC-4 requires that editing/deleting a template never alters a past output. There
are two structurally different homes for the `template_id` link, and they differ in blast radius on the
one path the AC's literal instrument does not mention: **fact acceptance**.

### The hazard the AC's "no RPC signature churn" line misses (F7)
`accept_application_facts` (the researched-facts insertion path) **inserts a NEW
`generated_cover_letters` row and repoints `applications.cover_letter_id` to it**
(`20260928000000…:104-109`). So if `template_id` is a column **on `generated_cover_letters`**, then the
moment a user accepts a fact on a cover letter they generated with template T, a fresh version row is
created with `template_id = NULL`, the application pointer moves to it, and **the template name silently
disappears from the past-application surface** — a complete instance of this repo's recurring
"mechanism present, user-facing hop gone, suite still green" defect class (nine prior instances, per the
brief). A test that generates-with-template and asserts the first row's column would pass while the
reachable surface, after any fact acceptance, shows nothing. The AC's §4 assertion "No RPC signature
churn: provenance is a plain column write" is **only true for the resume**; for the cover letter it is
false unless something carries provenance across the version bump.

### Two architectures

**Arch A — provenance on the generated rows (the AC's literal §4).**
`template_id` (+ label) on `generated_resumes` AND `generated_cover_letters`.
- Resume: clean — one column, written by `saveGeneratedResume` (no RPC).
- Cover: requires re-issuing `accept_application_facts` a THIRD time (after N59's `20260928000000`) so it
  copies `template_id`/label forward from the superseded version into the new one. This can be done as a
  **body-only** `create or replace` with the **identical 8-arg signature** (no `drop`, no overload
  window — strictly safer than N59's signature change), but it means copying the whole function body
  verbatim from `20260928000000` into a new migration and adding: two `declare`s, one `select … into`
  of the current `cover_letter_id` row's `template_id`/label, and two columns in the `insert`. Real,
  delicate, and it re-touches the most sensitive function in the repo.

**Arch B — provenance on the `applications` row (RECOMMENDED).**
`resume_template_id` + `cover_template_id` (+ label snapshots) on `public.applications`, written by the
same `persistGeneratedDocuments` update that already sets `resume_used_id`/`cover_letter_id` (F15).
- The accept RPC repoints `cover_letter_id` but **never touches `cover_template_id`**, so provenance
  **survives fact acceptance with ZERO change to the RPC.** The provenance-loss bug is made
  *structurally impossible*, not merely absent — the RPC cannot null a column it does not name.
- ONE table altered instead of two; NO function re-issue.
- Grain: application-level "which template did this application use" (last-generation-wins). This matches
  exactly the question AC-5 asks ("which template a past application used") and matches what any surface
  can actually reach today — there is no per-generation template display anywhere, and re-tailoring
  already moves both the document pointer and (here) the template pointer together, so they stay
  consistent. Per-version provenance, if a future version-history UI ever wants it, is a clean additive
  column on the generated rows later (§8) — Arch B does not foreclose it.

**Ruling: Arch B.** It satisfies the brief's "prefer a structure where the wrong thing is IMPOSSIBLE"
directive on the exact path that is otherwise a nine-th missing-hop, and it avoids a third re-issue of
`accept_application_facts`. The cost is one deviation from the AC's literal instrument wording, filed as
**BL-2** below for the orchestrator to reconcile (it is a wording change, not a weakening: AC-5(a)
"a generated row carries the selected `template_id`" becomes "the application row carries the selected
`template_id`(s)"; AC-4's FK assertion generalises to "no FK cascades a template delete onto an
application or generated row", which Arch B satisfies via `on delete set null` on the two application
columns). The rest of this document specifies Arch B; §7.4 gives the Arch-A migration delta as the
fallback the orchestrator can select instead.

## 2. Decision: the CRUD surface does NOT reuse `makeCrudHandlers`

The AC §1.4 says "the saved-templates route should use `makeCrudHandlers`, not a bespoke handler." I
read `crudRoute.js` and `apiSupport.js` in full and this reuse is **wrong**, for three checkable
reasons (F3):
1. Every mutation calls `ensureSeeded(supabase, userId)` → `seedUserLibrary(...)`, seeding the tailoring
   **library** (`tailor_profile`) — irrelevant to templates and a surprising side effect.
2. Every mutation calls `bumpVersion(...)` → bumps `tailor_profile.library_version` and
   `invalidateLibraryInProcess(userId)` — cache-busting for a subsystem templates are not part of.
3. The `POST` insert hardcodes `sort_order: Math.floor(Date.now()/1000)` and does a pure-JSON row
   insert with **no storage upload**. Templates are docx bytes; the save is inherently a
   storage-upload-plus-row operation `makeCrudHandlers` cannot express.

**Ruling:** the templates route mirrors the `saved_searches` idiom (F4) — `getUser()`→401→
`.eq("user_id", user.id)` on every read/write, plus its per-account count-cap pattern — and adds
explicit storage handling. This is reuse of the *right* precedent. `makeCrudHandlers` stays untouched.

public.resume_templates      -- generic across kinds; "resume" in the name is the bucket/legacy sense
  id           uuid  primary key default gen_random_uuid()

route on rename/replace, mirroring `crudRoute.js:46` — there is no `updated_at` trigger in the persona

## 4. Contracts (full signatures)

### 4.1 `lib/document/templateStore.js`

```js
// All functions take the AUTHED supabase client; RLS + explicit .eq("user_id") both enforce ownership.
// Bucket is always "resumes". No throws on the storage half that would strand a row (see saveTemplate).

/** Upload bytes THEN insert the row, so a row never exists without bytes.
 *  Server-generates id, uploads to `${userId}/templates/${id}.docx`, and only on upload success inserts
 *  { id, user_id, name, kind, storage_path }. On insert failure, deletes the uploaded object (best-effort).
 *  @param supabase, {userId:string, name:string, kind:'resume'|'cover', bytes:Uint8Array|ArrayBuffer, fileName:string}
 *  @returns {Promise<{ row: {id,name,kind,storage_path,created_at} } | { error: string }>}
 *  Rejects (error, no write) when fileName is not .docx (isDocxResume, F13) or name is empty/duplicate. */
export async function saveTemplate(supabase, { userId, name, kind, bytes, fileName }) {}

/** @returns {Promise<{ rows: Array<{id,name,kind,storage_path,created_at,updated_at}> }>} own rows only. */
export async function listTemplates(supabase, { userId, kind /* optional filter */ }) {}

/** Row-only update of name (+ updated_at). id AND user_id gated. Dup-name → { error }. Bytes/path unchanged. */
export async function renameTemplate(supabase, { userId, id, name }) {}

/** Overwrites the SAME storage object (upsert:true) at the row's storage_path; row id/name/path unchanged.
 *  This is AC-1 "replace bytes never destroys another template": it targets one id's object only. */
export async function replaceTemplateBytes(supabase, { userId, id, bytes, fileName }) {}

/** Deletes the row (id+user_id gated) then best-effort removes the storage object.
 *  The row delete is what fires `on delete set null` on applications.{resume,cover}_template_id (AC-4). */
export async function deleteTemplate(supabase, { userId, id }) {}

/** Downloads the template's docx bytes for use as templateDocxB64 at generation (F12).
 *  @returns {Promise<{ bytes: Uint8Array } | { error: string }>} */
export async function getTemplateBytes(supabase, { userId, id }) {}
```

Load-bearing ordering in `saveTemplate`: **upload-before-insert** with a client-known id. Rationale: the
storage object *is* the template, so a row without bytes is useless; making `storage_path NOT NULL` and
inserting only after a successful upload makes "usable-row-without-bytes" impossible. The residual
failure mode (object uploaded, insert fails → orphaned bytes) is invisible to the user and sweepable,
strictly less harmful than a listed-but-broken template.

### 4.2 `app/api/templates/route.js` (idiom = `saved_searches`, §2/F4)

## 6. Rulings on the brief's explicit questions

### 6.1 A template is mutable in place — and provenance is still honest (edit handling)
Templates ARE editable in place: rename (row) and replace-bytes (same storage object). This does not make
provenance a lie because a past output is **frozen bytes** captured at generation (F12,
`generated_*.docx_path`) and application provenance stores a **name-snapshot label** (§6.7). So: editing
a template's bytes changes only future generations; a rename is reflected live for the still-existing
template (correct — it is the same template) and never affects a past output's downloadable file (AC-4).

### 6.2 Deleting a template never breaks a past application (AC-4 mechanism)
FK `applications.{resume,cover}_template_id → resume_templates(id) ON DELETE SET NULL`. Deleting a
template nulls the pointer; the frozen output bytes and the snapshot label are untouched, so download and
provenance-display both survive. There is no path from template delete to a generated/application-output
row delete or re-render (no cascade; outputs are not re-derived from the live template).

### 6.3 The legacy slot is NOT migrated away (AC-8 compatibility)
No backfill that seeds template rows from the legacy `${userId}/resume` slot, and the legacy upload in
`ApplyingControls.js:84-119` stays. A zero-template user's cron/manual/interactive generation is
byte-for-byte today's path. "Seed one row from the legacy slot" (an AC-8 option) is explicitly **not**
chosen — it would create a template row with ambiguous provenance and risk the readers in Seam 3. The
legacy slot remains the implicit default; a template is an *additional* named object.

### 6.4 Last-used default store — RULING: a per-user `localStorage` key, NOT a DB column
`localStorage["n64.lastTemplate.<kind>"] = templateId`, read when the picker mounts to preselect (AC-3
default = last-used, zero extra clicks). Rationale: it is a per-device UI convenience, not data that must
be shared or auditable; a DB column would add write traffic on every generation for a preference. Stated
cost (also flagged by AC §10): it does **not** survive a device change — on a new device the default
falls back to "most recently created template" (derivable from `created_at`, no storage) or the legacy
slot if none. If the owner wants cross-device last-used, it becomes a single nullable column
`tailor_profile.last_resume_template_id`/`last_cover_template_id` later — additive, not a blocker. I
decide `localStorage` for this chunk (reversible).

### 6.5 Storage growth — no retention policy; optional soft cap named as a question
Templates are user-managed INPUTS (a handful per user, small .docx), removed only by explicit delete
(AC §5). **No retention/cleanup policy this chunk.** A soft per-user cap to bound abuse is *optional* and
I do not require it, but if the owner wants one it is a one-line reuse of the `saved_searches`
count-then-409 pattern (F4). **Owner question (not my call):** cap templates per user (e.g. 25 per kind),
yes/no? Default if unanswered: no cap. This does not block the chunk.

### 6.6 minimize-clicks (AC-3 / [[minimize-clicks]])
Pick at generation is one control preselected to last-used (§6.4) — common case adds zero clicks. Save is
inline at the point the user already uploads a docx ("Save this as a template", default name = filename
sans extension) — one action, no wizard. Rename and pick take no confirmation; **delete confirms** (the
one irreversible action). Controls stay keyboard-reachable. 1c/1e owns the exact component; this is the
structural constraint it must satisfy.

### 6.7 What the user sees for a deleted template — honest, not blank (AC-5)
Provenance stores BOTH the FK id (live link, rename-safe) AND a `*_template_label` **name snapshot** taken
at generation. Display precedence is §4.4. The snapshot is the honesty mechanism: without it, a deleted
template (FK nulled) would leave only a generic "(no template)" and the user could never learn what was
used. With it, they see `"Finance Resume (no longer saved)"`. This closes the recurring missing-hop class
for the delete case specifically.

### 6.8 AC-7 holds — no new decision-ledger entry, and why
Template CRUD is user-driven and its result is captured structurally by the provenance columns (§4.3);
it is not an app *decision* the user needs a downloadable trace of. This chunk adds **no**
`recordDecision(...)` and no `DECISION_LEDGER` entry, so `decisionCoverage.sweep.test.js` (which binds
the ledger ↔ call sites both ways) stays green with no change. The deferred matcher (half B) is where a
`template-auto-select` entry would later belong (§8) — not here.
