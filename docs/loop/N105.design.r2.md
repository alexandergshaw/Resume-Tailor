## 1. M1 (safety) — gate → emitted-document reassembly is now specified and owned

**The defect (check M1).** r1 §3/§4 had the truthfulness gate emit span-level `{kept, flagged, dropped}`, but never stated that the shipped `applicationReady.result/resultLines/docxB64` are REBUILT from those spans. An implementer could set `applicationReady.result = applicationReadyCandidate.result` (pre-gate text) and merely list `dropped` in `review` — the fabrication then ships in the downloadable `.docx` while the gate is cosmetic. AC-4's instrument asserted absence from a span list, not from the emitted bytes.

**Decision — a named decompose→gate→recompose seam, owned by one module.** The split and the re-join are a seam no single file sees, so they get their own PURE module, server + node-testable:

**New module `lib/llm/ideal/spanDocument.js` (PURE).** Two functions:
```
decomposeToSpans(result, resultLines, { contextKeyOf }) =>
  { spans: [{ id, text, section, contextKey, order }], layout }
  // id: app-MINTED, stable within this decompose call (span discipline).
  // order + layout: everything recompose needs to rebuild the document in
  //                 original reading order from a SUBSET of spans.

recomposeFromSpans(layout, retained) =>
  { result, resultLines }
  // retained = kept spans (emitted VERBATIM) ++ flagged spans (emitted but
  //            carrying their flag, per AC-4 policy). DROPPED spans are NOT
  //            in `retained`, so they are ABSENT from result/resultLines by
  //            CONSTRUCTION — recompose can only emit spans it is handed.
```

**Data flow (orchestrator `lib/llm/ideal/idealPipeline.js`, revised §3 step 2):**
1. `engine.tailorIdeal(args)` → `{postingAnalysis, keywordMap, hypothetical, applicationReadyCandidate}`.
2. `{spans, layout} = decomposeToSpans(applicationReadyCandidate.result, applicationReadyCandidate.resultLines, {contextKeyOf})`.
3. `{kept, flagged, dropped} = applicationReadyGate({ candidateSpans: spans, realMaterial })` (§5).
4. `{result, resultLines} = recomposeFromSpans(layout, [...kept, ...flagged])`.
5. **The emitted `applicationReady` carries these RECOMPOSED `result`/`resultLines`** — never `applicationReadyCandidate.*`. The `docxB64`/template bytes in §8 are built FROM these recomposed lines through `resolveDocumentBlobBytes`. **A dropped fabrication is therefore absent from the emitted BYTES, not merely annotated.**

**Why "impossible" not "absent" (standing rule 2).** `recomposeFromSpans` is a pure function of the spans handed to it; it has no reference to `applicationReadyCandidate`, so it cannot re-introduce a dropped span. The only way a dropped fabrication reaches the output is for the orchestrator to bypass recompose entirely — which the AC-4 mutant control below turns red.

**Flagged-span RENDERING is a plan/1c input, NOT a structure question.** AC-4 allows a borderline claim to be "surfaced under an explicit `unverified — confirm before use` flag" instead of dropped. WHERE that flag appears (inline text marker in the body vs. a sibling panel reading `review.flags[].spanId`) is a 1c/plan decision. Structure fixes only: flagged spans are in `retained` (so they are emitted and distinguishable by spanId), dropped spans are not. This marker is unrelated to OD-4 (which removes only the HYPOTHETICAL content label; the AC-4 unverified-claim flag is a separate, required affordance).

**Checkable invariant (AC-4, tightened to emitted bytes):**
- The fabrication fixture (AC-4 row i) asserts the dropped claim's text is **ABSENT from `applicationReady.result`, from `applicationReady.resultLines`, and from the text extracted from `applicationReady`'s template bytes** — not merely listed in `review.dropped`.
- **Mutant control:** an implementation that sets `applicationReady.result = applicationReadyCandidate.result` (skips recompose) must turn that assertion RED while a clean recompose stays green. Apply to a diff: the orchestrator's `applicationReady.result`/`resultLines` must trace to `recomposeFromSpans(...)` output, never to `applicationReadyCandidate.result`.

- `SCOPES`/`SCOPE_LABEL` still gain a `hypothetical` entry (so the tab has a label and the scope is a first-class vocabulary member); visibility is gated by SUPPLY, not by the static list.
- Plan input: if the dialog genuinely cannot take the one-identifier edit within its ceiling, pass `visibleScopes` as a prop and keep the map body unchanged — either way no new dialog logic.

**Checkable invariant (AC-17):** render the preview for a level-1-5 run → assert NO tab, label, or node containing "HYPOTHETICAL"/"Hypothetical" is present (not merely disabled). Mutant: revert `visibleScopes`→`SCOPES` → the ordinary-run assertion reds.

## 7. M4 — shared-reviewer contract gains `evidenceRef`; FINAL contract (ready to scope the OD-3 chunk)

**The defect (check M4).** AC-5 requires a consistency flag "between the two drafts where they reference the same real fact." The r1 §6 flag carried only `evidenceSpanId` ("a single posting/real-material span") — a cross-draft inconsistency's evidence lives in the OTHER draft, which is neither posting nor real-material, so the contract could not express it.

**Decision — replace the single-origin `evidenceSpanId` with a typed `evidenceRef` that names the span's origin, including the other draft.** This is the ONE field the brief asked the design to decide ("needs a field" — confirmed). The FINAL `reviewDocuments(...)` contract, to be scoped verbatim by the OD-3 foundational chunk:

```
reviewDocuments({
  drafts: [
    { kind: "hypothetical",     spans: [{ id, text, section, contextKey }], authorityReference: "internal-consistency" },
    { kind: "applicationReady", spans: [{ id, text, section, contextKey }], authorityReference: "user-material" },
  ],
  posting:      { requirements: [{ id, text }] },                        // step-1 spans (AC-8)
  realMaterial: { spans: [{ id, text, contextKey }] } | null,           // null unless a draft's authorityReference === "user-material"
}) => {
  flags: [{
    draftKind,                 // which draft the offending span is in
    spanId,                    // the app-MINTED id of the offending span (EXACTLY ONE; never a union)
    category: "missing-keyword" | "vague-unsupported" | "repetition"
            | "unverifiable-metric" | "employer-plausibility" | "consistency"
            | "unsupported-authority",
    evidenceRef?: { origin: "posting" | "real-material" | "draft",      // WHERE the evidence span lives
                    draftKind?,                                          // required iff origin === "draft" (the OTHER draft)
                    spanId },                                            // the single evidence span (never a union)
    message,
  }],
  unresolvedQualifications: [{ requirementId, text }],                   // posting reqs wording alone cannot resolve — AC-13 consumes
}
```

Change from r1: `evidenceSpanId?` → `evidenceRef?: { origin, draftKind?, spanId }`. A `category:"consistency"` flag between the drafts sets `origin:"draft"` and `draftKind` = the other draft; a posting/real-material-checked flag sets `origin:"posting"|"real-material"` and omits `draftKind`. Span discipline is preserved: `evidenceRef.spanId` is EXACTLY ONE span regardless of origin.

**Load-bearing contract properties N105 depends on (each checkable) — unchanged from r1 §6 except the field:**
1. Span identity is the APP's; the reviewer never re-chunks; containment/consistency is one span vs one span.
2. Authority reference is SPLIT PER DRAFT (AC-5): `user-material` for application-ready; `internal-consistency` for hypothetical (checked against posting-plausibility + internal date/title/seniority coherence, NOT user material). A strong-but-internally-coherent hypothetical authority claim produces no flag; an incoherent one does.
3. `unverifiable-metric` applies to BOTH drafts (verifiability is draft-internal).
4. `unresolvedQualifications` is the AC-13 wording-cannot-resolve list.
5. Pure/deterministic, no side effects; THE single document-weakness analyzer — N105 imports it and adds none (AC-6).

**On the check's low note (reviewer `realMaterial` has no `chronology` handle).** Confirmed adequate and NOT a gap: the hypothetical's authority check is `internal-consistency` (draft-internal spans only, no chronology needed); the application-ready's date/employer coherence is enforced UPSTREAM by the gate's MEMBERSHIP/`contextKey` rule (§5, whose `realMaterial` DOES carry `chronology`). The reviewer therefore needs no chronology handle. No contract change.

**AC-6 invariant & sequencing (unchanged):** a structural census over N105's OWN additions shows `idealPipeline.js` imports the shared reviewer and introduces no second analyzer (canaried against the known export); behavioral drive over both drafts. AC-6 is RED until the OD-3 chunk lands — sequencing flag for the plan (§9).
