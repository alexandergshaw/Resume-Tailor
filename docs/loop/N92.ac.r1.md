# N92 - Acceptance criteria (round 2, settling round)

Feature: three controls for positioning and smoothing inserted company facts in the cover letter.
Owner request, verbatim (two parts, 2026-09-28):

1. "the fact insertions are working now, but now i need controls to move each fact forward or backward
   a sentence in the letter, and also a control to use the llm to make the transition into the fact
   sentence and the sentence after the fact sentence more natural"
2. "also make it to where i can tell the app to apply the positioning of facts forward on all future
   generated cover letters"

- **CONTROL A** (deterministic): move one inserted fact one SENTENCE forward / backward.
- **CONTROL B** (LLM): rewrite the fact sentence and its neighbours so the transition reads naturally.
- **CONTROL C** (persisted preference): a per-user toggle that applies a standing FORWARD positioning
  to facts on all FUTURE generated letters (Control A's forward-move applied automatically at insert time).

They are ONE feature about fact positioning and must stay coherent. A and C share one positioning primitive.

**Round-2 changes:** owner ruling on B3 faithfulness (CONFIRM-BEFORE-PERSIST, Section 3); corrected the
false-absence "no segmenter exists" (Section 0/D1 - three splitters exist); added segmentation-quality,
multi-sentence-fact, whitespace-byte-identity, move-provenance, cross-paragraph-highlight, Control-C
per-fact, and B-module criteria. Confirmed-sound items from the checker are unchanged and marked.

Author: AC seat (Opus). This artifact binds design (1b/1c/1d/1e), the plan, the 4b tests, the
implementer and the verifier. Where it names a mechanism it does so only to make a criterion checkable;
design may choose a different mechanism that satisfies the same criterion.

## 1. Decisions (stated so downstream does not re-litigate)

- **D1 - Segmentation is REUSE, not new (CORRECTED).** Design must decide: reuse `summarize.js`'s exported
  `splitSentences` vs a purpose-built segmenter, and JUSTIFY. Constraints on the choice: it must satisfy
  AC-A10 (named non-boundary fixtures) and must not force the line-global whitespace normalization that
  breaks AC-A4 (`summarize.js` collapses whitespace up front - if reused, the move must not feed the
  collapsed form back into the letter). Control A and Control C consume ONE shared move primitive (AC-A1/C2).
- **D2 - Boundary behaviour.** A move CROSSES paragraph boundaries within the letter BODY (owner: "in the
  letter"), bounded to body paragraphs: never into the greeting (line 0) or a closing/signature block, and
  never outside the region `markInsertedFacts` can highlight. What would change this: an owner/UX
  preference for paragraph-bounded moves; edges AC-A6/A7 still apply with the range narrowed.
- **D3 - Control C is an independent boolean modifier, not a placement id.** Placement decides WHERE a
  fact starts; the forward toggle applies exactly one Control-A forward-move AFTER placement resolves.
  Deliberately a boolean (one nudge), not an integer offset. **[C magnitude + composition CHECKER-CONFIRMED SOUND.]**
- **D4 - Control B on embedded: disable with an honest reason.** No silent no-op, no deterministic
  pretend-smoothing. **[Embedded B falsifiability CHECKER-CONFIRMED SOUND.]** Section 6.
- **D5 - Control C load-failure and not-yet-loaded both resolve to "do not apply forward"** (safe
  direction: never fabricate a positioning the user did not set). AC-C6.
- **D6 - Control C applies to the automatic insert path only** (autoInsertFactsForJob), not to a manual
  per-article placement set by hand in the research dialog. AC-C8.
- **D7 - CONTROL B IS CONFIRM-BEFORE-PERSIST (owner ruling 2026-09-28, resolves blocker N92C-1).** A
  smoothed rewrite is NEVER applied automatically. After smoothing, the user is shown the actual
  before/after and must approve before it lands in the letter. The USER is the faithfulness check for
  MEANING changes (negation, inflation) that reuse existing tokens and that no automated proxy can catch.
  The automated guards are a first layer over scope and added tokens only. See AC-B3/B5/B10/B11/B12.

## 2. CONTROL A - move a fact forward / backward one sentence

**RED-on-HEAD basis:** no move control, handler, or primitive exists at HEAD (grep
`moveFact|moveInsertedFact|moveForward|moveBackward` = none, 2026-09-28). Every AC below fails on HEAD by
absence unless marked GUARD.

- **AC-A1 (the primitive exists and is pure).** A single pure function computes, for `lines: string[]`, a
  located record `{id,text,lineIndex,offset}`, and a direction (`forward`|`backward`), the new
  `{lines, record}` with the fact relocated by exactly one sentence slot, or an unchanged result on a
  boundary no-op. Never mutates input; returns the same `lines` reference on a no-op.
  *Instrument:* pure vitest unit. *RED on HEAD.*
- **AC-A2 (one click = one sentence; correct direction).** Forward moves the fact past exactly one
  sentence boundary toward the END of the letter; backward before exactly one. Two forward clicks = two
  slots.
  *Instrument:* jsdom strip render + click, asserting resulting sentence ORDER (not merely "changed").
  *RED on HEAD.* *Power depends on AC-A10* - without a pinned segmenter this asserts order against whatever
  the segmenter itself reports. *Failure direction:* swapped/off-by-one is a defect.
- **AC-A3 (crosses paragraph boundaries, bounded to body).** A fact at the last sentence of a body
  paragraph, moved forward, lands at the first slot of the NEXT body paragraph; at the first sentence of
  the first body paragraph, backward is a no-op (AC-A6). Never into greeting (line 0) or closing.
  *Instrument:* pure unit, multi-paragraph fixture incl. greeting. *RED on HEAD.* *Failure direction:* a
  move into greeting/closing is the unsafe failure.
- **AC-A4 (reversible - span-local, whitespace-safe; resolves N92C-5).** For any non-boundary fact,
  forward-then-backward returns the letter to byte-identical `lines` AND the record to identical
  `{lineIndex, offset}`. **To make this satisfiable, the move must operate SPAN-LOCAL:** it removes the
  fact's own span plus exactly the one insertion-owned adjoining space, and re-inserts adding exactly one
  space, WITHOUT applying a line-global `.replace(/\s{2,}/g," ").trim()` that would destroy pre-existing
  whitespace elsewhere in the touched paragraphs (the hazard in `factInsertion.js:252`,`:66-71`).
  **Documented relaxation:** if design proves span-local is infeasible on the existing splice seam, AC-A4
  relaxes to "identical MODULO the app's existing single-space normalization", the round-trip test asserts
  that weaker equality, and design records why. The unsafe outcome - silent loss of the candidate's own
  intentional spacing - must be called out either way.
  *Instrument:* pure unit round-trip on a fixture that CONTAINS pre-existing double spaces outside the
  fact span. *RED on HEAD.*
- **AC-A5 (record stays consistent - N81/N90 class).** After ANY single move, every surviving record in
  `entry.insertedFacts` locates its OWN text at its stored `offset`/`lineIndex` (the `relocateSurvivors`
  invariant, `:615-627`), and the moved fact appears in the letter EXACTLY ONCE.
  *Instrument:* class-invariant rc test (assert over all survivors), style of
  `removeInsertedFact.coalesced.rc.test.js`. *RED on HEAD.* *Failure direction:* a stale offset
  (unremovable/unhighlightable) or a duplicated fact is the N61/N81 defect.
- **AC-A6 (boundary no-op is honest).** A fact at the first movable slot has backward DISABLED; at the
  last, forward DISABLED - announced to assistive tech, not silently no-op.
  *Instrument:* jsdom disabled/aria assert at + off the boundary. *RED on HEAD.* *Failure direction:* a
  live-looking control that silently no-ops is the defect.
- **AC-A7 (two adjacent facts).** Moving one of two same-line/adjacent facts PAST the other leaves BOTH
  records locating their own text (AC-A5), the two in the new relative order, neither excised/merged.
  *Instrument:* pure + jsdom, two same-line facts. *RED on HEAD.*
- **AC-A8 (hand-edited letter: safe no-op, never a guess).** If a hand-edit moved the fact's span off
  `(lineIndex, offset)`, a move is a no-op leaving `lines` unchanged with an honest reason (mirroring
  `planRemoveFact`'s stale-locator no-op `:240-241`), never a relocation guessed against another
  occurrence.
  *Instrument:* unit with a stale locator. *RED on HEAD.* *Failure direction:* moving the wrong text is
  the unsafe failure; the safe outcome is the no-op.
- **AC-A9 (not gated on cover bytes).** A move proceeds on the letter TEXT with no engine bytes to splice
  (restored chip / version switch), as `removeInsertedFact` does (`:638-646`); a non-appliable splice
  drops stored bytes to `""` so the download rebuilds from the moved lines, never shipping stale bytes.
  *Instrument:* hook rc, `hasCoverBytes=false` + splice-refusal fixtures. *RED on HEAD.*
- **AC-A10 (segmenter quality is pinned; resolves N92C-3).** The chosen segmenter is tested against a
  NAMED fixture set that must be treated as NON-boundaries: honorifics/abbreviations ("Ph.D.", "U.S.",
  "e.g.", "i.e.", "Dr.", "Inc."), decimals ("3.5"), currency ("$50M."), and periods inside quotes/
  parentheses. Each fixture asserts the fact lands in the intended inter-sentence gap, never mid-token.
  If the chosen segmenter cannot pass a given class, that class is recorded as an OWNER-ACCEPTED
  limitation naming the specific mis-split, rather than left silent. (Note: `summarize.js`'s lookahead
  handles "Node.js"/"$50M." but "U.S. Army" would mis-split - so this is real, not theoretical.)
  *Instrument:* pure unit of the segmenter over the named fixtures. *RED on HEAD.* *Rationale:* without
  this, AC-A2 is zero-power - it asserts order against whatever the segmenter reports. *Failure
  direction:* a phantom slot that lands a fact mid-abbreviation.
- **AC-A11 (multi-sentence fact is atomic; resolves N92C-4).** A fact whose recorded text spans multiple
  sentences (possible per `normalizeFactText`, `:84-86`) is an ATOMIC movable unit: its INTERNAL sentence
  boundaries are NOT move slots; the whole fact moves as one across EXTERNAL slots. AC-A4 reversibility and
  AC-A5 consistency hold for it.
  *Instrument:* pure + rc test with a two-sentence-fact fixture. *RED on HEAD.* *Failure direction:*
  splitting a fact across a move (half moves, half stays) corrupts the claim and its provenance.
- **AC-A12 (move preserves provenance; resolves N92C-6).** A move preserves the fact's `id`/`url`/`title`
  (parallel to AC-B4), so the source link (when `safeExternalHref` accepts the url) and one-click remove
  survive after a move.
  *Instrument:* jsdom + hook rc asserting id/url/title unchanged and remove still excises cleanly post-move.
  *RED on HEAD.*
- **AC-A13 (cross-paragraph move re-lands the highlight; resolves N92C-9).** After a move that changes the
  fact's paragraph, `markInsertedFacts` flags the run carrying the fact as `insertedFact` in the NEW
  paragraph of the docx-parsed model (it matches by `(text, offset)` per paragraph, NOT by `lineIndex` -
  `versionDiff.js:154-175`,`:143-144`). A `previewReloadKey` bump alone is NOT sufficient - the marked
  model itself must carry the flag on the moved fact.
  *Instrument:* build the model, run `markInsertedFacts` with the post-move locator, assert the flagged run
  is in the destination paragraph. *RED on HEAD.* *Failure direction:* a highlight left on the old
  paragraph or lost = an unreviewable fact = the N61 egress risk.

## 3. CONTROL B - LLM-smooth the transition (CONFIRM-BEFORE-PERSIST)

**RED-on-HEAD basis:** no smoothing control/handler/engine method/route exists at HEAD (grep
`smoothTransition|smoothFact` = none). Criteria fail on HEAD by absence unless marked GUARD.

**Owner ruling (D7):** the rewrite is proposed, shown, and applied only on explicit user confirmation. The
faithfulness architecture is TWO layers - an automated first layer (AC-B1/B5/B7 + the added-token check in
B3) and the user's confirm gate (AC-B10/B11/B12) for meaning changes the automation cannot catch.

- **AC-B1 (scope pinned to three sentences).** A smoothing may change ONLY the sentence BEFORE the fact
  (the "transition into"), the fact sentence, and the sentence AFTER it. After a smoothing the letter
  differs ONLY within that contiguous span; every other paragraph/sentence is byte-identical.
  *Instrument:* diff pre/post `lines`; assert equality outside the span. *RED on HEAD.* *Failure
  direction:* a whole-paragraph or distant-sentence rewrite is the defect. This bounds hallucination blast radius.
- **AC-B2 (scope shrinks at a boundary; never crosses into an adjacent paragraph).** Fact first-in-
  paragraph -> no "before" touched, no reach into the previous paragraph; last-in-paragraph -> no "after".
  Greeting and closing never touched.
  *Instrument:* unit, fact at each edge. *RED on HEAD.*
- **AC-B3 (faithfulness architecture is explicit; recast per owner ruling, resolves N92C-1).** The
  criteria MUST state plainly, and the implementation MUST behave so, that:
  (a) the automated RUNTIME rejection covers SCOPE (AC-B1/B2) and ADDED TOKENS only - a smoothed output is
  auto-rejected if it introduces a number, date, currency amount, or proper name not present in the
  in-scope material (the three sentences + the fact's recorded text) before smoothing;
  (b) negation and inflation that REUSE existing tokens (e.g. dropping a "not", changing "helped" to "led",
  "a team" to "the team") are NOT auto-catchable and are NOT claimed to be;
  (c) therefore NOTHING smoothed is persisted to the letter, the store, or any download until the user
  explicitly approves the shown before/after diff (AC-B10). The confirm gate is the guard for meaning.
  *Instrument:* unit test of the added-token check (positive: an injected new number is rejected; control:
  a faithful reword passes the added-token check but still requires confirm); plus the criteria text
  itself asserting (a)/(b)/(c). *RED on HEAD.* *Failure direction:* claiming the automation catches
  meaning changes, or persisting without confirm, is the unsafe failure.
- **AC-B4 (provenance preserved).** Smoothing never changes the record's `url`/`title`/`id`; post-confirm,
  the source link still renders and the fact is still one-click removable with its span re-located to the
  smoothed text (AC-A5 invariant).
  *Instrument:* jsdom + hook rc. *RED on HEAD.*
- **AC-B5 (automated runtime rejection => discard, no persist).** If the engine errors, times out, returns
  empty, returns output failing the scope guard (text outside the span), or failing the added-token check
  (AC-B3a), the proposal is discarded: `lines` stay byte-identical to pre-smoothing, nothing is persisted,
  an honest error is surfaced, and the decision is logged with a negative outcome (AC-X1). This is distinct
  from the user DECLINING a valid-looking proposal (AC-B11).
  *Instrument:* hook rc with stubbed engine returning error/empty/out-of-scope/added-token; assert `lines`
  unchanged and no PUT to `/api/accepted-facts`. *RED on HEAD.* *Failure direction:* showing/persisting an
  auto-rejectable rewrite is the defect.
- **AC-B6 (post-apply undo).** After a smoothing has been CONFIRMED and applied, the user can undo it with
  one click, restoring the letter to byte-identical pre-smoothing `lines` and re-locating the fact; the
  undo persists (survives repaint + download).
  *Instrument:* jsdom confirm-then-undo; assert byte-identity + persistence. *RED on HEAD.*
- **AC-B7 (egress scoped).** The engine request payload contains ONLY the three in-scope sentences and the
  fact's recorded text (plus contract framing); NOT the whole letter, resume, job description, or unrelated
  paragraphs.
  *Instrument:* drive the real handler with the engine/fetch spied, assert actual payload contents, WITH a
  positive control that records a real request on that path. *RED on HEAD.* *Failure direction:*
  over-sending is a privacy defect.
- **AC-B8 (strictly user-initiated - spend; module note per N92C-8).** The smoothing engine call fires
  ONLY on an explicit user click - never on the N72 auto-insert path, generation, a repaint, a reload, a
  version switch, Control A, or Control C. No numeric cap (N65 precedent).
  - **AC-B8a (structural, preferred):** the unattended paths do not import/reference the smoothing seam.
    *This forces the smoothing function into its OWN module* - the file-level guard is unprovable
    otherwise, because the auto-insert path lives in `useCompanyResearch.js`, which would also host a
    co-located smoothing handler. Design either isolates the smoothing seam in its own module (making
    B8a provable by a static import check) or explicitly falls back to AC-B8b as the sole guard and says so.
  - **AC-B8b (behavioural fallback):** engine-spy tests over auto-insert/repaint/reload assert ZERO
    smoothing calls, each with a positive control that a click DOES call it.
  *RED on HEAD (partly GUARD):* today no smoothing seam exists, so the auto-path assertions are vacuously
  true until B exists; the click-fires-a-call half is genuinely RED. Stated honestly.
- **AC-B9 (engine dependence).** On embedded (`wantsEmbedded` true) Control B is DISABLED with a visible,
  honest reason and fires NO engine call; on gemini/external it is enabled. Disabled state announced to
  assistive tech.
  *Instrument:* jsdom per-engine; assert enabled/disabled + no call under embedded. *RED on HEAD.*
  **[Embedded B falsifiability CHECKER-CONFIRMED SOUND.]** Section 6 - owner call on disable vs fallback.
- **AC-B10 (CONFIRM BEFORE PERSIST; new, owner ruling).** A smoothed rewrite is NEVER written to the
  letter `lines`, the accepted-facts store, or any download until the user explicitly confirms the shown
  before/after. Before confirmation the letter is byte-identical to pre-smoothing and no PUT to
  `/api/accepted-facts` has fired.
  *Instrument:* hook/jsdom - after a smooth call, assert no store write and unchanged `lines` until
  confirm; on confirm, the PUT fires and `lines` update. *RED on HEAD.* *Failure direction:* auto-applying
  without confirm is the unsafe failure this whole ruling exists to prevent.
- **AC-B11 (decline discards and restores; new).** Declining the proposal discards the rewrite entirely
  and leaves the letter byte-identical to before smoothing; nothing is persisted; the decision logs a
  negative outcome (AC-X1). Distinct from an automated rejection (AC-B5) - a decline is a valid proposal
  the USER refused.
  *Instrument:* jsdom smooth-then-decline; assert byte-identity + no store write. *RED on HEAD.*
- **AC-B12 (the shown diff IS the applied change; new).** The before/after presented for confirmation is
  exactly the text that will be applied on confirm - not truncated, re-generated on confirm, or
  paraphrased. The confirmed applied `lines` equal the previewed "after".
  *Instrument:* capture the previewed "after", confirm, assert the resulting `lines` contain exactly that
  text. *RED on HEAD.* *Failure direction:* showing one thing and applying another voids the user's
  faithfulness check - the unsafe failure.

## 4. CONTROL C - persisted "position facts forward on future letters"

**RED-on-HEAD basis:** no forward-preference key, toggle, or insert-time modifier exists at HEAD.

- **AC-C1 (composition with placement is pinned).** The forward preference is an INDEPENDENT boolean
  modifier applied AFTER placement resolves: the fact is placed per `defaultPlacement || DEFAULT_PLACEMENT`,
  then if the toggle is ON exactly one Control-A forward-move is applied, subject to the body-boundary rule
  (AC-A3); if that move would exceed the last movable slot it is a no-op (no error). Toggle OFF = today's
  placed position.
  *Instrument:* pure unit over the insert planner, toggle x each placement id. *RED on HEAD.*
  **[C composition per placement value CHECKER-CONFIRMED SOUND.]** *Failure direction:* the toggle must not
  silently change WHICH placement is used.
- **AC-C2 (shares Control A's primitive).** The forward nudge uses the SAME pure function Control A uses
  (AC-A1), not a divergent copy.
  *Instrument:* same symbol (structural/import check) + identical results on a shared fixture. *RED on HEAD.*
- **AC-C3 (persistence rides user-prefs additively; guards not weakened).** A new allowlisted boolean key
  on `/api/user-prefs`, sanitized strict-boolean (absent/non-boolean dropped), added like
  `ALLOWED_BOOLEAN_KEYS` (`route.js:9-13,63-64`). Existing sanitize behaviour for `coverFactPlacement`,
  `appliedSort`, `excludedTitleKeywords`, and the booleans is byte-unchanged.
  *Instrument:* route unit (key round-trips only as boolean; garbage dropped) + existing sanitize tests
  stay green. *RED def / GUARD sanitize.* *Failure direction:* a type-only/absent guard letting garbage
  through is the N62/N82 defect.
- **AC-C4 (last hop: set -> generate -> forward, visible AND downloaded).** With the toggle ON, a newly
  generated letter that auto-inserts facts positions them one forward-slot from placement, visible in the
  preview highlight AND at that position in the download.
  *Instrument:* hook/integration through `autoInsertFactsForJob` + preview render + download rebuild. *RED
  on HEAD.* **[Last-hop coverage CHECKER-CONFIRMED SOUND as a requirement.]** *Failure direction:* stored
  state changes but the visible/downloaded letter does not = the last-hop defect class.
- **AC-C5 (turn-off-able / not one-way - N82).** The toggle is bidirectional: `false` is settable,
  persists, and future letters place facts WITHOUT the nudge. `false` is not swallowed as "no preference".
  *Instrument:* route + hook toggle true->false, assert OFF behaviour at insert time. *RED on HEAD.*
- **AC-C6 (failed / not-yet-loaded resolves SAFE - N86).** A failed GET, non-ok GET, or not-yet-loaded
  state must NOT be read as "forward on": the modifier applies only on an explicit loaded `true`.
  Not-yet-loaded and load-failure both behave as "do not apply forward". Control C must NOT add a second
  independent fetch race; it reuses a shared source (the one N86's fix consolidates) so the settings UI and
  the insert path cannot silently disagree.
  *Instrument:* hook test simulating failed/pending load asserting no nudge; a test that both consumers
  read one source. *RED on HEAD.* *Failure direction:* fabricating a forward the user did not set is the
  unsafe failure. Depends on N86 (still open) - if unresolved when this lands, design must state how
  Control C avoids adding a new race.
