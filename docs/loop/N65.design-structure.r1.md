## 1. The decisions that are expensive to reverse

### D1 — A DEDICATED grounded route, NOT grounding bolted into `/api/chat`. (load-bearing)

The estimate must be a structured, cited, labelled artifact (R4, S2, S4, S13). `/api/chat` is a free-prose
endpoint whose whole contract is `{ reply: string }` (F1, F13) and whose system prompt invites an
ungrounded guess (F2). Two structurally different homes:

- **Bolt grounding into `/api/chat`.** Rejected. It would mean one route conditionally switching between two
  inverted SDK surfaces (`generateContent` vs `interactions.create`, F6) keyed on a detected "salary intent",
  entangling the estimate's spend and citation contract with the general chat turn, and it would give the
  free-prose reply and the structured estimate ONE response envelope that the client (F13) cannot tell apart.
- **A dedicated `POST /api/salary-estimate`.** CHOSEN. It is the `application-digest` precedent verbatim
  (F7): its own auth, its own module-scope rate limiter (the spend surface OWNER-2 governs is then one route,
  not smeared across chat), its own embedded refusal, its own grounded call, its own STRUCTURED response.
  The estimate is thereby impossible to confuse with a chat reply because it arrives on a different route with
  a different envelope.

**Consequence for the trigger:** a DEDICATED affordance ("Estimate salary") on the pinned-posting context,
not an intercepted natural-language question. This is deterministic (no NL classification competing with the
free-prose path), satisfies S12 (pinned posting flows in, first click, no wizard), and gives S13's removal
test a single structural gate to target. A typed salary question in the chat still reaches `/api/chat`; D6
governs what that path is allowed to say.

### D2 — NOTHING is stored; every ask is fresh. (removes the migration question entirely)

Ruling: the estimate lives only in the in-memory chat transcript, exactly like every other assistant turn
(F13). No table, no column, no migration.

Basis: (a) **Safety** — a stored estimate is one refactor away from being read as stated pay, the precise
S11 hazard; keeping it out of the database makes that impossible rather than merely forbidden. (b) **AC R5 /
app-vs-chat** — persistence is *Corpus*, classed INHERITED; it does not justify the feature and its absence
does not weaken the earned claim, which is the provenance guarantee. (c) **Staleness** — salaries drift; a
cached range silently ages. (d) **The brief's own hazard** — a migration auto-deploys to production and this
repo has confirmed live-schema drift (`applications.UNIQUE(user_id, position_id)`), so the cheapest correct
migration is none. Reversible: if a future owner wants a saved estimate, it attaches as its OWN table
carrying its OWN provenance and MUST NOT touch `feed_postings.salary_min/max` (S11); §8 names where.

### D3 — The number's provenance is the CITATIONS, and the range is extracted by app code from a fixed envelope. (S2/S3)

The Interactions surface returns annotated free text, not a structured `{min,max}` (F5). So the range must
come from the model's text — but the AC's guarantee (S2) is not "the number is JSON"; it is "no number
without a resolvable citation, else withhold." This design honours it two ways at once:

1. The model is instructed (D6-prompt) to emit its estimate on ONE fixed first line
   `ESTIMATE: $<min>–$<max>` (or `ESTIMATE: none`). A pure `parseEstimateRange` reads ONLY that envelope line
   and requires BOTH bounds (via `parseSalary` + the existing annual band clamp, F9); anything else →
   `null` → withhold. Scanning the whole prose for a stray number is deliberately NOT done — that would let an
   incidental figure become "the salary" (S3 failure direction).
2. The number is SHOWN only when ≥1 citation survives `citationHref` extraction (D4). Zero usable citations →
   no number, ever (S2). This is S13's removal-test gate, and it lives in one pure function so a diff can be
   checked against it.

Both the range's presence AND its display gate are app-controlled, deterministic, and testable without the
model.

### New — `lib/salary/salaryEstimate.js` (pure; no I/O, no React; safe to import server- and client-side)

```
// The S1/R2 gate, in ONE home. Reuses resolvePostingSalary (F9).
// stated iff a structured bound is present OR parseSalary(description) yields one.
export function postingSalaryStated({ salaryMin, salaryMax, description }): boolean

// Reads ONLY the fixed envelope line `ESTIMATE: $X–$Y`; requires BOTH bounds after
// normalizeSalaryPair band-clamp (F9). Returns null on any miss (→ withhold, S3).
export function parseEstimateRange(outputText: string): { min: number, max: number } | null

// Structured citations that survive the URL control (S5/S6). For each source:
//   href = citationHref(source.uri); drop if null.
//   host = citationHost(href); drop if servesGroundingRedirect(host, href).
// Returns [{ url: href, title: citationTitle-or-"" , host }]. De-duped by host+url.
export function usableCitations(sources: Array<{uri,title}>): Array<{url,title,host}>

// S7 support-vs-membership. "company" iff company non-empty AND some citation's
// title OR host contains the normalized company token; else "comparable" if any
// citation; else "none".
export function deriveBasisKind(citations, company: string): "company"|"comparable"|"none"

// The one builder the route calls. Pure. Never throws.
export function buildSalaryEstimate({
  outputText: string,        // interactionOutputText(interaction) — may be ""
  sources,                   // extractCitationSources(interaction)
  searched: boolean,         // interactionSearched(interaction)
  truncated: boolean,        // interactionTruncated(interaction)
  company: string,
}): SalaryEstimate
```

`SalaryEstimate` (the ONLY thing that crosses the wire and reaches the render):

```
{
  status: "estimated" | "insufficient_sources" | "failed"
        | "refused_stated" | "unavailable_embedded",  // last two set by the ROUTE, not the builder
  reason: "ok" | "no_sources" | "no_range" | "not_searched"
        | "stated" | "embedded" | "provider_error",   // drives the ledger `reason` field (S10) — a CANNED code, never prose
  range: { min: number, max: number } | null,          // present iff status==="estimated"
  basisKind: "company" | "comparable" | "none",
  sourceCount: number,                                  // usableCitations.length
  citations: Array<{ url, title, host }>,               // present iff status==="estimated"; url already citationHref-admitted
  searched: boolean,
  truncated: boolean,
}
```

Builder logic (the decision table, order matters):
1. `cites = usableCitations(sources)`
2. if `!searched` → `{ status:"failed", reason:"not_searched", range:null, basisKind:"none", sourceCount:0, citations:[] }` (S6/S14 — no proof of search means retrieval degraded, never a negative).
3. if `cites.length === 0` → `{ status:"insufficient_sources", reason:"no_sources", range:null, basisKind:"none", sourceCount:0, citations:[] }` (S2 gate — THE removal-test target, S13).
4. `range = parseEstimateRange(outputText)`; if `!range` → `{ status:"insufficient_sources", reason:"no_range", range:null, basisKind:"none", sourceCount:cites.length, citations:[] }` (S3 — have sources, no usable range → still withhold).
5. else → `{ status:"estimated", reason:"ok", range, basisKind:deriveBasisKind(cites,company), sourceCount:cites.length, citations:cites }`.

**Checkable property (apply to a diff):** step 3 is the only place `status:"estimated"` can be produced with
`citations`, and it is guarded by `cites.length === 0` returning first. A reviewer greps `salaryEstimate.js`
for `status: "estimated"` — it must appear exactly once, AFTER the `cites.length === 0` early return. Removing
that early return is what S13's test detects.

### New — `lib/salary/salaryEstimatePrompt.js` (string literals + fenced builder; the F19 idiom)

```
export const SALARY_ESTIMATE_SYSTEM_PROMPT: string   // module const, literals only
export function buildSalaryEstimateInput({ title, company, location }): string
```

`SALARY_ESTIMATE_SYSTEM_PROMPT` states, in prose the constant pins (S9's falsifiable half):
- Research typical annual USD compensation for THIS role using web search; cite real sources.
- Emit the estimate on the FIRST line exactly as `ESTIMATE: $<min>–$<max>` in USD/year, or `ESTIMATE: none`
  if the sources do not support a range. Then at most two plain-prose sentences of basis.
- NEVER give negotiation, "what to ask for", or offer-evaluation advice; NEVER state a figure as this
  specific company's pay unless a cited source is about that company.
- Plain text; no markdown, no pasted URLs in the prose (citations ride as annotations, F5).

`buildSalaryEstimateInput` sends ONLY `title`/`company`/`location`, fenced with `<untrusted-data>` +
`neutraliseFence` (F19). The posting BODY is deliberately NOT sent (it is untrusted scraped text, and the
grounded query needs only role+company+location — the same body-not-re-sent discipline glossaryPrompt uses).

```

```

Gate order (each gate is the cheapest that can refuse; a refused POST still spends a rate token, so the
CLIENT must not fire when it can predict a refusal — see D5 and the client-triggers memory):
1. `getUser()` → 401 if absent.
2. `salaryLimiter.check(identify(request,{userId}))` → 429 (headers) — before body validation, so junk still
   exhausts the caller's own allowance (F7).
3. parse JSON → 400; require non-empty `title` (and prefer `company`) → 400 if absent.
4. `wantsEmbedded(body.engine)` → 200 `{ salaryEstimate:{ status:"unavailable_embedded", reason:"embedded", ... } }` (S8). 200, not 503, so the client renders the explicit message as an assistant turn rather than a fetch error — a deliberate divergence from digest's 503, justified because this result is shown IN the transcript, not a table cell.
5. `body.salaryStated === true` → 200 `{ salaryEstimate:{ status:"refused_stated", reason:"stated", ... } }` (S1 server backstop; NO grounded call — cheapest refusal; this is a claim-level guard behind the client gate D5, since the route has no description to recompute from — stated plainly).
6. Otherwise the grounded call, INSIDE a try (a vendor-shape surprise must land on the failure path, F7):
   ```
   interaction = await client.interactions.create(
     { model, input: buildSalaryEstimateInput({title,company,location}),
       tools: [{ type: "google_search" }] },              // TOP-LEVEL — F6 trap
     { timeout: GROUNDED_CALL_TIMEOUT_MS, maxRetries: GROUNDED_CALL_MAX_RETRIES });   // PER-CALL
   built = buildSalaryEstimate({
     outputText: interaction.output_text ? interactionOutputText(interaction) : "",
     sources:    extractCitationSources(interaction),
     searched:   interactionSearched(interaction),
     truncated:  interactionTruncated(interaction),
     company });
   ```
   `catch` → 200 `{ salaryEstimate:{ status:"failed", reason:"provider_error", range:null, basisKind:"none", sourceCount:0, citations:[] } }` (S14).
7. return 200 `{ salaryEstimate: built }`.

The route writes NOTHING to any database (D2) and NEVER touches `feed_postings` (S11).

where a citation becomes a link is `usableCitations` → `citationHref` (S5/S6). Ingestion (`ingestFeed.js`,
`llmSearch.js`, the tailor cron) is not on this diagram and gains no call (S11).

## 4. The citation contract

- **Source of truth:** `client.interactions.create` + `extractCitationSources` — real publisher URLs, never
  legacy `generateContent`+`googleSearch` `web.uri` proxies (F5/F6, S6). No `config` object; `tools` top-level.
- **Admission:** a source's URL becomes a link ONLY if `citationHref(uri) !== null` AND
  `!servesGroundingRedirect(host, href)` (F8, S5). A `vertexaisearch.cloud.google.com` / `grounding-api-redirect`
  URI is dropped, never shown as a publisher link. A refused URL contributes NO anchor and does not count
  toward the ≥1-citation gate.
- **Label:** a citation renders as `title || host`, where `host = citationHost(href)` is derived from THAT
  anchor's own href (F8's rule: a displayed domain comes only from the href it links to). `citationTitle` is
  reused to admit/normalize the vendor title; an inadmissible title falls back to the host.
- **Gate:** zero admitted citations ⇒ `status !== "estimated"` ⇒ no number (S2). Proof-of-search
  (`interactionSearched`) is required before any number (S6).
- **Basis honesty (S7):** "at {company}" only if an admitted citation's title or host contains the company;
  otherwise "similar roles in this market". Derived from the admitted citations, not from prose.

| `insufficient_sources` | "I couldn't find enough salary data to estimate a range for this role right now." (explicitly NOT "this role pays nothing/badly", S14) | none — no number, no chip, no citation list | `skipped` |
| `failed` | "I couldn't retrieve salary sources right now — try again in a moment." (S14 — a retrieval problem, never a negative result) | none | `failed` |
| `refused_stated` | "This posting already states its pay, so there's nothing to estimate." | none — the stated figure stays owned by the posting surface, never re-rendered here (S1/S11) | `refused` |
| `unavailable_embedded` | "A salary estimate needs the AI engine and isn't available on the embedded (offline) engine." (S8) | none | `refused` |

S4 is enforced structurally: a STATED salary is rendered by `FeedPostingCard`/`formatSalary` on the posting
surface with no "Estimate" label; the estimate is rendered ONLY inside the chat estimate block, always inside
the "Estimate" chip. The two never share an affordance. **Checkable property:** the string "Estimate" (the
label) appears on the estimate chip and NOWHERE on any stated-salary render path.

## 6. What happens to the EXISTING free-prose salary path (the brief's required ruling)

Today a user who types "what's the salary?" into the Ask AI panel with a posting pinned hits `/api/chat`,
whose prompt invites "here is what I can infer" (F1/F2) and returns a bare, uncited number in prose. Leaving
that beside the new grounded path is the "two different answers to the same question" hazard.

**Ruling (D6):** the sanctioned salary NUMBER path is the dedicated estimate ONLY. To stop `/api/chat` from
emitting its own ungrounded figure, its `SYSTEM_PROMPT` (F1, `route.js:23-32`) is amended so that, asked about
a posting's pay, the model does NOT state a specific salary number and instead directs the user to the
"Estimate salary" affordance (which gives a grounded, cited range). The `:31` "here is what I can infer"
clause is narrowed to exclude compensation.

**Honest limit (S16):** this is a PROSE-level control. It is falsifiable only at the prompt-CONSTANT level
(a test asserts the constant contains the salary-deferral instruction and no longer invites an inferred pay
figure); whether the non-deterministic model always obeys cannot be asserted by an automated test. That
residue is exactly S16 — a manual/adversarial check at 6/8b, not an automated green. The embedded path already
emits no number (F4) and is unchanged; on the embedded engine the affordance still returns the explicit
`unavailable_embedded` message (S8). **This is the one place the design cannot make the wrong thing
structurally impossible; it is disclosed rather than papered over.**
