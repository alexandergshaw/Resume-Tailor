## 1. Contradictions routed to me — resolved

### P1 (I OWN THIS). In N151a, **marking a material as a template ALSO sets the selection pointer** ("mark = add to library + make active").
The design §7 claims "N151a alone delivers 'mark a résumé as a template, and future generations use it'" AND "no switcher is needed yet." Those are only *both* true if the mark writes the selection, because with no selection writer and a mark that writes a **named** row (§3.2, not the reserved name), consumption would fall back to `reserved ?? null` and the just-marked template would be inert until N151b.
- **Chosen mechanism:** the register write (library route POST) performs, server-side in one request: validate `.docx` → upload bytes → insert the named `resume_templates` row → `setSelection(user,kind → new row)`. One user click, good default (minimize-clicks).
- **What proves it:** a test asserting that after marking material M, `getActiveTemplateBytes(user,'resume')` returns **M's bytes** (not the reserved row's).
- **Why it does not steal N151b's scope:** N151b adds the **switcher** — a picker to *change* the active selection among multiple library entries without re-marking. Mark-sets-selection is the default; the switcher is the override. Clean seam.
- **Second benefit:** it gives `template_selections` a live writer in N151a, so the table + selection store are **reachable** and do not land as an unwired-module / orphan-export exportReachability finding (see §6).

### OR-3 (confirm). Résumé-only this slice. Mark writes `kind='resume'`; the materials locker has no kind tag (F12), so a cover affordance would need a kind selector — OUT. Matches design §10 OR-3. No ruling needed beyond the fixed OR-3.

### OR-4 (confirm). I adopt design §4.1 Opt A: new `template_selections` table, PK(user_id,kind), `template_id` nullable FK → `resume_templates(id) ON DELETE SET NULL`. Fixed by the brief's OR-4. Encoded in Step 1.

### OR-5 (defer, with seam). "Regenerate-into persists vs one-off" is N151c, not this slice (brief). N151a writes **no** `applications.*_template_id` provenance (F2 columns stay unused). ST-13 holds.

### OR-6 (DEFER to N151c — I flag this). The brief's OR-6 ("keep N97's preview capture control, relabel to 'Add to template library'") is a *fixed ruling* but does not name a slice. Relabeling the preview control to say "library" while it still writes the **single reserved-name row** (its handler is unchanged N97 machinery, `useDocumentPreview.js:529-532`, writing via `saveDefaultTemplate` reserved-name) is a label/behaviour mismatch — "library" implies named entries. Making that control genuinely add a **named** library entry is a handler change in the preview modal, which is **Seam 4 (concurrent-edit hot zone)** and belongs with N151c's preview work.
- **Recommendation:** N151a leaves the N97 capture control **untouched** (it keeps writing the reserved row, which is exactly the §6.1 fallback substrate). OR-6's relabel + named-write lands in N151c. This keeps N151a entirely off the preview modal. **Flagged for the orchestrator** — if OR-6 must land in N151a, it is a cosmetic string-only change (Step 8, below, as OPTIONAL) that also breaks `DocumentPreviewDialog.setDefaultTemplateControl.test.js` and must update it.

### Step 1 — DB: `template_selections` (migration only)
- **File:** NEW `hello-world/supabase/migrations/20261008010000_n151a_template_selections.sql` (stamp `> 20261008000000`, the verified true latest; no applied migration edited in place).
- **Shape:**
  ```
  create table if not exists public.template_selections (
    user_id     uuid not null references auth.users (id) on delete cascade,
    kind        text not null check (kind in ('resume','cover')),
    template_id uuid references public.resume_templates (id) on delete set null,
    updated_at  timestamptz not null default now(),
    primary key (user_id, kind)
  );
  alter table public.template_selections enable row level security;
  -- 4 policies auth.uid() = user_id (select/insert/update/delete), modelled on resume_templates :149-163
  grant select, insert, update, delete on table public.template_selections to authenticated;
  grant all on table public.template_selections to service_role;
  ```
  `create table if not exists` + RLS loop idiom is the SAFE form here (this repo is the sole author of this table — the N64 header `:88-91` establishes the rule). Additive-only.
- **Contract:** PK(user_id,kind) ⇒ at most one selection per kind (structural). `template_id` nullable; `ON DELETE SET NULL` ⇒ deleting the selected template nulls the pointer, never errors, never cascades the selection row away.
- **Verifiable:** migration-shape test (§4) asserts PK, FK target, `on delete set null`, RLS enabled, 4 policies, stamp ordering.
- **Landable alone:** yes — pure DB; no code reads it yet.

### Step 2 — Storage lib: selection store
- **File:** NEW `lib/document/templateSelectionStore.js`.
- **Signatures / contracts** (every statement carries `.eq("user_id", userId)` atop RLS; reads return null on missing substrate, never throw — BL-A parity with `defaultTemplateStore.js:15-20`):
  - `getSelection(supabase, { userId, kind }) → { template_id: string|null } | null` — null when no row or substrate absent.
  - `setSelection(supabase, { userId, kind, templateId }) → { ok: true } | { error: string }` — upsert on PK(user_id,kind); `templateId` validated as a uuid the caller owns (RLS enforces, store passes it through); invalid `kind` → `{error}`.
  - `getActiveTemplateBytes(supabase, { userId, kind }) → { bytes: Uint8Array } | null` — **precedence (load-bearing): selection's template bytes ?? reserved-row bytes (`getDefaultTemplateBytes`) ?? null.** Resolves `getSelection` → if `template_id`, load that `resume_templates` row (id+user_id gated) → download its `storage_path`; on any miss, fall through to `getDefaultTemplateBytes(supabase,{userId,kind})` (the N97 reserved row, §6.1); else null.
- **Imports:** `getDefaultTemplateBytes` from `defaultTemplateStore.js` (reuse, reachable).
- **Verifiable:** unit tests on precedence + RLS-shape (§4). **Reachable in N151a** because the route (Step 4) imports `getActiveTemplateBytes` and `setSelection`.
- **Landable alone:** yes — exports with importers added in Step 4 (same wave).

### Step 3 — Storage lib: library store
- **File:** NEW `lib/document/templateLibraryStore.js`.
- **Signatures / contracts:**
  - `listTemplates(supabase, { userId, kind }) → Array<{id,name,kind,storage_path,updated_at}>` — `.eq("user_id",userId).eq("kind",kind)`, ordered by `updated_at desc`; `[]` on error/absent (BL-A).
  - `registerTemplate(supabase, { userId, kind, name, bytes }) → { row } | { error }` — **ordering load-bearing (bytes before row, mirrors `defaultTemplateStore.js:62-67`):** generate `id = crypto.randomUUID()`; upload `bytes` to **`${userId}/templates/${id}.docx`** (per-id path — NOT the material's `${userId}/materials/${name}` path, NOT N97's fixed `default-${kind}.docx`) with `contentType: DOCX_MIME, upsert:true`; then `insert { id, user_id: userId, kind, name, storage_path }`. Invalid kind / empty bytes → `{error}`. **23505 (unique `(user_id,kind,lower(name))`) → friendly `{ error: "You already have a template named \"<name>\"." }`, never a raw constraint error** (reuse the `isUniqueViolation` idiom at `defaultTemplateStore.js:56-60,121-132`).
  - `deleteTemplate(supabase, { userId, id }) → { ok: true } | { error }` — delete row (`.eq("id",id).eq("user_id",userId)`) + best-effort `storage.remove`. (Shipped for completeness/library CRUD; UI delete control is OPEN for N151b, see §8.)
- **Imports:** `DOCX_MIME` from `@/lib/drive/driveMime` (reuse, as `defaultTemplateStore.js:22`).
- **Decoupling rationale (design §3.2):** bytes are COPIED to a per-template object, so deleting/renaming the material never breaks a template; a template is an immutable snapshot at mark time.
- **Verifiable:** unit tests (§4): per-id path, named row, `.eq(user_id)` everywhere, 23505 → friendly.
- **Landable alone:** yes — importers added Step 4/5 (same wave).

### Step 4 — Route: library endpoints + selection-aware bytes resolution
- **Files:** NEW `app/api/templates/library/route.js`; EDIT `app/api/templates/default/route.js`.
- **New route** (`runtime="nodejs"`; `getUser()`→401; `userId` ALWAYS from session, never body — reuse the `app/api/templates/default/route.js:32-35` idiom; `VALID_KINDS=['resume','cover']`, `kind='email'`→400):
  - `GET ?kind=` → `{ templates: [...] }` via `listTemplates`.
  - `POST multipart { file, kind, name }` → validate kind; **reject non-docx bytes (NEW GUARD) → 4xx** (see §3.3 below); `registerTemplate(...)`; on success **`setSelection(user,kind → row.id)` (P1)**; return `{ row }`. On `registerTemplate` error → 4xx/500 with `{error}`.
  - `DELETE ?id=` → `deleteTemplate`.
- **`.docx`-only server guard (NEW, structural per OR-2):** the route must reject a non-docx upload by BYTES, not just by the client gate. A `.docx` is a ZIP → first bytes `PK\x03\x04` (`0x50 0x4B 0x03 0x04`). Check: `file.name` ends `.docx` AND the first 4 bytes are the ZIP magic; else 400 `{ error: "Templates must be .docx files." }`. (Extension alone is spoofable; magic-bytes alone rejects empty/renamed files. Both, loudly — because a non-docx row would later be silently skipped by `isDocxResume` at the override and render native output with no error.)
- **Edit to `app/api/templates/default/route.js`:** the **only** behaviour change — `GET ?kind=&bytes=1` calls `getActiveTemplateBytes` (Step 2) instead of `getDefaultTemplateBytes` (`route.js:47`). Everything else (POST reserved-name promote, DELETE, the non-bytes GET `hasDefault`) UNCHANGED. This is what makes the client resolver selection-aware **without touching the client** (F9, §4.2).
- **Verifiable:** route unit tests (§4): list/register/delete; non-docx → 4xx; register sets selection; `default` route bytes path returns `selection ?? reserved ?? 404`.
- **Landable alone:** yes — the new route is a Next.js entry; the default-route edit is behaviour-compatible when no selection exists (falls back to reserved, = HEAD).
