## Findings (ranked)

### F-A (SAFETY, verdict-driving) — the `coverage.complete===false` partial-review state is entirely unhandled; C17 "No issues flagged" violates N106 AC-17 on every slice-1 clean review
**Location:** §5.8 band states; C17 (line 423); C20 no-review; UX-26; UXR-1 (§12).
**Failure.** The UX was authored at r1 before N106 AC r2 added `coverage`. It has NO state for a review that ran but is PARTIAL. Its two "clean-ish" states are:
- `fresh, nothing flagged` → C17 "No issues flagged. The automated review is not a guarantee…"
- `no-review` → C20, keyed on `ideal.review absent/null`.

N106 AC-17 (SAFETY usage contract): a consumer presenting "no weaknesses found" when `coverage.complete===false` is FORBIDDEN; the consumer MUST distinguish a COMPLETE review from a PARTIAL one and require `complete===true` before any clean verdict. C17 "No issues flagged" is exactly the forbidden clean verdict, and the generic caveat ("not a guarantee") is NOT a partial-coverage indicator.

This is not an edge case. Per N106 AC-8 and AC-10, `employer-plausibility` and the full semantic depth of `unsupported-authority`/`consistency` are **second-slice deferred**; the first-slice reviewer that N105 consumes sets `complete:false` on every invocation, including the gemini "full" path. So in slice 1 the "fresh, nothing flagged" C17 state is **unreachable correctly** — every time it would render, it is an AC-17 violation. N105's `no-review` (keyed on `review` null) does not cover it: the N106 contract always returns a `review` object with `coverage`; `complete===false` means the review DID run (so C20 "did not run" is also wrong copy for it).

Compounding: **UXR-1 (the orchestrator-join list) does not forward `review.coverage`** — it names per-flag `excerpt` and `review.dropped`/`counts` only. The field cannot reach the client as written.

**Required 1c addendum (two parts):**
1. UXR-1: the orchestrator must forward `review.coverage` (at minimum `complete`, `engineMode`, `evaluatedCategories`) to the client.
2. §5.8 + `idealBandState` must gain a `partial` state read from `coverage`: the zero-flag clean copy (C17) renders ONLY when `flags` empty AND `coverage.complete===true`; when `complete===false` the band names that the review is partial (which checks did not run — e.g. employer plausibility, deeper authority/consistency), per AC-17. UX-26's word-sweep ("never verified/safe") extends to forbid "No issues flagged" while `complete===false`. The `thin` (C21) and `no-review` (C20) states stay distinct from `partial`.

### F-B (SAFETY, verdict-driving) — OC-2 resolved to PANEL-ONLY, but the UX is built end-to-end on an inline in-bytes marker; the reconciliation re-opens the AC-4 hole §5.4 existed to close
**Location:** §5.4 (whole section), C18 (line 424), UX-22, §4.7 ("Inline unverified markers inside that text" rows), §5.1 item 1, M-table interplay.
**Failure.** The owner resolved OC-2 to panel-only (no inline `[unverified — confirm before use]` text in the document). The UX r1 chose the OPPOSITE (§5.4 "The unverified marker travels INSIDE the application-ready file"; §11 lists OC-2 as still-open, recommending inline). Everything in §5.4 is predicated on that marker: the live `countMarkedLines(text)` count, the warning-token preview highlight, Tier A resolution ("delete the bracketed text"), Tier B per-row strip/delete, C18, UX-22, and the §4.7 "markers kept across reload" rows. Under panel-only, none of that machinery is valid — there is no bracket in the text to count, highlight, or delete.

The reason the 1c seat gave for inline (§5.4 items 1–3) is a genuine AC-4 hazard that panel-only reintroduces: the application-ready résumé is persisted like any résumé (U11, `page.js`:2004) and `handleTailorJob` downloads it **immediately** (U11, :2066-2076), while the review panel is session-only (D-14). A panel-only flag therefore leaves a flagged claim sitting in the saved/downloaded `.docx` as a **plain bullet** after reload or on the immediate-download path — the exact AC-4 failure ("never emitted as a plain truthful bullet").

**OC-2 panel-only reconciliation (the answer the brief asks for).** The clean reconciliation is NOT "emit the span with no marker" (that is the AC-4 hole) but **drop flagged spans from the emitted bytes and surface them only in the panel** (as "confirm / could not verify"), alongside the existing "Left out" dropped group. Then:
- Nothing ships as a plain unverified bullet → AC-4 "never a plain truthful bullet" holds on every egress, reload-proof.
- Nothing writes flag text into the document bytes → reinforces OD-4's clean-document rule. **Confirmed: after dropping §5.4's inline marker, the inline marker is the ONLY in-bytes flag text in the design** (the HYPOTHETICAL distinction is filename-only, M1/M3; the banner M2 is UI; an in-document label is explicitly not done, OD-4). So panel-only yields fully clean bytes.
- **Structure consequence to escalate:** D-6b currently feeds `recomposeFromSpans(layout, [...kept, ...flagged])` — flagged emitted into bytes. Under panel-only, recompose must emit `kept` only; `flagged` and `dropped` both stay out of bytes and surface in the panel. This is a D-6b/§1 structure note, not a 1c-local fix; the orchestrator must route it.
- The band "N to confirm" count can no longer be the text-marker count (§5.4); it becomes the panel flag count (spanId-based). The 1c addendum must restate the resolution model (Tier A "edit mode delete the bracket" is gone; resolution is panel-driven or by editing the bullet the panel points to).

### F-C (MEDIUM) — the silent-auto-download closure (hazard 2.3 / UXR-6) is under-specified for the chip and feed paths, which today only download and never open a preview
**Location:** §2.3; §4.1 "delivery must surface them"; UXR-6; U11.
**Failure.** §2.3 closes the silent-download hazard by saying single-job Ideal "is delivered by OPENING THE PREVIEW, not by silently downloading." But U11 (first-hand in the UX) establishes that `handleTailorJob` (chip) and `handleTailorFeedPosting` **download immediately and never open the modal**; only the URL flow opens the preview (`finishByOpeningPreview`, URL-flow only). So "deliver by opening the preview" is a **net-new behavior** on those two entry points, not a `skipDownload` flag flip. The design names skipping the download but does not specify the preview-open mechanism for chip/feed Ideal results. If unspecified, the implementer either (a) suppresses the download and leaves the Ideal result with **no surface at all** (the hypothetical, the band, and the unresolved-quals list never appear — AC-13 failure), or (b) leaves the immediate download in place (hazard not closed). The plan input must say: chip/feed Ideal flows must both suppress the download AND route to the preview (generalize `finishByOpeningPreview`, or equivalent), opening on the Application-ready tab.

### F-D (MEDIUM, cross-seam) — OC-3 resolved to PREFIX, but the structure the UX displays still inserts the marker as a SUFFIX
**Location:** M3 (banner shows the file name read-only), M4 (download button), UX-15; vs design D-8 / §6 `ensureHypotheticalMarker` ("inserts `[HYPOTHETICAL]` before the extension").
**Failure.** OC-3 is resolved to prefix (prefix survives file-picker/mail-client truncation; a suffix can be hidden). The structure's `ensureHypotheticalMarker` places the token as a suffix before the extension. The UX displays this name read-only in the banner (M3) and on the download button, so a truncating file picker could hide the marker — the exact risk the prefix resolution addresses. UX-15's sweep is position-agnostic (`/HYPOTHETICAL/i` anywhere), so it would pass either way and will NOT catch the regression. The plan must update `ensureHypotheticalMarker` to a prefix and the UX must display/assert the prefixed name. Primarily a structure addendum (D-8), surfaced here because the UX is the surface that renders it.

## V. Verified SOUND first-hand (the brief's NOT-VERIFIED items)

- **Slider a11y fix (U4) is real, not an SSR-probe artifact.** `ApplyingControls.js`:187-199: `<label htmlFor="aggressiveness">` + `<Slider id="aggressiveness">`. MUI spreads `id` onto the Slider root `<span>`, not the inner `<input type=range>`; a `<label for>` on a non-labelable span names nothing, and the label itself has no `id` to be referenced. The input thus has no accessible name — matching U4. The probe's positive control (adding `getAriaValueText`+`aria-labelledby` DID land the attributes on the input) validates the instrument. L3's fix (label gets an `id`; input named via `aria-labelledby`/`slotProps.input`; per-stop `getAriaValueText`) is the correct, real remedy.
- **422 refusal path is coherent.** `page.js`:1949/:2211/:2473 all `throw new Error(payload.error||…)` on `!response.ok`; :2214/:2476 fall back to `payload.result?.trim() || "No output returned from Gemini."`. A 422+`{error}` therefore fails CLOSED via the existing throw in every client, while a 200 would be stored as a fake "No output returned" result. The design's 422-not-200 choice (§3.2) is correct and load-bearing.
- **`visibleScopes` phantom-tab fix is real.** `DocumentPreviewDialog.js`:595 renders `SCOPES.map` with `disabled`+`(none)` labels; a static `hypothetical` in `SCOPES` would render a disabled "Hypothetical (none)" tab in every level-1-5 preview (AC-17 breach). D-10/§4.2 (dialog iterates mount-supplied `visibleScopes`, default `LEGACY_SCOPES`) closes it; UX-13's mutant (default→`SCOPES` reds) is the right pin.
- **False `other-version` fix is real.** :2214 stores `payload.result?.trim()`, so a raw `===` against the untrimmed `ideal.applicationReady.result` would report `other-version` on a FRESH run and wrongly demote the tab to "Resume" + hide the review. §5.8/UX-26's normalize-both-sides (trim, CRLF→LF) with a raw-`===` mutant is the correct closure.
- **OC-1 consistent.** §2.3/§11/C5: every Ideal run is `scope=resume`; cover/email untouched (U12). Matches résumé-pair-only.
- **Hazard closures (Revise/Focus/Framing §4.6; CL-wipe UXR-2; false-other-version 5.8) are real as designed**, each resting on a named mount/code change (UXR-5 nulls the three callbacks keyed on `entry.ideal`; UXR-2 adds an explicit Ideal branch to `handleTailorFeedPosting`). The Focus/Framing closure correctly keys on `entry.ideal`, not engine, so a post-run switch to embedded cannot resurface them.
- **Minimize-clicks (AC-15) and app-vs-chat (AC-16) are satisfied with evidence**, not merely asserted: §1 click-cost table (both documents, 0 extra) and §9 REMOVAL-test mapping (each advantage → a failing-on-removal AC).
