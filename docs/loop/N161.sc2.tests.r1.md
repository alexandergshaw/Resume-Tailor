## The load-bearing finding the arch MISSED (escalation for the orchestrator)

The arch §3.3/§3.4 says carry `codingSolution` onto the entry "exactly like `pageSources`". That is **necessary but NOT sufficient.** A detected coding answer carries **no `points`** (SC-1 / AC-11 REPLACE; route returns `{ codingSolution, type }` with no `points`). The ONE cache-admission gate every reveal funnels through — `answerGrounding.js:114 if (points.length === 0) return null;`, reached by the live hook directly and by practice via `cachedSampleAnswerFor` → `cachedAnswerFor` — **rejects a pointless entry.** `pageSources` rides an entry that also has points, so it is a HIT; a coding entry has no points, so it is a MISS and every reveal refetches. **AC-8 ("survives a reveal→hide→reveal of a cache HIT" + "cache-reuse (live)") cannot hold until that gate is relaxed to admit an entry whose points are empty but which carries `codingSolution`/`codingFallback`.**

The implementer must do this IN ADDITION to carrying the field. `answerGrounding.js` is **not in the arch's SC-2 file list** ({useDraftAnswer, useSampleAnswer, sampleAnswerState}). Two options, both proven to turn all reds green:
- relax the gate once in `answerGrounding.js:114` (`&& !entry.codingSolution && !entry.codingFallback`) — cleanest, one line, shared by both hooks (this is what the reference used); OR
- confine to SC-2 files: a coding-aware hit branch in `useDraftAnswer.js` + `cachedSampleAnswerFor`.
The tests pin the **observable** contract (a coding entry hits and replays), leaving the choice open.
