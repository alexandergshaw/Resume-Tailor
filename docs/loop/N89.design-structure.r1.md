## 1. The state model this fix turns on (revised from AC §1)

Two independent axes: **has faithful engine docx bytes** (splice source) and **is the letter
rebuildable from a template** (line source). The refusal gate today conflates them.

| Shape | engine bytes resolve? | rebuildable? | Strategy | Notice/outcome |
|---|---|---|---|---|
| A. Byte engine (embedded/external), or a splice already persisted | yes | (irrelevant) | **splice** (unchanged) | persisted / session-only |
| A′. Byte engine, letter already hand-edited | yes | yes | **lines** (text-only, splice skipped on purpose) | HAND_EDITED_NOTICE (unchanged) |
| **B. Gemini + template available** (owner's bug) | no | yes | **lines** (NEW) | LINE_REBUILD_NOTICE (new) |
| C. no bytes, not rebuildable (residual) | no | no | **refuse** | today's `NO_ENGINE_BYTES_REASON`, unchanged; dissolved by Part 2 |

"Rebuildable" (`canRebuild`) evolves across the two parts and is the discriminator AC-9 demands:
- **Part 1:** `canRebuild = an in-session cover template File is present` (`coverLetterFile`).
- **Part 2:** `canRebuild = in-session File present OR the entry carries a resolvable stored
  template path` (`entry.coverLetterTemplatePath`).

The owner's reported bug (#76 fresh `/api/tailor`, 53 s = the LLM/Gemini engine) is Shape B with the
File in session — fixed by Part 1 alone. The reloaded case becomes Shape B (not C) once Part 2 has
stored the template.

## 1.3 The single strategy selector (make the wrong branch impossible — AC-5)

To stop the two sibling functions drifting (AC §3), route both through **one** module-scoped pure
function in `useCompanyResearch.js` (NOT a new export — see §4 census):

```
// Pure. The one place the three-way branch is decided, so acceptFacts and
// autoInsertFactsForJob cannot diverge. splice and lines are mutually
// exclusive by construction on hasCoverBytes.
// @param {{hasCoverBytes:boolean, canRebuild:boolean, coverAlreadyEdited:boolean}}
// @returns {"splice" | "lines" | "refuse"}
function coverFactStrategy({ hasCoverBytes, canRebuild, coverAlreadyEdited }) {
  if (hasCoverBytes) return coverAlreadyEdited ? "lines" : "splice";
  if (canRebuild) return "lines";   // Shape B
  return "refuse";                  // residual C (today's behaviour)
}
```

Load-bearing invariant this creates (the property a reviewer applies to a DIFF): **every call to
`applyCoverDocxEdits(` and every assignment of `coverLetterDocxB64` from a splice result must sit
inside a `strategy === "splice"` block.** If a diff ever puts a splice or a `coverLetterDocxB64 =
spliced.docxB64` under the `"lines"` branch, the byte engines regress. This is the mechanical check
for AC-5's "bytes present ⇒ splice, absent ⇒ lines, mutually exclusive."

I recommend **not** exporting this helper (keeps the census pinned; see §4). If the TDD seat wants a
direct unit test of the three-way table, it may instead be exported from
`lib/acceptedFacts/factInsertion.js` (already a production+test-referenced module) — but that adds
one exported symbol and moves `TEST_REFERENCED` 364 → 365 (`exportReachability.sweep.test.js:688`),
which the implementer must then re-pin. AC-5/AC-6 already cover the behaviour through the hook rc
tests, so the non-exported form loses no coverage.

# PART 2 — persist the uploaded template (dissolves Shape C in any session)

## 2.1 Ruling: reuse N64's vehicle; NO new migration

**Decision: persist the uploaded cover-letter template as a `public.resume_templates` row
(`kind = 'cover'`) and record the pointer on `public.applications.cover_template_id` /
`cover_template_label` — the columns N64 already landed (`20260930000000_n64_saved_templates.sql`).
No new migration is authored.**

Why N64 fits (answering the brief's explicit question):
1. **It was built for exactly this.** N64's header: "saved formatting templates for resumes and
   cover letters," storage at `${user_id}/templates/${id}.docx` in the existing `resumes` bucket
   (`:101-103`), `kind in ('resume','cover')` (`:133`). It is currently **unwired** — grep for
   `resume_templates` / `cover_template_id` across `hello-world/**/*.js` returns **zero** production
   references (instrument: Grep, root `hello-world`, glob `*.js`; canary: the same pattern matches
   the migration `.sql`). So there is no live machinery to be "parallel" to; Part 2 *is* the first
   consumer N64 anticipated.
2. **Provenance already lives on `applications`, which survives fact acceptance.** N64 put the
   template pointer on `applications` (not `generated_cover_letters`) precisely because
   `accept_application_facts` re-inserts a new `generated_cover_letters` row on every accept and only
   repoints `cover_letter_id` (`20260928000000_...sql:104-115`; N64 header `:8-22`). A template path
   on `generated_cover_letters` would be NULLed on the next accept unless threaded through the RPC on
   every call — fragile. `applications.cover_template_id` is structurally safe.
3. **No migration = no production-schema risk.** A simpler `applications.cover_template_path` column
   would need a new migration on `applications` — the exact drift-prone table N64's header spends 90
   lines warning about, and it would auto-deploy to production. Reusing N64's landed columns avoids
   that risk class entirely. This is the decisive factor.

The one tension, stated honestly: N64's unique index `(user_id, kind, lower(name))` (`:144-145`) is
designed for **user-curated, named** templates, not per-generation auto-capture. Consequence: keying
the row on the uploaded **filename** means a user with one cover template (the common case) gets one
row, upserted to the latest bytes; two *different* templates sharing a filename would collapse to one
row (job 1 would rebuild with job 2's formatting). **This is an inherited limitation of N64's own
model (you cannot save two same-named templates), not a new defect** — so reuse is consistent, not
lossy in a way a bespoke design would avoid. If the owner later wants per-generation isolation, that
is a migration to relax the constraint, filed separately. I flag this as the one place my ruling
trades a rare-case correctness edge for zero migration risk; the alternative (a new
`applications.cover_template_path` column, per-generation isolation, one migration) is a legitimate
call the owner could take instead — I recommend against it on the migration-risk ground above.

## 2.2 Write side — persist at generation time

New module **`lib/supabase/coverTemplateStore.js`** (production importer:
`lib/supabase/persistGeneration.js`; see §4 census). Contract:

```
// Persists the uploaded cover-letter template as a resume_templates row
// (kind 'cover') and returns its pointer, or null on any failure — never
// throws (mirrors saveGeneratedCoverLetter's best-effort contract).
// Storage bytes go to the resumes bucket at `${userId}/templates/${id}.docx`
// (N64 convention). Upserts by (user_id, kind='cover', lower(name)); name is
// the File's own name.
// @param {SupabaseClient} supabase
// @param {{ userId: string, file: File }} params  file = the uploaded .docx template
// @returns {Promise<{ templateId: string, label: string } | null>}
export async function persistCoverTemplate(supabase, { userId, file }) { ... }
```

Steps (each best-effort, degrade to `null` = today's session-only behaviour):
1. Guard: `userId`, `isDocxResume(file)`. `label = file.name`.
2. `SELECT id FROM resume_templates WHERE user_id = userId AND kind = 'cover' AND lower(name) =
   lower(label)` (RLS: `auth.uid() = user_id` select policy, migration `:150-151`).
   - **Found:** `templateId = row.id`; re-upload bytes to `${userId}/templates/${templateId}.docx`
     with `upsert:true` (freshens formatting); optionally `update updated_at`.
   - **Not found:** `INSERT (user_id, name=label, kind='cover', storage_path='')` RETURNING id
     (two-step id-then-path, matching `saveGeneratedCoverLetter.js:37-58`); upload bytes to
     `${userId}/templates/${id}.docx`; `UPDATE storage_path` to that path.
3. Bytes source: `await file.arrayBuffer()` uploaded directly (Supabase storage accepts
   ArrayBuffer/Blob), `contentType` = the docx MIME. No base64 round-trip needed on the write side.
4. Return `{ templateId, label }`.

The upload/fetch of raw bytes could alternatively be factored beside `coverDocxStore.js`; I place
the row+path logic in `coverTemplateStore.js` because it also touches the `resume_templates` table,
which `coverDocxStore.js` does not.

**Wiring into generation (`lib/supabase/persistGeneration.js` + `app/page.js`):**
- `persistGeneratedDocuments` (`persistGeneration.js:43-110`) gains an optional param

  `coverLetterFile` in scope (they read it at `:1952, :2205, :2467`). Each passes

## 2.4 Part 2 discriminator generalization (AC-9, Part 2)

In the hook, `canRebuild` becomes:
`canRebuild = hasInSessionTemplate || (typeof entry.coverLetterTemplatePath === "string" &&
entry.coverLetterTemplatePath.length > 0)`.
Cheap (no fetch) — presence of the path string is the gate; a path that fails to fetch at render
degrades to the existing "Upload your cover letter template" download error (`docx.js:764`), a rare
residual, never a silent blank doc. This is what turns a reloaded Gemini letter from Shape C into
Shape B.
