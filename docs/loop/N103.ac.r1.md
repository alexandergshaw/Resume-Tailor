# Acceptance criteria — N103: an adversarial-review button in the preview/edit modal AND in the Ask-AI chat — r1

Seat: AC (1). Round: r1. Artifact only. No source edited, no git writes.

**What N103 is.** A one-click control that runs an ADVERSARIAL REVIEW of the current document — in the preview/edit modal (the document shown) and in the Ask-AI chat (the conversation's current résumé/CL artifact) — and surfaces the shared reviewer's findings. N103 is a **CONSUMER** chunk: it grows NO analyzer, NO span-minter, NO presentation table, and NO complete-vs-partial rule. All four already exist and are verified. N103 wires them to two surfaces.

**This is the point of the chunk (token efficiency): consume, don't duplicate.** Every reuse below was re-read first-hand this round and is live on HEAD:

| Primitive | Module (verified present this round) | Role for N103 |
|---|---|---|
| The ONE analyzer | `lib/review/reviewDocuments.js` → `reviewDocuments(input, {judge?})` | run the review; **no judge** on the default path |
| Span minting | `lib/llm/ideal/spanDocument.js` → `decomposeToSpans(result, resultLines, {contextKeyOf})` (mints `s1,s2,…`, ids never derived from text) | turn the current document into `spans:[{id,text,section,contextKey}]` |
| Complete-vs-partial rule | `lib/review/reviewVerdict.js` → `reviewVerdict(review)` ⇒ `{kind:"none"|"partial"|"complete", missingChecks, checkedChecks}` (fails CLOSED) | decide whether any clean copy is permitted; name unchecked categories |
| Flag presentation | `app/components/preview/ReviewFlagsPanel.js` + `lib/review/flagPresentation.js` (`groupFlagsBySpan`, `presentFlag`, `checkLabel`, `CHECK_LABELS`, `TIER`) | render flags; render the partial notice |
| Reference consumer | `app/components/preview/IdealResultBands.js` (N105 step-8 UI) | the pattern N103 follows; its `coverageLine()` is the partial-notice precedent |

**The two surfaces (first-hand this round):**
- Modal: `app/components/DocumentPreviewDialog.js` (renders the shown `.docx` model; has `onAskAi`, per-scope `busy/notice/error`, `visibleScopes` which may include the N105 `hypothetical` tab).
- Chat: `app/components/ChatPanel.js` — **holds no tailored-document content today** (grep `tailored*|resumeText|coverLetter|resultLines` over `ChatPanel.js` → 0 hits). The chat's document context is assembled server-side in `lib/chat/applicationContext.js` from the `applications` array (`tailoredResume: resume?.content`). So the chat "current document" (AC-5) is **net-new client plumbing**, and that is the single highest-risk design decision in this chunk.

## 1. Scope

**FIRST SLICE = ALL of N103** (the dependency, N106, is built; N103 is small): the review control + results surface in BOTH the modal and the chat, running the **mechanical** reviewer (no judge, no key). There is no second slice of N103; the review "deepens automatically" (AC-9) when N110 lands, with **no N103 code change**, because the surfaces read `coverage` through `reviewVerdict`.

**OUT of scope (design must NOT build; verifier must NOT file as missing):**
- The LLM judge body and any LLM-category DEPTH — that is **N110**. N103 ships the mechanical floor only.
- N104 (weakness summary + "regenerate to fix") and N105's auto-rendered Ideal band — separate chunks. N103 adds an **on-demand** control; it does not replace or re-implement the N105 band.
- A second analyzer, span-minter, presentation table, or complete/partial rule — forbidden by AC-7/AC-8/AC-11.
- The exact wiring of where each surface *obtains* `posting.requirements`, `realMaterial`, and (chat) the current artifact — these are **bounded 1b inputs** (I1–I4 below). N103's ACs fix the OBSERVABLE behaviour and the safety invariants; 1b picks the plumbing within those bounds.
- Motion/animation of the loading state, and the app-vs-chat "why not a plain LLM?" removal AC — **1c/1e** concerns, noted, not authored here.
- Server routes / egress — the mechanical path is in-process (P6); N103 adds no network call.

**Cumulative-surface note (rule 6b).** N103 ADDS, in the **modal**, one review control plus an on-demand results region to a dialog that is already dense (tabs, framing/focus/spacing/version/Drive/Revise/Copy controls, the N105 Ideal band). It DISPLACES nothing. Two composite costs the 8b re-judge must weigh: (a) the control must not read as a seventh competing button — minimize-clicks (AC-9) keeps it to one action with a default; and (b) when the shown document already carries the N105 auto-band, the on-demand result must **reuse the same panel/verdict/vocabulary** (AC-7/AC-11) and must not double-render a second, differently-worded verdict for the same document. In the **chat**, N103 ADDS one control to a panel whose other AI features are Gemini-gated; the review being key-free (AC-9) is a legibility *gain* (it works on embedded, unlike salary/open chat), but the control must still say which document it reviewed (AC-5). The per-surface panel legibility lands in each surface's own 1c/8b judgement; N103's obligation to the composite is the single shared invocation path (AC-11) so both surfaces render ONE vocabulary.

## 2. Acceptance criteria

Run from PowerShell in `hello-world/`: `.\node_modules\.bin\vitest.cmd run <path>`. Instruments are jsdom renders of the two surfaces (both already have jsdom test harnesses: `DocumentPreviewDialog.*.test.js`, `ChatPanel.*.test.js`) plus pure-module tests. "Instrument: NEW" = must be built. Every corpus-scored assertion states its failable-row count.

### — HIGHEST-RISK ACs —

### AC-1 (SAFETY/USAGE, CONSUMER — inherits N106 AC-17) — Neither surface shows a clean verdict unless `reviewVerdict(review).kind === "complete"`
Both surfaces decide "may I say anything reassuring?" **only** by calling the shared `reviewVerdict` (P2) and treating `"none"` and `"partial"` identically for the purpose of clean copy. A surface MAY render a clean/"no weaknesses"/"no issues"/"looks good" verdict **only** when `reviewVerdict(review).kind === "complete"`. When the kind is `"partial"`, the surface MUST render a partial-review indicator that NAMES the unchecked categories (from `missingChecks` via `checkLabel`/`CHECK_LABELS`, the N105 `coverageLine` precedent, P5) and MUST NOT render any clean copy. An empty `flags` with `coverage.complete !== true` is PARTIAL, never clean.
- **Why "impossible" not "forbidden" (rule 4):** the clean-verdict branch is gated on `reviewVerdict(...).kind === "complete"`, not on `flags.length === 0`. A surface physically cannot reach clean copy from a mechanical-only result because `reviewVerdict` returns `"partial"` for it (P2: `engineMode==="mechanical-only"` is treated as contradicting any `complete:true`).
- **Instrument (NEW, per surface):** feed each surface a review with empty `flags` and `coverage:{engineMode:"mechanical-only", complete:false, evaluatedCategories:[4 floor cats]}` → assert (a) NO clean-verdict copy is rendered (sweep the result region's `textContent`, excluding `[data-quoted]` nodes per the `ReviewFlagsPanel` quoting convention, for "no weakness"/"no issues"/"looks good"/"all clear"/"clean"); (b) a partial indicator IS rendered naming ≥1 unchecked category label (e.g. `CHECK_LABELS` for `employer-plausibility` = "whether claims fit the employer"). Then feed empty `flags` + `coverage:{engineMode:"full", complete:true, evaluatedCategories:[all 7]}` → the clean verdict IS permitted.
- **Stub controls:** (i) a surface that renders "No weaknesses found" whenever `flags.length===0` (ignoring `coverage`) REDS the partial case — **this is the exact mutant N106 AC-17 named, discharged here.** (ii) a surface that hardcodes the partial banner always REDS the `complete:true` case (over-caution is caught too, so the field is not a dead always-partial signal).
- **RED on HEAD:** yes, by absence of the surfaces' result regions. The primitive side (`reviewVerdict`/`coverage`) already PASSES on HEAD — this AC's teeth are entirely on the consumer side, which does not exist. Stated plainly so this is not mistaken for a guard that passes today.
- **Failure direction (load-bearing):** presenting a mechanical-only (partial) review as a complete clean one — "reviewed, no problems" over a document whose authority/plausibility was never judged — is the exact "looks done, analyzed nothing" failure. Safe direction: require positive `kind==="complete"` before any reassurance.

### AC-2 (SAFETY) — The chat "current document" is a DETERMINATE, NAMED artifact; absent one, the review refuses, never reviews a substitute
Define, for the chat surface: **"the current document" = the most-recent tailored résumé or cover-letter artifact available to the conversation** (the pinned context's tailored document, else the latest tailored artifact the conversation references). The surface MUST (a) select it **deterministically**, (b) **name to the user which document it reviewed** (title/scope, so a verdict is never orphaned from its subject), and (c) when no tailored artifact exists, render the AC-10 "nothing to review" state — NEVER silently review a different or stale document and attribute the verdict to the current one.
- **Instrument (NEW):** with a conversation exposing TWO tailored artifacts (older A with a clean line, newer B carrying a planted `+300%` unverifiable-metric line) → the rendered result quotes B's line and its result region names B; a build that reviews A reds (differential: the quoted excerpt is A's, not B's). With a conversation exposing ZERO tailored artifacts → AC-10 state, no flags, no verdict. Failable rows: wrong-artifact (1) + none-present (1) = 2.
- **Bounded 1b input (I3):** the exact source of the chat's current artifact (pinned context vs a new "document in focus" field) and how its `resultLines` are obtained for `decomposeToSpans`. The SELECTION DETERMINISM, the NAMING, and the refuse-on-absence are fixed here; the field plumbing is 1b's, within these bounds.
- **RED on HEAD:** yes — the chat holds no document content today (P7), so there is nothing to select, name, or review. Stub: a build that reviews the first/any application in `applications` instead of the named current artifact reds the differential.
- **Failure direction (load-bearing):** reviewing document X while telling the user it reviewed the current document — a verdict (clean OR partial) attributed to the wrong subject — is the worst outcome; the safe direction is name-the-subject-or-refuse.

### AC-3 (SAFETY) — `authorityReference` is chosen by the reviewed document's KIND; a hypothetical is NEVER judged against `realMaterial`, a real doc's authority is NEVER presented as clean without it
For the document being reviewed, N103 sets `authorityReference` by kind (reusing the N106 AC-2 split at the consumer): a **hypothetical/ideal** draft (e.g. the modal's `hypothetical` tab) ⇒ `"internal-consistency"` and `realMaterial` is NOT consulted for its authority; a **real/application-ready tailored** document ⇒ `"user-material"`, judged against the user's real material. When a real document is reviewed and `realMaterial` is unavailable, the review fails closed per N106 AC-13 (flags authority claims as unsupported, or refuses) — it NEVER returns a result a surface can read as "authority claims all supported".
- **Instrument (NEW):** (a) review a hypothetical draft whose authority claim exceeds anything in a supplied `realMaterial` → NO `unsupported-authority` flag attributable to the real-material comparison (invariant to `realMaterial`, reusing N106 AC-2 fixture H). (b) review a real tailored doc with `realMaterial=null` carrying an authority claim → the result is NOT clean-complete and NOT silently clean for authority (AC-1 keeps it partial; N106 AC-13 keeps authority fail-closed). Failable rows: 2.
- **RED on HEAD:** yes, by absence. Stub: a surface that always passes `authorityReference:"user-material"` (reviewing the hypothetical against realMaterial) flags legitimate ambition → reds (a); a surface that drops the kind→reference mapping reds.
- **Failure direction (load-bearing):** on a hypothetical, flagging legitimate ambition as "unsupported" is the pre-split degeneracy; on a real doc, passing an unverified authority claim as clean is the fabrication-shipping direction. Both pinned; the mechanism (where `realMaterial` comes from per surface) is bounded 1b input I2.

### — REACHABILITY / MINIMIZE-CLICKS —

### AC-4 — The review control is reachable in the preview/edit modal, by accessible name, in ONE action with a default
A control with an accessible name clearly denoting an adversarial review of the shown document (e.g. `name: /review/i` and not colliding with existing modal control names) is present and reachable when the modal is open, and a SINGLE activation runs the review on the mechanical path — no intermediate configuration/engine-pick step is required before findings appear.
- **Instrument (NEW):** jsdom render of `DocumentPreviewDialog` (existing harness) with a shown document → `getByRole("button", {name: /review/i})` resolves and is enabled for a non-empty document; one `click` yields the result region (AC-6) with no interstitial dialog gating the run. Negative control: a build without the control fails `getByRole`.
- **RED on HEAD:** yes, by absence. **Failure direction:** a control that needs a config step or an engine switch before it runs violates minimize-clicks; the safe direction is one action, mechanical default.

### AC-5 — The review control is reachable in the Ask-AI chat, by accessible name, in ONE action with a default
As AC-4, for `ChatPanel`. The control is reachable when the chat is open, works on the **embedded** engine (no Gemini needed — unlike the chat's salary/open-chat features), and a single activation runs the review on the current document (AC-2).
- **Instrument (NEW):** jsdom render of `ChatPanel` (existing harness) with a current document present → `getByRole("button", {name: /review/i})` resolves and is enabled on `engine==="embedded"`; one click yields the result region. Negative control: no control ⇒ `getByRole` fails. Engine control: the button is NOT disabled with an "Offline · no AI" reason on embedded (contrast the existing embedded-gated chip).
- **RED on HEAD:** yes, by absence. **Failure direction:** gating the review behind Gemini (as if it needed a key) would make a key-free capability look unavailable; safe direction is enabled on embedded.

### — BEHAVIOUR: CONSUMES THE SHARED REVIEWER —

### AC-6 — Activation runs the shared `reviewDocuments` over spans minted by the shared `decomposeToSpans` from the current document, and renders real findings
In both surfaces, clicking the control decomposes the current document via `decomposeToSpans` (P3) and runs `reviewDocuments` (P1); a planted mechanical-floor defect in the document produces the corresponding flag, rendered through `ReviewFlagsPanel` (AC-7). The findings are a function of the actual document text, not a fixture.
- **Instrument (NEW, per surface):** plant `"Improved performance by 300%"` (no baseline) in the current document → after activation, a flag row appears with the `flagPresentation` label for `unverifiable-metric` (`"Figure cannot be checked"` on a real doc / `"Unsourced figure"` on a hypothetical) and the quoted excerpt is that planted line. **Differential (proves it is not hardcoded):** change the planted line's text/number → the quoted excerpt in the row changes to match. Clean control: a document with only concrete, baselined, distinct lines → no mechanical-floor flag row (and, per AC-1, a partial indicator, not a clean verdict). Failable rows per surface: 1 (planted) + 1 (differential) + 1 (clean control) = 3.
- **Stub controls:** (i) an inert button whose handler renders nothing reds the planted case; (ii) a handler that renders a canned/hardcoded flag list reds the differential; (iii) a handler that renders the raw document text instead of flags reds (no `flagPresentation` label present).
- **RED on HEAD:** yes, by absence. **Failure direction:** a control that appears to review but renders canned or empty output is the "looks done, analyzed nothing" failure at the UI; the safe direction is findings provably derived from the document's own spans.

### AC-7 — Flags render through the REUSED `ReviewFlagsPanel` + `flagPresentation`; N103 adds no parallel presentation
The findings surface renders flags via `ReviewFlagsPanel` (one row per span, tier groups, unresolved list) and labels/tiers from `lib/review/flagPresentation.js` — not a new panel or a new label table. The partial notice reuses `checkLabel`/`CHECK_LABELS`.
- **Instrument (NEW):** (a) a rendered flag row carries the stable `flagPresentation` label and tier grouping (e.g. `unverifiable-metric` on a real doc sits under the "Confirm before you send" group per `FLAG_PRESENTATION`), which a bespoke panel would not reproduce byte-for-byte. (b) A census over N103's OWN new files asserts no second flag-presentation table (no local `FLAG_PRESENTATION`/`CHECK_LABELS`/`presentFlag` clone; no second `component="blockquote"` flag renderer), canaried against the presence of the `ReviewFlagsPanel` import (so the instrument fires). Per `loop-traps-search`: assert the token near the import/usage, not a whole-file regex.
- **RED on HEAD:** yes, by absence. **Failure direction:** a parallel panel would drift from the other two consumers' vocabulary; one shared panel keeps the three consumers legible together. A clone that passes a shape check but duplicates the table is caught by the census.

### AC-8 (CENSUS) — N103 introduces NO second document-weakness analyzer and NO second span-minter
N103's own new file(s) contain no local analyzer (no keyword set-difference, metric regex, repetition/vagueness detector) and no local span-id minter; both surfaces reach the ONE `reviewDocuments` and the ONE `decomposeToSpans`. This mirrors N106 AC-16's single-analyzer census, extended to the span-minter because a surface that re-chunks the document its own way would break single-span containment (N106 AC-1).
- **Instrument (NEW):** a per-file census over N103's new module(s): assert zero local detector signatures (e.g. a `/\d|%|\$/`-style metric test, a `WEAK_OPENERS`-style lexicon, a keyword diff) and zero local id minting (`s${...}` / `crypto.randomUUID`-style id assignment on span-shaped objects), canaried against the known `reviewDocuments`/`decomposeToSpans` imports so the sweep is shown to fire (count both; both > 0 for the canary). **Behavioural backstop (not a source-only row):** the AC-6 differential already proves the rendered excerpt comes from `decomposeToSpans`' real spans; a build that re-chunks locally would mis-align the quoted excerpt and red AC-6.
- **RED on HEAD:** yes, by absence (no N103 file exists; the canary proves the instrument fires once it does). **Failure direction:** a second analyzer/minter forces the three consumers to diverge and defeats containment; one shared pair is the safe direction.

### — KEY-FREE, DETERMINISTIC, FUTURE-PROOF —

### AC-9 — The default path is mechanical (no Gemini key), deterministic, and deepens automatically when N110 lands
The default activation calls `reviewDocuments` with **no** `options.judge`, so (a) it touches no network and needs no key (P6); (b) it is deterministic across runs; (c) the partial/complete state is DERIVED from `coverage` via `reviewVerdict` (AC-1), never hardcoded — so when N110 wires a judge and `coverage` flips to `engineMode:"full"`/`complete:true`, the surfaces render the deeper review and permit the clean verdict with NO N103 code change.
- **Instrument (NEW):** (a) spy `globalThis.fetch` with a recording positive control (per `loop-traps-spec` egress rule) → assert zero calls during a default review; assert no import in N103's graph monkeypatches `fetch`. (b) Run the review twice on the same document → identical rendered flags. (c) Feed a `coverage` with `engineMode:"full"`/`complete:true`/all-7 → the surface permits the clean verdict (same code path, no literal "mechanical-only" string driving the UI). Failable rows: fetch (1) + determinism (1) + flip (1) = 3.
- **RED on HEAD:** yes, by absence. **Failure direction:** hardcoding "mechanical-only, partial" into the surface would (i) lie if a judge ever runs and (ii) couple N103 to the slice; deriving from `coverage` keeps it honest and future-proof. Over-claiming direction (hardcoding "complete") is caught by AC-1's partial case.

### — EMPTY / ABSENT INPUT —

### AC-10 — An empty/absent/whitespace-only current document fails CLOSED to an honest "nothing to review", never a clean verdict, never a crash
In both surfaces, when the current document is absent, empty, or whitespace-only (chat: no tailored artifact, AC-2; modal: an empty scope), activation (or the control's own availability) yields an honest "nothing to review" state: NO flags, NO clean/"no weaknesses" verdict, NO crash. "Nothing to review" (there was no document) is DISTINCT from "no weaknesses" (a document was reviewed and found clean) — the latter is forbidden here.
- **Instrument (NEW, per surface):** render with an empty/whitespace document → assert no throw; assert the result region (if any) shows the "nothing to review" copy and renders zero flag rows; assert it does NOT render clean-verdict copy. Failable rows per surface: 1.
- **Stub controls:** (i) a build that renders "No weaknesses found" on empty input reds (false-clean — the worst direction); (ii) a build that throws on `decomposeToSpans("")`/empty `drafts` reds (crash).
- **RED on HEAD:** yes, by absence. **Failure direction:** telling the user an empty/absent document is "clean" is a false reassurance; the safe direction is "nothing to review".

### — STRUCTURAL: ONE SHARED PATH —

### AC-11 (make-the-wrong-thing-impossible) — Both surfaces route through ONE shared review-invocation path; they cannot diverge in verdict logic or vocabulary
N103 exposes a single shared invocation helper — pure or near-pure — that: builds the request (`decomposeToSpans` → shape `drafts`/`posting`/`realMaterial`) → calls `reviewDocuments` → derives the verdict via `reviewVerdict`. Both the modal and the chat consume THIS helper and this helper's output; neither surface re-implements span-building, analyzer invocation, verdict derivation, or clean-vs-partial logic inline.
- **Why structural (rule 4):** AC-1/AC-3/AC-8/AC-9 are each a discipline that could be broken independently in two surfaces; routing both through one helper makes a divergence between the two surfaces *impossible to introduce without editing the shared helper*, where one test covers both.
- **Instrument (NEW):** (a) a unit test of the shared helper over a planted-defect document asserts it returns both the `reviewDocuments` result AND the `reviewVerdict` kind. (b) A census asserts both surfaces import and call this helper and that neither surface imports `reviewDocuments` or `decomposeToSpans` directly (the helper is the single chokepoint), canaried against the helper import. (c) The per-surface behaviour tests (AC-6) pass for both surfaces from the one helper.
- **RED on HEAD:** yes, by absence. **Failure direction:** two independent invocation paths drift (one honours `coverage`, the other forgets); one chokepoint is the safe direction. Bounded 1b input I5: the helper's exact signature and module home.
