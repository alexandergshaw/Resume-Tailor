## 1. The control (1c experience)

**Label:** `View/Edit`. Distinct from the existing text-only **Resume** button (`AppViewDialog`) and the desktop **View full**. "View/Edit" names what the modal actually offers (faithful render + inline edit + version history + download + Drive save) and reads correctly even when only a cover letter exists.

**Behaviour:** one click opens the rich modal (minimize-clicks — no intermediate menu, no confirmation). Opens to the **resume** scope when a stored resume is present, else the **cover** scope. The modal's existing resume/cover tabs let the user switch; no new tab UI.

**Placement (mobile card):** in the first action row, immediately after the **Resume** button and before **Download** (`ApplicationCard.js:182`). Rendered with `variant="outlined"` and `sx={TOUCH_TARGET_SX}` to match the siblings (keeps the 44px touch floor and the focus-ring system).

**Placement (desktop table):** the SAME control in the resume `<TableCell>` (`TrackingTab.js:743-757`), beside "View full"/the download control, but gated on document presence (§4) — not nested inside the `resume?.content ? … : "—"` block, so a cover-only application still shows it.

**Gating:** shown iff the application has a stored resume OR cover (§4). Hidden (not disabled) when it has neither — consistent with the conditionally-rendered JD/Resume/Download buttons already in the row, and avoids an inert control.

**Also add to AppViewDialog — RECOMMENDED (v1).** `AppViewDialog` is the text-view the current **Resume** button opens; a "View/Edit" action there lets a user escalate from read-only text to the rich editor without closing and hunting for the row control (minimize-clicks). Contract: a new prop `onOpenPreview(app)` threaded `page.js → TrackingTab → AppViewDialog`; a button in `DialogActions` (or beside the resume page) shown when `hasPreviewableDocs(dApp)`; on click it calls `setAppDialog({open:false,…})` then `onOpenPreview(dApp)`. `page.js` wires `onOpenPreview` to the SAME `openApplicationPreview` handler. Lower priority than the row control; if the plan defers it, the row control alone satisfies the owner request. Cost: two new props on the `TrackingTab → AppViewDialog` edge.

## 2. The open path (1b structure)

A new handler **lives in `page.js`** (it needs `tailoringMap`, `setTailoringMap`, `preview.openResumePreview`, `preview.previewScopeAvailable`) and is threaded down exactly like `openEditApplicationDialog`:

```
page.js  openApplicationPreview(app)
  → TrackingTab prop  openApplicationPreview
      → ApplicationCard prop  openApplicationPreview   (onClick)
      → desktop table row                              (onClick)
      → AppViewDialog prop  onOpenPreview              (recommended; same fn)
```

### 2.1 Handler contract (new, in page.js)

```js
// Opens the rich preview/edit modal for a tracking-table application, loading
// its stored resume + cover letter on demand so the modal is never empty.
// No return value; a no-op when the app has no stored docs.
function openApplicationPreview(app: MergedApplicationRow): void
```

Body (specified, not pseudo-optional):

1. `const positions = app?.positions || null;`
2. **jobId resolution:** `const jobId = positions?.external_id ? String(positions.external_id) : \`app:${app?.id}\`;`
   - When `external_id` is present this equals the key the rehydration effect uses, so an in-session entry is reused (§3b) and `resolvePositionId` resolves version history (§3c).
   - When `external_id` is absent, the synthetic `app:<uuid>` key is collision-free against real external-id keys; content still renders; version history simply stays hidden (resolve returns null). This is the sanctioned degraded path.
3. `const existing = tailoringMap[jobId];`
4. `const entry = rehydratedEntryFromApp(app, { existing, fallbackTitle: positions?.title || "" });` (§3a). If `null`, **return** (the control should not have been shown).
5. **Precedence guard (mirrors the effect exactly):** `const keepExisting = !!(existing?.result || existing?.status === "tailoring");`
   - If not keeping, write the built entry: `setTailoringMap((cur) => ({ ...cur, [jobId]: entry }));`
   - `const openEntry = keepExisting ? existing : entry;`
6. **Scope:** `const tab = preview.previewScopeAvailable(openEntry, "resume") ? "resume" : "cover";`
7. **Open** (note `opts.entry` — §2.2):
   ```js
   preview.openResumePreview(
     { id: jobId,
       title: openEntry.generatedJobTitle || positions?.title || "",
       company: positions?.company || "",
       description: positions?.description || "",
       url: app.application_url || positions?.url || "" },
     { tab, entry: openEntry },
   );
   ```

The modal body renders from `tailoringMap[jobId]`, which is populated by step 5 before `DocumentPreviewMount` re-renders (React batches the two `setState` calls in one commit; `loadPreviewModel` reads the fresh hook closure after that commit — `useDocumentPreview.js:412`). So the body is never empty.

### 2.2 One additive hook change (the only edit to `useDocumentPreview.js`)

`openResumePreview` reads the map **synchronously** for the tab decision and research warm-up (`:292,309`). In the same tick as step 5's `setTailoringMap`, that read is STALE (the write has not committed), so a cover-only application would open on the resume tab and research would not warm. Fix with a single additive fallback:

```js
// was:  const t = tailoringMap[job.id] || {};
const t = tailoringMap[job.id] || opts.entry || {};   // :292
```

- Backward compatible: every existing caller passes no `opts.entry`, so `tailoringMap[job.id] || {}` is unchanged (`openResumePreview` from StatusBar/screenshots, `finishByOpeningPreview`).
- It does NOT change what the body renders (that path already reads the fresh map); it only makes the initial tab + research warm-up correct on first open from a freshly-written entry.

**No other change to the hook, `DocumentPreviewMount`, or any preview prop.** This satisfies invariant §5.

## 3. The entry-presence edge (the load-bearing risk)

### 3a. Is every table row guaranteed a populated tailoringMap entry? NO — so load on demand.

The rehydration effect only populates `trackedJobs` and skips in-session entries (§0). A tracking-table row is `applicationData`, a different list. Therefore the control MUST load the app's stored `generated_resumes`/`generated_cover_letters` into the entry on demand before opening (step 4–5 above).

**Anti-drift structure (RULING):** extract the entry builder into one pure module used by BOTH the effect and the handler, so the on-demand entry can never diverge from the rehydrated one (prefer wrong-thing-impossible over absent-today).

New file `hello-world/lib/tracking/applicationPreviewEntry.js`:

```js
/**
 * Build the tailoringMap entry for an application's STORED generated docs,
 * byte-identical to page.js's rehydration effect (page.js:1317-1333).
 * Returns null when the app has neither stored resume text nor cover lines
 * (the same `!resumeText && coverLines.length === 0` guard the effect uses).
 * Pure; no React, no I/O.
 *
 * @param app  merged application row: app.generated_resumes {content,
 *   content_lines, docx_path}, app.generated_cover_letters {content,
 *   content_lines, docx_path}, app.positions {title}.
 * @param opts.existing     current tailoringMap entry for this job id, spread
 *                          UNDER the rebuilt fields exactly as `...(existing||{})`; default null.
 * @param opts.fallbackTitle title when neither existing.generatedJobTitle nor
 *                          app.positions.title is set (effect passes job.title).
 * @returns the entry object, or null.
 */
export function rehydratedEntryFromApp(app, { existing = null, fallbackTitle = "" } = {})

/** True iff rehydratedEntryFromApp(app) would return an entry — the show/hide
 *  predicate for the control. Pure. */
export function hasPreviewableDocs(app)
```

The returned object MUST be field-for-field the current `page.js:1317-1333` block (`status:'done'`, `downloaded:true`, `generatedJobTitle`, `result`, `resultLines`, `coverLetterResultLines`, `docxPath`, `coverLetterDocxPath`, `error:''`), with `generatedJobTitle` falling back to `fallbackTitle` last. `hasPreviewableDocs` returns `resumeText.length>0 || coverLines.length>0` using the SAME derivations.

The effect at `page.js:1292-1338` is refactored to call the helper (keeping its own `existing?.result || existing?.status==='tailoring'` skip and its `!app` skip):
```js
const entry = rehydratedEntryFromApp(app, { existing, fallbackTitle: job.title });
if (!entry) continue;
next[job.id] = entry; changed = true;
```
This is byte-identical in output.

**Checkable property (apply to a DIFF):** `rehydratedEntryFromApp`'s returned literal has exactly the keys and value-expressions of the pre-refactor `page.js:1317-1333` block, and the effect's `next[job.id] = …` now assigns the helper's result. A reviewer diffs the helper body against the removed inline block; a unit test asserts `rehydratedEntryFromApp(app)` deep-equals the fields for a representative row. This makes "the two builders drifted" a failing diff, not a latent bug.

### 3b. In-session vs stored precedence — RULING: in-session wins (stored fills only an absent/empty entry).

If `tailoringMap[jobId]` already carries in-session content (`existing.result`) or is mid-generation (`status==='tailoring'`), opening shows THAT content and the handler does not overwrite it (step 5). This is correct: in-session content is the latest the user generated or hand-edited this session; the stored app docs are an older snapshot. This mirrors the rehydration guard (`page.js:1298`) exactly — the two now make the same ruling for the same reason. Stored docs are loaded only when the entry is absent or has no `result`.

### 3c. positionId resolution — CONFIRMED, with a named degraded path.

A tracking-table row's application is persisted, so its `positions` row exists. When `external_id` is present, `jobId === String(external_id)`, and `resolvePositionId(currentUser, jobId)` finds the row → version history loads and the version control shows (`documentVersionLoad.js:13-26`). If it does NOT resolve — signed out, or `external_id` null (synthetic `app:` key) — `positionId` is null, `documentVersions` stay `{resume:[],cover:[]}`, the version control stays hidden, and the modal still renders the entry content (text or faithful docx). No new code is needed for the degraded path; it is the hook's existing AC-7 behaviour.

---

## 4. Disabled / hidden state — RULING: hidden when no docs.

The control renders iff `hasPreviewableDocs(app)` is true (stored resume text OR cover lines). When the app has neither, the control is NOT rendered — mirroring the conditionally-rendered JD/Resume/Download buttons (`ApplicationCard.js:177,180,183`) and avoiding an inert disabled control. This predicate is the SAME one `rehydratedEntryFromApp` uses to decide null, so the control is shown exactly when an entry can be built (handler step 4 can only early-return on a race where the row changed between render and click — safe).

Note: gating is on document PRESENCE, not on `canDownloadResume`. `canDownloadResume` (`ApplicationCard.js:69`) additionally requires an uploaded docx template (`resumeFile` + `isDocxResume`) because the DOWNLOAD rebuilds from that template. The PREVIEW does not need it — `buildPreviewBlob`/`loadPreviewModel` fall back to a plain-text model (`useDocumentPreview.js:416-423`). Gating the preview on `canDownloadResume` would wrongly hide it for a signed-in user whose template is absent but whose stored text exists. So the preview gate is strictly `hasPreviewableDocs`.

## 5. Invariants preserved

The control only (a) writes a `tailoringMap` entry via `setTailoringMap` (precedence-guarded) and (b) calls the existing `openResumePreview`. The single hook edit is the additive `|| opts.entry` fallback on line 292.

Therefore the modal's existing behaviour is untouched: version history (AC-2/4/6/7), scope tabs, inline edit + auto-save, download with the N83 live file-name override (`useDocumentPreview.js:506-540`, `resolveDownloadPayload`), Drive save, the N125 ideal bands (if rendered) — all driven by `resumePreview`/`tailoringMap`/`documentVersions` exactly as for a StatusBar or Generate-flow open. No new `DocumentPreviewMount` prop; no change to any existing opener's signature.

**Checkable property (apply to a DIFF):** (i) the only modified line in `useDocumentPreview.js` is `:292`, changed solely by inserting `|| opts.entry` between `tailoringMap[job.id]` and `|| {}`; (ii) `DocumentPreviewMount` has no prop added/removed; (iii) no existing call site of `openResumePreview` passes `opts.entry`. A reviewer greps `openResumePreview(` across the repo and confirms (iii), and diffs `useDocumentPreview.js` to confirm (i)/(ii).

## 7. Acceptance criteria (observable; jsdom unless marked BROWSER)

Test seams: ApplicationCard is presentational (assert it calls `openApplicationPreview(app)` and renders/hides the button); the handler + hook open path is a page/hook-level wiring test (render with the real `useDocumentPreview`, or assert `resumePreview` after invoking the handler); the helper is a direct unit test.

- **AC-1 (present when docs exist):** a row whose app has a stored resume renders a control named "View/Edit"; a row whose app has only a stored cover letter also renders it. (jsdom)
- **AC-2 (hidden when no docs):** a row whose app has neither a stored resume nor cover letter renders NO "View/Edit" control. (jsdom)
- **AC-3 (label distinct):** the control's accessible name is "View/Edit" and is not the existing "Resume" text-view button; both can coexist on a resume-bearing row. (jsdom)
- **AC-4 (opens to this app's job id):** clicking "View/Edit" results in `resumePreview.open === true` and `resumePreview.jobId === String(app.positions.external_id)` (and `=== \`app:${app.id}\`` when `external_id` is null). (jsdom)
- **AC-5 (entry populated at open):** after the click, `tailoringMap[jobId]` has `result`/`resultLines` when the app has a stored resume, and `coverLetterResultLines.length>0` when it has a stored cover — i.e. the modal is not empty. (jsdom)
- **AC-6 (scope: resume-if-present-else-cover):** `resumePreview.tab === 'resume'` when a stored resume is present; `=== 'cover'` for a cover-only app. (jsdom)
- **AC-7 (on-demand load when entry absent):** with `tailoringMap[jobId]` initially undefined, clicking populates it from `app.generated_resumes`/`generated_cover_letters` (via `rehydratedEntryFromApp`) before/at open. (jsdom)
- **AC-8 (in-session precedence):** with `tailoringMap[jobId]` already carrying `{result:'IN SESSION', …}` (or `status:'tailoring'`), clicking does NOT overwrite it; the opened content is the in-session entry. (jsdom)
- **AC-9 (helper fidelity / anti-drift):** `rehydratedEntryFromApp(app, {existing, fallbackTitle})` deep-equals the field set the rehydration effect produces for the same row; `rehydratedEntryFromApp` returns `null` and `hasPreviewableDocs` returns `false` for an app with neither resume nor cover. (jsdom/unit)
- **AC-10 (existing openers unaffected):** `openResumePreview(job)` called with no `opts.entry` behaves exactly as before (tab/research decided from `tailoringMap[job.id]`); no existing call site passes `opts.entry`. (jsdom + grep)
- **AC-11 (desktop parity):** the desktop table row shows "View/Edit" under the same presence gate (incl. cover-only rows) and invokes the same handler. (jsdom)
- **AC-12 BROWSER:** the faithful .docx render in the opened modal, the N83 live file-name on download, Drive save, and the N125 ideal bands render correctly — none of this is observable in jsdom (`parseDocxToModel` of a real template, actual download, Drive OAuth). These are a visible-browser / owner pass, not jsdom.
- **AC-13 BROWSER (optional, if AppViewDialog door is included):** from the text "Resume" view, the "View/Edit" action closes `AppViewDialog` and opens the rich modal for the same app. The open-path half is jsdom; the rendered docx is BROWSER.

**jsdom vs browser split:** AC-1…AC-11 and AC-13's wiring half are jsdom (render, click, state, handler args, helper equality, grep). AC-12 and AC-13's render half require a visible browser.
