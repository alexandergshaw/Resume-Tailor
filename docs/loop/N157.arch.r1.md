## 1. Settled owner decisions (binding — recorded verbatim, not re-opened)

- **D-8 Research source.** REUSE the existing grounded interview-research (IP3) pipeline; extend it,
  do NOT build a rival. 1b defines the exact seam (what the study-plan layer calls, what it receives).
- **D-5 Transport.** Because we reuse the existing pipeline, N157 adopts NO new transport and accepts
  NO new API Additional Terms. Use whatever the existing pipeline already uses. (Still mind the
  grounding-redirect trap if citation display is touched: `web.uri` is a vertexaisearch REDIRECT.)
- **D-2 Research budget.** MANUAL REFRESH ONLY. Research runs once when the plan is first created; the
  user taps a "Refresh research" control to spend again. No automatic re-research on every plan build.
  Cache the research result with the plan.
- **D-3 Customization knobs (ALL FOUR in scope).** (1) new-vs-review ratio, (2) remediation focus
  (user marks weak areas; plan weights them), (3) time budget / pace (hours-per-day or days-until-
  interview sizes & schedules the plan), (4) topic scope (include/exclude topic areas).
- **D-1/D-4 Persistence.** PER-APPLICATION, PERSISTED — one saved study plan per tracked application,
  in a NEW table with a migration + RLS (`auth.uid() = user_id` policy pattern). Walkthrough PROGRESS
  persists across sessions/devices. The migration must be self-contained and match the live patterns
  ([[schema-migration-drift]]).
- **Orchestrator rulings.** The tool is a NEW SECTION within the existing practice MODE
  (copilot `mode==="practice"` — modes, not literal tabs; the owner's "new tab" intent is honored as
  a new practice sub-view). A TRACKED APPLICATION is REQUIRED (company/role/stage grounding comes from
  it).

## 4. The D-8 research-reuse seam (the highest-leverage decision) — EXACT shape

**Decision: SC-A does NOT issue its own grounded `generateContent` call. It reads the two existing
persisted grounded artifacts and adapts them; (re)research is produced by TRIGGERING the existing IP3
generation path, never a rival client.** This is what satisfies D-8 ("reuse, don't build a rival") and
D-5 ("no new transport, no new Additional Terms") simultaneously, and it is the reuse branch the AC
explicitly provides for in **AC-N157-S4** ("satisfied by reuse … name which entry point").

### 4.1 Read seam (every plan build, no spend)

```
studyPlanEvidence.gatherEvidence(deps, { applicationId, userId }) -> Promise<EvidenceSet>
  deps = {
    readPrepPack = prepStore.readPrepPack,          // injected, defaulted to the real fn
    readDigest   = <application_digests reader>,     // injected; see §12 (reader not opened this round)
  }
```

- Calls `readPrepPack(supabase, {applicationId, userId})`, then `packStagesSnapshot(pack)` and
  `stageItemSources(provenance, snapshot)` / `stageItemLabel(...)` from `stageResearchView.js` to
  extract, per stage item: `{ text, url, publisherKey, publishers, sourced:boolean }`. **Redirect
  suppression is inherited for free**: `stageItemSources` already drops any
  `servesGroundingRedirect` host (verified, lines 230-233), so no vertexaisearch host can reach the
  evidence set (S2).
- Optionally folds in `application_digests.sources` for company-level facts (same redirect-safe
  treatment via `citationHref`).
- **Refusal-honest empty result (S3):** a pack with no research snapshot ⇒ `packStagesSnapshot`
  returns `null` ⇒ `EvidenceSet` is `{ complete:false, items:[], reason:"no-research" }`. Never
  "trusted by default."

`EvidenceSet` (the SC-A → generation contract):
```
{
  complete: boolean,                 // false ⇒ generation must flag the plan partial/unsourced (S6)
  researchedAt: string|null,         // carried from the snapshot
  postingFingerprint: string,        // for staleness (reuse the concept, §4.3)
  items: [ { topicHint, text, citations:[{url,publisherKey,publishers}], sourced:boolean } ],
  reason: null | "no-research" | "unsourced" | "needs-refresh"
}
```

### 4.2 Trigger seam (create + "Refresh research" only — the only spend, D-2)

On first create (no plan row) and on explicit "Refresh research", `app/api/study-plan/route.js`
invokes the **existing IP3 generation path** to (re)produce the prep pack / digest, which itself
re-researches the grounded digest. N157 adds **no** grounded transport. The exact IP3 entry point to
invoke (the `app/api/interview-prep/route.js` POST handler vs a server-callable orchestration in
`finishAttempt.js`) is **named but NOT confirmed invokable server-to-server this round** — see §12;
the plan seat must open `route.js`/`finishAttempt.js` and pick the server-reachable one. The `tools`-
nesting wire test that pins IP3's grounded digest call already exists and still covers the path taken
(S4's reuse clause); **no new wire test is owed unless the plan seat finds the trigger must issue its
own call**, in which case S1/S4 revert to the fresh-client branch and `companyFactsSource.js` is the
template.

### 4.3 Caching (D-2)

The generation step writes the `EvidenceSet` into `study_plans.cached_research` (JSONB) alongside the
plan, plus `researched_at` and `posting_fingerprint`. Subsequent plan rebuilds (a knob change, SC-D)
reuse `cached_research` and spend nothing. Staleness reuses the **concept** proven in IP3
(`posting_fingerprint` + a researched-at stamp), **not** the `packIsStale`/`packRenderState`
functions — those are still **noted UNIMPLEMENTED** in `prepContract.js:9-23` (confirmed this round);
N157 depends on neither.

## 5. The plan schema (SC-B) — persisted shape

`studyPlanSchema.js` is the frozen contract. `STUDY_PLAN_VERSION = 1`. Every reader normalizes;
unknown/malformed input degrades to an empty-but-valid shape (never throws), matching `normalizePack`.

### 5.1 `plan` (JSONB column `plan`)
```
{
  v: 1,
  engine: "gemini" | "external" | "embedded",           // S6 provenance
  provenance: {
    research: "complete" | "partial",                   // S6: never present partial as complete
    unsourcedTopicIds: string[]                          // topics with no corroborated evidence
  },
  modules: [
    {
      id: string,                                        // content-derived, stable (not an array index)
      title: string,
      topics: [
        {
          id: string,
          title: string,
          area: string,                                  // for D-3 knob 4 topic scope
          weak: boolean,                                 // D-3 knob 2 remediation focus (plan weights it)
          items: [
            {
              id: string,                                // content-derived, stable
              kind: "new" | "review",                    // D-3 knob 1 new-vs-review
              prompt: string,                            // drill front
              reveal: string,                            // drill back (Quizlet flip)
              citations: [ { url, publisherKey, publishers } ],  // provenance pointer to SC-A evidence
              sourced: boolean                           // false ⇒ model-prior, rendered "unsourced" (S3/S6)
            }
          ]
        }
      ]
    }
  ]
}
```
**Keys are content-derived, never array indices** — the walkthrough cursor and progress address items
by `id`, so reordering or regenerating the plan cannot silently resume at the wrong card
([[measurement-instruments]] index-vs-identity).

### 5.2 `progress` (JSONB column `progress`) — D-4 persistent, cross-device
```
{
  v: 1,
  cursor: { moduleId: string|null, topicId: string|null, itemId: string|null },  // resume point
  seen: { [itemId]: { revealedAt: string, grade?: "again"|"hard"|"good"|"easy", dueAt?: string } },
  startedAt: string|null,
  updatedAt: string|null
}
```

### 5.3 `knobs` (JSONB column `knobs`) — D-3, with working defaults (S12)
```
{
  v: 1,
  newReviewRatio: number,            // 0..1  DEFAULT 0.5
  weakTopicIds: string[],            //       DEFAULT []
  pace: { hoursPerDay?: number, daysUntil?: number },  // DEFAULT { daysUntil: 7 }
  topicScope: { excludedAreas: string[] }              // DEFAULT { excludedAreas: [] }
}
```
`DEFAULT_KNOBS` is exported so "a user who sets nothing still gets a usable plan" (S12) is a single
source of truth the create path and the controls both read.

### 5.4 `cached_research` (JSONB column) — D-2
The `EvidenceSet` of §4.1, verbatim, so a knob-change rebuild needs no re-read of the prep tables.

## 6. Migration sketch — `supabase/migrations/20261011000000_n157_study_plans.sql`

Self-contained, idempotent, matching the `application_digests` precedent (the simplest 1:1 table in
the tree). **Stamp `20261011000000` is later than the tree's actual latest `20261008010000`**
(verified §2). One table; no function; no second table.

```sql
create table if not exists public.study_plans (
  application_id      uuid primary key references public.applications (id) on delete cascade,
  user_id             uuid not null references auth.users (id) on delete cascade,
  status              text not null default 'partial',   -- 'ready' | 'partial' | 'unavailable'
  engine              text,                               -- S6 provenance
  plan                jsonb not null default '{}'::jsonb,
  knobs               jsonb not null default '{}'::jsonb,
  progress            jsonb not null default '{}'::jsonb, -- D-4 (same row; see §6 note)
  cached_research     jsonb not null default '{}'::jsonb, -- D-2
  posting_fingerprint text not null default '',           -- staleness basis (concept reuse)
  researched_at       timestamptz,
  created_at          timestamptz not null default now(),
  updated_at          timestamptz not null default now(),

  constraint study_plans_status_check
    check (status in ('ready', 'partial', 'unavailable')),

  -- S6 mirror of interview_prep_packs_ready_is_complete: 'ready' requires a non-empty modules array.
  -- CASE-guarded (not a bare `and` chain) exactly as position_glossaries / interview_prep do, because
  -- PostgreSQL does not guarantee left-to-right `and` evaluation and an unguarded jsonb_array_length
  -- on a non-array raises a type error instead of a clean constraint violation.
  constraint study_plans_ready_has_modules
    check (
      status <> 'ready' or (
        case when jsonb_typeof(plan #> '{modules}') = 'array'
             then jsonb_array_length(plan #> '{modules}') > 0
             else false end
      )
    )
);

create index if not exists study_plans_user_id_idx on public.study_plans (user_id);

alter table public.study_plans enable row level security;

drop policy if exists "study_plans_select_own" on public.study_plans;
create policy "study_plans_select_own" on public.study_plans for select using (auth.uid() = user_id);
drop policy if exists "study_plans_insert_own" on public.study_plans;
create policy "study_plans_insert_own" on public.study_plans for insert with check (auth.uid() = user_id);
drop policy if exists "study_plans_update_own" on public.study_plans;
create policy "study_plans_update_own" on public.study_plans for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
drop policy if exists "study_plans_delete_own" on public.study_plans;
create policy "study_plans_delete_own" on public.study_plans for delete using (auth.uid() = user_id);

grant select, insert, update, delete on table public.study_plans to authenticated;
grant all on table public.study_plans to service_role;
```

**§6 note — progress in the same row vs its own table (D-1 sub-question).** Recommended: **same row,
JSONB `progress`**, written only by `writeStudyPlanProgress` via a column-scoped update
(`{progress, updated_at}`), so a frequent progress tick never rewrites `plan`/`cached_research` and
never races a regeneration's content write. The alternative (a `study_plan_progress` child table) buys
independent write isolation at the cost of a second table and a join; it is worth it only if the owner
expects very high-frequency progress writes. **Flagged to the owner as a confirm, not re-opened.**

**Schema-drift caution ([[schema-migration-drift]]).** The migration is self-contained and FKs only to
`public.applications(id)` (its PK — confirmed by both `application_digests` and `interview_prep` FKing
to it). The live DB's known extra constraint `applications UNIQUE(user_id, position_id)` does not touch
`study_plans`. I cannot read the live project's actual RLS/CHECK state from here; the shape test (S7)
proves only that the declared SQL is internally consistent — see §12.

## 7. Store contracts (SC-B) — defence-in-depth (S8)

`studyPlanStore.js` mirrors `prepStore.js` exactly: injected `supabase` first arg, named projections
from `studyPlanContract.js`, never `select("*")`, never throws, **every read and write chains BOTH
`.eq("application_id", applicationId)` AND `.eq("user_id", userId)`** in addition to RLS.

```
readStudyPlan(supabase, { applicationId, userId })
  -> { plan, knobs, progress, cachedResearch, status, engine, researchedAt, postingFingerprint, error }
     (reads are client-safe: no server-only import, callable from the browser client like readPrepPack)

writeStudyPlan(supabase, { applicationId, userId, status, engine, plan, knobs, cachedResearch,
                           postingFingerprint, researchedAt })
  -> { written: boolean, error: string|null }
     plain UPSERT keyed on application_id; normalizes plan/knobs via studyPlanSchema before writing.

writeStudyPlanProgress(supabase, { applicationId, userId, progress })
  -> { written: boolean, error: string|null }
     column-scoped update of { progress, updated_at } ONLY; never rewrites plan/cached_research.
```

**S9 (identity off the wire).** `applicationId`/`userId`/`engine` are passed explicitly from the
mounted parent; **no `= ""` default on any id** (the exact `applicationId: posting?.id || ""` hazard
the copilot surface already carries at `CopilotClient.js:549,565` — the study path must pass a real id
and refuse when none is selected, since a tracked application is REQUIRED).

## 9. Walkthrough state model (SC-C)

A pure reducer over `(plan, progress, knobs)`; the component holds only the reducer state and the
debounced progress writer. States per item: `drilling(itemId)` → (user reveals) → `revealed(itemId)`
→ (user grades, SC-D) → next item chosen by `studyPlanSchedule.nextDue(progress, plan, knobs, now)`.

- **C1 structure/aria.** The step heading is a real heading at the correct level (no `h3→h6` skip;
  avoid MUI `subtitle2`→`h6`). Progress indicator is labelled. Next/Prev/Reveal are keyboard-reachable
  and in DOM order (reorder the rendered array, never CSS `order` — [[copilot-mobile]] WCAG 2.4.3).
- **C2 cold reveal.** `reveal` text is **absent from the accessibility tree** until the explicit
  reveal control is activated, and is **not** inside an `aria-live` region (role-drill precedent).
  Diff-check: the reveal panel is conditionally rendered on a `revealed` boolean, not merely visually
  hidden.
- **C5 resume.** D-4 is persistent, so a remount reads `progress` via `readStudyPlan` and resumes at
  `cursor` (addressed by `itemId`, not index). Test: mount parent, seed the store, assert resume.
- **C6 egress disclosure.** A notice naming what leaves the device (create/refresh sends company/role/
  posting text to Gemini) is present, over-states rather than under-states, and is **not** the block
  collapsed to shorten mobile scroll ([[copilot-mobile]] — shipped-twice failure).
- **C3 mobile.** `TOUCH_TARGET_SX`/`WRAP_ROW_SX`/`PHONE_PANE_SX` imported from `mobileSx.js`, not
  hand-rolled (no-copies sweep stays green).
