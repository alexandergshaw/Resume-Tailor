## 1. Decisions / contradictions routed to me — resolved

### P1 (I OWN). The switcher's home is the Materials section, as a "Template library" panel — NOT the preview modal.
Reasons, from the code: the selection is per-(user,kind) and GLOBAL, so a per-document modal control misrepresents its
scope; the modal's live HTML preview renders the model (`DocumentPreviewDialog.js:340,852`), not the formatting
template, so flipping the selection there changes nothing visible until the next download — a confusing no-op; and
the modal is Seam 4 (concurrent-edit hot zone, N151a §1) with a pinned button census (AC-C12, `DocumentPreviewDialog.js:876-882`).
The Materials section already OWNS template creation ("Add to template library", `ApplyingControls.js:393`), so the
library list belongs beside it — add → see list → pick active → delete is one closed loop. **Proof it works:** picking
a template writes the selection, and the already-shipped selection-aware default route (`default/route.js:49`) means the
NEXT generation/download/preview/Drive-save resolves the chosen bytes with no further wiring (the four surfaces are
untouched). See OR-B — the owner named the modal, so this is flagged for confirmation.

### P2 (I OWN). The server needs exactly two additive affordances; everything else reuses N151a.
(1) The list GET must also return the current selection so the panel can show which template is active. Chosen
mechanism: **extend `GET /api/templates/library?kind=` to return `{ templates, selectedId }`** (`selectedId` = the
explicit `template_selections.template_id`, or null). One place, atomic with the list, backward-compatible — the
shipped GET test asserts only `body.templates` (`route.test.js:183`), so the added field does not red it.
(2) Activating an EXISTING template needs a verb. Chosen mechanism: **a `PUT /api/templates/library` taking
`{ kind, templateId }`** that VERIFIES the template is the caller's own (a single `resume_templates` row read gated by
`id + user_id + kind`) BEFORE `setSelection`. The ownership check is a loud guard against a dangling/foreign selection
(a route is attacker-reachable; a foreign id would silently resolve to null bytes → native output — the exact silent
failure class). This keeps the shipped `templateSelectionStore.setSelection` UNTOUCHED (no second ownership read on the
register path, which just created the row). Rejected alternatives: a separate `/api/templates/select` route (more
surface for one upsert); overloading POST with a fileless `selectId` (muddies the register contract the N151a tests pin).

### OR-B (confirm — the owner named the modal). Recommend: N151b switcher → Materials; modal template switching → N151c.
If the owner wants switching INSIDE the edit/view modal, that is the N151c "re-render this document into another
template" capability — where the preview actually re-renders through the shipped `formattingTemplate` override
(N151 design §5) — not the N151b persistent pointer. Recommend keeping N151b off the modal entirely and delivering
modal switching as N151c. **Decision needed before Step 4 ships the panel's home.**

### OR-C (confirm — low stakes). No "clear to native" action this slice.
The shipped `setSelection` refuses `!templateId` (`templateSelectionStore.js:55`), so there is no store path to set the
pointer back to null short of DELETING a template. N151b's switcher picks AMONG existing templates and represents the
null state in copy, but offers no "use no template / app default" toggle. A user who wants native formatting without
deleting a template has no path. Recommend DEFER (a small `deleteSelection`/null-pointer verb is a clean N151c-era
add). Flagged so the AC/UX seat does not assume a clear button exists.

### OR-D (confirm — résumé-only, matches N151a OR-3). The panel shows `kind='resume'` templates only this slice.
Only résumé templates can be created today (N151a mark writes `kind='resume'`; no cover mark path). The hook + panel
are kind-parameterised so a cover switcher is a trivial later mount with no backend change. Recommend résumé-only.

## 3. Ordered steps — each independently landable and verifiable

> **MIGRATION POSITION: THERE IS NONE.** `template_selections` (stamp `20261008010000`) and `resume_templates` (N64)

### Step 1 — Route: list the current selection + add a select-by-id verb
- **File:** EDIT `app/api/templates/library/route.js`.
- **GET change (one field, backward-compatible):** after `listTemplates`, read the selection and return it:
  ```
  const selection = await getSelection(supabase, { userId: user.id, kind });
  return Response.json({ templates, selectedId: selection?.template_id ?? null });
  ```
  Import `getSelection` from `@/lib/document/templateSelectionStore.js`. `getSelection` is null-safe, so a missing
  substrate yields `selectedId: null` (the shipped GET test asserts only `templates` → stays green).
- **NEW `PUT` handler** (idiom identical to the file's existing handlers: `createClient()` → `requireUser` → 401; `userId`
  ALWAYS from the session, never the body):
  - Parse `{ kind, templateId }` (JSON body). `VALID_KINDS` check → 400; `!templateId` → 400.
  - **Ownership guard (load-bearing):** `supabase.from("resume_templates").select("id").eq("id", templateId).eq("user_id", user.id).eq("kind", kind).maybeSingle()`; if no row → `404 { error: "That template is not in your library." }`. This refuses a foreign/dangling id LOUDLY rather than letting it resolve to null bytes → native output silently.
  - `await setSelection(supabase, { userId: user.id, kind, templateId })`; on `{error}` → 500; else `{ ok: true }`.
- **Contract:** GET → `{ templates: [...], selectedId: string|null }`; PUT `{kind,templateId}` → `{ok:true}` | 4xx/5xx `{error}`.
- **Verifiable:** route unit tests (§7 T1-T2): GET returns selectedId; PUT sets an owned selection, rejects a foreign id (404), rejects bad kind (400), 401 unauth.
- **Landable alone:** yes — GET field is additive; PUT is a new verb; POST/DELETE untouched. The shipped `route.test.js` stays green (it asserts `body.templates` only, `:183`).

### Step 2 — Client glue: list / select / delete helpers
- **File:** EDIT `lib/document/templateLibraryClient.js` (add three exports beside `registerTemplateFromBytes`; same no-throw, `credentials:"include"`, `AbortSignal.timeout` idiom as `:25-31`).
- **Signatures:**
  - `listLibraryTemplates(kind) → { ok:true, templates, selectedId } | { ok:false, error }` — `GET ?kind=`.
  - `selectLibraryTemplate({ kind, templateId }) → { ok:true } | { ok:false, error }` — `PUT`, JSON body.
  - `deleteLibraryTemplate(id) → { ok:true } | { ok:false, error }` — `DELETE ?id=`.
  - Each: on network/abort → `{ ok:false, error }`; on `!res.ok` → `{ ok:false, error: body?.error || <fallback> }`. Never throws.
- **Verifiable:** unit tests the request method/URL/body shape and failure → `{ok:false}` (§7 T3).
- **Landable alone:** yes — importers added Step 3 (same wave).

### Step 3 — Hook: `useTemplateLibrary`
- **File:** NEW `app/hooks/useTemplateLibrary.js`.
- **Signature:** `useTemplateLibrary({ currentUser, kind }) → { templates, selectedId, loading, error, refresh, select, remove }`.
  - State: `templates: []`, `selectedId: string|null`, `loading: bool`, `error: string`.
  - `refresh()` — if `!currentUser`, clear to `{templates:[], selectedId:null}` and return; else `loading=true`, `listLibraryTemplates(kind)`, set `templates`/`selectedId` or `error`, `loading=false`. Guard against a stale response overwriting a newer one (a `cancelled`/req-id ref, as `useMaterialsLocker.js:42-50` does).
  - `select(id)` — optimistic `setSelectedId(id)`; `selectLibraryTemplate({kind, templateId:id})`; on `{ok:false}` revert + set `error`; then `refresh()` to reconcile.
  - `remove(id)` — `deleteLibraryTemplate(id)`; on `{ok:false}` set `error`; on success `refresh()` (the selection may have nulled via `ON DELETE SET NULL`, so `selectedId` is re-read, never assumed).
  - `useEffect([currentUser, kind])` → `refresh()` on mount and when either changes.
- **Verifiable:** renderHook/host-mount tests (§7 T4): refresh populates; select updates selectedId + calls PUT; remove calls DELETE + refetches; signed-out clears.
- **Landable alone:** yes — imported by the panel (Step 4) and page.js (Step 5), same wave.

### Step 4 — Component: `TemplateLibraryPanel`
- **File:** NEW `app/components/applying/TemplateLibraryPanel.js` (sibling of the existing `applying/*` section components, e.g. `ProfileListSection`).
- **Props:** `{ kind='resume', currentUser, library }` where `library` is the `useTemplateLibrary` result (mounted in page.js so a mark can refresh it — §Step 5).
- **Render (states, a11y) — [[minimize-clicks]], [[mui-a11y-traps]]:**
  - Wrapped in a `styles.fieldGroup` with a `<FormLabel component="legend">` / `styles.label` heading "Template library" and a one-line caption distinguishing it from the source résumé ("The formatting your tailored résumés are poured into. Add one from your materials below.").
  - `!currentUser` → "Sign in to save and switch templates."
  - `library.loading` → a small `CircularProgress` / "Loading templates…".
  - `library.error` → a `var(--danger)` line.
  - `templates.length === 0` → empty state "No saved templates yet. Use 'Add to template library' on a .docx material below."
  - else a **MUI `RadioGroup`** (`aria-labelledby` the legend; value = `selectedId ?? ""`), one `FormControlLabel`/`Radio` per template labelled by `template.name` (the radio's accessible name comes from the label text — NOT a Tooltip), `onChange={(e)=>library.select(e.target.value)}`. Each row carries a `Button` `color="error"` `aria-label={`Delete ${template.name}`}` → `library.remove(template.id)` (no confirm dialog — matches the materials "Remove" at `ApplyingControls.js:411`; a template is re-creatable by re-marking and deleting the active one just falls back).
  - **Null-state copy (OR-C):** when `selectedId` is null AND templates exist, no radio is checked and a caption reads "No template selected — new résumés use your saved default, or the app's standard formatting." (Honest: `selectedId` is the explicit pointer; the reserved-row fallback is not guessed.)
- **Verifiable:** real-parent MOUNT (§7 T5): the active template's radio is checked; selecting a different radio calls `library.select(id)`; a delete button calls `library.remove(id)`; empty/signed-out/null states render; group has an accessible name and each delete button a distinct one.
- **Landable alone:** yes — additive component.
