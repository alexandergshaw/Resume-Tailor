## 2. The value contract (AC-1, AC-3) — the derivation is the whole ballgame

The indicator is a **pure derivation** `indicatorModel(spacing)`; specifying it precisely is this
seat's core deliverable because a naive derivation prints the `null` → "1x/0pt" lie (AC §1).

**Input:** `spacing : { lineSpacing: number|null, paragraphSpacingPt: number|null } | null`.

**The applied predicate (the alignment that must not drift).** N96's "Custom" must mean exactly
"something is being applied", i.e. it must equal `applySpacingToHtml`'s own non-no-op condition
(`docxPreview.js:356,358`):

```
isApplied(spacing) === (spacing != null && (spacing.lineSpacing != null || spacing.paragraphSpacingPt != null))
```

- `isApplied === false` ⇒ **Default** state. Covers `null` AND the degenerate `{lineSpacing:null, paragraphSpacingPt:null}`
  object (which the transform also treats as a no-op). This is the AC-3 failure-direction guard: the
  indicator must never say "Custom" while the transform applies nothing.
- `isApplied === true` ⇒ **Custom** state (any single axis set counts — AC-3 partial-override row).

**Per-axis display text (never fabricate the unset axis):**

```
lineText  = spacing?.lineSpacing        != null ? `${spacing.lineSpacing}x`          : DOC_DEFAULT_PHRASE
paraText  = spacing?.paragraphSpacingPt != null ? `${spacing.paragraphSpacingPt}pt`  : DOC_DEFAULT_PHRASE
```

where `DOC_DEFAULT_PHRASE` is a source-fidelity phrase (e.g. "your document") and MUST NOT be a
number. A partial override `{lineSpacing:1.5, paragraphSpacingPt:null}` therefore reads Custom with
line "1.5x" and paragraph "your document" — never "0pt" (the same fabrication trap as the whole-null
case).

**Readout textContent contract (`data-testid="spacing-current"`):**

| `spacing` | State word | Readout text must CONTAIN | Readout text must NOT match |
|-----------|-----------|---------------------------|-----------------------------|
| `null` (or all-null) | `Default` | `Default` + a source phrase ("your document") | `/\b1(\.0)?x?\b\|\b0\s*pt\b/` (no fabricated numbers) |
| `{lineSpacing:1.5, paragraphSpacingPt:12}` | `Custom` | `1.5` AND `12` | — |
| `{lineSpacing:2, paragraphSpacingPt:6}` | `Custom` | `2` AND `6` (MUST differ from the 1.5/12 render — discriminator) | — |
| `{lineSpacing:1.5, paragraphSpacingPt:null}` | `Custom` | `1.5` and a source phrase for the paragraph axis | `/\b0\s*pt\b/` |

This single readout element satisfies **AC-1** (explicit numbers), **AC-3** (contains the distinct
`Default`/`Custom` word), and — because it is hosted in a live region (§4) — **AC-2 clause ii**
(announced on change). It is layered ON TOP of the existing `variant` highlight (AC-1 keeps the
highlight; the highlight is not removed).

## 3. The active-state contract (AC-2 clause i) — announced, not only drawn

Each preset control must expose a **machine-readable selected state on EVERY preset**, true on the
active one and **explicitly `false` on the inactive peers** (AC-2 canary rejects a scan that finds
the active one but never a false one).

**The predicate MUST be the identical expression the visual `variant` uses**, so the drawn state and
the announced state cannot drift (the N84 class — indicator drawn, not announced; and its inverse,
announced-but-not-drawn):

```
line preset p:  selected = (current.lineSpacing        === p.value)   // === SpacingControl.js:52
para preset p:  selected = (current.paragraphSpacingPt === p.value)   // === SpacingControl.js:68
```

Because `current = spacing || {}`, `spacing===null` yields `selected=false` for every preset — the
correct mapping (`null` is NOT "1x"). Render this as `aria-pressed={selected}` (a boolean, always
present) on each preset control.

**Widget choice is 1e's, not this seat's.** AC-2 pins the observable (`aria-pressed`/`aria-current`
with a false peer + announcement), not the component. `ToggleButtonGroup` sets `aria-pressed`
natively and is the low-risk shape (mui-a11y memory), but a `Button` with an explicit
`aria-pressed={selected}` also satisfies the observable. Either is acceptable to this seat provided:
- the attribute is present on **every** preset (true or false), never omitted; and
- the predicate is the same expression as the `variant`.

**mui-a11y trap (Tooltip-steals-name):** the only current `Tooltip` wraps the disabled-hint **Box
span** (`SpacingControl.js:76-80`), not a button, so no control's accessible name is stolen today.
1e MUST NOT wrap a preset **button** (or the reset button) in a `Tooltip` without giving it its own
`aria-label`, or the Tooltip title becomes the control's name and the preset label is lost.

## 4. The announcement seam (AC-2 clause ii) — **BLOCKER B-1**

The readout of §2 lives inside a **polite live region hosted INSIDE `SpacingControl.js`** (not in
`DocumentPreviewDialog.js`). Because the control re-renders whenever the `spacing` prop changes, and
the readout text is a pure function of `spacing`, a value change is a text change on an
already-mounted region — which is what a screen reader announces (F9 idiom).

**No `seq` nonce is needed** (unlike `CopyFeedbackStrip`, which forces a mutation on byte-identical
repeats): for spacing, identical readout text means the value did not change, so *not* re-announcing
is correct. This also satisfies AC-2's "announces on EVERY render (noise) fails" — the derived-text
region announces only on a real value change.

### B-1 (BLOCKER): the live region MUST NOT carry `role="status"`.

`SpacingControl` mounts at `DocumentPreviewDialog.js:748` — **earlier in document order** than
`DriveResultRegion` (~`:875`) and `CopyFeedbackStrip` (`:886`). Two landed suites key off the
**document-order-first** `[role="status"]`:
- `DocumentPreviewDialog.drive.test.js:239` — `document.querySelector('[role="status"]')` must be
  DriveResultRegion's node.
- `DocumentPreviewDialog.copy.test.js:538-558` — the first `[role="status"]`/`[role="alert"]` must
  lack `data-copy-status` and precede the copy strip's regions (the test titled "keeps the FIRST
  [role=\"status\"] in the document as DriveResultRegion's").

If `SpacingControl` adds `role="status"`, it becomes the **first** `[role="status"]` in the document.
Both suites would then **silently pass while measuring the wrong element** (SpacingControl's region
still precedes Close and the copy strip, and carries no `data-copy-status`) — the exact
"green while measuring the wrong element" corruption the copy suite's `:538` test exists to prevent,
defeated from a direction that test does not cover (a region *earlier* than DriveResultRegion rather
than the copy strip reordered before it). The screen-reader ordering guarantee those tests protect
would become false and undetected.

**Ruling:** the spacing live region uses `aria-live="polite"` and `aria-atomic="true"` **without
`role="status"`**. A bare `aria-live="polite"` element is a valid polite live region (announced by
screen readers); `aria-atomic="true"` restores the whole-region announcement semantics that
`role="status"` would have implied. It is selected in tests by its own `data-testid`
(`spacing-current`), never by role, so it never enters the `[role="status"]` lookups above.

**Diff-check (applies to any future edit of `SpacingControl.js`):** grep the file for
`role="status"` — it MUST be absent; the readout region MUST carry `aria-live="polite"`. Canary the
grep against `DriveResultRegion.js` (a known positive for `role="status"`).

**Scope of B-1's verification:** the `[role="status"]` collision is verified for the four
`DocumentPreviewDialog.*.test.js` suites (drive, copy, titleCopy, fileNameStaleness) and
`DocumentPreviewMount.test.js`, which select by `[role="status"]` or `data-copy-status`. I did NOT
exhaustively prove no suite anywhere selects a global `[aria-live="polite"]` that would sweep this
dialog; the ones found (`ChatPanel.gaps.test.js`, `factAutoInsertMessage.rc.test.js`) scope their
queries to their own `container`, not `document`, so they cannot see this dialog. Treat "no
`[aria-live]` global sweep hits the dialog" as CITED, not exhaustively verified — the 4b seat should
canary it when the region lands.

## 5. The reset seam (AC-4) — writes `null`, not `{1,0}`

A reset control (a `Button`, e.g. "Reset to default") whose `onClick` calls **`onSetSpacing?.(scope,
null)` — literal `null`, bypassing `setPartial`**.

- `setPartial` (F2) would build `{lineSpacing:null, paragraphSpacingPt:null}` — an *object*, not
  `null`. That object is a no-op for the transform (§2) so it *looks* like a reset, but it defeats
  the AC-4 assertion `onSetSpacingSpy` was called with `(scope, null)` and re-introduces the N82
  one-way-door ambiguity in the persisted store. The reset handler MUST NOT go through `setPartial`.
- **Reachability & canary:** rendered AND enabled only when `isApplied(spacing) === true` (§2);
  absent OR disabled when `spacing===null` (nothing to reset — AC-4 canary). It also inherits the
  control's `disabled` prop (an unavailable scope disables reset too, for consistency; the shared
  setter makes a stray reset harmless either way).
- **Flow to both documents + persistence:** the reset value `null` travels the identical path the
  presets use — `onSetSpacing` (dialog prop) → `setDocumentSpacing(scope, null)` → `updateTailoringJob(jobId, {spacing:null})`
  (F7, shared `entry.spacing`, scope-ignored, so both résumé and cover reflect it) → persisted as
  `spacing: entry.spacing || null` (F8). No new wiring; the setter already exists and already fans
  out to both docs and persistence.

**Diff-check:** the reset `onClick` handler contains `null` and does NOT reference `setPartial`.

## 6. Whole-document framing (AC-5)

- **(a) scope caption:** a small static caption element (e.g. `data-testid="spacing-scope-note"`)
  whose text conveys whole-document scope and that one setting governs both files (e.g. "Whole
  document — applies to résumé and cover letter"). Kept as a **separate** element from the readout so
  the readout's discriminators (§2) stay clean; 1e MAY instead fold it as the readout's prefix (its
  craft call) provided the readout's "no fabricated number in the `null` case" contract is preserved.
- **(b) same value on both tabs:** an invariant, not new work — the shared single `entry.spacing`
  (F7) already makes both tabs read one value. The readout/aria being a pure function of the shared
  `spacing` prop preserves it: switching tabs re-mounts the control with the same `spacing`, so the
  readout and active state are identical on the cover tab. **Diff-check:** the control derives its
  displayed value only from the `spacing` prop (no per-tab local spacing state that could diverge).

## 7. Synchronous update (AC-6)

No structural work — enforced by construction. The readout, the `aria-pressed` state, and
`displayHtml` (`DocumentPreviewDialog.js:544`) all derive from the same `spacing` value, so a single
parent `setState` re-render updates all three in the same `act`. `applySpacingToHtml` is synchronous
(F5), so there is nothing to await. **No spinner / `[role="progressbar"]` / pending state may be
added around the preview spacing change** (owner ruling; AC-6 negative half). **Diff-check:**
`SpacingControl.js` introduces no `setTimeout`/`Promise`/`aria-busy`/progress element around the
spacing readout.
