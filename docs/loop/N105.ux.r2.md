**Decisions at a glance**
1. Level: the existing Slider gets a sixth stop "Ideal" (label renamed "Tailoring level"); a caption states what it builds and, if the engine cannot run it, says so calmly with a one-click "Switch to Gemini". Persists under its own key (section 2).
2. Refusal: info-toned pre-click caption plus a server 422 carrying the same sentence; empty resume text refuses BEFORE generation; any failed run produces zero artifacts (section 3).
3. Two outputs: two tabs, "Application-ready" first and default, "HYPOTHETICAL" last; the hypothetical is read-only with a non-dismissible banner, a read-only forced file name (marker as the PREFIX, OC-3) and its own download button (section 4).
4. **The application-ready FILE is clean (F-B).** It contains KEPT spans only - no flagged claim, no inline flag text. Gate-flagged middle-tier claims are REMOVED from the file and listed in the review panel as "Removed - verify and add back", with the claim text and a one-click "Copy line" (and, only if a plan verification passes, "Add back"). Dropped claims are listed as "Left out" with no action (section 5.4, 5.7).
5. **A partial review never reads as a clean one (F-A).** The orchestrator forwards `review.coverage`; the band has a `partial` state; the clean "No issues flagged" verdict renders in exactly one of the 36 input combinations (fresh, complete review, no findings, not thin); in slice 1 `coverage.complete` is false on every invocation so it is unreachable on real input (section 5.8).
6. **An Ideal result is never auto-downloaded (F-C).** The chip and feed entry points open the preview on the Application-ready tab instead of downloading; batch hides "Tailor & download"; a cover-only regenerate under Ideal takes the standard path (section 2.3).
7. Safety hazards found and closed in the UX: Revise/Focus/Framing would bypass the gate (4.6); an unscoped run wipes the cover letter (U12); silent auto-download skips the review (2.3); a `visibleScopes` default of `SCOPES` shows "Hypothetical (none)" everywhere (4.2); a raw text compare falsely reports `other-version` (5.8); a partial review rendered as clean (5.8); a cover-scoped regenerate under a global Ideal selection would write a resume pair over a cover letter (2.3, D6).
8. Owner calls: OC-1 (resume pair only), OC-2 (flags panel-only) and OC-3 (filename marker is a prefix) are RESOLVED and designed to; no owner call remains open (section 11).

### 2.3 Delivery of an Ideal result on EVERY entry point (F-C)

**The problem (U11, U20-U22, U26).** Two single-job entry points - the chip `handleTailorJob` and the feed `handleTailorFeedPosting` - only DOWNLOAD and never open a preview; `finishByOpeningPreview` is called only by the URL flow (`page.js` :2318) and the JD-tab hook. An Ideal result is two documents plus a review, and the review band, the removed-claims list and the unresolved requirements exist only in the modal (session-only, D-14). If the Ideal branch merely skipped the download the result would have no surface (AC-13 fail); if it kept the download the file would leave before its review was seen. Both are closed by the rules below; each is stated as behaviour first and mechanism second.

| Entry point | Today | Under Ideal |
|---|---|---|
| URL flow `handleUrlSubmit` | opens the preview (`finishByOpeningPreview`) | unchanged; opens on Application-ready (`applyCover:false`, so the tab is "resume") |
| JD tab `tailorPosting` (`useManualTailor.js`) | opens the preview unless queued (`opts.openPreview`) | unchanged; queued entries do not auto-open and stay reachable from each entry's own preview button |
| Chip single run `handleTailorJob(job)` (default opts) | downloads immediately | **no download; opens the preview (D2)** |
| Chip run with `skipDownload` (batch tailor-only, screenshots, library re-tailor) | no download | unchanged: no download, no auto-open (the caller owns delivery; D4) |
| Feed `handleTailorFeedPosting` | downloads immediately | **no download; opens the preview (D2)**; returns `null` so the feed card shows no error (U25) |
| Batch "Tailor & download" | downloads each | hidden; "Tailor only" becomes the primary action; C12 (D5) |
| Chip "Regenerate" with `scope` "cover" | regenerates the cover letter | **standard path regardless of level (D6)** |
| Chip menu download / drag-out / Applying-tab download, later | application-ready file | unchanged (the file is clean, section A); not gated |

- **D1 Never auto-download.** The Ideal branch of every entry point contains no call to `downloadDocxFiles`; `downloaded` stays false. Structural, not a flag the UI can forget: a source sweep asserts no `downloadDocxFiles` token inside the Ideal delivery helper (assert near the named function, not file-wide - `[[loop-traps-search]]`). Hiding the batch download button (D5) is honesty about what the button would do, not the safety barrier.

## 3. Refusals and failures (brief items 4 and 5) - unchanged from r1

### 3.1 Design stance
"Needs the AI engine" is a requirement, not a fault. It is stated before the user spends a run, in an info tone, with a one-click remedy, and the same sentence is what the server returns if the run is attempted anyway.

### 3.2 Layers (cheapest first; the server is the guarantee)
1. **Pre-click (selector caption, L5/L6).** Prevents most refusals, costs no request.
2. **Run-entry fast-fail (optional, plan decides within the 7-line `page.js` budget).** Most valuable at `handleTailorAllVisible` (`page.js` :2096, reports through `setJobSearchError`) so a batch of N never becomes N refusals.
3. **Server refusal (authoritative, D-3).** HTTP **422** `{ error: <the sentence>, refusal: { level: "ideal", code: "engine-unsupported", engine, requires: "gemini" } }`, none of the output keys. 422 + `error` and not 200 + `refusal`: every client throws `payload.error` on `!ok` (U16), so an entry point that forgets to check `refusal` fails CLOSED with the right sentence; a 200 would fall into `payload.result?.trim() || "No output returned from Gemini."` and store a fake result.
4. **One sentence source.** `idealRefusalMessage(code, ctx)` in `tailorLevel.js` produces C6, C8 and C9.

### 3.3 Tone rules for the refusal (checkable)
- Leads with the requirement ("The Ideal level needs ..."), never "Error", "Failed", "Sorry", "Unable".
- Names the user's CURRENT engine by its `ENGINE_OPTIONS` label.
- States a reachable remedy: the caption button (1 click) or, in the red channels, "Switch the engine in the top bar" (`AppHeader.js` :139) "or pick another level".
- Produces no artifact: no Hypothetical tab, no band, no `done` result, no download, nothing persisted (AC-2).

### 3.4 Empty or unreadable resume text (structure input D-7b)
- **Decision: refuse BEFORE generation.** If the trimmed `readResumeText` result is empty on an Ideal request: 422 `refusal.code = "empty-resume"` with C9, zero artifact, no AI request spent. (The client MAY pre-empt on an empty `templateLines`; the server stays authoritative.)
- **C9** names the file, says why Ideal needs the text, and gives the reachable remedy (re-upload a `.docx`/`.txt`/`.md` with selectable text on the Materials tab, `ApplyingControls.js` :70-89).
- **Thin corpus (text exists, nothing can be matched).** A SUCCESS state: when `review.counts.keptAccomplishments === 0` the band shows C21 (and C21b when lines were set aside). The file is still delivered and still honest. Under F-B this is more likely than at r1, because flagged claims also leave the file.

### 3.5 Run failure is atomic
A run that cannot finish (a stage fails, timeout, rate limit, truncated structured response) produces **zero artifacts**: never the hypothetical alone, never an application-ready without its review. Copy C10; retry is the existing Generate control. In flight the existing button reads "Generating..." and C11 adds the expectation; **no duration is stated** (U18). A review that did not run is a different state from a failed run (5.8, `no-review`).

### 5.1 Three sources, one band

**The safe realization (D-6b amended, section A).** The emitted application-ready bytes contain KEPT (unflagged) spans only. **Axis R - review kind (`reviewVerdict(review)`, shared with N103/N104):**
- `none`: `review` absent/null.
- `partial`: `review` present AND NOT (`coverage` is an object AND `coverage.complete === true` AND `coverage.evaluatedCategories` contains all seven categories). This fails CLOSED: a missing, malformed or self-contradicting `coverage` is `partial`, never `complete`. (The consumer re-checks the coupling N106 AC-15 requires of the producer: defence in depth against an overclaiming `complete:true`.) `missingChecks` = the categories absent from `evaluatedCategories` (all seven when `coverage` is unusable).
- `complete`: the positive case only.

**Axis F - freshness:** `fresh` iff `normalize(currentText) === normalize(ideal.applicationReady.result)` where `normalize` is `trim()` plus CRLF -> LF applied to BOTH sides (the entry stores `payload.result?.trim()`, `page.js` :1952, :2214; a raw `===` against the untrimmed reviewed text reports `other-version` on a FRESH result and demotes the tab). Else `edited` iff the user edited this scope - `editedForScope(entry, "resume") || !!scopes.resume.html` (U24: a text-only save, which Tier B uses, sets the entry flag but not `html`, so `html` alone is not enough; and text equality is checked FIRST so a spurious `edited` flag over unchanged text still reads `fresh`). Else `other-version` (a saved version was selected).

**Axis T - thin:** `review.counts.keptAccomplishments === 0`.

**What shows (fixed precedence; groups render only where stated):**

| Condition (first match wins for the HEADLINE) | Headline | Groups below |
|---|---|---|
| F = `other-version` | C19b: a different saved version is showing; the review belongs to the generated version and is hidden. Tab text reverts to "Resume". | none |
| R = `none` | C20: the review did not run for this result; treat every line as unchecked (warning tone) | none |
| R = `partial` | **C22: "Partial review - mechanical checks only."** + the checked/not-fully-checked line built from `coverage` (below). Warning tone. Not dismissible, not collapsible away. | all non-empty groups |
| R = `complete`, no findings (no removed, no reviewer flags, no unresolved), F = `fresh`, not thin | **C17 "No issues flagged ..." - the ONLY state that may show it** | the collapsed "Left out" group only, if non-empty (it records what the gate already refused; it is not a finding) |
| otherwise (R = `complete` with findings, or edited, or thin) | C15 summary line of NON-ZERO counts | all non-empty groups |

Additive notes (shown in any state that renders groups): F = `edited` adds C19a ("You have edited this resume since the review ran. The notes below describe the version that was generated."); thin adds C21 (and C21b when `counts.removed > 0`). **The clean license** `verdictClean` = R `complete` AND F `fresh` AND no findings (no removed, no reviewer flags, no unresolved; "Left out" is informational and is not a finding) AND not thin. It is true in exactly ONE of the 36 combinations of {F: 3} x {R: 3} x {thin: 2} x {has findings: 2}; the pure function is total over all 36 and UX-26 tests all 36 (UX-33 tests that `coverage` reaches the band).

**The partial copy, and why it does not say "needs the AI engine".** The brief's suggested wording ("deeper review needs the AI engine") would be WRONG here: Ideal already requires the Gemini engine (embedded refuses), so telling the user to get the AI engine offers a remedy they cannot take and misdescribes why the review is partial (the deeper checks are not built yet). C22 is data-driven from `coverage` instead: "Partial review - mechanical checks only. Checked: {ran}. Not fully checked: {missing}. Read the whole resume once before you send." where `ran`/`missing` are plain phrases from `CHECK_LABELS` (e.g. posting keywords, repeated phrasing, figures with no baseline, vague wording / dates and titles lining up, role and seniority claims, whether claims fit the employer). It self-corrects when the second slice lands. When `coverage` is unusable: "Which checks ran is unknown for this result. Treat the whole resume as unchecked."

**Partial-state rules (checkable):**
- P1 The clean verdict and its equivalents NEVER render unless `verdictClean`. The UX-26 sweep forbids, in the band's CHROME text (quoted claim/evidence nodes are marked `data-quoted` and excluded, else a resume line that says "no issues" trips it): /no issues flagged/i, /no weaknesses/i, /nothing (was )?(flagged|found)/i, /found nothing/i, /no (problems|concerns|issues)\b/i, /all clear/i, /looks good/i, /passed/i, /\bverified\b/i, /safe to send/i. Positive control: the clean row must render C17 so the sweep can find the phrase.
- P2 No zero count renders in any state (groups with zero items are omitted; the summary lists non-zero counts only), so "0 removed / 0 requirements" cannot be read as a clean bill in a partial state.
- P3 The partial notice is visible without expanding anything and at every viewport; the mobile collapsed summary contains it (below).
- P4 `thin`, `no-review`, `partial` are three DISTINCT states with distinct copy; none borrows another's wording.
- P5 The notice is static text present at open, not a transition: it needs no live region (section 7).

**Mobile (`useIsMobile()`):** the band collapses to its summary line, which always carries the partial state ("Partial review - {n} to check" when there are findings, "Partial review" alone when none) so it is read without expanding; tap target >= `MOBILE_TAP_MIN`. The density rule is unchanged: the expanded band has a capped height with its own scroll (the repo's `vh`/`dvh` pair; read the raw `<style>` text, not CSSOM - `[[measurement-instruments]]`).

### 5.9 Residual risk (stated, not hidden)

The FILE is clean in the two senses this design controls: kept-only (no gate-unverified claim) and no flag text. What it cannot control: **reviewer-only Confirm-tier flags (AC-5) on KEPT lines are advisory and session-only** - they cannot be embedded (panel-only, OC-2) and cannot feed back into recompose (the settled structure runs the reviewer after recompose). After a reload such a line is a plain bullet with no note. The exposure is bounded: the gate already requires every authority/metric token of a kept line to trace to one real span (AC-4.1), and in slice 1 the reviewer does not yet evaluate the semantic depth of authority or consistency at all, which the partial notice states. UXR-8 stays a plan input (a second recompose pass that also removes kept lines carrying a Confirm-tier flag is a structure change, not slice 1).

## 7. Keyboard, focus and accessibility (F-F: live-region census)

- **Tab order follows the DOM:** tab list (roving, arrows, MUI `Tabs`) -> toolbar -> band disclosure buttons and per-row actions -> (hypothetical: banner download button) -> document -> action bar. Escape closes the dialog.
- **Disclosures** are real buttons with `aria-expanded` and `aria-controls` resolving to a real node; caret glyphs are `aria-hidden` (`[[mui-a11y-traps]]` 7). The band is a `role="region"` labelled by its title (one landmark per tab).
- **No `Tooltip` on any new control** (items 1, 2); reasons are visible text (item 8). **No `Select`** anywhere (items 9, 10).
- **Label-in-name (WCAG 2.5.3):** the visible text is the accessible name (or a prefix of it) for the new tab, "Download hypothetical .docx", "Switch to Gemini", "Copy line", "Add back" and the disclosures (assert with the name resolver of `[[mui-a11y-traps]]` 3).
- **Focus:** after "Switch to Gemini" focus moves to the slider thumb (L6). An "Add back" button never unmounts under focus (RC-5).
- **Colour is never the only signal.** Tokens from `app/theme/tokens.js`, light and dark; contrast of body copy on `--warning-soft` is a 1e computation (not asserted). Any numeric `sx` width/margin follows `[[mui-sx-numeric-traps]]`.

**Live-region census (the prior collision history in this modal is real: the dialog's first `[role=status]`/`[role=alert]` belong to DriveResultRegion, pinned by a landed test, U23).** Every live node on the surfaces this feature touches, and who owns announcing under Ideal:

|---|---|---|---|
| Materials tab, level control | none | **ONE** hidden polite announcer in `TailorLevelCaption` (L5b); the visible caption is not live | C6 short form on entering the cannot-run state; C7 after the switch |
| Preview dialog | DriveResultRegion status+alert (first in DOM); `CopyFeedbackStrip` status+alert+chip (second); the mount's N95 pair inside the band slot, only when `insertedFacts.length > 0` | **ZERO new nodes.** The Ideal band mounts no `role=status`, no `role=alert` and no `aria-live`. | Hypothetical tab | as above | none (the banner is static text) | nothing |

- **State changes announce nothing.** `partial`, `no-review`, `thin`, `edited`, `other-version` are static text: present at open or changed in place, never a live transition. In particular the `edited` flip happens while the user types in the Edit surface; announcing it would interrupt typing (`[[mui-a11y-traps]]` 4) and r1's "announced once on the transition" is WITHDRAWN. - **If an MUI `Alert` is used anywhere in the new leaves it must set `role` explicitly** (item 5: it defaults to `role="alert"`); the design uses plain `Box`es, not `Alert`, in the band.
- jsdom can assert structure, names, roles, attributes, text, declared `getComputedStyle` values. **Only a real browser can assert** tab-bar fit at 375/768/900 px, band height, overlap, focus ring and real screen-reader output; those are manual measurements for 1e/8d, reported INVALID until measured, never as zero.

## 9. App-vs-chat claim (`[[app-vs-chat]]`; AC-16)

**Class:** Guaranteed (earned, with the mechanism named below), with Corpus as the enabling input and the Word-on-your-template property as a second Guaranteed.

**What the user does instead today, and what it costs:** pastes the posting and the resume into a chat for each application; gets one undifferentiated blob that mixes "what a perfect candidate would say" with "what is true of me"; audits every bullet by hand for invented numbers, titles or scope; copies the result into Word and rebuilds the one-page layout; carries the standing risk of submitting a line that was never true. Repeated across dozens of applications the cost is the re-paste, the manual truth audit and the reformat each time, plus the cost of the one time it goes wrong.

**What this UX gives that the chat does not (each removal-tested by an existing AC):**
1. The two-file split with a STRUCTURAL marker - a filename prefix that cannot be stripped by renaming and a banner that cannot be dismissed (AC-7 + AC-3). Remove it and the hypothetical is just another resume file.
2. A fail-closed grounding gate against the user's own stored resume that produces a FILE with nothing unverified in it, plus a visible account of what it took out and what it refused to say ("Removed", "Left out") and a partial-review state that does not pretend to a verdict it did not earn (AC-4 + AC-10; UX-25, UX-33, UX-35, UX-36). A chat will not tell you what it declined to claim for you.
3. The output on the user's own template as a real `.docx` (AC-12a), saved and downloadable in one click.

**REMOVAL test mapping:** delete the HYPOTHETICAL marker surfaces -> UX-15/UX-41/AC-3(d) red; delete the review band -> UX-21..26/UX-33/AC-13 red; delete "Removed"/"Left out" -> UX-25/UX-36 red; delete the gate or hand recompose `kept + flagged` -> UX-35/AC-4 red; route output through a bespoke generator -> AC-12a red. If any can be removed with every test green, the feature has collapsed to chat-equivalent.
