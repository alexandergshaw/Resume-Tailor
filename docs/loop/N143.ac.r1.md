Row 1 = a PRE-WARMED per-application pool of hypothetical benchmark projects, best-matched per question and shown instantly. The crux (quality) is not instrumentable in this checkout (no `GEMINI_API_KEY`), so per the N135 standing rule the gating deliverable is an owner-env PROBE, not a fix.

## Acceptance criteria

Each is tagged **[unit-testable]** (jsdom/vitest/SQL-shape, instrument named) or **[owner/Gemini-env]** (content/latency needing the owner's real key — not instrumentable in this checkout). RED-on-HEAD status stated per criterion.

### Group A — Row 1: the pre-warmed pool (storage + contract)

**AC-N143-1 [unit-testable]** A migration creates `public.application_project_pool` with: `application_id uuid primary key references public.applications(id) on delete cascade`, `user_id uuid not null references auth.users(id) on delete cascade`, a `projects jsonb not null default '[]'::jsonb` payload, `status text not null` constrained by a CHECK to the set `('pending','ready','failed')`, an `error text`, an `engine text`, `created_at`/`updated_at timestamptz not null default now()`, and a `user_id` index. RLS is enabled with four owner-scoped policies (`auth.uid() = user_id` for select/insert/update/delete) and grants to `authenticated` + `service_role`.
*Instrument:* a migration-shape test modeled on `applicationDigestsMigrationShape.test.js` (asserts the `create table`, the PK/FK/cascade, the CHECK set, RLS-enabled, the four policies). *Failure direction:* the CHECK **must** include `'pending'` (an un-warmed row is a real state, below) — a CHECK of only `('ready','failed')` is a blocker. *RED on HEAD:* no such migration exists.

**AC-N143-2 [unit-testable]** A storage lib (e.g. `lib/supabase/applicationProjectPool.js`) exposes read + upsert functions that take the caller's `supabase` + `userId`, scope every query by `user_id` in addition to RLS, **never throw** (return `{ pool/..., error }`), and upsert **column-wise on an explicit whitelist** spelled exactly as the columns. A field the whitelist does not name is not sent.
*Instrument:* a lib test modeled on `applicationDigests.test.js` — a transient PostgREST error returns `{ error }` not a throw; an upsert omitting a column leaves it unchanged; a field not on the whitelist never reaches the client. *RED on HEAD:* no such lib exists.

**AC-N143-3 [unit-testable]** The stored shape is defined and pinned: `projects` is a JSON array of pool entries, each entry carrying at minimum `{ competency, domain, title, body, hypothetical: true }` and no field that can hold a posting figure verbatim (see AC-N143-13). The pool is keyed one-row-per-application (PK = `application_id`), so "does this application have a pool" is a primary-key lookup; it cascade-deletes with the application.
*Instrument:* a shape test over a representative stored row; a deletion test (deleting the application removes the pool row — assertable via the FK/cascade shape test if a live DB is unavailable). *RED on HEAD:* shape undefined (no table).

**AC-N143-4 [unit-testable]** The pool is **persisted** and survives reload and a new copilot session: once a pool is `ready` for an application, a later load reads the stored row rather than regenerating. A generation is attempted at most once per application until `force`/explicit retry — a re-render or a new session does not re-fire generation for a row that is already `ready` **or** already `failed`.
*Instrument:* a route/hook test mirroring the digest short-circuit — an already-`ready` pool returns as-is with no model call; a `failed` pool is not auto-retried on load (only an explicit retry re-fires). *Failure direction:* re-firing a model call for a `ready`/`failed` row is the billed-stampede defect — the safe/passing direction is no model call. *RED on HEAD:* no prewarm path exists.

### Group B — Row 1: generation, selection, instancing

**AC-N143-5 [unit-testable]** The pool contains **N** hypothetical benchmark projects spanning the role's key competencies, where **N is a named, owner-surfaced, owner-tunable constant** (proposed default **5** — see Decisions-needed D1). The generation is asked to produce entries that span DISTINCT competencies/domains for the posting (not N near-duplicates of one).
*Instrument:* an assertion that the pool size is driven by the named constant (not a literal buried in the prompt), and a structural check that entries carry distinct `competency` values. *Content quality of the spread is [owner/Gemini-env]* — see the probe. *RED on HEAD:* no generation exists. *Note:* N (and the prewarm trigger) are flagged owner-tunable per the RETRO-695e23d owner-tunable-threshold rule so a guessed number ships surfaced, not as a future reactive chunk.

**AC-N143-6 [unit-testable]** At question time the pool entry **best-matching the question** is selected and shown. "Best-matching" is defined as competency/domain fit of the entry to the question (the same class of ranking as `selectBestStory`/`buildKnowledgeBaseBlock`), computed over the already-stored pool. The selection adds **zero model calls on the answer path** for Row 1.
*Instrument:* an answer-route test with `generateContent`/`interactions.create` spied — with a warmed pool present, Row 1 selection contributes **0** model calls (Row 2 is the only added call; see AC-N143-10). A positive control: the spy records a real call on some other path so the zero is not a dead spy. *RED on HEAD:* no selection exists.

**AC-N143-7 [unit-testable]** The per-question SELECTION is **never cached** and is re-computed fresh for every question — it must NOT be written into `answerSessionCache.js`, nor into `application_project_pool`, nor into any per-session store. (The POOL itself is cached/persisted — it is question-independent, scoped to the application; only the ranked pick is fresh.)
*Instrument:* mirror `route.latency.test.js`'s existing guard — two different questions in one session can select two different pool entries (no stale carry of question one's pick to question two); plus a static assertion that the selection result never enters the session cache. *Failure direction:* this is the exact "answer question two with question one's selection, every other test still green" hazard the cache header names — the safe/passing direction is a fresh pick each question. *RED on HEAD:* no selection/cache interaction exists. *This is also a standing non-regression guard on the cache invariant.*

**AC-N143-8 [unit-testable]** The **not-yet-warmed** state is defined and rendered honestly: before a pool is `ready` (`status` = `pending`, or no row yet), Row 1 shows a neutral pending/placeholder state (or renders nothing) — it never shows a stale or fabricated benchmark, and it never blocks the answer or the other rows.
*Instrument:* a jsdom render of `AnswerAids` with a `pending`/absent pool — asserts no benchmark project text renders as ready, and the answer + "Project to talk about" + words rows still render. *Failure direction:* showing placeholder/stale content as a real benchmark is the over-claim — safe direction is the neutral pending state. *RED on HEAD:* no Row 1 rendering exists.

**AC-N143-9 [unit-testable]** The **failure** state is graceful and non-poisoning (= N130): a failed pool generation persists `status='failed'` (never a `ready` row with empty/placeholder `projects`, never a null that reads as ready), is not auto-retried on every load, leaves the existing "Project to talk about" row and the drafted answer standing, and surfaces an actionable-but-non-blocking signal in Row 1 (not a thrown error, not a torn-down answer).
*Instrument:* a test that a generation error writes a `failed` row and the answer still returns 200 with its other aids; a render test that a `failed` pool shows the degraded Row 1 state, not a crash and not a fake benchmark. *RED on HEAD:* no failure path exists.

### Group C — Row 2: on-the-spot (live per question)

**AC-N143-10 [unit-testable]** Row 2 is a fully idealized hypothetical project generated **live per question on the ANSWER route** (which has `applicationId`), **never on the question route**. It is async/non-blocking: the drafted answer and Row 1 render FIRST; Row 2 streams/swaps in when ready. A pending or failed Row 2 **never blocks the answer and never turns the response into an error** — the answer, Row 1, and the existing rows are unaffected by Row 2's outcome.
*Instrument:* (a) a route-graph/static check that the on-the-spot generation call site is in `app/api/copilot/answer/` and absent from `app/api/copilot/question/`; (b) an answer-route test that a Row-2 generation rejection/timeout still yields a 200 with the answer + Row 1 present; (c) a render test that Row 2 has an explicit pending state and a failed state that leaves everything else intact. *Failure direction:* Row 2 blocking or erroring the answer is the worst outcome (the candidate is mid-interview) — safe direction is the answer always standing. *RED on HEAD:* no Row 2 exists.

**AC-N143-11 [unit-testable]** Row 2's model call rides the existing answer-route generation path/timeout budget and does not extend the time-to-first-content of the answer or Row 1. (It is additive and late, not in the critical path.)
*Instrument:* an answer-route latency/ordering test — the done-frame/first content is emitted independent of Row 2 settling (Row 2 arrives in a later frame or a separate swap-in). *RED on HEAD:* no Row 2 exists. *Real latency is [owner/Gemini-env].*

## AC-N143-Q — Owner-env QUALITY PROBE (gating deliverable, [owner/Gemini-env], STANDING N135)

The reason this chunk exists is a model-CONTENT quality bar this checkout cannot instrument (no `GEMINI_API_KEY`). Per the N135 standing rule, the **FIRST and gating deliverable is an owner-run probe set**, not a fix: no claim that the examples are "good/relevant" is accepted until the owner runs it. The probe must enumerate every candidate cause of the "wrong-kind project" failure and give each a **distinct, owner-observable outcome in a single run**.

**Probe protocol (one owner sitting, real Gemini key):** run **K ≥ 3 representative questions in each of ≥3 distinct domains** — e.g. a teaching/curriculum question, an SRE/infra question, and a non-tech question (sales or nursing) — against at least one real posting per domain, and for **each** question capture:
1. the Row-1 pool entry shown (its `title` + `competency` + `domain`);
2. the **full pool** for that application (all N entries' titles/competencies);
3. the Row-2 on-the-spot project;
4. an owner verdict per row: **domain-relevant? (Y/N)** and **template-generic? (Y/N)**.

**Discriminators (each candidate cause → a distinct cell, so one run attributes cause unambiguously):**

| Candidate cause | Distinct observable in the single run |
|---|---|
| (a) prompt ignores the question's domain/competency | Row shown is off-domain (teaching Q → ops/SRE project): item 4 "domain-relevant?" = N, AND no better-fitting entry exists in the full pool (item 2) |
| (b) prompt takes domain but defaults to a generic skeleton | item 4 "template-generic?" = Y across domains; two different-domain runs share the SAME skeleton ("owned X end-to-end, process metrics") — detectable only because item 2/1 are captured for multiple domains |
| (c) pool competency-spread too narrow | item 2 shows all N entries clustered on one competency/domain, so the per-question match is forced off even when selection works |
| (d) best-match SELECTION picks the wrong pool entry | item 2 contains a clearly better-fitting entry than the one item 1 shows (isolates selection from generation) |
| (e) Row 1 and Row 2 quality diverge | item 1 vs item 3 verdicts disagree (e.g. pool generic, on-the-spot relevant, or vice versa) |

**Pass condition for the owner to declare content-quality met:** across the K×3 runs, every shown row is domain-relevant = Y and template-generic = N, with no (d) mis-selection. Any N routes to the specific cause above rather than to "another round." **No mechanical quality fix is in scope until the owner runs this probe** and attributes cause. The probe itself (the capture harness/instructions) is the deliverable this chunk must ship; the owner's verdict gates the quality claim.

## Composite-surface cost (rule 6b — for the 8b re-judge and N144)

`AnswerAids` is a cumulatively-growing surface shared by three copilot views. Today it renders up to **3** rows (role, "Project to talk about", words). This chunk ADDS **2** rows, taking it to up to **5** stacked rows, **three of which are now "projects"** — one REAL (the candidate's) and two HYPOTHETICAL. The displacement risk is legibility and confusion between the real and invented projects, inside the height-locked nested-scroll live wrapper on `sm+`. No per-diff gate measures this composite; it is raised here so the 8b experience re-judge and N144 weigh it. Nothing here asks to redesign the surface — AC-N143-13 (clear real-vs-hypothetical distinction) and AC-N143-18 (layout non-regression) are the mitigations in THIS chunk; the ordering/visual-weight of five rows at phone width is explicitly N144's to settle.
