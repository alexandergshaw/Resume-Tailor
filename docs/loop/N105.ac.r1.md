## 1. Owner / orchestration decisions surfaced (design must NOT silently resolve these)

**OD-1 — Is the new level a 6th value on the 1–5 slider, or a distinct selectable mode?** N105 produces TWO
outputs and runs an 8-step pipeline — categorically unlike "turn aggressiveness up one notch." **AC recommends a
distinct, clearly-highest selectable option** (its own control or a labeled top entry), NOT slider=6, because
the clamp (F1) would otherwise silently swallow it into "Strong"/5. AC-1 makes the *no-silent-downgrade*
requirement checkable either way; the control shape is 1c/1b's call.

**OD-2 — Which engines support N105, and what does an unsupported engine do?** The embedded engine cannot
genuinely invent a strongest-plausible-candidate profile (F4) and already fabricates ungrounded content (F3).
**AC recommends: gemini/external support the full pipeline; embedded either (a) refuses honestly and directs
the user to an LLM engine, or (b) produces a deliberately reduced, clearly-scoped hypothetical — owner's call.**
The **non-negotiable** part, regardless of (a)/(b): embedded must NEVER silently emit a level-5 template fill
relabeled as the N105 two-output result (AC-2). The structural choice is 1b's; the fail-honest constraint is
fixed here.

**OD-3 — Who builds the shared reviewer primitive, and when (N103/N104/N105 share it)?** N105 step 6 CONSUMES
it. **AC recommends one shared module (reusing `critique.js` for its deterministic path), built once and
imported by all three.** Which chunk lands it first is orchestration. AC-6 pins "one primitive, not three" as
a checkable import census once built.

**OD-4 — Exact label string + is the hypothetical EVER persistable?** AC recommends the exact string
*"hypothetical — not for submission"* (owner may adjust) and that the hypothetical is **never** savable as a
tracked/submittable application document (a safety stance, not just a label). Both are owner calls; AC-3 is
written to whatever exact string the owner fixes.

**OD-5 — Part-time-teaching cover-letter + sourced institution facts (step 8 tail):** AC recommends DEFERRING
(a conditional sub-feature). Flagged, not assumed.

### — SAFETY ACs (highest severity; first slice; never deferred) —

### AC-3 (SAFETY) — The hypothetical is labeled AND the label travels into every export; a UI-only badge FAILS
The hypothetical output carries the exact label *"hypothetical — not for submission"* (OD-4) and there is **NO
path** — Download (all 3 entry points, F5), Drive save, copy-to-clipboard, "set as default template", combine —
by which the hypothetical's *content* leaves the app without that label present **in the exported artifact
itself** (the docx bytes and the copied text), not merely in a screen badge.
- **Preferred structural form (rule 4 — make the wrong thing impossible):** either the hypothetical is not
  routable to the normal submittable export/Drive/default-template paths at all, OR the label is injected at
  generation (`serializeDocx`, engine.js:330, F5) and preserved at the single choke point
  `resolveDocumentBlobBytes` (docx.js:653) so edited rebuilds (docx.js:692) cannot drop it. 1b picks; this AC
  fixes the invariant.
- **Instrument (NEW), modeled on `lib/document/defaultTemplateEgress.census.test.js`:** (a) BEHAVIORAL — produce
  the hypothetical, drive each export/copy path, assert the label string is present in the output bytes/text;
  (b) MUTANT CONTROL — removing the label-injection line must turn (a) RED; (c) CENSUS over the export
  call-sites so a NEW export path that forgets the label reds per-surface (with the instrument canary that
  census file already uses).
- **RED on HEAD:** yes — no hypothetical, no label (F6).
- **Failure direction (load-bearing):** a badge stripped on download/copy is the exact failure this AC exists to
  prevent; the label must live in the bytes. Over-label (label present even when arguably unnecessary) is safe;
  dropping it is the lie.

### AC-4 (SAFETY) — Application-ready carries ONLY truthful, supported claims: SUPPORT + MEMBERSHIP, fail-closed
Every claim in the application-ready résumé (each **bullet-sized span**, the app mints its ids) must satisfy
**two separate rules**, evaluated against **exactly one** source span (never a union, never a document — per
[[loop-traps-spec]]):
1. **SUPPORT** — the claim is contained in ONE span of the user's OWN real material (the user's résumé /
   experience library), not the hypothetical.
2. **MEMBERSHIP / ELIGIBILITY** — that source span must belong to the context the claim appears in: a
   metric/accomplishment/skill placed under employer/project/role X must trace to the user's real material
   *about X*. A real metric from employer A may NOT support a bullet under employer B. (This is the spec's
   "associate required skills with an employer/project only when supported.")
A claim that satisfies neither is **dropped, or surfaced under an explicit `unverified — confirm before use`
flag — never emitted as a plain truthful bullet.** This gate applies to whatever the engine produces,
**including the embedded engine's `allowFabricated`/gap-keyword content (F3)**, which must not reach the
application-ready output ungrounded.
- **Instrument (NEW):** two contamination fixtures built so the two halves provably cannot sit in one span:
  (i) the hypothetical contains a fabricated accomplishment absent from the user's real material (e.g. "scaled
  to 10M users") — assert it is absent from, or flagged in, the application-ready output; (ii) a real metric
  under the user's employer A is NOT emitted under employer B. Report the **failable-row count** of each fixture
  (how many claims could fail the gate) so the measurement is not zero-power.
- **RED on HEAD:** yes — no application-ready output exists.
- **Failure direction (load-bearing):** emitting an unsupported claim as truthful is the worst outcome; the safe
  direction is drop/flag (fail closed). If in doubt whether a span supports a claim, drop it.

### AC-5 (SAFETY) — Step-6 adversarial review flags unsupported authority + unverifiable metrics on BOTH drafts
The step-6 reviewer runs over **both** the hypothetical AND the application-ready draft and flags: missing
keywords, vague/unsupported claims, repetition, **unsupported authority** (claimed seniority/leadership/scope
not evidenced in the user's real material), **unverifiable / ambiguous metrics**, employer/domain
plausibility, and **consistency** across dates/titles/seniority/leadership (including between the two drafts
where they reference the same real fact). It also emits the list of posting requirements that **wording alone
cannot resolve** (genuine qualification gaps, distinct from phrasing gaps).
- **Instrument (NEW):** feed a HELD-OUT draft (not authored from the same template as the reviewer's rules, to
  avoid the self-authored-corpus zero-power trap — [[loop-traps-spec]]) containing a planted unsupported-authority
  claim ("Directed a 50-person org" with no such real role) and a planted unverifiable metric ("+300% revenue"
  with no source). Assert BOTH are flagged on BOTH drafts, and a clean control draft produces no false flags.
- **RED on HEAD:** yes — no document reviewer (F8).
- **Failure direction:** a review that silently passes an unsupported-authority or unverifiable-metric claim is
  the failure; over-flagging is the safe direction.

### — INTEGRATION ACs (first slice) —

### AC-1 — The new highest level is selectable and is NOT silently downgraded to level 5
Selecting the new highest level in the tailoring-level UI routes a request the server recognizes as the N105

- **Instrument (NEW):** select the level in the UI → assert the FormData value maps to the N105 path in the

- **RED on HEAD:** yes — `route.js:19-21` and `Math.min(5,…)` (F1) reject/clamp anything above 5; no N105 path.
- **Failure direction (load-bearing):** the clamp silently absorbing N105 into "Strong"/5 is the specific
  regression hazard; the passing direction is an explicitly-recognized distinct level.

### AC-2 — Engine support is explicit; an unsupported engine FAILS HONESTLY, never silently degrades
For each engine (`gemini`/`external`/`embedded`, F2), N105's behavior is defined and enforced: a supporting
engine produces both outputs (AC-7); a non-supporting engine (per OD-2) returns a **clear, honest
refusal/redirect and produces NO artifact presented as an N105 result**.
- **Instrument (NEW):** invoke N105 through `resolveEngineName`/`getEngine` on each engine; assert supporting
  engines return `{hypothetical, applicationReady}` satisfying AC-3/AC-4/AC-7, and non-supporting engines

- **RED on HEAD:** yes — no N105 path on any engine.
- **Failure direction (load-bearing):** embedded emitting a level-5 fill relabeled as the two-output result
  (populating the safety model with fake "hypothetical"/"application-ready" content) is strictly worse than an
  honest refusal. Over-refuse.

### AC-6 — ONE shared reviewer primitive, consumed by N105 step-6 / N103 / N104 (not three copies)
The step-6 reviewer is a single shared module consumed by N105 step 6, N103's adversarial-review button, and
N104's weakness summary; its deterministic/embedded path reuses `lib/resume/critique.js` (F8) rather than
reinventing bullet analysis. No second weakness-analysis module appears.
- **Instrument (NEW):** import/structural census — N105 step-6, N103 and N104 entry points all import the same
  reviewer module; assert no second document-weakness analyzer is introduced. Plus a behavioral check that the
  primitive is engine-aware (a deterministic path exists).
- **RED on HEAD:** yes — the primitive does not exist and N103/N104 are not built. (Partly an orchestration
  commitment; checkable as a census once the first of the three lands.)
- **Failure direction:** three divergent reviewers is the drift this AC prevents (one shared recipe per the N103
  card).

### — OUTPUT / PIPELINE-STEP ACs —

### AC-7 — Exactly two outputs, clearly distinguished
A single N105 run yields exactly two distinct artifacts — the hypothetical ideal and the application-ready —
each separately identifiable (distinct titles/filenames and on-screen labels), never merged into one document
nor presented ambiguously. The hypothetical carries AC-3's label; the application-ready (the submittable one)
does not carry that label.
- **Instrument (NEW):** run N105 → assert two distinct outputs with distinct identifiers; assert the label is on
  the hypothetical and absent from the application-ready.
- **RED on HEAD:** yes.
- **Failure direction:** one merged document, or two indistinguishable ones, defeats the whole two-output safety
  model.

### AC-8 (step 1) — "What earns an interview" is extracted from, and grounded to, the POSTING
Step 1 extracts the screening requirements, responsibilities, preferred quals, leadership scope, tools, and
industry language **from the posting**, each item traceable to a span of the posting text (grounding span sized
to a requirement line / sentence, not the whole posting — [[loop-traps-spec]]).
- **Instrument (NEW):** feed a fixture posting; assert each extracted requirement grounds to a posting span, and
  a planted requirement NOT present in the posting does not appear in the extraction.
- **RED on HEAD:** yes.
- **Failure direction:** inventing a requirement absent from the posting mis-steers the entire pipeline; the
  passing direction is posting-grounded extraction.

### AC-9 (step 2) — Prioritized keyword map onto résumé sections, posting-grounded
Step 2 produces a prioritized keyword map assigning posting keywords to headline/summary/competencies/bullets;
each keyword traces to a posting span (reuse AC-8 grounding) and the map is ordered by a stated priority signal
(posting emphasis).
- **Instrument (NEW):** assert the map exists, is ordered by the stated priority signal, and every keyword
  grounds to the posting.
- **RED on HEAD:** yes.
- **Failure direction:** an unordered or ungrounded "map" is decoration; the passing direction is a prioritized,
  grounded assignment.

### AC-10 (step 4) — Real-chronology integrity: employers/dates/education EXACT; titles may be truthfully reframed
The application-ready résumé's name, contact, employers, employment dates, degrees and institutions **match the
user's real stored records exactly** — none invented or altered — and progression stays coherent (no impossible
overlaps/gaps introduced). Market-facing **titles MAY be reframed** to truthful standard equivalents, but
seniority/scope inflation is forbidden and routes to AC-5's unsupported-authority flag.
- **Instrument (NEW):** contamination fixture where the hypothetical invents an employer ("Google, 2018–2022")
  the user never had; assert the application-ready contains only the user's real employers/dates/education and
  NOT the invented one; assert a reframed title maps to a truthful equivalent of a real role, not a higher one.
- **RED on HEAD:** yes.
- **Failure direction (load-bearing):** fabricating/altering a real employer, date, or degree is the worst class
  of résumé lie; exact match to the stored real chronology is the passing direction.

### AC-12a (step 7, automatable) — Both outputs are built through the existing template path, inheriting its styling
Both outputs are produced through the existing template-based docx path (`resolveDocumentBlobBytes` →
`docxModel`/template, F5/F7), NOT a new ad-hoc generator, so they inherit the one-page Calibri layout, gray
dividers, date tabs, competency indents and aligned bullets baked into the template.
- **Instrument (NEW):** assert each output's bytes are produced via the template path (the Calibri font run /
  template structure present via `docxModel`/text-level assertions), not `buildMinimalistDocx`.
- **RED on HEAD:** yes.
- **Failure direction:** a bespoke generator would diverge from the template's professional layout; the passing
  direction routes through the shared template path.

### AC-12b (step 7, OWNER-JUDGED REAL RENDER — manual instrument, round 1; automation deferred)
Clipping/overlap and the target page count are verified by **rendering the two docx outputs and visually
inspecting them** — an owner/human judgment. There is **no automated instrument** for pixel layout/page count in
this repo (F7: no puppeteer/playwright/libreoffice; `mammoth` extracts text only; jsdom cannot measure layout —
[[measurement-instruments]]).
- **Instrument:** MANUAL real-render inspection by the owner/verify seat on the actual .docx files. A jsdom or
  text-level test asserting "one page / no clipping" is a **false clean** and must not be written as if it
  discharges this AC.
- **RED on HEAD:** N/A — **INVALID-until-rendered**, not green. It is an owner-judged check, not an automated pass.
- **Failure direction:** claiming layout correctness from a non-rendering test is the trap; this AC is flagged
  manual precisely so that claim is never made.

### AC-13 (step 8) — Delivery distinguishes the two files AND surfaces the unresolved-qualification flags
Delivery presents the two files clearly distinguished (AC-7) and surfaces, to the user, the step-6 list of
posting requirements that **wording alone cannot resolve** — explicit unresolved-qualification flags — so the
user is not left with a false impression of fit. (The prose "explain major tailoring choices" and the
teaching-CL tail are DEFERRED — §2.)
- **Instrument (NEW):** assert the delivery surface shows two distinct files and renders the unresolved-quals
  list produced by step 6; a draft with a known genuine gap surfaces that gap.
- **RED on HEAD:** yes.
- **Failure direction:** silently omitting the unresolved-quals flags lets the user submit believing they
  qualify; surfacing them is the passing direction.

### AC-16 — App-vs-chat REMOVAL ac: the level gives what a chat LLM does not
The level delivers three things a user pasting the posting into a chat LLM does not get, each pinned by a

- **Instrument:** coverage guarantee — removing any one of the three advantage-classes fails its named AC above

- **RED on HEAD:** yes (via its underlying ACs).
- **Failure direction:** if any of the three could be removed with every test still green, the feature has
  collapsed to chat-equivalent and this AC has failed.

### AC-17 — Non-regression: levels 1–5 and non-N105 runs are unchanged (guard)
