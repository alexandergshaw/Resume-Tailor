# N104 - EXPERIENCE design (seat 1c, round r1)

Backlog N104: a weakness summary of the generated resume/cover letter against the posting, plus a "regenerate to address these weaknesses" action, in the preview/edit modal. Binds to `docs/loop/N104.ac.r1.md` (9 ACs; AC-1/2/3/4 are the safety rows). REUSES the built presentation: `ReviewFlagsPanel`, `flagPresentation`, `reviewPresentation` (N103/N105), N103's `DocumentReviewSection` strip pattern, and the N105 Ideal band. Experience only: no source edited, no git writes, no structure re-opened. Where the experience needs something the AC or the structure does not give, it is listed in section 12 (AC deltas) or section 13 (plan inputs); the one genuine owner fork is section 11.

**Decisions at a glance**
1. **No new panel, no second verdict.** The weakness summary IS the live review of the text on screen: the N105 band on a fresh Ideal resume, the N103 strip's result everywhere else. N104 adds three things to it and nothing else: a class hint under each existing group, the document-level treatment of missing keywords (R-4), and the two new controls below (section 2).
2. **The two controls live in the existing N103 strip** (`DocumentReviewSection`, in the dialog's `resultBands` slot), not in a sibling panel: a **Regenerate row** after the result region, and a **"What regenerating changed" report** at the top of the result region. Dialog: 0 lines (978 of 980 stay 978). This answers AC I4 and replaces the structure seat's proposed `WeaknessSummaryPanel` with two small leaves inside the strip (section 11, reconciliation).
3. **Resolvable vs unqualified is already the panel's grouping.** Improve group = rewording can address; unresolved group = cannot be supplied by rewording; Confirm group = only the user can check. Each gets one plain hint sentence. No group other than Improve has any action (section 4). The AC's two-class split leaves the Confirm tier unclassified; the design adds it as a third, non-regenerable class (delta G-1).
4. **ONE regenerate action, secondary style.** "Regenerate to address weaknesses", outlined (Download .docx stays the single primary action). One click from a cold Ideal result; never a wizard, never a confirmation: the safety device is an **Undo**, not a dialog (section 5).
5. **Truthful framing is stated before the click, in the control's own caption**, in words that promise only what the gate delivers ("using only what your resume supports; anything it cannot support is set aside and listed, never added"), never "fill", "fix" or "guaranteed" (section 5.3).
6. **After-feedback is derived from the re-review and worded as what the checks flagged**: "No longer flagged / Still flagged / Newly flagged", with a line-count delta so closure-by-deletion is visible. The words "fixed", "addressed", "closed", "resolved", "ATS" and "score" are forbidden in this chrome (section 6).
7. **Engine reality.** The summary and Review button are identical on every engine. On an engine that cannot regenerate the row shows an info caption plus an in-modal **Switch to Gemini** button, because the top-bar remedy the N105 copy names is unreachable under a modal dialog (section 7).
8. **Announcements reuse the mount's existing N95 pair; ZERO new live regions.** A start cue is added because a regenerate is genuinely long (section 9).
9. **Owner fork (section 11):** whether regenerate is offered on level 1-5 jobs. The structure seat recommends yes (every job, via the gated chain); this seat recommends Ideal-built results only for slice 1, on experience grounds the structure doc does not weigh (lost Revise/Focus controls, discarded steering, a comparison that cannot be made, a posting-less "before").

## 2. Composition (brief items 1, 5; AC I4): what lives where

### 2.1 The surface, per tab and job kind

Strip DOM order (always): **(1)** the N103 review row (button + caption, unchanged) -> **(2)** the result region, with the **report at its top** when one exists -> **(3)** the **Regenerate row**. The Regenerate row follows the summary it acts on, so reading order is "what is weak, then what the button will do", and it sits OUTSIDE the 30vh scroll box so it is never scrolled out of view.

| Tab | Job kind | Review row | Band above | Regenerate row |
|---|---|---|---|---|
| resume | Ideal, text fresh (band live) | `Review resume` (-> "covered") | N105 band: the weakness summary | `ready` / `nothing-to-address` / `engine-cannot`, built from the BAND's review (no click needed) |
| resume | Ideal, edited or other version | `Review resume` runs a full review | band with its edited note, or hidden | `stale` until the user reviews again, then `ready` |
| resume | level 1-5 | `Review resume` | none | after a result exists: the one `unsupported-job` sentence; no button (fork F-1, option b) |
| cover | any | `Review cover letter` | none | after a result exists: the one `unsupported-scope` sentence |
| hypothetical | Ideal | `Review hypothetical resume` | HYPOTHETICAL banner (always first) | none (nothing is sent from it) |
| email | any | none | none | none |

The band keeps its own groups, notes and footer UNCHANGED (its 36-combination state function and tests stay as they are). It is the summary on a fresh Ideal tab; the strip never repeats it.

## 3. The weakness summary display (brief item 1)

### 3.1 Source: exactly one live review per text version

A pure helper (plan input UXW-1, `lib/review/`) returns the review that describes the text on screen, normalised to one shape `{flags, unresolvedQualifications, verdictKind, missingChecks, checkedChecks, engineMode, lineCount, inputs}`:
- Ideal tab with the band fresh and coverage usable -> the band's `ideal.review` (inputs: real material true; posting true iff `postingAnalysis.requirements` is non-empty);
- otherwise the strip's own `runDocumentReview` outcome, while its reviewed text equals the text on screen;
- otherwise NONE (nothing is known, so no Regenerate row).

Both sources go through `classifyWeaknesses` (structure) and nothing else. The helper never mints spans, never runs a detector, and never mixes the two sources for one text version (the existing `covered` rule already guarantees there is one).

### 3.2 What the user reads (unchanged chrome, plus three additions)

Headline, "Checked / Not fully checked", the partial notice, the shared summary line and the group list are the shipped N103/N105 output. Coverage honesty is therefore INHERITED, not re-decided: a mechanical-only review reads "Partial review - mechanical checks only." and the clean sentence is licensed in exactly one combination (`verdictKind === COMPLETE`, fresh, no findings, non-empty, both inputs given). Today `verdictKind` is never COMPLETE on real input, so clean copy is unreachable and the Regenerate row and report must never be the first place a reassuring sentence appears (section 6.4).

Three additions to the existing view:
1. **Class hints** (4.2).
2. **Missing keywords are document-level** (4.3).
3. **The posting-compared line** (3.3).

### 3.3 The posting-compared line (grounding made visible)

The subject header already reads "Reviewed {label} - {n} lines". Append, from the strip's own `request.posting.requirements.length` (no reviewer change): ", compared with {k} posting requirements" when `inputs.posting` is true. When it is false, the shipped N103 sentence ("No job posting was available, so keywords were not matched.") stays as the notice AND the Regenerate row stays absent (the class split cannot be made without the posting and the real material; see 5.2 `needs-material` and the `unsupported-job` state). Why: a user must be able to tell "9 requirements compared, none missing" from "nothing was compared", and a vacuous keyword pass is exactly the false comfort the feature exists to avoid. A zero is never printed: with no posting the clause is simply absent.

### 3.4 Honest summary states (each is rendered, none is clean)

| Situation | What shows | Regenerate row |
|---|---|---|
| Partial review, findings (today's norm) | shipped partial headline + notice + groups | per 5.2 |
| Partial review, no findings | shipped partial headline; no groups; no zero counts | `nothing-to-address` (never "all addressed") |
| Posting not available | shipped notice; keyword item absent from Checked; unresolved group hidden if real material is also absent | `needs-material` or `unsupported-job` |
| Real resume file not available | shipped notice; unresolved group hidden | `needs-material` |
| Empty document | shipped `empty` state | none |
| Review failed to run | shipped `failed` state | none |
| Stale (text edited since the review) | shipped stale note over the earlier list | `stale` |

## 4. Resolvable-by-wording vs genuinely-unqualified (brief item 2; AC-2)

### 4.1 The mapping (derived, no new classifier)

| Class | Reviewer output | Existing group | Regenerate | Never |
|---|---|---|---|---|
| **Rewording can address** | `missing-keyword` (requirement NOT in `unresolvedQualifications`), `vague-unsupported`, `repetition` | "Could be stronger" (Improve) | acts here, only here | presented as certain: it is a presumption the re-review tests |
| **Only you can check** | `unsupported-authority`, `unverifiable-metric`, `consistency`, `employer-plausibility` | "Confirm before you send" | leaves alone | a regenerate must never "fix" an unverifiable figure by changing the number: that IS the fabrication |
| **Your materials do not support it** | `unresolvedQualifications` | "Requirements your resume cannot meet by rewording" | leaves open, always reported open after | filled, even truthfully worded; moved to "No longer flagged" |

The classification is `classifyWeaknesses(outcome)` (structure); the presentation of it is the three existing groups. `weaknessSteering` receives the first class only (AC-2).

### 4.2 Class hints: one sentence under each title, always true, never about the button

Added as data in `PANEL_COPY` and rendered by `ReviewFlagsPanel` only when it is passed `classHints` (default none, so the N105 band's DOM is unchanged unless the caller opts in; the strip result opts in always; the band opts in when the Regenerate row is present for it, plan input UXW-4).

| Group | Hint (exact) |
|---|---|
| Could be stronger | Rewording can address these. |
| Confirm before you send | Only you can check these - they depend on what is true of you. |
| Requirements your resume cannot meet by rewording | (existing) Rewording cannot supply these - they need real experience or a different story. |

The hints describe the class, not the control, so they stay true on every engine, every job kind and when no Regenerate row exists. The Regenerate caption (5.3) points at the groups by their visible titles, built from the same `PANEL_COPY` constants so a renamed title follows.

### 4.3 Missing keywords are document-level (precondition; the shared R-4 defect)

A `missing-keyword` flag is a statement about the whole document, but it is anchored on line 1 (U6). Under the shipped panel, 5 missing terms render as ONE row quoting the first bullet with five labels, which reads "this first bullet lacks Kubernetes, Terraform, ...". For N104 (and for the regenerate's "closed" claim) that is wrong. Requirement (N104-UX-3): **no missing-keyword item is ever shown as a finding about a specific line.** Mechanism is the plan's call (N103's two options stand: the join emits an empty `excerpt` for that category AND `groupFlagsBySpan` stops merging an excerpt-less flag into a quoted row, giving one row per term with the "From the posting: ..." evidence; do NOT re-anchor). Document-level rows sort before line-level rows inside "Could be stronger". Instrument: a fixture with a clean first line and one missing posting keyword; the keyword's row contains no blockquote of that line; mutant: restore the anchor quote -> red.

### 4.4 Never presented as fillable

- No row in the Confirm group or the unresolved group has any button (the group-subtree button census finds only `CappedList`'s "Show all / Show fewer").
- The Regenerate caption names these groups as left alone (5.3). After a run they stay listed under "Still listed in the review" (6.2), never under "No longer flagged".
- If the user truly has the experience, the remedy is real, stated once in the report when unqualified requirements remain: "If you do have that experience, add it to your resume and run again." (the N105 thin-corpus precedent). It is a sentence, not a control.

## 5. The Regenerate control (brief item 3; AC-1, AC-5, AC-6)

### 5.1 The control and the click path

One outlined button after the result region: **"Regenerate to address weaknesses"** (K1). One click runs the whole gated regenerate with defaults; nothing is asked first (no engine pick, no scope picker, no confirmation). After a report exists the same node reads "Regenerate again".

| Task | Today (no feature) | With N104 |
|---|---|---|
| Fix wording gaps on a fresh Ideal result | copy resume + posting into a chat, ask for gaps, ask for a rewrite, hand-audit every new line for invented claims, re-paste and reformat in Word: 6+ actions per application | open the preview (existing) -> **1 click**; the comparison is on screen |
| After editing the text | repeat the paste | **Review again (1) + Regenerate (1)** |
| Engine is not Gemini | n/a | **Switch to Gemini (1) + Regenerate (1)** |
| Take it back | re-find your old text | **Undo regenerate (1)** |
| Ordinary (level 1-5) job, option b | n/a | summary (Review, 1 click); regenerate not offered, one sentence says why |

### 5.2 The state machine (pure, total, in `lib/review/regenerateAvailability.js`)

Inputs: tab kind, job kind (has an Ideal block), `idealLevelEnabled()`, engine, live-review source (3.1) and its freshness, `inputs.posting` / `inputs.realMaterial`, resolvable / unqualified / confirm counts, in-flight (per job), report present. Output: ONE state. Unknown or unusable input falls to the not-ready side, never to `ready`.

| State | Condition | Visible (below the row) | Button | If activated (keyboard/AT) | Announced |
|---|---|---|---|---|---|
| `hidden` | no live review, or hypothetical/email tab | nothing | absent | n/a | nothing |
| `unsupported-scope` | cover tab, a result exists | K9 | absent | n/a | nothing (static) |
| `unsupported-job` | resume tab, level 1-5 job, a result exists (option b) | K8 | absent | n/a | nothing (static) |
| `needs-material` | real material or posting not available, so the class split cannot be made | K7 | `aria-disabled`, dimmed | reason announced | polite K7 |
| `stale` | live review no longer describes the text on screen | K6 | `aria-disabled`, dimmed | reason announced | polite "Review again before regenerating." |
| `engine-cannot` | engine is embedded or external | K10 (info tone) + **Switch to Gemini** | `aria-disabled`, dimmed | reason announced | polite "Regenerating needs the Gemini AI engine." |
| `nothing-to-address` | resolvable count is 0 | K5 (+ tail) | `aria-disabled`, dimmed | reason announced | polite K5 |
| `ready` | all of the above clear, resolvable count > 0 | K2 (+ tail, + K12 when hand-edited) | enabled | runs | polite start cue (K20a) |
| `running` | a regenerate for THIS job is in flight | K4 | `aria-disabled`, `aria-busy`, "Regenerating..." | no-op | none further |
| `failed` | last run could not finish | K11 above the row, persistent | enabled again | runs | alert, persistent (K20c) |

Precedence (first match wins): hidden, unsupported-scope, unsupported-job, running, engine-cannot, needs-material, stale, nothing-to-address, ready. `failed` is an overlay on `ready` (or `nothing-to-address`'s absence), not a precedence rung.

Never `disabled` (focus must not be dropped; reasons are visible captions linked by `aria-describedby`, `[[mui-a11y-traps]]` 8). No state renders a zero, "none", or any clean phrase.

### 5.3 The truthful framing, as copy (K2)

The promise must be exactly as strong as the gate: the gate verifies that every factual token traces to the user's own material and sets aside what it cannot support; it does not verify truth in the world and it does not judge recruiter value. So the caption promises the mechanism, never the outcome.

> Rewrites the lines under **Could be stronger** using only what your resume supports. Anything it cannot support is set aside and listed, never added. [tail]

Tail, built from the live counts and omitted when both are zero: "Requirements your resume cannot meet by rewording, and items to confirm, are left as they are."

Rules (checkable, one sweep over K1-K20): no "fill", "fix", "guarantee", "verified", "true", "safe", "100%", "ATS", "score", "optimize"; the group title is quoted from `PANEL_COPY.improveTitle`; the caption is the button's `aria-describedby` target and is non-empty.

### 5.4 In flight

- The button keeps its place, becomes `aria-disabled="true"` + `aria-busy="true"`, reads "Regenerating..." with a `CircularProgress size={14}` start icon (the Review button's idiom). No fake progress bar and no duration (chain latency is unmeasured; the N105 UX stated none).
- The caption becomes K4: "Regenerating - this runs several AI passes and takes longer than a review. Your resume stays as it is until the new one is ready." The last sentence is a requirement on the structure, not copy: **nothing on screen changes until the run completes**.
- The Review button is also unavailable while a regenerate runs (a review of a text about to be replaced is noise); the dialog's existing `busy` treatment of editing controls is reused if the regenerate sets it (plan input UXW-5), otherwise the editor is not locked and the hand-edit rule in 5.6 covers the race.

### 5.5 Not spammable (the guard must outlive the strip)

N103's guard is a component-local ref, adequate for a review that resolves in one tick. A regenerate takes many seconds and the strip is KEYED by job and scope (`review-{job}-{scope}`): switching tabs or reopening the dialog remounts it. Requirement (N104-UX-6): **the in-flight flag is per job, owned above the strip** (a mount-level ref/entry flag keyed by job id), checked and set synchronously in the handler, so (a) two clicks in one tick start ONE run, (b) a remounted strip reads `running`, never an enabled button, (c) a result that lands after a tab switch or a close is written to its own job, never rendered over another document. Re-activation while running is a no-op, not a queue. No cancel in slice 1 (parity with Revise/Generate); closing the dialog does not cancel.

### 5.6 Atomic, and what it replaces

- **Atomic.** A refused or failed run leaves the text, the band, the review, any earlier report and the HYPOTHETICAL byte-identical. K11 (alert, persistent): "The regenerate could not finish, so your resume is unchanged. Try again." It leads with the state, not "Error/Failed/Sorry". No automatic retry (a paid call is never auto-retried).
- **It replaces the text on screen**, including hand edits. Because replacement is the destructive direction, the design supplies reversal instead of a confirmation: the pre-run text, review, band state and hypothetical are retained for the session and **Undo regenerate** (6.5) restores them in one click. When the text on screen is hand-edited (`editedForScope` or saved html), K12 is added to the caption: "You have edited this resume. Regenerating replaces your edits; Undo regenerate brings them back until you close this window." If the structure also persists the prior text as a saved version (signed in, position row), K12 may drop its tail; that is 1d's call (UXW-6).
- **Tab-scoped.** Only the Application-ready document changes. The HYPOTHETICAL tab and its file are untouched; if the chain rebuilds it anyway (U8), the report says so (K17) and Undo restores it. UX prefers reusing the existing hypothetical (a stable reference document, fewer AI passes); that is a plan input (UXW-7).

## 6. After-regenerate feedback: closed and still-open (brief item 4; AC-4)

### 6.1 Shape: a compact report at the top of the strip's result region

Section `aria-label="What regenerating changed"`, inside the same 30vh scroll box as the result (so the strip's total height stays bounded; the Regenerate row stays outside it), above the NEW review. On the Ideal tab the new review is the band above; the strip's own region holds the report. Session-only, kept per job beside the `ideal` block so it survives a tab switch and a close-and-reopen within the session (the regenerate's effect persists in the text, so its explanation must live as long); cleared by the next regenerate, by a non-Ideal run on the job, or by Undo.

### 6.2 Contents, derived ONLY from the re-review

Computed by `compareReviewGaps` (structure) over the review the user saw (before) and the re-review of the shipped text (after); rendered by `lib/review/regenerateReportView.js` into rows. The report claims nothing a re-review does not show.

| Part | Source | Copy |
|---|---|---|
| Headline | counts of the before-set | closed > 0: "Regenerated. {a} of {b} suggestions are no longer flagged." closed = 0: "Regenerated. The {b} suggestions are still flagged." unchanged text: K13c |
| **No longer flagged** | identity-stable gaps (missing keywords, by key) absent from the re-review; plus category deltas | rows (below) |
| **Still flagged** | identity-stable gaps present in both | rows; hint "The new version did not change these." |
| **Newly flagged** | gaps in the re-review with no counterpart before, and net category increases | hint "These were not flagged in the version before." |
| Still listed in the review | the AFTER counts of unresolved requirements and Confirm-tier items | "Still listed in the review: {m} requirements your resume cannot meet by rewording, {c} to confirm." (each part omitted at 0) |
| Length | `lineCount` before/after, shown when different | "Length: {x} lines before, {y} now." |
| Set aside | `ideal.counts` of the new run | "{r} lines were set aside for you to verify and {l} left out because your resume does not support them. They are listed in the review." (each part omitted at 0) |
| Unqualified remedy | only when `m > 0` | "If you do have that experience, add it to your resume and run again." |

Row formats (text tags carry the status; colour is never the only signal):
- **Missing keywords (identity-based):** `Posting keyword missing - "{term}"` under the group that applies. The term is shown only when the structure can supply it from the reviewer's own flag (UXW-9); the display never parses prose it cannot key.
- **Line-level categories (vague, repetition) are NOT identity-based** (a rewritten line has no stable id; AC delta G-2): "Vague wording: {x} before, {y} now." / "Repeated phrasing: no longer flagged (was {x})." Never "this line was fixed".

### 6.3 Why "closed" is not the word, and what is forbidden

"Closed", "addressed", "fixed", "resolved" and "filled" claim an outcome the checker cannot measure: it detects the PRESENCE of a posting term, not where or how it landed. A keyword satisfied by a bare skills-list append clears the flag and an ATS filter and gives a recruiter nothing; the detector cannot see placement. So the report says only what the checks flagged: "no longer flagged / still flagged / newly flagged".

Forbidden in the report, the Regenerate row and their announcements (chrome only; `[data-quoted]` terms and requirement text excluded): the shipped N103 forbidden list, plus `/\b(fixed|resolved|addressed|closed|filled)\b/i`, `/all (clear|done|good)/i`, `/nothing left/i`, `/\bATS\b/`, `/\bscore\b/i`, `/optimi[sz]/i`. Positive control: a fixture that legitimately prints "no longer flagged" must pass, and a planted "fixed" must fail, or the sweep proves nothing.

### 6.4 Never clean, never a zero

The report appears only after a re-review exists and is always followed by the shipped review (partial notice included). Its footer states the scope of the claim (K18): "This compares what the checks that ran flagged. It is not a verdict on the whole resume." The report never renders a zero count or "none": an empty part is omitted, so an all-closed run reads "{b} of {b} suggestions are no longer flagged" over a still-partial review, not "nothing left".

### 6.5 Undo and the unchanged case

- **Undo regenerate** (button in the report footer, visible text = name): one click restores the pre-run text, review, band state and hypothetical; the report is replaced by one line K19 ("Restored the version from before the regenerate."); **focus moves to the Regenerate button** (the Undo button unmounts with the report; a control that vanishes under focus drops the keyboard user to `<body>`). Polite announce K20e. The affordance is withdrawn the instant it is used (the N93 rule), so a second click cannot double-revert. One level only; further history is the saved-versions mechanism where it exists.
- **Unchanged text.** If the regenerated text equals the previous (normalised), nothing is replaced and the report reads K13c: "Regenerated, but the text came out the same, so nothing changed. Your resume may not support more wording for these." No Undo (nothing to undo).

### 8.2 `[[mui-a11y-traps]]`
No `Tooltip` anywhere in the new leaves (visible text is the name); no `Select`; no MUI `Alert`; carets and icons `aria-hidden`; reasons are visible sibling captions linked by `aria-describedby`, asserted to resolve to a non-empty node (trap 8); label-in-name asserted with the name resolver (trap 3) for "Regenerate to address weaknesses", "Regenerating...", "Regenerate again", "Switch to Gemini", "Undo regenerate". ### 8.3 Domain notes the copy and structure must respect
- **Keyword flag is the one users are most tempted to "fix" by inserting an untrue skill**; recruiters probe skills in the screen and titles in the reference check. Hence no per-keyword fix action, no "insert" affordance, and a gate-bounded regenerate (a keyword that IS in the user's material may be surfaced; one that is not stays under the unresolved group).
- **A mechanical check is not an ATS score.** No chrome may imply the app measured how an applicant tracking system will rank the resume; the sweep forbids "ATS", "score", "optimize".
- **Closure by deletion is real**: removing a vague line clears its flag and costs the user content on a one-page resume. The Length line and the Set-aside line exist to make that visible.
- **Cover letters**: a keyword-coverage check on prose coaches padding; the strip already withholds the posting for covers. Regenerate is resume-only in slice 1 (the gated chain is resume-only, OC-1).

## 10. Persistence, feature log, app-vs-chat

### 10.1 What persists
Nothing is written to storage. The Regenerate result changes the job's entry exactly as an Ideal run does (one writer, not a parallel path, so Download, Drive, Combine and the chip all see the new text: [[download-rebuild-formatting]]). The report and the Undo snapshot live on the entry beside `ideal` for the session. After a reload the new resume remains (a persisted resume, as for Ideal) and the report, band and Undo are gone, exactly as the N105 band is (the footer sentence already says so).

### 10.2 Feature log (`[[feature-logs]]`)
One `DECISION_LEDGER` entry `weakness-regenerate`, bound to the module that owns the single `recordDecision(` call. Fields (closed list, counts and codes only): `reason` (canned: regenerated, unchanged, nothing-to-address, engine-cannot, needs-material, stale, failed, undone), `engine`, `suggestionsBefore`, `suggestionsAfter`, `newlyFlagged`, `unqualifiedCount`, `confirmCount`, `coverageComplete`. Outcomes: acted, refused, failed. NEVER resume text, requirement text, keywords, excerpts, labels, company or title. **Visible download**: the shared `ActivityLogButton` ("Download activity log") in the report footer, where the log is interesting (right after a run); it costs no density when no report exists, and the shared button stays in Settings > Admin tools. This is a deliberate reading of "clearly visible" (the directive forbids burying it in a menu); the orchestrator may flip it to menu-only as N103 did (non-fork). The N103 `document-review` entry is not in the tree (U13); N104 does not depend on it.

### 10.3 App-vs-chat claim (`[[app-vs-chat]]`)
**Class: Guaranteed (earned, mechanism named), with Corpus as the enabling input.**
**What the user does instead, and what it costs:** pastes the posting and the resume into a chat for each application, asks for weaknesses and then for a rewrite, and audits every new line for an invented number, title or scope by hand; a model asked to "fill the weaknesses" will do exactly that. Per application: the re-paste, the manual truth audit, the reformat on the template, and the one time a plausible invention goes out.
**What the button gives:** (1) a summary whose every row quotes or names something that provably exists in THEIR document and posting, split by who can resolve it; (2) a regenerate that cannot add what their resume does not support, with the unsupported lines listed rather than hidden; (3) a before/after report computed by re-running the review, never claimed; (4) nothing re-pasted: posting, resume and template already live in the app.
**Removal map:** drop the K2 framing or the set-aside line -> N104-UX-5/14 red; render engine output un-gated -> AC-1 red; claim closure without the re-review, or list an unqualified requirement as "no longer flagged" -> N104-UX-11/13 red; drop Undo -> N104-UX-15 red.

## 12. AC deltas (AC seat to adopt or reject; the design stands on the stricter reading)

- **G-1 (SAFETY).** AC-2 names two classes (resolvable, genuinely-unqualified) and leaves the Confirm tier (unsupported-authority, unverifiable-metric, consistency, employer-plausibility) classless. A regenerate that "addresses" an unverifiable figure by changing it is the fabrication AC-1 forbids. Add: the regenerate never targets Confirm-tier flags either; they are a third class, "only you can check". The design already shows it as such (4.1).
- **G-2.** AC-4 says a gap is closed when "that flag" is gone. That is sound only for identity-stable gaps (missing keywords by requirement id and message, unresolved requirements by id). Draft-anchored flags (vague, repetition) have no identity across a rewritten draft; the report must show them as category count deltas. The structure seat already agrees; fold it into the AC so a test cannot assert a per-line "closed".
- **G-3.** The AC never says which scopes the regenerate covers. The gated chain is resume-only (OC-1); a truthful cover-letter regenerate does not exist. State "resume only" in AC-1/AC-6, so the card's "resume/cover letter" is not read as covering both.
- **G-4.** The card says "missing/under-weighted requirements". No detector measures weight (presence only). Copy says "missing", never "under-weighted"; AC-3 grounding should say so.
- **G-5.** AC-4 needs a comparability precondition: closure may be reported only when before and after used the same posting requirements and the same real material (the structure doc states it; the AC should too).
- **G-6.** "Closure by deletion": AC-4's "measurably closes" is satisfiable by deleting the offending lines. Add a visibility requirement (the Length and Set-aside lines) so a smaller resume cannot read as a better one.
