## 1. The level signal (AC-1) — distinct request field, NEVER the aggressiveness clamp

**Decision.** N105 is NOT represented as `aggressiveness=6`. P8 proves the route clamps any value >5 to 5 at route.js:111, so a slider raised to 6 would be silently absorbed into level-5 "Strong" — the exact AC-1 failure direction. N105 must travel as a **distinct request signal** the route branches on before `parseAggressiveness` runs.

**Structure.**
- New FormData field, recommend `tailorMode` with values `"standard"` (default/absent) | `"ideal"` (N105). The route reads it immediately after engine selection (route.js ~311), before the resume generation at :409.
- The selector UI (1c owns the surface) presents N105 as the TOP entry of the one existing tailoring-level selector. When N105 is chosen, the client sends `tailorMode=ideal` and leaves `aggressiveness` at whatever it was (the N105 branch ignores it). When any of levels 1-5 is chosen, `tailorMode` is absent/`standard` and today's path runs byte-for-byte (AC-17).
- **Centralize the level→request mapping in a new lib module** `lib/tailor/tailorLevel.js` (pure): `levelToRequestFields(level) → { aggressiveness?, tailorMode? }` and a label/ordering table. Reason: page.js is at 3008/3015 (7-line headroom, P11/P12-adjacent) and has 4+ FormData-append sites (P11); a per-site inline change risks the ceiling and drift. One helper keeps each call site a one-liner and gives the selector a single ordering source.

**Checkable invariant (AC-1):** selecting the top option produces a request the route routes to the N105 pipeline, and `parseAggressiveness` does NOT determine the branch. Apply to a diff: the N105 branch predicate reads `tailorMode`, never a numeric comparison against aggressiveness; grep shows no `aggressiveness >= 6` or `=== 6` anywhere.

**Alternatives rejected.** (a) Slider max=6 — rejected: clamp at route.js:111 absorbs it (AC-1 failure). (b) Overload an existing engine name — rejected: engine axis is orthogonal (P7); N105 must run on gemini/external, so it cannot BE an engine.

## 2. Engine capability + embedded refusal (AC-2, OD-2)

**Decision.** N105 is a new ENGINE CAPABILITY, declared on the engine object, so the registry (P7) stays the single source of which engines support it. Embedded declares it unsupported and the route refuses honestly with zero artifact.

**Contract — new engine method (call shape is the I2/3b research item, NOT designed here):**
```
engine.tailorIdeal(args) =>
  {
    postingAnalysis,              // step 1 extraction (AC-8), posting-grounded
    keywordMap,                   // step 2 prioritized map (AC-9), posting-grounded
```

## 3. The N105 pipeline + the two-output shape (AC-7) + truthfulness boundary (AC-4)

**Decision.** A new server-side orchestrator module owns steps 1-8; the engine owns only generation (step 1-5 drafting); the truthfulness gate and the shared reviewer sit DOWNSTREAM of the engine inside the orchestrator.

**New module** `lib/llm/ideal/idealPipeline.js` (orchestrator, server-only). Flow:
1. `engine.tailorIdeal(args)` → `{postingAnalysis, keywordMap, hypothetical, applicationReadyCandidate}`.
2. **Truthfulness gate** (§4) runs on `applicationReadyCandidate` against the real-material corpus → final `applicationReady` (`{kept, droppedOrFlagged}`). This placement is the AC-4 boundary: the gate is OUTSIDE the engine, so it governs output from ANY engine and cannot be bypassed by an engine that fabricates (P9 is the embedded instance; the gate is engine-agnostic).
3. **Shared reviewer** (§6) runs over BOTH drafts → flags + `unresolvedQualifications`.
4. Assemble the two-output response.

**Two-output response shape (AC-7).** The route's response gains a `ideal` block, distinct from today's single-resume fields:
```
ideal: {
  hypothetical:    { result, resultLines, docxB64?, title, isHypothetical: true  },
  applicationReady:{ result, resultLines, docxB64?, title, isHypothetical: false },
  review:          { flags: [...], unresolvedQualifications: [...] },   // AC-5/AC-13
  postingAnalysis, keywordMap,                                          // AC-8/AC-9 (assertable)
}
```
Two distinct files (AC-7): each carries its own `title`/filename base and its own `isHypothetical` identity (§5). The application-ready is the submittable file and carries NO marker; the hypothetical carries the marker on filename + UI.

**Persistence / migration.** First slice keeps `ideal` as RESPONSE/session state only — the hiring-email precedent (route.js:536 "session state only … no table"). **No migration in the first slice.** If re-download-after-reload is later wanted, a new table (e.g. `generated_ideal_resumes`) with a timestamp later than P14's `20260930000000` is required — FLAGGED, not built. Rationale: avoids schema-drift and the migration-edit hazard; the two safety ACs (AC-3/AC-4) do not require persistence.

## 4. Truthfulness gate (AC-4) — placement, shape, and the real-material source (I1)

**New module** `lib/llm/ideal/applicationReadyGate.js` (PURE, server + node-testable). Runs downstream of the engine (§3 step 2).

**Contract:**
```
applicationReadyGate({
  candidateSpans: [{ id, text, section, contextKey }],   // app-MINTED ids; one bullet-sized line each (span discipline)
  realMaterial:  { spans: [{ id, text, contextKey }], chronology: ChronologySource },
}) => {
  kept:    [{ id, text }],                                // SUPPORTED + member; retained (liveness)
  flagged: [{ id, text, reason: "unsupported"|"membership", flag: "unverified — confirm before use" }],
  dropped: [{ id, text, reason }],
}
```
- **SUPPORT** (AC-4.1): a candidate span is supported iff every FACTUAL TOKEN (quantity/metric, named entity, authority/seniority/leadership assertion) traces to EXACTLY ONE real-material span (never a union, never a document — span discipline). Pure reword/strengthen with NO new factual token PASSES.
- **MEMBERSHIP** (AC-4.2): the supporting span must share the candidate span's `contextKey` (employer/project/role). A real metric under employer A cannot support a bullet under employer B.
- **LIVENESS** (AC-4 F-4): at least one supported span per `contextKey` present in real material MUST appear in `kept`. The gate must not degrade to drop-everything.

**Real-material source (I1 resolved — P13).** There is NO server-authoritative structured chronology. The corpus the gate evaluates against is, in precedence:
1. **The uploaded résumé text** (`resumeText`, always present — required at route.js:324), decomposed into bullet-sized spans with app-minted ids. This is the always-available, user-authored real-material source and the primary corpus.
2. **Optional client-supplied structured chronology** — the `EMPLOYMENT`/`EDUCATION` localStorage lists (P13), when the client includes them in the N105 request, provide `contextKey` partitioning (employer/date/degree). They are a BONUS structured surface, never required and never authoritative (per-device, user-editable).

`ChronologySource` is therefore: `{ employers: [{contextKey, name, startDate?, endDate?}], education: [...] } | null`, assembled client-side from localStorage and/or `parseEmployment.js` over the résumé, and sent in the request. When null, `contextKey` falls back to résumé-section grouping.

**This is the I1 mapping seam.** AC-10's "exact match to stored records" compares the application-ready's employers/dates/degrees against this corpus (résumé-parsed + optional structured entries), NOT against a server store (none exists). The invariant — no employer/date/degree invented or altered relative to the user's own résumé — is checkable regardless of whether structured entries are present.

**Checkable invariant (AC-4):** the gate's four fixture rows (must-drop fabrication, must-drop cross-`contextKey`, must-survive pure reword, must-keep supported) all evaluate against exactly one span each; failable-count and keepable-count both >0. Apply to a diff: no gate path compares a candidate token against a UNION of spans or the whole document.

## 5. I3 — the filename-marker choke point + combine/set-default refusal (AC-3, SAFETY)

**The problem precisely.** The marker must appear in the FILENAME of every named egress and be impossible to drop per call-site (AC-3; N101 proved a whole-file census false-clean). P1-P6 map the egresses:
- `resolveDocumentFileName` (docx.js:68) is the common resolver for: the 3 download paths (via buildDownloadArgs → docx.js:749-750), copy-filename (P3), and Drive-save's no-override branch (P4). **BUT** two gaps leak: (i) `resolveDocumentFileName`'s own override branch returns the user's typed name verbatim (P2) — a hypothetical downloaded under a user-typed name would lose the marker; (ii) `driveDocName`'s override branch (P4, driveNames.js:28-29) bypasses `resolveDocumentFileName` entirely.
- `downloadCombinedDocuments` (P5) and `saveDefaultTemplate` (P6) never read the title at all — they are markerless-adoption paths.

**Decision — two structural controls:**

**(A) Force the marker; make override-stripping impossible.** The hypothetical is a distinct document identity carried in the DATA (recommend a new DOCX scope `hypothetical` in `documentScopes.js`, so it inherits tab/preview/download/copy/version wiring — P12 — with `DOCX_SCOPES` gating; the application-ready maps to the existing `resume` scope). Add a single pure forcing function in docx.js:
```
export const HYPOTHETICAL_TOKEN = "HYPOTHETICAL";   // 1b picks case → UPPERCASE, as a bracketed suffix "… [HYPOTHETICAL].docx"
export function ensureHypotheticalMarker(name, isHypothetical) // appends token before extension iff isHypothetical && token absent
```
- `resolveDocumentFileName` takes the identity and applies `ensureHypotheticalMarker` to its FINAL return (after BOTH the override and builder branches), so neither a user override nor the builder can emit a markerless name for the hypothetical.
- `driveDocName` applies the SAME `ensureHypotheticalMarker` to BOTH its branches (its override branch currently bypasses the resolver — this is the one existing egress the design must change to close the leak).
- Preferred form per AC-3 rule-4: mint the token into the hypothetical's canonical `title`/filename base AT GENERATION (the `ideal.hypothetical.title` in §3), so egresses that read the title inherit it; the forcing function is the backstop that makes dropping it impossible even when an egress reconstructs from jobTitle/company (Drive's no-override branch) or honors a user override.

**(B) Refuse the markerless-adoption paths.** The hypothetical scope is EXCLUDED from the combine scope set (combine iterates `DOCX_SCOPES`; the hypothetical must not be in the combined set) and the `SetDefaultTemplateControl` is not mounted / is disabled for the hypothetical scope (`VALID_KINDS` in defaultTemplateStore stays `["resume","cover"]` — no `hypothetical` kind, so `saveDefaultTemplate` already refuses an unknown kind at :70). Defense in depth: both handlers assert-refuse a hypothetical input so a future wiring mistake red-tests rather than silently adopting fabricated bytes under a markerless name.

**Checkable invariant (AC-3), per call-site:** produce the hypothetical; drive EACH named egress (docx.js:725/809/842, Drive save, copy-filename) through its REAL filename resolution; assert the resolved name contains `HYPOTHETICAL` at each one separately. Per-site mutant: drop the identity/forcing at ONE egress → only that egress's assertion reds. Census asserts the forcing call NEAR each named egress (N101 G1/G2 per-call-site form), not whole-file. Refusal: combine and set-default with a hypothetical input must refuse (no markerless submittable artifact derivable).

**Alternatives rejected.** Mint-into-title alone (no forcing function) — rejected: Drive's no-override branch reconstructs from jobTitle/company (ignores the title) and both override branches bypass it, so the title mint is necessary but not sufficient; the forcing function on the final return is what makes it impossible.

## 6. Shared adversarial-reviewer CONTRACT (OD-3, AC-5/AC-6) — N105 CONSUMES, does not build

OD-3: the reviewer is a SEPARATE foundational chunk built first. This section defines ONLY the contract N105's step-6 needs — the deliverable to scope that chunk. Internals are out of N105 scope.

```
reviewDocuments({
  drafts: [
    { kind: "hypothetical",     spans: [{ id, text, section, contextKey }], authorityReference: "internal-consistency" },
    { kind: "applicationReady", spans: [{ id, text, section, contextKey }], authorityReference: "user-material" },
  ],
  posting: { requirements: [{ id, text }] },          // step-1 extraction, each a sized posting span (AC-8)
  realMaterial: { spans: [{ id, text, contextKey }] } | null,   // null when authorityReference !== "user-material"
}) => {
  flags: [{
    draftKind,                 // which draft
    spanId,                    // the app-MINTED id of the offending span (EXACTLY ONE span; never a union)
    category: "missing-keyword" | "vague-unsupported" | "repetition"
            | "unverifiable-metric" | "employer-plausibility" | "consistency"
            | "unsupported-authority",
    evidenceSpanId?,           // the single posting/real-material span it was checked against
    message,
  }],
  unresolvedQualifications: [{ requirementId, text }],  // posting reqs WORDING ALONE cannot resolve (genuine gaps), distinct from phrasing gaps — AC-13 consumes this
}
```

**Load-bearing contract properties N105 depends on (each checkable):**
1. **Span identity is the APP's, not the reviewer's.** The reviewer operates over app-minted span ids and never re-chunks; containment/consistency is evaluated against EXACTLY ONE span (span discipline, [[loop-traps-spec]]).
2. **Authority reference is SPLIT PER DRAFT** (AC-5, F-2 fix): `authorityReference="user-material"` for application-ready (unsupported authority = seniority/leadership/scope not evidenced in real material); `authorityReference="internal-consistency"` for hypothetical (authority checked against posting-plausibility + internal date/title/seniority coherence, NOT user material). A strong-but-internally-coherent hypothetical authority claim produces NO flag; an internally-incoherent one does.
3. **`unverifiable-metric` applies to BOTH drafts** (verifiability is draft-internal, independent of `authorityReference`).
4. **`unresolvedQualifications`** is the step-6 wording-cannot-resolve list AC-13 surfaces to the user.
5. **Pure/deterministic over inputs, no side effects.** It is THE single document-weakness analyzer; N105 must import it and add none of its own (AC-6).

**AC-6 checkable invariant:** a structural census over N105's OWN additions shows `idealPipeline.js` imports the shared reviewer module and introduces no second document-weakness analyzer (canaried against the known shared export); a behavioral check drives it over both drafts.

**N105's dependency on the foundational chunk:** AC-6 cannot go green until the shared reviewer lands. Sequencing flag for the plan (§10).
