# N95 — Acceptance criteria (round 1)

**Feature (owner request, verbatim, 2026-09-29):** "the working and loading indicators and animations for moving facts in sentences forward and back and the process of confirming a fact need to be a lot more smooth."

**What this is.** A perceived-smoothness pass over two interactions on the N92 inserted-fact review strip. It changes *how each interaction feeds back to the user*, not *what any control does*. No control is added, removed, or repurposed; no fact-positioning, smoothing, or dedupe logic changes. The two interactions:

1. **MOVE** — moving an inserted fact one sentence forward/back (`InsertedFactsStrip.js:77-94` back/forward `IconButton`s → `onMove` at `DocumentPreviewMount.js:421-424` → `moveInsertedFact` at `useCompanyResearch.js:635-697`).
2. **CONFIRM** — three sub-surfaces, in the owner's words "the process of confirming a fact":
   - **Smooth produce** — `handleSmooth` (`DocumentPreviewMount.js:348-363`) awaits `requestSmoothTransition` (`smoothTransition.js:191-260`), a POST to `/api/cover-fact-smooth` (LLM round-trip; the longest wait of all).
   - **Smooth apply** — `handleApplySmooth` (`:364-373`) awaits `confirmSmoothTransition` → `applySmoothedFact` (splice + upload + PUT). The Apply/Discard buttons live in `CoverFactSmoothConfirm.js:28-33`.
   - **Accept** — the `CompanyResearchDialog` "Insert into cover letter" action → `acceptFacts` (`useCompanyResearch.js:358`).

## Grounded state on HEAD (read 2026-09-29, cited file:line — verified this round unless marked CITED)

- `moveInsertedFact` (`useCompanyResearch.js:635-697`) sets **no** pending/busy flag of any kind. Confirmed by reading the whole function body. Contrast `acceptFacts:396`, which sets `companyResearch.busy = true`. **So a move has zero immediate feedback.**
- The move `IconButton`s' only `disabled` driver is the caller-precomputed `movability` map (`InsertedFactsStrip.js:80,89`), computed from `planMoveFact` dry-runs at render (`DocumentPreviewMount.js:388-394`). It does **not** change while an op is in flight. **So a move is fully spammable** — a second click launches a second `moveInsertedFact`, i.e. a second splice+PUT.
- The move async path is up to three IO operations: `resolveCoverEngineBytes` (may fetch the docx from Supabase storage) + `commitFactMove` = `applyCoverDocxEdits` (docx splice) + `uploadCoverDocx` (storage upload) + `fetch` PUT `/api/accepted-facts`.
- On move success, the preview updates via `setPreviewReloadKey((k) => k + 1)` (`:694`) — a **full body-model re-parse** (the function's own comment: "re-parses the body model"). This is the abrupt "jump"; there is no transition.
- No move outcome is announced to a screen reader — no `role=status`/live-region text change accompanies a move.
- `handleSmooth` awaits the LLM produce call with **no** pending indicator and **no** disable of the Smooth control → spammable, and the longest silent wait in the feature.
- `handleApplySmooth` awaits apply with **no** pending indicator; `CoverFactSmoothConfirm.js`'s Apply/Discard have **no** `disabled` prop → **Apply double-fires**.
- The accept flow's pending state **is drawn** (button label toggles to "Inserting…" and disables, `CompanyResearchDialog.js:364-377`) but is **not announced** — a disabled button's label change is not a live region. This is the N84 draw-not-announce class.

## Measurement reality (be honest)

jsdom does no layout, no real timing, no animation (see the `measurement-instruments` memory). **"Smooth", "animated", "no flicker", "no jump" are real-browser judgments the owner must make.** The criteria below are split into **TESTABLE** (falsifiable in jsdom/RTL) and **OWNER-JUDGED** (real-browser). No jsdom criterion pretends to measure animation quality; a criterion that asserted "the fact animates smoothly" would be a zero-power measurement and is deliberately absent.

## LOAD-BEARING DECISION — D-N95.1 (owner/design call; AC recommends)

**Optimistic-with-rollback vs pending-spinner, for the MOVE interaction.**

- **Recommendation: OPTIMISTIC-WITH-ROLLBACK for MOVE.** `planMoveFact` produces the final `lines`/`records` synchronously *before* any await (`moveInsertedFact:640`), so the on-screen result can appear on click and reconcile in the background. This is the smoothest result and the one the owner's wording points at. It preserves correctness because **the server write is unchanged** — `commitFactMove` still does the real byte-splice + PUT; only the client preview updates early. On failure, restore the captured pre-move snapshot exactly and record `fact-position`/`failed`/`save-failed` (already the enum/code at `:669` — no ledger change needed).
- **The SMOOTH produce and apply paths take a pending indicator regardless of D-N95.1.** Produce has no result to show optimistically (you cannot pre-render an LLM answer you do not have). Apply is concurrently being restructured by N93 (undo) — do not over-constrain its internals.
- **This is escalated, not decided here,** because optimistic UI is an outward-facing behavior change (a fact briefly shown at a position the server has not yet confirmed, and a visible snap-back on the rare failure). If the owner/1c prefers never to show an unconfirmed position, fall back to pending-spinner for MOVE too; the criteria are written to hold under either choice except where marked **[OPTIMISTIC-ONLY]**.

## Scope

**IN:** immediate feedback, double-fire prevention, honest failure recovery, and screen-reader announcement for the MOVE, SMOOTH-PRODUCE, SMOOTH-APPLY, and ACCEPT interactions; the composition/placement of that feedback within the existing strip; the decision above.

**OUT (explicit, so the design seat does not widen and the verifier does not file these as missing):**
- The faithfulness guards of smoothing (scope / added-token / confirm-before-persist) — N92 Wave 3, settled and unchanged here.
- Post-apply **undo** of a smoothing — that is **N93** (AC-B6); N95 must not implement it and must not assume it exists.
- The disabled-on-embedded Smooth control's **reason chip/tooltip** — that is **N94**'s UX note.
- Backgrounding generation/research latency — **N68** / the latency chunk (`useManualTailor.js`, `useDocumentPreview.js`).
- Any change to move byte-identity, sentence segmentation, offset invariants, dedupe, or what smoothing persists — **preserved as non-regression guards** (Group X), never edited.
- Adding motion to any surface other than the two interactions named.

## Criteria

Legend: **RED** = fails on HEAD today (verified how). **GUARD** = a non-regression criterion that passes today and must keep passing (buys no new coverage, guards against the smoothness work breaking correctness — said plainly per the seat rules). **IMPL-CHECK** = falsifiable against the implementation diff, not red-on-HEAD because the surface does not exist yet. **OWNER** = real-browser judgment, not falsifiable in jsdom.

### Group M — MOVE feedback

**AC-M1 (RED). A move shows a working indicator for the duration of its async op, and the indicator is gone once the op resolves (success or failure).**
Instrument: RTL render of the strip with `onMove` wired to `moveInsertedFact`, `fetch`/`commitFactMove` stubbed with a deferred promise; assert an in-flight marker (an `aria-busy="true"` on the fact's row or the triggered control, and/or a pending element with an accessible name) is present after click and absent after the promise settles both ways.
RED on HEAD: `moveInsertedFact` sets no pending state (verified, `:635-697`); nothing renders in-flight. Instrument would find no marker → fails.
Failure direction: the safe failing state is **indicator absent** (never a spinner that outlives the op — see AC-M4). A test that only checks "present after click" without "absent after settle" is insufficient; assert both.

**AC-M2 (RED). A second activation of a fact's move control while that fact's move is in flight does not launch a second move operation.**
Instrument: stub `moveInsertedFact` (or the underlying `fetch`) to count calls and hang; fire the control twice synchronously; assert exactly **one** `moveInsertedFact` call is dispatched for that fact.
RED on HEAD: no in-flight guard exists; `movability` (the only `disabled` driver) does not change during flight (`InsertedFactsStrip.js:80,89`) → a second click dispatches a second call → fails.
Prefer STRUCTURAL over disciplinary: the in-flight control should be *unable* to dispatch (disabled / guarded), not merely "should not be clicked". **The pending guard must be independent of `movability`** — `movability` legitimately recomputes under optimistic UI (the arrow's boundary state changes), so it cannot double as the in-flight guard.
Failure direction: safe failure is **refuse the second dispatch**. Launching two concurrent splice+PUTs against the same fact is the harm.

**AC-M3 (RED). A move's pending state is ANNOUNCED to assistive tech, not merely drawn.**
Instrument: assert the pending state is carried by a live region (`role=status`/`aria-live=polite`) whose **text changes** on move start (and clears/updates on settle), using the shipped `useCopyFeedback`/`AutoInsertFactsMessage` pattern. A region that mounts already carrying its text is not reliably announced (`answerStatus.js` header lesson) — the assertion must be on a **text change of an already-mounted region**, or a keyed-span mutation (the `CopyFeedback` `seq` idiom).
RED on HEAD: no announcement of a move exists → fails.
Guards against the N84 trap: any spinner glyph must either carry an accessible name or be `aria-hidden` with the announcement carried by the region — assert one of these; a bare unnamed `CircularProgress` fails.

**AC-M4 (RED, partial — see honesty note). A failed move clears the pending state, re-enables the control, and surfaces the reason honestly; it never spins forever.**
Instrument: stub the commit to reject / return `{ok:false, reason}`; assert (a) the pending indicator is removed, (b) the fact's move control is usable again, (c) the reason text appears in the strip's existing `role=alert` band (`InsertedFactsStrip.js:59-63`).
RED on HEAD: (c) **already works** today (`DocumentPreviewMount.js:422-423` → `setRemoveError` → alert) — so the error-surfacing half is **not** new. (a) and (b) are RED only in the sense that there is no pending state to clear and nothing gets disabled today; they become real obligations once AC-M1/AC-M2 add a pending state. Stated plainly: this criterion's *new* content is "the pending state and disable that M1/M2 introduce are correctly torn down on failure" — it is vacuous until M1/M2 exist, and must be authored as their teardown partner, not as standalone coverage.

**AC-M5 [OPTIMISTIC-ONLY] (IMPL-CHECK; conditional on D-N95.1 = optimistic). If optimistic UI is chosen, the on-screen fact position updates synchronously on click (before the async path resolves), and reconciles or rolls back on the server result; a rollback restores the exact pre-move `coverLetterResultLines` and `insertedFacts`.**
Instrument: stub the commit to hang, assert `tailoringMap[job].coverLetterResultLines`/`insertedFacts` already reflect `planMoveFact`'s `moved.lines`/`moved.records` before the promise settles; then resolve-failure and assert both arrays are byte-identical to the captured pre-move snapshot.
Not red-on-HEAD (the behavior does not exist and is only required if the decision selects it). If the decision is pending-spinner, this criterion is void and must be removed rather than left as dead coverage.
Failure direction: a rollback that restores *approximately* (e.g. drops a coalesced survivor's offset) is worse than no optimism — assert exact array equality, and pin it against the N81/N90 coalesced-offset class (a two-fact-same-paragraph fixture).

### Group S — CONFIRM: smooth produce + smooth apply

**AC-S1 (RED). The smooth PRODUCE step (LLM round-trip) shows a working indicator from click until the candidate/rejection/failure returns, and the Smooth control cannot launch a second produce while one is in flight.**
Instrument: stub `requestSmoothTransition`'s `fetch` with a deferred promise; assert a pending indicator appears on click and the Smooth control does not dispatch a second `requestSmoothTransition` on a second synchronous click; assert the indicator clears on `proposed`, `rejected`, `failed`, and `unavailable_embedded`.
RED on HEAD: `handleSmooth` (`DocumentPreviewMount.js:348-363`) awaits with no pending state and no disable → fails on both present-during and no-double-fire.
This is the highest-value gap: the longest wait in the feature with zero feedback today.

**AC-S2 (RED). The smooth APPLY step shows a working indicator while `applySmoothedFact` is in flight, and Apply cannot double-fire; Discard is likewise guarded against a second dispatch.**
Instrument: stub `applySmoothedFact` with a deferred promise; fire Apply twice synchronously; assert exactly one `applySmoothedFact` call and a pending indicator present until settle.
RED on HEAD: `CoverFactSmoothConfirm.js:28-33` Apply/Discard have no `disabled`/pending; `handleApplySmooth` awaits with no pending state → fails.
Coordination note (not a criterion): N93 is restructuring the apply path (`commitSmoothedFact.js`). The pending indicator must sit at the confirm-surface/handler layer (`DocumentPreviewMount`/`CoverFactSmoothConfirm`), above the persist internals N93 owns, so the two chunks do not fight over the same lines.

**AC-S3 (RED). The smooth produce/apply pending state is ANNOUNCED via a live region (same rule and instrument as AC-M3).**
RED on HEAD: no announcement of either smooth step exists → fails.

**AC-S4 (GUARD). Discard remains a no-op on persistence and the confirm surface still shows nothing until a candidate is `proposed` (AC-B10/B11 preserved); adding a pending indicator to produce must not render the confirm surface before a candidate exists.**
Instrument: `CoverFactSmoothConfirm` returns `null` unless `candidate.status === "proposed"` (`:14`); assert a pending-produce state does not mount the before/after surface.
Passes today; a guard against the pending UI leaking the unconfirmed candidate early.

### Group C — composite surface (6b)

### Group O — OWNER-JUDGED (real-browser; NOT falsifiable in jsdom)

Named explicitly so the verifier does not file them as missing and no jsdom test pretends to cover them. These are for 1c/1e design and the owner's real-browser acceptance.

- **AC-O1 (OWNER).** The fact visibly transitions to its new position on a move rather than snapping abruptly.
- **AC-O2 (OWNER).** The preview does not flicker or reflow jarringly when a move updates it. **Root-cause note for 1b:** the abruptness is caused by `setPreviewReloadKey((k)=>k+1)` (`:694`) forcing a **full body re-parse**. Whether to keep that or replace it with a targeted in-place update is the real smoothness lever and a **1b structural decision** — surfaced here, not decided.
- **AC-O3 (OWNER).** The working indicators read as responsive and intentional (not a jarring flash for a sub-100ms op, not an absent indicator for a multi-second LLM wait). 1c should consider a short delay before showing a spinner for the fast MOVE path so a quick op does not flash.
- **AC-O4 (OWNER).** The fact's highlight follows it to the new position without a visible mismatch (`versionDiff.markInsertedFacts` matches per `(text, offset)`).
- **AC-O5 (OWNER / 1e+9b decision).** Any newly introduced CSS transition respects `prefers-reduced-motion`. **Constraint:** `prefers-reduced-motion` has **zero** guards in this repo today, and some files pin zero motion (`page.module.dupFlag.test.js:143`, `knowledgeSafety.sweep.test.js:142`), but `CopyFeedback.js:124` ships an unguarded 180ms opacity transition. So either (a) new motion is gated behind `@media (prefers-reduced-motion: reduce)` — the first such guard in the repo — or (b) 1e/9b explicitly rules a sub-200ms opacity fade exempt on the `CopyFeedback` precedent. This is a decision, checkable once made.
