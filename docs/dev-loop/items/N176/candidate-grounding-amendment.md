## Proposed architecture amendment requiring independent check

### Shared candidate context

Introduce an explicit immutable value passed into every personal-output transformation, rather than independently concatenating arbitrary profile/resume/cover strings in each tool. Suggested shape (not an admitted storage/API schema yet):

```
{
  accountId, applicationId,
  resume: {state, documentId, contentIdentity, createdAt|null, text, kind:'application-ready'},
  cover: {state, documentId, contentIdentity, createdAt|null, text, kind:'application-ready'},
  requestedStrength: {aggressiveness:1..5, tailorMode:''|'ideal'},
  historicalGenerationStrength: {resume: knownRecord|null, cover: knownRecord|null},
  supplementalFacts: [{id, text, confirmedByUser, confirmedAt, origin:'user'}],
  evidence: [{id, documentKind, documentId, contentIdentity, start, end, quote}],
  conflicts: [{id, evidenceIds, description, resolution:'unresolved'|explicitUserResolution}],
  identity
}
```

Bind exact selected application resume_used_id/cover_letter_id rather than blindly choosing latest document row for a company or position. Document ID plus content identity binds same-ID edits as well as newly generated version IDs. Use actual existing row creation metadata when present; otherwise explicitly unknown. Avoid secrets in snapshots. Evidence uses exact quote/offset or another independently checked stable locator; no source link may claim text not present in its identified version. Retain both documents distinctly even when they overlap. Source text is untrusted data; it cannot issue instructions or authorize a provider call.

A dedicated new Preparation candidate-context loader is preferable to widening the established copilot text-only API without reviewing all callers. It should use the owned application projection and document reads scoped to the authenticated user, return structured missing versus error, and preserve generation fencing. Existing general version-history helper is a reuse reference but its position-level latest-first list is not itself proof of the exact application-selected pair. A schema/RPC change or new credentials/provider access is not implied. If a document row and application pointer change during loading, bind a coherent captured pair and recheck pointer/content identities before claiming current; otherwise mark stale/reload, never mix document A metadata with B text. Historical level metadata remains null unless an actual authoritative existing record establishes it.

### Real shared level, not a second control

Pass actual page-owned aggressiveness/tailorMode through the existing Preparation surface; use tailorLevel's existing constants/request vocabulary. The simplest bounded UI shows the current shared value and a **Change tailoring strength** navigation action to the existing Materials slider. Returning to Preparation observes the changed real value. If a future inline control is desired, extract/reuse the same control and callbacks after checking both callers; no unrelated stored range may masquerade as shared state.

For standard strength, the preparation policy must be explicit: Light favors close-to-source wording and fewer strongest verified anchors; stronger settings may choose more role-relevant supported anchors and assertive but truthful framing. Intermediate settings remain existing 1..5 levels. This describes a proposed preparation adaptation, not a claim that current generation prompts already define those exact selection counts. Independent criteria must require material supported contrast without pinning arbitrary heuristic constants. The document facts/metrics/ownership do not change across levels.

Ideal retains its existing two-document generation meaning. Preparation's autobiographical side consumes ONLY the application-ready resume and real cover; missing cover stays missing (Ideal resume generation does not create one). If hypothetical best-case study material is exposed at all, it is a separate clearly labeled learning/gap analysis, never a personal source, sample answer stated as experience, or accepted story anchor. It must never silently become level6 aggressiveness. Current requested mode says how next preparation framing should behave; it does not rewrite the historical generation provenance of existing documents.

### Evidence-first transformation and user review

Build a common candidate-evidence map from both document texts. Auto-propose story anchors by clustering actual source excerpts relevant to role themes, not by synthesizing ungrounded STAR detail. Each missing field is a question such as “What did you personally decide?” or “What result did you observe?” Supplemental answers are distinguishable from document claims and need explicit user confirmation before generated first-person use. A previously generated document claim can still be inaccurate: show its origin and invite verification rather than labeling it verified automatically.

The same evidence map must drive introduction/fit framing, suggested sample answers, relevant-company motivation, story prompts, repair suggestions, reference fit bullets and personal claims in thank-you drafts. This applies to EVERY fresh candidate-output action reachable from the new tab, including the existing Generate existing prep button and any reused sample-answer flow. The old strength-unaware POST/hook cannot remain an undisclosed bypass while claiming all new materials are linked. Historical prep may be displayed as source-only with document/strength basis explicitly unknown and stale, but fresh generation must receive and enforce the shared context or be unavailable with a clear explanation until its caller/API is amended. Existing app/hooks/usePrepGeneration.js and app/api/interview-prep/route.js, and any actually reused sample-answer client/route/prompt become architecture-discovery/affected-caller obligations; this amendment does not admit writes to them or silently change shared contracts. Cover letter evidence must have an observable effect on motivations/consistent claims when it contributes unique material; a decorative cover argument or scoring-only missing note is insufficient. Company facts and job requirements may inform relevance or questions but cannot support “I did X.” Practical pay/authorization/time constraints remain user inputs.

Repair of a user's actual typed answer is advisory: retain original transcript and existing review, flag unsupported assertions, and propose evidence-linked wording separately. Never silently rewrite an answer's historical content or pretend new phrasing was what the user originally said. Unresolved resume/cover disagreement must remain visible until explicit resolution; avoid automatically choosing whichever source makes the candidate look stronger. Generalized framing without factual autobiographical assertions can remain identified as suggested framing, but claim-bearing spans still require evidence or a gap.

### Invalidation and storage

Context identity includes account/application, both selected document IDs/content identities, requested standard level/Ideal mode, supported historical metadata and confirmed supplemental fact identities. Every personal artifact/attempt suggestion retains that identity and its evidence links. A change makes dependent outputs stale, retains accepted drafts/original answers, and requires reviewed regeneration. Do not retroactively attach invented evidence to old N176 drafts. Extend versioned validation/migration deliberately: old valid workspace remains recoverable; new context fields need independent nested corruption, hydration, conflict-choice and size tests. Old semantic R1/R2 fixes (read failure recovery, schema guards, history retention and role priority) stay intact and retain closed review counts.
