## Completion controls

Construct an otherwise complete item with accepted current final/verification/whole-change artifacts, all existing gate evidence and no outstanding ownership. Its shipped transition must reject only for missing live verification. A historical shipped marker with those same prerequisites but no live report must yield pending in manual handoff and blocked in supervisor scheduling. A raw snapshot without freshly observed candidate/artifacts cannot prove completion. Existing state migration can normalize an absent live map to empty but cannot create a pass.

Positive control adds same-item live-verification assignment/artifact/report imported through the public event lifecycle and separately clean-reviewed by another instance AND context. All current candidate fields, canonical target, known deployment binding, passing covered steps, immutable evidence and reconciled cleanup qualify. Shipped succeeds; fresh handoff passes locally; root overall completion still additionally requires remote Git delivery. Public CLI record/import acceptance must exercise real serialized bytes and a process/store reload, not only direct applyEvent calls.

## Negative families and expected direction

- Identity/ownership: wrong item artifact, wrong activity kind, worker mismatch, nonexistent assignment, report self-review, checker sharing author context, reporter sharing implementation identity/context, foreign-item evidence where ownership is required: reject record or completion, never silently select the foreign report.
- Freshness: change each candidate dimension separately (source revision/tree, policy, environment, tools); mutate report source, supersede accepted report, invalidate activity/artifact or binding evidence: completion becomes pending/rejected even if shipped already. Missing fresh context fails closed. Restore exact original bytes to prove recovery.
- Integrity: replace event report JSON while keeping imported artifact hash, tamper stored report blob, delete attachment, tamper attachment, symlink evidence out of immutable store: rejected record/load/completion. Valid immutable attachments remain positive controls. No unchecked raw filesystem reference can stand in for imported evidence.
- Trusted target: localhost, another origin, credentials, alternate protocol, query redirect, fragments, lookalike host and absent URL must fail; exact trusted canonical URL passes. A separate same-origin affected route cannot redefine the trusted deployment target.
- Deployment binding: unknown/empty revision, missing binding references, empty method, pending deployment observation or unrelated evidence fail eligibility. A successful Vercel status or Git equality alone never substitutes for browser steps.
- Coverage: zero steps, empty expected/observed text, failed/pending step, unknown or omitted criterion mapping, mapping to missing/nonpassing step or a trivial unrelated flow fail. Explicit justified nonlive criteria must be represented. Smoke requires engine/docs-only scope statement; product behavior cannot use smoke as an unexplained bypass. Exact all-required live mappings form the positive control.
- Time: future observation finish, finish before start, invalid/infinite/noninteger clock, and unbounded timestamp records fail; fresh bounded observations pass. Candidate stability remains necessary even if clocks are valid.
- Cleanup: pending/unreconciled disposable data fails. Complete cleanup with evidence passes; not-needed requires clear no-created-data rationale. Existing user records must never be deleted as a test control.
- Historical/caller boundaries: direct shipped event, manual handoff, root handoff, supervisor shipped fast path all share fail-closed semantics. Owner residuals, absent optional legacy field, unknown flags and test fixture switches cannot waive mandatory live evidence. Git-only loop:delivery remains repository publication proof and explicitly labels that limitation.

## Mutation oracle

Use an isolated temporary copy and current source identity. Record baseline rejection test PASS with otherwise-complete item missing only live acceptance. Introduce one exact guard-bypass mutation; confirm changed bytes/hash; rerun the named negative test and require its assertion to FAIL because shipment/completion becomes possible. Restore exact original bytes and require PASS. Preserve raw outputs and subprocess exit codes. If the chosen mutation never reaches the asserted boundary, it is not a successful control. Never mutate shared checkout during concurrent activity.
