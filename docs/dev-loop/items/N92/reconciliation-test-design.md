## Compatibility and failure controls

- Native unedited splice: real ZIP edit+successful upload+PUT+immediate preview/download remain correct. This is a positive unchanged-path canary.
- Native upload failure with actual spliced candidate: upload returns failure/null path, accepted-facts PUT succeeds; operation must remain successful with fresh session bytes and null path. Immediate preview/download contains updated text. Assert stored path null and no claim that reloading recovers an upload that never existed. A test demanding refusal/durable path here is incorrect.
- Native successful empty/null candidate: line/template rebuild uses current lines and clears stale sources. Do not force native source into the strict-original contract.
- Strict recovered original missing/corrupt/foreign/wrong-kind/pending marker, and required-upload failure: no accepted-facts PUT or replacement client success, original source/edited identity retained. Existing real writer tests may be reused after checking current bytes and assertions; add client-state/refusal integration where absent.
- Accepted-facts409/network/refusal after upload: Move restores only captured cover fields while preserving unrelated updates introduced during pending transport; Smooth and refused Undo retain their previous accepted state and fail visibly/ledger-wise. An uploaded orphan is a named existing residual, not permission to delete it or mark the operation successful.
- Proposal-only, Discard, move boundary and invalid locator controls: no unauthorized PUT/upload/client-success; downloaded semantic content stays unchanged. Assert original displayed proposal is what Apply persists; response generation must not recur on Apply/Undo/reload.
- Harmless field control: add/update unrelated job or entry metadata during pending commit, then ensure success/rollback leaves it intact; this distinguishes a cover-only merge from wholesale state replacement.
